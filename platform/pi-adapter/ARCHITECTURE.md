# pi-adapter architecture

The only shipped code that imports pi packages (`@earendil-works/*`, `typebox`). It imports nothing else from the repo, and `types/` imports only other `types/` files. Everything outside the folder reaches it through `index.ts`: the contract types of `types/`, split by domain (`Host`, the main session as an extension sees it, the intersection of the `ToolHost`, `PromptHost`, `LifecycleHost`, `MessagingHost`, `EntryHost` and `SessionHost` capabilities plus `ui`, a `HostUi` composed of `NoticeUi`, `ClipboardUi`, `OverlayUi`, `WidgetUi`, `EditorUi`, `KeysUi` and `style`; `AgentRuntime`, spawning and reading agent sessions; `ThemeToken`, the union of `PaintToken`, `StatusToken`, `MessageToken` (pi's `customMessageLabel`, `customMessageText` and `userMessageText`) and `ThinkingToken`, the last derived from `THINKING_LEVELS`), plus `createPiExtension`, `settleWithin`, `resolveModel`, `textMetrics` and the row geometry (`PAD`, `CHILD_COLUMN`, `CHILD_MARK`, `isBlankLine`, `childLead`, in `ui/row-layout.ts`). The folder holds everything in pi's domain (model resolution, runtime phases, usage math, row layout, prompt sections), even where a file imports no pi package directly, so that extensions see one adapter surface; `child/model-resolver.ts` and `runtime/settle-within.ts` are examples. It knows nothing about any extension: each entry passes its root, its namespace for custom entries and the source directories child sessions must not load.

## Startup

1. pi loads each entry listed in `package.json` (`pi.extensions`). Each default export is the factory `createPiExtension(boot, { root, namespace, childExclude, skillInventory })` returns; every extension builds it through `createManagedExtension` (see the [extension-manager architecture](../extension-manager/ARCHITECTURE.md)), which supplies the `boot`.
2. The factory returns immediately when it runs inside an agent session (an `AsyncLocalStorage` scope set while children load), so no extension boots inside an agent.
3. Otherwise it builds a `Host` over pi's `ExtensionAPI` and an `AgentRuntime` over pi's SDK, then calls `boot(host, runtime, paths)`.

## Host

Behaviour worth knowing:

- The adapter keeps the latest pi `ExtensionContext`, captured on every event, tool call and command. On `session_shutdown` every registered handler runs even if an earlier one throws, the context is then always dropped, and the first error is rethrown afterwards so pi reports it.
- `Host.session()` always returns a `SessionInfo`; outside a live session (before `session_start`, after `session_shutdown`) it throws, and so do `readEntries`/`sessionUsage` without a file argument. Every other Host call that needs the context (UI, `publish`, `appendEntry`, `dispatchCommand`, `isIdle`) is then a no-op. Code that can run after its own shutdown (spending, for reports arriving while other extensions shut down) must not call `session()`.
- `onSessionStart(info)`: `SessionInfo.parentSession` is the session header's parent, filled on every start and by `Host.session()`; `SessionInfo.created` is true when pi started the session by `new` or `fork` (`/new`, `/fork`, `/clone`, a handoff switch) and false for resume, startup and reload, kept from the last `session_start` for `Host.session()`. Code that must act once per lineage step (spending's inheritance) reads the parent only when `created`; code that must see the parent on every start (the subagents registry) reads it regardless. `readEntries(customType, file?)` and `sessionUsage(file?)` read the live session, or another session file when one is given. `onCompact` fires after pi compacts the main session.
- pi builds a fresh extension instance and event bus for every session (`/new`, `/resume`, `/fork`, `/reload`) and fires `session_start` once per instance, except in RPC mode where it fires twice. State therefore starts empty in each instance: handlers that only reset state at session start and unsubscribe handles at shutdown are not needed. Settings are the exception below.
- `onIdle` is pi's `agent_settled` and passes `{ aborted }`, true when the run that just settled was aborted; pi awaits the extension handlers before its session listeners see the event, after the run's last `message_end`, so an entry appended there follows the run's last message in the transcript and in the session file (pinned by the conformance case `emits an entry appended in an extension's agent_settled after the run's last message`); `onTurnEnd` passes a `ContextSnapshot` (tokens, window, percent).
- `onAssistantStart` fires at each assistant `message_start` (subagents counts a wake as answered once the model starts a reply after it). `onAssistantEnd` passes `{ toolCalls, final }` of each assistant message. `final` says the run ends with this message as far as pi tells before drawing it: no tool calls and a `stop` stop (an `error` stop may be retried, a recoverable `length` stop makes pi compact and retry in the same run, an `aborted` one is no answer), nothing in pi's steering or follow-up queues (`ctx.hasPendingMessages()`, which counts only user text) and no custom follow-up an adapter host queued in this session that has not started yet (`runtime/follow-ups.ts`: a record on `globalThis` keyed by session id, filled when `sendMessage`/`sendHiddenMessage` queue a follow-up, emptied per message at the custom `message_start` that delivers it, each message object taken once however many hosts see it, and cleared at `agent_settled`, after which pi has drained or dropped its queue, and at `session_shutdown`). A custom follow-up queued by a third-party extension, or a continuation pi decides at a turn boundary, is not seen, so `final` can be true for a reply the run goes past. The handlers run synchronously inside the adapter's own `message_end` listener, before it returns, and pi runs extension handlers before its own listeners draw and store the message, so an entry appended there lands above the message (pinned by `emits and stores an entry appended in an extension's message_end before that message`; a custom follow-up starting after the reply that would end the run is pinned by `starts a custom follow-up queued during a run after the reply that would end it`).
- `onPhase` is computed by `phase.ts` from `turn_start`, `message_update`, `message_end`, `tool_execution_*` (top-level only), `agent_end`, `agent_settled`; `idle` fires after `onIdle`. A phase is emitted only when it changes; the adapter keeps the ids of the running top-level tools so the phase stays `tool` until the last one ends.
- `editor.ts` installs one `HostEditor` subclass when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `onEmptyEditorDown`, `onEmptyEditorEscape`, `captureEditorKeys`) is used; the frame is optional; keys reach the hooks only while the editor has focus. `onEmptyEditorEscape` fires on pi's interrupt key (matched by keybinding, so a rebound key works) when the editor is empty, pi is idle and no autocomplete shows; a handler returns true to consume the key, otherwise pi gets it. The frame's `decorate(lines, layout, paint, theme)` gets the border paint and a `ThemeLike` over `ctx.ui.theme` of the adapter copy that set the frame (no theme, no frame). Every extension of the package shares that editor: pi loads each extension with its own module cache, so the frame, hooks and installed factory live in one record on `globalThis` (`Symbol.for("pi-extensions.editor-hooks")`, like `child-scope.ts`). Hooks registered while the extension loads are kept and the adapter installs the editor at `session_start`; at `session_shutdown` each adapter copy drops what it registered. It removes the editor again when no frame and no hook remain. The record also holds the ↑ input history, kept by `history.ts`, which each `HostEditor` takes as one collaborator: it points pi's private `history` array at the shared one, so prompts survive pi rebuilding the editor on `/reload` and `/new`, and on `/resume` and `/fork` the copy that installs the editor seeds it with the session's user messages, as pi does for its own editor.
- `onModelSelect` is pi's `model_select` with source `set` (the selector's Enter or Ctrl+S, `/model <name>`, login, RPC, an extension's `setModel`) or `cycle` (Ctrl+P); it passes the opaque `provider/id` ref, and `restore` is ignored, as is the model a handoff restores (below). pi emits it only when the model actually changes, never at startup or resume, and never in a child session, where no adapter extension boots. `saveDefaultModel(ref)` (`runtime/default-model.ts`) does what pi's Ctrl+S does: it creates a file `SettingsManager` over the session's cwd and agent dir, calls `setDefaultModelAndProvider`, adds the ref to `enabledModels` when the session has a model scope without it and `enabledModels` is non-empty and lacks it (case-insensitive), and awaits `flush()`. pi's save re-reads the file under its lock and writes only the fields changed, so the other keys survive and the running pi's later saves of other keys keep the value. It resolves to the global-scope errors pi recorded, joined, or `undefined`; the running pi's own in-memory settings (the selector's `default` badge) see the change from the next session (`/new`, `/resume`, restart).
- `onThinkingSelect` is pi's `thinking_level_select`, emitted whenever the session's level actually changes: the thinking selector's Enter or Ctrl+S, Shift+Tab, `/thinking <level>`, `pi.setThinkingLevel`, and the reset a model switch applies. Pi sets the startup or resumed level without it, and no adapter extension boots in a child session. It passes the opaque, already clamped level, and drops two kinds of event. The reset inside a switch: pi assigns the new model before it resets the level and emits `model_select` after (pinned in `conformance.test.ts`), so an event whose `ctx.model` is not the model the host last saw at `session_start` or `model_select` belongs to a switch not yet reported. A superseded event: its level is no longer `pi.getThinkingLevel()`, and the later change has its own event. This holds however other extensions' async handlers interleave, since both checks read live state. `setThinkingLevel(level)` is `pi.setThinkingLevel` for a valid level (pi clamps it and emits the event when it changes). `saveDefaultThinkingLevel(level)` writes it as `defaultThinkingLevel` through the same file `SettingsManager` path as `saveDefaultModel` (`setDefaultThinkingLevel`, as the thinking selector's Ctrl+S does), and resolves to pi's global-scope errors, or to an error text for a string that is not a thinking level.
- `onDialog` is pi's `ui_prompt_start/end` (outermost dialog only; overlays are `custom`). `HostUi.onKeyPress` observes terminal input without consuming it.
- `onInput(handler)` is pi's `input` event, which pi fires for every prompt before it expands prompt templates and skills, idle or as a mid-run steer or follow-up; extension commands run before it and never reach it. The handler gets a `UserInput` (`{ text, images, source }`: `images` as `{ data, mimeType }`, `source` `interactive`, `rpc` or `extension`) and returns true to consume it; the first handler that does ends the round and the adapter answers pi `handled`, so nothing is sent; otherwise `continue`. `HostUi.getEditorText` and `setEditorText` read and replace the editor text in any mode with a UI (session-limits puts kept messages back there); they stay next to the other `EditorUi` methods in `ui/create-ui.ts` rather than in `editor/input.ts`, whose methods work in tui mode only.
- `dispatchCommand` delivers immediately when idle, otherwise as a follow-up (pi counts a run as busy from its submission, and still runs an extension command at once). `sendMessage(message)` sends a displayed custom message: during a run a follow-up with `triggerTurn`, otherwise the held path below, whose message starts a run itself; pi emits `before_agent_start` for such runs, so `setMainPrompt` applies. `sendHiddenMessage` takes the same path with `display: false`, so nothing is rendered. `newSession` takes a required `fill` thunk instead of the seed (required), follow-ups and editor text (both optional), and calls it inside pi's `withSession`, after pi has awaited the old session's shutdown handlers, so what the caller gathers until then (messages the user typed during the switch) still arrives. It passes the seed's `details` along and appends the seed, always plain text, without a turn; with `continueWithSeed` it sends the seed with `triggerTurn` instead, so the seed starts the new session's first run, and does not await it (pi resolves that send only when the run settles); a rejected send shows a warning. `followUps` (`UserMessage`s, text and images, as a content array) are sent after the seed with pi's `sendUserMessage`, one after another, as follow-ups with template expansion: pi marks the seed's run active synchronously, so they queue behind it and pi expands a `/template` or `/skill:x` (only when the whole text starts with `/name`) in the new session; without a run the first starts one. Pi delivers each queued follow-up as its own user message with its own turn (its default `one-at-a-time` follow-up mode; `all` would put them in one turn as separate messages), never merged, and the chat shows each as pi's own user message; like pi's own queued follow-ups their images skip the resize pi applies to the prompt that starts a run (pinned by `delivers follow-ups queued behind the seed's run as user messages in order, one turn each`). `editorText` is put in the new session's editor before the seed. A failed follow-up shows a warning. Pi emits `session_start` and awaits its handlers before it calls `withSession`, so that run starts on the kept model. With `keepSelection` it writes a `pi-adapter:kept-selection` entry (`{ provider, id, thinking }` of the current session) into the new session through pi's `setup`, before `session_start`; on that `session_start` (reason `new`) the first adapter host to see the entry sets the model and then the thinking level, which pi clamps to the model, before any `onSessionStart` handler runs. Before setting the model it records a restored-selection marker for the session on `globalThis` (`{ model, thinking, applied }`; after the thinking level it stores the level pi applied and `applied: true`; a failed `setModel` removes it). Every host filters by value against that marker, not by timing, since pi awaits each `model_select` listener but fires `thinking_level_select` without awaiting it: `onModelSelect` skips a ref equal to the marker's model and removes the marker on any other ref; `onThinkingSelect`, while the session is on the marker's model, skips every level unless the marker is applied, the level differs from the stored one and is pi's current level (a later choice, which removes the marker), so the reset level of the restore's model switch and the kept level never reach the handlers. The release needs the event's level to be pi's current level when the adapter's listener runs, so if a non-adapter listener that awaits I/O is registered before every adapter host and the user changes the level twice (away and back to the restored level) within one microtask chain, the return is not saved; TUI keypresses are separate macrotasks, so this does not occur in practice. `session_shutdown` drops the marker and the claim. Nothing is saved as pi's default, and model-default's handlers see neither value. A model that is gone or has no credentials leaves pi's default in place and shows a warning. While pi is busy without a run (a compaction) the message is held until idle; a run starting meanwhile takes the held messages as follow-ups; several messages sent in one pass go out as next-turn messages behind the first, which starts one run for all of them.
- `AgentRuntime.skillCatalog()` lists the available skills as `{ name, description, scope, path }`, `scope` being `project`, `user` or `temporary`; `skillNames()` is the same list by name: where skill names come from (agent files, overrides, `/agents setup`, `/agents create`). `sessionSkillNames()` is the main session's loaded skill commands, read live from `getCommands()` (settings exclusions applied): the main session's effective skill set, and what `skills: all` resolves to when the main session is the caller. The inventory (`skills.ts`) is the main session's loaded skill commands first (`--skill` paths, `resources_discover` additions), then, under names not already taken, every skill pi's default discovery finds for the main cwd and agent dir: pi's `DefaultPackageManager.resolve` with missing packages skipped (never installed), over a settings manager whose storage reads the user and project settings files without a lock, drops writes and strips the `!` and `-` entries of their `skills` arrays (so those exclusions apply to the main session only; plain entries, globs and `+` includes stay, as do other resource types and package filters), its enabled skill paths (auto-discovered skill folders mapped to their `SKILL.md` as pi's resource loader does; packages already give `SKILL.md` files) and loaded by `loadSkills` (`includeDefaults: false`). Nothing is written; the project's `.pi/skills` and `.agents/skills` count only when it is trusted. Skills with `disableModelInvocation` are included; the loader's diagnostics (collisions) are dropped. A loaded skill's scope is its command's `sourceInfo.scope`. A discovered skill's scope is the `metadata.scope` of the resolved resource that holds its file (the most specific one), since `loadSkills` with explicit paths marks most of them `temporary`; with no such resource it is `project` under the cwd, else `user`. So `.agents/skills` in the project or its ancestors, `.pi/skills` and the project settings' entries and packages are `project`; the agent dir, `~/.agents/skills` and the user settings' entries are `user`. An extension built with `createPiExtension(…, { skillInventory: true })` (subagents only) scans in a `session_start` handler registered before the host's, so the scan ends before any start handler (and the definitions load) runs; every session start (pi's `/reload` included) scans again. A failed scan is not caught: pi's runner reports a throwing `session_start` handler as an extension error and runs the remaining handlers. Before the first scan, during and after a failed one and in other extensions, the inventory is the loaded skill commands alone. The main session keeps whatever skills pi gives it; the discovered part of the inventory does not depend on them (only the loaded part does). The adapter's `sessionSkillFiles(pi)` reads the loaded skill commands; the runtime gets them as `ParentSource.sessionSkillFiles` and the inventory as `ParentSource.inventorySkillFiles`. `AgentRuntime.availableModels()` (`model-catalog.ts`) is the model catalogue for `/agents setup`: every model of pi's registry whose provider has configured credentials, as `provider/id` with its context window, input and output price and the thinking levels it accepts (pi-ai's `getSupportedThinkingLevels`: `off` alone for a model without reasoning; `xhigh` and `max` only when the model maps them), sorted by ref; credentials are checked once per provider. `AgentRuntime.reserveCodemodeWorkers(agentSessions)` (`codemode.ts`) sizes pi's process-wide codemode worker cap, which every in-process agent shares: it sets `PI_CODEMODE_MAX_WORKERS` to `agentSessions` plus two spare workers (the main session, and a cancelled worker that is still exiting) unless the value was set by someone else, recognises the value it wrote last through a `globalThis` marker shared by every adapter copy (so `/reload` re-applies it rather than taking it for a user value), never changes a value it did not write (an invalid one counts as unset), and returns a `CodemodeShortfall` (`setting`, `workers`, `wanted`) when such a value is below the wanted count, otherwise `undefined`.
- `setMainPrompt` replaces pi's default prompt in `before_agent_start` and re-adds the `tools`, `rules` and `docs` sections pi would otherwise drop (`main-prompt.ts`). Only the subagents `run-agent` plugin calls it, so the main prompt is replaced only when that plugin is enabled.
- `ToolSpec` and overlay/widget factories are plain-text contracts; the adapter converts them to pi tools and TUI components. UI calls degrade to no-ops outside TUI mode. The `ThemeLike` every renderer receives carries `width(text)`, `truncate(text, cols)` and `wrap(text, cols)`, pi-tui's `visibleWidth`, `truncateToWidth(text, cols, "...")` (pi's own ASCII ellipsis, the one every pi tool renderer cuts with) and `wrapTextWithAnsi` (`textMetrics` in `theme-bridge.ts`; plain text comes back plain, the resets pi wraps around the ellipsis are stripped; `wrap` keeps at least one column), so the extensions measure, cut and wrap text by the rule the adapter cuts their lines with (`fitLines` in `theme-bridge.ts`, used for widgets, overlays, forms and entry renderers). `ThemeToken` is the subset of pi's theme colour names the extensions paint with (`piColor` passes a token through unchanged, typed so that every token must be a pi colour): the status colours (`accent`, `muted`, `dim`, `success`, `warning`, `error`, `text`), and `thinkingOff` through `thinkingMax`, pi's thinking-level colours of the same names (an extension maps `Host.thinkingLevel()` to its token itself; `/context` leaves `thinkingMax` unused so red there only means failure). `inverse(text)` is pi's `Theme.inverse`; `panels` is false when `getBgAnsi("toolSuccessBg")` is the bare default background `\x1b[49m` (pi's system theme without a terminal colour report), so renderers can fall back from background panels to foreground colour and inverse. `bg(token, text)` paints a background by `BgToken`: `added`, `removed` and `userMessage` are pi's `toolSuccessBg`, `toolErrorBg` and `userMessageBg` (the last with `userMessageText` lets an entry look like pi's user message), `addedWord` and `removedWord` those colours mixed 40% toward `toolDiffAdded` and `toolDiffRemoved` (pi-tui's `mixColors` over `Theme.colors`, applied with `Theme.style(text, { bg })`).
- `ToolSpec` also carries pi's `promptGuidelines` (bullets pi adds to the prompt's guidelines while the tool is active; `main-prompt.ts` keeps them when the main prompt is replaced), `executionMode` (`sequential` or `parallel`) and `modelOnly` (the model calls the tool directly and codemode scripts cannot; `toPiTool` maps it to pi's `model-only` exposure and passes the others through unchanged).
- `KeyPress.name` names pi's editor bindings (`up`, `down`, `left`, `right`, `toggleTools`) and the fixed keys `pageUp`, `pageDown`, `home`, `end`, `enter`, `escape`, `backspace`, `space`, `tab` and `backTab` (Shift+Tab, pi-tui `Key.shift("tab")`); anything else is `other` with `char` for a single character, and every key carries `raw`, the terminal data. An `other` key also carries `shortcut`, the character to match letter hotkeys against, so they fire in a Cyrillic layout: a Russian letter, or the Ukrainian `і`, `ї`, `є` or Belarusian `ў`, becomes the QWERTY character on the same key (`ч` is `x`, `Ч` is `X`, `key-layout.ts`; `і` follows the Ukrainian `s`, not the Belarusian `b`, and `ґ`, whose key differs between Ukrainian layouts, is left out), any other character stays as typed (Dvorak or QWERTZ letters are not remapped), and a kitty CSI-u event without a single character, plain or with Shift only, takes its base-layout letter from pi-tui's `parseKey`; `char` stays as typed, so text input keeps Cyrillic. Ctrl and Alt combinations are a non-goal and never get a `shortcut` letter, in legacy, modifyOtherKeys or kitty mode (pi matches its own through the kitty base-layout key); none of the repo's hotkeys use them.
- `HostUi.showForm(factory, { signal })` (`form.ts`, with `overlay.ts` and `text-input.ts`) shows a form inline, in the editor's place, through pi's non-overlay `ctx.ui.custom` (pi saves and restores the editor text). Before it opens it waits until no overlay is visible (`overlaysCleared`: `TUI.hasOverlay()`, polled every 100 ms on an unref'd timer; the TUI is the last one a widget or overlay saw, or is captured through a widget factory that is removed at once), because pi would move focus to the inline form while an overlay such as `/agents` still covers it. The factory gets `theme`, `requestRender`, `done(value)` and `createTextInput()`, a pi-tui `Editor` behind `TextInput` (`render`, `handleKey`, which forwards `key.raw`, `text`, `setText`, `onSubmit`) whose `focused` follows the form's, so the hardware cursor and IME land in it. The promise resolves with the value given to `done`, or `undefined` outside tui, when the signal aborts (while waiting or before the form opens, nothing is shown; while open, the form closes), or when the session changed while it waited. Keys are named by `keyPress` and every line is cut to the width, as for overlays.
- `setPromptSection(name, text)` adds a named section (`<name>…</name>`, placed by pi after `cwd`) to the main session only; `undefined` removes it. Agents get nothing from an extension's prompt sections: the hidden child extension applies none, and every extension built through the adapter's `createPiExtension` (which `createManagedExtension` builds on) never boots inside a child, so a child's prompt carries only what the subagents extension passes on purpose (`promptAppend`). Each extension loads its own adapter copy, and each copy's host keeps its own sections in a local map. Every host registers its own `before_agent_start` handler for the main session, which copies that map into the same `systemPromptOptions`, after `setMainPrompt`'s replacement and independently of it, so a change reaches the next run of the main session. At `session_shutdown` a copy clears its own map; another copy's sections are never touched.
- `ToolSpec` renderers receive `ToolRenderState` (pi's render context: `expanded`, `isPartial`, `isError`, `args`, `invalidate`, plus `result`, the latest result of the call, and `aborted`, set by the same text match as tool rows) and may set `renderShell: "row"` (pi's self shell through `RowComponent` in `row-component.ts`: every line after pi's `outputPad`, rendered at the width left after it and cut with `...`, no background, empty lines without the pad, an empty render draws nothing; the call is rendered when pi draws the row, after `updateDisplay` has run both renderers, so a row's `renderCall` sees the result its `renderResult` was last given; pi puts one blank line before the call; the repo's tools build their lines with `platform/ui-kit/row.ts`); the `ToolResult` a `renderResult` receives carries `isError`. `execute` gets only the abort `signal`; pi's partial-update callback is not exposed. The adapter keeps every spec an extension passes to `registerTool`, by name, and an overlay's transcript renders calls with them.
- `contextFacts()`, `lastRequestUsage()` and `mainRequestUsage()` (`platform/pi-adapter/context/context-facts.ts`, composed from `context-prompt.ts`, `context-messages.ts` and `usage-events.ts`) measure the main session for `/context` and the footer. They return what pi exposes and no `/context` policy: `ContextFacts` is the model name, window, pi's total (or null), the compaction reserve, the system prompt as named sections with their text, every declared tool and every tool pi loads on demand with its source (`builtin`, `mcp` or `extension`), an `onDemand` flag and the size of its declaration in characters, and each conversation message with pi's `estimateTokens` figure (assistant messages also per content block); prompt usage figures are `PromptTokens`, the type `platform/shared/cache-hit.ts` reads too. `ToolInfo`, exposures, source paths and usage records stay inside the adapter. `mainRequestUsage()` is memoised on the session id, session file and leaf id, so a fork or resume never serves a stale figure; outside a live session the facts are undefined and the usage zero.
- `registerEntryRenderer(customType, render)` (`entry-renderers.ts`) wraps pi's `registerEntryRenderer`: `render(data, width, expanded, theme)` returns plain lines, the adapter puts each after the shared output pad (pi gives entries no `outputPad`; the adapter reads pi's `outputPad` setting from `getSettings()` at every tui session start and then takes the `outputPad` of each tool render, kept on `globalThis` under `Symbol.for("pi-extensions.tool-rows")`; so a change of the setting during a session reaches entries only after the next tool render), renders at the width left after it, cuts each line with `...` and passes pi's tool-expansion state (`Ctrl+O`) as `expanded`. Custom entries are stored in the session file and never enter the model's context. `registerMessageRenderer(customType, render)` does the same for displayed custom messages (pi's `registerMessageRenderer`), with `{ text, details }` of the message (text parts joined) and pi's own `outputPad` as the pad. Each registration is also kept in a record on `globalThis` (`Symbol.for("pi-extensions.message-renderers")`) as `{ customType, owner, render }`, keyed by type and owner (one owner per adapter copy); `session_shutdown` removes only that copy's entries. The transcript pane draws a custom message with the latest entry still present for its type, so an agent view reached through another copy draws what this copy registered, and falls back to pi's own component for an unknown type; `display: false` messages are skipped.
- `registerToolRows(rows)` (`tool-rows.ts`) restyles tool calls the repo does not draw itself. It registers one `pi.registerToolRenderer` resolver: for each tool name it takes `next()` (the renderers pi would use, built-ins merged in) and keeps them for any tool other than pi's built-ins (`read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`) that renders itself in any way (a self shell, its own `renderCall` or `renderResult`; pi's built-in `edit` draws its own frame, so the built-ins are always restyled), or when `rows` returns nothing for a probe view of the name; otherwise it hands pi a self shell whose call and result are `RowComponent`s over `ToolRow.call` and `ToolRow.result` (`(width, theme) => string[]`, from a `ToolCallView`: name, args, `argsComplete`, `started` (pi's `executionStarted`, or a result exists), `isPartial`, `isError`, `expanded`, `cwd`, `durationMs` (pi's recorded `ToolResultMessage.durationMs`, live, on resume and in the agent pane), `aborted`, `label`, `skill` (`{ name }` when the call is a `read` of a `SKILL.md`: pi's folder rule and path resolution in `skill-reads.ts`, the same in both panes), and the result's text, details, `isError` and image count). The call's view is built when pi draws the row, not when it calls `renderCall`: `renderResult` keeps pi's result on the row's slot (a `WeakMap` on pi's renderer state, `slotFor` in `row-component.ts`), and the call reads it, so a title can carry the failure reason, duration or abort of its result. `aborted` is pi's wording matched by `abortedText` (`row-component.ts`): an error result that is exactly `Operation aborted` or `Aborted after N retry attempt(s)`, or a `bash`/`powershell` result whose last line is `Command aborted`; a result that is only the abort text reaches the rows as empty text. `label` is `server/tool` for an MCP tool: from `getAllTools()` (source path `builtin:mcp`, `namespace.aliases[0]` and the name after `<namespace>__`), else pi's own `mcp__<server>__<tool>` pattern (`mcpLabel`, the only source in the agent pane); the host looks each name up once. A component pi hands back is reused, and keeps its drawn lines per width until pi updates it (`renderCall`/`renderResult`) or invalidates it, so a frame does not recompute every row. When the row is expanded and sets `piBody`, the result also draws the base renderers' own `renderResult` (pi's diff for `edit`, the whole output for `read`, `bash`, `grep`, `find`, `ls`) under it, rendered at the width left after the pad and four columns (`CHILD_COLUMN`), leading blank lines dropped, hung under `  ↳ ` when the row draws no result line of its own and indented four columns otherwise, blank lines left empty, and without pi's `Took …`/`Elapsed …` timing line when the row sets `dropTiming`, with its own state and component kept per tool row (a `WeakMap` on pi's renderer state), so pi's renderer never sees the row's component; a throwing base renderer draws no body. The rows are also kept on the `globalThis` record with an owner token per registering copy, so a transcript pane of any adapter copy (the agent view) applies them through `applyToolRows`; at `session_shutdown` a copy drops its own rows, and the record falls back to the rows of the latest copy still registered, empty once none is. A row whose `call` or `result` throws draws pi's own call or result component instead. There are two paths to one source: pi's resolver closes over the `rows` it was registered with, the agent-view overlay reads them from the record. pi still wraps call and result in its click `MouseRegion` (a click toggles the row in fullscreen mode) and appends images.
- `HostUi.setHiddenThinkingLabel(label, hint?)` (`create-ui.ts`, tui only) and `thinking-label.ts`. There are no overrides of pi's message components: user and assistant messages are pi's own. The label is composed as `label`, or `label`, a space, a full SGR reset `\x1b[0m` and the hint in `dim` (`composeLabel`), because pi wraps the whole label in `theme.italic(theme.fg("thinkingText", …))` and chalk reopens italic after an inner `\x1b[23m` but leaves a full reset alone; so the hint draws dim and upright. The composed label goes to pi's `ctx.ui.setHiddenThinkingLabel` and onto a `globalThis` record (`Symbol.for("pi-extensions.thinking-label")`) kept per owner, from which transcript panes pass it to the assistant messages they build; `session_shutdown` releases the copy's own label. `thinking-label.ts` also holds `OSC133_ZONE_PREFIX`, the prompt marks transcript panes take off pi's message lines.
- `terminalNotify(message, channel)` writes BEL for `bell`, and for `auto` only an OSC 9 notification (OSC 777 titled `pi` on rxvt), no BEL; tui only.
- `ClipboardUi.copyText(text)`, its own capability since copying is not a notice, wraps pi's `copyToClipboard` (native clipboard or system tool, plus OSC 52 over SSH/mosh or with `PI_CLIPBOARD_OSC52=1`); it rejects when no route works or the OSC 52 payload (~75 KB) is too large.

## Child sessions

`runtime.spawn` returns a `ChildSession`. The adapter tracks a `running` flag, set when `start`, `send` or `wake` issue `session.prompt` or `sendCustom` starts a run with its message, and cleared on the `settled` event. While `running` is set (including the window before pi marks the session as streaming), `send(msg, "steer" | "followUp")` and `wake(text)` never call `prompt` again: they queue on pi's own steer or follow-up queue, so a message sent right after `start` joins the first turn and pi's "already processing" error cannot come from the adapter. When nothing is in flight they start a new prompt; if pi rejects it, the child emits an error `assistant_message` and `settled` so the runner closes the agent instead of hanging. If extension binding fails during spawn, the child's extensions get `session_shutdown` and the session is disposed before the error propagates. `lastText()` is the last assistant text; `runTexts()` (`finalRunTexts` in `message-text.ts`) returns every non-empty assistant text of the child's final run, read from its session entries: from the last user message that follows an assistant message without tool calls (or the start), so a message steered into a running turn does not cut the run short; a displayed custom message (a `custom_message` entry with `display` not false) starts a run exactly like a user message, a hidden one is no boundary. `sendCustom(message, delivery)` takes a `CustomMessage`, mirroring `Host.sendMessage`, and sends it as a displayed pi custom message with no `[message from …]` prefix (`sendCustomMessage` with `deliverAs` steer or follow-up and `triggerTurn` while pi is streaming, as a next-turn message while `running` is set but pi is not yet streaming so it joins the starting run instead of starting a second one, and with `triggerTurn` when idle). Because pi's `clearQueue` also drops the agent's queued custom messages, the child remembers the custom messages it queued (removed one at a time when pi starts them with `message_start`) and, when a run settles with anything pending, re-queues them as next-turn messages next to the re-prompted text, or starts the run with the first one when there is no text; a settle after an abort or a dispose re-queues nothing, because the runner closes the agent after an abort. The main session needs no such mirror: the adapter never calls `clearQueue` there and pi's interactive loop drains its own queue, while a child's settle must clear pi's queue to re-prompt the text left in it, which would drop the custom messages with it. `start(task, seed)` appends the seed as a displayed custom message and only then prompts, with `running` already set so a `send` in between queues.

A custom tool whose name another extension's main-session tool also has wins in the child: tool names are merged as a set and the custom spec is what the child binds (pinned in `child-runtime.test.ts`).

Model resolution (`child/model-resolver.ts`): no request means the main session's model; otherwise exact `provider/id` or id among models with credentials (preferring the session provider, then the default provider), then fuzzy matching by tokens and edit distance within a provider scope, newest version per family. Several families -> `ambiguous`, nothing -> `unknown` with suggestions; both make `run_agent` fail with the candidates. Thinking level: request suffix, then definition, then the main session's level.

Agents never compact and never get cache warming; their prompt prefix is fixed at spawn.

## Tests

`platform/pi-adapter/tests/` may import adapter files and pi packages directly. `conformance.test.ts` pins the pi internals the adapter relies on, offline, so a pi update that changes one fails `npm run check`; the list of those internals is in the [transcript architecture](../../extensions/transcript/ARCHITECTURE.md#upgrade-notes). `tests/live/wake.live.test.ts` wakes a real child session under `npm run test:live`.
