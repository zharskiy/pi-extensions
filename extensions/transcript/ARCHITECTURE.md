# Transcript architecture

## Boot

`index.ts` exports `api/extension.ts`, a `createManagedExtension` call with namespace `pi-transcript` and one plugin, `transcriptPlugin` (`api/plugin.ts`). Its `enable` calls `createTranscript(host)`, which registers `Host.registerToolRows` with `transcriptRows` (`ui/tools.ts`), a session-start handler for the thinking label, an entry renderer for `pi-transcript:answer` and the `Host.onAgentStart`/`onAssistantEnd`/`onIdle` handlers and the `pi:background-work` subscription behind it, and returns nothing to undo. No settings; the one channel it reads is `pi:background-work` and the one session entry is the answer entry below.

The tool rows are split in two: `core/tool-kinds.ts` classifies a call without a theme (its arguments, `read`'s line range, the listed count of `grep`/`find`/`ls` output, a missing-file failure, the edit's `details.diff` text, the duration worth showing) and `core/word-spans.ts` finds the changed words of a diff line pair; everything under `ui/` paints.

## Runtime

- `extensions/transcript` switches the row look on. At load it registers `Host.registerToolRows` with `ui/tools.ts`; at a tui session start it calls `setHiddenThinkingLabel("∴ Thinking", "(K to expand)")`, `K` read from `HostUi.keyText("app.thinking.toggle")` (pi's thinking visibility toggle; no hint when unbound), which the adapter records for the agent pane too (see the thinking label in the root `ARCHITECTURE.md`). User and assistant messages are pi's default: the repo patches no pi component. Disabling the extension leaves pi's look (the repo's own tools keep their rows, which they draw themselves).
- The answer rule separates the final answer of one turn of work from the steps before it. A turn runs from the user's prompt until the session has settled with no background work pending, so it spans the wait for background agents and the runs their results start. The first `onAgentStart` while no turn is open opens a `TurnWork` (`core/turn-summary.ts`: start time and tool count); an `onAssistantStart` while no turn is open opens one too; later starts join it, whether an auto-retry, a continue, a run a background result starts or a prompt the user types while work is still pending. `onAssistantEnd` adds each message's tool calls. The transcript keeps the last `pi:background-work` count of each source (`parseBackgroundWork`, `platform/shared/channels/host-channels.ts`; subagents counts its background batches until a reply starts after their wake, so the count is current at that reply's end). The rule goes above the final answer: at the `onAssistantEnd` of a reply the adapter marks `final` (no tool calls, a `stop` stop, nothing queued to continue the run; see `AssistantEnd` in `platform/pi-adapter/ARCHITECTURE.md`) while no source has work pending, the turn settles and, when at least one tool ran in it, appends the custom session entry `pi-transcript:answer` with `{ ms }`, the time since the turn opened. Pi runs extension `message_end` handlers before its own listeners, so the entry is drawn above that reply (the reply is still pi's streaming component, before which `addCustomEntryToChat` inserts) and stored before it in the session file, so a resume draws the same order. A reply given while agents still run, or one after which the run goes on, gets no rule; the reply that answers the last results does. When the turn settles without such a reply, the rule is appended at the end as before: at `onIdle` when no source has work pending (the turn ended on an `error` or `length` stop, which pi may retry and so is never `final`), or at the report that brings the last count to 0 while no run is active (a result never reached the model). A turn that only answers gets no rule. An aborted run (`onIdle` with `aborted`) closes the turn without a rule, even with work pending: the user cut the turn short and pi already marks the stop; a result that arrives later opens a new turn. The entry is written only in a tui session (`onSessionStart` sets the flag): print, json and rpc runs, and child agent sessions, which bind in print mode, write no UI entries into their session files. When `final` is wrong (a custom follow-up a third-party extension queued, or a continuation pi decides at a turn boundary), the rule sits above that reply. The run can also go on after a final reply without a new `onAgentStart` (a prompt flushed into the active run, a continuation pi decides); `onAssistantStart` opens a turn too when none is open, so tool work after that reply gets its own rule, above its final reply or at the end. Pi persists the entry but never sends it to the model (custom entries do not take part in the context) and `/tree` hides it by default. `ui/answer-rule.ts` renders it with the adapter's `labelledRule` (`worked 42s`, dim, full width behind pi's pad); data that does not parse (`finite ms >= 0`) draws no line, though pi still adds its blank line above the entry, which only a hand-edited file can cause. Nothing is drawn while the turn works, so no row ticks, and nothing above the viewport changes.
- Which tools get rows (`platform/pi-adapter/tools/tool-rows.ts`): pi's built-in tools (`BUILTIN_TOOLS`), tools without a renderer of their own, and tools of pi's built-in extensions (e.g. `codemode`), which `ExtensionAPI.getAllTools()` lists with `sourceInfo.source` `builtin`; the check runs only for a tool that has a renderer of its own. Any other tool with a `renderCall`, `renderResult` or self shell keeps its look, so a third-party extension that replaces `codemode` draws itself. An extension that restyles a pi-shipped tool through `registerToolRenderer` keeps its look only when it loads before transcript (its resolver then wraps ours); loaded after, its renderers arrive through `next()` and the rows replace them. The agent view has no `getAllTools`; there the pi-shipped renderers it captures (`capturePiRenderers`) count as pi's.
- `ui/tools.ts` is pure: it picks a `Look` (`ui/tool-look.ts`) per tool and builds every row the same way over `platform/ui-kit/row.ts`: the call is the title line, the result the children. The title of every row except a collapsed skill read is the mark (`markOf`: `◌` until the call finished, `⊘` when the adapter reports `aborted`, then `✗` or `✓`), the bold verb, the lowercase tool id as codemode prints its calls (`read`, `edit`, `write`, `bash`, `powershell`, `grep`, `find`, `ls`), the target in accent (paths cwd-relative or `~/…` by `homeRelative`, cut at the start; patterns and commands cut at the end), muted arguments (`read`'s `:5-14` range, `grep`'s ` in path`, a multi-line command's ` ...`), and then, after a muted ` · `: `stopped` (muted) for an aborted call, otherwise a failure reason in `error` when `failureSuffix` lets it sit on the title, then the recorded duration (`formatDuration` of `durationMs`, only from 5 s on and never on a running or timed-out call: a running row never ticks, since a changing row above the viewport forces pi's regular-mode renderer to clear and replay the scrollback). A title whose key argument has not streamed yet is the verb alone. Reasons come from the result: for shell rows pi's last status line (`ui/output.ts` `shellResult`: `Command exited with code N` gives `exit N`, `Command timed out after N seconds` gives `timed out after Ns`, `Command aborted` is the stop), `file not found` for a missing file, otherwise the error's text; a reason that does not fit is the `↳` line, wrapped at column 4.
- Outcomes are the `↳` children: `read` counts lines (`Image` for images), `write` the lines of its `content` argument (`Empty file`), `edit` the added and removed lines of `details.diff` (`Added N lines, removed M lines`), `grep`, `find` and `ls` matching lines, files and entries from pi's text (`No matches`, `No files`, `Empty directory`; pi's bracketed notices not counted). Shell rows (`ui/shell.ts`) show the last three output lines under pi's count line `... (N earlier lines, ctrl+o to expand)`, muted in every state, `No output` when there is none. MCP and unknown tools (`ui/generic.ts`) are titled `server/tool` in accent bold (the adapter's `label`) or the bold tool name, with up to three `key=value` arguments, and show the first three output lines, each cut, then `... (N more lines, ctrl+o to expand)`, every line wrapped when expanded. `codemode` (`ui/codemode.ts`) is titled `codemode` with the script's first line muted (after a leading `// @options:` line); its outcome comes from `details.calls`, pi's per-call records `{ name, args, status, durationMs, cost, error }`: `3 calls, 1 failed · 1611 lines of output` (output counted without pi's `Script completed/failed … Output:` header), `2 calls` while running; expanded, the whole script, every call as a nested row (`running`, `ok`, `error` and `cancelled` mapped to `◌`, `✓`, `✗`, `⊘`; pi's own `12ms` and `$0.0012` figures kept dim; a failed call's error under it) and the output. A failed non-shell call shows its error in the error colour, three rows until expanded.
- The hint is `expandHint` with the key of `HostUi.keyText("app.tools.expand")` at render time, only while collapsed and only where expanding shows more: after an edit, write or codemode summary, and pi's count line where output is cut. `read`, `grep`, `find` and `ls` have none (the count is the result), except a collapsed skill read. When the row is narrow the hint gives way to the content, and a count line drops only its `, key to expand` part.
- Bodies: an expanded `edit` draws `details.diff` itself (`ui/diff.ts`, parsed once per render from pi's display lines `+NN text`, `-NN text`, ` NN text` and the blank-numbered `...` between hunks; the counts come from the same parse, so a diff it cannot read shows none and pi's own body instead): the gutter `+`/`-`, the right-aligned number and a space, tabs expanded to three spaces and control characters dropped, each run of removed lines paired with the added run after it, the changed tokens of a pair marked (`core/word-spans.ts`: a longest common subsequence over grapheme-safe word, space and single-symbol tokens, skipped above 400 tokens or when more than half of the pair's characters changed); removed and added rows sit on the `removed`/`added` backgrounds padded to the width with the changed tokens on the word backgrounds, wrapped lines keep the background under a blank gutter, and context and gap rows are muted. When `ThemeLike.panels` is false (pi's system theme without a terminal colour report, where every panel background is the bare default) the diff falls back to pi's own look: changed lines in `success`/`error` and the changed tokens `inverse`. An expanded `write` draws every line of `content` the same way, as added lines. `piBody` is set for every built-in but `write` when the result is not a failure (for `edit` only when its diff does not parse, for shell rows only when there is output), so expanded rows show pi's own output at column 4 under the outcome; shell rows set `dropTiming`, since the title already carries the duration. An aborted call draws no outcome or body, except shell rows, which keep their streamed output.
- Skill reads: with `view.skill` set (the adapter's detection of a `read` of a `SKILL.md`) and the row collapsed, `ui/skill.ts` draws pi's glyph-free `[skill] name` line in `customMessageLabel` (bold) and `customMessageText`, the range in `warning`, `· stopped` or `· reason` on the same line, and the hint through `appendHint` once done. Expanded, it is the normal read row.
- Not done: tool-call grouping (folding consecutive reads and searches into one row), a per-run thinking duration (pi has one hidden-thinking label for every message), the answer rule in the subagents agent pane (child sessions write no entries; the pane would have to build it from its messages), a rule for an aborted turn, a separate denied state (a call another extension blocked is `✗` with the reason: the adapter never sees another extension's block decision), syntax highlighting in diffs, an ASCII glyph fallback.

### Upgrade notes

The rows depend on these pi internals. Most are pinned by a conformance test in `platform/pi-adapter/tests/conformance.test.ts` (the test name in brackets), so a pi update that changes one fails `npm run check` before it reaches a user. At runtime a tool row whose render throws draws pi's own component instead.

- The hidden thinking label: `AssistantMessageComponent` taking it as the fourth constructor argument and drawing it inside `italic` and `thinkingText`, where the composed hint after `\x1b[0m` stays dim and upright (`messages and the thinking label`; the level of pi's own chalk, resolved from pi's theme module, is raised for that test, since tests run without a colour terminal); `ExtensionUIContext.setHiddenThinkingLabel` (`gives extensions the API and UI methods`).
- The order of an extension's `message_end` handlers and pi's own: pi runs them before its listeners draw and store an assistant message, so an entry appended there sits above the message in the chat and the session file (`emits and stores an entry appended in an extension's message_end before that message`); a custom follow-up queued during a run starts after the reply that would end it (`starts a custom follow-up queued during a run after the reply that would end it`). If the first changes, the rule lands below the answer.
- The OSC 133 marks on `UserMessageComponent`: `ESC]133;A BEL` on the first line, `ESC]133;B BEL ESC]133;C BEL` on the last, which `OSC133_ZONE_PREFIX` takes off (`messages and the thinking label`).
- `Container.prototype.handleMouse`, which routes a click in a transcript pane by the child heights of the last render.
- `ToolExecutionComponent.updateDisplay` calling `renderCall` before `renderResult` in one pass and handing both `durationMs` from the result (`draws the call before the result`); `durationMs` stored on `ToolResultMessage`, so a resumed or agent-pane row has it too.
- `getAllTools()` source info: `ToolInfo.sourceInfo.source` is `builtin` for pi's built-in tools and for `codemode` from pi's built-in extension, and not for a third-party extension's tool (`marks pi's own tools, codemode among them`); `sourceInfo.path` `builtin:mcp` and `ToolInfo.namespace` with `name` and `aliases` on an MCP tool, from which the adapter builds the `server/tool` label (`gives extensions the API and UI methods`, `is seen through the /mcp command`).
- `ExtensionAPI.registerToolRenderer`, `registerMessageRenderer`, `getSettings()` (its `outputPad`, 0 or 1, unset meaning 1) and `theme` (`gives extensions the API and UI methods`).
- The `ToolRenderContext` fields the rows read: `args`, `argsComplete`, `executionStarted`, `isPartial`, `isError`, `expanded`, `cwd`, `outputPad`, `state`, `lastComponent`, `durationMs`; and the self shell's one blank line before the call (`transcript rows`).
- `Theme.getBgAnsi`, `Theme.italic` and `Theme.inverse` on pi's `Theme`, and `truncateToWidth(text, cols, "...")` keeping the width (`gives extensions the API and UI methods`, `cuts with the ASCII ellipsis`).
- The theme colours `toolSuccessBg`, `toolErrorBg`, `toolDiffAdded`, `toolDiffRemoved` and `userMessageBg` in `Theme.colors`, `Theme.style(text, { bg })` with a token or a colour, and pi-tui's `mixColors` (`transcript rows`, `finds every pi export`); `Theme.colors` giving concrete colours for tokens set to the terminal default (`gives concrete colours for tokens set to the terminal default`).
- The theme colours `customMessageLabel` and `customMessageText` in `Theme.colors` (`has the theme colours, background style and colour mixing …`).
- `details.diff` of an edit, `generateDiffString`'s lines: `+NN text`, `-NN text`, ` NN text` with the number padded, and a blank-numbered `...` between hunks, checked on the output of pi's edit tool run on a file (`transcript rows`; `extensions/transcript/tests/pi.test.ts` parses that output with `parseDiff` through the `test/framework/pi/tool-row-rendering.ts` harness).
- `Theme.fg` closing with `\x1b[39m` (`\x1b[22;39m` for faint tokens) and never `\x1b[0m` or `\x1b[49m`, so the coloured `+`/`-` marker keeps the line background around it (`transcript rows`).
- Built-in renderers: `edit`'s `renderResult` shows `details.diff` when its call was never drawn (the fallback for a diff the rows cannot parse); `read` and `bash` show their whole output when expanded; the built-in tool names (`transcript rows`).
- pi's codemode renderer drops the `Script completed`/`Script failed`, `Wall time … seconds`, `Output:` header, the same header the rows strip before counting output lines (`pi's codemode renderer drops the … header`).

Not pinned by a conformance test; the unit tests use fixtures in pi's current shape, so check these by hand when pi changes them:

- `addCustomEntryToChat` in the interactive mode inserting a new entry before the `streamingComponent` while one exists (`interactive-mode.js` around l.3093-3112; the assistant message stays the streaming component until pi's own `message_end` handling clears it), which puts the rule above the final answer, and appending at the end otherwise (the fallback after an error or a result that never reached the model); and the resume order, which draws entries in file order.
- `details.calls` of a codemode result: `{ name, args, status: running | ok | error | cancelled, durationMs, cost, error }` per call, from pi's codemode extension (`ui/codemode.ts`).
- Pi's `SKILL.md` naming rule (`getCompactReadClassification` in pi's `read.js`), which `skillOfRead` in `platform/pi-adapter/tools/skill-reads.ts` follows with pi's path resolution.
- The abort texts the adapter matches (`abortedText` in `platform/pi-adapter/tools/row-component.ts`): an error result that is exactly `Operation aborted` or `Aborted after N retry attempt(s)`, and a `bash`/`powershell` result whose last line is `Command aborted`; there is no abort flag. The agent pane writes `Operation aborted` itself for calls an aborted child left open. A result that is only the abort text reaches the rows as empty text, so no row prints it as output.
- `ToolExecutionComponent.markExecutionStarted()` is called only from the live `tool_execution_start` event: the session rebuild (`renderSessionEntries`, on resume, `/reload` and after compaction), the `message_end` path of an aborted or failed turn and the agent pane give a call its result without it. The adapter therefore counts a call as started once it has a result (`ToolCallView.started`).
- The shell status lines `Command exited with code N` and `Command timed out after N seconds`, and the `Took …`/`Elapsed …` timing line that `dropTiming` removes from pi's body; the `No matches found`, `No files found` and `(empty directory)` texts of `grep`, `find` and `ls`.
- Panel detection: `getBgAnsi("toolSuccessBg")` returning the bare `\x1b[49m` when the theme leaves the panel colour to the terminal (pi's system theme without a colour report); `ThemeLike.panels` is false exactly then.
- The binding ids `app.tools.expand`, `app.thinking.toggle` and `app.interrupt` whose keys the hints name.
