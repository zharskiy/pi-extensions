# Context architecture

## Boot

`index.ts` exports `api/extension.ts`, a `createManagedExtension` call with namespace `pi-context` and one plugin, `contextPlugin` (`api/plugin.ts`). Its `enable` calls `createContext(host, { home, now })`, which registers the `pi-context:snapshot` entry renderer and the `/context` command and returns nothing to undo. No settings, no channels, no state outside the session entry.

## Runtime

- `/context [all]` (main session only, like everything in the package) builds a snapshot: the breakdown the extension makes from `Host.contextFacts()` (`core/buckets.ts`), `lastRequestUsage()`, `mainRequestUsage()`, the time and `expandedByDefault` for `all`. Memory file paths are shortened to `./` (under the working directory) and `~` (under home) when the snapshot is taken. In tui mode it appends the snapshot as a `pi-context:snapshot` custom entry and the extension's entry renderer draws it in the transcript; pi draws it at once and again on resume, from the frozen figures, and the entry never enters the model's context. The renderer validates a stored entry field by field (`core/snapshot.ts`: numbers where numbers belong, `total` a number or null, `model` a string or absent, every message bucket a number) and draws nothing for one it cannot read. Other modes get a one-line `notify` summary instead (`ui/summary.ts`, plain text, no theme), since no entry renderer runs there.
- Facts (`platform/pi-adapter/context/context-prompt.ts`, `context-messages.ts`): the system state is the replay of the `role: "system"` messages in `sessionManager.buildSessionProjection().messages` (`replaySystemMessages` in `session-file.ts`, the same replay agent session files use). pi writes the first system message when a run starts, so before the first request the adapter falls back to `ctx.getSystemPrompt()` (only the `<project_context>` and `<skills>` blocks cut out as their own sections, the rest as `prompt`) and to the active tools whose exposure is declared (not `hidden`, `deferred` or `codemode`). A tool's source comes from `getAllTools()` `sourceInfo.path`: `builtin:mcp` (pi's bundled MCP extension) is `mcp`, other `builtin:` paths `builtin`, anything else `extension`; registered tools that are `deferred` or `codemode` and not declared come with `onDemand: true`. Messages are pi's `estimateTokens` per non-system message of the projection. The reserve is compaction's `reserveTokens` (model override, setting, then pi's default) while compaction is on, else 0.
- Breakdown (`core/buckets.ts`): section `project_context` becomes the memory files, one row per `<project_instructions path>` block (one row when it cannot be split), `skills` one row per `<skill>` block, every other section and the leftovers of those two the system prompt; each is chars/4. Tools are chars/4 of their declaration, grouped by source; tools loaded on demand count 0 and only the MCP ones are listed, as loaded on demand. Messages are bucketed into user, assistant text, thinking, tool calls, tool results and other. The usage model (`core/breakdown.ts`) gives Messages the rest of pi's total after the fixed categories, or scales the fixed categories down to the total by largest remainder (`apportion`) and leaves Messages at 0 when their estimates exceed it (so the legend always adds up to the header), and falls back to the sum of the estimates, marked `~` and `estimated`, when pi does not know the total (after a compaction); free space is what is left after the reserve.
- Cache figures: hit rate = `cacheRead / (input + cacheRead + cacheWrite)` (pi normalises the four prompt buckets so they do not overlap, and its `/session` uses the same formula). Last turn = `getLastAssistantUsage` over the current branch (skips aborted, error and empty usage); session = `sumAssistantUsage` (`platform/pi-adapter/context/usage-math.ts`) over every assistant message of the main session file, leaving out cache-warming `usage` entries, compaction and branch-summary usage and tool-result usage, so it can differ slightly from pi's `/session`, which includes them. Agents' usage lives in their own session files and is never counted. Nothing is shown until the session reported a cache read or write; a last request without cache activity in a session that had it shows `0%` in the warning colour. The session figure is `sessionCacheHit` and every percentage is painted by `cachePercentText` (`platform/shared/cache-hit.ts` and `platform/ui-kit/cache-tone.ts`, success from 70 %, warning from 30 %, error below), the same functions the footer uses, so both show the same session figure.
- Rendering (pure over `ThemeLike`): `ui/grid.ts` draws a 10 × 10 grid (20 × 10 for windows of 1M, 5 × 5 below 50 columns), each cell an equal share of the window; the filled cells are the rounded share in use, split between the categories by largest remainder, filled row-major in legend order as `■`, then free space `·`, then the reserve `░`, three shapes common fonts carry, so the grid reads the same in monochrome (there is no partial cell). The layout is measured: the widest of the header, cache and legend lines (`theme.width`) decides; 20 × 10 only when the grid, the gap and that line fit in the width, else 10 × 10 beside it when that fits, else the grid on top with the header, cache line and legend under it, and a header still too wide drops its `tokens` word; overflowing legend lines continue in the legend column. `ui/details.ts` adds one section title per category with its summary on a `↳` line (a nested row: text at column 6), or every item by tokens when expanded, and `ui/render.ts` composes the row: the accent info mark `»` (a snapshot, not a call that succeeded) before the bold `Context usage` and the dim ` · <time>`, then the grid, legend, overflow warning and details at column 4, and while collapsed pi's count line `... (N more items, ctrl+o to expand)` counting what expanding would list (none when expanded); the adapter's entry renderer puts the lines after the shared output pad and cuts them to the width with `...`. The window is `formatWindow` (`platform/shared/format.ts`), as in the footer. Category colours are pi's thinking-level tokens from `thinkingOff` to `thinkingXhigh` (system prompt, system tools, MCP tools, extension tools, memory files, skills), messages `text`, free space `muted` and the reserve `warning`, so they follow the theme and red only ever means a failure.
- Footer segment: the footer reads `host.mainRequestUsage()` on each render and, once the session reported cache activity, shows `cache 91%` on its context line, with the rate from `sessionCacheHit` painted in `muted` by the footer itself rather than by `cachePercentText`; the footer's own drop order decides when it goes.
