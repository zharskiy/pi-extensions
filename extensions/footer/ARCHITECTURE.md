# Footer architecture

`index.ts` re-exports `api/extension.ts`, which builds the extension with `createManagedExtension` (namespace `pi-footer`, no settings) and one plugin, `footerPlugin` in `api/plugin.ts`. The plugin keeps the last spending totals through `watchTotals` (`core/status.ts`), installs the footer at session start and draws it with `renderFooter` (`ui/render.ts`) over the state `footerState` (`core/segments.ts`) reads from the host on every render. Its `enable` returns nothing to undo.

- Replaces pi's footer (`HostUi.setFooter(render)`, tui only) with a block aligned to the composer prompt (`PAD`, one space, the composer margin) that starts and ends with one blank line (so pi's command list never touches it): context tokens (warning above 70 %, error above 90 %), the session cache hit rate (`cache 91%`, `cachePercentText`, hidden until the session reported cache activity and dropped first when the line is too narrow), main cost, model name and window (`formatWindow`); the session total (main plus every spending source); folder with `git:(branch)` when there is a branch, then the session name; thinking level with the `app.thinking.cycle` key; then the other extensions' status texts, one line per key sorted by key, without spending's own `pi-spending` status (`SPENDING_STATUS_KEY`), whose figures the block already shows.
- Cost and tokens come only from `spending:totals` (`TOTALS_CHANNEL`, parsed by `parseTotals`): the footer keeps the last payload, so a render reads only cheap live values (`Host.context()`, `mainRequestUsage()`, `model()`, `thinkingLevel()`, `sessionName()`; the adapter memoises `context()` on the session leaf id and the model, as pi's own footer does, and `mainRequestUsage()` on the session id, file and leaf id). Until spending publishes the cost segment and the session-total line are hidden; the session total gets a dim ` (sub)` when `subscription` is set. The footer re-renders when totals arrive, on idle and on git branch changes.
- Placement: the adapter draws the block as the below-editor widget `pi-footer` and installs an empty component in pi's footer slot (pi draws its built-in footer whenever the slot is unset; the empty component also hands the adapter pi's `footerData` for branch and statuses). Order is editor, notices, footer block, then the agent panel. pi keeps below-editor widgets in first-set order and clears them all before every `session_start`; the footer sets its widget in its `session_start` handler and the adapter only re-renders it while it is mounted, so the order rests on timing, not on load order.
- Notices (`HostUi.setNotice`) sit between the editor and the footer block: while the footer widget is mounted it draws every notice (sorted by key, indented by `PAD`) as its first lines. Notices are not statuses, so the footer's status lines never repeat them.
- The adapter (`platform/pi-adapter/ui/footer.ts`) truncates every line to the width, re-renders on git branch changes and on `refresh()`, and drops the branch subscription when pi disposes the footer.
