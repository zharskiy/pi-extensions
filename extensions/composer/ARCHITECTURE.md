# composer architecture

- `index.ts` re-exports the default of `api/extension.ts`, which calls `createManagedExtension` with the namespace `pi-composer` and one plugin, `composerPlugin` (`api/plugin.ts`). The plugin's `enable` builds the frame once and returns nothing to undo. No settings, no bus, no services, nothing persisted.
- On session start the plugin hands `host.ui.setEditorFrame(frame)` a pure `EditorFrame` (`chrome`, `left`, `minWidth`, `decorate(lines, layout, paint)`) built by `createFrame` in `ui/frame.ts`. The adapter (`pi-adapter/editor/editor.ts`) installs one `HostEditor` subclass of `CustomEditor` through `ctx.ui.setEditorComponent` when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `onEmptyEditorDown`, `captureEditorKeys`) is used, only in `tui` mode and only when no editor other than the one the package installed is set (`getEditorComponent()`). Composer and subagents share that one editor through a `globalThis` record, whichever loads first; hooks registered before `session_start` take effect at session start. The record also keeps the ↑ input history shared by every `HostEditor` instance, so it survives `/reload` and `/new`; `/resume` and `/fork` add the session's user messages to it like pi's own editor. The subclass is constructed with pi's `embedWorkingStatus`, as pi's own editor is, so pi draws the working, compaction and retry status inside the top rule (`── ⠹ Pondering · 12s ──`) with no blank line or spacer; the top rule is still one line that `decorate` extends. The frame is optional (without one the editor renders as pi's own), the instance reads the current frame on every render, and keys reach the hooks only while the editor has focus.
- The subclass renders pi's editor `chrome` columns narrower and passes the lines, the layout and the editor's live `borderColor` to `decorate`; below `minWidth` it renders the plain editor. The layout comes from the subclass's `renderTopBorder` and `renderBottomBorder` overrides, not from parsing lines: `bottom` is the index of the line `renderBottomBorder` returned and `scrolled` is whether the top border is an `↑ N more` hint. The rules are extended by `chrome` painted rule characters to the full width: the top rule gets them in front, so pi's embedded working status starts right of the prompt gutter (3 columns right of the input), the bottom rule gets them after; the lines between get a one-column left margin (`MARGIN`) and the prompt gutter (pi's `›` message cursor, bold in the live `borderColor`, so it follows the thinking level and bash mode like the rules, `CHEVRON` in `ui/frame.ts`, only on the first line and not while scrolled), and lines below the bottom rule (autocomplete) are indented by `MARGIN`, so pi's `→` sits under the prompt. No pipes or corners: `chrome` and `left` are the margin plus the gutter width. Mouse events are shifted left by `left` and narrowed by `chrome` before pi's editor handles them, so clicks land on the clicked character.
