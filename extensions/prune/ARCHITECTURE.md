# Prune architecture

`index.ts` re-exports `api/extension.ts`, whose `pruneExtension(deps)` builds the extension with `createManagedExtension` (namespace `NAMESPACE`, `pi-prune`, exported once from `core/settings.ts`; the settings file, the live folder and the `pi-prune:` prefix of every notice derive from it) and one plugin, `prunePlugin` in `api/plugin.ts`; the default export passes the handoff root (`handoffRoot()` from `platform/shared`), the process check `pidAlive` and a once-per-process record (`globalRecord("prune")` from the adapter, `{ swept, marker }`, which survives pi building a new extension for every session in the same process). Tests build their own with a temp handoff root and their own record. Its one setting, `days` (`core/settings.ts`, `pi-prune.json`; a whole number from 0 to 36500, default 180, 0 turns the sweep and the configured-days paths of `/prune` off), loads with `scope: "user"`: in a trusted project a `.pi/pi-prune.json` is not read and is reported as a settings error, so it turns off the sweep and `/prune apply` until the file is deleted; in an untrusted project it is not looked at. Any load error (an invalid value, bad JSON, a project file) is visible to the plugin through `settingsErrors()` and keeps it from removing anything at the configured days; days the user picks or types still work. Extensions are not loaded in agent sessions (`createPiExtension`), so only main pi processes sweep.

## Session start and shutdown

- Every `onSessionStart` writes the liveness marker `<agentDir>/pi-prune/live/<session id>.<pid>.json`, `{ id, pid, file, parentSession }` (`null` for a missing one), to a temporary name and renames it in place, so a reader never sees half a marker (`core/live-markers.ts`). It creates the folder first and writes only when `lstat` shows a real folder. Then it removes the marker the record held, when that is a different file, and keeps the new path in the record. `onSessionShutdown` removes it only for `quit`; after `new`, `resume`, `fork` and `reload` the next start replaces it. A process only ever removes its own markers; the sweep removes those of ended processes.
- The first session start of the process sweeps when the marker was written, `days > 0` and the settings loaded without errors: `planAt`, then `apply`, fire and forget. An aborted plan warns `pi-prune: nothing removed, <reason>` and a marker that could not be written warns the same with `<live dir>: cannot write the liveness marker`; a sweep that throws warns `pi-prune: sweep failed, <error>`. All of these happen only on that first start, so at most once per process. When anything was removed it notifies one line, `pi-prune: removed <n> sessions, <m> agent runs, <k> handoff dirs older than <d> days, <bytes> freed`, zero parts left out and the bytes only when above zero (`ui/prune-report.ts`, `bytesText`: below 1000 `<n> B`, else base 1000 with one decimal in kB, MB, GB or TB, moving up a unit when the rounding reaches 1000).
- The scanned folders are the real subfolders of `<agentDir>/sessions` and nothing else: `info.file` is never used to find a session dir, since `--session <path>` can point anywhere.
- `/prune [<days>] [apply]` (`core/command-args.ts`: `parseArgs`, a trailing `apply` and at most one whole number from 7 to 36500, else the usage line as an error; `completeArgs` offers the intervals and `apply`, after a number only `apply`). With `<days>` it prints the plan at those days, or with `apply` plans, applies and prints the counts, without asking in any mode: the typed `apply` is the consent. Without `<days>` in the TUI and without `apply` it opens the picker. Otherwise it uses `days`: the settings errors when there are any, the off text when it is 0, else the plan or, with `apply`, the counts. Output goes through `host.ui.notify`, as mcp-import's reports do; models never see the command, its output or the picker.
- The picker (`ui/interval-pick.ts`, `pickInterval`) takes `now` once, scans once with the 7-day cutoff and plans each interval of `INTERVALS` (7, 30, 60, 90, 180, 365) from that scan. An aborted scan warns instead, and nothing to remove at any interval says so instead. Each row is `<n> days` with its counts; `days` is marked and preselected when it is listed and the settings have no error, 180 otherwise. Escape, or `showForm` returning undefined because another overlay is open, does nothing. An interval with nothing to remove notifies without asking. Otherwise `host.ui.confirm` asks; on yes it plans again with a fresh `now` and applies `within(fresh, confirmed)`, only what both plans remove, so a session written to or opened between the picker and the answer is kept.

## Plan (`core/sweep-plan.ts`)

`scan({ slugDirs, agentDir, handoffRoot, current, isAlive }, latestCutoff)` reads the disk once and returns either `{ aborted }` or every input a plan needs, unfiltered by the cutoff: live set, the session chains with each session's mtime, id and parent (headerless ones too), the runs of the sessions in chains removable at `latestCutoff`, orphan and `pi-subagents/<id>/` runs, the handoff root state, the handoff folders of the sessions removable at `latestCutoff` and the old handoff folders no readable session or live id owns. `plan(scan, cutoff)` is pure and applies the rules below for any cutoff at or before `latestCutoff` (a later one throws, since the scan drops what is fresh at `latestCutoff`), so one scan serves every interval of the picker with the same result as a fresh plan. `planAt({ ...scanInput, days, now })` is `plan(await scan(input, cutoff), cutoff)` with `cutoff = cutoffAt(now, days)`, `now - days * 86_400_000`; the sweep and typed days use it, and reading only the runs of the sessions in removable chains keeps the sweep's reads to what it may remove. A plan is `{ cutoff, aborted?, chains, orphans: { stems, handoffs }, markers, kept, unreadable, handoffsSkipped }`, `chains` holding the candidates chain by chain; nothing is removed. Every candidate carries its file's `bytes` from the scan's `lstat`, and every planned run and handoff folder its `{ dir, bytes }` (`Sized`), the sizes of the files directly in it (`measure`, one level deep like the touch time, so a nested folder's content is not counted and bytes are never overstated). `totals(plan)` gives the planned `Removed`, a handoff folder two candidates share (duplicate ids) counted once. `within(fresh, confirmed)` keeps of `fresh` only the chains whose every candidate has the same file and modification time in `confirmed`, so a chain that gained or changed a member since the confirm is dropped whole, the runs and orphan stems and handoffs `confirmed` also removes, and `fresh`'s markers. Reads run in a bounded pool (`core/pool.ts`, `pooled`: at most `LIMIT`, 64, steps at once, results in source order, the first error rethrown once every running step has settled), one pool per stage and never one inside another, so the open files stay bounded: the session folders are listed, then every session header is read, then the run folders of every stem are listed and then every run is read; the live markers are read one at a time. Every folder is checked with `lstat` first, and its entries come from `withFileTypes`, so a symbolic link is never followed and never listed as a file or folder (`core/real-dirs.ts`). Session paths are compared through `pathKey` (`core/path-key.ts`: `resolve`, lower-cased on darwin and win32). Rules, in order:

1. Live set (`readLive`): markers whose `pid` is alive (`process.kill(pid, 0)` does not throw, or throws `EPERM`) give live ids (`id` from the JSON) and live files (`file` and `parentSession`); the current session's id, file and parent are live too. Every other marker is dead and listed for removal. When the live folder is not a real, readable folder (any `lstat` error but ENOENT, a symbolic link, a failed listing) the plan is `aborted`.
2. Sessions: every `*.jsonl` directly in each scanned folder, with its `lstat` modification time and header (`readSessionHeader` from the adapter: the first line within 64 KiB). A file without a valid header is `unreadable`: never removed, its folder never pruned. A read error other than a vanished file makes the plan `aborted: "<path>: <error>"`.
3. Chains (`core/session-chains.ts`, `chainsOf`): every scanned session is a member, linked to the scanned session its `parentSession` names (compared through `pathKey`; a parent that was not scanned or the session itself adds no link), and the links taken both ways group the members into chains. The grouping spreads level by level from each unvisited member through a visited set, so a cycle ends and no depth is capped. A chain is kept whole when any member is modified at or after the cutoff, is live (its id or file is live) or has no readable header (`pinned`, so a link to it keeps its chain); its members are kept as `fresh`, `live` or `chain`, headerless ones are listed as `unreadable`. Every member of the other chains is a candidate; each carries its id, its folder's stale runs (`stem`) and its handoff folder (`handoff`).
4. Orphans: a session folder whose `<stem>.jsonl` is not listed and not a live file, and `<agentDir>/pi-subagents/<id>/` whose id is not kept or live, go through the run rules. A kept or unreadable session's folder, or one beside a symlinked file, is skipped.
5. Run rules (`core/agent-runs.ts`, `staleRuns`): in `<folder>/agents/`, each real subfolder is a run, touched at the newest `lstat` time of the folder and its entries; an unparsable manifest is a plain run; a run whose manifest has a `worktree` with `cleanup` other than `"removed"` is spared. A subfolder without `manifest.json`, or one that cannot be read, is a spared run with no links and an infinite touch time, so a chain that names it is kept. Runs link through `predecessorId` and `successorId` inside the same `agents/`, walked both ways, stopping at an id already visited or not present. A run is stale when every run of its chain was touched before the cutoff and none is spared.
6. Handoff folders `<handoffRoot>/<id>/`, only when the root is safe (`core/handoff-root.ts`: a real folder, owned by `process.getuid()` where that exists, not group- or world-writable; `handoffsSkipped` when it exists and is not). `scanHandoffs` (`core/handoff-scan.ts`) streams the root with `opendir` through the pool and never builds the whole listing. A name owned by a readable session or a live id is skipped without a look unless that session is a candidate at `latestCutoff` (and its id is not also kept, for duplicate ids); every other entry is `lstat`ed and skipped unless it is a real folder. A candidate's folder goes with the candidate whatever its age. Any other folder is an orphan when the folder and its entries were all modified before the cutoff (`measure` in `core/real-dirs.ts`, one level deep); when the folder's own mtime is at or after `latestCutoff` it is fresh at every cutoff the scan serves, so it is dropped without reading it. An old folder is still read, because a handoff document is rewritten in place (`platform/shared/handoff/handoff-tool.ts`), which changes the file's mtime and not the folder's. A folder that cannot be read is kept. `plan` gives a candidate its folder unless the id is kept at that cutoff, and keeps the orphans touched before the cutoff.

## Apply (`core/sweep-apply.ts`)

`apply(plan, { agentDir, handoffRoot, current, isAlive })` removes nothing for an aborted plan. Otherwise it removes the chains through the pool, then the orphan runs, handoff folders and markers through the pool, and returns `{ sessions, runs, handoffs, bytes }` (`Removed`, from `core/sweep-plan.ts`), the counts and bytes of what it actually removed: a session's size from its re-check `lstat`, a run's or handoff folder's planned size only when its `rm` succeeded. For each chain it first reads the live markers and `lstat`s every member: when one is now live or present with another modification time, nothing of the chain is removed; a member already gone does not stop it. Then it goes through the members one at a time: it reads the live markers again and `lstat`s the member, stops the chain when the member is now live or changed, skips it when it is gone, and unlinks the file; only when that unlink succeeded it removes the member's stale runs and its handoff folder, and a failed unlink, like any error of the re-check, stops the rest of the chain. Then the orphan runs and handoff folders, then the dead markers. Runs and handoff folders are removed with `rm(path, { recursive: true })` (without `force`, so a folder already gone is not counted); the handoff root's safety is checked again before each one; after a folder lost a run its `agents/` and the folder itself are removed when empty. Every removal catches its own error, so one failure never stops the rest.
