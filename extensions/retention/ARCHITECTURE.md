# Retention architecture

`index.ts` re-exports `api/extension.ts`, whose `retentionExtension(deps)` builds the extension with `createManagedExtension` (namespace `pi-retention`) and one plugin, `retentionPlugin` in `api/plugin.ts`; the default export passes the handoff root (`handoffRoot()` from `platform/shared`), the process check `pidAlive` and a once-per-process record (`globalRecord("retention")` from the adapter, `{ swept, marker }`, which survives pi building a new extension for every session in the same process). Tests build their own with a temp handoff root and their own record. Its one setting, `retentionDays` (`core/settings.ts`, `pi-retention.json`; a number from 0 to 36500, default 60, 0 turns the sweep and `/retention` off), loads with `scope: "user"`: in a trusted project a `.pi/pi-retention.json` is not read and is reported as a settings error, so it turns off the sweep and `/retention apply` until the file is deleted; in an untrusted project it is not looked at. Any load error (an invalid value, bad JSON, a project file) is visible to the plugin through `settingsErrors()` and keeps it from removing anything. Extensions are not loaded in agent sessions (`createPiExtension`), so only main pi processes sweep.

## Session start and shutdown

- Every `onSessionStart` writes the liveness marker `<agentDir>/pi-retention/live/<session id>.<pid>.json`, `{ id, pid, file, parentSession }` (`null` for a missing one), to a temporary name and renames it in place, so a reader never sees half a marker (`core/live-markers.ts`). It creates the folder first and writes only when `lstat` shows a real folder. Then it removes the marker the record held, when that is a different file, and keeps the new path in the record. `onSessionShutdown` removes it only for `quit`; after `new`, `resume`, `fork` and `reload` the next start replaces it. A process only ever removes its own markers; the sweep removes those of ended processes.
- The first session start of the process sweeps when the marker was written, `retentionDays > 0` and the settings loaded without errors: `plan`, then `apply`, fire and forget, every error dropped. When anything was removed it notifies one line, `retention: removed <n> sessions, <m> agent runs, <k> handoff dirs older than <d> days`, zero parts left out (`ui/retention-report.ts`).
- The scanned folders are the real subfolders of `<agentDir>/sessions` and nothing else: `info.file` is never used to find a session dir, since `--session <path>` can point anywhere.
- `/retention` prints the plan without applying it: days, cutoff, counts to remove, kept sessions by reason, unreadable files, a skipped handoff root, or the abort reason. `/retention apply` plans and applies now and prints the counts, or the abort reason. Both print the settings errors instead when there are any, and say the sweep is off when `retentionDays` is 0. Output goes through `host.ui.notify`, as mcp-import's reports do.

## Plan (`core/sweep-plan.ts`)

`plan({ slugDirs, agentDir, handoffRoot, current, retentionDays, now, isAlive })` reads the disk and returns `{ cutoff, aborted?, sessions, orphans: { stems, handoffs }, markers, kept, unreadable, handoffsSkipped }`; nothing is removed. `cutoff = now - retentionDays * 86_400_000`. Every folder is listed one at a time (`core/serial.ts`), checked with `lstat` first, and its entries come from `withFileTypes`, so a symbolic link is never followed and never listed as a file or folder (`core/real-dirs.ts`). Session paths are compared through `pathKey` (`core/path-key.ts`: `resolve`, lower-cased on darwin and win32). Rules, in order:

1. Live set (`readLive`): markers whose `pid` is alive (`process.kill(pid, 0)` does not throw, or throws `EPERM`) give live ids (`id` from the JSON) and live files (`file` and `parentSession`); the current session's id, file and parent are live too. Every other marker is dead and listed for removal. When the live folder is not a real, readable folder (any `lstat` error but ENOENT, a symbolic link, a failed listing) the plan is `aborted`.
2. Sessions: every `*.jsonl` directly in each scanned folder, with its `lstat` modification time and header (`readSessionHeader` from the adapter: the first line within 64 KiB). A file without a valid header is `unreadable`: never removed, its folder never pruned. A read error other than a vanished file makes the plan `aborted: "<path>: <error>"`.
3. Kept: a session is `fresh` (modified at or after the cutoff) or `live` (its id or file is live); then the sessions a kept one names as `parentSession` are kept as `parent`, one level. The rest are candidates; each carries its id, its folder's stale runs (`stem`) and its handoff folder (`handoff`).
4. Orphans: a session folder whose `<stem>.jsonl` is not listed and not a live file, and `<agentDir>/pi-subagents/<id>/` whose id is not kept or live, go through the run rules. A kept or unreadable session's folder, or one beside a symlinked file, is skipped.
5. Run rules (`core/agent-runs.ts`, `staleRuns`): in `<folder>/agents/`, each real subfolder is a run, touched at the newest `lstat` time of the folder and its entries; an unparsable manifest is a plain run; a run whose manifest has a `worktree` with `cleanup` other than `"removed"` is spared. A subfolder without `manifest.json`, or one that cannot be read, is a spared run with no links and an infinite touch time, so a chain that names it is kept. Runs link through `predecessorId` and `successorId` inside the same `agents/`, walked both ways, stopping at an id already visited or not present. A run is stale when every run of its chain was touched before the cutoff and none is spared.
6. Handoff folders `<handoffRoot>/<id>/`, only when the root is safe (`core/handoff-root.ts`: a real folder, owned by `process.getuid()` where that exists, not group- or world-writable; `handoffsSkipped` when it exists and is not): skipped when the id is kept or live; a candidate's goes with the candidate; any other is an orphan when the folder and its entries were all modified before the cutoff.

## Apply (`core/sweep-apply.ts`)

`apply(plan, { agentDir, handoffRoot, current, isAlive })` removes nothing for an aborted plan. Otherwise it works one item at a time and returns `{ sessions, runs, handoffs }`, the counts of what it actually removed. For each candidate it reads the live markers again and skips the candidate when its id or file is now live, then unlinks the file only when its modification time still equals the planned one, and only when that unlink succeeded removes its stale runs and its handoff folder. Then the orphan runs and handoff folders, then the dead markers. Runs and handoff folders are removed with `rm(path, { recursive: true })` (without `force`, so a folder already gone is not counted); the handoff root's safety is checked again before each one; after a folder lost a run its `agents/` and the folder itself are removed when empty. Every removal catches its own error, so one failure never stops the rest.
