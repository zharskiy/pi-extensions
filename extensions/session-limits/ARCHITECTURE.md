# Session-limits architecture

## Boot

`index.ts` re-exports `api/extension.ts`, a `createManagedExtension` call with namespace `pi-session-limits`, `host: conversationOnly` (`core/conversation-host.ts`: session start (with the plain `SessionInfo`, created flag and parent included), turn end, agent start, idle, compact and command runs pass only in `tui` and `rpc` modes) and `settings: { defaults, schema, file }` from `core/settings.ts`. The manager reads `pi-session-limits.json` from the user and project settings on every session start, before the plugin's own session-start handlers, and reports errors as `pi-session-limits settings: …` warnings; the plugin reads `ctx.settings` at use time. Its one plugin, `sessionLimitsPlugin` (`api/plugin.ts`), registers the `handoff` tool the `pi-handoff-request` and `pi-handoff-seed` message renderers (`platform/ui-kit/handoff-rows.ts`) and the `pi-session-limits:kept-rule` and `pi-session-limits:kept-message` entry renderers (`ui/kept-entries.ts`), and starts `watchLimits` (`core/limits.ts`) with `segmentFor` (`ui/threshold-text.ts`) for the notice text. It returns nothing to undo; `watchLimits` clears its own timers on session shutdown.

`core/limits.ts` is the state machine: the phases, the displayed handoff request, the saved handoff (kept from the `handoff` tool's callback), the `/session-handoff` command, the switch, the `pi:busy` subscription and the user messages kept through `Host.onInput`. `core/thresholds.ts` holds the pure decisions (level, next step; the level is the shared `limitLevel` over the shared `mainLimit`, both in `platform/shared/handoff/handoff-limit.ts` with the `Limits` type, and the footer tones its context figure with the same pair) and `core/handoff.ts` what the main session says in a handoff: `HANDOFF_COMMAND`, `MAIN_AUDIENCE` (statuses `done`, `partial`, `blocked`, the background-work rule: the automatic switch waits for running work, each running piece goes under Evidence with its id, what runs it, the question it answers and what the result is for, that use under Next, and results arriving later go into the seed; and the `Skills: <names>` line), `sessionPreface` (the seed's preface, naming `/session-handoff` for a manual handoff), `withLateResults` (the held results appended after the handoff under a fixed heading), `userPrompts` (the kept messages as the new session's user prompts: consecutive messages joined into one by `joinParagraphs`, the one join the editor text also uses, with all their images, and a message starting with `/`, after any leading spaces, kept as a prompt of its own and sent from its slash, so pi expands it), the handoff path and the validator. The instruction is built by the shared `handoffInstruction` with `MAIN_AUDIENCE`, and the seed text by the shared `seedText` over `sessionPreface`; the template lives in `platform/shared/handoff/handoff-prompt.ts`.

## Runtime

- Active only in `tui` and `rpc` modes (a `Host` wrapper suppresses events otherwise). Thresholds compare main session context tokens to `min(window × ratio, token cap)`: the soft threshold (`softRatio` 0.45, `softTokens` 125,000) shows the warning notice `» handoff at <hard threshold> tokens · <used> used` (`» handoff at 175k tokens · 142.3k used`) through `HostUi.setNotice` (key `pi-session-limits`, below the editor and above the footer block), the hard threshold (`hardRatio` 0.60, `hardTokens` 175,000) triggers the handoff. Ratios decide on small windows, the caps on large ones (`mainLimit` in `platform/shared/handoff/handoff-limit.ts`).
- On each session start the plugin publishes its settings object on `LIMITS_CHANNEL` (`session-limits:limits`, `{ softRatio, hardRatio, softTokens, hardTokens }`, nothing else, nothing on disable), so the footer can compute the same thresholds from the live window with `mainLimit`. The settings change only on session start, and the managed settings watcher registers its reload before the plugins, so the payload is current. The wrapped `Host` publishes only in `tui` and `rpc` modes.
- Sequence: turn end at hard level -> send the shared handoff instruction (the template makes the model call the `handoff` tool and then end its turn without a reply, since the tool row already shows the save) as a displayed custom message (`Host.sendMessage`, custom type `pi-handoff-request`, delivered after the run, `details` `{ reason: "limit", tokens, request }`, or `{ reason: "manual", command: "/session-handoff" }`) drawn in the transcript by the shared request row (`» handoff requested · 175k of 175k tokens`, the command label when manual, the instruction on expand) with the path `<OS temp dir>/pi-handoff/<session id>/main-handoff.md` and no toast (the row is the only sign) -> the model calls the `handoff` tool, which writes the file, validates it (same six sections, Status `done`, `partial` or `blocked`) and returns the errors to the model at once; its callback hands the text and the validation to `core/limits.ts`, and on each turn end/idle the phase machine looks at the last save -> if valid and no busy source -> dispatch `/session-handoff` -> `newSession({ parentSession, keepSelection: true, showPrevious: { label }, continueWithSeed, fill })`, where `fill` returns the seed, follow-ups and editor text and runs only when the new session is ready (the adapter calls it inside pi's `withSession`, after the old session's shutdown handlers), keeping the model and thinking level (the adapter restores them in the new session; pi's defaults are untouched), showing the previous session's transcript above the seed (the seam rule reads `handed off · context limit` after an automatic handoff and `handed off · /session-handoff` after the command) (the adapter's `pi-adapter:previous-session` entry, drawn from the old file and never sent to the model) and seeding the new session with a `pi-handoff-seed` custom message holding the handoff (`details` `{ from: "session" }`, so the row takes the session title). `continueWithSeed` is set for every automatic handoff, whatever its Status (`done`, `partial` or `blocked`): the seed then starts a run and the new session carries on. After any `/session-handoff` the new session waits for the user.
- `/session-handoff [what the next session is for]` starts the same flow on demand, with the reason "the user ran /session-handoff" and the optional focus folded into the instruction and the new session's seed. By phase: while watching it sends the instruction, or holds it while pi is busy (see `queued` below); while requested it only notifies that one is already being written; while waiting it switches at once without arguments; while stuck it switches at once when the last save is valid and no focus was given, otherwise it sends (or, while pi is busy, queues) a fresh request; the switching call is the internal dispatch. A manual handoff does not wait for busy sources: when the last save is valid it dispatches the switch and the busy confirm (`Switch to a new session?`) asks. On No the phase becomes `waiting` and the switch happens when the work ends, as in the automatic flow, and stays manual, so the new session still waits for the user, with what the user typed meanwhile in its editor.
- `queued`: when `/session-handoff` would send a request while a run is active (tracked from `onAgentStart` to `onIdle`) or pi is not idle (a compaction before or without a run), the request is held in phase `queued` instead of going into pi's follow-up queue, which RPC `abort` and a mid-turn `/compact` do not clear. A clean settle sends it; an aborted settle drops it with `Session handoff cancelled.` and returns to `watching`. After a compaction with no run active, `onCompact` polls `isIdle()` every 250 ms and sends it once pi is idle, unless a run starts first, which then holds it until its settle. While queued a new focus replaces the stored one and the automatic request does not fire, so a turn end at the hard level sends the queued manual request at settle.
- Esc during the writing turn of a manual request (the settle reports `aborted` while the phase is `requested`) cancels it: the phase returns to `watching`, path, focus and counters are cleared, and an info notice says `Session handoff cancelled.`; an automatic request still gets its resend.
- The `handoff` tool (`platform/shared/handoff/handoff-tool.ts`, registered in every mode, print and json included) is the only way to save: no file is read back, no modification time is checked, and a file written by hand is not picked up. It saves only while the phase is `requested`, `waiting` or `stuck` with a path set, and refuses in `watching`, `queued` and `switching`, and in the modes where no request is ever made. Agents are unaffected: every agent gets its own `handoff` tool, which replaces this one. A settle with no valid save gets one resend (`The handoff was not accepted: …` with the errors, or `no handoff was saved with the handoff tool`); after 2 instructions the phase becomes `stuck`, the notice tells the user to ask the session to call the `handoff` tool and run `/session-handoff` again (it switches at once when a valid save exists). No user turn starts while a handoff is in flight (see kept user messages below), so a valid save is never superseded by later activity and the switch uses it as it is.
- Busy sources: any extension can publish `pi:busy { source, busy }`. Subagents publishes it while any agent is open; the switch waits until all sources are idle (then 1 s), and a switch with busy sources asks for confirmation (always for a manual handoff). The notifications extension reads the same channel to hold its idle notification.
- Pending handoff and held results: the plugin publishes `pi:handoff-pending { source: "pi-session-limits", pending }` whenever that value changes, `true` from the moment a request is sent through phases `requested`, `waiting` and `switching` (`handoffInFlight` in `core/thresholds.ts`), `false` once the phase leaves them (Esc cancel, `stuck` after the give-up, a failed or stalled switch), and its current value at every session start. While it is `true`, sources hold the results that would start a run in this session and publish them on `pi:held-results { source, text }`, each publish carrying everything that source holds (subagents holds its wakes this way), so no wake turn keeps pi from being idle or reads as user activity while the handoff is pending. The plugin keeps the last text per source and forgets them all when pending goes `false`, at which point the sources send them as usual. `performSwitch` appends the held texts to the handoff in the seed under `Batch results that arrived while the handoff was pending:`, so the new session gets the handoff and the late results in one seed run. Because the seed is composed in `fill`, results that reach the plugin while pi tears the old session down still go in it.
- Kept user messages: while `handoffInFlight` holds, the `Host.onInput` handler consumes every prompt whose source is not `extension` (typed or sent over RPC, idle or as a mid-run steer or follow-up; extension commands such as `/session-handoff` never reach it, prompt templates and skills such as `/review` or `/skill:x` reach it unexpanded), keeps its text and images in a list next to `held`, and shows it, so the old session never answers it and no user turn can start while the handoff is pending. Messages from other extensions pass. `performSwitch` delivers them through `fill`, so a message typed while the old session shuts down is delivered too. After an automatic handoff the seed holds only the handoff and the held results; the kept messages go out as `followUps` through `userPrompts`, which the adapter sends as ordinary user messages after the seed (text and images, with template expansion), queued behind the seed's run, so the new session shows them as pi's own user messages and answers them after it has picked the handoff up. They are joined into as few messages as possible because pi delivers each queued follow-up as its own user message and turn (its default `one-at-a-time` follow-up mode); a message starting with `/` stays alone, since pi expands a prompt template or skill only when the whole text starts with `/name`, and anything joined after it would become its arguments. After `/session-handoff` (`continueWithSeed` false) every message, `/` ones included, is joined into `editorText`, which the adapter puts in the new session's editor; an editor holds no images, so a message kept for a manual handoff loses its images when it is kept, with a warning. In TUI mode (`info.mode` of the last `onSessionStart`, so no live session is needed when a failed switch restores the messages after shutdown) a kept message is shown in the old session's chat as custom entries (entry names, data types and parsers in `core/kept-entries.ts`, labels and drawing in `ui/kept-entries.ts`, registered in `api/plugin.ts`; pi draws a custom entry at once, even mid-run above the live reply, stores it in the session file and never sends it to the model): each message appends a `pi-session-limits:kept-message` entry (`{ text, images }`, the image count) drawn like pi's user message: registered with `{ flush: true }`, so the adapter gives it the whole chat width and pi's output pad, it is a block on `userMessage` (pi's `userMessageBg`) from the chat's left edge to its right edge, a blank row above and below, the text wrapped the pad in from each side in `userMessageText`, then a muted `N images` line; pi's one-row gap above a custom entry is the same gap it leaves above a user message, so the block sits where pi's own bubble would. Both kept renderers are registered with `{ previousSession: false }`, so the previous-session block the new session shows above itself leaves the kept rule and messages out: the messages are re-sent into the new session as its user prompts and would otherwise appear twice. Before a message, `keptRuleFor` picks the rule the current state calls for and, when it differs from the last rule drawn for this handoff, appends a `pi-session-limits:kept-rule` entry (a `labelledRule`, the same rule as the transcript's `worked …` line): `kept` (`handing off, messages below go to the new session`), `editor` after `/session-handoff` (`… go to the new session's editor`), and `waiting` / `editor-waiting`, which add `/session-handoff switches now`. So several messages share one rule, a message during the switch adds none, and `/session-handoff <focus>` while waiting draws a fresh rule without the stale hint. A message whose images were dropped (manual handoff) and that has no text draws nothing. The next handoff starts with a new rule. Outside TUI (rpc) nothing is drawn and a notice `Kept for the new session: …` names where the message goes, adding `Run /session-handoff to switch now.` while waiting, since the session cannot be talked to until it switches. When pending turns `false` without a switch (Esc cancel, give-up, a failed, cancelled or stalled switch, a queued manual request), `syncPending` puts the joined text back in the current editor ahead of whatever is typed there, says so (in TUI a rule with state `returned`, `handoff abandoned, messages are back in the editor`, appended whenever a kept message was drawn, images-only ones included, so the chat does not claim they went on; outside TUI an info notice when text came back) and, when any kept message had images, warns once that they were dropped; nothing is sent. The notice below the editor does not count them, since it shows no handoff progress.
- All state is in memory, per extension instance; the only file is the handoff the tool writes. A pending switch whose `/session-handoff` command never runs ends in the failed phase at the next idle, turn end or user message, which then goes through and gets the kept messages back in the editor; a second `/session-handoff` while the switch runs is ignored. A context window of 0 or unknown token usage turns the extension off for that moment (no request, notice cleared).
- The seed message is drawn by a message renderer (`Host.registerMessageRenderer`, `handoffSeedMessage` in `platform/ui-kit/handoff-rows.ts`) as an informational row like the `/context` row: `» handoff from the previous session` with the seed's first sentence, muted, on the `↳` line and the `(ctrl+o to expand)` hint after it (cut with the sentence on a narrow terminal); expanded, the whole seed wrapped at column 4.
- `Host.onCompact` fires after pi compacts the main session; session-limits uses it to forget its cached context size (pi reports unknown tokens after compaction), which clears the notice until the next turn. The notice only warns: in every phase except `stuck` it is the threshold line, `» handoff at <hard threshold> tokens · <used> used` in the warning colour, shown once the soft level is reached and empty below it or while the context size is unknown; phases in progress add no text of their own, since the transcript already shows the handoff request. `stuck` shows `✗ handoff failed · run /session-handoff` in the error colour (`segmentFor` in `ui/threshold-text.ts`).
