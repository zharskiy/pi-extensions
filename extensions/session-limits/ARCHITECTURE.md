# Session-limits architecture

## Boot

`index.ts` exports `api/extension.ts`, a `createManagedExtension` call with namespace `pi-session-limits`, `host: conversationOnly` (`core/conversation-host.ts`: session start, turn end, agent start, idle, compact and command runs pass only in `tui` and `rpc` modes) and `settings: { defaults, schema, file }` from `core/settings.ts`. The manager reads `pi-session-limits.json` from the user and project settings on every session start, before the plugin's own session-start handlers, and reports errors as `pi-session-limits settings: …` warnings; the plugin reads `ctx.settings` at use time. Its one plugin, `sessionLimitsPlugin` (`api/plugin.ts`), registers the `handoff` tool and the `pi-handoff-request`, `pi-handoff-seed` and legacy `pi-session-limits-handoff` message renderers (`platform/ui-kit/handoff-rows.ts`) and starts `watchLimits` (`core/limits.ts`) with `segmentFor` (`ui/threshold-text.ts`) for the notice text. It returns nothing to undo; `watchLimits` clears its own timers on session shutdown.

`core/limits.ts` is the state machine: the phases, the displayed handoff request, the saved handoff (kept from the `handoff` tool's callback), the `/session-handoff` command, the switch and the `pi:busy` subscription. `core/thresholds.ts` holds the pure decisions (level, next step; `mainBudget` builds the budget from `thresholdsFor` and the level comes from `budgetLevel`, the evaluator subagents share, in `platform/shared/handoff-budget.ts`; the `Limits` type and `thresholdsFor` come from `platform/shared/handoff-limits.ts`) and `core/handoff.ts` the handoff path and validator (the statuses of `MAIN_AUDIENCE`). The instruction is built by the shared `handoffInstruction` with the main audience, and the seed text by the shared `successorPreface` and `seedText`; both live in `platform/shared/handoff-prompt.ts`.

## Runtime

- Active only in `tui` and `rpc` modes (a `Host` wrapper suppresses events otherwise). Thresholds compare main session context tokens to `min(window × ratio, token cap)`: the soft threshold (`softRatio` 0.45, `softTokens` 125,000) shows the warning notice `» Handoff at <hard threshold> tokens · <used> used` (`» Handoff at 175k tokens · 142.3k used`) through `HostUi.setNotice` (key `pi-session-limits`, below the editor and above the footer block), the hard threshold (`hardRatio` 0.60, `hardTokens` 175,000) triggers the handoff. Ratios decide on small windows, the caps on large ones (`thresholdsFor` in `core/thresholds.ts`).
- On each session start the plugin publishes its settings object on `LIMITS_CHANNEL` (`session-limits:limits`, `{ softRatio, hardRatio, softTokens, hardTokens }`, nothing else, nothing on disable), so the footer can compute the same thresholds from the live window with `thresholdsFor`. The settings change only on session start, and the managed settings watcher registers its reload before the plugins, so the payload is current. The wrapped `Host` publishes only in `tui` and `rpc` modes.
- Sequence: turn end at hard level -> send the shared handoff instruction (the template makes the model call the `handoff` tool and reply `handoff saved`) as a displayed custom message (`Host.sendMessage`, custom type `pi-handoff-request`, delivered after the run, `details` `{ reason, tokens, request }`) drawn in the transcript by the shared request row (`» Handoff requested · 175k of 175k tokens`, `· /session-handoff` when manual, the instruction on expand) with the path `<OS temp dir>/pi-handoff/<session id>/main-handoff.md`, plus one info notice naming the path -> the model calls the `handoff` tool, which writes the file, validates it (same six sections, Status `done`, `partial` or `blocked`) and returns the errors to the model at once; its callback hands the text and the validation to `core/limits.ts`, and on each turn end/idle the phase machine looks at the last save -> if valid and no busy source -> dispatch `/session-handoff` -> `newSession({ parentSession, seed })`, seeding the new session with a `pi-handoff-seed` custom message (`details` `{ from: "session" }`) holding the handoff. The plugin also registers the legacy seed type `pi-session-limits-handoff` with the same renderer, so sessions seeded by older versions still draw.
- `/session-handoff [what the next session is for]` starts the same flow on demand, with the reason "the user ran /session-handoff" and the optional focus folded into the instruction and the new session's seed. By phase: while watching it sends the instruction (notice `» Handoff writing the document`), or holds it while pi is busy (see `queued` below); while requested it only notifies that one is being written; while waiting it switches at once without arguments; while stuck it switches at once when the last save is valid and no focus was given, otherwise it sends (or, while pi is busy, queues) a fresh request; the switching call is the internal dispatch. A manual handoff does not wait for busy sources: when the last save is valid it dispatches the switch and the busy confirm (`Switch to a new session?`) asks. On No the phase becomes `waiting` and the switch happens when the work ends, as in the automatic flow.
- `queued`: when `/session-handoff` would send a request while a run is active (tracked from `onAgentStart` to `onIdle`) or pi is not idle (a compaction before or without a run), the request is held in phase `queued` (warning notice `» Handoff after this turn`) instead of going into pi's follow-up queue, which RPC `abort` and a mid-turn `/compact` do not clear. A clean settle sends it; an aborted settle drops it with `Session handoff cancelled.` and returns to `watching`. After a compaction with no run active, `onCompact` polls `isIdle()` every 250 ms and sends it once pi is idle, unless a run starts first, which then holds it until its settle. While queued a new focus replaces the stored one and the automatic request does not fire, so a turn end at the hard level sends the queued manual request at settle.
- Esc during the writing turn of a manual request (the settle reports `aborted` while the phase is `requested`) cancels it: the phase returns to `watching`, path, focus and counters are cleared, and an info notice says `Session handoff cancelled.`; an automatic request still gets its resend.
- The `handoff` tool (`platform/shared/handoff-tool.ts`, registered in every mode, print and json included) is the only way to save: no file is read back, no modification time is checked, and a file written by hand is not picked up. It saves only while the phase is `requested`, `waiting` or `stuck` with a path set, and refuses in `watching`, `queued` and `switching`, and in the modes where no request is ever made. Agents are unaffected: every agent gets its own `handoff` tool, which replaces this one. A settle with no valid save gets one resend (`The handoff was not accepted: …` with the errors, or `no handoff was saved with the handoff tool`); after 2 instructions the phase becomes `stuck`, the notice tells the user to ask the session to call the `handoff` tool and run `/session-handoff` again (it switches at once when a valid save exists). User activity after the request causes the instruction to be re-sent before switching.
- Busy sources: any extension can publish `pi:busy { source, busy }`. Subagents publishes it while any agent is open; the switch waits until all sources are idle (then 1 s), and a switch with busy sources asks for confirmation (always for a manual handoff). The notifications extension reads the same channel to hold its idle notification.
- All state is in memory, per extension instance; the only file is the handoff the tool writes. A pending switch whose `/session-handoff` command never runs ends in the failed phase at the next idle or turn end; a second `/session-handoff` while the switch runs is ignored. A context window of 0 or unknown token usage turns the extension off for that moment (no request, notice cleared).
- The seed message is drawn by a message renderer (`Host.registerMessageRenderer`, `handoffSeedMessage` in `platform/ui-kit/handoff-rows.ts`) as an informational row like the `/context` row: `» Handoff from the previous session` with the seed's first sentence, muted, on the `↳` line and the `(ctrl+o to expand)` hint after it (cut with the sentence on a narrow terminal); expanded, the whole seed wrapped at column 4.
- `Host.onCompact` fires after pi compacts the main session; session-limits uses it to forget its cached context size (pi reports unknown tokens after compaction), which clears the notice until the next turn. Every notice follows one pattern, `Handoff <phase>` plus an optional ` · <detail>`, after pi's info marker `»` and in the warning colour (`» Handoff after this turn`, `» Handoff writing the document`, `» Handoff waiting for running work`, `» Handoff switching to a new session`), except the failure, `✗ Handoff failed · run /session-handoff` in the error colour (`segmentFor` in `ui/threshold-text.ts`); the normal level shows nothing.
