# Notifications architecture

`index.ts` re-exports `api/extension.ts`, which builds the extension with `createManagedExtension` (namespace `pi-notifications`) and one plugin, `notificationsPlugin` in `api/plugin.ts`. The manager's `settings` option (`{ defaults, schema, file: "pi-notifications.json" }` from `core/settings.ts`) reads the user file and the trusted project file at every session start, before the plugin's own session-start handler, warns once per error under `pi-notifications settings:` and patches `ctx.settings` in place; the plugin reads it at use time. The plugin subscribes to the host and the channels and forwards each event to `createNotifier` (`core/notifications.ts`), which owns the timers and the rules and sends through `HostUi.terminalNotify`. Its `enable` returns nothing to undo.

- Active only in `tui` mode and when `channel` is not `off`; otherwise it registers no key listener and arms no timer. Nothing is persisted, timers are unref'd and cleared on shutdown, and the key listener is dropped.
- Idle notification: `Host.onIdle` (pi's `agent_settled`, once per run) marks the settle pending and, when no source is on the busy channel (`pi:busy`, kept as a set of source names like session-limits), arms an `idleDelayMs` timer. `Host.onAgentStart`, any key (`HostUi.onKeyPress`, observed without consuming) and a busy source appearing cancel it; the last busy source clearing or a dialog ending re-arms it with the full delay while the settle is still pending. At fire time it checks only that no dialog or waiting source is open (a dialog starting does not clear the timer), sends `pi is waiting for your input` and clears the pending settle, so a settle notifies at most once.
- Agents and the wake: subagents holds the busy channel while any agent is open. Agents finishing while main is idle arm the timer, but the outbox's hidden wake starts a run at once, which cancels it; that run's settle arms it again. One notification follows the finished work.
- Waiting extensions: a source on the awaiting-input channel (`pi:awaiting-input`, `{ source, waiting, title? }`, parsed by `parseAwaitingInput` in `platform/shared/channels/host-channels.ts`) counts as an open dialog with that title, under the same rules below: it arms the dialog notification, holds the idle one, and `waiting: false` from the same source closes it like a dialog ending. Open waits are kept in a map keyed by owner (pi's dialog is one owner, each source its own), so a dialog opening over a waiting source, or the reverse, closes only its own entry. The questionnaire publishes it while it waits to show its form and while the form is open, since pi reports that form only as a `custom` dialog, which is ignored.
- Dialog notification: `Host.onDialog` (pi's `ui_prompt_start`/`ui_prompt_end`, outermost dialog only, main-session dialogs only since agents never open one; `custom` overlays ignored). `dialogDelayMs` after the later of the latest wait opening and the last key it sends `pi needs your input: <title>` (just `pi needs your input` when that wait has no title) with the most recently opened wait's title and marks every open wait as notified, so each notifies at most once; a wait closing re-arms the full delay while a wait not yet notified remains open, and cancels it otherwise.
- Output: `HostUi.terminalNotify(message, channel)` with `auto` (OSC 9/777 only, no BEL: the idle notification follows ordinary replies too, and a bell each time is noise) or `bell`.
