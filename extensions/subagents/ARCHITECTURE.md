# Subagents architecture

How the extension behaves at runtime. The file map is in [STRUCTURE.md](STRUCTURE.md); the repository-wide picture (adapter, manager, channels shared with other extensions) is in the root [ARCHITECTURE.md](../../ARCHITECTURE.md).

`index.ts` re-exports the extension from `api/extension.ts`, the single entry: it hands the extension's root, settings and the plugin list from `api/plugins.ts` to `createManagedExtension` in `platform/extension-manager/`, which boots them on the pi adapter in `platform/pi-adapter/` and keeps child sessions from loading the extension's folder. Only `platform/pi-adapter/` talks to pi. The plugin entries in `api/plugins/` use the shared contract (`platform/pi-adapter/index.ts`) and the typed bus and wire the theme-free code in `core/` to the painted code in `ui/`; `core/` never imports `ui/` or `api/`, and `ui/` never imports `api/`. `core/model/` holds the subagents types, bus events, service map, settings schema and paths. Plugin and component tests are under `tests/` (local helpers in `tests/support/`); adapter tests live in `platform/pi-adapter/tests/`, manager tests in `platform/extension-manager/tests/`, and the shared fakes and harnesses in `test/framework/`. The prompt-quality evals of the main-session prompt and the planner, reviewer and implementer agents live in `test/evals/subagents/`.

## Plugins

Plugins (`api/plugins.ts`, one entry each in `api/plugins/`; requirements in brackets): `fetch-tool` (the `fetch` tool as a `fetchTool` service, no requirements), `agent-registry` (in-memory records, `manifest.json`), `agent-definitions` (agent `.md` files, agent prompts), `run-agent` [registry, definitions] (runner, tools, outbox, main prompt, the `handoff` service: `instruction` and `validate`), `usage-report` [run-agent], `agent-status` [registry], `limits` [registry, run-agent], `agent-panel` [registry] (panel below the footer block, keyboard selection), `interrupt` [registry, run-agent] (Esc on an empty idle editor offers to stop running agents), `agent-setup` [definitions] (`/agents setup` and `/agents create`, the `agentSetup` service with their usage lines, the model-only `agent_skills_proposal` tool), `agent-view` [registry] (`/agents`: the menu, the list and the agent view in one overlay, the `agentView` service; `setup` and `create` are routed to `agentSetup`, and give an error naming that plugin when it is off).

## Agent definitions and prompts

- Markdown files with frontmatter are loaded from the built-in `agents/` when the plugin enables, and from the built-in `agents/`, then `<agentDir>/agents/`, then `<cwd>/.pi/agents/` (trusted projects) at session start. Later files override earlier ones by `name`. Invalid files, unknown `subagents` references and `subagents` cycles remove the offending definitions and produce warnings.

These are the frontmatter fields of an agent file:

| Field | Type | Required or default | Meaning |
|---|---|---|---|
| `name` | letters, digits, `-`, `_` | required | Name the caller passes to `run_agent`. |
| `description` | text | required | When to use the agent; shown in the `run_agent` description. |
| `model` | `name[:thinking]` or `inherit[:thinking]` | `inherit` | Model the agent runs on; `inherit` is the main session's model. |
| `limit` | integer, at least 5000 | required | Context limit in tokens; at the limit the agent writes a handoff. |
| `tools` | list, `[]` or `all` | required | Tools the agent may use; any tool also brings `codemode` and `tool_search`, plus every MCP tool with `mcp: true`, and `[]` brings none of them. `[]`: no tool of its own (only the agent tools when it may start agents), and no MCP server connects (see [A run_agent call, end to end](#a-run_agent-call-end-to-end)). `all`: the tools active in the main session when the agent starts, as pi's `defaultTools` setting, `--tools` and any tools toggled since left them; this package's tools follow `subagents`. |
| `skills` | list, `[]` or `all` | required | Skills by name. `[]`: none. `all`: every skill of the agent's caller (the main session's loaded skills, or the calling agent's skills). Named skills are picked from the available skills, found from the main session's project, so a `worktree: true` agent gets uncommitted project skills too. A name that is not an available skill gives a warning at session start and is skipped; the others still load. |
| `subagents` | list of agent names, `[]` or `all` | required | Agents it may start. `[]`: none. `all`: every other agent, among those loaded, never itself. |
| `worktree` | `true` or `false` | `false` | `true` runs the agent in its own git worktree. See [Worktrees](#worktrees). |
| `mcp` | `true` or `false` | `true` | `true` loads pi's MCP built-in in the agent's session, so it connects every enabled server and gets every MCP tool; `false` keeps `codemode` and `tool_search` but no MCP. The shipped leads have `true`, the chores `false`. |

- Shipped agents name `model: provider/id:thinking`. A file without a `model` line (or with `inherit[:thinking]`) runs on the main session's model and, without a suffix, its thinking level.
- An agent's configured model and thinking are computed in one place, `parseDefinition` (`core/agent-definitions/loader.ts`), and stored on the `AgentDefinition`; the runner (`planModel`) and the `run_agent` description read them only through the `definitions` service. `startBatch` reads each definition once and keeps it in the agent's launch slot, so a queued agent and every handoff successor start with that definition even if a reload changed it meanwhile. The `model` parameter of `run_agent` and the main-session fallback are applied on top in `planModel`.
- Overrides: `pi-subagents.json` may hold `agents: { <name>: { model?, thinking?, skills? } }`. The settings schema parses it as an object rule (`core/model/settings.ts`: `model` is `provider/id[:thinking]` or `inherit`, a suffix becomes `thinking`; `thinking` a known level; `skills` a list or `all`; any other field is an error that says to create an own agent), and `loadSettings` merges user then project per agent and per field. After the files are loaded (the file that wins the name decides the definition), `loadDefinitions` applies each override field by field: each field replaces the definition's (`inherit` clears the model), so `skills: []` gives an agent no skills. It checks each override at load: a `model` that `runtime.resolveModel` does not resolve, or `skills` that name a skill that is not available (`runtime.skillNames()`), warn and drop that field; an agent file's own `skills` list (when no override replaced it) that names a skill that is not available gives a file warning and is kept, since unknown names are skipped at spawn; an override for an unknown agent warns, and one for an agent defined only in an untrusted project's `.pi/agents` gives an info message instead (each notice once per extension instance). The `model`, `thinking` and `skills` value checks (and the unknown-skill text) live in `core/model/agent-override.ts`, shared by the settings schema, the one-line `/agents setup` and `/agents create`; `core/model/model-resolution.ts` `resolutionProblem` is the one text for a model that does not resolve (the load notice, the setup line and, wrapped with advice, `run_agent`). One load reads `runtime.skillNames()` at most once, resolves each override model once, and reads the untrusted project's agent files only when an override names an agent that is not loaded. `definitions.reload()` is the one place that re-reads the settings files at runtime (`reloadSettings` in `core/model/settings.ts`, the same function the session start uses) and then re-runs the load; `/agents setup` calls it after a save. Every `reloadSettings` (session start and `definitions.reload()`) also calls `runtime.reserveCodemodeWorkers(maxConcurrent * maxDepth)`, the agent sessions the tree may keep alive (an agent that waits on its own batch gives up its semaphore slot but keeps a codemode worker when it waits inside a script); a shortfall joins the settings errors and is shown once like them. Settings errors, invalid-file errors, file warnings and override notices are each shown once per extension instance.
- `mcp` (frontmatter, `true` or `false`, default `true`) is stored on the definition and passed to `SpawnSpec.mcp`; the shipped leads set `true`, the chores `false`.
- Agent prompt = pi's own prompt for the child, with appended text: `prompts/base-system-prompt.md` (shared rules and the one result contract: `Status: done|partial|blocked`, the agent's sections, `Verification`, `Open`), then `# Agent: <name>` and the file body. The one exception to the result contract is the handoff reply, the line `handoff saved`. Agent bodies hold only the role, its rules and its sections; no output line.
- The shipped roster is ten agents: `scout` (codebase questions), `editor` (exactly described edits), `planner` (ordered batches of briefed tasks), `implementer`, `reviewer`, `fetch`, `shell`, `image`, `verifier` (pass, fail or incomplete against given checks) and `general` (fallback). `planner` may start `scout`, `shell` and `fetch`, `reviewer` `scout` and `shell`, `implementer` `scout`, `shell` and `verifier` (it runs no checks itself; one `verifier` is its last step); `general` may start every other agent. `scout` replaces the former search agent, with no alias.
- The main session keeps its full tool set; nothing restricts it. Its prompt is `prompts/main-session.md` (its role: understand the request, read one short file or run one orienting command when a brief needs it, delegate the rest, judge every result, and for multi-step or ambiguous work agree a plan with the `planner` lead and the user first; a guide to which agent fits; the brief template; the result handling, where `unverified partial output` is not a result and a `Result file:` line on a planner result means reading the file before any batch). The lead prompts add that a lead never hands its whole task to another agent and returns `Status: partial` instead. The main prompt is set by `run-agent` at session start (plus `prompts/main-session-agent-status.md` when the agent-status plugin is on). The agents' handoff instruction is the shared template in `platform/shared/handoff-prompt.md`, built by `core/run-agent/handoff.ts` with the agent audience; its rule for the main session's own handoffs (start no agents, list the ones delegated to) stays in `prompts/main-session.md`. Prompt files are read once when their plugin enables.

## A run_agent call, end to end

1. Main model calls `run_agent { agents: [...], wait? }` (each item: `agent`, `task`, `description`, optional `files`, `model`, `skills`) -> `runner.startBatch` validates agent names, the caller's allowed `subagents`, depth (`callerDepth + 1 <= maxDepth`, main is depth 1), the spawn cap (`capError`: an agent caller may start at most `maxChildrenPerAgent` agents per run, counted per handoff-chain root over all its batches in the runner's `spawned` map, and a refused call starts nothing; the main session is not capped), the `skills` names (`skillError`: each must be in the caller's effective skill set, `runtime.sessionSkillNames()` for the main session and the caller record's `skills` for an agent, and the agent's tools must include `read`; a union with the agent's own skills, `all` resolved to the caller's effective set, is stored on the new record as its `skills` and passed to the spawn as names, never as `all`) and resolves every model. Any error throws and nothing starts.
2. Registry creates one record per agent (`queued`), writes `manifest.json`, emits `agent:changed`. The tool reports the batch through `update(text, details)` at once (`details.agents`: id, agent, description, model), returns ids and tells the model to end its turn (`wait: true` blocks until the batch settles instead). The block renders with `renderShell: "row"`: `renderCall` draws nothing, so only the result row is drawn (it stays defined so pi draws no generic call line; the working-status line shows the run); `renderResult` draws the block from the first update as one row (`ui/run-agent/render.ts` over `platform/ui-kit/row.ts`, bound to the tool specs by `ui/run-agent/pending-rows.ts`) whose title is the header and whose children are one nested row per agent, from the registry (chain terminals, chain totals). The header is `N [background] [kind] agent(s)`, with the kind when every agent of the batch shares it. Its mark (`blockMark`) comes from the chain terminals: `◌` while any is open, then `✗` when the call or an agent failed, `⊘` when every agent was stopped or handed off, otherwise `✓` with `· N stopped` when some were; an interrupted `wait: true` call, whose result is pi's abort text, is `⊘ … · stopped`. Once every terminal closed, the header adds the batch receipt: the wall time from the earliest start to the latest close, then the summed calls, tokens and cost. While any record of a main-session batch is open, the header carries the hint `(↓ to manage, ← to list)`, each key only while its plugin (`agent-panel`, `agent-view`) is not in `disabledPlugins`, `← to list` dropped first when the header is narrow; a batch an agent started, drawn only in the agent view, gets no hint. Each agent row is `name  description · id:thinking` (the model without its provider, dim, left out when fewer than 20 columns would stay for the description) with a receipt status line under it: a background batch never ticks in scrollback, so open agents read `Queued`, `Starting`, `Running` or `Stopping` (the panel carries the live figures), a `wait: true` batch is the live bottom row and shows the running receipt (`Elapsed 42s · 9 calls · …`), a closed agent its finished receipt with the worktree outcome after it, a short failure reason leads the receipt and a long one wraps under it, two rows and a count line while collapsed. An errored call without a batch is `✗ No agents started · <reason>`, a long reason on the `↳` line, the whole error when expanded. The adapter indents each line by pi's `outputPad` and cuts it, never wraps. Each rendered block is computed once per width and changes only when `renderResult` runs again: the stored `invalidate` (the latest per batch) re-renders through `watchAgents` at once on an `agent:changed` of an open batch, then at most every `renderThrottleMs`, and once more at `batch:settled`; without a record (a `/fork` or `/clone` of the session, whose agents dir is new) a row carries `»` and reads `Status unavailable · /agents <id>` (`Status unavailable` when the agent-view plugin is off).
3. `launch` per agent: acquire a semaphore slot (`maxConcurrent`, shared by the whole tree) -> optionally create a git worktree -> `runtime.spawn(SpawnSpec)` -> record becomes `running` -> `child.start(task)` -> messages queued while `queued` are steered in.
4. `spawn` builds an in-process pi `AgentSession` (not a subprocess) inside the child scope: in-memory copy of the main session settings with compaction disabled, `reserveTokens` set and cache warming off; tools = the definition's allowlist or the main session's active tools (minus excluded extension paths), plus `codemode` and `tool_search` unless `tools: []`, and MCP (pi's MCP built-in and the MCP tool names) only when the spec's `mcp` is not false (the definition's `mcp`, default true), plus custom tools from the runner (the `handoff` tool for every agent, the agent tools when it may start agents, and the `fetch` tool, built by the `fetch-tool` plugin from the `fetchTimeoutSeconds`, `fetchMaxBytes` and `fetchMaxChars` settings, only when the definition's `tools` lists `fetch`; `tools: all` does not include it); skills = the inventory's skill files named by the spec's `skills` (always a resolved list; `noSkills` and `additionalSkillPaths`, so the child's own cwd is never scanned and a worktree agent keeps uncommitted project skills; names outside the inventory are dropped); model resolved again by exact ref; session file in the agent's dir with `parentSession` = main session file; binds no UI, like pi's print mode: dialogs resolve to their denials (`confirm` false, `select` and `input` undefined), `notify` does nothing, `ctx.hasUI` is false; only the main session is interactive, and an agent that needs a decision reports it in its result.
5. The child's first message is `Task from <caller> (agent id <id>):`, `Agent folder: <dir>` (`core/run-agent/task.ts`; the agent's own folder, where a shell agent keeps its command logs), the task and `Input files:`.
6. A hidden child extension cancels every compaction and, on the first provider request, appends a `pi-subagents:prompt-record` entry (`{ providerPayload }`, the raw provider payload) to the child session file. The entry stays in the session file and `runtime.readSession` returns its payload with the transcript items (`kind` plus pi's raw message; user items also carry their text, tool items their `toolCallId`); the agent view shows its provider payload, the first request as sent, as one collapsed Request block (key `r`; key `c` copies it).
7. Child events (`turn_end`, `assistant_message`, `tool_start`, `settled`) update the record (turns, tool calls, tokens, context, last text, and `activity`: the last tool name or `writing` after assistant text, set only when it changes and cleared while the agent waits idle for its own batches) and emit `agent:turn` and `agent:usage`.
8. On `settled`: if the agent has its own open batches or undelivered wakes, it goes idle and releases its slot. Otherwise it closes: `done` with its result written to `result.md`, or `failed` (abort, error stop reason, empty result). The result is picked without an extra turn (`pickResult` in `core/run-agent/result.ts`): the last text of `child.runTexts()` that carries a `Status:` line within its first five non-empty lines (case-insensitive, markdown emphasis and heading marks ignored), else the run's last text; a run without texts gives an empty result (the cumulative last text of earlier runs is never used). The Status-line check is stored on the record as `statusLine` when it closes, so the batch text does not scan the result again. A failed or stopped agent's text, picked the same way, is stored as well when there is any, as partial output. Closing releases the slot, emits final usage, disposes the session and immediately stops any open children of that agent.
9. When every record of the batch is closed and every worktree cleanup is done, `batch:settled` fires and the batch text (one `## <id> (<agent>) - <state>` section per chain terminal, its summary line the plain receipt the UI draws, `Done · 1m 5s · 4 calls · 12.3k tokens · $0.04` or `Failed · <error> · …`, summed over a chain; results inline up to `inlineResultChars` (8000), otherwise the head up to it, cut at the last newline before the limit, and a last line `Result file: <path> (<N> more chars)`; a done result without a Status line gets a `(shape: no Status line)` note; failed and stopped agents' text, under the same rule, with an `(unverified partial output: <error>)` note) is posted to the caller's outbox.
10. Outbox: for the main session the batch texts posted in one synchronous pass are joined (`---` between them) into one `pi-subagents:wake` hidden message sent through `Host.sendHiddenMessage` on the next microtask. The adapter picks the path: while a run is active the hidden message joins it as a follow-up; when idle the hidden message starts a run itself. Either way nothing new appears in the transcript besides the working indicator and the model's reply. For an agent caller it holds texts while that agent's turn runs and, on its idle, re-acquires a slot and wakes the child with the joined texts as one follow-up prompt.

Nesting: a child gets `run_agent`, `message_agent` and `agent_status` as custom tools only when its definition allows subagents and it is below `maxDepth`; these tools are bound to the child as caller and drive the same runner, which applies `maxChildrenPerAgent` to them (the cap and the prompt rules of each role keep helper fan-out small; a helper's result wakes the agent that started it, never the main session).

Skills narrow down the tree in three layers: the definition's `skills`, replaced field-wise by an `agents.<name>` override, plus the call-time `skills` of `run_agent`. A caller may pass only skills of its own effective set: the main session's is its loaded skills (`runtime.sessionSkillNames()`), an agent's is the `skills` stored on its record at spawn (its own, with `all` resolved to its caller's set, plus what its caller passed; a successor inherits it).

The main prompt and tool list stay the same for the whole session. A child waiting on its batch holds no slot, so the tree cannot deadlock.

## Messages, stop and shutdown

- `message_agent` (only the agent's caller) routes `[message from <sender>]` text: held while queued, steered while a turn is in flight, a follow-up (after re-acquiring a slot) when idle. Its render is silent: `renderCall` and a successful `renderResult` draw nothing (shell `row`, so nothing at all), and an error result draws `✗ message_agent <id> · <error>`, or the error on the `↳` line in the error colour when it does not fit on the title. The model still gets the result text unchanged.
- Stop: a running agent enters `grace`, its turn is aborted and its slot released; a message during grace is answered, otherwise after `stopGraceSeconds` it closes as `stopped` (last text kept as result). A queued agent, a second stop during grace, or `stopGraceSeconds: 0` closes at once.
- Interrupt (`interrupt` plugin, no state): Esc on an empty idle editor (`HostUi.onEmptyEditorEscape`) with at least one queued or running agent (`stoppableAgents` in `core/components/tree.ts`, also used by the list's stop-all) is consumed and opens a confirm `Stop running agents?` naming up to three ids. Yes stops each with `runner.stop` (the graceful stop above) and notifies `stopping N agents`; No leaves them, and the next Esc asks again. Without running agents, or while pi is busy, the key is not consumed. While agents run, pi's double Esc is not reachable from an empty prompt; `/tree` and `/fork` remain. `disabledPlugins: ["interrupt"]` turns it off.
- Session shutdown: unsent wakes are dropped, every open agent closes as `failed (interrupted)` (or `stopped` if in grace), children are aborted and disposed.

## Context limits and handoff chains

- Effective limit = `min(definition limit, model window - reserveTokens)`; `agentBudget` (`core/model/context-limit.ts`) turns it and the ratios into a shared `HandoffBudget` and `limits` asks `budgetStep` (`platform/shared/handoff-budget.ts`) what to do. After each turn that continues with tool calls, `limits` compares context tokens: at `softContextRatio` it routes one warning; at the limit it sets `handoffRequested` and routes the shared handoff instruction (`handoffInstruction`, agent audience) as a displayed custom message (`pi-handoff-request`, steered into the running turn like any routed message, so the agent view draws the shared request row and the model sees no `[message from pi-subagents]` prefix; the warning stays a plain routed message) with the agent's handoff path (`<OS temp dir>/pi-handoff/<session id>/<agent id>-handoff.md`), which tells it to call its `handoff` tool and then reply `handoff saved`. Every agent gets that tool (`handoffTool` from `platform/shared/handoff-tool.ts`, its rows `handoffToolRows` from `platform/ui-kit/handoff-rows.ts`) whatever its `tools`; a main-session tool of the same name, such as session-limits' `handoff`, is shadowed in agents, because tool names are merged as a set and the custom spec is what the child binds (so read-only agents need no general write tool); it is bound to the agent's own record, refuses before `handoffRequested` is set, writes its `content` to the agent's handoff path, validates it and returns `Handoff saved at <path>` or the validation errors so the agent can fix the sections and call again (an invalid handoff stays saved). `limits` aborts the agent 3 turns after the request, or past `limit * hardContextRatio` from the second turn after it (the first turn is a grace turn, so a single huge tool result that crossed the hard line at once still leaves the agent one turn to hand off; the tool call turn and the one-line reply fit in that).
- When an agent with a handoff request settles, the runner reads the handoff file; when there is none (the agent did not call the tool) and the agent's whole final reply validates as a handoff, a fallback the prompt does not mention, it writes that reply to the handoff path and goes on as if the agent had written it. It validates the handoff (sections Status, Outcome, Evidence, Blocker, Next, Files touched in order; Status `partial` or `blocked`). `partial` within `maxChainLength`, not stopped and not in a settled batch -> a successor record in the same batch (same task, same worktree; the successor starts with a `pi-handoff-seed` message holding the handoff inline, drawn by the seed row in the agent view, before its task, so an agent without `read` can continue its own chain) and the predecessor closes as `handoff`. Otherwise the agent closes as `handoff`, flagged invalid if the schema failed. No file and a final reply that is not a handoff is `failed`.
- Chains are invisible to the caller: one wake, one result section with a `Chain:` line, and any id of a chain resolves to its last link for status, messages and stop.

## Status and views

- `agent_status` (snapshots in `core/agent-status/snapshot.ts`, rows in `ui/agent-status/status-text.ts`) reads in-memory records only; it never touches the agent. Its text gives one line per agent in the receipt's words (`<id> (<agent>, <model>) running · 42s · 9 calls · 31.0k tokens · 31% context`) with `last:`, `error:`, `result:`, `handoff:` and `worktree:` lines under it. Its row is `✓ agent_status <ids or all>` with `↳ N agents (ctrl+o to expand)` under it and, expanded, one agent row per agent in the panel's columns (static marks, the figures as of the call). The `handoff` tool every agent gets (`platform/shared/handoff-tool.ts`, its rows in `platform/ui-kit/handoff-rows.ts`) draws `✓ handoff` with `↳ Saved <path>` (`~/…` under home) or its error lines.
- Every surface reads the same clock, state marks and spinner (`ui/components/state-text.ts`: `◌` queued, starting or stopping, `✓` done, `✗` failed, `⊘` stopped or handed off; on the live surfaces, the panel, the list and the agent view header, a running agent draws pi's braille spinner with the frame from `Date.now()` instead, and scrollback rows draw the static `◌`), the receipt (`agentReceipt` in `core/components/receipt.ts`, over `receipt` in the same file: the ordered segments of a state word or failure reason, the time (`Elapsed …` only while running), calls (`formatCalls`, `1 call`, `4 calls`), tokens, cost and activity, with empty ones omitted except `0 calls` on `Stopped`, which `receiptText` (`ui/components/format.ts`) joins with a muted ` · ` (`plainReceipt` joins the bare text), dropping the activity, then the cost, the calls and the tokens to fit, never the word or the time; `formatTokens`, `formatDuration` and `errorText` come from `platform/shared/index.ts`: `Elapsed 1m 5s · 4 calls · 12.3k tokens · $0.04 · grep` while running, `1m 5s · …` once done, `Queued`, `Starting`, `Stopping · Elapsed …`, `Stopped · …` and `Handed off · …` otherwise), the state words and the `x` hint words per state (`stopWords`, same file), the chain and tree helpers (`core/components/tree.ts`: `isTerminal`, `withLinks`, `carrySelection`, `treeOrder`, over `chainTerminal`/`chainLinks` from `core/model/agent-record.ts`; the connector glyphs are `nestPrefix` in `ui/components/tree-glyphs.ts`, which take any `{ get }` lookup: the registry or a `Map`) and the tick cadence (`core/components/refresh.ts` `tickFor`: 100 ms while a record runs or is in grace, 1 s while one is queued or closed rows linger, none otherwise); widths and truncation come from `ThemeLike.width`/`truncate`, backed by pi-tui, so the extension and the adapter cut lines by one rule; the record's `activity` (last top-level tool name or `writing`, set by the runner, cleared while the agent waits for its batches, not persisted) feeds the panel. The agent view renders nested calls with the specs the extension registered on the host, which the adapter keeps. Re-render throttling is `renderThrottleMs` everywhere.
- The agent panel (`agent-panel`) renders the registry in tree order (`core/components/tree.ts`, rows and the shown cut in `core/agent-panel/panel-state.ts`, lines in `ui/agent-panel/panel-lines.ts`, the widget in `ui/agent-panel/panel.ts`) with the shared agent row (`ui/components/agent-row.ts`; every row reserves the two pointer columns, blank unless selected, where the selected row draws the accent `›`, so names do not shift when a selection appears; an agent started by another sits under its caller, the first child with `↳` in its parent's glyph column and later siblings indented to the same column; `rowLayout` aligns the columns over the shown rows: the name (capped at 24 columns, `#N` for a chain link and `(+N)` for open descendants dim, finished names muted), the muted description (capped at 48 columns), the dim model as `id:thinking` without the provider (capped at 20 columns, cut in the middle so the `:thinking` suffix stays, `modelLabel`; dropped for the whole surface when it would not fit), and the receipt, which on a narrow row first cuts the description down to 12 columns and then drops the activity, the cost, the calls and the tokens, never the state word or the time) in a `belowEditor` widget (set when the first row appears, never during session start, so it lands under the footer block; see Footer; rows are recomputed on each refresh (throttled events and ticks), not per frame): a glance summary that never scrolls (`panelView` gives the `shown` rows and the `hidden` count): up to `PANEL_ROWS` (five) agents are all drawn as a tree; past that it collapses to the lead rows (depth 0, each keeping its `(+N)`) when they fit in five, otherwise keeps five leads, open before closed (a closed lead with an open descendant ranks as open), each group in creation order; once the tree collapses, `reconcile` moves a selected descendant to its top-level lead, and a selected lead the cap cuts takes the last slot (or is appended when slots are free); `x` clearing a row with no drawn successor selects the row now in the same slot; ## Agent setup and agent files

- `/agents` with no argument, in tui mode, opens a menu (`subcommandPicker` in `ui/agent-view/picker.ts`, a `selectForm` titled `Agents`): `view` (the agents list, with `N running · M finished` from `listCounts` and `countsText` in `core/agent-view/list-model.ts`, which also build the list title, so both count as finished every agent at any depth under a closed list root, and as running every open agent at any depth), `setup` and `create`. Esc closes it silently. Without the `agent-setup` plugin the menu is skipped and the list opens. Outside tui, `/agents` and `/agents view` notify that the list needs the interactive terminal. `←` on an empty editor still opens the list directly.
- `/agents` takes `view`, `setup` and `create` as first words (completed in the slash menu with the agent names after `setup `); any other argument is an agent id. `view` works without the `agent-setup` plugin.
- `/agents setup` (`agent-setup` plugin) in tui mode first checks the loaded overrides (`settings.agents`: the user file merged with the project file, the project only when trusted). When no agent other than a chore has a `skills` override (`hasSkillsOverride` in `core/agent-setup/autosetup.ts`) it starts autosetup (below) at once; otherwise it asks `Propose skills automatically for this project?` in a `selectForm` with Yes preselected (Enter picks it): Yes starts autosetup, No opens the form, Esc does nothing. The form opens through `HostUi.showForm` (`setupForm` in `ui/agent-setup/setup-overlay.ts`, state and keys in `ui/agent-setup/form.ts`, lines in `ui/agent-setup/setup-render.ts`): one tab per loaded agent and a Submit tab. Each `SetupAgent` carries a `role`, `lead` when `isLead` (`core/model/agent-record.ts`) finds a `subagents` grant that is not none and `chore` otherwise; tabs run leads, then chores, each shipped agents by name and then own agents by name. The tab bar is `groupedTabBar` from `platform/ui-kit/tabs.ts`, a `Leads` row and a `Chores` row with Submit closing the last, indented one column like the body; the keys are `tabStep` from the same file. `fieldsOf(agent)` gives a lead three fields and a chore two, Model and Thinking: a chore's Skills shows as a dim row `<grant> · fixed for chores` that the cursor skips and that never yields a change. An agent tab is a fixed block, each section padded to its own row count (`FIELD_ROWS`, `PRESETS.length`, `INFO_ROWS`) and the body to the same height as the Submit tab: the name row, exactly two description rows (`fixedBlock`, cut with `...`), the field rows (one row each, the ` (changed)` suffix always kept when the value is cut), a `Previous` preset row (the effective settings, `agent.initial`) and a `Suggested` row (the `proposed` draft, leads only; a blank slot otherwise), `rowsOf` giving the cursor order and `selectedRow` the row under it (none while a picker is open), so the renderer compares rows instead of indexes; a preset row reads `skills · model · thinking` for a lead and `model · thinking` for a chore. Enter on a preset replaces the draft with it, and the preset equal to the draft reads ` (in use)` (`presetInUse`). Below the presets sits the info view, exactly three rows (Proposed, blank when there is no note, Tools and MCP). An open picker fits inside the block the field rows, the preset rows and the info view occupy (`BLOCK_ROWS` in `form.ts`, 10 rows, from `blockRows` in `ui/agent-setup/setup-layout.ts`, which adds the field and preset counts `form.ts` passes in, the two `GAP_ROWS` separators the renderer also draws and `INFO_ROWS`), right under the name and description rows: its first row is the title with the query beside it, then the `↑ N more` slot, the list and the `↓ N more` slot; the title and the two slot rows are `PICKER_CHROME_ROWS`; the model and thinking pickers give the list the rest of the block (`listHeight` in `setup-layout.ts`, 7 rows, also the PageUp/PageDown step), the skills picker 5 rows, and after its `↓ N more` slot come two detail rows (`DETAIL_LINES`). So the form height never changes while a picker is open: at a given width it is the same for every agent tab and the Submit tab with the pickers closed and for every picker in every scroll, filter and detail state; the footer is one row (`framed(..., { oneRow: true })`) that leads with the Esc hint, since the row is cut from the right. At 80 columns the form is 21 lines, with or without an open picker. The fields are pre-filled from the effective definition, or from a `proposed` draft when the context gives one (the effective values stay the baseline, so proposed values show as changed and a `note` shows as a `Proposed:` line): Model (a picker over `inherit` and `runtime.availableModels()`), Thinking (the levels the chosen model accepts) and Skills (the `platform/ui-kit/multi-select.ts` checkbox rows over `runtime.skillCatalog()`, drawn with `{ slots: true }` so the window is always 5 rows plus the two `↑ N more`/`↓ N more` slots: first an `all` row, `every skill of the agent's caller`, exclusive with the rest, so ticking it clears every skill and ticking a skill clears it, ticked when the draft is `all` and confirmed as `all`; then one row per skill, `name  description` with the description cut to the row, the draft's skills first in the draft's order and then the rest in inventory order, an order the picker holds while it is open so toggling never moves a row and the confirmed list is written in that order; right below the `↓ N more` slot two rows always show the description of the skill under the cursor, wrapped and the second row cut with `...`, blank on the `all` row). Every picker carries its query beside the title, `/ type to filter` (`queryKey` and `matching` in `form.ts`): printable keys type into it, so the multi-select's `a` and `n` shortcuts do not reach the list, Backspace deletes, the rows narrow to labels containing the query case-insensitively with `<shown> of <total>` right-aligned on the title row or `no <model|level|skill> matches "<query>"` when none do, and Esc clears a non-empty query before it closes the picker. While filtering the `all` row is hidden; with an empty catalogue it is hidden too, the list reads `(none available)` and Enter closes the picker without touching the draft; Enter on a model or level picks only a shown row and does nothing with none; checked skills that the filter hides stay checked and the confirmed list keeps the picker's order. The agent tab also shows read-only Tools and MCP lines. The Submit tab shows the context's `project` line when given, lists the changes as `name: field new (was old)`, with `(suggested)` after a value equal to the proposal, cutting the new value so the suffix stays, (`changeRows` in `form.ts` decides the rows and the mark, the renderer only formats them) under a `Submit` title row, a `Project:` row (blank without a project) and a `Changes`/`No changes` row; the changes take every row the agent-tab body leaves above the `Save to:` block (a blank row, the label, and the scope rows plus the untrusted note padded to three rows), six rows, and only when more changes exist than rows does the last row read `... (N more items)`; then it picks the file: in a trusted project this project's `.pi/pi-subagents.json` (preselected) or the user's `<agentDir>/pi-subagents.json`; in an untrusted project only the user file, with a line saying pi does not read the project file and the user file applies to every project. Outside tui mode it fails with a message naming both files and the one-line form.
- Autosetup (`core/agent-setup/autosetup.ts`, `core/agent-setup/proposal.ts`): the leads (`isLead` in `core/model/agent-record.ts`) are the loaded agents whose `subagents` grant is not none, `all` included; the folder an agent file sits in plays no part, and overrides cannot change the role because they carry no `subagents`. `general` is a lead: its line reads `skills: all (every skill of the agent's caller)`, and the prompt tells the main session that a lead with `all` keeps it when left out of the call and gets a list only when a narrower one fits better. The candidates are `runtime.skillCatalog()` minus skills whose SKILL.md body (after the frontmatter) contains one of `INTERACTIVE_TERMS`, case-insensitive; an unreadable file is kept. With no lead or no candidate it only notifies. Otherwise it sends `prompts/autosetup-skills.md` as a hidden message (custom type `pi-subagents-autosetup`) filled (`fillTemplate` in `core/agent-setup/template.ts`, shared with `/agents create`) with the cwd, its top-level entries (`projectListing`: names only, folders marked, `.git` and `node_modules` skipped, at most 60), one line per lead (description, tools, current skills) and one per candidate (`[project]` on project-scope skills, descriptions cut at 200), and sets an in-memory pending mark with the candidate names, with no notice. Chores appear in no text. The main session answers with `agent_skills_proposal` (model-only, sequential, no prompt snippet; `{project, assignments: [{lead, skills}], reasons: [{skill, why}]}`, arrays rather than maps so strict tool schemas accept it). The tool refuses with no pending mark, outside tui, and on an unknown agent, a non-lead (`<name> is not set up here`), a repeated lead, a skill that is not a candidate (one left out as interactive is refused as `"<name>" asks the user; agents cannot use it`) or more than five skills, listing every problem and the accepted names; the mark stays set. A valid call clears the mark, dedupes each list keeping its order, answers `Nothing to change` without a form when every list equals the current one in the same order (`sameGrant` in `core/model/agent-record.ts`, which also decides the form's `(changed)` marks), and otherwise opens the form with each proposed list as the `proposed` draft, the reasons as its note and the project line, publishing `pi:awaiting-input` around it. Cancel and an unchanged confirm save nothing; a confirm saves as the form does but without the save notice, and the result gives the model the path, the changed agents and the `/new` suggestion to relay (a shadow warning still notifies). The extension never runs `/new`. The mark is also cleared on session start.
- One-line form (`core/agent-setup/line.ts`): `/agents setup <agent> model=<provider/id[:thinking]|inherit> thinking=<level> skills=<a,b|all|none> scope=<project|user>` (any subset; scope `project` by default in a trusted project, `user` in an untrusted one); the model is resolved and the skills checked before anything is written. `skills=` on a chore (`LineCheck.chores`) is refused: `<name> is a chore; /agents setup changes only its model and thinking`.
- Saving (`core/agent-setup/write.ts`) reads the JSON file (refusing a file that is not an object or whose `agents` is not one), merges the changed fields into `agents.<name>` and keeps every other key, then calls `definitions.reload()`, which reloads the settings and the agent files, so agents started afterwards use the new values; running agents keep theirs. A user save that a project override shadows gets a warning naming the fields. `save` returns the path written and that warning, or the error, for the proposal tool.
- `/agents create [<name> [project] | <what the agent is for>]` (`core/agent-setup/create.ts`) writes no file. It checks what it can (a shipped agent's name, a name that is not letters, digits, `_` and `-`, an existing file, `project` outside a trusted project), then sends a brief to the main session as a hidden message (`Host.sendHiddenMessage`, custom type `pi-subagents-create`, which starts a turn when the session is idle) and notifies that it did. The brief is `prompts/create-agent.md` filled by `createBrief`: the command as typed, the name or purpose when given, the target path (the user agents dir; the project dir too in a trusted project, when the name is not fixed), the names taken, the available skills with descriptions and both `core/agent-setup/agent-template.ts` skeletons, lead and chore, so the brief cannot drift from the kind defaults. The main session asks the user for what is missing, writes `<agentDir>/agents/<name>.md` (or `<cwd>/.pi/agents/<name>.md`) with its own write tool and tells the user to run `/reload`. The `/agents` menu's `create` runs the same flow with no name.

## Worktrees

`worktree: true` writes `<cwd>/.pi/worktrees/.gitignore` (`*`) when missing, then runs `git worktree add -b pi-agents/<id>-<stamp> <cwd>/.pi/worktrees/<id>-<stamp> <base>` from the session cwd, where `base` is the HEAD sha; the agent's cwd is the same subdirectory inside it. A failed git or fs step fails the agent with `worktree failed: <error>`. `Worktree = { path, branch, base, cwd, cleanup? }`. A successor is created holding its predecessor's worktree. `releaseLive` is one teardown per agent: it disposes the child, then, for a closed record without a successor, runs `git worktree remove <path>` (no `--force`), deletes the branch only if it still points at `base`, and stores the outcome as `worktree.cleanup` (`removed`, `branch kept`, `kept`) on every link of the chain. A batch settles only after every member's cleanup, so results show the final outcome; shutdown awaits every pending removal except one whose `git worktree add` is still running. Stopping an agent queued for a slot tears it down at once.
