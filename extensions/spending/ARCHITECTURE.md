# Spending architecture

`index.ts` re-exports `api/extension.ts`, which builds the extension with `createManagedExtension` (namespace `pi-spending`, no settings) and one plugin, `spendingPlugin` in `api/plugin.ts`. The plugin wires the host hooks and channels to `createSpending` (`core/spending.ts`), which keeps the offsets and the ledger (`core/ledger.ts`), and paints the footer segment with `footerText` (`ui/footer-text.ts`). Its `enable` returns nothing to undo.

- Main cost = `sumUsage` over the session entries (assistant, tool result, `usage`, compaction and branch-summary usage; `Host.sessionUsage()`), as priced by pi. Child agents use the same `sumUsage` (`ChildSession.ownUsage`).
- Other costs arrive on `spending:usage { source, id, usage }` (`USAGE_CHANNEL`, parsed by `parseUsageReport` from `platform/shared/host-channels.ts`). Subagents' `usage-report` forwards every `agent:usage` (child session's own usage, at any depth, since all agents share one runner) with `source: "agents"` and the agent id as `id` (ids are unique within the session's agents folder, earlier runs included), with no dedup of its own, since the ledger is idempotent.
- The ledger keeps the latest report per `(source, id)` and replaces it only when neither cost nor tokens go down and one goes up (monotonic: totals never go down), sums per source, and the plugin shows `main $x · agents $y · total $z` (plus `(sub)` when the adapter's `subscription` is set: pi reports OAuth for the main model and the provider's OAuth sign-in is marked as a subscription, pi's own footer check) in the footer under the status key `pi-spending` (`SPENDING_STATUS_KEY`) once any source is above zero, each figure in the shared money format (`formatCost`: two decimals, `<$0.01` under a cent, `$0.00` for nothing); total is the raw sum rounded once.
- Persistence: changed reports are appended as `pi-spending:usage` custom entries in the main session file at once when a report arrives while the main session is idle (agents mostly run then, so a crash loses little), otherwise on the next idle, and on shutdown; they are replayed on session start (resume). Reports that arrive after spending's own shutdown are ignored. Offset entries that are not finite numbers read as zero.
- Lineage: totals cover the whole session lineage. Compaction and `/tree` only append to the same file, and `sumUsage` reads every entry of every branch. When a session is created from another one (`/fork`, `/clone` or a handoff switch; `parent` set) spending appends a `pi-spending:main-offset` entry (the parent's main cost, its own last offset plus all its entries, minus the usage of the entries copied into the new session), so main = last offset + `sumUsage` of the new session's entries; it also appends a continuation marker report, absorbs every parent `pi-spending:usage` report under an id prefixed with the parent file name (so new agents cannot collide with parent agent ids) and persists them into the new session at once; restore ignores reports before the last marker, so resumed sessions and chains of forks and handoffs keep the totals. Only a plain `/new` starts at zero; a handoff switch keeps the totals, since it continues the same work in a new session. Without a session file (`--no-session`) there is no parent file: a fork starts from the copied entries only, and a handoff switch starts from zero (session-limits passes no parent). A parent that cannot be read falls back to the resume path over the session's own entries, with a warning. Only the first `session_start` of an instance inherits: pi's rpc mode rebinds extensions twice for fork, clone and new-with-parent, and a second inheritance would append a second continuation marker after the absorbed parent reports, which a later resume would then drop.
- Totals: on every refresh (session start, accepted report, turn end, compaction, idle) spending publishes `spending:totals { main: { cost, tokens }, sources: [{ source, cost, tokens }], subscription }` (`TOTALS_CHANNEL`). pi constructs every extension and runs its subscriptions before `session_start`, so listeners hear the first publish regardless of load order; there is no request channel. Tokens are chargeable tokens (`input + output + cacheRead + cacheWrite`); main tokens carry over a fork or handoff through a `pi-spending:main-tokens-offset` entry, like main cost (a parent forked before that entry existed has none, so main tokens undercount its ancestors while cost stays right; new chains are complete). Both offsets are read once at session start (or set by the fork inheritance) and each refresh reads `sessionUsage()` once.
