# launcher threat model

What the sandbox protects, where its trust boundaries are, and what each feature weakens. How it works is in [ARCHITECTURE.md](ARCHITECTURE.md); what the user sees is in [README.md](README.md).

## 1. Assets

- **Host credentials:** model provider keys and OAuth tokens in `~/.pi/agent/auth.json`, keys and header values in `models.json` and `mcp.json`, environment variables, keychain items, password manager entries, MCP OAuth tokens, parent proxy credentials.
- **Host files:** everything in the home directory outside the repository, other repositories, `~/.pi`, the launcher's state and config.
- **Host pi sessions:** the transcripts in `~/.pi/agent/sessions/` (under `PI_CODING_AGENT_DIR` when set), one directory per repository; host pi reads them on `/resume`, `-c` and `--session`.
- **The network:** hosts the developer can reach (internal services, cloud metadata, private ranges) and the developer's identity toward them.

The agent inside the container is assumed hostile: it may run any command, write any file it can reach, and send anything to any host the proxy lets through.

## 2. Trust boundaries

- **Container:** runs pi and every tool it starts. Sees the repository and its git dir (read-write; hooks, git config, `commondir`, `gitdir` and a `.git` file read-only from launcher snapshots), its own agent volume, its `node_modules` and cache volumes, the user's shared cache volumes (`mounts.sharedCaches`, read-write, shared with every other sandbox of the user), host pi's session directory for this repository (read-write, at its host path, while `sessions.host` is on), the read-only render dir and the trust bundle. In workspace mode the "repository" is the workspace folder, and every repository in it has its git metadata protected as one repository's is. Its only network path is the proxy URL, authenticated with a per-repository token.
- **Proxy:** a host process per policy hash. Holds secrets in memory only, decides every connection, terminates TLS for credential rule hosts and the MCP authorization hosts found by host-side discovery and injects credentials there. Trusts the launcher (control token), never the container; the authorization endpoints it trusts come from host-side discovery, never from container traffic.
- **Host pi helper:** pi's managed install in the host agent dir (its current release run with the launcher's node, not through the `bin/pi` wrapper), else the bundled pi next to the launcher, run on the host to print credentials (`pi auth print-api-key`, `print-bearer-token`), to sign in and refresh MCP OAuth (`pi mcp login`, `pi mcp list` in `<state>/mcp-auth/`), to discover MCP authorization servers, and to read the provider host table. It runs with the developer's rights. Neither is writable by the sandbox: the host agent dir is never mounted and a repository that contains or lies inside it (or `~/.pi`) is refused, and the bundled pi lies in the launcher's install. A `pi` found on `PATH` never serves these jobs, since one proxy daemon serves every repository of a policy; it runs only for `pi --no-sandbox` and a bare `pi update`, typed by the developer, and only when neither it nor its real path lies in the repository, its git common dir or `mounts.extraReadOnly` and its `PATH` entry is absolute. The proxy daemon is restarted at the next launch after the host pi version or its commands change; until then a running daemon keeps the command it started with.
- **Colima VM:** runs the container engine and mounts `$HOME` writable so repositories under it can be mounted. The VM is not a security boundary against the developer's own files; only the container's mounts are.

## 3. Baseline guarantees

- No real secret in the container's filesystem, environment or volumes. Rendered `auth.json`, `models.json` and `mcp.json` hold placeholders (`pi-sandbox-` plus 24 hex of a salted hash; JWT-shaped for JWT access tokens), the rendered files are read-only links (re-created at every container start, so a file the agent put in their place is replaced), the render copy of agents, prompts, skills, themes and extensions skips `.git`, `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `id_*`, key and certificate stores and secret-named files (source and markdown files excepted), a `settings.json` package URL with userinfo and a stdio MCP server's URL userinfo or secret-named `--name=value` argument become clean or placeholders, an MCP URL with a secret-like query parameter is dropped with a notice, and `pi sandbox doctor` sweeps the environment, `auth.json`, `mcp.json`, `mcp-auth.json` and the `settings.json` packages for anything else.
- Egress allowlist: a host leaves only when it is in `egress.allow`, a credential rule host, a derived host or a grant; `egress.deny` always wins.
- SNI check: a tunnel whose ClientHello names another host than the CONNECT target is refused.
- Private-range deny: IP literals, localhost, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except the names in `egress.privateHosts`.
- Workspace guard: a repository at or above the home directory, `~/.pi`, the state or config dir, or `/` is refused before anything is mounted.
- Host session directory: the one exception to "nothing of `~/.pi` is mounted". The launcher recomputes the path from the agent dir and the repository's real path with pi's slug formula, and mounts it only when it is exactly one level under `<agent dir>/sessions`, its name matches `--…--` without a `/`, it is a real directory (not a symlink), its real path is that slug under the real path of `<agent dir>/sessions`, and that real path neither is nor contains `~/.pi` or the agent dir, nor overlaps any other agent dir entry. `mounts.extraReadOnly` still refuses everything under `~/.pi` and the agent dir, so the exception cannot be widened by config. The launcher creates the directories 0700 before the check, so the engine never creates a root-owned one.
- Extra mounts: each `mounts.extraReadOnly` entry must exist as a file or directory and is bound at its real path; it is refused when it is or contains the home, or is, contains or lies under `~/.pi`, the agent dir, the state dir, the user config, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys`, `/dev`, a `.git` dir or the engine socket (`pi-sandbox: mounts.extraReadOnly: <path> is not allowed (<reason>)`). Nested `.git` dirs deep inside an allowed directory are not scanned.
- Git dir layout, checked before any git call: the launcher finds the nearest `.git` itself (`lstat`, no link followed) and accepts a real `.git` directory, or a `gitdir:` file whose target is either its own git dir (a separate git dir, a submodule opened as a repository) or a linked worktree's `<common>/worktrees/<name>` whose `commondir` resolves to that common dir and whose `gitdir` resolves to this checkout's `.git`. `git rev-parse --show-toplevel --git-common-dir` must then agree, and a failing git refuses too, so a `gitdir:` file rewritten to point at an arbitrary host directory is never mounted. A `gitdir:` file pointing at a directory named `.git` (another checkout's git dir) refuses. A link at `.git`, at the gitdir target, at `commondir` or `gitdir`, a `commondir` in a git dir where git never writes one (the common dir, a submodule git dir) with any content but the launcher's pin (an empty one, the bind mountpoint the engine creates when a stopped container is started without the launcher, is opened without following links and, when it is still an empty regular file with one link, filled with the pin in place, so the mount on it stays attached), or a worktree `commondir` pointing at another repository refuses the launch (`pi-sandbox: git: <path> was not written by git or the launcher`, `... is a symbolic link`, `... points at <path>`). The launcher's own host git calls run with `-c core.fsmonitor=false -c core.hooksPath=<an empty dir under the state dir>`.
- Read-only git dir: what is protected is the code the host's git runs from the git dir. Inside the container these are read-only: the common dir's and every submodule git dir's `config`, `config.worktree` and `hooks`, `core.hooksPath` when it resolves inside the repository or git dir (refused when the path goes through a link inside them), every `worktrees/*/commondir`, `gitdir` and `config.worktree`, the checkout's `.git` file when it is one, and a `commondir` pin with content `.` (git reads it as the git dir itself) in the common dir and in each submodule git dir. They are bound from launcher-owned snapshots under `<state>/git/<repo hash>/snapshots/`, copied right before every container create or start (also the restart of a stopped one, under the repository's container lock, after an outdated container is discarded): each file is opened without following links, its device and inode must match a fresh `lstat`, its real path must equal its path inside the repository or git dir and pass the `mounts.extraReadOnly` protected-path check, and a hooks dir is copied as regular files and directories only; a symbolic link inside it refuses the launch (symlinked hooks are not supported inside the sandbox). A link at any of these paths, or a path whose real path goes through one, refuses the launch, so no bind ever reaches a link target. The paths are found once per launch; right before a start, after the pins are written the layout is checked again, and after missing hook dirs are created every protected path is checked again, so a link planted between discovery and start refuses too. The pin is written on the host (by a hard link of a temporary file, or an exclusive create where hard links are unsupported, never over an existing entry; a failed write refuses the launch) before every start, so the engine never creates an empty `commondir` (which would break host git), and removed after the last session of the repository stops its container, only when it still reads `.` (any other content is removed with a notice), and only when no created or running sandbox of another checkout shares the git dir (the check and the removal run under a lock per git common dir under the state dir, which a launch also holds from the pin write through the container start) (a linked worktree and its main checkout, a superproject and a submodule opened as its own repository; the containers carry `pi-sandbox.git-common-dir`), since deleting the file under a bind would detach the read-only mount in that container. The git dir and every directory between the repository root (or a git dir outside it) and a read-only path, such as `.git/modules/<name>` and `.git/worktrees/<name>`, are bound onto themselves, so the agent cannot rename `.git` or one of those parents away from its mounts (the kernel refuses to move a mountpoint). On the Docker engine these binds use typed mounts, so a missing source fails the start instead of being created. After the last session the launcher re-runs the layout checks and prints any failure as a notice.
- Workspace mode: started in a folder that is not inside a repository, the launcher searches the whole folder (hidden directories included, `node_modules`, `.pi` and the inside of `.git` dirs skipped, links not followed) and applies the read-only git dir protection, the pins, the launch checks and the session-end checks to every repository it finds. It fails closed: the launch refuses when a repository fails the single-repository checks, when its git dir or common dir lies outside the folder, when a git config file the folder or a repository reads (every scope but the command line, files named by `include.path` and `includeIf` included) or a `core.hooksPath` lies inside the folder but outside every repository (inside any nested repository, a sibling included, it is bound read-only in the overlay of the repository that reads it), when a directory cannot be read (`workspace: <dir> cannot be protected: cannot read it (<code>)`), when an installed git fails to list a configuration, when the folder holds more than 128 repositories, and when the search would visit more than 50 000 directories, so no repository present at launch is mounted without its protection. Every nested repository root and each directory between the folder and it is bound onto itself, so the agent cannot rename a repository away from its read-only mounts. The workspace's container carries all git common dirs in `pi-sandbox.git-common-dirs`, so a pin is removed only when no workspace or single-repository sandbox holding that git dir is created or running. Submodule checkouts are protected through their superproject's `.git/modules`.
- Per-repository networks: each repository's containers join their own internal network `pi-sandbox-<first 12 of the repo hash>`, so containers of different repositories share no network; the relay, which only forwards to the proxy port, is the one container on more than one of them.
- MCP token vault: real MCP access tokens, refresh tokens, authorization codes and dynamically registered client secrets stay on the host: the proxy terminates TLS to the authorization hosts found by host-side discovery, answers placeholder refreshes itself, swaps a single-use code placeholder in only at the sign-in's token endpoint and redirect URI, and refuses any token response outside a sandbox sign-in. Every launch, and every intercepted `pi mcp login|logout` while the container runs, sweeps the volume's `mcp-auth.json` of any token that is not a placeholder.
- Per-repository proxy tokens: one repository's container cannot use another repository's grants, rules, vault servers, env secrets or parent-proxy credentials (the proxy keeps `dynamic.json` rules and vault servers per repository token hash, and the env secrets of each launch under its `repoTokenHash`), and the container never holds the instance (control) token. A repository token exists only as a file in the instance's `tokens/` directory and the proxy maps requests to repositories from those files alone, so deleting one (as `pi sandbox gc` does when it removes the repository's container) revokes it. Grants are checked against the live sessions read on every request, with no cache. Upstream keep-alive connections are pooled per repository, host, port and access, so one repository's requests never ride another's upstream connection or parent tunnel.

## 4. What each feature weakens, and the mitigation

| feature | what it weakens | mitigation |
| --- | --- | --- |
| TLS termination of rule hosts | The launcher CA is trusted inside the container and has no name constraints, so it could sign any name there. | The CA key never leaves the host state dir; only rule hosts are terminated, every other tunnel stays end to end. |
| Placeholder substitution (D4) | A rule host that echoes request headers or bodies reflects the real secret back into the container. | Substitution happens only in the rule's own header, or, for a rule without one, in auth-like request headers (`authorization` and secret-like names, never `proxy-authorization` or `sec-*`); the placeholder is stripped from every other header and never substituted in query parameters or bodies. On terminated hosts, an absolute-form target for another origin and a path with dot segments (raw, `%2e`, an encoded slash or a backslash) get `400`, and `pathPrefix` is matched on the decoded path. Every response header value is scrubbed by substring (`Location`, `Set-Cookie`, `WWW-Authenticate` included). Response bodies are not scrubbed: allow rule hosts that do not echo. |
| Derived hosts | Host config files widen egress: every provider and MCP host in `auth.json`, `models.json` and `mcp.json` becomes reachable. | `credentials.derive.enabled: false` or `credentials.derive.hosts` (final when the policy or org layer sets them), and `egress.deny`. |
| `egress.privateHosts` | Names in `privateHosts` (a private gateway host, for example) skip the private-address filter, so a rebinding DNS answer for them reaches an internal address. | Only names, no IP literals or localhost; set by policy, org or user, never by a project, and final when the policy or org layer sets it. A rule host that resolves privately and is not listed gets a launch notice (D10). |
| Grants | The developer can widen egress at run time, for one repository or every repository, until the grant is revoked. | `egress.grants: false` from policy or org turns grants off for good; `egress.deny` and the private-range check still apply. The container cannot create grants: the CLI runs on the host only and the proxy has no grant endpoint. |
| Parent proxy | DNS is delegated: with a parent proxy set, an NXDOMAIN locally is passed to the parent, which resolves it. | The private-range check still runs on every local resolution; `noProxy` names are dialled directly. The parent's credentials are resolved on the host and kept in the proxy's memory; with `"env"` they are sent over the control socket and stripped from the environment the proxy starts with. The proxy process starts with a minimal environment (path, home, temp, locale, CA files, the launcher's path overrides, `HTTPS_PROXY` without userinfo), so no secret variable of the launcher reaches it except through the control message; an env secret with a CR or LF is refused at launch, so it cannot split a header. |
| Extra CAs | Trust widens to the corporate CA, inside the container, in the proxy's upstream trust and during image builds. | `tls.extraCa` is a policy or user key, never a project key, and only shrinks under a higher layer. The build removes the CA from the image again. |
| Image layers | `image.dockerfile` runs as root at build time on the engine's default network. | Policy, org or user only, an absolute path, used verbatim; the layer runs on top of the sandbox image and ends with a fixed tail (`USER pi`, the workdir, the launcher's entrypoint and an empty `CMD`). The proxy, CA and environment are set by the container spec at run time, not by the image. Treat the file as code the developer runs. |
| Host pi helper | `!command` values in host `models.json` and `mcp.json` run on the host, as they would with local pi. | Only values from the developer's own host files; a value in a file the container can write (the repository's `.pi/`) is never run on the host. |
| MCP auth store on the host | `<state>/mcp-auth/` holds real OAuth tokens; a token seeded from the host's own `mcp-auth.json` then lives in two places. | Mode 600 files outside every mount. The helper `mcp.json` is written only by `pi mcp login|logout <name>` typed in the shell and holds only `{ url, oauth }` with plain values (D1); refresh uses the recorded definition, never a file the container can write: vault servers' definitions are recorded on every launch (`containerMcpAuth` writes `servers/<name>.json` from the host user `mcp.json`), host sign-ins' at `pi mcp login`. A server defined only in the repository's `.pi/mcp.json` needs a y/N confirmation. |
| `pi install|remove` on the host | Typed in the sandbox shell, it runs the host pi on the host and changes the host `~/.pi/agent/settings.json`. | Only the command the user typed, as `pi mcp add` is. A local install source inside the repository, its git dirs or the workspace root (checked on the path and its real path) is refused and nothing is written, since host pi would load code the container can rewrite. Nothing from the volume reaches host config: at launch the host `settings.json` keys overwrite the volume copy, and `npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor` and `httpProxy` are host-owned (the volume's values are dropped). |
| Org baseline | A compromised baseline file changes the effective policy. | An absolute path on the host, read at every launch and validated as the `org` layer, which cannot set a key the policy sets; a missing file stops the launch, `pi --no-sandbox` included. Whoever can write the file can change the baseline, so it belongs in a path only the administrator writes. |
| Denial page | A denied CONNECT is accepted and answered over TLS with a launcher-CA certificate for the denied name, so the container sees a certificate the launcher CA issued for a host it may not reach. | For a host the egress allowlist or port check denies, the proxy accepts the CONNECT, serves a 403 text page carrying the allow hint over TLS with a launcher-CA certificate for the denied name, and never resolves or contacts that host; at most 30 new denial certificates are minted per minute and 256 are kept, beyond which the CONNECT itself gets a 403. Denial certificates live in memory only (LRU of 256). Rule and vault host leaves are minted under a file lock, written atomically to `<state>/ca/leaf/`, checked key against certificate on load, and expired ones are pruned at daemon start. |
| MCP token vault (`credentials.vault.enabled`, on by default) | Server-published OAuth metadata widens egress (its resource-metadata, issuer, token and registration hosts) and those hosts are terminated; the agent can make the host open a real authorization page in the developer's browser. | The vault hosts pass `egress.deny` and the private-range check; discovery runs on the host, never from container traffic. The agent can open a configured server's real authorization page at most 5 times per 10 minutes per repository, and only on the host's own browser and loopback callback port; it never receives the code. Only servers in the user `mcp.json` without a header, URL password, `auth` or `clientSecret` qualify. Policy or org can turn it off for good. |
| Removing `PI_OFFLINE` | Startup installs and catalog refreshes reach the network. | They reach only allowed hosts; a denial is reported, never bypassed. |
| Host sessions, write path (`sessions.host`, on by default) | The agent can create, rewrite or delete this repository's session files on the host, the ones from before the sandbox and the subagent runs under `<session>/agents/` included. | Only this repository's directory is mounted. Policy or org can turn the key off and lock it; a project file cannot set it. |
| Host sessions, read path | The agent can read this repository's earlier host sessions, which may hold secrets a tool printed in an unsandboxed session; for this one repository that weakens "the agent never sees a real credential". | `sessions.host: false` keeps sessions in the volume; the README names the trade-off. |
| Host sessions, host parsing | Host pi parses the JSONL line by line and runs no code from it, but a session resumed with `--no-sandbox` carries injected content into an unsandboxed agent, and a header `cwd` makes host pi switch to that directory on resume. | The sweep finds each top-level `*.jsonl`'s header as pi does (first non-blank line that parses, lines split on `\n`) and renames it to `.rejected-<random>` (deleting it when the rename fails) when that session's `cwd` is outside the repository, when a bare carriage return (a `\r` not followed by `\n`) appears before the header (pi's listing splits lines at it and its opening does not, so the two could see different headers; pi never writes one), when no deciding line turns up within 1 MiB (opening reads past that) or when it cannot be read, before each launch, after pi exits and before host pi runs on `--no-sandbox`, with the feature on or off. The `cwd` check is lexical: a `cwd` of `<repo>/link` whose `link` points outside passes, which adds nothing to what the writable repository already allows. Content injection stays: resuming a sandboxed session outside the sandbox trusts what the agent wrote, as the repository's own files already require (`.pi/extensions` can be planted anyway). |
| Host sessions, symlinks and special files | Host pi follows links when it lists sessions, so a link could pull another repository's session (or any file) into this list, and a fifo could hang `/resume`; a symlinked `<session>/agents` could redirect host-side subagent writes. | The sweep `lstat`s every entry, re-checks device and inode right before acting, and deletes only the entry itself (symlinks, fifos, sockets, devices), never a target. Top-level entries are swept at every launch and exit; the `agents/` trees only while no container of the repository runs (after the last session's stop, and before a launch that finds none running), decided and run under the repository's session registry lock, only when no other session is registered and the container is not running, so no agent can start and swap a directory for a link during that walk. Hard links cannot cross the mount. A directory the guest made read-only (its uid maps to the host owner) gets `u+rwx` back before the sweep acts in it; an entry that still can be neither renamed nor deleted makes the launch, and `pi --no-sandbox`, refuse with a message naming it, and the exit sweep warns. |
| Host sessions, size | No cap: the agent can fill the disk through that directory. | The same is possible through the repository bind; the sweep warns about a top-level file over 256 MiB. |
| Host sessions, slug collisions | pi gives `/a/b-c` and `/a/b/c` the same slug, so two such repositories share one session directory and see each other's sessions. | Isolation between repositories is as good as pi's slug; the header check renames sessions whose `cwd` lies outside this repository, which also hides the colliding repository's legitimate host sessions from host pi (a known gap). |
| Workspace mode | One container sees every repository in the folder, so the agent can read and change all of them, and their files outside the git dirs are as writable as one repository's. Launching costs two git calls per repository and recreates the container when a repository is added or removed. | Only folders without a repository above them; the home, `~/.pi`, the state and config dirs and `/` are refused as for a repository; each repository's git metadata is protected and the launch fails closed (see section 3). Start pi inside one repository to give the agent only that one. |
| Shared caches (`mounts.sharedCaches`) | One volume per entry and user is mounted read-write into every sandbox of that user, so it is a write channel between repositories: one sandbox can plant a poisoned package or build output that another repository's sandbox then runs. It never reaches the host: the host folder of the same name is not mounted. | Off by default (`[]`); policy, org or user only, refused in a project file, and final when the policy or org layer sets it. Entries must lie under the home and not be or lie under `~/.pi`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `~/.config` or `~/.local/bin`, so no credential store or `PATH` directory of the sandbox user is shared. The volumes carry only the user hash (from the state dir) and the path, never a repository label; `pi sandbox gc --shared-caches` removes them. Opt in only for package caches, knowing that a poisoned entry reaches every repository that uses the cache. |
| `node_modules` overlays (`mounts.autoNodeModules`, on by default) | The launcher creates missing `node_modules` directories (empty) and missing `mounts.cacheVolumes` targets on the host as mount points, and hands the volume mount points to the sandbox user with one root exec after each start. | A convenience, not a security control: the overlay keeps native modules built for Linux off the host and, as a side effect, keeps the sandbox from writing into the host's `node_modules` (and its `.bin`) at those paths, but the agent can still write every other file host tools run, `package.json` scripts included. The mount points are created as the host user, one level at a time, and a link or non-directory in their place refuses the launch; the `chown` runs inside the container on its own mount points only (`chown -h`). A project file may turn the overlay off. |
| VM shares (Colima) | A repository outside the home gets the whole `/Volumes/<name>` volume, or its parent folder, shared with the Colima VM, writable when the repository needs it, and the share stays. | The home is re-added, or upgraded to writable, only when a bound path under it (the state dir, the host session dir) requires it. This widens what the VM sees, not what a container sees: a container still gets only the binds of its spec. The launcher restarts only its own `pi-sandbox` profile, only when no pi session is live and never from the doctor. |

## 5. Known gaps

- Plain HTTP is refused (CONNECT to port 80 has no SNI to check).
- The git common dir is mounted read-write, and `.git/config` is readable inside, so a token in a remote URL (`https://user:token@host/...`) is visible to the agent; keep credentials in a credential helper, not in remote URLs.
- Repository contents stay untrusted for host tools. The agent can create a nested repository anywhere in the checkout (a new `.git` dir or file, or a rewritten `.git` file of a submodule checkout pointing at a git dir it made under `.git/modules/`), add gitlinks, write `objects/info/alternates`, and change any file host tools read (editor settings, `.envrc`, package scripts). Host git run inside such a nested repository uses its config and hooks. After the last session the launcher walks the checkout (up to 50000 directories, the launch scan's budget, links not followed, the git dir skipped) and reads the index with `git ls-files --stage`, comparing with the list it recorded at the container start, and prints `pi-sandbox: git: the sandbox created <path>` (or `changed`, or `added the gitlink <path>`) with the advice to review it before running host git tools there; `alternates` and `http-alternates` are named at launch. It reports these; it cannot prevent them. Launching pi from such a nested checkout mounts the git dir its `.git` file names; the launch refuses one that git does not open or that is another checkout's `.git`, but a rewritten `.git` file naming another repository's separate git dir (or a git dir the agent made) is accepted, so heed the notice before launching there.
- Workspace mode protects the repositories present at launch. One the agent creates during the session (a new `.git` anywhere in the folder) is not protected while the session runs; the session-end walk of the folder (every known git dir skipped) reports it, and the next launch protects it or refuses. `pi sandbox status`, `gc` and `reset` discover the folder leniently (no git calls, no refusals); `pi --no-sandbox` does the same; they mount nothing. Without git on the host, the folder's own config listing is skipped.
- In single-repository mode a config origin inside the repository's working tree or git dir (an `include.path` or `includeIf` target in the checkout, for example) is bound read-only, but when git fails to list the configuration the failure is ignored, as for `core.hooksPath`, and such included files are then not bound read-only.
- Shared caches are written by several sandboxes at once; tools without their own cache locking may corrupt them.
- The missing-command hint (`BASH_ENV` and the first line of `/etc/bash.bashrc` in the image, the second because bash skips `BASH_ENV` for a socket-stdin `bash -c` without `SHLVL`, which is how pi runs commands) reaches only bash; it is a convenience, and an agent can unset or redefine it in its own shell.
- The base image in `image/Dockerfile` is pinned by tag (`node:24-bookworm-slim`), not by digest, so a rebuild picks up whatever the tag points at; that is how security updates arrive. A digest pin with a deliberate update step is a follow-up; `image.digest` pins the whole sandbox image meanwhile.
- A config change does not reach a running container while another session of the repository uses it: the new launch joins the old container (with its old mounts and spec) and prints a notice; the change applies once every session has exited. A tightened policy therefore waits for the last session to end; `pi sandbox reset` applies it at once.
- Host-local model servers (`localhost`, plain `http`) are unreachable from the sandbox; a notice says so.
- Secrets in the `env` of stdio MCP servers become placeholders that nothing replaces until a manual `credentials.rules` entry binds them to the host the server calls.
- Provider `/login` inside the interface fails (read-only `auth.json`); log in on the host. Binding codes to provider token endpoints would need per-provider knowledge.
- Pasting the redirect URL into pi (a remote browser, or a callback port in use on the host) puts the real authorization code and the PKCE verifier inside the container; the token response is then refused, but the agent could race the code to the authorization server itself. Sign in with this machine's browser.
- Servers with `oauth.clientSecret` and project-only servers stay on host `pi mcp login`; a sign-in for them done inside anyway keeps a real token in the volume until the next launch's sweep.
- A sign-out inside the sandbox applies only inside, until the next launch restores the host sign-in.
- Project-level OAuth MCP servers get no token inside: move the server to the user `mcp.json` or give it a placeholder `Authorization` header with a rule.
- Providers whose client derives the API host from the token content may not work with a placeholder token (D5); the doctor's per-rule check shows a 401 or 403.
- NTLM and Kerberos parent proxies need a local relay such as `px` or `cntlm`.
- Private image registries: pulls send no registry credentials.
- Org baselines have no signature and no ETag, only a pinned sha256.
- `tls.extraCa` `hostStore` reads the macOS System keychain only; on Linux use `{ file }`.
- No in-interface prompt for a blocked host: the 403 denial page (or, past its limits, the CONNECT failure) carries `pi-sandbox: <host> is not allowed; run pi sandbox egress allow <host>`, and the launcher prints one line per blocked host when pi exits (with `egress.grants: false`, a line pointing at `egress.allow` instead of the grant hint).
- No in-container unauthenticated proxy shim, so tools that cannot send proxy credentials (headless browsers) have no network.
- Domain fronting through a CDN host on the allowlist.
- A relay kept for other repositories while its proxy came back on another port forwards to the old port; if another local process took that port, the kept sandboxes send their repository token (which only identifies a repository to the proxy) and their tunnels to it until they exit.
- Locks follow the holder's pid, except `mcp-auth.json.lock`, which keeps pi's `mkdir` format and is judged by its age: a launcher that stalls for more than 10 s while holding it can lose it to pi or to another launcher, and the two writes of the vault store can then overlap.
- The Colima VM sees all of the home directory.
- Host pi running alongside a sandbox of the same repository: while the container runs, the sweep only checks the top level, so a link the agent planted under `<session>/agents/` stays until the last session stops; host pi and its subagents may follow it in that window.
- Host sessions in a custom session dir (`PI_CODING_AGENT_SESSION_DIR` or `sessionDir` on the host) are not shared, since that directory holds every repository's sessions; a project `.pi/settings.json` `sessionDir` and a user `--session-dir` are not considered. A change of these host settings recreates the container at the next launch that is alone in the repository.
- The share check proves the directory is shared and writable from the sandbox at container creation (and on each doctor run), not later.
- On a slug collision the sweep of one repository renames the other repository's host sessions to `.rejected-<random>`, so host pi no longer lists them; rename them back by hand.
