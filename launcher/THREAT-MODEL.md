# launcher threat model

What the sandbox protects, where its trust boundaries are, and what each feature weakens. How it works is in [ARCHITECTURE.md](ARCHITECTURE.md); what the user sees is in [README.md](README.md).

## 1. Assets

- **Host credentials:** model provider keys and OAuth tokens in `~/.pi/agent/auth.json`, keys and header values in `models.json` and `mcp.json`, environment variables, keychain items, password manager entries, MCP OAuth tokens, gh and glab tokens, registry passwords, parent proxy credentials.
- **Host files:** everything in the home directory outside the folder pi starts in, other repositories, `~/.pi`, the launcher's state and config (`<agent dir>/pi-sandbox/state/` and `<agent dir>/pi-sandbox/config.json`, with the CA key in `state/ca/ca-key.pem`).
- **Host pi sessions:** the transcripts in `~/.pi/agent/sessions/` (under `PI_CODING_AGENT_DIR` when set), one directory per folder; host pi reads them on `/resume`, `-c` and `--session`.
- **Host git:** the hooks and config host git runs in the folder's repositories.
- **The network:** hosts the developer can reach (internal services, cloud metadata, private ranges) and the developer's identity toward them.

The agent inside the container is assumed hostile: it may run any command, write any file it can reach, and send anything to any host the proxy lets through.

## 2. Trust boundaries

- **Container:** one per launch, removed when its pi exits. It runs pi and every tool it starts. It sees the folder and its git dirs (read-write, with each git dir's `hooks` dir read-only), its agent volume, its build output overlay volumes, the user's shared cache volumes (`mounts.sharedCaches`, read-write, shared with every other sandbox of the user), host pi's session directory for this folder (read-write, at its host path, while `sessions.host` is on), the read-only render dir (`<agent dir>/pi-sandbox/state/vm/render/<h>/`) and the read-only trust bundle (`<agent dir>/pi-sandbox/state/vm/trust.pem`). In workspace mode every repository in the folder is handled as one repository is. Its only network path is the proxy URL, authenticated with a per-repository token.
- **Proxy:** a host process per repository, shared by its launches. Holds secrets in memory only (they reach it on stdin or are fetched on the host), decides every connection, terminates TLS for credential rule hosts and injects credentials there. Trusts the launcher that started it, never the container.
- **Host pi helper:** pi's managed install in the host agent dir, and no other pi, run on the host to print credentials (`pi auth print-api-key`, `print-bearer-token`), to sign in and refresh MCP OAuth (`pi mcp login <name>` against the host agent dir, from an empty folder so no project `.pi/mcp.json` loads), to read the provider host table, and for the commands the developer types that start no session (`pi auth …`, help and `--list-models` from an empty folder, `--export` in the cwd). It runs with the developer's rights. It is not writable by the sandbox: of the host agent dir the container sees only the three paths above (this folder's session directory read-write, the render dir and `trust.pem` read-only), never the agent dir, `pi-sandbox/`, `config.json`, `ca/ca-key.pem` or pi's install, and a folder that contains or lies inside the agent dir (or `~/.pi`) is refused. A pi in an npm folder (the launcher package's or a checkout's `node_modules`) is never used, and neither is a `pi` found on `PATH`, since the repository or its `PATH` could plant one. The proxy daemon is restarted at the next launch that is alone in the repository after the host pi version or its commands change.
- **Colima VM:** runs the container engine. What it can reach depends on `workspaceRoots`. Without it, the VM mounts `$HOME` writable so folders under it can be mounted: a container escape (root in the VM) reaches all of `~`, read and write, the launcher's config and state and the CA key included. With it, the VM shares exactly the roots (writable), `<agent dir>/sessions` (writable) and `<state>/vm` (read-only, the render dirs and `trust.pem` only), so an escape reaches those and nothing else of the host: not the rest of the home, `~/.ssh`, the rest of the agent dir, the CA key, the proxy tokens or the grants. The launcher restarts the VM to that exact list at a launch with no other launch live; a running launcher container of another agent dir counts as a live launch, since all agent dirs share the one VM. The VM is not a security boundary against the files it shares; only the container's mounts are. Since root in the VM can write anywhere inside a root, a root may not be, hold or lie inside a path whose contents the host runs or trusts: `~/.pi`, the agent dir, the state dir, the user config and its folder (taking these would hand the VM the launcher's config, keys and grants), `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.kube` (credentials), `~/.colima` (the VM's own `colima.yaml`, so its mounts), `~/.config` and `~/Library` (shell, git and gh settings, `LaunchAgents`), `~/.local/bin` (`PATH`), `/etc`, `/usr`, `/opt`, `/System`, `/Library`, `/bin` and `/sbin` (system config and programs, Homebrew); nor be or hold `/private` or `/var`, the home or `/`. A root written inside another root is dropped before its links are followed, so the container cannot point it elsewhere by replacing the folder with a link; the rest are checked on their real paths.

## 3. Baseline guarantees

- **No credential bytes inside.** No real secret is in the container's filesystem, environment or volumes. The agent can still use every credential against the hosts its rule names (section 5). In detail:
  - Rendered `auth.json`, `models.json` and `mcp.json` hold placeholders (`pi-sandbox-` plus 24 hex of a salted hash; for a JWT access token a JWT with the launcher's own header and signature that keeps the token's lasting claims, an account id for example, never its header, signature or times). So do the rendered tool files (gh `hosts.yml`, glab `config.yml`, `.npmrc`, `pip.conf`, the Maven servers), `GH_TOKEN`, `GITLAB_TOKEN` and what the gitconfig's credential helper for gh and glab hosts prints inside (the placeholder is written into the gitconfig).
  - The rendered files are read-only links, except `auth.json`, a 0444 copy in the agent volume (pi locks it beside its resolved path, so a link would put the lock in the read-only render dir); the gitconfig and the glab config are writable copies. All are re-created at every container start, and nothing written to a copy reaches the host.
  - The render copy of agents, prompts, skills, themes and extensions skips directories named `secrets`, `.secrets`, `credentials` or `.credentials` outside `node_modules`, secret-looking files, private keys and files over 8 MiB, and names what it skipped in a notice.
  - A `settings.json` package URL with userinfo and a stdio MCP server's URL userinfo become clean. A stdio MCP server's env value or flag value (a `--flag=value`, or the argument after a bare flag) becomes a placeholder when its name has a secret segment (token, secret, password, passwd, pass, passphrase, authorization, jwt, dsn, cookie, apikey, privatekey, pat, credential, or `key` as the last segment) and is not qualified (max, count, file, dir, path, mode, url, timeout, type …), or when the value is `Bearer`/`Basic`/`Token`-prefixed, a JWT or a URL with userinfo; numeric, empty and boolean values are kept. A credential's `env` values in `auth.json` with a secret name or credential shape become placeholders, and any header with a credential-shaped value is a placeholder whatever its name.
  - A URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`) keeps its shape with a placeholder for the password, or for the user name when the token is the user name, bound to that host (and, for npm, its path); any other `.npmrc` or `pip.conf` value with URL userinfo and every npm and pip proxy setting stay on the host. Userinfo in a Maven mirror URL is removed, Maven profile properties are not copied, and a Maven server's `httpHeaders` values become placeholders like its password (a server with only a `privateKey` or `passphrase` stays on the host).
  - The host `settings.json` `httpProxy` is never synced. An MCP URL or a `models.json` `baseUrl` with a secret-like query parameter is dropped with a notice.
  - `env.allow` refuses every variable the launcher sets inside the container, the proxy and CA variables included, and does not forward a value with URL userinfo, a `Bearer`/`Basic`/`Token` prefix or a JWT shape; the launch names the variable.
  - `pi sandbox doctor` sweeps the environment, `auth.json`, `mcp.json`, `mcp-auth.json` and the `settings.json` packages inside for anything else. It reads `mcp-auth.json` and `settings.json` from the volume as regular files only, with the same 5 s host-side timeout as the write-back; one that is not a regular file or does not answer in time counts as not a JSON object.
- **Container hardening:** pi runs as the unprivileged `pi` user (uid 1000) in a container that drops every Linux capability except `CHOWN`, runs with `no-new-privileges` and is limited to 4096 processes, so a fork bomb stays inside the sandbox. `CHOWN` is left only for the launcher's own root exec that hands new volume mount points to `pi`; pi cannot reach it, since setuid binaries gain no privileges under `no-new-privileges`. The relay container keeps no capability at all, runs with `no-new-privileges` and at most 1024 processes. The root filesystem is read-only. Tools that need raw sockets (`ping`) do not work inside.
- **Egress allowlist:** a host leaves only when it is in `egress.allow` (empty by default) or is `pi.dev`, a credential rule host, a derived host or a grant, on its port; `egress.deny` always wins: an entry `d` blocks `d` and every name under it, and `*.d` every name under `d`.
- **SNI check:** a tunnel whose ClientHello names another host than the CONNECT target is refused.
- **Private-range deny:** IP literals, localhost, link-local, private and reserved ranges, the metadata address, the NAT64, 6to4 and IPv4-translated (SIIT) IPv6 ranges, site-local IPv6 and names that resolve only to such addresses are refused, except the names in `egress.privateHosts`. The check runs before the tunnel opens and again at dial time, so a rebinding answer is refused too.
- **Workspace guard:** a folder that is or contains the home directory, `~/.pi`, the agent dir (`PI_CODING_AGENT_DIR` when set), the launcher folder `<agent dir>/pi-sandbox/`, the state dir or the user config, `~/.config` (it holds files the host runs or trusts, such as shell, git and gh settings) or the old launcher config folder `~/.config/pi-sandbox/`, or an image dir (`/bin`, `/sbin`, `/lib`, `/opt`, `/usr/bin`, `/usr/sbin`, `/usr/lib`, `/usr/local`), or that lies inside `~/.pi`, the agent dir, the state or config dir, `~/.config/pi-sandbox/`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `~/.local/bin`, `~/Library`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys` or `/dev`, is refused. The folder to mount (the nearest repository root above the cwd, else the cwd) is checked before it is searched, and the repository root and git common dir again after discovery. `/` refuses because it contains the home.
- **Host session directory:** the one read-write path of the agent dir in the container (the render dir and `trust.pem` under `<agent dir>/pi-sandbox/state/vm/` are read-only). The launcher recomputes the path from the agent dir and the folder's real path with pi's slug formula, and mounts it only when it is exactly one level under `<agent dir>/sessions`, its name matches `--…--` without a `/`, it is a real directory (not a symlink), its real path is that slug under the real path of `<agent dir>/sessions`, and that real path neither is nor contains `~/.pi` or the agent dir, nor overlaps any other agent dir entry. The launcher creates the directories 0700 before the check, so the engine never creates a root-owned one.
- **Configuration from the host only:** the sandbox reads one config file, `<agent dir>/pi-sandbox/config.json`, never a file in the folder. That file is owned by the user who runs the launcher; there is no administrator layer, so nothing stops that user from widening egress, adding credentials or turning a protection off. A team that shares one file shares a starting point, not an enforced limit.
- **Git dir layout, checked before any git call:** the launcher finds the nearest `.git` itself (`lstat`, no link followed) and accepts a real `.git` directory, or a `gitdir:` file whose target is either its own git dir (a separate git dir, a submodule opened as a repository) or a linked worktree's `<common>/worktrees/<name>` whose `commondir` resolves to that common dir and whose `gitdir` resolves to this checkout's `.git`. `git rev-parse --show-toplevel --git-common-dir` must then agree, and a failing git refuses too, so a `gitdir:` file rewritten to point at an arbitrary host directory is never mounted. A `gitdir:` file pointing at a directory named `.git` (another checkout's git dir) refuses. A link at `.git`, at the gitdir target, at `commondir` or `gitdir`, a worktree `commondir` pointing at another repository, or a `commondir` in a git dir where git never writes one (the common dir, a submodule git dir) that does not read `.` refuses the launch (`git: <path> was not written by git`, `… is a symbolic link`, `… points at <path>`). The launcher's own host git calls run the git found on `PATH` outside the folder and its repository, with `-c core.fsmonitor=false -c core.hooksPath=<a dir under the state dir that holds no hooks>` (`/dev/null` for the git identity probe).
- **Read-only hooks:** inside the container the common dir's `hooks` dir and every submodule git dir's `hooks` dir (under `modules/`, and under `worktrees/<name>/modules/` for a linked worktree) are bound read-only from the host, as hardening. A missing one is created empty on the host first and left in place. The common dir and the folders between the repository root and each module git dir are bound onto themselves, so the agent cannot rename them away from those binds (the kernel refuses to move a mount point). These binds use typed mounts, so a missing source fails the start instead of being created. Right before the start the layout is checked again and every hooks dir must be a real directory, not reached through a link.
- **Everything else in `.git` is writable:** config, config.worktree, commondir, worktree pointers, module configs and a `.git` file are writable by the agent, like the working tree. That includes `core.hooksPath`, `core.fsmonitor`, aliases and includes, so a determined agent can still plant code that host git runs. Read-only file binds are not used: on a case-insensitive volume another letter case of the name (`.git/CONFIG`) writes the host file through the bind. Directory binds hold. The launcher writes no file into `.git`.
- **Git changes are reported, not prevented:** at the start of a repository's first launch the launcher records a digest of each repository's own git files: the common dir's config, config.worktree, commondir and hooks; every `worktrees/*` commondir, gitdir and config.worktree; every module git dir's config, config.worktree, commondir and hooks; and the launched checkout's `.git` file. It also records every nested `.git` entry and git-dir-shaped folder (a git dir with a digest of its config, config.worktree, commondir and hooks). When the folder's last launch ends, each changed path is printed (`git: <path> changed while the sandbox ran; review it before running git there`), together with new or changed nested `.git` entries, gitlinks and alternates. A record left by a session whose end check did not run (crash, reboot, stop) is reported at the next launch that is alone in the folder.
- **Workspace mode:** started in a folder that is not inside a repository, the launcher first refuses the folder if the guard would (before any search), then searches the whole folder (hidden directories included; `node_modules`, `.pi`, the inside of `.git` dirs in any letter case and of git-dir-shaped folders skipped; links not followed), binds each repository's hooks dirs read-only and reports its git changes after the session.
  - Nothing outside the folder is ever mounted for a nested repository. A `gitdir:` pointer is resolved as git resolves it, one component at a time with links followed on each existing prefix, and a nested checkout counts as a repository only when its git dir and common dir lie wholly inside the folder by the resolved, the lexical and the real path.
  - A nested `.git` file whose git dir or common dir does not lie wholly inside the folder, or whose git dir is missing, makes a detached checkout: its files are mounted as plain files with no bind, no git runs for it, and git does not work there inside the container; a notice names these checkouts, and a changed `.git` file there is reported after the session.
  - A folder has the shape of a git dir when it holds an entry named `HEAD` and either `commondir` or both `objects` and `refs`, of any file type, names compared ignoring letter case. Such a bare repository or loose git dir outside every nested repository and its git dirs is bound read-only as a whole (a directory bind), with no git call and the folders above it bound onto themselves: clone and fetch work, push does not, and nothing can be planted in it; a notice names them. Right before the start the bare dirs are checked again, and one that is missing or changed its kind refuses (`workspace: <path> changed while pi was starting, refusing`).
  - A directory entry whose name is `.git` in another letter case (`.GIT`) refuses the launch on every volume (`workspace: <path> is a letter-case variant of .git, which git opens as a repository on a case-insensitive volume, refusing`); so does a repository root whose only git entry is such a variant.
  - A directory the search cannot read refuses the launch when it belongs to the user, who could `chmod` it open from inside; one owned by someone else stays unreadable inside too and is left alone.
  - With `mounts.autoOverlays` on, the search does not descend into a marked build output folder (`.venv`, `target`, `.gradle`) that its overlay volume hides; more than 512 overlays repeat the search without skipping. As a backstop the spec refuses the launch when, for an overlay folder, the mount with the longest target over it is not a volume or a read-only bind, or a writable bind has its target or source inside it.
  - It fails closed: the launch refuses when a repository fails the layout checks, when the folder itself cannot be read (`workspace: cannot read <dir> (<code>), refusing`), when pi starts in a bare repository or inside a git dir, when the folder holds more than 128 repositories and bare repositories, and when the search would visit more than 50 000 directories. Every nested repository root and each directory between the folder and it is bound onto itself, so the agent cannot rename a repository away from its read-only hooks.
- **Per-repository networks:** each repository's containers join their own internal network `pi-sandbox-<first 12 of the repo hash>`, so containers of different repositories share no network; each repository has its own relay, which only forwards to its proxy port.
- **MCP OAuth tokens** stay in host pi's `mcp-auth.json`, which the launcher only reads; the proxy injects the access token for a placeholder `Authorization`, and pi inside never holds a token, a refresh token or a client secret (the sandbox `mcp.json` has no `oauth` block).
- **Per-repository proxies:** each repository has its own proxy process with its own rules, env secrets, parent-proxy credentials and token, so one repository's container cannot use another's. The token (`<state>/repos/<repo hash>/proxy/token`, mode 600) is a proxy credential, not a provider secret, and is in the container's env; it is deleted when the repository's last launch ends, so a later launch gets a new one. Grants are read live from `grants.json`.
- **Launch accounting:** a launch is registered before the VM stage, so a share restart or `pi sandbox stop` cannot pull the VM from under one that is still preparing.

## 4. What each feature weakens, and the mitigation

| feature | what it weakens | mitigation |
| --- | --- | --- |
| TLS termination of rule hosts | The launcher CA is trusted inside the container and has no name constraints, so it could sign any name there. | The CA key never leaves the host state dir; only rule hosts are terminated, every other tunnel stays end to end. |
| Placeholder substitution | A rule host that echoes request headers or bodies reflects the real secret back into the container. | Substitution happens only in the rule's own header, or, for a rule without one, in auth-like request headers (`authorization` and secret-like names, never `proxy-authorization` or `sec-*`); the placeholder is stripped from every other header, placeholders of the host's other rules (another port or path prefix) are dropped before any rule applies, and nothing is substituted in query parameters or bodies. A `Basic <base64>` value is decoded for the check, the stripping and the substitution, and re-encoded, so the decoded secret goes only to the rule host; the exact base64 sent is scrubbed from response headers like the secret. On terminated hosts, an absolute-form target for another origin and a path with dot segments (raw, `%2e`, an encoded slash or a backslash) get `400`, and `pathPrefix` is matched on the decoded path. Every response header value is scrubbed by substring (`Location`, `Set-Cookie`, `WWW-Authenticate` included). Response bodies are not scrubbed: allow rule hosts that do not echo. |
| Derived hosts | Host config files widen egress: every provider and MCP host in `auth.json`, `models.json` and `mcp.json` becomes reachable. | `credentials.derive.enabled: false` or `credentials.derive.hosts`, and `egress.deny`. |
| `egress.privateHosts` | Names in `privateHosts` (a private gateway host, for example) skip the private-address filter, so a rebinding DNS answer for them reaches an internal address. | Only names, no IP literals or localhost; set in the config file. |
| Grants | The developer can widen egress at run time, for one repository or every repository, until the grant is revoked. | Grants cannot be turned off. `egress.deny` and the private-range check still apply to a granted host. The container cannot create grants: the CLI runs on the host only and the proxy has no grant endpoint. |
| Parent proxy | DNS is delegated: with a parent proxy set, an NXDOMAIN locally is passed to the parent, which resolves it. | The private-range check still runs on every local resolution; `noProxy` names are dialled directly. The parent's credentials are resolved on the host and kept in the proxy's memory; they reach it on stdin and are kept out of the environment the proxy starts with; the host helpers the proxy runs (`pi auth`, `pi mcp login`, command secrets) get `HTTPS_PROXY` with them. The proxy process starts with a minimal environment (path, home, temp, user and login name, locale, `NODE_OPTIONS`, CA files, the gh, glab and XDG config dirs, `HTTPS_PROXY` without userinfo), so no other secret variable of the launcher reaches it except through its stdin input; an env secret with a CR or LF is refused at launch, so it cannot split a header. An `HTTPS_PROXY` that is not an `http://` URL gives neither a parent route nor credentials to the proxy; the launch warns and the proxy connects directly. |
| Extra CAs | Trust widens to the corporate CA, inside the container, in the proxy's upstream trust and during image builds. The holder of its key can read the sandbox's TLS traffic, including the real tokens the proxy injects on credential-rule hosts, as it already reads them when pi runs on the host. | `tls.extraCa` is set only in the launcher's config file, never by a project file. Each entry names one certificate, by SHA-256 fingerprint in the macOS System or login keychain or by PEM file; every certificate must be a CA and within its validity dates, or the launch stops. A CA certificate is public, so mounting it leaks nothing. The build removes the CA from the trust store and the final filesystem again. |
| Image layers | `image.dockerfile` runs as root at build time on the engine's default network. | Set in the config file only, an absolute path, used verbatim; the layer runs on top of the sandbox image and ends with a fixed tail (`USER pi`, the workdir, the launcher's entrypoint and an empty `CMD`). The proxy, CA and environment are set by the container spec at run time, not by the image. Treat the file as code the developer runs. |
| Host pi helper | `!command` values in host `models.json` and `mcp.json` run on the host, as they would with local pi. | Only values from the developer's own host files; a value in a file the container can write (the repository's `.pi/`) is never run on the host. gh, glab and git found inside the repository or its git common dir are never run. |
| `pi install\|remove` on the host | Typed by the developer, it runs the host pi on the host and changes the host `~/.pi/agent/settings.json`. | Only the command the user typed, as `pi mcp add` is. Host pi runs from an empty folder, with local sources handed over as absolute paths. A source counts as remote only as a plain `npm:<name>[@version]`, an `http(s)://`, `ssh://` or `git://` git URL with owner and repository, or `git:git@host:owner/repo` and `git:host.tld/owner/repo`; every other source is a local path, and one inside a git working tree or a folder a sandbox has run in (checked on the path and its real path) is refused by `install` and nothing is written, since host pi would load code the container can rewrite. An `npm:` spec naming a path or another protocol (`npm:file:…`, `npm:link:…`, `npm:/…`) is refused. Nothing from the volume reaches host config except the data-only preferences of the write-back row below: at launch the filtered host `settings.json` replaces the volume copy, and `npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor` and `httpProxy` are host-owned and not copied. |
| `pi update` and `pi config` on the host | Typed by the developer, every `pi update` form runs the host pi on the host: it updates the host pi, the npm and git packages in the host `settings.json` (with the host `npmCommand`) or the host model catalogs. `pi config` without `-l` changes the host `settings.json`. | Only the command the user typed. Every form except a bare self-update (`update`, `update pi\|self\|--self`) and `config` without `-l` runs host pi from an empty folder against the host agent dir, so pi loads only user-scope settings: it reads project settings only from `<cwd>/.pi/settings.json`, and the empty folder has none. The bare self-update runs in the cwd but reads only the global `selfUpdateCommand` and `npmCommand` for the self target. Local-path packages are never run by an update (pi updates only npm and git sources). `pi config -l` stays in the sandbox, since it writes the project `.pi`. |
| `pi auth`, help, `--list-models` and `--export` on the host | Typed by the developer, they run host pi on the host instead of in a sandbox: `auth login\|logout` change the host `auth.json`, `--list-models` resolves the host's credentials (a `!command` in host `models.json` runs, as in the host pi helper row), and `--export` reads a session file and writes an HTML file in the cwd. | Only a whole command line `cli/host-routes.ts` recognises; a flag value, a word after `--` or any extra flag launches instead. None of them loads an extension or a package resource or installs a package, so a package a sandbox can rewrite (a local path in the host `settings.json`) never runs on the host through them: top-level help and `--list-models` run with `--no-extensions --no-skills --no-prompt-templates --no-themes --offline` from an empty folder, `auth`, subcommand help and mcp's help return before pi reads packages or extensions, and `--export` runs before pi loads any resource and only parses the session file, as host pi does on `/resume`. `pi list` and `pi config -l` stay in the sandbox, since host pi would run a trusted project's `npmCommand`. |
| Config file | Whoever can write `<agent dir>/pi-sandbox/config.json` sets every limit: that is the user who runs the launcher, and any process of that user on the host. | The container cannot reach it: the workspace guard refuses a folder that is or contains the launcher folder, and of the agent dir only the folder's session directory (read-write) and the render dir and `trust.pem` (read-only) are mounted, so the file is not inside. The launcher reads the file and never writes it. |
| Denial page | A denied CONNECT is accepted and answered over TLS with a launcher-CA certificate for the denied name, so the container sees a certificate the launcher CA issued for a host it may not reach. | For a host `egress.allow` does not list on that port, the proxy accepts the CONNECT, serves a 403 text page carrying the allow hint over TLS with a launcher-CA certificate for the denied name, and never resolves or contacts that host. At most 30 new denial certificates are minted per minute, beyond which the CONNECT itself gets a 403; the 256 most recently used are kept. Denial certificates and rule host leaves live in the proxy's memory (a leaf's key is written briefly under the state dir for openssl to sign); the CA itself is created once under a file lock. |
| MCP sign-in on the host | A sandbox request can open a host browser tab for a host-configured server: a request whose injected token has expired or was rejected starts `pi mcp login <name>` on the host. | Only servers in the host user `mcp.json` (the login runs from an empty folder against the host agent dir, and the URL is built by host pi); only when the proxy itself injected the token (a `401` to the container's own `Authorization` starts nothing); a server for which the host holds no token starts no login, and a host sign-in state is never cached. The proxy starts at most one per server per 60 s host-wide, none for 10 min after a failure, and at most one per server per 10 min caused by a rejected token that has not expired, whatever its exit code, so an identity provider that approves at once cannot be made to open a tab every minute (one lock per server, and `<state>/mcp-login.json` written under its own file lock, shared with the launch-start sign-in, which a launch whose input and output are a terminal runs once and skips for 24 h after a failure); the login runs in its own process group, killed when the proxy stops. |
| Proxy settings for tools (`JAVA_TOOL_OPTIONS`, `PI_SANDBOX_PROXY_TOKEN`, Maven settings) | The repository token sits in more places inside the container, and every JVM prints it on stderr (`Picked up JAVA_TOOL_OPTIONS:`), so it lands in tool output and session logs. | The token is the same one `HTTPS_PROXY` already carries: it only identifies the repository to the proxy and grants nothing a process inside does not already have; no provider secret is in these variables or in the rendered `m2-settings.xml`. The launcher CA joins the image's system store, inside the container only. |
| gh, glab and registry credentials (derived by default) | The host's gh and glab tokens and the registry passwords of `~/.npmrc`, `pip.conf` and `~/.m2/settings.xml` are usable from the sandbox on their hosts, with the user's identity (reach in section 5). | The container holds placeholders only; the tokens come from `gh auth token` and `glab config get token` on the host at request time and reach only the token's own host and API host (and `uploads.github.com` for github.com); `credentials.derive.enabled: false` or `credentials.derive.hosts` removes them; encrypted Maven passwords are never derived. |
| Pi runs online | Startup installs and catalog refreshes reach the network. | They reach only allowed hosts; a denial is reported, never bypassed. |
| Host sessions, write path (`sessions.host`, on by default) | The agent can create, rewrite or delete this folder's session files on the host, the ones from before the sandbox and the subagent runs under `<session>/agents/` included. | Only this folder's directory is mounted. `sessions.host: false` turns it off. |
| Host sessions, read path | The agent can read this folder's earlier host sessions, which may hold secrets a tool printed in an unsandboxed session; for this one folder that weakens "no credential bytes inside". | `sessions.host: false` keeps sessions in the volume; the README names the trade-off. |
| Host sessions, host parsing | Host pi parses the JSONL line by line and runs no code from it, but a session resumed with `--no-sandbox` carries injected content into an unsandboxed agent, and a header `cwd` makes host pi switch to that directory on resume. | The sweep finds each top-level `*.jsonl`'s header as pi does (first non-blank line that parses, lines split on `\n`) and renames it to `.rejected-<random>` when that session's `cwd` is outside the folder, when a bare carriage return (a `\r` not followed by `\n`) appears before the header, when no deciding line turns up within 1 MiB or when it cannot be read, before each launch, after pi exits and before host pi runs on `--no-sandbox`, with the feature on or off. A file it cannot rename is reported and kept, and the launch refuses until it is fixed. The `cwd` check is lexical: a `cwd` of `<repo>/link` whose `link` points outside passes, which adds nothing to what the writable folder already allows. Content injection stays: resuming a sandboxed session outside the sandbox trusts what the agent wrote, as the folder's own files already require (`.pi/extensions` can be planted anyway). |
| Host sessions, symlinks and special files | Host pi follows links when it lists sessions, so a link could pull another repository's session (or any file) into this list, and a fifo could hang `/resume`; a symlinked `<session>/agents` could redirect host-side subagent writes. | The sweep `lstat`s every entry, re-checks device and inode right before acting, and deletes only the entry itself (symlinks, fifos, sockets, devices), never a target. Top-level entries are swept at every launch and exit; the `agents/` trees only while no other launch of the folder is live and no container of it runs, under the repository launch lock, so no agent can start and swap a directory for a link during that walk. Hard links cannot cross the mount. A directory the guest made read-only gets `u+rwx` back before the sweep acts in it. |
| Host sessions, size | No cap: the agent can fill the disk through that directory. | The same is possible through the folder bind; the sweep warns about a top-level file over 256 MiB. |
| Host sessions, slug collisions | pi gives `/a/b-c` and `/a/b/c` the same slug, so two such folders share one session directory and see each other's sessions. | Isolation between folders is as good as pi's slug; the header check renames sessions whose `cwd` lies outside this folder, which also hides the colliding folder's legitimate host sessions from host pi (a known gap). |
| Workspace mode | One container sees every repository in the folder, so the agent can read and change all of them. Launching costs one git call per repository at discovery and one more for the git baseline. | Only folders without a repository above them; the guard refuses as for a repository, before the folder is searched; each repository's hooks are read-only and its git changes reported, bare repositories are read-only, checkouts whose git dir lies outside get no git, and the launch fails closed (see section 3). Start pi inside one repository to give the agent only that one. |
| Shared caches (`mounts.sharedCaches`) | One volume per entry and user is mounted read-write into every sandbox of that user, so it is a write channel between repositories: one sandbox can plant a poisoned package or build output that another repository's sandbox then runs. It never reaches the host: the host folder of the same name is not mounted. | Off by default (`[]`). Entries must lie under the home and not be or lie under `~/.pi`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `~/.config` or `~/.local/bin`, so no credential store or `PATH` directory of the sandbox user is shared. The volumes carry only the user hash and the path, never a repository label. Opt in only for package caches, knowing that a poisoned entry reaches every repository that uses the cache. |
| Build output overlays (`mounts.autoOverlays`, on by default) | The launcher creates missing overlay directories (`node_modules`, `.venv`, `target`, `.gradle`; empty) on the host as mount points, and hands the volume mount points to the sandbox user with one root exec after each start. | A convenience, not a security control: the overlay keeps native modules built for Linux off the host and, as a side effect, keeps the sandbox from writing into the host's `node_modules` (and its `.bin`) at those paths, but the agent can still write every other file host tools run, `package.json` scripts included. The mount points are created as the host user, one level at a time, and a link or non-directory in their place refuses the launch; the `chown` runs inside the container on its own mount points only (`chown -h`). The launcher never creates a mount point whose real path lies inside a git dir or a read-only mount, whatever its spelling (case, links): an overlay there is skipped with a notice. |
| Settings write-back | The sandbox can now change host files: the allowlisted keys of `<agent dir>/settings.json` (`defaultProvider`, `defaultModel`, `defaultThinkingLevel`, `enabledModels`, `theme`, `hideThinkingBlock`, `quietStartup`, `collapseChangelog`, `doubleEscapeAction`, `treeFilterMode`, `steeringMode`, `followUpMode`) and of `pi-subagents.json`, `pi-style.json`, `pi-notifications.json` and `pi-session-limits.json` (their extensions' top-level keys, except `pi-subagents.json` `disabledPlugins`). A hostile agent can change host preferences such as the default model, provider or theme. | The allowlist is fixed in launcher code with no config key, and holds data only: no key whose value the host runs or uses as a URL or command, so no package, extension, skill, prompt, theme path, command, shell, editor, proxy, session dir, trust or model override, and never `auth.json`, `models.json`, `mcp.json`, `trust.json` or agent files. The one key host pi turns into a path is `theme` (a file name in its themes dir), accepted only as `[A-Za-z0-9._-]+` and not `.` or `..`. Every `settings.json` value is type-checked (strings, booleans, a string list, or pi's own enum values) and a failing change is dropped with a notice; `pi-*.json` values are left to their extensions' schemas. The launcher's host process does the write, never the container; it reads volume files through exec with a size cap (64 KiB for a `pi-*.json`) and a 5 s host-side timeout, only as regular files, skips one that is missing, not a regular file, unreadable or not a JSON object (no key of it counts as deleted), compares against a baseline in the state dir the container cannot see, keeps the host value when both sides changed a key, keeps every other host key, and prints every change it writes. |
| VM shares (Colima) | A folder outside the home gets the whole `/Volumes/<name>` volume, or its parent folder, shared with the Colima VM, writable when the folder needs it, and the share stays. A share already inside the new one is merged into it (colima refuses nested mounts), so the VM may see a wider folder than before. | This widens what the VM sees, not what a container sees: a container still gets only the binds of its spec. The launcher restarts only its own `pi-sandbox` profile, only when no other launch is live; `pi sandbox doctor` never shares a path or restarts the VM; it only names a missing share or, with `workspaceRoots`, shares that differ. With `workspaceRoots` set, shares are not widened: the VM gets exactly the roots, the session dir and `<state>/vm`, and a root that is the home, above it, or overlaps a protected path (listed under Colima VM above) is refused. |

## 5. Known gaps

This is the one list of what the launcher does not cover; the other docs link here.

Lifecycle:

- A launcher killed with `kill -9` leaves its container, relay, network, proxy, token and created folders in place until the next launch of any repository, `pi sandbox stop` or the uninstall. Its launch entry stops counting as soon as its pid is gone and its proxy exits about a minute later. A VM restart removes the containers and relay.
- A change to the credential rules, an env secret, the parent proxy or the extra CAs does not reach a repository's running proxy while another launch of it is live: the new launch keeps the old proxy with a notice, so a removed credential stays usable until the last session ends. Egress settings (`egress.allow`, `egress.deny`, `egress.privateHosts`, derived hosts) reach the running proxy only when a new pi starts in that folder and rewrites `egress.json` (editing the config alone changes nothing for running sessions); from then on every new CONNECT of the folder uses them, with a notice to the new launch, and connections already open stay until they close. Other config changes apply at the next launch, since every launch gets its own container.
- If a repository's proxy dies while its sessions run, the relay forwards to the old port until the next launch restarts the proxy and recreates the relay; a local process that took that port in between receives the repository token (which only identifies the repository) and the tunnels.
- Locks, launch entries and proxy records follow the holder's pid, boot time and process start time, never a timer, except `vm.lock`, judged by its age. A running pid counts as live when the start-time tool itself failed, and as dead when no start time is obtainable for that pid. macOS reports the start time to the second, so a pid reused within the same second as the recorded process would still count as live; the effect is a sandbox kept, never one removed. A hung launcher keeps its lock: other launches of the repository wait up to 120 s and then fail without removing anything.
- A repository on an unmounted disk or share keeps its state and volumes; only a folder whose parent exists and whose mount point is mounted counts as deleted. Forgetting a repository also removes its grants, so a later folder at the same path starts without them.

Network and credentials:

- The agent can use every credential it cannot read: while a session runs it can make authenticated calls to every rule host (the proxy is a confused deputy).
- Reach of the derived gh and glab tokens, on by default: through the token's hosts the sandbox can push to every repository the token can write, create gists, add deploy keys and push workflows that run with the repository's CI secrets; glab adds deploy tokens and CI variables. Limit it with `credentials.derive.hosts` or a token with fewer scopes on the host.
- A sandbox request can open a sign-in tab in the host browser: a request to a host-configured OAuth MCP server whose injected token has expired or was rejected starts `pi mcp login` on the host, from the proxy at most once per server per 60 s host-wide, none for 10 minutes after a failure, and at most one per 10 minutes per server for a rejected token that has not expired; the launch-start sign-in runs once per launch whose input and output are a terminal and is skipped for 24 hours after a failure.
- Exfiltration through an allowed host stays possible, and a host that fronts many sites (a CDN) can carry traffic to sites behind it through domain fronting; allow such hosts deliberately.
- Response bodies are not scrubbed, so a rule host that echoes request headers into a body reflects the secret.
- The launcher CA has no name constraints; it is trusted inside the container only.
- URL credentials in `.npmrc` and `pip.conf` are read back by key or index position, not checked against the rule host; editing those files on the host during a session can send one registry's password to another rule host after a `401`.
- JVM HTTP clients that cannot authenticate to the proxy (`HttpURLConnection` and `java.net.http`, which ignore the `proxyUser` and `proxyPassword` properties, and the `mvnw` jar downloader) have no network, and neither do other tools that cannot send proxy credentials (headless browsers). There is no unauthenticated proxy shim inside.
- Project-only OAuth MCP servers (defined only in the repository's `.pi/mcp.json`) get no sign-in on the host and no token inside; `pi mcp add` puts a server in the user `mcp.json`.
- The gateway hostname is visible inside: the sandbox `models.json` keeps each `baseUrl` host (minus userinfo), so an internal gateway's name shows, though never its token. A JWT placeholder keeps the token's lasting claims, such as an account id or email.
- Providers whose client derives the API host from the token content may refuse a placeholder token; the doctor's per-rule check shows a 401 or 403.
- Provider `/login` inside fails (`auth.json` is a 0444 copy of the placeholder file, re-created at every start); log in on the host.
- Secrets in the `env` of stdio MCP servers become placeholders that nothing replaces until a `credentials.rules` entry binds them to the host the server calls.
- A secret written as a purely numeric or boolean value in a stdio MCP server's env or flags is copied, and one under a name without a secret segment is copied unless its value has a credential shape; give it a clearer name or a `credentials.rules` entry.
- When the glab token probe (`glab config get token`) does not answer in time, a Keychain prompt for example, glab has no credentials in the sandbox for that launch.
- Plain HTTP is refused (CONNECT to port 80 has no SNI to check), and host-local model servers (`localhost`, plain `http`) are unreachable.
- Inside the internal network DNS resolves container names only, so tools that resolve names before using the proxy fail.
- NTLM and Kerberos parent proxies need a local relay such as `px` or `cntlm`.
- Image pulls send no registry credentials, so a prebuilt image must be pullable anonymously from the VM.
- A `tls.extraCa` `sha256` entry is looked up in the macOS keychains only; elsewhere it stops the launch and a `file` entry is needed. A self-signed certificate without the CA flag (an old v1 root) is accepted as a CA.
- A `command` secret source is not checked when the config loads; a broken one fails only when the proxy first needs it. It gets 30 s, a failed one is retried at most every 5 s, and it runs with the proxy's minimal environment, so a password manager CLI that needs a session variable fails.
- Registry tokens a tool reads from an environment variable inside get no placeholder: a project `.npmrc` with `_authToken=${NPM_TOKEN}`, uv's `UV_INDEX_<NAME>_PASSWORD` or a `GITHUB_TOKEN` for GitHub Packages. `env.allow` refuses secret-looking names and no rule sets a variable inside, so the tool fails to authenticate. Only `~/.npmrc` is derived (its `${VAR}` tokens included); `PIP_INDEX_URL` and `PIP_CONFIG_FILE` on the host are not derived.
- uv config is not derived: uv ignores `pip.conf`, so `uv sync` resolves against public PyPI (when `pypi.org` is allowed) instead of an internal index, which also opens a dependency-confusion path. Point uv at the index by hand and add a `credentials.rules` entry for it.
- No setting can be enforced on the user who runs the launcher: the config file is theirs to edit, and grants cannot be turned off.

Files and git:

- The hooks dirs are read-only, but the agent can point `core.hooksPath` or `core.fsmonitor` elsewhere by editing `.git/config`, add an alias or an include, or rewrite a worktree pointer; host git then runs what it names. The session-end report names the changed files; nothing prevents the change.
- The git common dir is mounted read-write and `.git/config` is readable inside, so a token in a remote URL is visible to the agent; keep credentials in a credential helper.
- Repository contents stay untrusted for host tools. The agent can create nested repositories, gitlinks and `objects/info/alternates`, and change any file host tools read (editor settings, `.envrc`, package scripts). After the last launch of the folder ends, the launcher reports new or changed `.git` entries (including a changed config or hooks entry inside an existing nested `.git` dir), gitlinks and changes to the repository's own git files; it cannot prevent them. Launching pi from such a nested checkout mounts the git dir its `.git` file names.
- A nested `.git` file pointing at a missing git dir inside the folder is left as plain files; the agent can create that git dir during the session, and host git then opens it with its config and hooks. Only the session-end report names the new git dir.
- Workspace mode protects the repositories present at launch; one the agent creates during the session is reported at the end, not protected, and so is a folder the agent makes unreadable during the session. Host git run on such paths during the session is not covered.
- A missing git dir that a detached checkout points at outside the folder is creatable by the agent only if it lies in another writable mount (the host session directory); the launcher does not check this, since a pointer into it is not one git writes and the agent's own `.git` writes are reported after the session.
- `node_modules` and `.pi` are never searched for repositories, overlaid or not, so a repository inside a `node_modules` or `.pi` folder that no overlay hides is mounted without protection and without a report.
- Names git on HFS+ treats as `.git` through ignorable Unicode code points (`.g‌it`) are not matched as `.git` by the search or the session-end report.
- A bare repository inside a nested repository's working tree counts as that repository's content and is not protected, as in single-repository mode.
- The launcher resolves `git` outside the folder, but runs `colima`, `openssl`, `security` and `tar` by name from `PATH`; a relative or in-folder `PATH` entry could make it run a file the agent wrote.
- With `mounts.autoOverlays` on, the host's and the sandbox's build output diverge.
- The settings write-back lets a hostile agent change the allowlisted host preferences (the default model, provider, thinking level, enabled models, theme, the extensions' limits and subagent overrides), never code or credentials; each change is printed at the session's end or the next launch. Its write can race host pi writing the same file at the same moment: the host file is re-read right before the atomic rename, but a host pi write in between can be lost, or overwrite the launcher's. `pi sandbox doctor` writes back before it syncs, as a launch does. When refreshing the volume fails the baseline is deleted and a warning says that later changes will not be written back.
- Without `workspaceRoots`, the Colima VM sees all of the home directory, writable; only the container's mounts limit what pi sees, and a container escape reaches all of `~`. VM shares added for folders outside the home are never removed automatically. With `workspaceRoots`, an escape still reaches every root, the session files of every folder and the rendered agent files of every folder; and while other launches run, a VM installed earlier keeps its home share until a launch with none running restarts it.

Image:

- Image builds (the base image and the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer) reach the network directly from the VM, outside the egress allowlist and the private-range deny. The launcher starts them, not the agent, so this is a supply-chain exposure rather than an agent channel.
- The launcher modifies the VM's system trust store: it installs the `tls.extraCa` certificates from the user's config under `/usr/local/share/ca-certificates/pi-sandbox/` (removed again when the list empties), so the VM's engine and every process in the VM trust them, and restarts `containerd` and `docker` to pick them up, only when no other launch is live; until then a change waits, and the engine keeps the previous roots. A launch's own containers do not inherit the VM's store. The certificates come only from the launcher's config file, as for the container.
- A pulled `image.digest` image lacks the launcher CA in its system store, so a tool that reads only the system store (a Debian JDK) does not trust the proxy's certificates for rule hosts.
- A JDK installed outside apt after the image build (toolchains, sdkman, a tarball) lacks the launcher CA; the entrypoint builds the truststore only for the `java` on `PATH` at container start.
- The base image is pinned by tag, not by digest, so a rebuild picks up whatever the tag points at.
- The missing-command hint reaches bash only, and an agent can unset it in its own shell.

Host sessions:

- The agent can read this folder's earlier host sessions, which may hold secrets a tool printed outside the sandbox; `sessions.host: false` keeps sessions in the volume.
- While a container of the folder runs, the sweep checks only the top level of the session directory, so a link the agent planted under `<session>/agents/` stays until the last session stops; host pi may follow it in that window.
- On a slug collision (pi gives `/a/b-c` and `/a/b/c` the same slug) two folders share one session directory, and the sweep of one renames the other's sessions to `.rejected-<random>`; rename them back by hand.
- A custom host session dir (`PI_CODING_AGENT_SESSION_DIR` or `sessionDir`) is not shared, a project `sessionDir` and a `--session-dir` you pass are not considered, and host sessions started in a subdirectory of the folder are not visible inside, since pi inside always uses the folder root's slug.
- The share check proves the directory is shared and writable at container creation and on each doctor run, not later.
- Handoff documents of sandboxed sessions live in the container's `/tmp` and are gone when the session is resumed on the host; only host pi prunes old subagent runs.
