# launcher threat model

What the sandbox protects, where its trust boundaries are, and what each feature weakens. How it works is in [ARCHITECTURE.md](ARCHITECTURE.md); what the user sees is in [README.md](README.md).

## 1. Assets

- **Host credentials:** model provider keys and OAuth tokens in `~/.pi/agent/auth.json`, keys and header values in `models.json` and `mcp.json`, environment variables, keychain items, password manager entries, MCP OAuth tokens, parent proxy credentials.
- **Host files:** everything in the home directory outside the repository, other repositories, `~/.pi`, the launcher's state and config.
- **Host pi sessions:** the transcripts in `~/.pi/agent/sessions/` (under `PI_CODING_AGENT_DIR` when set), one directory per repository; host pi reads them on `/resume`, `-c` and `--session`.
- **The network:** hosts the developer can reach (internal services, cloud metadata, private ranges) and the developer's identity toward them.

The agent inside the container is assumed hostile: it may run any command, write any file it can reach, and send anything to any host the proxy lets through.

## 2. Trust boundaries

- **Container:** runs pi and every tool it starts. Sees the repository and its git dir (read-write; hooks, `commondir`, `gitdir` and a `.git` file bound read-only directly from the host, git config read-only from a launcher-owned copy), its own agent volume, its `node_modules` and cache volumes, the user's shared cache volumes (`mounts.sharedCaches`, read-write, shared with every other sandbox of the user), host pi's session directory for this repository (read-write, at its host path, while `sessions.host` is on), the read-only render dir and the trust bundle. In workspace mode the "repository" is the workspace folder, and every repository in it has its git metadata protected as one repository's is. Its only network path is the proxy URL, authenticated with a per-repository token.
- **Proxy:** a host process per repository. Holds secrets in memory only (they reach it on stdin), decides every connection, terminates TLS for credential rule hosts and injects credentials there. Trusts the launcher that started it, never the container.
- **Host pi helper:** pi's managed install in the host agent dir (its current release run with the launcher's node, not through the `bin/pi` wrapper), else the bundled pi next to the launcher, run on the host to print credentials (`pi auth print-api-key`, `print-bearer-token`), to sign in and refresh MCP OAuth (`pi mcp login <name>` against the host agent dir, from an empty folder so no project `.pi/mcp.json` loads), and to read the provider host table. It runs with the developer's rights. Neither is writable by the sandbox: the host agent dir is never mounted and a repository that contains or lies inside it (or `~/.pi`) is refused, and the bundled pi lies in the launcher's install. A `pi` found on `PATH` never serves these jobs, since one proxy daemon serves every repository of a policy; it runs only for `pi --no-sandbox` and a bare `pi update`, typed by the developer, and only when neither it nor its real path lies in the repository, its git common dir or `mounts.extraReadOnly` and its `PATH` entry is absolute. The proxy daemon is restarted at the next launch after the host pi version or its commands change; until then a running daemon keeps the command it started with.
- **Colima VM:** runs the container engine and mounts `$HOME` writable so repositories under it can be mounted. The VM is not a security boundary against the developer's own files; only the container's mounts are.

## 3. Baseline guarantees

- No real secret in the container's filesystem, environment or volumes. Rendered `auth.json`, `models.json` and `mcp.json` hold placeholders (`pi-sandbox-` plus 24 hex of a salted hash; JWT-shaped for JWT access tokens), and so do the rendered tool files (gh `hosts.yml`, glab `config.yml`, `.npmrc`, `pip.conf`, the Maven servers), `GH_TOKEN`, `GITLAB_TOKEN` and what the gh and glab credential helpers print inside; the rendered files are read-only links, the gitconfig and the glab config writable copies (all re-created at every container start, so a file the agent put in their place is replaced), the render copy of agents, prompts, skills, themes and extensions skips `.git`, `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `id_*`, key and certificate stores and secret-named files (source and markdown files excepted), a `settings.json` package URL with userinfo and a stdio MCP server's URL userinfo or secret-named `--name=value` argument become clean or placeholders, a URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`, `PIP_INDEX_URL`) keeps its shape with a placeholder for the password, or for the user name when the token is the user name, bound to that host (and, for npm, its path), any other `.npmrc` or `pip.conf` value with URL userinfo and every npm and pip proxy setting stay on the host, userinfo in a Maven mirror URL is removed, the host `settings.json` `httpProxy` is never synced (the sandbox uses the launcher's proxy), an MCP URL or a `models.json` `baseUrl` with a secret-like query parameter is dropped with a notice, and `pi sandbox doctor` sweeps the environment, `auth.json`, `mcp.json`, `mcp-auth.json` and the `settings.json` packages for anything else.
- Egress allowlist: a host leaves only when it is in `egress.allow` (with the `egress.presets` hosts), a credential rule host, a derived host or a grant; `egress.deny` always wins.
- SNI check: a tunnel whose ClientHello names another host than the CONNECT target is refused.
- Private-range deny: IP literals, localhost, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except the names in `egress.privateHosts`.
- Workspace guard: a repository at or above the home directory, `~/.pi`, the state or config dir, or `/`, or inside `~/.pi`, the state or config dir, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube` or a system dir, is refused before anything is mounted; the guard and `mounts.extraReadOnly` read the same protected table.
- Host session directory: the one exception to "nothing of `~/.pi` is mounted". The launcher recomputes the path from the agent dir and the repository's real path with pi's slug formula, and mounts it only when it is exactly one level under `<agent dir>/sessions`, its name matches `--…--` without a `/`, it is a real directory (not a symlink), its real path is that slug under the real path of `<agent dir>/sessions`, and that real path neither is nor contains `~/.pi` or the agent dir, nor overlaps any other agent dir entry. `mounts.extraReadOnly` still refuses everything under `~/.pi` and the agent dir, so the exception cannot be widened by config. The launcher creates the directories 0700 before the check, so the engine never creates a root-owned one.
- Extra mounts: each `mounts.extraReadOnly` entry must exist as a file or directory and is bound at its real path; it is refused when it is or contains the home, or is, contains or lies under `~/.pi`, the agent dir, the state dir, the user config, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys`, `/dev`, a `.git` dir or the engine socket (`pi-sandbox: mounts.extraReadOnly: <path> is not allowed (<reason>)`). Nested `.git` dirs deep inside an allowed directory are not scanned.
- Git dir layout, checked before any git call: the launcher finds the nearest `.git` itself (`lstat`, no link followed) and accepts a real `.git` directory, or a `gitdir:` file whose target is either its own git dir (a separate git dir, a submodule opened as a repository) or a linked worktree's `<common>/worktrees/<name>` whose `commondir` resolves to that common dir and whose `gitdir` resolves to this checkout's `.git`. `git rev-parse --show-toplevel --git-common-dir` must then agree, and a failing git refuses too, so a `gitdir:` file rewritten to point at an arbitrary host directory is never mounted. A `gitdir:` file pointing at a directory named `.git` (another checkout's git dir) refuses. A link at `.git`, at the gitdir target, at `commondir` or `gitdir`, a `commondir` in a git dir where git never writes one (the common dir, a submodule git dir) with any content but the launcher's pin (an empty one, the bind mountpoint the engine creates when a stopped container is started without the launcher, is opened without following links and, when it is still an empty regular file with one link, filled with the pin in place, so the mount on it stays attached), or a worktree `commondir` pointing at another repository refuses the launch (`pi-sandbox: git: <path> was not written by git or the launcher`, `... is a symbolic link`, `... points at <path>`). The launcher's own host git calls run with `-c core.fsmonitor=false -c core.hooksPath=<an empty dir under the state dir>`.
- Read-only git dir: what is protected is the code the host's git runs from the git dir. Inside the container these are read-only: the common dir's and every submodule git dir's `config`, `config.worktree` and `hooks`, `core.hooksPath` when it resolves inside the repository or git dir (refused when the path goes through a link inside them), every `worktrees/*/commondir`, `gitdir` and `config.worktree`, the checkout's `.git` file when it is one, and a `commondir` pin with content `.` (git reads it as the git dir itself) in the common dir and in each submodule git dir. Right before every container create (under the repository's container lock), every one of them is checked: its real path must equal its path inside the repository or git dir and pass the `mounts.extraReadOnly` protected-path check. The hooks dirs, `commondir`, `gitdir` and the checkout's `.git` file are then bound read-only directly from the host; only a host-side actor that swaps a checked path between the check and the bind defeats this, which is outside the threat model. The `config` and `config.worktree` files are copied into `<state>/repos/<repo hash>/git/<sha16 of the path>` (opened without following links, device and inode equal to a fresh `lstat`) and bound read-only from that private copy, which the last session's end deletes; a symbolic link inside a hooks dir resolves inside the container, where its target is not mounted, so its target is never copied or exposed. A link at any of these paths, or a path whose real path goes through one, refuses the launch, so no bind ever reaches a link target. The paths are found once per launch; right before a start, after the pins are written the layout is checked again, and after missing hook dirs are created every protected path is checked again, so a link planted between discovery and start refuses too. The pin is written on the host (by a hard link of a temporary file, or an exclusive create where hard links are unsupported, never over an existing entry; a failed write refuses the launch) before every create, so the engine never creates an empty `commondir` (which would break host git), recorded in `<state>/repos/<repo hash>/pins.json`, and removed after the last session of the repository removes its container (or by the sweep after a crash), only when it still reads `.` (any other content is left in place with a notice, and the next launch refuses the repository), and only when no created or running sandbox of another checkout shares the git dir (the check and the removal run under a lock per git common dir under the state dir, which a launch also holds from the pin write through the container start) (a linked worktree and its main checkout, a superproject and a submodule opened as its own repository; the containers carry `pi-sandbox.git-common-dir`), since deleting the file under a bind would detach the read-only mount in that container. The git dir and every directory between the repository root (or a git dir outside it) and a read-only path, such as `.git/modules/<name>` and `.git/worktrees/<name>`, are bound onto themselves, so the agent cannot rename `.git` or one of those parents away from its mounts (the kernel refuses to move a mountpoint). These binds use typed mounts, so a missing source fails the start instead of being created. After the last session the launcher re-runs the layout checks and prints any failure as a notice.
- Workspace mode: started in a folder that is not inside a repository, the launcher searches the whole folder (hidden directories included, `node_modules`, `.pi` and the inside of `.git` dirs skipped, links not followed) and applies the read-only git dir protection, the pins, the launch checks and the session-end checks to every repository it finds. It fails closed: the launch refuses when a repository fails the single-repository checks, when its git dir or common dir lies outside the folder, when a git config file the folder or a repository reads (every scope but the command line, files named by `include.path` and `includeIf` included) or a `core.hooksPath` lies inside the folder but outside every repository (inside any nested repository, a sibling included, it is bound read-only in the overlay of the repository that reads it), when a directory cannot be read (`workspace: <dir> cannot be protected: cannot read it (<code>)`), when an installed git fails to list a configuration, when the folder holds more than 128 repositories, and when the search would visit more than 50 000 directories, so no repository present at launch is mounted without its protection. Every nested repository root and each directory between the folder and it is bound onto itself, so the agent cannot rename a repository away from its read-only mounts. The workspace's container carries all git common dirs in `pi-sandbox.git-common-dirs`, so a pin is removed only when no workspace or single-repository sandbox holding that git dir is created or running. Submodule checkouts are protected through their superproject's `.git/modules`.
- Per-repository networks: each repository's containers join their own internal network `pi-sandbox-<first 12 of the repo hash>`, so containers of different repositories share no network; each repository has its own relay, which only forwards to its proxy port.
- MCP OAuth tokens stay in host pi's `mcp-auth.json`, which the launcher only reads; the proxy injects the access token for a placeholder `Authorization` and pi inside never holds a token, a refresh token or a client secret (the sandbox `mcp.json` has no `oauth` block).
- Per-repository proxies: each repository has its own proxy process with its own rules, env secrets, parent-proxy credentials and token, so one repository's container cannot use another's. The token (`<state>/repos/<repo hash>/proxy/token`, mode 600) is a proxy credential, not a provider secret, and is in the container's env; it is deleted with the container, so the next fresh container gets a new one. Grants are read live from `grants.json`.

## 4. What each feature weakens, and the mitigation

| feature | what it weakens | mitigation |
| --- | --- | --- |
| TLS termination of rule hosts | The launcher CA is trusted inside the container and has no name constraints, so it could sign any name there. | The CA key never leaves the host state dir; only rule hosts are terminated, every other tunnel stays end to end. |
| Placeholder substitution | A rule host that echoes request headers or bodies reflects the real secret back into the container. | Substitution happens only in the rule's own header, or, for a rule without one, in auth-like request headers (`authorization` and secret-like names, never `proxy-authorization` or `sec-*`); the placeholder is stripped from every other header and never substituted in query parameters or bodies. A `Basic <base64>` value is decoded for the check, the stripping and the substitution, and re-encoded, so the decoded secret goes only to the rule host; the exact base64 sent is scrubbed from response headers like the secret. On terminated hosts, an absolute-form target for another origin and a path with dot segments (raw, `%2e`, an encoded slash or a backslash) get `400`, and `pathPrefix` is matched on the decoded path. Every response header value is scrubbed by substring (`Location`, `Set-Cookie`, `WWW-Authenticate` included). Response bodies are not scrubbed: allow rule hosts that do not echo. |
| Derived hosts | Host config files widen egress: every provider and MCP host in `auth.json`, `models.json` and `mcp.json` becomes reachable. | `credentials.derive.enabled: false` or `credentials.derive.hosts` (final when the policy or org layer sets them), and `egress.deny`. |
| `egress.privateHosts` | Names in `privateHosts` (a private gateway host, for example) skip the private-address filter, so a rebinding DNS answer for them reaches an internal address. | Only names, no IP literals or localhost; set by policy, org or user, never by a project, and final when the policy or org layer sets it. A rule host that resolves privately and is not listed gets a launch notice. |
| Grants | The developer can widen egress at run time, for one repository or every repository, until the grant is revoked. | `egress.grants: false` from policy or org turns grants off for good; `egress.deny` and the private-range check still apply. The container cannot create grants: the CLI runs on the host only and the proxy has no grant endpoint. |
| Parent proxy | DNS is delegated: with a parent proxy set, an NXDOMAIN locally is passed to the parent, which resolves it. | The private-range check still runs on every local resolution; `noProxy` names are dialled directly. The parent's credentials are resolved on the host and kept in the proxy's memory; with `"env"` they reach it on stdin and are stripped from the environment the proxy starts with. The proxy process starts with a minimal environment (path, home, temp, locale, CA files, the launcher's path overrides, `HTTPS_PROXY` without userinfo), so no secret variable of the launcher reaches it except through its stdin input; an env secret with a CR or LF is refused at launch, so it cannot split a header. |
| Extra CAs | Trust widens to the corporate CA, inside the container, in the proxy's upstream trust and during image builds. | `tls.extraCa` is a policy or user key, never a project key, and only shrinks under a higher layer. The build removes the CA from the image again. |
| Image layers | `image.dockerfile` runs as root at build time on the engine's default network. | Policy, org or user only, an absolute path, used verbatim; the layer runs on top of the sandbox image and ends with a fixed tail (`USER pi`, the workdir, the launcher's entrypoint and an empty `CMD`). The proxy, CA and environment are set by the container spec at run time, not by the image. Treat the file as code the developer runs. |
| Host pi helper | `!command` values in host `models.json` and `mcp.json` run on the host, as they would with local pi. | Only values from the developer's own host files; a value in a file the container can write (the repository's `.pi/`) is never run on the host. |
| `pi install|remove` on the host | Typed in the sandbox shell, it runs the host pi on the host and changes the host `~/.pi/agent/settings.json`. | Only the command the user typed, as `pi mcp add` is. A local install source inside the repository, its git dirs or the workspace root (checked on the path and its real path) is refused and nothing is written, since host pi would load code the container can rewrite. Nothing from the volume reaches host config: at launch the host `settings.json` keys overwrite the volume copy, and `npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor` and `httpProxy` are host-owned (the volume's values are dropped); the host `httpProxy` is not synced either, since it can carry the proxy password. |
| Org baseline | A compromised baseline file changes the effective policy. | An absolute path on the host, read at every launch and validated as the `org` layer, which cannot set a key the policy sets; a missing file stops the launch, `pi --no-sandbox` included. Whoever can write the file can change the baseline, so it belongs in a path only the administrator writes. |
| Denial page | A denied CONNECT is accepted and answered over TLS with a launcher-CA certificate for the denied name, so the container sees a certificate the launcher CA issued for a host it may not reach. | For a host the egress allowlist or port check denies, the proxy accepts the CONNECT, serves a 403 text page carrying the allow hint over TLS with a launcher-CA certificate for the denied name, and never resolves or contacts that host; at most 30 new denial certificates are minted per minute and 256 are kept, beyond which the CONNECT itself gets a 403. Denial certificates and rule host leaves live in the proxy's memory only (LRU of 256 each); the CA itself is created once under a file lock. |
| MCP sign-in on the host | A sandbox request can open a host browser tab for a host-configured server: a request whose injected token is missing, expired or answered `401` starts `pi mcp login <name>` on the host. | Only servers in the host user `mcp.json` (the login runs from an empty folder against the host agent dir, and the URL is built by host pi); only when the proxy itself injected the token (a `401` to the container's own `Authorization` starts nothing); host-wide at most once per server per 60 s, none for 10 min after a failure, and at most one per server per 10 min caused by a rejected token (a `401` to an injected token that has not expired), whatever its exit code, so an identity provider that approves at once cannot be made to open a tab every minute (one lock per server and `<state>/mcp-login.json`, shared with the launch-start sign-in); the login runs in its own process group, killed when the proxy stops. |
| Egress presets (`egress.presets`, npm, pypi and github by default) | The default allowlist is a little wider than one host per registry: the yarn registries, `codeload.github.com`, `objects.githubusercontent.com`, `raw.githubusercontent.com` and `release-assets.githubusercontent.com` are reachable, and the GitHub content hosts serve any public repository's files. | Only package registry and download hosts, no API host; other presets are opt-in; the policy or org can set `egress.presets: []` for good, and a project file may not set it. |
| Proxy settings for tools (`JAVA_TOOL_OPTIONS`, `PI_SANDBOX_PROXY_TOKEN`, Maven settings) | The repository token sits in more places inside the container, and every JVM prints it on stderr (`Picked up JAVA_TOOL_OPTIONS:`), so it lands in tool output and session logs. | The token is the same one `HTTPS_PROXY` already carries: it only identifies the repository to the proxy and grants nothing a process inside does not already have; no provider secret is in these variables or in the rendered `m2-settings.xml`. The launcher CA joins the image's system store, inside the container only. |
| gh, glab and registry credentials (derived by default) | The host's gh and glab tokens and the registry passwords of `~/.npmrc`, `pip.conf` and `~/.m2/settings.xml` are usable from the sandbox on their hosts, with the user's identity (reach in section 5). | Allowed by the derive exception: the container holds placeholders only, the tokens come from `gh auth token` and `glab config get token` on the host at request time and reach only the token's own host and API host; `credentials.derive.enabled: false` or `credentials.derive.hosts` removes them; encrypted Maven passwords are never derived. |
| Removing `PI_OFFLINE` | Startup installs and catalog refreshes reach the network. | They reach only allowed hosts; a denial is reported, never bypassed. |
| Host sessions, write path (`sessions.host`, on by default) | The agent can create, rewrite or delete this repository's session files on the host, the ones from before the sandbox and the subagent runs under `<session>/agents/` included. | Only this repository's directory is mounted. Policy or org can turn the key off and lock it; a project file cannot set it. |
| Host sessions, read path | The agent can read this repository's earlier host sessions, which may hold secrets a tool printed in an unsandboxed session; for this one repository that weakens "the agent never sees a real credential". | `sessions.host: false` keeps sessions in the volume; the README names the trade-off. |
| Host sessions, host parsing | Host pi parses the JSONL line by line and runs no code from it, but a session resumed with `--no-sandbox` carries injected content into an unsandboxed agent, and a header `cwd` makes host pi switch to that directory on resume. | The sweep finds each top-level `*.jsonl`'s header as pi does (first non-blank line that parses, lines split on `\n`) and renames it to `.rejected-<random>` (deleting it when the rename fails) when that session's `cwd` is outside the repository, when a bare carriage return (a `\r` not followed by `\n`) appears before the header (pi's listing splits lines at it and its opening does not, so the two could see different headers; pi never writes one), when no deciding line turns up within 1 MiB (opening reads past that) or when it cannot be read, before each launch, after pi exits and before host pi runs on `--no-sandbox`, with the feature on or off. The `cwd` check is lexical: a `cwd` of `<repo>/link` whose `link` points outside passes, which adds nothing to what the writable repository already allows. Content injection stays: resuming a sandboxed session outside the sandbox trusts what the agent wrote, as the repository's own files already require (`.pi/extensions` can be planted anyway). |
| Host sessions, symlinks and special files | Host pi follows links when it lists sessions, so a link could pull another repository's session (or any file) into this list, and a fifo could hang `/resume`; a symlinked `<session>/agents` could redirect host-side subagent writes. | The sweep `lstat`s every entry, re-checks device and inode right before acting, and deletes only the entry itself (symlinks, fifos, sockets, devices), never a target. Top-level entries are swept at every launch and exit; the `agents/` trees only while no container of the repository runs (after the last session's stop, and before a launch that finds none running), decided and run under the repository's session registry lock, only when no other session is registered and the container is not running, so no agent can start and swap a directory for a link during that walk. Hard links cannot cross the mount. A directory the guest made read-only (its uid maps to the host owner) gets `u+rwx` back before the sweep acts in it; an entry that still can be neither renamed nor deleted makes the launch, and `pi --no-sandbox`, refuse with a message naming it, and the exit sweep warns. |
| Host sessions, size | No cap: the agent can fill the disk through that directory. | The same is possible through the repository bind; the sweep warns about a top-level file over 256 MiB. |
| Host sessions, slug collisions | pi gives `/a/b-c` and `/a/b/c` the same slug, so two such repositories share one session directory and see each other's sessions. | Isolation between repositories is as good as pi's slug; the header check renames sessions whose `cwd` lies outside this repository, which also hides the colliding repository's legitimate host sessions from host pi (a known gap). |
| Workspace mode | One container sees every repository in the folder, so the agent can read and change all of them, and their files outside the git dirs are as writable as one repository's. Launching costs two git calls per repository and recreates the container when a repository is added or removed. | Only folders without a repository above them; the home, `~/.pi`, the state and config dirs and `/` are refused as for a repository; each repository's git metadata is protected and the launch fails closed (see section 3). Start pi inside one repository to give the agent only that one. |
| Shared caches (`mounts.sharedCaches`) | One volume per entry and user is mounted read-write into every sandbox of that user, so it is a write channel between repositories: one sandbox can plant a poisoned package or build output that another repository's sandbox then runs. It never reaches the host: the host folder of the same name is not mounted. | Off by default (`[]`); policy, org or user only, refused in a project file, and final when the policy or org layer sets it. Entries must lie under the home and not be or lie under `~/.pi`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `~/.config` or `~/.local/bin`, so no credential store or `PATH` directory of the sandbox user is shared. The volumes carry only the user hash (from the state dir) and the path, never a repository label; `pi sandbox gc --shared-caches` removes them. Opt in only for package caches, knowing that a poisoned entry reaches every repository that uses the cache. |
| Host caches: sandbox can poison host builds (`mounts.hostCaches`) | The listed host cache folders (`~/.m2/repository`, `~/.gradle/caches` and `~/.gradle/wrapper`, `~/.npm/_cacache`, `~/Library/Caches/pip`, `~/go/pkg/mod`, `~/.cargo/registry` and `~/.cargo/git`) are bound read-write, the first path where the sandbox writes to the host outside the repository and the session dir: the agent can plant or replace artifacts (Maven and Gradle plugin jars, a Gradle wrapper distribution, npm tarballs, wheels, Go modules, crates) that host builds then run with the user's rights, and every repository that enables the preset shares them. Gradle's cross-process lock pings cannot cross the VM, so a host build running in parallel may wait for a lock the sandbox holds. | Off by default (`[]`); policy, org or user only, refused in a project file (a repository cannot opt its user into host poisoning), final when the policy or org layer sets it. Each preset names a cache subfolder, never the tool's config folder, so `settings.xml`, `settings-security.xml`, `gradle.properties`, `init.d`, `.npmrc`, `.pypirc`, `pip.conf`, `credentials*`, `config.toml`, `.netrc` and `.git-credentials` are never mounted, and a cache folder that holds one of these names at its top level is refused. The folder must not be a link, must resolve under the home and not into a protected path (the `mounts.extraReadOnly` table), and is checked before the launcher creates a missing one; the container's `chown` touches only the guest parents (`~/.m2`), never the bound folder. Each launch names the shared presets. Opt in only when the faster build is worth trusting the sandbox with what host builds run. |
| Build output overlays (`mounts.autoOverlays`, on by default) | The launcher creates missing overlay directories (`node_modules`, `.venv`, `target`, `.gradle`; empty) and missing `mounts.cacheVolumes` targets on the host as mount points, and hands the volume mount points to the sandbox user with one root exec after each start. | A convenience, not a security control: the overlay keeps native modules built for Linux off the host and, as a side effect, keeps the sandbox from writing into the host's `node_modules` (and its `.bin`) at those paths, but the agent can still write every other file host tools run, `package.json` scripts included. The mount points are created as the host user, one level at a time, and a link or non-directory in their place refuses the launch; the `chown` runs inside the container on its own mount points only (`chown -h`). A project file may turn the overlay off. |
| VM shares (Colima) | A repository outside the home gets the whole `/Volumes/<name>` volume, or its parent folder, shared with the Colima VM, writable when the repository needs it, and the share stays. | The home is re-added, or upgraded to writable, only when a bound path under it (the state dir, the host session dir) requires it. This widens what the VM sees, not what a container sees: a container still gets only the binds of its spec. The launcher restarts only its own `pi-sandbox` profile, only when no pi session is live and never from the doctor. |

## 5. Known gaps

This is the one list of what the launcher does not cover; the other docs link here.

Lifecycle:

- A launcher killed with `kill -9` leaves its container, relay, network, proxy, token, `commondir` pins and created folders in place until the next launch of any repository, `pi sandbox gc`, `pi sandbox stop` or the uninstall. Its launch entry stops counting as soon as its pid is gone and its proxy exits about a minute later. A VM restart removes the container and relay.
- A config change does not reach a running container while another session of the repository uses it: the new launch joins the old container and prints a notice, so a tightened policy waits for the last session to end; `pi sandbox reset` refuses while a session of the repository runs.
- If a repository's proxy dies while its sessions run, the relay forwards to the old port until the next launch restarts the proxy and recreates the relay; a local process that took that port in between receives the repository token (which only identifies the repository) and the tunnels.
- Locks, launch entries and proxy records follow the holder's pid, boot time and process start time, never a timer, except `vm.lock`, judged by its age. macOS reports the start time to the second, so a pid reused within the same second as the recorded process would still count as live; the effect is a sandbox kept, never one removed. A hung launcher keeps its lock: other launches of the repository wait up to 120 s and then fail without removing anything.
- A repository whose parent folder is missing (a disk that is not mounted) keeps its state, pins, container and volumes until the folder is back or `pi sandbox reset` runs there. `mcp-login.json` is written under one lock per server, so two servers' records written at the same instant can lose one cooldown entry.

Network and credentials:

- A sandbox request can open a sign-in tab in the host browser: a request to a host-configured OAuth MCP server whose injected token is missing, expired or rejected starts `pi mcp login` on the host, at most once per server per 60 s host-wide, none for 10 minutes after a failure, and at most one per 10 minutes per server for a rejected token that has not expired.
- Reach of the derived gh and glab tokens, on by default under the derive exception: through the token's host and API host the sandbox can push to every repository the token can write, create gists, add deploy keys and push workflows that run with the repository's CI secrets; glab adds deploy tokens and CI variables. Limit it with `credentials.derive.hosts` or a token with fewer scopes on the host.
- The proxy can be used as a confused deputy: while a session runs, the agent can make authenticated calls to every rule host.
- Exfiltration through an allowed host stays possible, and a host that fronts many sites (a CDN) can carry traffic to sites behind it through domain fronting; allow such hosts deliberately.
- Response bodies are not scrubbed, so a rule host that echoes request headers into a body reflects the secret.
- The launcher CA has no name constraints; it is trusted inside the container only.
- JVM HTTP clients that cannot authenticate to the proxy (`HttpURLConnection` and `java.net.http`, which ignore the `proxyUser` and `proxyPassword` properties, and the `mvnw` jar downloader) have no network, and neither do other tools that cannot send proxy credentials (headless browsers). There is no unauthenticated proxy shim inside.
- Project-only OAuth MCP servers (defined only in the repository's `.pi/mcp.json`) get no sign-in on the host and no token inside; `pi mcp add` puts a server in the user `mcp.json`.
- The gateway hostname is visible inside: the sandbox `models.json` keeps each `baseUrl` host (minus userinfo), so an internal gateway's name shows, though never its token.
- Providers whose client derives the API host from the token content may refuse a placeholder token; the doctor's per-rule check shows a 401 or 403.
- Provider `/login` inside fails (read-only `auth.json`); log in on the host.
- Secrets in the `env` of stdio MCP servers become placeholders that nothing replaces until a `credentials.rules` entry binds them to the host the server calls.
- Plain HTTP is refused (CONNECT to port 80 has no SNI to check), and host-local model servers (`localhost`, plain `http`) are unreachable; a notice says so.
- Inside the internal network DNS resolves container names only, so tools that resolve names before using the proxy fail.
- NTLM and Kerberos parent proxies need a local relay such as `px` or `cntlm`.
- Private image registries: pulls send no registry credentials.
- Org baselines have no signature; the file is trusted as the host delivers it, and carries config only, not pi files.
- `tls.extraCa` `hostStore` reads the macOS System keychain only.
- A `command` secret source is not checked when the config loads; a broken one fails only when the proxy first needs it.

Files and git:

- `mounts.hostCaches` lets the sandbox poison host builds: it can plant or replace plugin jars, a Gradle wrapper distribution, npm tarballs, wheels, Go modules or crates in the bound caches, which host builds then run with your rights, and every repository that enables the preset shares them. Gradle's cross-process lock pings cannot cross the VM, so a parallel host build may wait on a lock the sandbox holds.
- Shared cache volumes (`mounts.sharedCaches`) are a write channel between your sandboxes, and tools without their own cache locking may corrupt them when several sandboxes write at once.
- Hooks, `commondir`, `gitdir` and a `.git` file are bound read-only directly from the host after the launcher checks them; a host-side actor that swaps a checked path between the check and the bind defeats this.
- The git common dir is mounted read-write and `.git/config` is readable inside, so a token in a remote URL is visible to the agent; keep credentials in a credential helper.
- Repository contents stay untrusted for host tools. The agent can create nested repositories, gitlinks and `objects/info/alternates`, and change any file host tools read (editor settings, `.envrc`, package scripts). After the last session the launcher reports new or changed `.git` entries and gitlinks; it cannot prevent them. Launching pi from such a nested checkout mounts the git dir its `.git` file names.
- Workspace mode protects the repositories present at launch; one the agent creates during the session is reported at the end, not protected. Without git on the host the folder's own config listing is skipped.
- In single-repository mode, when git fails to list the configuration, included config files inside the repository are not bound read-only.
- With `mounts.autoOverlays` on, the host's and the sandbox's build output diverge.
- The Colima VM sees all of the home directory; only the container's mounts limit what pi sees. VM shares added for repositories outside the home are never removed automatically.

Image:

- A pulled `image.digest` image lacks the launcher CA in its system store, so a tool that reads only the system store (a Debian JDK) does not trust the proxy's certificates for rule hosts; it also records no pi version.
- A JDK installed outside apt after the image build (toolchains, sdkman, a tarball) lacks the launcher CA; the entrypoint builds the truststore only for the `java` on `PATH` at container start.
- The base image is pinned by tag, not by digest, so a rebuild picks up whatever the tag points at.
- The missing-command hint reaches bash only, and an agent can unset it in its own shell.

Host sessions:

- The agent can read this repository's earlier host sessions, which may hold secrets a tool printed outside the sandbox; `sessions.host: false` keeps sessions in the volume.
- While the container runs, the sweep checks only the top level of the session directory, so a link the agent planted under `<session>/agents/` stays until the last session stops; host pi may follow it in that window.
- On a slug collision (pi gives `/a/b-c` and `/a/b/c` the same slug) two repositories share one session directory, and the sweep of one renames the other's sessions to `.rejected-<random>`; rename them back by hand.
- A custom host session dir (`PI_CODING_AGENT_SESSION_DIR` or `sessionDir`) is not shared, a project `sessionDir` and a `--session-dir` you pass are not considered, and host sessions started in a subdirectory of the repository are not visible inside, since pi inside always uses the repository root's slug.
- The share check proves the directory is shared and writable at container creation and on each doctor run, not later.
- Handoff documents of sandboxed sessions live in the container's `/tmp` and are gone when the session is resumed on the host; only host pi prunes old subagent runs.
