# launcher threat model

What the sandbox protects, where its trust boundaries are, and what each feature weakens. How it works is in [ARCHITECTURE.md](ARCHITECTURE.md); what the user sees is in [README.md](README.md).

## 1. Assets

- **Host credentials:** model provider keys and OAuth tokens in `~/.pi/agent/auth.json`, keys and header values in `models.json` and `mcp.json`, environment variables, keychain items, password manager entries, MCP OAuth tokens, glab tokens, registry passwords, parent proxy credentials.
- **Host files:** everything in the home directory outside the workspace root (`workspaceRoot`), `~/.pi`, the launcher's state and config (`<agent dir>/pi-sandbox/state/` and `<agent dir>/pi-sandbox/config.json`, with the CA key in `state/ca/ca-key.pem`).
- **Host pi sessions:** the transcripts in `~/.pi/agent/sessions/` (under `PI_CODING_AGENT_DIR` when set), one directory per folder; host pi reads them on `/resume`, `-c` and `--session`.
- **Host git:** the hooks and config host git runs in repositories outside the workspace root.
- **The network:** hosts the developer can reach (internal services, cloud metadata, private ranges) and the developer's identity toward them.

The agent inside the container is assumed hostile: it may run any command, write any file it can reach, and send anything to any host the proxy lets through.

## 2. Trust boundaries

- **Container:** one per launch, removed when its pi exits. It runs pi and every tool it starts. It sees the whole workspace root (read-write, every project in it and their git dirs included), the install's one agent volume at `~/.pi/agent` (read-write and mounted by every session's container of every folder, so any session can change what every other session loads: installed packages, extensions under `git/` and `npm/`, `settings.json`, the `pi-*.json` files and anything else pi reads from there; with `sessions.host` off it also holds the sessions of every other folder, which any session can read or change), its build output overlay volumes, the `mounts.volumes` volumes (read-write; each is one volume shared with every session of every folder), the `mounts.binds` sources (read-only), host pi's session directory for this folder (read-write, at its host path, while `sessions.host` is on) and the read-only render dir (`<agent dir>/pi-sandbox/state/vm/agent/`, one for the install, built from the host agent dir, the home and the config, nothing of the folder). It joins the network of its install (one launcher state dir), which every session's container of that install, its relay and its services pod share. Its only way out is the relay at `pi-sandbox-proxy:3128`, which forwards to the proxy on the host; the container holds no proxy token.
- **Proxy:** one host process per launcher state dir, shared by every launch in every folder. Holds secrets in memory only (they reach it on stdin or are fetched on the host), decides every connection, terminates TLS for credential rule hosts and injects credentials there. Trusts the launcher that started it, never the container.
- **Host pi helper:** pi's managed install in the host agent dir, or without one the pi of `npm install -g` in npm's global root, and no other pi, run on the host to print credentials (`pi auth print-api-key`, `print-bearer-token`), to sign in and refresh MCP OAuth (`pi mcp login <name>` against the host agent dir, from an empty folder so no project `.pi/mcp.json` loads), to read the provider host table, and for the commands the developer types that start no session (`pi auth …`, help and `--list-models` from an empty folder, `--export` in the cwd). It runs with the developer's rights. It is not writable by the sandbox: of the host agent dir the container sees only the two paths above (this folder's session directory read-write, the render dir read-only), never the agent dir, `pi-sandbox/`, `config.json`, `ca/ca-key.pem` or pi's install, and a folder that contains or lies inside the agent dir (or `~/.pi`) is refused. A pi in a project's `node_modules` (the launcher package's or a checkout's) is never used, and neither is a `pi` found on `PATH`, since the repository or its `PATH` could plant one. The npm global pi is taken only from what `npm root -g` reports, asked from the home folder (no project `.npmrc`) of an `npm` on `PATH`, with that `npm`'s own folder first on `PATH` so the `node` beside it runs it; the npm pi then runs as the launcher's own Node with the package's entry, never `<prefix>/bin/pi` or a `node` found on `PATH`. A pi linked into the global root from elsewhere (`npm link`) is refused: the package's real path must lie inside the global root's and the entry's inside the package's. One trust rule then covers `npm`, the package folder and the entry, each as found and as its real path: none may lie in the workspace root or in a folder launcher state records a sandbox in. A git checkout outside those does not count, since Homebrew (`/opt/homebrew`) and nvm (`~/.nvm`) install npm and its global packages inside one. The check is made at launch, when the host pi is looked up; the proxy daemon reruns the accepted command without checking again. The workspace root is read from the config; when the config does not load or sets no root, only the recorded folders count. The record of sandboxed folders covers the launch folder only, and is lost when launcher state is removed (uninstall) or a folder is renamed. The npm global prefix itself is the developer's, as `~/.pi/agent` is. The proxy daemon is restarted at the next launch with no other session of its state dir live after the host pi version or its commands change.
- **Colima VM:** runs the container engine. The VM shares exactly the workspace root (`workspaceRoot`, writable), `<agent dir>/sessions` (writable), `<state>/vm` (read-only, the render dirs only) and the folders of `mounts.binds` sources outside the root (read-only), so a container escape (root in the VM) reaches those and nothing else of the host: not the rest of the home, `~/.ssh`, the rest of the agent dir, the CA key, the proxy token or the grants. The home is never shared whole: with no `workspaceRoot` no launch starts, and a root that is the home or holds it is refused (`~` when the config loads, a path that resolves there at launch, before the VM is touched). The launcher restarts the VM to that exact list at a launch with no other launch live; a running launcher container of another agent dir counts as a live launch, since all agent dirs share the one VM. The VM is not a security boundary against the files it shares; only the container's mounts are. Since root in the VM can write anywhere inside the root, the root may not be, hold or lie inside a path whose contents the host runs or trusts: `~/.pi`, the agent dir, the state dir, the user config and its folder (taking these would hand the VM the launcher's config, keys and grants), `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.kube` (credentials), `~/.colima` (the VM's own `colima.yaml`, so its mounts), `~/.config` and `~/Library` (shell, git and gh settings, `LaunchAgents`), `~/.local/bin` (`PATH`), `/etc`, `/usr`, `/opt`, `/System`, `/Library`, `/bin` and `/sbin` (system config and programs, Homebrew); nor be or hold `/private` or `/var`, the home or `/`. The root is checked on its real path.

## 3. Baseline guarantees

- **No credential bytes inside.** No real secret is in the container's filesystem, environment or volumes. The agent can still use every credential against the hosts its rule names (section 5). In detail:
  - Rendered `auth.json`, `models.json` and `mcp.json` hold placeholders (`pi-sandbox-` plus 24 hex of a salted hash; for a JWT access token a JWT with the launcher's own header and signature that keeps the token's lasting claims, an account id for example, never its header, signature or times). So do the rendered tool files (glab `config.yml`, `.npmrc`, `pip.conf`, the Maven servers), `GITLAB_TOKEN` and what the glab credential helper prints inside.
  - The rendered files are read-only links, except `auth.json`, a 0444 copy in the agent volume (pi locks it beside its resolved path, so a link would put the lock in the read-only render dir); the gitconfig and the glab config are writable copies. All are re-created at every container start, and nothing written to a copy reaches the host.
  - The render copy of agents, prompts, skills, themes and extensions, and of the host `~/.agents/skills` (the one path outside `~/.pi/agent` the render reads; pi loads user skills from there too), skips directories named `secrets`, `.secrets`, `credentials` or `.credentials` outside `node_modules`, secret-looking files, private keys and files over 8 MiB, and names what it skipped in a notice. It follows no symlink, so a link cannot pull a file from elsewhere on the host into the render dir; skipped links are named in a notice too. Resource paths of `settings.json` reach the container only inside the repository or the copy; others are dropped, so the container learns no other host path from them.
  - A `settings.json` package URL with userinfo and a stdio MCP server's URL userinfo become clean. A stdio MCP server's env value or flag value (a `--flag=value`, or the argument after a bare flag) becomes a placeholder when its name has a secret segment (token, secret, password, passwd, pass, passphrase, authorization, jwt, dsn, cookie, apikey, privatekey, pat, credential, or `key` as the last segment) and is not qualified (max, count, file, dir, path, mode, url, timeout, type …), or when the value is `Bearer`/`Basic`/`Token`-prefixed, a JWT or a URL with userinfo; numeric, empty and boolean values are kept. A credential's `env` values in `auth.json` with a secret name or credential shape become placeholders, and any header with a credential-shaped value is a placeholder whatever its name.
  - A URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`) keeps its shape with a placeholder for the password, or for the user name when the token is the user name, bound to that host (and, for npm, its path); any other `.npmrc` or `pip.conf` value with URL userinfo and every npm and pip proxy setting stay on the host. Userinfo in a Maven mirror URL is removed, Maven profile properties are not copied, and a Maven server's `httpHeaders` values become placeholders like its password (a server with only a `privateKey` or `passphrase` stays on the host).
  - The host `settings.json` `httpProxy` is never synced. An MCP URL or a `models.json` `baseUrl` with a secret-like query parameter is dropped with a notice.
  - `env.allow` refuses every variable the launcher sets inside the container, the proxy and CA variables included, and does not forward a value with URL userinfo, a `Bearer`/`Basic`/`Token` prefix or a JWT shape; the launch names the variable.
  - `pinata doctor` sweeps the environment, `auth.json`, `mcp.json`, `mcp-auth.json` and the `settings.json` packages inside for anything else. It does not check an `env.set` variable while it holds the value in the config, and names the secret-named ones it skipped in its passing line, so a secret written into `env.set` is not caught. It reads `mcp-auth.json` and `settings.json` from the volume as regular files only, with the same 5 s host-side timeout as the write-back; one that is not a regular file or does not answer in time counts as not a JSON object.
- **Container hardening:** pi runs as the unprivileged `pi` user (uid 1000) in a container that drops every Linux capability except `CHOWN`, runs with `no-new-privileges` and is limited to `resources.pids` processes (4096 by default, at most 4194304), so a fork bomb stays inside the sandbox. `CHOWN` is left only for the launcher's own root exec that hands new volume mount points to `pi`; that exec and the pod's run `/bin/sh` and `/bin/chown -h` by absolute path, and no `mounts` target may cover them or the files they load (the reserved targets in [CONFIGURATION.md](CONFIGURATION.md#mount-targets)). pi cannot reach the capability through a setuid binary, since those gain no privileges under `no-new-privileges`. The root commands do not start clean, though: the engine merges the container's environment, every `env.set` variable and every `ENV` line of the image, into each exec, so a dynamic loader variable such as `LD_PRELOAD` pointing at a library pi wrote into a volume would run that library as root with `CHOWN`. Those execs therefore carry their own environment, which wins over the container's: a fixed `PATH` and an empty value for each loader and libc variable glibc drops for setuid programs (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT` and the rest of its list, plus `GLIBC_TUNABLES`), which also covers the two musl honours (`LD_PRELOAD`, `LD_LIBRARY_PATH`). The engine can only override a variable, not remove it, so `LD_SHOW_AUXV`, `LD_DYNAMIC_WEAK` and `LD_TRACE_LOADED_OBJECTS`, which act on presence alone, still reach the root commands when set; none of them loads code (at worst the exec prints its auxiliary vector to output the launcher discards, or `chown` does nothing and the hand-over fails or leaves the volumes unwritable). `env.set` itself is not restricted, since tools may need `LD_LIBRARY_PATH`. The services pod keeps `CHOWN` for the same reason (section 4, Services). The relay container keeps no capability at all, runs with `no-new-privileges` and at most 1024 processes. The root filesystem is read-only. Tools that need raw sockets (`ping`) do not work inside.
- **Egress allowlist:** a host leaves only when it is in `egress.allow` (empty by default) or is `pi.dev`, a credential rule host, a derived host or a grant, on its port; `egress.deny` always wins: an entry `d` blocks `d` and every name under it, and `*.d` every name under `d`.
- **SNI check:** a tunnel whose ClientHello names another host than the CONNECT target is refused.
- **Private-range deny:** IP literals, localhost, link-local, private and reserved ranges, the metadata address, the NAT64, 6to4 and IPv4-translated (SIIT) IPv6 ranges, site-local IPv6 and names that resolve only to such addresses are refused, except the names in `egress.privateHosts`. The check runs before the tunnel opens and again at dial time, so a rebinding answer is refused too.
- **Workspace guard:** a folder that is or contains the home directory, `~/.pi`, the agent dir (`PI_CODING_AGENT_DIR` when set), the launcher folder `<agent dir>/pi-sandbox/`, the state dir or the user config, `~/.config` (it holds files the host runs or trusts, such as shell, git and gh settings), or an image dir (`/bin`, `/sbin`, `/lib`, `/opt`, `/usr/bin`, `/usr/sbin`, `/usr/lib`, `/usr/local`), or that lies inside `~/.pi`, the agent dir, the state or config dir, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys` or `/dev`, is refused. The launch folder (the nearest repository root above the cwd, else the cwd) and the workspace root are both checked before any VM work. `/` refuses because it contains the home.
- **Host session directory:** the one read-write path of the agent dir in the container (the render dir under `<agent dir>/pi-sandbox/state/vm/` is read-only). The launcher recomputes the path from the agent dir and the folder's real path with pi's slug formula, and mounts it only when it is exactly one level under `<agent dir>/sessions`, its name matches `--…--` without a `/`, it is a real directory (not a symlink), its real path is that slug under the real path of `<agent dir>/sessions`, and that real path neither is nor contains `~/.pi` or the agent dir, nor overlaps any other agent dir entry. The launcher creates the directories 0700 before the check, so the engine never creates a root-owned one.
- **Configuration from the host only:** the sandbox reads one config file, `<agent dir>/pi-sandbox/config.json`, never a file in the folder. That file is owned by the user who runs the launcher; there is no administrator layer, so nothing stops that user from widening egress, adding credentials or turning a protection off. A team that shares one file shares a starting point, not an enforced limit. `pinata init` is a host-side writer of the same file and changes only the project folders, the VM size and `writeBack.enabled`.
- **Git dirs inside the root:** the launcher finds the nearest `.git` itself (`lstat`, no link followed) and reads the git dir and common dir from the files (a `gitdir:` file, a worktree's `commondir`), without running git on the project. A launch whose git dir or common dir lies outside the workspace root is refused before any VM work (`git: the git dir <dir> of <repo> is outside the workspace root (workspaceRoot: <root>)`), since the sandbox mounts only the root and git would not work there. Nothing more is checked: the layout is not confirmed with git, and a link or rewritten pointer is not refused.
- **The sandbox can write every project under the root:** the container binds the workspace root read-write at its own path, and no narrower bind (read-only hooks or otherwise) is placed inside it. The agent can write every file of every project under the root: `.git/hooks`, `.git/config` (`core.hooksPath`, `core.fsmonitor`, aliases, includes), sibling projects' `node_modules` and package scripts, and the sources of pi extensions and packages that pi on the Mac loads from there. Host git and host tools run what it wrote there with the developer's rights. This is accepted because the root holds only the user's projects, which the user already trusts the agent with; git changes are not recorded or reported, and nothing is checked after the session. Keep anything the agent must not change outside the root.
- **One internal network per install:** every session's agent container of one install (one launcher state dir), its relay and its services pod join one internal network, `pi-sandbox-network-<install id>`, the install id being a short hash of the state dir. Each install on the VM has its own network (the engine picks its subnet), relay, proxy, token, pod and services. The launcher lists, changes and removes only engine objects that carry its own install label, so one install cannot list, alter or remove another install's relay, network, pod, services or volumes. The one exception is the daily collection of older builds' objects: it removes stopped containers, unused volumes and free networks named `pi-sandbox-*` that carry the `pi-sandbox.managed=true` label and no install label at all, never one labelled by any install, never one without the managed label and never a shared volume (`pi-sandbox-shared-*`). It does not separate the sessions of one install: a container can reach every listening port of another session's agent container and every port of the pod (section 5, Sessions share one network). What it keeps out is everything outside it. The relay only forwards to the proxy port and serves only clients whose address is inside its install network's subnet. Any other connection is closed before the relay opens an upstream one, so a container on the VM's default bridge, such as a fetching image build, or a process in the VM's own network namespace cannot use the relay to borrow the proxy token; on the real engine a default-bridge client and a host-network client that connect to the relay's bridge address get no bytes, and the relay opens no connection to the proxy for them. Since every session and the pod are inside the subnet, this check does nothing between sessions; it only keeps the rest of the VM out. The network is created internal, without IPv6 (`EnableIPv6: false`) and with an isolated IPv4 gateway (`com.docker.network.bridge.gateway_mode_ipv4=isolated`, Docker Engine 28 or later, checked before the create), so the network has no gateway and the VM itself has no address on it. The relay opens only port 3128. A joining container has only the on-link route and no default route: the VM's `docker0`, the lima host and public addresses answer `ENETUNREACH`, so a container cannot reach the VM's own services, its SSH port included. The engine's embedded DNS resolves the relay (as `pi-sandbox-proxy` and as `pi-sandbox-relay-<install id>`), the pod (as `pi-sandbox-services`) and the containers on the network, and no outside name (`EAI_AGAIN`); a tool must leave resolution to the proxy (CONNECT by name). A network of that name that is not labelled by the launcher fails the launch with a message naming it. One that carries the launcher's managed label is used as it is, since only this launcher creates a network of the install's name.
- **MCP OAuth tokens** stay in host pi's `mcp-auth.json`, which the launcher only reads; the proxy injects the access token for a placeholder `Authorization`, and pi inside never holds a token, a refresh token or a client secret (the sandbox `mcp.json` has no `oauth` block).
- **One proxy and one token:** one proxy process serves every session of the launcher's state dir, in every folder, with one set of rules, env secrets, parent-proxy credentials and one token. Nothing in the proxy tells one session from another: the egress rules are the same for all (the latest launch writes them, with a notice when other sessions run), the grants are shared, and the access and denial log is shared (section 5, Sessions share one proxy). The token (`<state>/proxy/token`, mode 600) is a proxy credential, not a provider secret, and never enters an agent container: only the relay holds it, in its own environment, and sends `PI-SANDBOX <token>` as the first line of every connection it opens to the proxy. The relay's environment shows in an engine inspect of the relay container, which needs the engine socket in the VM; no launcher container has it. The proxy reads that line on the raw socket before any HTTP (at most 128 bytes within 5 s, compared in constant time) and closes the connection without a reply when it is wrong or late; the launcher's own requests (doctor, health) send the same line. So whoever reaches the relay on the install's network, which is every session's agent container, the pod and its services, can use the proxy without knowing the token. The token protects the proxy's host listener (`127.0.0.1`, reached from the VM through lima's port forwarding) from every other process in the VM and on the host. The relay's upstream connection crosses the VM's default bridge unencrypted, so a process in the VM that can capture packets there could read the token and the CONNECT requests. The agent containers, the relay, the pod and the services have no such capability. An image build that reaches the network (the base build, and a layer with `image.packages`, `image.npmGlobal` or `image.dockerfile`) runs on that bridge with the engine's default capabilities, `NET_RAW` among them, so a build step could sniff the bridge or ARP-spoof the relay's upstream while sessions run (section 5, Image). On the real engine, from a pod joiner, `/healthz` and `/denials` answer 200, a CONNECT to a host that is not allowed gets 403 with the JSON reason and a plain-HTTP proxied request gets 403 with rule `plain-http`; from the host, a connection with no preamble or a wrong one is closed with no bytes. The proxy never answers `407`. The token is deleted by the ground teardown (a sweep, `pinata stop` or the uninstall) when no session of the state dir is live and the ground lock is free, so a later launch gets a new one. A `Proxy-Authorization` header a client still sends is ignored and never forwarded. Grants are read live from `grants.json`.
- **Service confinement:** each configured service runs in its own container with no capabilities, `no-new-privileges`, a read-only root, an init, a numeric non-root user (uid 0 and gid 0 are refused), at most 4096 processes, writable only `/tmp`, its `tmpfs` paths and its own volumes, and its own `env` only: no workspace, home, render folder, credential, placeholder or forwarded variable reaches it. Its image is whatever the config author names (pulled by the engine, not built by the launcher), and the sandbox trusts it no more than the agent. It runs in the pod's network namespace on the install's network, so it reaches the relay at `pi-sandbox-proxy:3128` like any agent container, whatever its `env` says; that is its only route out, under the same egress policy as the agent. It gets no CPU or open-file limit, and a memory limit only with `memoryGiB`. The pod that holds the services' network namespace runs `sleep` as 65534 with a read-only root, an init and at most 64 processes; its one root exec hands the service volume roots to their users. The services are one set per install, not per session or per folder.
- **Sandbox status file:** The status file tells the agent the proxy URL and its `/healthz` and `/denials` addresses, the resource limits, the guest volume targets, the bind targets, the setup commands and each service's name, command, ready check and ports. All of it is configuration the agent already sees or could probe from inside, and it holds no token, no host path and nothing per launch, so it is shared safely by every session. A service's `command` appears as written, so a secret placed in it (rather than in the service's `env`) shows to the agent.
- **Launch accounting:** a launch is registered before the VM stage, so a share restart or `pinata stop` cannot pull the VM from under one that is still preparing.
- **File-cache watcher:** it runs fixed commands only: `lsof` and `sysctl` on the host and `sudo sysctl -q -w vm.drop_caches=2` in the VM. Nothing from the config, a repository or the sandbox reaches their arguments. The `file cache` check of `pinata doctor` runs the same `lsof` and `sysctl` reads and nothing else: it never runs the release.

## 4. What each feature weakens, and the mitigation

| feature | what it weakens | mitigation |
| --- | --- | --- |
| TLS termination of rule hosts | The launcher CA is trusted inside the container and has no name constraints, so it could sign any name there. | The CA key never leaves the host state dir; only rule hosts are terminated, every other tunnel stays end to end. |
| Placeholder substitution | A rule host that echoes request headers or bodies reflects the real secret back into the container. | Substitution happens only in the rule's own header, or, for a rule without one, in auth-like request headers (`authorization` and secret-like names, never `proxy-authorization` or `sec-*`); the placeholder is stripped from every other header, placeholders of the host's other rules (another port or path prefix) are dropped before any rule applies, and nothing is substituted in query parameters or bodies. A `Basic <base64>` value is decoded for the check, the stripping and the substitution, and re-encoded, so the decoded secret goes only to the rule host; the exact base64 sent is scrubbed from response headers like the secret. On terminated hosts, an absolute-form target for another origin and a path with dot segments (raw, `%2e`, an encoded slash or a backslash) get `400`, and `pathPrefix` is matched on the decoded path. Every response header value is scrubbed by substring (`Location`, `Set-Cookie`, `WWW-Authenticate` included). Response bodies are not scrubbed: allow rule hosts that do not echo. |
| Derived hosts | Host config files widen egress: every provider and MCP host in `auth.json`, `models.json` and `mcp.json` becomes reachable. | `credentials.derive.enabled: false` or `credentials.derive.hosts`, and `egress.deny`. |
| `egress.privateHosts` | Names in `privateHosts` (a private gateway host, for example) skip the private-address filter, so a rebinding DNS answer for them reaches an internal address. | Only names, no IP literals or localhost; set in the config file. |
| Grants | The developer can widen egress at run time, for every session in every folder at once, running ones included, until the grant is revoked. | Grants cannot be turned off. `egress.deny` and the private-range check still apply to a granted host, and `egress allow` refuses a host `egress.deny` names. The container cannot create grants: the CLI runs on the host only and the proxy has no grant endpoint. |
| Parent proxy | DNS is delegated: with a parent proxy set, an NXDOMAIN locally is passed to the parent, which resolves it. | The private-range check still runs on every local resolution; `noProxy` names are dialled directly. The parent's credentials are resolved on the host and kept in the proxy's memory; they reach it on stdin and are kept out of the environment the proxy starts with; the host helpers the proxy runs (`pi auth`, `pi mcp login`, command secrets) get `HTTPS_PROXY` with them. The proxy process starts with a minimal environment (path, home, temp, user and login name, locale, `NODE_OPTIONS`, CA files, the glab and XDG config dirs, `HTTPS_PROXY` without userinfo), so no other secret variable of the launcher reaches it except through its stdin input; an env secret with a CR or LF is refused at launch, so it cannot split a header. An `HTTPS_PROXY` that is not an `http://` URL gives neither a parent route nor credentials to the proxy; the launch warns and the proxy connects directly. |
| Extra CAs | Trust widens to the corporate CA, inside the container, in the proxy's upstream trust and during image builds. The holder of its key can read the sandbox's TLS traffic, including the real tokens the proxy injects on credential-rule hosts, as it already reads them when pi runs on the host. | `tls.extraCa` is set only in the launcher's config file, never by a project file. Each entry names one certificate, by SHA-256 fingerprint in the macOS System or login keychain or by PEM file; every certificate must be a CA and within its validity dates, or the launch stops. A CA certificate is public, so trusting it leaks nothing. The base image build trusts the CAs only during its steps and removes them from the trust store and the final filesystem again; the local layer, which is always built, also over a pinned image, bakes the launcher CA and the `tls.extraCa` certificates into the system store and every JDK's `cacerts`, so a changed CA rebuilds the layer. |
| Image layers | `image.dockerfile` runs as root at build time on the engine's default network. | Set in the config file only, an absolute path, used verbatim; the layer runs on top of the sandbox image and ends with a fixed tail (`USER pi`, the workdir, the launcher's entrypoint and an empty `CMD`). The environment and the proxy variables are set by the container spec at run time. The CAs and the JDK proxy settings are baked into the local layer: its system store trusts the CAs before these lines, and after them, before the fixed tail, it runs the JDK trust script as root, which adds the CAs to every JDK's `cacerts` and writes its `net.properties` (Java pointed at `pi-sandbox-proxy:3128`, no credentials), so a JDK the file installs is covered too. Treat the file as code the developer runs. |
| Host pi helper | `!command` values in host `models.json` and `mcp.json` run on the host, as they would with local pi. | Only values from the developer's own host files; a value in a file the container can write (the repository's `.pi/`) is never run on the host. glab and git found inside the workspace root are never run. |

## 5. Known gaps

This is the one list of what the launcher does not cover; the other docs link here.

Lifecycle:

- A launcher killed with `kill -9` leaves its container and created folders in place, and with no other session running also the services and their pod, relay, network, proxy and token, until the next launch of any repository, `pinata stop` or the uninstall. Its launch entry stops counting as soon as its pid is gone and its proxy exits about a minute later. A VM restart removes the containers and relay.
- A change to the credential rules, an env secret, the parent proxy or the extra CAs does not reach the running proxy while another session of the state dir runs: the new launch keeps the old proxy with a notice, so a removed credential stays usable until the last of those sessions ends. Egress settings (`egress.allow`, `egress.deny`, `egress.privateHosts`, derived hosts) reach the running proxy only when a new pi starts in any folder and rewrites `egress.json` (editing the config alone changes nothing for running sessions); from then on every new CONNECT of every session uses them, with a notice to the new launch, and connections already open stay until they close. Other config changes apply at the next launch, since every launch gets its own container.
- If the proxy dies while sessions run, the relay forwards to the old port until the next launch starts a new proxy and recreates the relay; a local process that took that port in between receives the relay's preamble, and with it the proxy token, and the tunnels of every session. A proxy whose process lives but does not answer is replaced only by a launch with no other session of the state dir live; while others run, the launch fails and the proxy is kept.
- Locks, launch entries and proxy records follow the holder's pid, boot time and process start time, never a timer, except `vm.lock`, judged by its age. A running pid counts as live when the start-time tool itself failed, and as dead when no start time is obtainable for that pid. macOS reports the start time to the second, so a pid reused within the same second as the recorded process would still count as live; the effect is a sandbox kept, never one removed. A hung launcher keeps its locks. The launch registry lock is waited for up to 120 s, then the waiter fails without removing anything. A folder's prepare lock and the ground lock, which guards the network, relay, proxy and services, have no timeout: while a hung launcher holds one, the other launches of that folder, or every other launch of the state dir, wait until Ctrl-C.
- A repository on an unmounted disk or share keeps its state and volumes; only a folder whose parent exists and whose mount point is mounted counts as deleted.

Services:

- A service's own process can do anything its image allows inside its confinement, including using the proxy whatever its `env` says, and every agent can talk to every service; a vulnerable or hostile service image is as trusted as the config that names it.
- Service data is shared by every session of the install in every folder and survives across sessions until `pinata restart` (or the uninstall): what one session's agent writes into a database, another folder's session reads.
- A service without `memoryGiB` is not counted against the VM's memory and can take it from the agent. No service gets a CPU or open-file limit, so a busy service can slow every session.
- `pinata stop` first sweeps, which stops the services, relay, network and proxy when no session of the state dir is registered (it waits for the ground lock while that holds, and says so); then it stops the VM, which checks again for sessions of every state dir. A launch that registers while the teardown runs can lose its services, relay or proxy; the next launch starts them again.
- A volume the agent shares with a service (a `mounts.volumes` entry with the service volume's `name`) is writable by every agent. A service that loads code or configuration from it runs what the agent wrote, as the service's user (`1000:1000`, which a shared volume requires) and with the service's `env`. The service's confinement limits the damage: no capabilities, `no-new-privileges`, a read-only root, no workspace, home, render folder or credentials of the agent, and only the install's network, whose one way out is the proxy under the same egress rules as the agent. Secrets in such a service's `env` are therefore reachable by the agent; keep a service whose `env` holds a secret off volumes the agent shares.

Sessions share one network:

- Every session's agent container of one install and its services pod are on one internal network. A session can reach every listening port of another session's agent container, in any folder, and every port of every service. A dev server, a debugger port or a language server one agent opens is open to every other agent.
- The relay's subnet check admits every container on that network, so it keeps out only the rest of the VM, not other sessions.
- What still separates sessions: each container mounts its own agent home volume and its own overlays. Every container mounts the whole workspace root, so a session can read and write the files of every other project in it, another session's working tree included; only projects outside the root are out of its reach. It can also talk to whatever the other session's processes serve on the network.
- Two installs (two launcher state dirs, such as two `PI_CODING_AGENT_DIR` values) share the VM, its engine and its default bridge, but not a network, relay, proxy, token, pod or service: each has its own, named and labelled with its install id. A container of one install cannot reach the other install's network. Both run in one VM, so a container escape in either reaches both; the VM is not a boundary between installs. The managed images are not install-scoped, since a pulled image cannot carry an install label and per-install layer tags would collide: one install's image cleanup or uninstall can remove an image another install uses. That install rebuilds or pulls it at its next launch, and a launch of it that is between image preparation and the container create at that moment fails once. Stop, a VM resize or restart and the uninstall see another install only through its running agent containers, which they count and name; a launch of another install that is still preparing has none yet, is not counted, and fails if the VM stops under it.

Sessions share one proxy:

- One proxy and one token serve every session of the state dir. The egress rules are the same for all: the latest launch in any folder sets them, with a notice when other sessions run, so one folder's `egress.allow` reaches every running session.
- Grants are shared: a grant made for one folder lets every session reach that host.
- The access and denial log is shared. The denial lines printed at a session's end and the output of `pinata egress list --denied` can name hosts another session tried.
- What still holds: the token is never in an agent-controlled container; the network is internal, with no gateway; the agent containers keep their hardening (section 3); the service containers and the pod keep theirs.

Network and credentials:

- The agent can use every credential it cannot read: while a session runs it can make authenticated calls to every rule host (the proxy is a confused deputy).
- Reach of the derived glab tokens, on by default: through the token's hosts the sandbox can push to every repository the token can write, add deploy keys and deploy tokens, push pipelines that run with the project's CI variables and change those variables. Limit it with `credentials.derive.hosts` or a token with fewer scopes on the host. A GitHub token the user gives with `credentials.rules` has the same kind of reach on the hosts its rules name.
- A sandbox request can open a sign-in tab in the host browser: a request to a host-configured OAuth MCP server whose injected token has expired or was rejected starts `pi mcp login` on the host, from the proxy at most once per server per 60 s host-wide, none for 10 minutes after a failure, and at most one per 10 minutes per server for a rejected token that has not expired; the launch-start sign-in runs once per launch whose input and output are a terminal and is skipped for 24 hours after a failure.
- Exfiltration through an allowed host stays possible, and a host that fronts many sites (a CDN) can carry traffic to sites behind it through domain fronting; allow such hosts deliberately.
- The proxy's preamble gate caps neither the number nor the rate of connections, so a sandbox can slow the one proxy, and with it every other session; it is left uncapped so parallel builds are not throttled.
- Response bodies are not scrubbed, so a rule host that echoes request headers into a body reflects the secret.
- The launcher CA has no name constraints; it is trusted inside the container only.
- URL credentials in `.npmrc` and `pip.conf` are read back by key or index position, not checked against the rule host; editing those files on the host during a session can send one registry's password to another rule host after a `401`.
- Project-only OAuth MCP servers (defined only in the repository's `.pi/mcp.json`) get no sign-in on the host and no token inside; `pi mcp add` puts a server in the user `mcp.json`.
- The gateway hostname is visible inside: the sandbox `models.json` keeps each `baseUrl` host (minus userinfo), so an internal gateway's name shows, though never its token. A JWT placeholder keeps the token's lasting claims, such as an account id or email.
- Providers whose client derives the API host from the token content may refuse a placeholder token; the doctor's per-rule check shows a 401 or 403.
- Provider `/login` inside fails (`auth.json` is a 0444 copy of the placeholder file, re-created at every start); log in on the host.
- Secrets in the `env` of stdio MCP servers become placeholders that nothing replaces until a `credentials.rules` entry binds them to the host the server calls.
- A secret written as a purely numeric or boolean value in a stdio MCP server's env or flags is copied, and one under a name without a secret segment is copied unless its value has a credential shape; give it a clearer name or a `credentials.rules` entry.
- When the glab token probe (`glab config get token`) does not answer in time, a Keychain prompt for example, glab has no credentials in the sandbox for that launch.
- Plain HTTP is refused (CONNECT to port 80 has no SNI to check), and host-local model servers (`localhost`, plain `http`) are unreachable.
- Inside the internal network the engine's DNS answers only the relay, the pod and the containers on the install's network, and every outside name fails (`EAI_AGAIN`), so a tool that resolves a name before using the proxy fails; it must send a CONNECT by name.
- NTLM and Kerberos parent proxies need a local relay such as `px` or `cntlm`.
- Image pulls send no registry credentials, so a prebuilt image must be pullable anonymously from the VM.
- A `tls.extraCa` `sha256` entry is looked up in the macOS keychains only; elsewhere it stops the launch and a `file` entry is needed. A self-signed certificate without the CA flag (an old v1 root) is accepted as a CA.
- A `command` secret source is not checked when the config loads; a broken one fails only when the proxy first needs it. It gets 30 s, a failed one is retried at most every 5 s, and it runs with the proxy's minimal environment, so a password manager CLI that needs a session variable fails.
- Registry tokens a tool reads from an environment variable inside get no placeholder: a project `.npmrc` with `_authToken=${NPM_TOKEN}`, uv's `UV_INDEX_<NAME>_PASSWORD` or a `GITHUB_TOKEN` for GitHub Packages. `env.allow` refuses secret-looking names and no rule sets a variable inside, so the tool fails to authenticate. Only `~/.npmrc` is derived (its `${VAR}` tokens included); `PIP_INDEX_URL` and `PIP_CONFIG_FILE` on the host are not derived.
- uv config is not derived: uv ignores `pip.conf`, so `uv sync` resolves against public PyPI (when `pypi.org` is allowed) instead of an internal index, which also opens a dependency-confusion path. Point uv at the index by hand and add a `credentials.rules` entry for it.
- No setting can be enforced on the user who runs the launcher: the config file is theirs to edit, and grants cannot be turned off.

Files and git:

- A bind source (`mounts.binds`) is checked on the host and again by `confirmBinds` right before the container is prepared and created, but the engine resolves the source only at the create. The window between the check and the create (the volume and mount point preparation in between) remains, and so does a bind source in a folder another session of the state dir mounts writable under an earlier workspace root, which the check does not know as a writable mount. A running session that can write there could swap the path for a symbolic link in that window. Binds are read-only and the swap can only expose a host folder the VM already shares.
- The agent can change anything git or a host tool runs in any project under the root: hooks, `.git/config`, worktree pointers, nested repositories, gitlinks, `objects/info/alternates`, editor settings, `.envrc`, package scripts and sibling `node_modules`. Nothing is read-only, recorded or reported; host git run there afterwards runs what the agent planted (section 3).
- The git config of every repository under the root is readable inside, so a token in a remote URL is visible to the agent; keep credentials in a credential helper.
- Local pi packages and extensions inside the root are rewritable by the sandbox, and pi on the host runs them as they are; `pi install` of such a source only prints a notice.
- The git layout is read from the files, not confirmed by git; a `.git` file or `commondir` the agent rewrote points the next launch at another git dir inside the root, which is mounted anyway.
- The launcher resolves `glab` and `git` outside the workspace root, but runs `colima`, `openssl`, `security` and `tar` by name from `PATH`; a relative or in-folder `PATH` entry could make it run a file the agent wrote.
- With `mounts.autoOverlays` on, the host's and the sandbox's build output diverge.
- The settings write-back lets a hostile agent change the allowlisted host preferences (by default the default model, provider, thinking level, enabled models, theme, the extensions' limits and subagent overrides, and whatever `writeBack.add` lists), never code or credentials the ceiling keeps out; each change is printed at the session's end or the next launch. The ceiling is a deny list of what the launcher knows host pi runs or trusts today: a key that a later pi or an extension starts treating as a command, path, URL or trust decision is not on it, and a user who adds such a key with a loose check (`json` in a `pi-*.json`, a long `string`) hands the agent that lever. An added `pi-*.json` file is also copied whole from the host into the sandbox, so its other keys become readable inside; the sync records which files it copied and, at the next sync whose table no longer names one (it left `writeBack.add`, or `writeBack.enabled` is false), removes its copy from the volume, while a `pi-*.json` the launcher never copied stays. A session still running under the old table copies it in again at its end, until the next sync under the new table (another session's end or the next launch) removes it. Its write can race host pi writing the same file at the same moment: the host file is re-read right before the atomic rename, but a host pi write in between can be lost, or overwrite the launcher's. `pinata doctor` writes back before it syncs, as a launch does. When refreshing the volume fails the baseline keeps only the list of copied files, so nothing is written back next time, and a warning says that later changes will not be written back.
- One pi folder (the agent volume) serves every session of every folder of the install, so a hostile agent in one project can plant an extension, a package checkout or a setting that every later session, in any folder, loads, and with `sessions.host` off can read and change other folders' sessions. The render links and the `auth.json` copy are re-created at each container start, but nothing else in the volume is reset; `pinata restart` removes it whole once no session runs.
- The launcher loads the configured extensions once in the launch's container before the user's pi starts (a `pi --help` run that installs what is missing), with the same trust as pi's own start: same container, network and egress rules, and the same code pi would load a moment later.
- A container escape reaches all of the workspace root, the session files of every folder and the rendered agent files of every folder; only the container's mounts limit what pi sees. While other launches run, a VM that still shares an older set (the home, from a launcher before `workspaceRoot`) keeps it until a launch with none running restarts it.

Image:

- Image builds (the base image and the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer) run on the VM's default bridge and reach the network directly from the VM, not through the proxy, outside the egress allowlist and the private-range deny; a layer with none of those three builds with network mode `none`. The launcher starts them, not the agent, so this is a supply-chain exposure rather than an agent channel.
- A networked build runs on the default bridge with the engine's default capabilities, `NET_RAW` among them, while other sessions may run. A hostile package or Dockerfile step could capture the relay's clear-text upstream there, and with it the proxy token and the CONNECT requests, or ARP-spoof that path. Accepted: build inputs are trusted as far as the config author is.
- The launcher modifies the VM's system trust store: it installs the `tls.extraCa` certificates from the user's config under `/usr/local/share/ca-certificates/pi-sandbox/` (removed again when the list empties), so the VM's engine and every process in the VM trust them, and restarts `containerd` and `docker` to pick them up, only when no other launch is live; until then a change waits, and the engine keeps the previous roots. A launch's own containers do not inherit the VM's store. The certificates come only from the launcher's config file, as for the container.
- The launcher CA and the `tls.extraCa` CAs sit in the image layer's system store and in every JDK's `cacerts`, so any process in the container trusts the proxy's leaves; the CA key stays on the host. The trust script runs as root during the layer build only. A CA removed from `tls.extraCa` stays trusted in every container created from the old layer; the next launch rebuilds the layer without it.
- A JDK installed after the layer build (toolchains, sdkman, a tarball in the home) lacks the sandbox CAs and the proxy in `net.properties` until its owner runs `/usr/local/lib/pi-sandbox/trust-jdk.sh <its folder>`.
- The base image is pinned by tag, not by digest, so a rebuild picks up whatever the tag points at.
- Mount targets are checked as text, after normalisation, not resolved inside the image. A symbolic link in the image at or above a target leads the mount to where the link points, a reserved tree included; Debian's own `/etc/localtime` and `/etc/alternatives` entries point into `/usr`. Only the user's config names targets, never the repository or the agent, and only the image holds such links, which the user's `image.dockerfile` lines or pinned image can add, so this stays inside what the user already controls.
- The missing-command hint reaches bash only, and an agent can unset it in its own shell.

Host sessions:

- The agent can read this folder's earlier host sessions, which may hold secrets a tool printed outside the sandbox; `sessions.host: false` keeps sessions in the volume.
- While a container of the folder runs, the sweep checks only the top level of the session directory, so a link the agent planted under `<session>/agents/` stays until the last session stops; host pi may follow it in that window.
- On a slug collision (pi gives `/a/b-c` and `/a/b/c` the same slug) two folders share one session directory, and the sweep of one renames the other's sessions to `.rejected-<random>`; rename them back by hand.
- A custom host session dir (`PI_CODING_AGENT_SESSION_DIR` or `sessionDir`) is not shared, a project `sessionDir` and a `--session-dir` you pass are not considered, and host sessions started in a subdirectory of the folder are not visible inside, since pi inside always uses the folder root's slug.
- The share check proves the directory is shared and writable at container creation and on each doctor run, not later.
- Handoff documents of sandboxed sessions live in the container's `/tmp` and are gone when the session is resumed on the host; only host pi prunes old subagent runs.
