# launcher threat model

What the sandbox protects, where its trust boundaries are, and what each feature weakens. How it works is in [ARCHITECTURE.md](ARCHITECTURE.md); what the user sees is in [README.md](README.md).

## 1. Assets

- **Host credentials:** model provider keys and OAuth tokens in `~/.pi/agent/auth.json`, keys and header values in `models.json` and `mcp.json`, environment variables, keychain items, password manager entries, MCP OAuth tokens, parent proxy credentials.
- **Host files:** everything in the home directory outside the repository, other repositories, `~/.pi`, the launcher's state and config.
- **Host pi sessions:** the transcripts in `~/.pi/agent/sessions/` (under `PI_CODING_AGENT_DIR` when set), one directory per repository; host pi reads them on `/resume`, `-c` and `--session`.
- **The network:** hosts the developer can reach (internal services, cloud metadata, private ranges) and the developer's identity toward them.

The agent inside the container is assumed hostile: it may run any command, write any file it can reach, and send anything to any host the proxy lets through.

## 2. Trust boundaries

- **Container:** runs pi and every tool it starts. Sees the repository and its git dir (read-write, hooks and git config read-only except on backends without single-file mounts), its own agent volume, host pi's session directory for this repository (read-write, at its host path, while `sessions.host` is on), the read-only render dir and the trust bundle. Its only network path is the proxy URL, authenticated with a per-repository token.
- **Proxy:** a host process per policy hash. Holds secrets in memory only, decides every connection, terminates TLS for credential rule hosts and the MCP authorization hosts found by host-side discovery and injects credentials there. Trusts the launcher (control token), never the container; the authorization endpoints it trusts come from host-side discovery, never from container traffic.
- **Host pi helper:** the bundled pi next to the launcher, run on the host to print credentials (`pi auth print-api-key`, `print-bearer-token`), to sign in and refresh MCP OAuth (`pi mcp login`, `pi mcp list` in `<state>/mcp-auth/`), and to read the provider host table. It runs with the developer's rights.
- **Colima VM:** runs the container engine and mounts `$HOME` writable so repositories under it can be mounted. The VM is not a security boundary against the developer's own files; only the container's mounts are.

## 3. Baseline guarantees

- No real secret in the container's filesystem, environment or volumes. Rendered `auth.json`, `models.json` and `mcp.json` hold placeholders (`pi-sandbox-` plus 24 hex of a salted hash; JWT-shaped for JWT access tokens), the rendered files are read-only links (re-created at every container start, so a file the agent put in their place is replaced), the render copy of agents, prompts, skills, themes and extensions skips `.git`, `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `id_*`, key and certificate stores and secret-named files (source and markdown files excepted), a `settings.json` package URL with userinfo and a stdio MCP server's URL userinfo or secret-named `--name=value` argument become clean or placeholders, an MCP URL with a secret-like query parameter is dropped with a notice, and `pi sandbox doctor` sweeps the environment, `auth.json`, `mcp.json`, `mcp-auth.json` and the `settings.json` packages for anything else.
- Egress allowlist: a host leaves only when it is in `egress.allow` or `egress.mcpHosts`, a credential rule host, a derived host or an active grant; `egress.deny` always wins.
- SNI check: a tunnel whose ClientHello names another host than the CONNECT target is refused.
- Private-range deny: IP literals, localhost, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except the names in `egress.privateHosts` and the legacy gateway host.
- Workspace guard: a repository at or above the home directory, `~/.pi`, the state or config dir, or `/` is refused before anything is mounted.
- Host session directory: the one exception to "nothing of `~/.pi` is mounted". The launcher recomputes the path from the agent dir and the repository's real path with pi's slug formula, and mounts it only when it is exactly one level under `<agent dir>/sessions`, its name matches `--…--` without a `/`, it is a real directory (not a symlink), its real path is that slug under the real path of `<agent dir>/sessions`, and that real path neither is nor contains `~/.pi` or the agent dir, nor overlaps any other agent dir entry. `mounts.extraReadOnly` still refuses everything under `~/.pi` and the agent dir, so the exception cannot be widened by config. The launcher creates the directories 0700 before the check, so the engine never creates a root-owned one.
- Extra mounts: each `mounts.extraReadOnly` entry must exist as a file or directory and is bound at its real path; it is refused when it is or contains the home, or is, contains or lies under `~/.pi`, the agent dir, the state dir, the user config, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys`, `/dev`, a `.git` dir or the engine socket (`pi-sandbox: mounts.extraReadOnly: <path> is not allowed (<reason>)`). Nested `.git` dirs deep inside an allowed directory are not scanned.
- Read-only git overlay: hooks, git config, `core.hooksPath` and submodule and worktree config are read-only inside, so the agent cannot plant code the host's git will run (hooks dirs everywhere; the single files only where the backend has single-file mounts, see the known gaps).
- Per-repository networks: each repository's containers join their own internal network `pi-sandbox-<first 12 of the repo hash>`, so containers of different repositories share no network; the relay, which only forwards to the proxy port, is the one container on more than one of them.
- MCP token vault: real MCP access tokens, refresh tokens, authorization codes and dynamically registered client secrets stay on the host: the proxy terminates TLS to the authorization hosts found by host-side discovery, answers placeholder refreshes itself, swaps a single-use code placeholder in only at the sign-in's token endpoint and redirect URI, and refuses any token response outside a sandbox sign-in. Every launch, and every intercepted `pi mcp login|logout` while the container runs, sweeps the volume's `mcp-auth.json` of any token that is not a placeholder.
- Per-repository proxy tokens: one repository's container cannot use another repository's grants, rules, vault servers, env secrets or parent-proxy credentials (the proxy keeps `dynamic.json` rules and vault servers per repository token hash, and the env secrets of each launch under its `repoTokenHash`), and the container never holds the instance (control) token.

## 4. What each feature weakens, and the mitigation

| feature | what it weakens | mitigation |
| --- | --- | --- |
| TLS termination of rule hosts | The launcher CA is trusted inside the container and has no name constraints, so it could sign any name there. | The CA key never leaves the host state dir; only rule hosts are terminated, every other tunnel stays end to end. |
| Placeholder substitution (D4) | A rule host that echoes request headers or bodies reflects the real secret back into the container. | Substitution happens only in the rule's own header, or, for a rule without one, in auth-like request headers (`authorization` and secret-like names, never `proxy-authorization` or `sec-*`); the placeholder is stripped from every other header and never substituted in query parameters or bodies. On terminated hosts, an absolute-form target for another origin and a path with dot segments (raw, `%2e`, an encoded slash or a backslash) get `400`, and `pathPrefix` is matched on the decoded path. Every response header value is scrubbed by substring (`Location`, `Set-Cookie`, `WWW-Authenticate` included). Response bodies are not scrubbed: allow rule hosts that do not echo. |
| Derived hosts | Host config files widen egress: every provider and MCP host in `auth.json`, `models.json` and `mcp.json` becomes reachable. | `credentials.derive.enabled: false` or `credentials.derive.hosts`, `egress.deny`, and the D3 cap: an `egress.allow` set by the policy or org layer clips derived hosts and the user layer's `credentials.rules` (the policy's own rules are exempt) unless that same layer opts in with `credentials.derive.enabled: true`. |
| `egress.privateHosts` and the legacy gateway | Names in `privateHosts` and the gateway host skip the private-address filter, so a rebinding DNS answer for them reaches an internal address. | Only names, no IP literals or localhost; set by policy or user, never by a project; a lower layer may only drop entries. A rule host that resolves privately and is not listed gets a launch notice (D10). |
| Grants | The developer can widen egress at run time. | `egress.grants.enabled`, `maxHours` and `permanent` from policy or org can only turn grants off or shrink them, the D3 cap clips them, `egress.deny` and the private-range check still apply. The container cannot create grants: the CLI runs on the host only and the proxy has no grant endpoint. `egress allow` refuses a host outside the cap rather than store a grant the proxy would ignore. Session grants end with their launch, after 12 h or `maxHours`, whichever is less. |
| Parent proxy | DNS is delegated: with a parent proxy set, an NXDOMAIN locally is passed to the parent, which resolves it. | The private-range check still runs on every local resolution; `noProxy` names are dialled directly. The parent's credentials are resolved on the host and kept in the proxy's memory; with `"env"` they are sent over the control socket and stripped from the environment the proxy starts with. The proxy process starts with a minimal environment (path, home, temp, locale, CA files, the launcher's path overrides, `HTTPS_PROXY` without userinfo), so no secret variable of the launcher reaches it except through the control message; an env secret with a CR or LF is refused at launch, so it cannot split a header. |
| Extra CAs | Trust widens to the corporate CA, inside the container, in the proxy's upstream trust and during image builds. | `tls.extraCa` is a policy or user key, never a project key, and only shrinks under a higher layer. The build removes the CA from the image again. |
| Image layers | `image.dockerfile` runs as root at build time on the engine's default network. | Policy, org or user only, an absolute path; `FROM`, `COPY --from`, `ADD --from`, `ENTRYPOINT`, `CMD`, `USER`, `HEALTHCHECK`, `ONBUILD`, `SHELL`, `STOPSIGNAL`, `VOLUME`, and `ENV` or `ARG` of the proxy, CA, `NODE_OPTIONS`, `PATH`, `HOME` and `PI_*` variables are refused; the layer runs on top of the sandbox image and ends as `USER pi`. Treat the file as code the developer runs. |
| Host pi helper | `!command` values in host `models.json` and `mcp.json` run on the host, as they would with local pi. | Only values from the developer's own host files; a value in a file the container can write (the repository's `.pi/`) is never run on the host. |
| MCP auth store on the host | `<state>/mcp-auth/` holds real OAuth tokens; a token seeded from the host's own `mcp-auth.json` then lives in two places. | Mode 600 files outside every mount. The helper `mcp.json` is written only by `pi mcp login|logout <name>` typed in the shell and holds only `{ url, oauth }` with plain values (D1); refresh uses the recorded definition, never a file the container can write: vault servers' definitions are recorded on every launch (`containerMcpAuth` writes `servers/<name>.json` from the host user `mcp.json`), host sign-ins' at `pi mcp login`. A server defined only in the repository's `.pi/mcp.json` needs a y/N confirmation. |
| Write-back of `packages` | The host `~/.pi/agent/settings.json` changes from a sandbox action. | Only the `packages` key, only on `pi install|remove <source>` typed in the shell with exit 0, only the entry for that source, and never a path that exists only inside the container. Agent edits inside are never written back. |
| Org baseline | A compromised baseline source changes the effective policy. | HTTPS or an absolute path, an optional pinned sha256 (a mismatch refuses a new copy; without a valid cache it stops the launch), validated as the `org` layer, which cannot override policy. On fetch failure the cached copy is used and a notice printed, and the next fetch waits an hour. A response is capped at 1 MiB. `pi --no-sandbox` reads only the cached copy; without one it runs host pi without the org layer, so `fallback: refuse` set only by an uncached org baseline does not stop it (host pi is the developer's own tool and outside the sandbox anyway; set `fallback` in policy to make it binding). |
| Denial page | A denied CONNECT is accepted and answered over TLS with a launcher-CA certificate for the denied name, so the container sees a certificate the launcher CA issued for a host it may not reach. | For a host the egress allowlist or port check denies, the proxy accepts the CONNECT, serves a 403 text page carrying the allow hint over TLS with a launcher-CA certificate for the denied name, and never resolves or contacts that host; at most 30 new denial certificates are minted per minute and 256 are kept, beyond which the CONNECT itself gets a 403. Denial certificates live in memory only (LRU of 256). Rule and vault host leaves are minted under a file lock, written atomically to `<state>/ca/leaf/`, checked key against certificate on load, and expired ones are pruned at daemon start. |
| MCP token vault (`credentials.vault.enabled`, on by default) | Server-published OAuth metadata widens egress (its resource-metadata, issuer, token and registration hosts) and those hosts are terminated; the agent can make the host open a real authorization page in the developer's browser. | The vault hosts pass the derived-host cap, `egress.deny` and the private-range check; discovery runs on the host, never from container traffic. The agent can open a configured server's real authorization page at most 5 times per 10 minutes per repository, and only on the host's own browser and loopback callback port; it never receives the code. Only servers in the user `mcp.json` without a header, URL password, `auth` or `clientSecret` qualify. Policy or org can lock it off. |
| Removing `PI_OFFLINE` | Startup installs and catalog refreshes reach the network. | They reach only allowed hosts; a denial is reported, never bypassed. |
| Host sessions, write path (`sessions.host`, on by default) | The agent can create, rewrite or delete this repository's session files on the host, the ones from before the sandbox and the subagent runs under `<session>/agents/` included. | Only this repository's directory is mounted. Policy or org can turn the key off and lock it; a project file cannot set it. |
| Host sessions, read path | The agent can read this repository's earlier host sessions, which may hold secrets a tool printed in an unsandboxed session; for this one repository that weakens "the agent never sees a real credential". | `sessions.host: false` keeps sessions in the volume; the README names the trade-off. |
| Host sessions, host parsing | Host pi parses the JSONL line by line and runs no code from it, but a session resumed with `--no-sandbox` carries injected content into an unsandboxed agent, and a header `cwd` makes host pi switch to that directory on resume. | The sweep finds each top-level `*.jsonl`'s header as pi does (first non-blank line that parses, lines split on `\n`) and renames it to `.rejected-<random>` (deleting it when the rename fails) when that session's `cwd` is outside the repository, when a bare carriage return (a `\r` not followed by `\n`) appears before the header (pi's listing splits lines at it and its opening does not, so the two could see different headers; pi never writes one), when no deciding line turns up within 1 MiB (opening reads past that) or when it cannot be read, before each launch, after pi exits and before host pi runs on `--no-sandbox`, with the feature on or off. The `cwd` check is lexical: a `cwd` of `<repo>/link` whose `link` points outside passes, which adds nothing to what the writable repository already allows. Content injection stays: resuming a sandboxed session outside the sandbox trusts what the agent wrote, as the repository's own files already require (`.pi/extensions` can be planted anyway). |
| Host sessions, symlinks and special files | Host pi follows links when it lists sessions, so a link could pull another repository's session (or any file) into this list, and a fifo could hang `/resume`; a symlinked `<session>/agents` could redirect host-side subagent writes. | The sweep `lstat`s every entry, re-checks device and inode right before acting, and deletes only the entry itself (symlinks, fifos, sockets, devices), never a target. Top-level entries are swept at every launch and exit; the `agents/` trees only while no container of the repository runs (after the last session's stop, and before a launch that finds none running), decided and run under the repository's session registry lock, only when no other session is registered and the container is not running, so no agent can start and swap a directory for a link during that walk. Hard links cannot cross the mount. A directory the guest made read-only (its uid maps to the host owner) gets `u+rwx` back before the sweep acts in it; an entry that still can be neither renamed nor deleted makes the launch, and `pi --no-sandbox`, refuse with a message naming it, and the exit sweep warns. |
| Host sessions, size | No cap: the agent can fill the disk through that directory. | The same is possible through the repository bind; the sweep warns about a top-level file over 256 MiB. |
| Host sessions, slug collisions | pi gives `/a/b-c` and `/a/b/c` the same slug, so two such repositories share one session directory and see each other's sessions. | Isolation between repositories is as good as pi's slug; the header check renames sessions whose `cwd` lies outside this repository, which also hides the colliding repository's legitimate host sessions from host pi (a known gap). |
| `PI_SANDBOX_TEST_RESOLVE` (D12) | A name-resolution override for live tests. | Honoured only when the launcher runs from its sources, never from the published `dist/` build; a unit test asserts it. |

## 5. Known gaps

- Plain HTTP is refused (CONNECT to port 80 has no SNI to check).
- The git common dir is mounted read-write, and `.git/config` is readable inside, so a token in a remote URL (`https://user:token@host/...`) is visible to the agent; keep credentials in a credential helper, not in remote URLs. On backends without single-file mounts (Apple `container`) the read-only overlays of `.git/config` and the other git files are not mounted at all (a directory bind there would hide the git dir), so the agent can also write `.git/config`, and through it hooks paths and filters the host's git would run.
- The base image in `image/Dockerfile` is pinned by tag (`node:24-bookworm-slim`), not by digest, so a rebuild picks up whatever the tag points at; that is how security updates arrive. A digest pin with a deliberate update step is a follow-up; `image.digest` pins the whole sandbox image meanwhile.
- A config change does not reach a running container while another session of the repository uses it: the new launch joins the old container (with its old mounts, spec and config hash) and prints a notice; the change applies once every session has exited. A tightened policy therefore waits for the last session to end; `pi sandbox reset` applies it at once.
- Host-local model servers (`localhost`, plain `http`) are unreachable from the sandbox; a notice says so.
- Secrets in the `env` of stdio MCP servers become placeholders that nothing replaces until a manual `credentials.rules` entry binds them to the host the server calls.
- Provider `/login` inside the interface fails (read-only `auth.json`); log in on the host. Binding codes to provider token endpoints would need per-provider knowledge.
- Pasting the redirect URL into pi (a remote browser, or a callback port in use on the host) puts the real authorization code and the PKCE verifier inside the container; the token response is then refused, but the agent could race the code to the authorization server itself. Sign in with this machine's browser.
- Servers with `oauth.clientSecret` and project-only servers stay on host `pi mcp login`; a sign-in for them done inside anyway keeps a real token in the volume until the next launch's sweep.
- A sign-out inside the sandbox applies only inside, until the next launch restores the host sign-in.
- Project-level OAuth MCP servers get no token inside: move the server to the user `mcp.json` or give it a placeholder `Authorization` header with a rule.
- Providers whose client derives the API host from the token content may not work with a placeholder token (D5); the doctor's per-rule check shows a 401 or 403.
- NTLM and Kerberos parent proxies need a local relay such as `px` or `cntlm`.
- Private image registries: pulls send no registry credentials.
- Org baselines have no signature and no ETag, only a pinned sha256.
- `tls.extraCa` `hostStore` reads the macOS System keychain only; on Linux use `{ file }`.
- No in-interface prompt for a blocked host: the 403 denial page (or, past its limits, the CONNECT failure) carries `pi-sandbox: <host> is not allowed; run pi sandbox egress allow <host>`, and the launcher prints one line per blocked host when pi exits (for a host outside the policy or org cap, a line saying so instead of the grant hint).
- No in-container unauthenticated proxy shim, so tools that cannot send proxy credentials (headless browsers) have no network.
- Apple `container`, unverified against a real CLI (tested against a fake only): `container network list --format json` (its flags and output shape; names are read from `id` or `config.id`) and whether `container network delete` refuses an in-use network (gc then skips it); the `--tmpfs /tmp:mode=1777` option syntax, how `--env-file` parses values (taken as raw text after the first `=`; values with line breaks are refused), and how bind sources behave. The launcher binds copies (the trust bundle at `/etc/pi-sandbox`) only as directories there and never as single files; the git file overlays are missing on Apple (see the git common dir above). Env values reach `container create` and `exec` through a mode 600 `--env-file` in a mode 700 temp dir, removed right after the call, so the repository proxy token is not in `ps`.
- Domain fronting through a CDN host on the allowlist.
- On a native Linux Docker Engine the proxy also listens on the `docker0` bridge gateway, so any container on the default bridge network, and a machine that routes to that address through this host, can reach it; every request still needs a repository or control token, the address is never `0.0.0.0`, and this path is unverified on a real Linux host.
- A relay kept for other repositories while its proxy came back on another port forwards to the old port; if another local process took that port, the kept sandboxes send their repository token (which only identifies a repository to the proxy) and their tunnels to it until they exit.
- Locks follow the holder's pid, except `mcp-auth.json.lock`, which keeps pi's `mkdir` format and is judged by its age: a launcher that stalls for more than 10 s while holding it can lose it to pi or to another launcher, and the two writes of the vault store can then overlap.
- The Colima VM sees all of the home directory.
- Host pi running alongside a sandbox of the same repository: while the container runs, the sweep only checks the top level, so a link the agent planted under `<session>/agents/` stays until the last session stops; host pi and its subagents may follow it in that window.
- Host sessions in a custom session dir (`PI_CODING_AGENT_SESSION_DIR` or `sessionDir` on the host) are not shared, since that directory holds every repository's sessions; a project `.pi/settings.json` `sessionDir` and a user `--session-dir` are not considered. A change of these host settings recreates the container at the next launch that is alone in the repository.
- The share check proves the directory is shared and writable from the sandbox at container creation (and on each doctor run), not later.
- On a slug collision the sweep of one repository renames the other repository's host sessions to `.rejected-<random>`, so host pi no longer lists them; rename them back by hand.
