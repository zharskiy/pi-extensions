# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a per-repository container and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens is in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` is run as a separate Node process against the pi installed next to the launcher and loads its provider list; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else, which `test/architecture.test.ts` asserts.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `config`, `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `config`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` (its own folder) and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only, and imports nothing from the per-folder test suites. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal. The proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), reported as `pi-sandbox: <message>` and `  hint: <hint>` on stderr with exit code 1 and no stack trace. Any other error is `pi-sandbox: unexpected error: <message>` with exit code 70.
- External processes run through the `CommandRunner` interface, so tests replace them with a scripted fake: git (workspace discovery, `core.hooksPath`, `ls-files --stage` for gitlinks, the checkout `HEAD`), npm (`npm pack`), tar (the build context), openssl (the launcher CA), `security` (keychain credentials and the host CA store), `ps` (checking a proxy pid before killing it), the Apple `container` CLI, secret `command`s, the bundled pi (`auth print-api-key`, `mcp login`, `mcp list`) and `hostpi/provider-hosts.mjs`.

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs.

Node refuses to strip types under `node_modules`, so the published command runs compiled JavaScript. `tsconfig.build.json` emits `dist/` with relative `.ts` imports rewritten to `.js`; `npm run build:launcher` builds it and `prepack` runs that. `bin/pi-sandbox.js` imports `../dist/cli/main.js`. Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, profiles, examples, schema, install scripts) stay in the `launcher/` folder and are published from there (`tsc` does not copy them into `dist/`, and nothing looks for them there), so code finds them through `launcherRoot()` (the `launcher/` folder in either layout) and runnable entries through `launcherEntry()`, never relative to its own compiled file.

## The pipeline

`pi [args]` runs these steps, each a function the other commands reuse (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir):

1. Discover the workspace (`workspace/discover.ts`, `workspace/git-layout.ts`): walk up from the real cwd to the nearest `.git` (`lstat`, no link followed); without one the repository is the cwd and git is never run. Before any git call, `gitLayoutAt` derives the git dir and common dir from the files alone: a real `.git` directory is both (its `commondir`, if any, must be the launcher's pin `.`); a `gitdir:` file names the git dir, which is its own common dir when it has no `commondir` (or the pin), and otherwise must be `<C>/worktrees/<name>` with `commondir` resolving to `C` and `gitdir` resolving to this checkout's `.git`. A link at any of these paths, a target that is not a directory, or a pointer that does not match refuses with `git: <path> ...`. Then `git -c core.fsmonitor=false -c core.hooksPath=<state>/git/no-hooks rev-parse --show-toplevel --git-common-dir` must agree on both real paths (a mismatch or a failing git refuses, so a `gitdir:` file pointing at a directory that is not a repository never gets mounted). A `gitdir:` file pointing at a directory named `.git` (the git dir of another checkout) refuses before git runs. The workspace carries `repoRoot`, `gitDir` and `gitCommonDir`.
2. Load the effective config from the layers (policy, org, user, project), print the org layer's notices, check `workspaceRoots`: the repository and its git common dir must be inside the roots (a linked worktree whose main repository is outside is refused); `outside: warn` prints a warning instead.
3. Intercepted commands (`cli/intercept.ts`, routed by `run.ts` before the pass-through and never with `--no-sandbox`): `install|remove <source>` without `-l`, `mcp add|remove`, `mcp login|logout <name>` with pi's own flags (`-l`, and `--timeout <seconds>` for login) and a bare `update`; see [Intercepted commands](#intercepted-commands).
4. `--no-sandbox`: the config loads offline (`loadEffectiveConfig({ offline: true })`): an HTTPS org source uses its cached copy of any age, and without one the org layer is skipped with a notice, so `--no-sandbox` never touches the network. Refused under `fallback: refuse`, naming the layer; otherwise sweep the host session directory of the repository when host sessions are on (`sweepForHostPi`, see [Host sessions](#host-sessions); the `agents/` trees too when the backend answers and the repository's container is not running) and exec the first host `pi` on `PATH` that is not the launcher.
5. Refuse a workspace that would mount too much (`workspace/guard.ts`, regardless of `workspaceRoots`): a repository root or git common dir that equals or contains `$HOME`, `~/.pi`, the launcher state dir, the user config dir, or `/`, or that lies inside `~/.pi`, the state dir or the config dir. The config dir is protected only when it is the default `~/.config/pi-sandbox`; with `PI_SANDBOX_USER_CONFIG` elsewhere only that file is, so a repository equal to or containing it is refused and its siblings are not. A dotfiles repository rooted at `$HOME` is the case this catches. The hint is `run pi inside a project directory`.
6. Select the backend (`auto` tries Colima, then Apple `container`). The error lists every adapter and why it is unavailable, and suggests `--no-sandbox` when the fallback is `host`.
7. Host side (`cli/derive.ts`): read the host pi files (`readHostPiFiles` of `PI_CODING_AGENT_DIR` or `~/.pi/agent`), seed MCP OAuth tokens (`seedMcpAuth`), read the provider host table through the bundled pi (`readProviderHosts`), when `vaultEnabled` look up the authorization server of each `vaultCandidates` server of the host user `mcp.json` (`discoverVaultServers`: `hostpi/mcp-discover.mjs` run on the host network with the bundled pi, cached in `<state>/mcp-auth/discovery/<name>.json` for 24 h, a failure for 60 s), `ensureSalt`, and `deriveSandboxPi` with the manual `credentials.rules`, the legacy gateway, `credentials.derive` and `vault: { enabled, discovery }`. Print its notices, the discovery failures (that server stays in header mode for the launch) and `privateHostNotices`. The proxy is needed when a gateway, an allowlist, MCP hosts or any rule exists; the trust bundle (`ensureTrustBundle`: the launcher CA plus `tls.extraCa`) is built when the proxy is needed and a rule or an extra CA exists.
8. Register the session (`registerSession`, under the repository's lock) with a fresh launch id. From here until pi starts, SIGINT, SIGTERM and SIGHUP end the launch the way a normal exit does (step 13: end the session, stop the container when no other session is live) and exit `128 + signal number`. The signal does not abandon the preparation: `withSandbox` aborts an `AbortSignal` that `prepareSandbox` and `prepareContainer` check between steps (after the proxy, after the image, before `ensureContainer`, before the file syncs), waits for the step in flight to finish, and only then ends the session, so no container is created or started after the session has ended and the session sweep never runs beside a container start. A second signal while that step finishes is not caught and ends the launcher at once.
9. Proxy (`cli/sandbox-proxy.ts`): `ensureProxyRunning` with the config, the D3 `egressCap`, the bundled pi command, `discoverCommand` (`mcpDiscoverCommand`) and a minimal environment (`PATH`, `HOME`, `TMPDIR`, user and locale, `NO_PROXY`, CA file variables, `PI_CODING_AGENT_DIR`, the `PI_SANDBOX_*` path overrides, and `HTTPS_PROXY` without userinfo; no secret and no other proxy variable); a proxy that cannot start stops the launch. An `env` secret whose value holds CR or LF stops the launch with `<VAR> contains a line break and cannot be used as a credential`. `repoProxyToken` gives this repository's token, `recordProxyDynamic` (under `<dynamic.json>.lock`, so concurrent launches do not lose each other's tokens) runs `writeProxyDynamic`, which records the derived rules, the derived hosts, the vault servers (`derived.vault`, with their placeholders and discovery; the proxy adds their hosts to egress under the derived-host cap) and `sha256(token) -> repo hash`, and `sendProxyControl` hands over the `env` secrets (rules whose secret is `{ env }`, and `egress.parentProxy.auth`), resolved from the launcher's environment, with `repoTokenHash: sha256(repo token)`; the daemon refuses a message that names no live repository token and keeps the secrets per repository, a launch replacing only its own map. `dynamic.json` holds a `shared` section (written with empty `tokens`) and `repos` keyed by token hash (only live token files kept), with the top-level `rules`, `derivedHosts` and `vault` as the union for readers; the proxy applies a repository's rules and vault servers only to that repository, derived hosts as a union.
10. Image: the hot path reads `<stateDir>/image.json` and, when `findCurrentContainer(backend, workspace, digest, configHash)` finds this repository's container with that digest and config hash, skips the base build; the cold path prints `preparing pi sandbox, one time`, resolves the extensions source and runs `ensureBuiltImage` (with the extra CAs and the parent proxy for the build). `ensureLayerImage` then adds the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer, or returns the base id when there is none. The container is created from the layer id; its digest label stays the base digest.
11. Container: `renderAgentDir` writes `<state>/render/<repo hash>/` (the copied agents, prompts, skills, themes and extensions skip `.git`, `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `id_*`, key and certificate stores and secret-named files other than source and markdown), `backend.prepareProxyRoute(port, policyHash, imageId, repoHash)` gives the guest's route on the repository's own network, `guestProxyUrl(route, repoToken)` the proxy URL, and `buildContainerSpec` adds the render mount, the trust mount and `PI_SANDBOX_TRUST_HASH`. Before the spec, `readyHostSessions` (`cli/host-sessions.ts`) prepares the host session directory when host sessions are on: it creates the missing directories 0700 (`prepareHostSessions`), checks the result with `assertHostSessionsDir`, and sweeps it (the whole tree when no container of the repository runs, the top level otherwise); the spec then binds it at its host path and sets `PI_CODING_AGENT_SESSION_DIR`. Before the spec, `gitLaunchNotices` re-runs the git layout checks (`assertGitIntegrity`: the layout as in step 1, every `worktrees/*/commondir` resolving to the common dir, the pin in the common dir and in each submodule git dir) and names `objects/info/alternates` and `http-alternates` when present; `discoverGitOverlay` then lists the git mounts without writing anything, and the spec is built from that list. `ensureContainer` runs under a per-repository lock (`<state>/copies/<short repo hash>.lock`), records the wanted identity (image digest, config hash, spec hash) next to it in `.wanted.json`, and reuses the running container whose labels match. When it is about to create or start one (a fresh create, the replacement of an outdated container after discarding it, or the restart of a stopped matching one), it first calls `beforeStart` inside `aroundStart` (in the launcher `withGitPinLock`, held through the create or start so another checkout's last session cannot remove a pin before the engine binds it), which in the launcher is `readyGitOverlay`: the checks again, the `commondir` pins written, missing hook dirs created, the git mounts discovered again, the snapshots rewritten and the nested-repository baseline recorded; the spec is rebuilt from that result and a stopped container is restarted only when its identity still matches the rebuilt spec, otherwise replaced. Joining a running outdated container whose labels lack `pi-sandbox.git-protection` prints `pi-sandbox: the running sandbox of this repository predates the read-only git dir snapshots; they apply after every session in this repository exits`. A container whose identity differs is replaced only when no other live session of the repository exists; otherwise it is reused and the launcher prints `pi-sandbox: the sandbox config changed; it applies after every session in this repository exits`. A create that fails on a name conflict (another launcher won the race outside the lock) re-reads and reuses that container. When it created one, the share probe (`probeHostSessions`) checks that the container sees the host session directory (a stop with `pi-sandbox: sessions: <dir> is not writable from the sandbox; set sessions.host: false or share it with the VM`, after removing the new container, when not), and `pruneGrants` drops session grants of ended launches. `syncWritableFiles` then merges, under `<state>/sync/<repo hash>/sync.lock`, the host `settings.json` (package URLs stripped of userinfo, with a notice) and the derived `mcp.json` into the volume, keeping mode 600 base copies, and `containerMcpAuth` plus `syncContainerMcpAuth` (`cli/mcp-auth-sync.ts`) write the vault servers' placeholder entries into the volume's `mcp-auth.json` and sweep every token there that is not a placeholder (under the volume's lock, taken over only when its mtime is older than 10 s; the launcher refreshes it every 5 s while it holds it and gives up after 15 s, and the in-container holder must refresh it the same way); the sync runs on every launch, with no entries when no vault server exists (a failure of either is a warning, not a stop).
12. Exec pi in the container with the host cwd as workdir, the `env.allow` host variables and `PI_SANDBOX_LAUNCH_ID` as the exec's environment, and return pi's exit code.
13. When pi exits: `readDenials` (`GET /denials?since=<launch start>` with the repository token) prints one stderr line per blocked host (`run pi sandbox egress allow <host>`, or `it is outside the allowlist set by <policy|org>` when the grant cap excludes it, since a grant could not help), and `endSession` removes the session and, under the same lock, stops the container (`stopIdleContainer`) when no live session of the repository remains (D2), then runs `gitSessionEndNotices` (under `withGitPinLock` (`<state>/git/pins/<sha256 of the git common dir>.lock`), unless `gitDirInUseElsewhere` finds a created or running container of another checkout whose `pi-sandbox.git-common-dir` label is, holds or lies inside this git common dir, removes each `commondir` pin, with a notice when its content changed or it could not be removed, re-runs the layout checks as notices, names alternates that appeared, and compares a new walk of the checkout and `git ls-files --stage` with the baseline, printing a notice for each new or changed `.git` entry and each new gitlink), then sweeps the whole host session directory, `agents/` trees included; when other sessions remain, only the top level is swept, after `endSession`. A session whose launcher pid is dead does not count, so a crashed launcher never keeps a container alive.

`pi sandbox doctor` runs the same steps one by one, so it builds the image and creates the container, then runs its probes through execs into it (`container/probes.ts`, `cli/commands/doctor-container.ts`) and its host checks (`cli/commands/doctor-host.ts`). Inside, `mcp-auth sweep` fails on any `mcp-auth.json` token that is not a placeholder, `settings sweep` fails on a `settings.json` package whose URL carries userinfo (`settings.json package <host> carries a credential in its URL`), and `browser` runs `xdg-open --pi-sandbox-check`, which must reach the proxy's `/healthz`; on the host, each vault server gets `mcp <name>: vault ready (authorization server <host>)` with its sign-in state from the host store (`signed in, token expires in <duration>`), or `vault discovery failed: <error>`, from the same cached `discoverVaultServers` the launch uses. A container the doctor created is removed when it ends, unless another session of the repository is live by then. Rendering stays in `cli/commands/doctor.ts`.

### Intercepted commands

- `pi install|remove <source>` without `-l` runs inside like any launch, around a read of the volume `settings.json` before and after. On exit 0, `packageChangeFor` compares exact source strings: an install counts only when the volume now holds an entry whose source is exactly the typed string (for a local path, the path relative to the guest agent dir, as pi stores it), a key-equal entry with another source prints `the sandbox recorded <entry> instead of <source>` and writes nothing, and a remove counts only when a matching entry existed before and none remains. `writeBackPackageChange` then writes the typed string (for a local path, relative to the host agent dir) to the `packages` key of the host `settings.json`, never the volume's entry; a host object entry for that package keeps its other fields and only its `source` changes (atomic, through the file's real path so a symlink stays, other keys and the indent kept). A local path outside the repository, its git dir and `mounts.extraReadOnly` (with `~/` expanded on both sides) exists only inside and is not written back; a local install inside the repository or its git dir (lexical or real path) is installed in the sandbox only, since host pi would load code the container can rewrite.
- `pi mcp add|remove ...` runs the bundled pi on the host with the host agent dir.
- `pi mcp login|logout <name>`: `mcpLoginServer` takes the server from the host user `mcp.json`, or from the repository's `.pi/mcp.json` after a y/N on the terminal; `prepareMcpLogin` records the sanitised `{ url, oauth }` in `<state>/mcp-auth/servers/<name>.json` and writes the one-server `mcp-auth/mcp.json`; the bundled pi then runs `mcp login <name>` there with `PI_CODING_AGENT_DIR=<state>/mcp-auth`, passing `--timeout` through and dropping `-l` (the helper dir has no project file). Logout uses the recorded server (`oneServerDir`). After an exit 0, when `findRepoContainer` finds this repository's container running, the launcher derives the vault servers again (`deriveVaultServers`) and re-runs the `mcp-auth.json` sync, so the running pi sees the new sign-in or sign-out.
- A bare `pi update` prints `pi follows the launcher; update it with npm install -g pi-extensions-mz`; `pi update <target>` and `pi update --extensions` pass through.

The bundled pi is `locateBundledPi()`: `@earendil-works/pi-coding-agent` found in a `node_modules` folder at or above the launcher, run as `[process.execPath, <bin>]`. Without it, `cli/host-pi.ts` falls back to the host pi on `PATH`.

### Signals

`runPi` (`container/run-pi.ts`) puts a tty stdin in raw mode, so Ctrl-C reaches pi as a keystroke. It listens for SIGTERM and SIGHUP, and for SIGINT only when stdin is not a tty. Pi runs as `sh -c 'echo $$ > /tmp/pi-sandbox-<launch id>.pid; exec "$@"' sh pi <args>`, with a random hex launch id per `runPi` call. On one of the signals it runs `kill -TERM "$(cat <pid file>)"` inside the container through `backend.exec`, waits up to five seconds for pi's exec to end, sends `kill -KILL "$(cat <pid file>)"` the same way only if it has not (never stopping the shared container, which other sessions may use), restores the terminal and returns `128 + signal number` (130, 143, 129). Afterwards it removes the pid file, best effort. Only pi gets the signal, so the container's idle process keeps running and the next `pi` reuses the container.

## Config

`SandboxConfig` is the merged result of the defaults, the profile, and the policy, org, user and project layers. Each layer is validated by a hand-written key spec (precise `<layer>: <key> <problem>` messages); `schema/sandbox-config.schema.json` documents the same keys, and a test keeps the two key sets equal.

The merge has two kinds of keys. Security keys (`egress.allow`, `egress.mcpHosts`, `credentials`, `mounts.extraReadOnly`, `fallback`, `workspaceRoots`, `ssh.agent`, `image.digest`, `image.reference` while a digest is pinned above, `gateway`, and `backend` when policy sets it) may only be tightened by a lower layer: lists may lose entries, `refuse` stays `refuse`, `ssh.agent: false` stays off, roots may only narrow, a value set above cannot change. The project layer is locked by everything above it, including the defaults and the profile, so it can never turn `ssh.agent` on; the user layer is locked by policy, and by the profile when policy chose it. A violation is a `LauncherError` naming the locking layer.

Three keys are host-only: a project layer that sets `env.allow`, `image.reference` or `image.digest` is refused when it loads, with a `LauncherError` naming the file. A project layer may not set `backend` either (`validate.ts`, with `credentials.rules`, `egress.grants`, `tls` and the other project-refused keys), so a repository cannot switch the runtime. Above the project, `env.allow` is the union of the policy and user layers, and secret-looking names (the shared `isSecretName` predicate, also used by the doctor's credential sweep) are refused. Convenience keys take the lowest layer's value; `resources` (`cpus`, `memoryGiB`) merges per subkey.

Egress entries are `host`, `*.domain`, `host:port` or `*.domain:port`. `fallback` is `refuse` or `host`. `PI_SANDBOX_POLICY_FILE` is honoured only when the default policy file does not exist, so a user environment cannot hide a real policy; `PI_SANDBOX_STATE_DIR` and `PI_SANDBOX_USER_CONFIG` always apply.

The org layer (`config/org-source.ts`) is named by `org` in the policy layer, else the user layer: an HTTPS URL (fetched with `node:https`, the system CAs plus `NODE_EXTRA_CA_CERTS`, three-second timeout) or an absolute path (a leading `~/` is expanded), cached in `<state>/org/baseline.json` with `meta.json` (`source`, `fetchedAt`, `sha256`), refreshed when older than `refreshHours` (24 by default), and validated as layer `org`. A response over 1 MiB is refused (`org: response larger than 1 MiB`). A failed fetch keeps the cache, records `failedAt` in `meta.json` and returns a notice, which `cli/` prints; the next attempt waits an hour, so offline a launch neither waits for the timeout nor repeats the notice until then; a pinned `sha256` that does not match refuses the new copy and, without a valid cache, the launch. Lockers: the project is locked by everything above it; the user by policy, org, and the profile when policy or org chose it; org by policy, and the profile when policy chose it. The new keys follow tighten-only rules: `credentials.rules` may only drop rules, `credentials.derive.enabled`, `credentials.vault.enabled` (effective only with `credentials.derive.enabled`, `vaultEnabled`), `egress.grants.enabled` and `.permanent` may only turn off, `egress.grants.maxHours` may only shrink, `credentials.derive.hosts`, `egress.privateHosts` and `tls.extraCa` may only lose entries, `egress.parentProxy` and `org` cannot change, `egress.deny` is the union, and `image.packages`, `npmGlobal` and `dockerfile` take the lowest layer. `config/rule-cap.ts` applies the derived-host cap to `credentials.rules` too when the config loads: a rule from a layer other than policy whose host and port no cap entry matches is dropped with a notice. `EffectiveConfig.egressCap` (D3) is the intersection of the `egress.allow` lists of policy and org, for derived hosts unless that layer sets `credentials.derive.enabled: true` and for grants unless it sets `egress.grants.enabled: true`; it goes to the proxy and into the policy hash. `EffectiveConfig.grantCaps` lists each capping layer with its list, so `pi sandbox egress allow` refuses a host outside it with `<host> is outside the allowlist set by <policy|org>; grants cannot add it` (exit 1), matching entries the way the proxy does. `setConfigValue` resolves the same four layers, so `config set` honours org locks, and holds a lock in `<state>/locks/` around its read, validate and write.

The merge also records the source layer of every dotted key, which `pi sandbox config` prints. `setConfigValue` applies a change to one layer, validates and lock-checks the result against the layers above, and writes nothing when refused. `configHash` is the sha256 of the key-sorted JSON of the effective config (`stableHash` in `shared/`), so every security key, `ssh.agent` included, changes it.

## Backend contract

A `Backend` is the only thing that talks to a container runtime. It detects itself, pulls images by digest (`pullImage(reference, digest?)`, which pulls `repo@digest` when a digest is given and verifies it), looks images up locally (`resolveImage`), builds them (`buildImage`), all returning `ImageInfo { id, digest }`; it finds, creates, starts, stops (`stopContainer(id, timeoutSeconds?)`) and removes containers, runs an exec (`exec(ExecSpec, ExecIo)`: stdin, separate stdout and stderr, tty, size and `onResize`), manages volumes, exports and imports them through a helper started from an image id the caller passes (`exportVolume(name, tarPath, imageId)`, `importVolume(name, tarPath, imageId)`), prepares the guest's proxy route (`ProxyRoute { network, address, notices? }`), names the host addresses the proxy must listen on besides `127.0.0.1` (`proxyListenHosts()`: the bridge gateway on a native Linux engine, none elsewhere) and reports a status map. Specs are runtime-agnostic: `ContainerSpec` (image id, mounts, `NetworkRef`, env, user, read-only root, tmpfs, init, resources, labels, and `sshAgent: { guestSocket }` when the agent is forwarded) and `ExecSpec` (container, command, env, workdir). The image id is opaque: on Apple it may be a `repo@digest` string.

Each backend declares `BackendCapabilities`, which the container spec and `status` read instead of branching on the backend name:

| capability | docker-engine (`colima`) | apple |
| --- | --- | --- |
| `singleFileMount` | yes | no |
| `sshAgent` | when a Colima profile is detected (bind mount of the forwarded agent socket) | yes (`--ssh`) |
| `internalNetwork` | yes | yes |

- `backend/docker-engine/` is the adapter behind the backend name `colima`. It speaks the Docker Engine HTTP API over a Unix socket with `node:http`. The socket is `DOCKER_HOST` (unix), then `~/.colima/pi-sandbox/docker.sock`, `~/.colima/default/docker.sock`, `/var/run/docker.sock`; `status()` reports it. Every spec mount goes into `HostConfig.Mounts` (`Type` `bind` or `volume`), so a missing bind source fails the create instead of being created as a root-owned directory; only the forwarded ssh agent socket stays in `Binds`. Exec is a hijacked `Upgrade: tcp` stream with raw stdin and demultiplexed stdout and stderr frames; the exit code comes from exec inspect. Volumes carry `pi-sandbox.managed` and are exported and imported as tar archives through a helper container, created from the given image id and never started. Builds use the legacy build endpoint, so the Dockerfile avoids BuildKit-only syntax.
- `backend/apple/` drives the `container` CLI through the `CommandRunner`; a tty exec uses the host terminal directly through an interactive spawn, a non-tty exec pipes `ExecIo`. Its ssh agent comes from `--ssh`. Every flag and JSON shape it relies on is kept in one table so it can be corrected against a real host.
- `backend/image-reference.ts` splits references into repository and tag and builds `repo@digest`.

A conformance suite runs the same behaviour tests against both adapters on fakes (an in-process engine HTTP server, a fake `container` CLI) and against a real engine in the live tests.

## Network: proxy instances and relays

There is one proxy instance per policy hash (`proxyPolicyHash(config, egressCap)`: allowlist, MCP hosts, deny list, manual rule hosts, gateway settings, credential source, private hosts, parent proxy, grant limits, extra CAs and the D3 cap), so two repositories with different policies never share a proxy. What changes with host files (derived rules and hosts) lives in `dynamic.json` instead, so a host-file change never restarts a proxy, and it does not recreate a container while the container's proxy route stays. It does when it decides whether the proxy is needed at all: the first derived rule of a repository that had no proxy adds the proxy route, the trust mount and their environment to the spec, so the spec hash changes and the container is recreated (deferred while other sessions are live).

Each instance has a control token (32 bytes, hex) in `proxy-token` (mode 600), which only the launcher holds: it authenticates `POST /control` as `Basic base64("pi-sandbox-control:" + token)`. Each repository has its own token in `tokens/<repo hash>` (mode 600, created once by `repoProxyToken`), which the guest gets in its proxy URL, `http://pi-sandbox:<repo token>@<route address>`; the proxy maps it to the repository hash (the token files, and `dynamic.json` `tokens`, keyed by `sha256(token)`), and answers `407` to any request without a known one (a repository token on `/control` gets `407` too). Restarting the proxy keeps both tokens, so the container's proxy URL and spec hash stay. They rotate only when the instance directory goes: `pi sandbox reset` removes the instance of the repository's policy hash (`removeProxyInstance`) unless a running container of another repository carries that `proxy-policy-hash` (`policyHashesInUse`, the same check `collectGarbage` uses). A token only proves which repository's container a request comes from; it is not a credential for anything else, and it never appears in the proxy's logs.

Agent containers have no route out. With the docker engine they join only their repository's internal bridge network `pi-sandbox-<first 12 of the repo hash>` (`prepareProxyRoute(port, policyHash, imageId, repoHash)`; without a repo hash the old shared `pi-sandbox`), carrying `pi-sandbox.managed` and `pi-sandbox.repo-hash`; the launcher inspects it and refuses a network of that name that is not internal or not managed, naming it. The relay is connected to each such network, and `removeContainer` deletes the repository's network (disconnecting relays first) when its last container is gone, unless called with `{ keepNetwork: true }`: `ensureContainer` passes that when it discards an outdated container to replace it, since the route (and so the network) was prepared before and the new container starts on it; reset, the doctor's cleanup, the probe failure and `gc` remove without it, so an ended repository's network still goes (the Apple adapter does the same); `uninstall.sh` removes every managed `pi-sandbox*` network, and `pi sandbox gc` prunes the managed networks (`pi-sandbox`, `pi-sandbox-<12 hex>`) of repositories outside the keep set (a container or a live session), force-disconnecting relays first and never deleting a network that holds a non-relay container (`backend.pruneNetworks(keepRepoHashes)`). One relay container per proxy instance, `pi-sandbox-relay-<first 8 of the policy hash>`, from the sandbox image id passed to `prepareProxyRoute` (which has socat), sits on the default `bridge` network and on each repository network it serves. It runs `socat TCP-LISTEN:3128` and forwards each connection to its proxy's port through `host.lima.internal` (Colima) or `host.docker.internal` (mapped to the host gateway). On a native Linux engine (the launcher runs on Linux, the socket is not Colima's, `/info` names neither Docker Desktop nor a rootless daemon) the host gateway is the default `bridge` network's gateway on the host itself, where the proxy's `127.0.0.1` is unreachable: the adapter reads that gateway from `/networks/bridge`, maps `host.docker.internal` to it, and `proxyListenHosts()` asks the proxy to listen there too (same port, same token check; never `0.0.0.0`; an address it cannot bind is logged in `proxy.log` and the proxy runs on loopback only). The proxy record keeps the listen hosts it was asked for, and an instance without the ones a launch needs is restarted. This path is covered by unit tests against the engine fake only; a native Linux engine has not been verified live. Its address is read from network inspect after creation, not fixed. Relays carry `pi-sandbox.managed`, `pi-sandbox.relay`, `pi-sandbox.relay-port`, `pi-sandbox.relay-image` and `pi-sandbox.proxy-policy-hash`; a relay whose port and policy hash labels match is reused whatever its image (started again when stopped, so it usually keeps its address and the agent's spec hash), and a relay whose port or policy hash differ is recreated only when no running container of another repository is attached to one of its networks; otherwise it is kept and `prepareProxyRoute` returns a notice (`route.notices`, printed by the launcher) that it still forwards to the old port, since recreating it would cut those sandboxes, whose proxy URL names the relay's address. The proxy keeps its port across restarts (`proxy-port` in the instance directory, reused when it is free), so a relay rarely sees a new port. The image id is used only when a relay is created and kept in `pi-sandbox.relay-image` for information. An agent container carries the same `pi-sandbox.proxy-policy-hash`, so `gc` removes relays and stops proxy instances that no running container uses and no repository with a live session (whose launch may still be preparing) has a token under; it also keeps a stopped or created container of a repository with a live session.

With `apple`, the agents join an internal network created with `--internal` and `--label pi-sandbox.managed=true`, and the route address is that network's gateway with the proxy's port. An existing `pi-sandbox` network is inspected first (`container network inspect` JSON, the fields assumed in `APPLE_NETWORK_FIELDS` in `apple/cli.ts`); one that is not internal, not managed, or whose output cannot show it is internal is refused with a `LauncherError`.

The internal network's embedded DNS answers container names only; external names do not resolve inside, so every tool must go through the proxy.

## Proxy

The proxy is a detached Node process (`proxy/daemon.ts`) on `127.0.0.1`, started on demand. Its state lives in `<stateDir>/proxy/<policyHash>/`: `proxy.json` (pid, port, policy hash, token), `proxy-token` (mode 600, kept when the proxy stops), `proxy-config.json` (mode 600), `proxy-port` (the last port, reused on the next start when free), `proxy.log` (the daemon's stderr), `proxy-access.log` and `lock`. Start-up holds `lock` (`withFileLock`, see Locks); the launcher reuses an instance whose pid is alive and whose `/healthz` answers with the same policy hash, and kills and replaces one that fails the health check twice. `readProxyInstances` lists only live instances; `stopProxy` stops one or all and removes dead records, keeping the token; `removeProxyInstance` stops one and deletes its directory. The launcher CA is shared at `<stateDir>/ca/`.

- `CONNECT host:port` is allowed for hosts in `egress.allow`, `egress.mcpHosts`, manual rule hosts and the gateway host, then for the repository's extra list: derived hosts and active grants (`extraAllowList`), each clipped by the D3 cap. `egress.deny` wins over all of them. Ports are 443 unless an entry names one. IP literals, localhost, loopback, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except names in `egress.privateHosts` and the legacy gateway host. For a tunnel that is not terminated the proxy resolves the name and refuses one that resolves only to restricted addresses with a `403`, then answers `200`, reads the TLS ClientHello and refuses a missing SNI or one that differs from the CONNECT host, and only then dials (itself or through the parent proxy), so a refused server name opens no upstream socket. Tunnels to hosts without a rule are not decrypted.
- A denial is `403` with a JSON body `{ denied, rule, reason }` and `Proxy-Agent: pi-sandbox`; an allowlist denial's reason is `pi-sandbox: <host> is not allowed; run pi sandbox egress allow <host>`. For a CONNECT the allowlist or port check denies, the denial page (`proxy/denial-page.ts`) accepts the tunnel instead, never resolves or contacts the host, serves a `403` text page carrying that reason over TLS with a launcher-CA leaf for the denied name (kept in memory only, LRU of 256), and closes; for a host the D3 grant cap excludes, the reason is `pi-sandbox: <host> is outside the allowlist set by policy or org`; it mints at most 30 new names a minute and keeps 256, beyond which the CONNECT itself gets the JSON `403`. The fetch tool inside thus shows the hint to the model. The last 200 denials per repository are kept in memory and served at `GET /denials?since=<ms>` to that repository's token. Plain HTTP is refused except `/healthz` (`{ ok, policyHash, pid }`), `/policy`, `/denials` and `/control`.
- Credential rules (`proxy/rules.ts`, `proxy/terminate.ts`): TLS is terminated for every rule host with a per-host leaf signed by the launcher CA (made with openssl under a file lock, written atomically, checked key against certificate on load, expired leaves pruned at daemon start); the daemon caches one TLS context per host and asks the CA for the leaf again after 60 s (`leafRecheckMs`), building a new context only when the certificate changed, so a leaf renewed on disk (by this or another daemon) is served without a restart. The CA itself is created once under `<stateDir>/ca/ca.lock`: a fresh key and certificate pair that match is never replaced; otherwise a new pair is made in a temporary directory and renamed into place under the lock, and a reader that finds a pair that does not match takes the lock and reads again; the TLS handshake of a terminated CONNECT gets the ClientHello timeout, and the parent proxy dial and CONNECT head a 10 s timeout. For the matching rule (host, port, path prefix), the placeholder is replaced only in the rule's header, or for a header-less rule in auth-like request headers (`authorization` and `isSecretName` names, never `proxy-authorization` or `sec-*`), and stripped from every other header, never in query or body; an absolute-form target for another origin and a dot-segment path (raw, `%2e`, encoded slash, backslash) get `400`, and `pathPrefix` matches the decoded path; then a `header` rule sets its header from `template` when it is absent or still carries the placeholder. Every response header value is scrubbed by substring (real secret to placeholder). A secret that cannot be resolved removes the header that carried the placeholder, so public endpoints still work, and logs `rule: credential, reason: unavailable`; an upstream `401` invalidates the cached secret once. The legacy gateway is one such rule plus its URL path rewrite. Server-sent events stream unbuffered and WebSocket upgrades are forwarded.
- Secret sources (`proxy/secrets/`, one file per kind, behind `createSecretResolver`): `env` (the map the launcher sent over `/control`, memory only, never the daemon's own environment), `file` (a JSON pointer into a host file), `command` (argv, stdout trimmed or `{ token, expiresAt }`, cached for `ttlSeconds`, 300 by default, single-flight), `piAuth` (the bundled pi's `auth print-api-key` or `print-bearer-token --min-expiry 5m`, cached 240 s), `mcpOAuth` (the token entry of `<state>/mcp-auth/mcp-auth.json` whose key ends with `|<url>`; within 30 s of expiry, the skew at which pi itself refreshes, or after a 401 it rewrites the one-server `mcp-auth/mcp.json` from the recorded server and runs `pi mcp list` there, single-flight; a token that is still unexpired afterwards is used and asked again after 10 s at most, an expired one is unavailable). Values never reach disk, logs or error messages.
- Parent proxy (`proxy/parent.ts`): `"env"` takes the address of `HTTPS_PROXY` and `NO_PROXY` from the daemon's environment, which the launcher passes without userinfo; the credentials from that URL come only from the control map under `egress.parentProxy`, sent on every launch. An object names the URL, `noProxy` and an `auth` secret for Basic auth. An IPv6 literal (`http://[::1]:3128`) is dialled without its brackets. The private-range check still runs on local resolution; an NXDOMAIN while a parent is set is passed to the parent.
- Daemon children (host pi refresh, discovery, command secrets) run with a minimal environment; `proxy/control.ts` also strips the daemon's own environment to `PATH`, `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, the CA file variables, `NODE_OPTIONS` and `PI_SANDBOX_TEST_RESOLVE`, and writes the parent proxy address without userinfo as `parentEnv` in `proxy-config.json`. File secrets lose trailing newlines; an env secret with CR or LF is unavailable (the launcher refuses it before).
- MCP token vault (`proxy/vault/`, `createVault`, used when `dynamic.json` lists vault servers): a corrupt `mcp-auth.json` is moved to `mcp-auth.json.corrupt-<ms>` before the next write (one log line); token and registration endpoint bodies are always buffered (64 KiB) whatever the Content-Type, a non-form token body or non-JSON registration body gets `400`, and a non-JSON token or registration response `502`. real access tokens, refresh tokens, authorization codes and dynamically registered client secrets stay in `<state>/mcp-auth/mcp-auth.json` (pi's format, locked with `withFileLock`); pi inside holds placeholders. The vault hosts (the discovery's resource-metadata, issuer, token and registration hosts, never the authorization endpoint host) are terminated like rule hosts.
  - `POST /oauth/open {url}` (repository token only), sent by the image's `xdg-open` (`image/xdg-open.mjs`) when pi opens the sign-in page: `open.ts` checks the URL against the discovery record (https, the server's `authorizationEndpoint`, only pi's query params, S256, state, a loopback `redirect_uri`), at most 5 opens per repository per 10 minutes; `callback.ts` binds the callback port on the host's `127.0.0.1` and `browser.ts` runs `open` or `xdg-open` on the host.
  - The host listener takes only the flow's path and `state`, keeps the real code and hands a single-use code placeholder to the shim, which long-polls `GET /oauth/callback?flow=` and replays the query to pi's listener inside; `POST /oauth/cancel` ends a flow when pi's port closes, and flows expire after 10 minutes.
  - `token.ts` on vault hosts: the code placeholder is swapped for the real code only in a form POST to that flow's token endpoint with its redirect URI; the client placeholder is swapped back in the form or Basic header; a registration response's `client_secret` is stored and replaced by the client placeholder; a token response bound to a sandbox sign-in is stored and answered with placeholders and a synthetic `expires_in` (the remaining life, at most 3600 s, at least 300 s); a placeholder refresh is answered from the host store (`invalid_grant` when the sign-in is gone, `temporarily_unavailable` when the host refresh failed); any other token response is refused. The access placeholder is injected by the unchanged `mcpOAuth` rule.
  - `discovery.ts` re-runs `discoverCommand` for `/oauth/open` only when the cache file is missing.
- Upstream trust is the system roots plus `<state>/ca/extra.pem` when `tls.extraCa` is set.
- Every decision is one JSON line in `proxy-access.log` (`time, user, repo, host, sni, decision, rule, reason, credential, bytesIn, bytesOut`), never a credential or a token.

## Credentials and derivation

`hostpi/` turns the host pi files into the sandbox's (`deriveSandboxPi`, pure, no secret value in its output):

- `auth.json`: an `api_key` entry becomes `{ type: "api_key", key: P }` with a rule `{ piAuth: id }`; an `oauth` entry keeps its non-secret fields, `access` becomes P (JWT-shaped when the token is a JWT, so the header and payload stay real), `refresh` an opaque placeholder and `expires` far in the future, with a rule `{ piAuth: id, bearer: true }`. A provider key found only in an environment variable the provider host table names gets an `api_key` placeholder and the same rule.
- `models.json`: `apiKey` becomes a placeholder; header values that are `$NAME`, `!cmd` or under an auth-like name become placeholders with `{ env }`, `{ command: ["sh","-c",cmd] }` or a `{ file, pointer }` into the host `models.json`; for a model with an `id`, its header and `baseUrl`-userinfo rules use a `command` secret instead, `hostpi/model-secret.mjs` run with node, which finds the model by provider, id and base URL when the secret is resolved and fails if it moved, so reordering `models.json` cannot send one model's secret to another's host (cached for the command TTL, 300 s by default). Rule hosts come from the provider and model `baseUrl`s, or the provider host table for built-in providers. A `localhost` or plain-`http` `baseUrl` gets a notice.
- `mcp.json`: HTTP server headers as in `models.json` (literal `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-Auth*`, `X-Api*`, `X-Access*` and `X-Session*` headers included), `oauth` blocks removed; a server whose URL has a secret-like query parameter (`isSecretName`, or `auth`, `sig`, `signature`, `pass`, `passwd`, `pwd`) is dropped with `mcp <name>: the url carries a credential in its query string; add a header rule instead` and is never a vault candidate; for a stdio server, env values with URL userinfo, URL arguments with userinfo and `--name=value` arguments with a secret-like name become placeholders, with the stdio notice; and a server without `Authorization` gets `Authorization: Bearer P` with an `mcpOAuth` rule (and a notice to run `pi mcp login <name>` when no token exists). A vault server (vault on, a name of `[A-Za-z0-9_-]`, no `Authorization` header, URL password, `auth` or `oauth.clientSecret`, a public endpoint, and a successful discovery for its URL) instead keeps its plain `oauth` fields and gets no header; its rule `derived:mcp:<name>:oauth` injects the access placeholder, and `derived.vault` carries its access, refresh and client placeholders (`vaultPlaceholders`) and discovery. Its notice is `mcp <name>: sign in from /mcp in pi, or with pi mcp login <name> in the shell`. stdio servers are copied; secret `env` values become placeholders with a notice.

Placeholders are `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`, so they are stable across launches and unguessable. Derived rule ids are `derived:<identity>`; manual ids cannot contain `:`. Rules and hosts are filtered by `credentials.derive`, and a manual rule for the same host wins. The provider host table comes from `hostpi/provider-hosts.mjs`, run with `process.execPath` against the bundled pi's provider list and cached at `<state>/provider-hosts/<pi version>.json`; when the bundled pi's version differs from the image pin, built-in providers get no rule and a notice.

## Provisioning the agent dir

- `renderAgentDir` (`provision/render.ts`) builds `<state>/render/<repo hash>/` on every launch: the derived `auth.json` and `models.json` and filtered copies of `agents/`, `prompts/`, `skills/`, `themes/`, `extensions/`, `AGENTS.md`, `SYSTEM.md` and `keybindings.json` (no symlink is followed, secret-looking files are left out, entries gone on the host are removed). It is mounted read-only as a directory at `/opt/pi-sandbox/render`, and the entrypoint links each present entry into the agent dir, replacing a dangling or older link, never a file or dir the user created inside. A read-only `auth.json` link makes `/login` fail instead of writing a real secret into the volume.
- `syncWritableFiles` (`provision/sync.ts`) keeps `settings.json` and `mcp.json` as writable files in the volume, since pi writes them: a top-level three-way merge against the last synced host copy in `<state>/sync/<repo hash>/` (host-changed keys win, volume-only keys stay, host-deleted keys go), through `backend.exec` (`cat`, and a write through stdin). Host-absolute local package paths outside the mounted paths are dropped with a notice, and the baked `pi-extensions-mz` entry is deduplicated against a host `npm:pi-extensions-mz`.
- `syncContainerMcpAuth` (`provision/mcp-auth.ts`) keeps the volume's `mcp-auth.json` writable (pi writes it during a sign-in), under a container-side `mkdir` lock (the format pi's own lock on that file uses; the launcher refreshes it every second while it holds it, and takes over a lock older than 10 s only after renaming it aside and checking that the renamed directory is still the one it measured, putting it back otherwise): it removes a symlink at the path, sets each vault key's `serverUrl`, `clientInformation` (a `client_secret` placeholder only when the host holds a real one), placeholder `tokens` when the host is signed in and the host `discovery`, drops `tokensExpireAt`, deletes every `access_token`, `refresh_token` or `id_token` anywhere in the file that is not a placeholder (with a notice naming the key), and writes with `umask 077`, a temp file and `mv`. The written copy is kept in `<state>/sync/<repo hash>/mcp-auth.json`. A sign-out inside is not copied back to the host.
- Nothing from the volume is written back to the host; an intercepted `pi install|remove` writes only the typed source string to the host `packages` key, and the sync drops the volume's host-owned settings (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`, `httpProxy`) in favour of the host's.

## Host sessions

`sessions.host` (default on, `cannotEnable` under policy and org, refused in the project layer) puts this repository's pi sessions in host pi's own session directory, so host pi lists them.

- `workspace/pi-session-dir.ts`: `hostAgentDir` (the one resolver of `PI_CODING_AGENT_DIR` or `~/.pi/agent`, also used by `mounts.ts` and `cli/deps.ts`), `sessionSlug` and `hostSessionsDir`, and `hostSessionsChoice`, which gives `{ dir }` or `{ off, notice }` (a custom dir counts when the env value or `sessionDir` is a non-empty string, as in pi; a `file://` `PI_CODING_AGENT_DIR` is converted as pi's `normalizePath` does; `sessionsSwitchNotice` names an unknown `PI_SANDBOX_SESSIONS_HOST` value, which is ignored): off when the key is off, when `PI_SANDBOX_SESSIONS_HOST=off`, when host pi uses a custom session dir (host `PI_CODING_AGENT_SESSION_DIR` or `sessionDir` in the host `settings.json`; that dir is flat and shared by every repository), and when the directory lies under the guest agent dir `/home/pi/.pi/agent` (a Linux host user named `pi`). The last two print a notice.
- The slug is a pi interface the launcher copies, since launcher code may not import pi: `--` + the resolved path with its leading `/` or `\` removed and `/`, `\` and `:` replaced by `-` + `--` (`getDefaultSessionDirPath` in pi's `core/session-manager.js`). The repository path is the real path, as the cwd pi runs in, so the slug matches what host pi writes for the repository root. The live test `tests/live/host-sessions.live.test.ts` checks that host pi and sandbox pi land in the same directory.
- `workspace/guard.ts` `assertHostSessionsDir` is the one exception to never mounting under `~/.pi`: it recomputes the directory, requires it exactly one level under `<agent dir>/sessions` with a slug matching `^--[^/]*--$`, a real directory (`lstat`, not a symlink), and a real path equal to the slug under the real path of `<agent dir>/sessions`; that real path may not be or contain `~/.pi` or the agent dir, and may not be, contain or lie inside any other entry of the agent dir (real paths compared, so a symlinked `sessions` that resolves into `extensions/` is refused).
- `provision/host-sessions.ts`: `prepareHostSessions` (`mkdir -p` with mode 0700, so only missing directories are created and an existing mode stays), `sweepHostSessions` and `probeHostSessions`. The sweep handles at most 8 top-level entries at a time; it `lstat`s each, re-`lstat`s and compares device and inode right before acting, and `unlink`s only that entry: symlinks, fifos, sockets and devices. A top-level `*.jsonl` is opened with `O_NOFOLLOW | O_NONBLOCK`, checked against the `lstat`, and read in 64 KiB chunks only until pi's header rule decides: the first non-blank line (split on `\n`, as pi's opening does) that parses to a truthy JSON value; a bare `\r` in any line up to that one rejects the file, because pi's listing (readline) also breaks at it, so with none the two splittings agree. A first entry that is not `type: "session"` makes pi skip the file, so it stays; a session whose `cwd` is not an absolute path inside the repository (lexically), no deciding line within 1 MiB (pi's listing has no such cap), or an open or read error fails closed: the file is renamed to `<name>.rejected-<random>` (so an existing name cannot block it), and deleted after the identity check when the rename fails. Empty files and a final line that does not parse yet (a header being written) stay, since pi does not list them either. A top-level file over 256 MiB gives a warning. Before reading the root or descending into a subdirectory, the sweep restores `u+rwx` on a directory the host user owns. It returns `failures` for an entry it could neither rename nor delete, or a directory it could not list; `readyHostSessions` and `sweepForHostPi` then refuse with a `LauncherError` naming the file and the dir (before any container is created, or before host pi runs), and the exit sweep warns. With `full`, the walk recurses into directories (the `<session>/agents/` trees) and removes special files at any depth. The probe writes an empty `.pi-sandbox-probe-<random>` on the host and runs `test "$PI_CODING_AGENT_SESSION_DIR" = "$1" && test -f "$1/$2" && : > "$1/$2.guest" && rm "$1/$2.guest"` inside, so the guest's own create and delete is what counts, then deletes both files; `probeSessionsShare` removes the new container when the probe fails or its exec throws.
- Sweep timing: before the spec and before host pi on `--no-sandbox`, `sweepWhenIdle` takes the repository's session registry lock (`withRepoSessionLock`, the lock `registerSession` and `endSession` use) and sweeps the whole tree only when no other live session is registered and the container is not running (on `--no-sandbox`, also only when the backend answers); every container start follows a `registerSession`, so no agent can start during that walk. After pi exits, the whole tree is swept inside `endSession`'s `onLast` after the stop, otherwise the top level after `endSession`. The swept directory is the repository's default slug directory whatever the toggle, so a directory left from an earlier launch is still cleaned when the feature is off; it is created only when the feature is on.
- The spec label `pi-sandbox.session-dir` holds the directory or the reason it is off; it is part of the spec hash with the bind and the env variable, so switching the key or a host change that switches it recreates the container. `pi sandbox status` prints `session dir:` from that label of the existing container, and the doctor's `sessions share` probe reads the same label of the container it probes (`target.containerId`), so both describe the container as created, not the config.
- `env.allow` refuses `PI_CODING_AGENT_DIR` and `PI_CODING_AGENT_SESSION_DIR` (`LAUNCHER_SET_VARIABLES` in `shared/pi-env.ts`, with the variable names the spec and the probe use), and `forwardedEnv` drops them, so no exec environment overrides the spec's value.
- No migration: sessions from the volume stay there (`/home/pi/.pi/agent/sessions/<slug>`), reachable inside with `--session-dir`, removed by `reset --volumes`.

## Sessions and grants

- `grants/sessions.ts`: one file per running launch in `<state>/sessions/<repo hash>/`, written and removed under a lock there; `liveSessions` ignores entries whose pid is dead. The launch id (16 hex) is in the exec environment as `PI_SANDBOX_LAUNCH_ID`, never in the spec.
- `grants/store.ts`: `<state>/grants.json` (mode 600, atomic, locked) holds `{ host, port, repoHash?, createdAt, expiresAt?, launchId? }`; no `repoHash` means every repository. `addGrant` applies `egress.grants` (`enabled`, `maxHours`, `permanent`); a session grant carries the launch id and expires after 12 h, or after `maxHours` when that is smaller. `egress allow --session` inside a sandbox session binds to `PI_SANDBOX_LAUNCH_ID`; outside one it adds one grant per live session of the repository and says so. Both are locked with `withFileLock` (see Locks). `activeGrants` keeps grants that have not expired, whose launch is live, for the repository or the user. The proxy reads them live on every CONNECT that the static policy refused; `pruneGrants` runs on container creation, `reset` and `gc`.

## Container identity

A container belongs to one repository: its name is `pi-sandbox-<first 12 of the repo hash>`. Its labels carry `pi-sandbox.managed`, the full `repo-hash`, `repo-root`, `image-digest`, `image-reference`, `config-hash`, `proxy-policy-hash` (when it has a proxy), `version`, `git-protection` (the spec binds the git dir snapshots), `git-common-dir` and `spec-hash`, the sha256 of the rendered spec as key-sorted JSON. The container is created from the image id, with the reference kept in its label. `ensureContainer` reuses a container whose image digest, config hash and spec hash all match (starting it when stopped) and otherwise stops and removes it and creates a new one. So a config change, a new image or any change in the rendered spec (a new proxy route, a token rotated by `reset`, a new mount) gives the next `pi` a fresh container, while the volumes survive.

The spec mounts the repository and git common dir read-write at their host paths, then, from `discoverGitOverlay` (`container/git-overlay.ts`), binds onto themselves read-write the git dir and every directory between the repository root (or a git dir outside it) and a read-only path (`.git`, `.git/modules`, `.git/modules/<name>`, `.git/worktrees/<name>`, the parents of a `core.hooksPath` inside the repository), so none of them can be renamed away from its mounts, and then the read-only paths, each bound from its snapshot `<state>/git/<repo hash>/snapshots/<first 16 of the sha256 of the path>`: the dirs `hooks` of the common dir and of every submodule git dir and the effective `core.hooksPath` when it resolves inside the repository or git dir (refused when it goes through a link inside them, or is the repository or contains the git dir; left out outside them, since the container cannot see it), and the files `config`, `config.worktree`, `commondir` of the common dir and of every submodule git dir (the `commondir` pin whether or not it exists yet), `commondir`, `gitdir` and `config.worktree` of every `worktrees/<name>`, and the checkout's `.git` when it is a file. `git config --show-scope --get-all core.hooksPath` (with the inert options of step 1) gives the hooks path, ignoring the command-line value. Submodule git dirs are found by walking `.git/modules/`: a dir with a `HEAD` file is a module git dir, and only its `modules/` subdir is walked further (a dir without `HEAD` is a path segment of a module name and is walked into), so objects are never listed; a link anywhere in that walk or under `worktrees/` refuses. Every listed path is `lstat`ed: a link refuses, a path whose real path differs from it refuses, and every path must pass the `mounts.extraReadOnly` protected-path check (`protectedPathGuard`). `writeGitSnapshots` (`container/git-snapshot.ts`) deletes the snapshot dir and copies each file through `readRegularFile` (`O_NOFOLLOW`, device and inode of the open file equal to a fresh `lstat`, at most 8 MiB) and each hooks dir as regular files and directories only; it runs only in `readyGitOverlay`, when no container of the repository runs, and the snapshot paths depend on the target path alone, so the spec hash stays stable from launch to launch. The spec labels `pi-sandbox.git-protection`. When the backend has no single-file mounts the file snapshots are left out and the dir snapshots and self binds stay (a THREAT-MODEL known gap), and the spec asks for copies under its `copiesDir` (`<stateDir>/copies/<repo hash>/`) only for the trust bundle, which `ensureContainer` binds as a directory: the copies of one guest directory go into their own subdirectory, bound read-only at that directory, and a copy whose guest directory lies inside another mount is not mounted at all. So on such backends (Apple) the trust bundle is bound at `/etc/pi-sandbox`. It adds `mounts.extraReadOnly`, checked by `workspace/mounts.ts` `resolveExtraMounts` (each entry exists as a file or directory, is bound from its real path at its `~`-expanded path, and is refused when it is or contains the home, or is, contains or lies under `~/.pi`, the agent dir, the state dir, the user config, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys`, `/dev`, a `.git` dir or the engine socket), the repository's agent volume `pi-sandbox-agent-<user hash>-<repo hash>` at `/home/pi/.pi/agent` and per-repository cache volumes; `repoVolumes` lists both kinds for `reset --volumes` and `migrate`. The root is read-only with tmpfs `/tmp` and `/home/pi`, under an init process, as `<uid>:<gid>` on Linux. It mounts the render dir read-only at `/opt/pi-sandbox/render` and, when there is one, the trust bundle at `/etc/pi-sandbox/ca.pem` (a read-only copy on backends without single-file mounts). The environment holds no host variables (the allowlisted ones and `PI_SANDBOX_LAUNCH_ID` go to each exec, so the spec hash does not change with the terminal): the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_USE_ENV_PROXY`) with the repository token when there is a proxy, `NODE_EXTRA_CA_CERTS` and `PI_SANDBOX_TRUST_HASH` when the trust bundle is mounted (so a CA change recreates the container), the CA bundle paths, `PI_SANDBOX=1`, `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`. `PI_OFFLINE` is not set, so pi installs configured packages and runs updates through the proxy. With `ssh.agent` on and a backend that can forward it, the spec asks for the agent at `/run/host-ssh-agent.sock` and the adapter sets `SSH_AUTH_SOCK`.

## Image

`image/Dockerfile` builds on a slim Node image with git, search tools, ssh, tini, socat and netcat, a `pi` user with uid 1000, pi pinned to the version in the package's dev dependencies, and this package's extensions from `EXTENSIONS_SOURCE`: a tarball packed from the checkout (`npm pack`, cached in `<stateDir>/pack/` by package version and git `HEAD`, `image/extensions.ts`), a registry version when the launcher itself runs from `node_modules`, or none when the digest is pinned. It bakes no pi config and no credential: `auth.json`, `models.json` and the rest come from the render dir at run time. `PI_SELF_UPDATE_COMMAND` points at a script that prints that pi follows the launcher. During the build the extra CAs are trusted (`trust.pem` in the context) and removed again at the end, and a parent proxy without credentials is passed as the predefined proxy build arguments (`image/build-proxy.ts`); one with credentials refuses the build.

The entrypoint removes dangling links into the render dir, re-creates every render link in the agent dir (`rm -rf` then `ln -s`, so whatever the agent put in place of `auth.json`, `models.json`, `skills` and the rest is replaced), seeds `settings.json` once (the agent dir is a volume), builds a CA bundle from the system roots plus `/etc/pi-sandbox/ca.pem` so tunneled hosts keep the system roots, and idles under tini; pi runs through exec. `ensureBuiltImage` pulls and verifies a pinned digest through `backend.pullImage`, or hashes the build inputs (reference, pi version, Dockerfile, entrypoint, tarball) against `<stateDir>/image.json` and rebuilds when they changed or the recorded image is gone. Either way it records the reference, digest and image id; `recordedImage` is the one reader of that record.

`ensureLayerImage` (`image/layer.ts`) renders `FROM <base id>`, `USER root`, the build trust, `apt-get install` of `image.packages`, `npm install --global` of `image.npmGlobal`, the `image.dockerfile` text (checked per instruction: line continuations join instruction lines, and the body of each heredoc of a `RUN`, `COPY` or `ADD` (`<<WORD`, `<<-WORD`, quoted or not, several per instruction) runs to its terminator line and is not checked as instructions; `FROM`, `COPY --from`, `ADD --from`, `ENTRYPOINT`, `CMD`, `USER`, `HEALTHCHECK`, `ONBUILD`, `SHELL`, `STOPSIGNAL`, `VOLUME`, and `ENV` or `ARG` of the proxy, CA, `NODE_OPTIONS`, `PATH`, `HOME` and `PI_*` variables are refused, in any case) and `USER pi`, tags it `pi-sandbox-layer:<first 12 of the inputs hash>` and records it as `image.json` `layer`, so it is built once per set of inputs.

## Locks

`shared/file-lock.ts` has the launcher's one lock primitive, used for the proxy start-up, the grants and session registries, `ensureContainer`, leaf minting and the CA, `provision/sync.ts`, `config/set.ts`, `dynamic.json` and the MCP refresh. `withFileLock` writes the holder's pid to a temporary file and links it into place, so the lock always holds a complete pid. A lock whose pid is alive is never taken over, however long its holder has stalled; one whose pid is dead is taken over at once, and one without a readable pid (an empty file, or a directory left by an older launcher) once it is older than the stale window (10 s). Takeovers go one at a time through `<lock>.takeover` (a lock of the same kind, held for the few system calls of the takeover); the taker checks the lock again under it, renames it to a unique name, compares the renamed file with the stale lock it measured (inode and mtime) and links it back when it is a different, live one. A holder removes the lock on release only when it is still its own file (same inode). `withDirectoryLock` is the `mkdir` lock pi takes on `mcp-auth.json` (`<state>/mcp-auth/mcp-auth.json.lock`, which host pi also locks during `pi mcp login` there): an empty directory whose mtime the holder refreshes every second, taken over when older than 10 s, through the same guard, rename and check. Because pi judges that lock by its mtime only, a launcher stalled for more than 10 s while holding it can lose it to pi.

## Files written

- `~/.local/state/pi-sandbox/` (or `PI_SANDBOX_STATE_DIR`): the launcher's own state, including `git/<repo hash>/snapshots/`, `git/<repo hash>/baseline.json` and the `git/pins/<hash>.lock` locks.
- `~/.config/pi-sandbox/config.json`: the user config, written by the installer when absent (its `org` key with `--org`), on `pi sandbox config set` and by `migrate`.
- `~/.pi/agent/sessions/<slug>/` on the host while host sessions are on: the launcher creates the missing `~/.pi/agent/`, `sessions/` and `<slug>/` (0700), writes and deletes the probe marker at container creation and on each doctor run, the installer `rmdir`s its smoke repository's empty slug dir, and the sweep deletes special files and renames (or, failing that, deletes) rejected sessions there, also with the feature off; pi inside writes the session files.
- `~/.pi/agent/settings.json` on the host: only the `packages` key, only on `pi install|remove <source>` typed in the shell with exit 0, only the typed source string (`writeBackPackageChange`, atomic).
- Inside the repository's git dir and worktree: empty hook directories (`.git/hooks`, a `core.hooksPath` inside a mounted path, submodule `hooks`) created when missing, so they can be mounted read-only, and the `commondir` pin (`.`, written by a hard link of a temporary file, or an exclusive create where the file system has no hard links, so it never replaces an entry) in the common dir and in each submodule git dir before every container create or start, removed after the last session only when it still reads `.`.
- `<repo>/.pi/sandbox.json`: written only on the user's command (`pi sandbox config set --project`). When the launcher creates `<repo>/.pi/`, it also writes `<repo>/.pi/.gitignore` with `*`. It may not import `platform/shared`, so it carries its own equivalent of that write; an existing `.pi/` is left as it is.

## Tests

Tests check behaviour with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server on a temp Unix socket, a fake `container` CLI, a fake backend, temp dirs, real localhost sockets and openssl certificates. A folder's tests may reach that folder's inner modules; everything else goes through `index.ts`. The CLI tests run whole commands against the fake backend with an injected proxy control (ensure, list, stop, remove, control, denials, trust), a fake bundled pi, a fake resolver and a fake terminal confirmation, and collect their output. Live tests against a real engine run only with `PI_SANDBOX_LIVE=1`.
