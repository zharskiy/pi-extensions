# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a container on a Colima VM, one container per launch, and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens and the known gaps are in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` runs as a separate Node process against the host pi of host jobs and loads its packages; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal; the proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), printed as `pi-sandbox: <message>` and `  hint: <hint>` with exit code 1. Any other error exits 70.
- External processes that run to completion (git, gh, glab, openssl, `security`, colima, tar, secret commands, the host pi's jobs) run through the `CommandRunner` interface, so tests replace them with a scripted fake. `cli/main.ts` resolves `git` once, to the git on `PATH` outside the started folder and its repository. The two detached children, the proxy daemon (`proxy/start.ts`) and the proxy's host `pi mcp login` (`proxy/sign-in.ts`), start through an injected `spawn`, and the liveness rule reads a start time with `ps` directly (`shared/process-start.ts`).

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs. Node refuses to strip types under `node_modules`, so the published `bin/pi-sandbox.js` imports `../dist/cli/main.js`, which `tsconfig.build.json` emits (`npm run build:launcher`, run by `prepack`). Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, examples, schema, install scripts) stay in `launcher/`, and code finds them through `launcherRoot()`.

## The pipeline

`cli/run.ts` routes the command line. `pi sandbox …` runs a command, the hidden `pi-sandbox __uninstall` runs the uninstall cleanup, intercepted commands run on the host, and everything else is a launch (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir from `cli/context.ts`):

1. **Intercepted commands** (`cli/intercept.ts`, with `cli/host-routes.ts` for the commands that start no session): `install|uninstall|remove <source>` without `-l`, `mcp add|remove|login|logout`, every `update …`, `config` without `-l`, every `auth …`, pi's help (`--help`, `-h`, `<command> --help`, bare `mcp`), `--list-models [search]`, `--export <file> [out]` and `--version` run on the host and stop here, before the folder is read. Only `--version` reads the config, to see whether the image is pinned.
2. **Folder and config** (`cli/context.ts`). `workspaceFolder` takes the real cwd and walks up to the nearest `.git` without following links; that root, else the cwd, is the folder to mount. The config is loaded from the one config file. Before anything is searched, the guard (`assertSafeMounts`) runs on the folder and `workspaceRoots` refuses a folder outside every root. Then discovery runs (below), and after it `workspaceRoots` and the guard run again on the repository root and its git common dir (`assertSafeWorkspace`).
3. **`--no-sandbox`** uses a lenient context (no guard, no search), checks `workspaceRoots`, sweeps the host session directory and execs host pi, mounting nothing.
4. **Register the launch** (`cli/launches.ts`, `grants/launches.ts`) under the repository launch lock, before the VM stage, so `pi sandbox stop`, a share restart and the uninstall count a launch that is still preparing. From here to the end of the session one guard holds SIGINT, SIGTERM and SIGHUP: during preparation the first signal prints `pi-sandbox: stopping after the current step` and ends the launch like a normal exit once the step in flight finishes, and a second signal ends the launcher at once. While pi runs, signals go to pi (`container/run-pi.ts`); during the teardown they are ignored until the cleanup finishes.
5. **VM** (`cli/vm.ts`, `backend/colima/`). The host pi files are read first and the host side (step 7) starts deriving alongside. The host session directory is created, then a stopped `pi-sandbox` profile is started plainly when its `colima.yaml` exists.
6. **Shares.** Without `workspaceRoots`, any path the running VM lacks (the folder, the git common dirs, `<state>/vm`, the host session dir) is shared by restarting the profile once with the full mount list, only when no other launch is live, and the share is kept. With `workspaceRoots`, the wanted list is exactly the roots (writable), `<agent dir>/sessions` (writable) and `<state>/vm` (read-only) (`workspace/roots.ts` refuses a root with `,` or `:`, the home or a folder above it, and a root that overlaps the agent dir, the state dir or `~/.ssh`, drops a root inside another and skips a missing one with a notice; `cli/vm.ts` builds the list and creates the two dirs). `reconcileShares` (`backend/colima/shares.ts`) compares it with the VM's shares under `vm.lock`: equal does nothing; different with no other launch live restarts the profile with exactly that list and one notice, which is what drops the home share of a VM installed earlier; different while another launch is live goes on with a notice when the current shares already cover this launch, and otherwise refuses like a missing share. The hidden `pi-sandbox __vm-shares` (`cli/commands/vm-shares.ts`) prints the same list, one `--mount` value per line (`<path>:w` or `<path>`), or `$HOME:w` without `workspaceRoots`, for `install.sh`. The shares the VM has are read from its `lima.yaml`. A new share absorbs any share inside it, since colima refuses nested mounts, and a share that colima mounts at another path in the VM is refused before the VM is stopped. Every `colima` command runs against `~/.colima`, whatever `COLIMA_HOME` says.
7. **Host side** (`cli/derive.ts`): read the provider host table, derive the sandbox files and the credential rules (`hostpi/`), build the trust bundle (the launcher CA and the `tls.extraCa` certificates: a `sha256` entry is matched by fingerprint, computed in Node, against `security find-certificate -a -p` of the macOS System and login keychains (a keychain that cannot be read is skipped, and named when nothing matches), a `file` entry is read as PEM, and every certificate must be unexpired and a CA or a self-signed root (issuer equals subject and the signature verifies with its own key), or the launch stops), run the orphan sweep, and sign in to MCP servers that need it (`cli/mcp-sign-in.ts`, only when input and output are a terminal, never from `pi sandbox doctor`, which reports `pi mcp login <server>` instead). Then the VM's trust store follows the `tls.extraCa` certificates (`backend/colima/vm-trust.ts`), so the VM's engine pulls through an inspecting proxy: the marker `/etc/pi-sandbox/extra.sha256` in the VM, read through `colima ssh` right after the VM stage, is compared with the SHA-256 of the certificates in `<state>/ca/extra.pem`; when they match, or there are no certificates and no marker, nothing else runs; a marker that cannot be read (ssh fails) counts as a mismatch. Otherwise, under `vm.lock` and only when no other launch is live (else one notice says the VM picks the change up at the first launch with no other pi session running), the launcher clears the marker, writes each certificate to its own `/usr/local/share/ca-certificates/pi-sandbox/pi-sandbox-extra-<n>.crt` (all removed when there are none), runs `update-ca-certificates --fresh`, restarts `containerd` and `docker` (which ends any container in the VM, with a 60 s timeout), writes the marker once that restart has run, then polls the engine for up to 60 s. Each step is a fixed `sudo` command through `colima ssh`; certificates and marker reach the VM on stdin, never in a command line. A failed step before the restart stops the launch and leaves no marker, so the next launch tries again; an engine that is still down after the wait stops the launch with the marker in place, so the next launch does not reinstall. Nothing is written on the host.
8. **Proxy and image, in parallel**, alongside rendering the agent dir, planning the git overlay and preparing the host session directory. `ensureRepoProxy` starts or reuses the repository's proxy (see Network); the proxy always runs. `ensureSandboxImage` ensures the current image (see Image).
9. **Container** (`container/lifecycle.ts`). Print the notices, then create the launch's own container under the repository's container lock: right before the create the git plan's `ready()` re-checks each repository's layout, creates missing hooks dirs (left in place), checks the hooks dirs and bare dirs, and records the git baseline. The create then prunes overlay volumes no container mounts, ensures the volumes, creates missing mount points, creates and starts the container, hands the volume roots to the sandbox user and probes the session share. Then the agent files are synced (see Provisioning): sandbox changes of the allowlisted keys are written back to the host, then the host `settings.json` and `pi-*.json` files are written into the agent volume.
10. **Run pi** through exec: `sh` starts in the repository root and `cd`s into the host cwd; a cwd the sandbox does not have (hidden by an overlay volume) prints `pi-sandbox: <cwd> is not in the sandbox, pi starts in <root>`. A pty and raw mode are used only when stdin and stdout are both terminals. The `env.allow` variables are forwarded, except one whose value is shaped like a credential (`env.allow: <NAME> holds a credential, so it stays on the host`). Pi flags that name a host file (`--system-prompt`, `--append-system-prompt`, `-e`/`--extension`, `--session`, `@file`) pass unchanged; when the file lies outside the mounts, a notice names it. A signal reaches pi as SIGTERM through a pid file in its container; when pi exits within 5 s its exit code is returned, else the launcher stops the container and returns 128+N. A closed stdout or stderr (EPIPE, EIO) stops pi like SIGTERM (exit 143). Pi's exit code is the launcher's.
11. **End the launch.** Print one line per blocked host from the proxy's denial list, `<host> was blocked in this folder's sandbox; <hint>`, with a hint for its kind: not allowed (`run pi sandbox egress allow <host> on the host from <root>`), a private, loopback, link-local or reserved address (the proxy's reason, which names the address a name resolved to, then `add <host> to egress.privateHosts in <config file>`), `egress.deny` (`denied by egress.deny`), plain HTTP (`use https`), an upstream failure of a spliced or terminated host (`it could not be reached: <reason>`), a credential the proxy could not supply (`it could not authenticate: <reason>`), a provider login host pi could not resolve (`the <provider> login on the host is missing or expired; log in again with pi --no-sandbox and /login`), else the proxy's reason. Write the sandbox's changes of the allowlisted keys back to the host and sync again (see Provisioning), only when the sandbox got ready and never from `pi sandbox doctor`. Remove the launch's container, also after a failed preparation or a signal, then the launch entry; when it was the repository's last live launch, `removeRepoSandbox` runs and then the git end-of-session report. `sweepOrphans` runs after either way (see Lifecycle).

`pi sandbox doctor` first computes the VM share coverage; while a path is missing its `vm shares` check warns with the path (with `workspaceRoots` set, it also warns, naming them, while the VM's shares differ from the wanted list), a `skip sandbox` check says the sandbox was not started, and only the host checks run. Otherwise it runs the same preparation without the shares stage and the MCP sign-in, turning each stage and probe into a check. A rule probe sends the rule's placeholder; when the proxy recorded a credential denial for that rule since the doctor's launch began, the rule check is a `warn` with the end-of-launch reason and hint (an expired provider login, say) instead of `ok` or `fail` on the status. When the probe got no HTTP answer and the proxy recorded a denial without `credentialRule` for the rule's host and port (a CONNECT refusal: a private address, `egress.deny`), the `fail` check is `<url>: the sandbox proxy refused it` with the end-of-launch reason and hint under it (`denialAdvice` in `cli/sandbox-proxy.ts` splits that hint into the two) instead of fetch's bare error code (`0`); any other fetch error keeps its text, and `CERT_NOT_YET_VALID` on a `trust` or `rule` check adds that the VM's clock is behind the host's (the proxy dates its certificates with the host's clock) and to restart the VM with `pi sandbox stop` and run the doctor again. The doctor writes no end-of-launch report: `withSandbox` hands the proxy's denials to its `denials` option before `finishLaunch` may stop the proxy (the default prints the end-of-launch lines), and the doctor turns those no rule check explains (credential denials and denials for a rule's host and port) into `warn blocked <host:port>` checks with reason and hint; when a stage failed before the probes, the sandbox never ran, there are no denials to read, and a `skip probes` check names the stage. Its stderr goes to a line sink during the run, so every launch notice (without the `pi-sandbox: ` prefix, deduplicated, without the missing-pi notice its `host pi` check repeats; without a host pi the `provider hosts` check is a `skip`, so the one cause fails once) lands in the report's `notices` section, also when an error ends the run, in which case the report so far comes before the error and has no result line. The checks are plain data (`cli/commands/doctor-checks.ts`: the result types and builders, the order and the verdict the exit code and the result line share), and `cli/commands/doctor-report.ts` renders them as text: sections in the order host, sandbox, network, credentials, leak sweep, notices, the checks of a section in the fixed order of their names (`LAYOUT`, so `vm size` follows `vm` and `parent proxy` comes before `no-route`, whatever order the probes finish in), one line per check (`  <status>  <name padded to 16>  <detail>`, the home shown as `~` where a path starts: at the start of the text or after a space, `(`, `:` or `=`), reasons and `hint:` lines indented under it, the passing credential rules collapsed into one `rules` line unless `--verbose`, the hint `run pi sandbox doctor` dropped as circular, and a `result:` line that counts every check. Colour (words only, the same layout) is used only when stdout is a terminal, `NO_COLOR` is unset or empty and `TERM` is not `dumb`. The preparation's progress (the build steps, `starting the sandbox VM`) reaches the doctor through the `progress` option of `withSandbox` instead of stderr: on a terminal whose `TERM` is not `dumb` it shows as one stderr line overwritten in place and cleared before the report, otherwise it is dropped. The exit code is 1 when a check failed, else 0, or 128 plus the signal number after a signal.

The `tls inspection` check (`cli/commands/doctor-tls.ts`) shows whether the network intercepts the TLS of tunnelled hosts, which the container verifies itself. On the host it runs a node script through the command runner that handshakes with `pi.dev:443` (the one host every allow list holds), through the parent proxy unless `NO_PROXY` bypasses it, with its credentials on stdin, never failing on an untrusted issuer: once against Node's built-in roots and, when `<state>/ca/extra.pem` holds a certificate, once against those roots plus it. Verified by the built-in roots it passes as `not inspected`; verified only with the extras, as `inspected by <issuer>, trusted via tls.extraCa`. A verdict that is not an issuer error (`UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, `SELF_SIGNED_CERT_IN_CHAIN`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`), such as an expired certificate or a name mismatch, fails as `TLS to pi.dev does not verify: <verdict>`. Otherwise it fails as `TLS to pi.dev is signed by "<root>" (sha256 <fp>), which the sandbox does not trust` with the `{ "sha256": … }` entry for the user config and a second hint for a PEM file: the root is the self-signed certificate above the topmost presented one, found by issuer name and signature among the certificates `security find-certificate -a -p` lists from the System and login keychains (walking up through keychain intermediates); the sha256 is given only for a root that is itself in a keychain, as the launcher looks it up there. With no such root, the detail names the topmost certificate's issuer and the hint says to ask IT for that CA as PEM. Nothing is added to the config. A failure that is not about the certificate (the parent proxy refuses, no answer) is `pi.dev:443: <error>`, as for other unreachable hosts. Inside the container, with the probes, `tls in sandbox` runs the same script with the container's node, its `HTTPS_PROXY` (the launcher's proxy) and its own trust (`NODE_EXTRA_CA_CERTS`); when the host trusts the chain and the container does not, it fails naming the layer: the sandbox proxy, when it presents another leaf than the host sees, else the container's trust. The keychains are read only for an untrusted chain.

### Discovery

`workspace/discover.ts` and `workspace/git/layout.ts`. Discovery reads files and runs git; it writes nothing.

- **One repository.** Derive the git dir and common dir from the files alone (a real `.git` dir, a separate git dir, a submodule git dir or a linked worktree), refuse any link or pointer git would not have written, and refuse a `commondir` in a git dir where git never writes one (the common dir, a submodule git dir) unless it reads `.`. Then `git rev-parse --show-toplevel --git-common-dir` must agree. A cwd that is or lies inside a git dir (`.git`, `.git/hooks`, a bare repository in the working tree) refuses with `workspace: <cwd> is a git dir, refusing` or `… lies inside the git dir …`. A repository root whose only git entry is `.git` in another letter case refuses.
- **A workspace.** Without a `.git` above the cwd the folder is a workspace: one walk finds every nested repository, each checked like a single repository; the launch fails closed when one fails those checks. A nested checkout counts as a repository only when its git dir and common dir lie wholly inside the folder (the `gitdir:` text resolved as git resolves it, one component at a time with links followed, and the lexical and real paths all inside). Any other nested `.git` file, one whose git dir is missing included, makes a detached checkout: plain files, no git call, nothing outside mounted. A folder shaped like a git dir (`HEAD` plus `commondir`, or plus `objects` and `refs`, any file type, names ignoring letter case) outside every nested repository is a bare dir, bound read-only as a whole with no git call; a cwd of that shape refuses. An entry named `.git` in another letter case refuses (the message names a case-insensitive volume). A directory the walk cannot read refuses when it is the cwd or belongs to the user, since the sandbox could `chmod` it open; one owned by someone else is left alone. More than 50 000 directories, or more than 128 repositories and bare dirs, refuse.
- **Build output.** The same walk collects the build output folders beside their marker files (`workspace/overlay-markers.ts`). With `mounts.autoOverlays` on it does not descend into a marked folder that exists, since its overlay volume hides it; off, it neither collects nor skips, and a single repository then skips the walk. More than 512 overlays turn every overlay off (a workspace walks again without skipping); a single repository whose walk exceeds 50 000 directories gets no overlays. Both print a notice. `node_modules` and `.pi` are never searched.
- **Lenient.** `pi sandbox status`, `config`, `egress`, `reset` and `--no-sandbox` use a lenient discovery without git calls or refusals; it walks nothing, except where a command asks for overlays (status), and never in the home or `/`. Nested repositories are not listed there.

### Intercepted commands and host pi

`pi install|uninstall|remove`, `pi mcp add|remove|login|logout`, every `pi update` and `pi config` without `-l` run the host pi on the host. A bare `update` (or `update pi|self|--self`) runs the managed install's own update in the same empty folder, with `PI_CODING_AGENT_DIR` set to the host agent dir, so it reads only user-scope settings (`selfUpdateCommand`, `npmCommand`) for the self target. Every other `update` form (`--all`, `--extensions`, `--extension <source>`, `<source>`, `--models`, `--force`, combined flags), `config` without `-l`, `install|uninstall|remove` and `mcp login|logout` run in an empty `<state>/mcp-login-<random>/` folder so no project config loads (pi reads project settings only from `<cwd>/.pi/settings.json`, so a project `npmCommand` never runs on the host); `update`, `config` and `mcp` get `PI_CODING_AGENT_DIR` set to the host agent dir; `mcp add|remove` run in the cwd. After an `update` exits 0 whose target includes pi itself as pi parses it (bare, `--self`, `--all`, `pi`/`self`, `--self --extensions`, `pi --extensions`; not `--extensions`, `--extension <source>`, `<source>` or `--models`), the launcher names the pi version the sandbox follows. A source counts as remote only as a plain `npm:<name>[@version]`, an `http(s)://`, `ssh://` or `git://` git URL with owner and repository, or `git:git@host:owner/repo` and `git:host.tld/owner/repo`; every other source is a local path, handed over as an absolute path (an `update` source that looks like a path, starting with `.`, `~` or `file://` or holding a `/`, is made absolute the same way). `install` refuses a local source whose path or real path lies in a git working tree (ignoring a git root no sandbox could hold, such as a home folder) or in a folder a sandbox has run in (the repository records under the state dir), wherever it is started. An `npm:` spec that names a path or another protocol (`npm:file:…`, `npm:link:…`, `npm:/…`) is refused too.

Commands that start no session run on the host too; `cli/host-routes.ts` decides, and what it does not recognise launches. `--help`, `-h`, `--version`, `-v`, `--list-models [search]` and `--export <file> [out]` count only as the whole command line, so a flag value (`--system-prompt --version`), a word after `--` or any other flag launches. A subcommand wins, as in pi: `-h` or `--help` anywhere after `install`, `remove`, `uninstall`, `update`, `list` or `config` is that command's help, bare `mcp`, `mcp help` and `mcp … --help` are mcp's help, and `auth …` always runs on the host. Help, `--list-models` and `auth` run host pi in the empty folder with `PI_CODING_AGENT_DIR` set to the host agent dir. Pi builds a runtime for top-level `--help` and `--list-models`, so they get `--no-extensions --no-skills --no-prompt-templates --no-themes --offline`: no extension (built-in ones included) or package resource loads and no missing package is installed, at the cost of extension flags in the help and extension-only providers in the list. Subcommand help, mcp's help and `auth` return before pi reads any package or extension. `--export` runs in the cwd, since pi exports before it loads any settings resource or extension and reads only the session file. `--version` starts nothing: it prints `imagePiVersion` of the resolved host pi, the version the image is built with, unless `image.reference` and `image.digest` pin an image, when pi inside answers. `pi list` stays inside, since host pi in a trusted project runs the project's `npmCommand` to find a global package, as do `mcp list`, `config -l` and `install -l`. Without a host pi these fail as `mcp login` does.

`cli/host-pi.ts` resolves one host pi for everything (host jobs, `--no-sandbox`, `pi update`, the doctor line): pi's managed install in the host agent dir (`locateManagedPi`: the `install/managed-install.json` marker, `install/current-version`, the release's pi package and an executable `bin/pi`), and nothing else. A pi installed with npm, including one in the launcher package's or a checkout's `node_modules`, and a `PATH` pi are never used, so how the launcher itself was installed does not matter. Without the managed install, the launch notice, the doctor's `host pi` line, `--no-sandbox`, a bare `pi update` and every intercepted command print the same line (`missingPiText`): no managed pi in the agent dir, that an npm or `PATH` pi is not used, what is lost (provider credentials, host commands, `--no-sandbox`) and the remedy (pi's own installer, then `install.sh` again). `install.sh` requires the same managed install in both modes, after its preflight and before it starts Colima or runs npm. Host jobs, `--no-sandbox` and a bare `pi update` (the managed install's own update) run its wrapper `<agent dir>/bin/pi`, as typing `pi` did before the launcher took the link: the wrapper picks the current release, puts the Node pi's installer brought on `PATH` for pi and its child processes (npm for `pi install`) and sets `PI_MANAGED_INSTALL_ROOT`; only the proxy's `pi auth` and `pi mcp login` and the launch-start MCP sign-in run the release's entry with the launcher's Node (`HostPi.command`), which is part of the proxy input. Nothing records which pi was picked, only what it was used for (the image's pi version, the proxy input's pi command), so a host pi update rebuilds the image at the next launch and restarts the proxy at the next launch that is alone in the repository. Without a host pi the image takes the pi version the launcher is tested with (`testedPiVersion`, the root `package.json` devDependency).

## Config

`SandboxConfig` is the defaults with the one config file, `<agent dir>/pi-sandbox/config.json` (`PI_SANDBOX_USER_CONFIG` overrides the path), laid over them (`config/`). The file belongs to the user who runs the launcher; there is no other layer. It is validated by a hand-written key spec; `schema/sandbox-config.schema.json` documents the same keys, and tests keep the key sets and the string constraints equal. One host grammar (`config/egress-entry.ts` `parseHostEntry`) checks every host field and the egress commands, and the proxy uses its `isHostName`. A validation message names the key and, for paths, names and choices, the value (cut at 200 characters, JSON-escaped when not printable); host, credential and `npmGlobal` values are never shown.

- A key the file sets replaces the default, per leaf key (`workspaceRoots` counts as one); a list the file sets adds to a non-empty default list, which only `env.allow` has (the terminal variables). `config/merge.ts` records each key's source, `default` or `config`, for `pi sandbox config`.
- `egress.allow` (empty by default) follows `pi.dev` (port 443, that name only, no credential), which pi fetches its model list from at start and which every allow list holds (`config/egress-allow.ts`); `egress.deny` still wins over it. Grants are always on and `--no-sandbox` always runs host pi. `config/parent-proxy.ts` is the one reader of `HTTPS_PROXY` (else `https_proxy`) and `NO_PROXY` for the launcher, the proxy, the image build and the doctor; a parent proxy is used whenever the shell that runs `pi` sets one.
- `image.reference` and `image.digest` are set together or not at all; without them the image is built locally.

The `pi-sandbox` command never writes the config file.

## Backend

Colima is the only engine. A `Backend` (`backend/types.ts`) is the only thing that talks to it, and the seam tests replace with a fake. `backend/colima/` speaks the engine HTTP API over `~/.colima/pi-sandbox/docker.sock` with `node:http`, and owns the VM as `Backend.vm` (start, shares, trust store, size, stop). It pulls by digest, builds through the classic build endpoint, creates the agent container with `AutoRemove`, typed mounts (a missing bind source fails the create), every capability dropped except `CHOWN`, `no-new-privileges` and a limit of 4096 processes (`backend/colima/container-body.ts`), runs execs over a hijacked stream with backpressure, manages labelled volumes, networks and relays, and imports only `shared`. `CHOWN` stays only for the launcher's own root exec that hands new overlay and shared cache volumes to the `pi` user; pi itself runs as uid 1000 with no capabilities. The relay container drops every capability, runs with `no-new-privileges` and at most 1024 processes (one socat per open connection); it runs socat as `pi` on port 3128, which needs no capability. `removeContainer` resolves only once the engine has removed the container, within 30 s, else it fails with the hint that the next pi start removes what is left. `removeRepoNetwork` keeps the repository's network while any container labelled with the repository other than its relay exists.

Requests other than builds, pulls and execs give up after 30 s without an answer, volume and image removals after 10 minutes and the ping after 5 s, and the error names the request; a container removal returns only once the engine has finished it, and gives up after 30 s for the delete and 30 s for the wait, or 10 s each for the relay, whose replacement runs under the repository launch lock. An answer that stops halfway is reported as closed by the engine, with the advice to run the command again. When colima reports the VM running but its engine does not answer the ping, the launch says so and advises `colima stop --profile pi-sandbox && colima start --profile pi-sandbox --activate=false`. An exec whose host output is closed ends quietly with the exec's exit code. A container name that is already taken is reported as an unexpected clash. A launch prepares its repository's network and relay under the repository launch lock, so two launches of one repository never create them at once; an outdated relay is removed, and its replacement created once the engine has finished the removal. A conformance suite runs the same tests against the adapter on an in-process engine, against the fake backend, and against the real engine in the live tests.

## Network

- **Per-repository proxy.** One proxy process per repository, `proxy/daemon.ts` (`dist/proxy/daemon.js` in a published install), on `127.0.0.1` of the host, shared by the repository's launches. It reads its `RepoProxyInput` (allow and deny lists, rules, derived hosts, `env` secret values, parent proxy) from stdin at start, and afterwards only the egress settings from `egress.json` (below); the parent proxy's credentials arrive separately from the `HTTPS_PROXY` it is handed and are put back into that URL only in memory. It records `{ pid, boot, start, port, inputHash }` in `repos/<hash>/proxy/proxy.json`. The launcher starts it with `repos/<hash>/proxy/` as its working directory, waits up to 10 s for its health check, and on failure quotes the daemon's own tagged line (`pi-sandbox-proxy failed: …`) from `proxy.log`. A live proxy with the same input hash is reused once its health check answers, within three tries; one with another hash is replaced only when no other launch of the repository is live, else kept with the notice `the credential, parent proxy or CA settings changed; the pi sessions running in this folder keep the earlier ones until they all exit (egress allow and deny changes apply now)`. The input hash covers the rules, `env` secret values, the parent proxy's address, `NO_PROXY` (`parentEnv`) and credentials, the extra CA file, the host pi command, the host agent dir and the access-log limit, not the egress settings: every launch writes `egress.allow`, `egress.deny`, `egress.privateHosts` and the derived hosts to `repos/<hash>/proxy/egress.json` (mode 600), which the running proxy re-reads when the file changes, as it does `grants.json`, so a tightened or loosened egress policy reaches every session of the folder from the first CONNECT after a new launch rewrote the file (editing the config alone changes nothing for running sessions), and that launch prints `the network allow and deny settings changed and now apply to every pi running in this folder` when other sessions of the folder are live. Each CONNECT is decided against one snapshot of those settings; tunnels and terminated connections already open stay until they close, and a missing, unreadable or garbled file keeps the last good settings and is read again at the next CONNECT; concurrent CONNECTs share one read.
- **Token.** The guest proxy URL is `http://pi-sandbox:<token>@pi-sandbox-proxy:3128`. The token (`repos/<hash>/proxy/token`, 32 random bytes, mode 600) identifies the repository to its proxy, which answers `407` to anything else. It survives proxy restarts and is deleted when the repository's last launch ends.
- **Relay and alias.** Containers join only their repository's internal network `pi-sandbox-<h12>` (the first 12 hex of the repository hash) and have no route out. One relay container per repository, `pi-sandbox-relay-<h12>`, sits on that network with the alias `pi-sandbox-proxy` and on the default bridge, and forwards with socat to the proxy port on `host.lima.internal`. It is recreated under the same name and alias when the proxy port changes.
- **Decisions.** A CONNECT is allowed for allowlisted, rule, derived and granted hosts on their ports; a host listed only for another port is denied as `egress.allow`, with a reason that names `host:port`. A rule host is terminated even when `egress.allow` also lists it. `egress.deny` wins, where an entry `d` denies `d` and every name under it and `*.d` every name under `d`. A CONNECT to port 80 and a plain HTTP request are refused as `plain-http`. IP literals, loopback, private and reserved ranges and the metadata address are refused. A name that resolves only to such addresses is refused with a 403 before the tunnel opens, for terminated and spliced hosts alike, unless `egress.privateHosts` names it; it is recorded as `private-address`, so it gets the `egress.privateHosts` hint; an IP literal or loopback name refused for its range gets the proxy's reason and the note that such hosts are never reachable instead, since `egress.privateHosts` rejects them. A tunnel that is not terminated must present a ClientHello whose SNI equals the CONNECT host before the proxy dials. A denied host gets a 403 page over TLS with a launcher-CA certificate for its name, carrying the grant hint. A terminated request whose upstream fails before the response headers answers `502` with the reason and is recorded as a denial (`upstream`, or the restricted-address rule when a rebinding answer is refused at dial time); a certificate failure adds a pointer to `tls.extraCa`, and the doctor counts a `502` as failed. Grants are read live from `grants.json`. Every decision is a JSON line in `access.log` carrying the repository hash, including requests without the token; an allow names the rule that allowed it (`egress.allow`, `credential`, `grant-or-derived`, and `terminate` for a terminated tunnel). An unavailable credential is a `deny` line with rule `credential` whose reason names the credential and the resolver's reason, or with rule `login` and the reason `the <provider> login on the host is missing or expired` when host pi's `auth` command exits non-zero; the request is forwarded without it. Its denial record carries the rule id as `credentialRule`. No line holds a credential or a token.
- **Termination.** TLS is terminated only for rule hosts, with per-host leaves signed by the launcher CA; a leaf's key is written briefly under the state dir for openssl to sign and kept in memory after. Upstream connections are pooled per host, port and access inside the repository's own process, so never shared between repositories. A parent proxy from `HTTPS_PROXY` is chained for upstream dials; an `HTTPS_PROXY` that is not an `http://` URL gives no parent route, and the launch warns and the proxy connects directly.

## Placeholders and secret sources

A placeholder is `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`; so placeholders are stable across launches and unguessable. A JWT access token gets a JWT-shaped placeholder: the launcher's own header (`{"alg":"none","typ":"JWT"}`), the token's payload without `exp`, `iat`, `nbf`, `jti` and `auth_time`, and the opaque placeholder as the signature, so it stays the same when the host refreshes the token and a consumer inside that reads an account claim still finds it.

On a terminated host, the proxy first drops every header that carries a placeholder of one of the host's other rules (another port or another path prefix). It then replaces the placeholder of the matching rule (host, port, decoded path prefix compared with the decoded path, which carries no query, so an encoded `?` cannot widen it) only in the rule's header, or in auth-like request headers for a rule without one, and strips stray placeholders from every other header. A rule with a `header` sets that header on every matching request. A placeholder is never substituted in a query or body. A `Basic` value is decoded, substituted and re-encoded, which is how git, npm, pip and Maven send passwords. Response headers are scrubbed of the secret and of the exact base64 the proxy sent. A dot-segment path or a cross-origin absolute target gets `400`. A request body sent chunked is forwarded chunked.

The secret comes from a source resolved on the host and kept in the proxy's memory only (`proxy/secrets/`): `env` (from the stdin input), `file` (a JSON pointer, or a key of an npmrc, ini or Maven settings file), `command` (stdout, or `{ token, expiresAt }` with `expiresAt` an ISO 8601 time; cached 300 s, or until `expiresAt` less 30 s; 30 s per run, a failed one retried at most every 5 s), `piAuth` (the host pi's `auth print-api-key` or `print-bearer-token`; a non-zero exit is reported as a missing or expired login, never with the command's output) and `mcpOAuth` (below). An upstream `401` invalidates a cached secret once. A failed lookup is retried at most every 5 s, except a host sign-in state (signed out, or a sign-in running), which is never cached, so a sign-in finished on the host is used by the next request.

Derivation (`hostpi/`) is pure: it turns the host `auth.json`, `models.json` and `mcp.json` into sandbox copies with placeholders and rules, and `hostpi/derive-tools.ts` adds the gh, glab, npm, pip, Maven and git derivers (`hostpi/tools/`), which read host files and run host commands and render placeholder-only tool files.

- gh, glab and git run only from absolute `PATH` entries outside the repository and its git common dir, each probe with a 10 s limit (the glab token probe and the provider host script 30 s; a probe that does not answer leaves that tool without credentials for the launch, with a notice). A `GH_CONFIG_DIR`, `GLAB_CONFIG_DIR` or `XDG_CONFIG_HOME` path inside those roots is ignored with a notice. For github.com the gh token reaches `github.com`, `api.github.com` and `uploads.github.com`.
- `auth.json`: a credential's `env` is copied, with placeholders for secret-named or credential-shaped values. A built-in provider whose key is only in the launcher's environment gets an `api_key` entry whose rule reads that variable (`{ env }`).
- `mcp.json`: a disabled HTTP server gets no rule and no sign-in; a server with `auth.provider` gets a rule on its host with that provider's placeholder and secret. Every other reachable HTTP server without a credential header gets the OAuth bearer. A header is a credential when its name is auth-like (authorization, a secret word, `auth`, `cookie`, `session id`) or its value has a credential shape or reads a host value; header names that differ only in case are merged, the last one winning. An absolute stdio `command` or `cwd` gets a notice. A `models.json` provider or model whose `baseUrl` has a secret-looking query parameter is dropped, as an MCP server is.
- npm and pip: a URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`) is rendered with a placeholder in place of the password, or of the user name when the token is the user name, and gets a rule on that host (for npm also the URL path) whose secret reads that part of the URL back from the host file. Other values with URL userinfo, npm and pip proxy settings, and values that reach userinfo through `${VAR}` stay on the host. `.npmrc` keys that name host paths (`prefix`, `cache`, `userconfig`, `globalconfig`, `init-module`, `script-shell`, `*file`) stay on the host with a notice. The pip config is the first of `~/.config/pip/pip.conf`, `~/Library/Application Support/pip/pip.conf` and `~/.pip/pip.conf`.
- Maven: the settings keep each profile's `id`, `activation`, `repositories` and `pluginRepositories` (never its properties), `activeProfiles`, `pluginGroups` and the mirrors, with URL userinfo removed and `localRepository` dropped with a notice; a server's password and its `httpHeaders` values become placeholders bound to the server's repository hosts (a header rule injects only in that header), a server with no credential field is copied unchanged, and one with only a private key stays on the host.
- A registry, mirror or index host with neither a credential rule nor an `egress.allow` entry gets a notice naming the entry to add; egress is not widened.
- Manual `credentials.rules` win over derived rules for the same host; `credentials.derive` filters or disables derived ones.

## MCP sign-in

MCP OAuth tokens stay in host pi's `<agent dir>/mcp-auth.json`, which the launcher only reads (`shared/mcp-auth-key.ts` is the one parser). The sandbox `mcp.json` has no `oauth` block; a server that gets the OAuth bearer has an `mcpOAuth` rule. Two triggers start `pi mcp login <name> --timeout 300` with the host pi, in an empty folder against the host agent dir:

- at launch start, when both input and output are a terminal, for each derived server whose token is missing or expired and has no refresh token (`cli/mcp-sign-in.ts`), interactively;
- in the proxy (`proxy/sign-in.ts`), when the token it injects has expired or was answered `401` upstream; a `401` to a request with the container's own `Authorization` starts nothing. The login runs in its own process group, which the proxy kills when it stops. While that login runs the request gets a local `503` (`pi-sandbox: sign-in to MCP server <name> opened in the browser on the host; finish it there, then retry.`); otherwise the request goes out without the credential. When the login the proxy started exits 0, the proxy uses the token host pi then holds even if its stored expiry has passed, until the server answers `401`.

A server for which the host holds no token gets its requests without a credential, so servers that need no sign-in work; a `401` to such a request starts no login and is answered with `pi-sandbox: MCP server <name> is not signed in on the host; run pi mcp login <name> on the host, then retry.` A `401` to an injected token answers "opened in the browser" when a sign-in starts, else "not signed in on the host", and the start spacing below applies.

Both triggers take one lock per server and record starts and failures in `<state>/mcp-login.json` (`lastStart`, `failedAt` and `rejectedStart` per server), written under its own file lock. The proxy starts at most one sign-in per server per minute host-wide and none for 10 minutes after a failure; a start caused by a `401` to an injected token that has not expired runs at most once per server per 10 minutes whatever its exit code. The launch-start sign-in runs once per launch and is skipped for 24 hours after a failed sign-in by either path, unless a later sign-in succeeded, printing `not signed in; run pi mcp login <name>` once per repository. Host pi's login refreshes a stored token silently when it can.

## Provisioning

`renderAgentDir` (`provision/render.ts`) writes `vm/render/<hash>/` on every launch (and removes the `repos/<hash>/render/` of earlier versions) under `render.lock`: the derived `auth.json`, `models.json` and `mcp.json`, filtered copies of the host agents, prompts, skills, themes, extensions and instruction files, and `tools/` (the Maven settings with the sandbox proxy and derived servers, and when derived the gh, glab, npm, pip and git configs; the gitconfig's credential helper for a gh or glab host is a shell function that prints the placeholder, so HTTPS git works without gh or glab in the image, and the gh and glab configs stay unused until the tool is added). The copy leaves out directories named `secrets`, `.secrets`, `credentials` or `.credentials` outside `node_modules`, secret-looking files, files over 8 MiB and private keys, follows no link, and one render notice lists what was left out and why. It is mounted read-only; the entrypoint links each entry into the agent dir and the tool files into the home, copying the ones the tools must write. `auth.json` is the exception in the agent dir: it becomes a regular 0444 copy, because pi locks it through its resolved path and a lock dir next to a link would land in the read-only render dir. The copy holds placeholders only. Every copy goes to a temp name carrying the entrypoint's pid, so concurrent containers of the repository never share one, and is then moved into place.

`syncVolumeFiles` (`provision/sync.ts`) runs under `sync.lock` and always writes back first, then syncs. The sync writes the filtered host `settings.json` into the volume: package URL credentials and the host `httpProxy` dropped, the host-owned keys (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`) and `sessionDir` left out, local package sources inside the repository handed over as absolute host paths (`file://` included), others skipped with a notice, and entries of `extensions`, `skills`, `prompts` and `themes` outside the repository named in a notice. It copies the host `pi-subagents.json`, `pi-style.json`, `pi-notifications.json` and `pi-session-limits.json` into the volume as they are (not through the read-only render dir, so they stay writable inside), and removes the volume copy of one the host lacks or holds as no JSON object. It then records, in `<state>/repos/<h>/sync/baseline.json`, the allowlisted keys of what it wrote.

Npm and git packages follow the host (`provision/host-packages.ts`, `provision/package-refresh.ts`). Pi in the container installs a configured package only when it is missing or, for npm, when the installed version does not satisfy the version in its source; it never refreshes an existing git checkout at start. So the sync pins every npm and git source of the volume `settings.json` to what the host has installed, read from host files only: `npm:<name>` becomes `npm:<name>@<version>` from `<agent dir>/npm/node_modules/<name>/package.json`, and a git source gets `@<commit>` in place of its ref, the commit read from `<agent dir>/git/<host>/<path>/.git/HEAD` (a loose ref or `packed-refs`). A package the host has not installed there (a legacy global npm install, a checkout the parser cannot place) keeps its source. Pi inside then reinstalls an npm package whose version changed by itself. For git, the launch-start sync (not the end-of-launch sync) compares the commits with `<state>/repos/<h>/sync/packages.json`, the identities and versions it pinned last time, removes the volume's `git/<host>/<path>` checkout of each git package whose commit differs or is not recorded (all of them when the record is missing or garbled), then writes the record. Host and every path segment must match `[A-Za-z0-9._-]+` and not be `.` or `..`, with at least two path segments, since the host `settings.json` is also written by extensions; a source that fails this keeps its source, gets no pin and is never removed, and the removal checks each `git/…` path again before it runs. While another launch of the repository is live, nothing is removed and the record stays, the settings are still pinned, and one line says `sandbox packages follow the host: git packages refresh at the next launch (another session is running)`; one line, `sandbox packages follow the host: reinstalling <n> packages`, counts the recorded packages whose version changed. A failed removal prints a warning and leaves the record, so the next launch tries again. Nothing is read from the container for this; the record lives on the host and only steers what is removed in the volume. An unchanged launch costs no exec and no network call. When the registry or git host is not reachable from the sandbox, pi inside reports the package as failed to install, as for any missing package, and does not load an old copy.

The write-back (`provision/write-back.ts` is the pure part: allowlist, three-way merge, lines) runs in the launcher's host process, never in the container, at every launch after the container exists and before the sync (this recovers changes left by a killed session or by another live session sharing the volume) and at the launch's end after pi exits and before the container is removed; `pi sandbox doctor` writes back before its sync too, so it never drops a live session's change. Without a baseline (the first launch) nothing is written back. The allowlist is fixed in code, with no config key: in `settings.json` `defaultProvider`, `defaultModel`, `defaultThinkingLevel`, `enabledModels`, `theme`, `hideThinkingBlock`, `quietStartup`, `collapseChangelog`, `doubleEscapeAction`, `treeFilterMode`, `steeringMode` and `followUpMode`; in the four `pi-*.json` files the top-level keys their extensions read, except `disabledPlugins` of `pi-subagents.json`, which the extension reads from the user file only. Each volume file is read through `sh -c` exec (`readVolumeText`, regular files only, at most 64 KiB for a `pi-*.json` and 1 MiB for `settings.json`, given up after 5 s on the host side through the exec's abort signal; the doctor's `readVolumeFile` of `mcp-auth.json` and `settings.json` follows the same two rules and reports such a file as not a JSON object); one missing is skipped silently and one not a regular file, unreadable, over its limit or not a JSON object is skipped with a notice, so a lost volume never deletes host keys. Each `settings.json` value is checked before it is written: `defaultProvider` and `defaultModel` strings of at most 512 characters, `enabledModels` a list of them, `hideThinkingBlock` and `collapseChangelog` booleans, `quietStartup` a boolean or `header`, `theme` a file name of `[A-Za-z0-9._-]` other than `.` and `..` (host pi joins it into a path), and `defaultThinkingLevel`, `doubleEscapeAction`, `treeFilterMode`, `steeringMode` and `followUpMode` one of pi's own values; a failing change is dropped with `<file>: <key> in the sandbox is not a valid value; not written back`. `pi-*.json` values are left to their extensions' schemas. Per key, with B the baseline, V the volume and H the host, compared by deep JSON equality (an absent key is a value): V = B or H = V leaves it; H = B writes V to the host (a deletion included); otherwise the host wins with `<file>: <key> changed on the host and in the sandbox; kept the host value`. The host file is re-read right before the write, a host file that is no JSON object is skipped, every other key is kept, a link is written through to its target, and the write is atomic in the target's dir with its mode kept; a missing host `pi-*.json` is created only from a volume copy. Each applied change prints `pi-sandbox: <file> <key>: <old> → <new> written to the host` (values cut at 60 characters, control, bidi and line separator characters replaced); nothing prints when nothing changed. A write-back failure prints one warning line and never fails the launch or changes pi's exit code. When the sync into the volume fails it deletes the baseline and warns that later changes will not be written back. Nothing else from the volume (`auth.json`, `models.json`, `mcp.json`, `trust.json`, agent files, other `settings.json` keys) reaches the host.

## Host sessions

With `sessions.host` on, the container binds host pi's session directory of the repository at its host path and `PI_CODING_AGENT_SESSION_DIR` points pi at it. The slug is pi's formula, copied since the launcher may not import pi. `assertHostSessionsDir` (`workspace/guard.ts`) is the one exception to never mounting under `~/.pi`: the directory must be exactly one level under `<agent dir>/sessions`, a real directory, and overlap no other agent dir entry. `provision/host-sessions.ts` creates missing directories 0700, probes the share from inside, and sweeps the directory before each launch, after pi exits and before `--no-sandbox`: it deletes links and special files and renames session files whose header `cwd` lies outside the repository (or cannot be read) to `.rejected-<random>`, reading headers as pi does. A file the sweep cannot rename is reported and kept, never deleted, and the next launch refuses until it is fixed. The whole tree is swept only while no other launch of the repository is live and no container of it runs, under the launch lock.

## Container

Every launch creates its own container and removes it when its pi exits. Its name is `pi-sandbox-<h12>-<launch id>`; its labels are the managed flag, the repository hash and root, the launch id, the image digest and reference, and the session dir. A launch never joins another's container, so container settings apply at the next launch. The volumes, the proxy, the relay and the network are per repository (in workspace mode, the workspace root) and shared by its containers. Containers run with `AutoRemove`.

The container drops every capability except `CHOWN`, runs with `no-new-privileges` and at most 4096 processes, and pi runs as the image's `pi` user (uid 1000) without capabilities. The spec mounts the repository and git common dirs read-write at their host paths, binds onto themselves the common dir and the folders between the repository root and each hooks dir (so none can be renamed away from its mounts), then each hooks dir read-only straight from the host. In a workspace it also binds each bare dir read-only and the folders between the workspace root and each nested repository and bare dir onto themselves. It adds the agent volume, the build output overlay volumes, the shared cache volumes, the host session dir, the render dir and the trust bundle. A build output overlay that lies inside a git dir or a read-only mount is left out with a notice (`<path> is not overlaid: it lies inside <guard>, which the sandbox protects`). The spec refuses a target mounted twice, and a mount that equals or contains `/usr/local/bin`, `/usr/local/lib`, `/opt/pi-sandbox`, `/etc/pi-sandbox`, `/home/pi` or `/tmp` (`the sandbox would mount <path> over <reserved>, which the sandbox image needs`). As a backstop it refuses (`workspace: the sandbox could write in <dir>, which the launcher did not search for repositories, refusing`) when, for an overlay folder, the mount with the longest target over it is not a volume or a read-only bind, or a writable bind has its target or source inside it. Mount points are created as the host user, one level at a time, after a real-path check, so no spelling (case, links) creates one inside a protected path. The agent volume is named from the host account name.

The root is read-only with tmpfs `/tmp` and `/home/pi` (exec allowed), under an init process, as the image's `pi` user. The environment holds the proxy variables with the token (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` in both cases, `NODE_USE_ENV_PROXY`, `PI_SANDBOX_PROXY_*`), the JVM proxy flags (`JAVA_TOOL_OPTIONS`; the Maven proxy is in the rendered `settings.xml`), the CA bundle paths (`SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `GIT_SSL_CAINFO`, and `NODE_EXTRA_CA_CERTS` for `trust.pem`), the derived tool variables (`GH_TOKEN`, `GITLAB_TOKEN` placeholders), `GIT_TERMINAL_PROMPT=0`, `PI_SANDBOX=1` and pi's own switches (no version check, no telemetry, OSC 52 clipboard), with `NO_PROXY` and `no_proxy` set to `localhost,127.0.0.1,::1` so a client reaches the container's own servers directly. No host variable is in the spec; the `env.allow` variables reach the exec only.

## Image

`image/Dockerfile` builds on `node:24-bookworm-slim` with only what pi and the launcher need (git, ripgrep, fd, socat, procps, openssh-client, less, ncurses-term, CA certificates), a `pi` user and pi installed at the host pi's version, passed as the `PI_VERSION` build argument. It bakes no pi config, package or credential. The launcher CA goes into the system store; extra CAs are trusted during the build steps and removed from the trust store and the final filesystem afterwards. `BASH_ENV` and the first line of `/etc/bash.bashrc` source `bash-env.sh`, which prints the missing-command hint and adds the JVM truststore flags. The entrypoint re-creates the render links and the read-only `auth.json` copy, builds the CA bundle and, when `java` is present, a JVM truststore, then idles under the engine's init.

`ensureSandboxImage` runs under `<state>/locks/build.lock`, so two launches never build at once; the second says it waits. It pulls `image.reference` at `image.digest` when both are set, else builds the base locally, tagged `pi-sandbox-base:local`, then adds the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer, tagged `pi-sandbox-layer:<hash of the layer Dockerfile>` (packages sorted and deduped) and reused while the inputs stay the same. `<state>/image.json` records the base image (id, digest, inputs hash) and the current layer tag; the inputs hash covers the Dockerfile, the entrypoint, `bash-env.sh`, the pi version and the launcher CA. Build contexts and their archives live under `<state>/build/` and are removed after the build; the sweep clears what a killed build left while no build holds the lock.

- The build gets the parent proxy (`HTTPS_PROXY`, else `https_proxy`, http only) as `HTTP_PROXY` and `HTTPS_PROXY` build arguments, with a loopback host (`127.0.0.1`, `localhost`, `::1`) pointed at `host.lima.internal`, and `NO_PROXY` from the same parser. A proxy the launcher does not use gives the build no proxy; one with credentials refuses the build.
- A failed build's error keeps the last 30 lines of the build output. A certificate error in a build step adds the `tls.extraCa` hint; a certificate error while the engine pulls the base or the pinned image adds the hint that the network's CA is not declared in `tls.extraCa` and that `pi sandbox doctor` prints the line to add; npm's `No matching version found` for the pi package says the host pi version is not published.
- Prune, one rule: after every build and in the daily collection (which skips while a build holds `build.lock`), layer tags other than the current layer, and untagged launcher images (the replaced base included) other than the recorded base, are removed once they are older than an hour and no container uses them.

## Locks and liveness

`shared/file-lock.ts` is the one lock primitive: the repository launch lock (launch registry, proxy start and idle exit, sweep, reset), the container lock, the render and settings sync locks, the grants, the CA and the per-server MCP sign-in lock. A lock file holds `<pid> <boot time> <process start> <nonce>`. The liveness rule (`shared/liveness.ts`) applies to locks, launch entries and `proxy.json`, and it is process identity, never a timer: a holder is live when its pid exists, the boot time matches and the process start time (`ps -o lstart=` on macOS, field 22 of `/proc/<pid>/stat` on Linux, read by `shared/process-start.ts`) is the recorded one. A running pid counts as live when the start-time tool itself failed, and as dead when no start time is obtainable for that pid. A sleeping Mac or a stopped launcher therefore keeps its sandbox, and a pid reused by another process does not count. A lock that is not live is taken over, one taker at a time. A live holder is waited for: the launch and container locks wait up to 120 s, the render, sync and CA locks 30 s, the build lock up to an hour, then the waiter fails and asks to run the command again. The VM lock is a directory lock judged by its age and refreshed while held (180 s wait), so a share restart, a VM start and `pi sandbox stop` never interleave.

## Lifecycle and sweep

- A launch registers an entry (`pid`, boot time, process start) under `repos/<hash>/launches/`; the sweep deletes the entries of dead launches. Every removal path runs under the repository launch lock and re-checks the live launches first. `pi sandbox reset` refuses while a session of the repository runs and names how many.
- **Records first.** Each mount point the launcher makes in the repository goes into `created.json` right after it is written, so a refused launch leaves nothing the sweep does not know. Hooks dirs are not recorded; they stay.
- **Launch end.** The launch's own container is removed, and the call waits until the engine has removed it. When it was the repository's last live launch, `removeRepoSandbox` (`cli/sweep.ts`) removes the repository's containers, relay and network, stops the proxy, deletes the token, removes the mount points in `created.json` (deepest first, only empty real directories), and sweeps the whole host session directory. When the engine is unreachable the engine steps are skipped and the rest still runs.
- **Git report.** The first launch of a repository records the git baseline; a launch that starts while another is live keeps the earliest one. At the last launch's end, after `removeRepoSandbox`, `gitLaunchEndNotices` prints the layout re-check failures, new alternates, changed own git files, new or changed nested `.git` entries and gitlinks, and deletes the baseline; an earlier launch's end makes no git call. A baseline left by an unfinished session is reported at the next launch that is alone in the repository, under `git: the check after the last sandbox session did not run; it reports now:`.
- **Proxy idle exit.** The proxy checks the live launches under the launch lock every 30 s and exits after two empty checks, stopping any sign-in it started.
- **Sweep.** `sweepOrphans` runs at every launch start and end and at `pi sandbox stop`. For a repository with live launches it removes the containers whose launch-id label is not a live launch; for one without, it runs `removeRepoSandbox` when the repository has leftovers (the proxy record or token, `created.json`, or engine objects with its label). A repository whose folder is gone is forgotten together with its grants and its `seen.json`. `repo.json` records `mountRoot`, the nearest mount point above the root: a missing root counts as unreachable (everything kept) while that mount point is not mounted or the parent folder is missing, and as gone only when the parent exists and the mount point is mounted. Once a day (`gc.json`, written only when the engine answered) the sweep also removes unused volumes of forgotten or deleted repositories and unused images.
- **kill -9.** A killed launcher's entry stops counting at once, since its pid is gone, and its proxy idles out within about a minute; its container, relay, network, token and created folders stay until the next launch of any repository, `pi sandbox stop` or the uninstall. A VM restart removes containers and relays.
- **Uninstall.** `uninstall.sh` runs the hidden `pi-sandbox __uninstall`, which refuses with exit 75 while a launch is live (the same liveness rule). Otherwise it runs `removeRepoSandbox` for every known repository and every repository the engine labels, each under that repository's launch lock and only when no launch of it started meanwhile (containers, relay and network when the engine answers, created folders, proxy, token, host sessions), then removes the managed volumes and images. The script then deletes the profile and the host files, even when the launcher could not run.

## Invariants

- No real secret in the container's filesystem, environment or volumes; derivers and renderers take placeholders only, and `tests/support/expect-no-leak.ts` checks specs, exec argv, env, stdin and render files.
- The container's only network path is its repository's proxy; SNI check and private-range deny are always on.
- Nothing is mounted from a protected path; the hooks dirs are read-only inside.
- Only the user's one config file is read; nothing in the repository configures the sandbox.
- Every removal re-checks liveness under the repository launch lock, so a live launch's container is never removed.
- Every file the launcher writes is listed below.

## Alternatives considered

- A published, pinned image instead of a local build: rejected as the default, so the sandbox runs the same pi version as the host; `image.reference` and `image.digest` pull one when an organisation builds it.
- An unauthenticated proxy shim inside the container: rejected; JVM flags and rendered tool settings cover most clients, and the rest is a documented gap.
- One shared proxy for every repository: replaced by one proxy per repository, so rules, env secrets and tokens never cross repositories.
- Read-only file binds for `.git/config` and the other git files: rejected, since on a case-insensitive volume another letter case of the name writes the host file through the bind; only directory binds are used.
- A second engine, Docker Desktop, or a host process under Seatbelt or OpenShell: not taken; Colima is the one engine, and a container keeps credentials out of reach by construction.

## Tests

Tests check behaviour through public entry points with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server, a fake backend, temp dirs, real localhost sockets and openssl certificates. The CLI tests run whole commands against the fake backend. Tests that run real git go through `tests/support/git.ts`, which keeps the developer's git config out. Live tests against the real Colima engine run only with `PI_SANDBOX_LIVE=1` and fail when their cleanup had to remove anything.
