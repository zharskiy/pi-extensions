# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a per-repository container on a Colima VM and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens and the known gaps are in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` runs as a separate Node process against the host pi of host jobs and loads its packages; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `config`, `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `config`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal; the proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), printed as `pi-sandbox: <message>` and `  hint: <hint>` with exit code 1. Any other error exits 70.
- External processes that run to completion (git, gh, glab, openssl, `security`, colima, secret commands, the host pi's jobs) run through the `CommandRunner` interface, so tests replace them with a scripted fake. The two detached children, the proxy daemon (`proxy/start.ts`) and the proxy's host `pi mcp login` (`proxy/sign-in.ts`), start through an injected `spawn`, and the liveness rule reads a start time with `ps` directly (`shared/process-start.ts`).

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs. Node refuses to strip types under `node_modules`, so the published `bin/pi-sandbox.js` imports `../dist/cli/main.js`, which `tsconfig.build.json` emits (`npm run build:launcher`, run by `prepack`). Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, examples, schema, install scripts) stay in `launcher/`, and code finds them through `launcherRoot()`.

## The pipeline

`pi [args]` runs these steps (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir from `cli/context.ts`). The other commands reuse them; `pi sandbox doctor` runs the same preparation and prints each stage, except that it starts a stopped VM without new mounts, never runs the shares stage and never restarts the profile; its read-only `vm shares` line names any needed path the VM lacks.

1. **Discover the workspace** (`workspace/discover.ts`, `workspace/git/layout.ts`). `workspaceFolder` takes the real cwd and walks up to the nearest `.git` without following links; that root, else the cwd, is the folder to mount, and a launch runs the guard (step 5) on it first and loads the config for it (step 2) before any search. Discovery then reads nothing but files and git, and writes nothing. Derive the git dir and common dir from the files alone (a real `.git` dir, a separate git dir, a submodule git dir or a linked worktree), refuse any link or pointer git would not have written, then require `git rev-parse` to agree. Without a `.git` above the cwd the folder is a workspace: one walk finds every nested repository, each checked like a single repository, and fails closed when one cannot be protected or when a git config file the folder reads lies inside it outside every repository. A nested `.git` file whose git dir and common dir all lie outside the folder makes a detached checkout; the `gitdir:` text is resolved as git resolves it (one component at a time, links followed on each existing prefix, the rest lexical from the first missing one, `workspace/paths.ts` `resolvedOnDisk`), and it counts as inside when that path, the lexical path or the real path lies inside: nothing outside is mounted and no git runs for it; the container binds its `.git` file read-only with the folders above it bound onto themselves. A `.git` file whose missing git dir lies outside the folder is detached the same way; one whose missing git dir lies inside the folder, where the sandbox could create it, refuses. A git dir that only partly lies outside (reached through a link in the folder, or an inside git dir with an outside common dir) refuses with `workspace: <repo> uses a git dir outside <root>`. A folder shaped like a git dir (`HEAD` plus `commondir`, or plus `objects` and `refs`, any file type, names ignoring letter case; `workspace/git/layout.ts`) that is not inside a nested repository or one of its git dirs is bound read-only as a whole, with no git call, the folders above it bound onto themselves; a cwd of that shape or inside one refuses. An entry named `.git` in another letter case refuses in strict discovery, in the folder and at a repository root, since git on a case-insensitive volume opens it; the lenient walk treats it as `.git`. Bare dirs, detached `.git` files and masked folders are checked again right before a start (`protectedWorkspaceOverlay`), and one that is missing or changed its kind refuses. A directory the walk cannot read is recorded for a mask (step 10); an unreadable cwd refuses. The same walk collects the build output folders beside their marker files (`workspace/overlay-markers.ts`). With `mounts.autoOverlays` on (the `overlays` option) it does not descend into a marked folder that exists, since its overlay volume hides it; off, it neither collects nor skips, and a single repository then skips the overlay walk. If more than 512 overlays turn every overlay off, the walk runs again without skipping. The lenient walk never skips. Discovery lists each repository's git configuration once (`workspace/git/config.ts`); a listing that fails with git installed refuses, and only a host without git lists nothing. The overlay plan reuses that listing and lists, one git call each, only the config files it could not read (inactive includes, `config.worktree` files, submodule configs). A missing include target or `config.worktree` refuses with the `touch` command that creates it empty in the hint; the launcher creates neither. Admin commands and `--no-sandbox` use a lenient walk without git calls or refusals: inside a repository the layout comes from the files, falling back to the `.git` file's target when the layout checks refuse.
2. **Load the config** from the policy, org, user and project layers for the folder to mount, before the walk, and check `workspaceRoots`.
3. **Intercepted commands** (`cli/intercept.ts`): `install|remove <source>` without `-l`, `mcp add|remove|login|logout` and a bare `update` run on the host and stop here.
4. **`--no-sandbox`** is refused under `fallback: refuse`; otherwise it sweeps the host session directory and execs host pi, mounting nothing.
5. **Guard** (`workspace/guard.ts`): refuse a folder, repository or git dir that is, contains or lies inside a protected path (`workspace/mounts.ts` holds the one table: the home, `~/.pi`, the host agent dir, the state and config dirs, `~/.ssh` and the other credential dirs, system dirs). `assertSafeMounts` runs on the folder to mount before discovery searches it, so the home, a folder under a dotfiles home and `/` refuse at once; after discovery `assertSafeWorkspace` runs it on the repository root and common dir. Lenient discovery skips both.
6. **Open the engine and the VM** (`cli/vm.ts`, `backend/colima/`). The host pi files are read first, and the host side (step 7) starts deriving alongside. The missing host cache dirs and the host session directory are created, then the stopped `pi-sandbox` profile is started when its `colima.yaml` exists, with every needed share it lacks in one start; any needed path the running VM still lacks (repository, git dirs, state dir, extra mounts, host session dir, host caches) is shared by restarting the profile, only when no pi session of any repository is live.
7. **Host side** (`cli/derive.ts`): read the provider host table, derive the sandbox files and the credential rules (`hostpi/`), build the trust bundle whenever the launch needs the proxy, run the orphan sweep, and sign in to MCP servers that need it (`cli/mcp-sign-in.ts`, terminal only, never from `pi sandbox doctor`, which reports `pi mcp login <server>` instead).
8. **Register the launch** (`cli/launches.ts`, `grants/launches.ts`) under the repository launch lock. From here to the end of the session one guard holds SIGINT, SIGTERM and SIGHUP: during preparation the first signal prints `pi-sandbox: stopping after the current step` and ends the launch like a normal exit once the step in flight finishes, and a second signal ends the launcher at once (its launch entry stops counting and the sweep cleans up). While pi runs, signals go to pi alone (`container/run-pi.ts`); during the teardown after pi exits they are ignored until the cleanup finishes.
9. **Proxy and image, in parallel**, alongside rendering the agent dir, planning the git overlay and preparing the host session directory. `ensureRepoProxy` starts or reuses the repository's proxy under the launch lock (see Network). `ensureSandboxImage` reuses the recorded image when a running container uses it, else pulls a pinned digest or builds the image with the host pi's version, then adds the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer.
10. **Container.** Print the launch notices, the private-address notices of rule hosts included, then `ensureContainer` under the container lock: reuse a running container whose identity matches, or, right before a create, pin `commondir`, re-check every protected git path, copy the git config files, create missing mount points and record the nested-repository baseline (every `.git` entry in any letter case and every folder shaped like a git dir, except the read-only bare dirs; the session end reports the new and changed ones). After a create, chown the volume mount points and probe the session share. Then sync `settings.json` into the volume.
11. **Run pi** through exec with the host cwd as workdir and the `env.allow` variables; pi's exit code is the launcher's. Signals go to pi alone through a per-launch pid file (`container/run-pi.ts`), never to the shared container.
12. **End the launch.** Print one line per blocked host from the proxy's denial list, with a hint for its kind: not allowed (`pi sandbox egress allow <host>`, or with grants off, ask the administrator to add it to `egress.allow`), a private address (`egress.privateHosts`), `egress.deny` (denied by policy), plain HTTP (use https), an upstream failure or any other refusal (its reason); remove the launch entry and, when it was the last live launch, run `removeRepoSandbox`, then the git end-of-session notices. `sweepOrphans` runs after either way (see Lifecycle).

### Intercepted commands and host pi

`pi install|remove`, `pi mcp add|remove|login|logout` and a bare `pi update` run the host pi on the host against the host agent dir; `mcp login|logout` run in an empty `<state>/mcp-login-<random>/` folder so no project `mcp.json` loads. `install|remove` also run in such an empty folder, with a local source handed over as an absolute path. A source counts as remote only as a plain `npm:<name>[@version]`, an `http(s)://` or `ssh://` git URL with owner and repository, or `git:git@host:owner/repo` and `git:host.tld/owner/repo`; every other source is a local path, and `install` refuses one inside the repository or workspace, since host pi would load code the sandbox can rewrite. An `npm:` spec that names a path or another protocol (`npm:file:…`, `npm:link:…`, `npm:/…`) is refused too, and so, from inside the repository, are hosted shorthands such as `git:user/repo` and npm aliases.

`cli/host-pi.ts` resolves the host pi in two orders. Host jobs (the proxy's pi command, the provider host table, MCP sign-in, the image's pi version) use pi's managed install in the host agent dir, else the pi installed next to the launcher, searched only inside the launcher's own package and used only when it lies outside the sandbox roots; never a `PATH` pi. `--no-sandbox`, `pi update` and the doctor line add the first `PATH` pi outside the repository, its git dir and `mounts.extraReadOnly` before the bundled one. Nothing records which pi was picked, only what it was used for (the image record's pi version, the proxy input's pi command), so a host pi update rebuilds the image and restarts the proxy at the next launch that is alone in the repository.

## Config

`SandboxConfig` is the merge of the defaults and the policy, org, user and project layers (`config/`). Each layer is validated by a hand-written key spec; `schema/sandbox-config.schema.json` documents the same keys, and tests keep the key sets and the string constraints equal. Two kinds of keys (`config/merge.ts`, which takes its leaf keys from the validator spec). A validation message names the key and, for paths, names and choices, the value (cut at 200 characters, JSON-escaped when not printable); host, credential, `org` and `npmGlobal` values are never shown. Union keys (`egress.allow`, `egress.deny`, `egress.privateHosts`, `image.packages`, `credentials.rules` and `env.allow`) collect the entries of every layer that may set them, so a lower layer adds entries and none removes one; a rule whose id a higher layer already uses is ignored, and `egress.deny` still wins over every allow. Every other key is final once the policy or org layer sets it (`fallback`, `egress.grants`, `egress.parentProxy`, `egress.presets`, `tls`, `sessions`, `credentials.derive`, `resources`, `mounts.hostCaches` and the rest). A project layer may set only `mounts.cacheVolumes`, `mounts.autoOverlays`, `resources.cpus` and `resources.memoryGiB` (an allowlist the merge enforces too), so it adds no rule, host, private host or package. A key a project may not set, or a final key a lower layer sets, is ignored rather than fatal: the merge keeps the higher value and the launch prints one warning naming every ignored key with its layer, once per repository and text (the notice store), and `pi sandbox config` lists them each time. `org` names a local file read at every launch as the `org` layer. `egress.presets` expands to registry hosts ahead of `egress.allow` (`config/egress-presets.ts`). The `pi-sandbox` command never writes a config layer; `install.sh --org` writes the user layer's `org` key.

## Backend

Colima is the only engine. A `Backend` (`backend/types.ts`) is the only thing that talks to it, and the seam tests replace with a fake. `backend/colima/` speaks the engine HTTP API over `~/.colima/pi-sandbox/docker.sock` with `node:http`, and owns the VM as `Backend.vm` (start, shares, size, stop). It pulls by digest, builds through the classic build endpoint, creates containers with `AutoRemove` and typed mounts (a missing bind source fails the create), runs execs over a hijacked stream with backpressure, manages labelled volumes, networks and relays, and imports only `shared`. Requests other than builds, pulls, execs and waits give up after 30 s without an answer, removals after 10 minutes and the ping after 5 s; only an unanswered ping advises restarting the VM, and the error names the request. Two launches of one repository may route at once: the network is created once, and a launch waits up to 15 s for a relay another launch created, or for its own dropped relay to be removed before it creates the replacement once more. A conformance suite runs the same tests against the adapter on an in-process engine, against the fake backend, and against the real engine in the live tests.

## Network

- **Per-repository proxy.** One proxy process per repository, `proxy/daemon.ts` (`dist/proxy/daemon.js` in a published install), on `127.0.0.1` of the host. It reads its `RepoProxyInput` (allow and deny lists, rules, derived hosts, `env` secret values, parent proxy and its credentials) from stdin only, and records `{ pid, boot, start, port, inputHash }` in `repos/<hash>/proxy/proxy.json`. The launcher starts it with `repos/<hash>/proxy/` as its working directory, waits up to 10 s for its health check, and on failure quotes the daemon's own tagged line (`pi-sandbox-proxy failed: …`) from `proxy.log`. A live proxy with the same input hash is reused once its health check answers, within three tries; one with another hash is replaced only when no other launch of the repository is live.
- **Token.** The guest proxy URL is `http://pi-sandbox:<token>@pi-sandbox-proxy:3128`. The token (`repos/<hash>/proxy/token`, 32 random bytes) identifies the repository to its proxy, which answers `407` to anything else. It survives proxy restarts and is deleted with the container. The container carries a hash of it, so a new token gives a new container.
- **Relay and alias.** Agent containers join only their repository's internal network `pi-sandbox-<h12>` (the first 12 hex of the repository hash) and have no route out. One relay container per repository, `pi-sandbox-relay-<h12>`, sits on that network with the alias `pi-sandbox-proxy` and on the default bridge, and forwards with socat to the proxy port on `host.lima.internal`. It is recreated under the same name and alias when the proxy port changes, so a running container keeps reaching its proxy by name.
- **Decisions.** A CONNECT is allowed for allowlisted, rule, derived and granted hosts on their ports; `egress.deny` wins, where an entry `d` denies `d` and every name under it and `*.d` every name under `d`. A CONNECT to port 80 and a plain HTTP request are refused as `plain-http`, naming the host. IP literals, loopback, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused unless named in `egress.privateHosts`. A tunnel that is not terminated must present a ClientHello whose SNI equals the CONNECT host before the proxy dials. A denied host gets a 403 page over TLS with a launcher-CA certificate for its name, carrying the grant hint. A terminated request whose upstream fails answers `502` with the reason; a certificate failure adds a pointer to `tls.extraCa`, and the doctor counts a `502` as failed. Grants are read live from `grants.json`. Every decision is a JSON line in `access.log` carrying the repository hash, including requests without the token; an allow names the rule that allowed it (`egress.allow`, `credential`, `grant-or-derived`, and `terminate` for a terminated tunnel), an unavailable credential the resolver's reason. No line holds a credential or a token.
- **Termination.** TLS is terminated only for rule hosts, with per-host leaves signed by the launcher CA and kept in memory. Upstream connections are pooled per host, port and access inside the repository's own process, so never shared between repositories. A parent proxy (`egress.parentProxy`) is chained for upstream dials; an `HTTPS_PROXY` that is not an `http://` URL is not used, and the launch warns and the proxy connects directly.

## Placeholders and secret sources

A placeholder is `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`; so placeholders are stable across launches and unguessable. A JWT access token is replaced with a JWT-shaped placeholder. On a terminated host, the proxy replaces the placeholder of the matching rule (host, port, decoded path prefix compared with the decoded path, which carries no query, so an encoded `?` cannot widen it) only in the rule's header, or in auth-like request headers for a rule without one, and strips stray placeholders from every other header; never in a query or body. A `Basic` value is decoded, substituted and re-encoded, which is how git, npm, pip and Maven send passwords. Response headers are scrubbed of the secret and of the exact base64 the proxy sent. A dot-segment path or a cross-origin absolute target gets `400`.

The secret comes from a source resolved on the host and kept in the proxy's memory only (`proxy/secrets/`): `env` (from the stdin input), `file` (a JSON pointer, or a key of an npmrc, ini or Maven settings file), `command` (stdout or `{ token, expiresAt }`, cached; 30 s per run, a failed one retried at most every 5 s), `piAuth` (the host pi's `auth print-api-key` or `print-bearer-token`) and `mcpOAuth` (below). An upstream `401` invalidates a cached secret once. A failed lookup is retried at most every 5 s, except a sign-in reply (`503`), which is never cached, so a sign-in finished on the host is used by the next request.

Derivation (`hostpi/`) is pure: it turns the host `auth.json`, `models.json` and `mcp.json` into sandbox copies with placeholders and rules, and `hostpi/derive-tools.ts` adds the gh, glab, npm, pip, Maven and git derivers (`hostpi/tools/`), which read host files and run host commands and render placeholder-only tool files. gh, glab and git run only from absolute `PATH` entries outside the repository, its git common dir and `mounts.extraReadOnly`, each probe with a 10 s limit (the glab token probe and the provider host script 30 s; a probe that does not answer, a Keychain prompt for example, leaves that tool without credentials for the launch, with a notice); a `GH_CONFIG_DIR`, `GLAB_CONFIG_DIR`, `XDG_CONFIG_HOME` or `PIP_CONFIG_FILE` path inside those roots is ignored with a notice. A URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`, `PIP_INDEX_URL`) is rendered with a placeholder in place of the password, or of the user name when the token is the user name, and gets a rule on that host (for npm also the URL path) whose secret reads that part of the URL back from the host file or variable (`urlPassword`, `urlUsername`). Other values with URL userinfo, npm and pip proxy settings, and values that reach userinfo through `${VAR}` stay on the host; Maven mirror URLs lose their userinfo. The Maven settings keep `profiles`, `activeProfiles`, `pluginGroups` and the mirrors, with secret-looking profile properties and URL userinfo removed and `localRepository` dropped with a notice; a server's password and its `httpHeaders` values become placeholders bound to the server's repository hosts (a header rule injects only in that header), a server with no credential field is copied unchanged, and one with only a private key stays on the host. The pip config is the first of `PIP_CONFIG_FILE`, `~/.config/pip/pip.conf`, `~/Library/Application Support/pip/pip.conf` and `~/.pip/pip.conf`. A `models.json` provider or model whose `baseUrl` has a secret-looking query parameter is dropped, as an MCP server is. Manual `credentials.rules` win over derived rules for the same host; `credentials.derive` filters or disables derived ones.

## MCP sign-in

MCP OAuth tokens stay in host pi's `<agent dir>/mcp-auth.json`, which the launcher only reads (`shared/mcp-auth-key.ts` is the one parser). The sandbox `mcp.json` has no `oauth` block, and an HTTP server without an `Authorization`, `Cookie` or secret-named header, and without a header read from a variable (`$…`) or command (`!…`) or shaped like a credential, whose name host pi can sign in to (`[A-Za-z0-9_-]`) gets a placeholder bearer with an `mcpOAuth` rule. Two triggers start `pi mcp login <name>` with the host pi of host jobs, in an empty folder against the host agent dir:

- at launch start, from a terminal, for each derived server whose token is missing or expired and has no refresh token (`cli/mcp-sign-in.ts`), interactively;
- in the proxy (`proxy/sign-in.ts`), when the token it would inject is missing, expired, or answered `401` upstream; a `401` to a request with the container's own `Authorization` starts nothing. The login runs in its own process group, recorded as `{ pgid, boot, start }`, which the proxy kills when it stops; the request gets a local `503` telling the user to finish the sign-in in the browser.

Both take one lock per server and record starts and failures in `<state>/mcp-login.json`, which is written under its own file lock. The proxy starts at most one sign-in per server per minute host-wide and none for 10 minutes after a failure; a start caused by a `401` to a token the proxy injected and that has not expired runs at most once per server per 10 minutes whatever its exit code (`rejectedStart`). The launch-start sign-in runs once per launch and is skipped for 24 hours after a failed sign-in by either path, printing `not signed in; run pi mcp login <name>`. Host pi's login refreshes a stored token silently when it can.

## Provisioning

`renderAgentDir` (`provision/render.ts`) writes `repos/<hash>/render/` on every launch: the derived `auth.json`, `models.json` and `mcp.json`, filtered copies of the host agents, prompts, skills, themes, extensions and instruction files (secret-looking files and directories named `secrets`, `.secrets`, `credentials` or `.credentials` outside `node_modules` left out, the directories with a notice, no link followed), and `tools/` (the Maven settings with the sandbox proxy and derived servers, and when derived the gh, glab, npm, pip and git configs). It is mounted read-only; the entrypoint links each entry into the agent dir and the tool files into the home, copying the ones the tools must write. `syncSettingsFile` (`provision/sync.ts`) writes the host `settings.json` keys over the volume copy, dropping package URL credentials and the host `httpProxy` (the sandbox uses the launcher proxy) and leaving the host-owned keys (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`) and `sessionDir` out of the sandbox copy, since they name host binaries and paths. Nothing from the volume is written back to the host.

## Host sessions

With `sessions.host` on, the container binds host pi's session directory of the repository at its host path and `PI_CODING_AGENT_SESSION_DIR` points pi at it. The slug is pi's formula, copied since the launcher may not import pi. `assertHostSessionsDir` (`workspace/guard.ts`) is the one exception to never mounting under `~/.pi`: the directory must be exactly one level under `<agent dir>/sessions`, a real directory, and overlap no other agent dir entry. `provision/host-sessions.ts` creates missing directories 0700, probes the share from inside, and sweeps the directory before each launch, after pi exits and before `--no-sandbox`: it deletes links and special files and renames session files whose header `cwd` lies outside the repository (or cannot be read) to `.rejected-<random>`, reading headers as pi does. The whole tree is swept only while no container of the repository runs, under the launch lock.

## Container

A container belongs to one repository (in workspace mode, the workspace root): name `pi-sandbox-<h12>`, labels with the repository, image digest, proxy token hash, git common dirs, the spec hash and one hash per spec section (config, image, credentials for the environment and token, overlays for the volumes, mounts for the binds). `ensureContainer` reuses a running container whose image digest, spec hash and proxy token hash match; one that differs is replaced only when no other session of the repository is live, else reused with a notice that names the sections whose hash differs from the running container's. Containers run with `AutoRemove`, so none is ever stopped and kept.

The spec mounts the repository and git common dir read-write at their host paths, binds onto themselves the git dir and every directory between the root and a read-only path (so none can be renamed away from its mounts), then the read-only git paths (hooks dirs, `commondir`, `gitdir`, a `.git` file, worktree pointers) directly from the host after the `ready()` checks, and `config` and `config.worktree` from private copies. It adds `mounts.extraReadOnly`, the agent volume, cache and overlay volumes, shared cache volumes, host caches (cache subfolders of the home only, bound read-write after the same protected-path checks and a refusal of top-level credential files), the render dir and the trust bundle. A `mounts.cacheVolumes` or shared cache target inside a git dir or a read-only mount is refused; a build output overlay found there is left out with a notice (`<path> is not overlaid: it lies inside <guard>, which the sandbox protects`). Each unreadable folder of a workspace gets a read-only bind of the empty `<state>/empty/` onto it (created with the host paths in step 6), so the sandbox can neither list it nor `chmod` it open. The spec then refuses (`workspace: the sandbox could write in <dir>, which the launcher did not search for repositories, refusing`) when, for an overlay folder or a masked one, the mount with the longest target over it is not a volume or a read-only bind, or a writable bind has its target or source inside it (targets compared normalised; `mounts.extraReadOnly` targets are normalised where they are resolved): a writable bind that lies inside, or re-exposes, a folder the walk skipped or masked. Mount points are checked by real path before each directory is created, so no spelling (case, links) creates one inside a protected path. The agent volume is named from the host account name. The root is read-only with tmpfs `/tmp` and `/home/pi` (exec allowed), under an init process, as the image's `pi` user. The environment holds the proxy variables with the token, the JVM proxy flags (`JAVA_TOOL_OPTIONS`) and Maven proxy variables, the CA bundle paths, the derived tool variables (`GH_TOKEN`, `GITLAB_TOKEN` placeholders), `GIT_TERMINAL_PROMPT=0` and `PI_SANDBOX=1`, with `NO_PROXY` and `no_proxy` set to `localhost,127.0.0.1,::1` so a client reaches the container's own servers directly; no host variable is in the spec, so the terminal does not change its hash.

## Image

`image/Dockerfile` builds on a slim Node image with git, search tools, socat, curl, jq, python3, gh and a pinned, checksum-checked glab, a `pi` user and pi pinned to the host pi's version. It bakes no pi config, package or credential. The launcher CA goes into the system store for good; extra CAs are trusted during the build only. `BASH_ENV` and the first line of `/etc/bash.bashrc` source `bash-env.sh`, which prints the missing-command hint and adds the JVM truststore flags. The entrypoint re-creates the render links, builds the CA bundle and, when `java` is present, a JVM truststore, then idles under the engine's init (`sleep infinity`). A failed build's error keeps the last 30 lines of the build output, and a certificate error in them adds the hint to set `tls.extraCa` or `image.digest`. The host's `HTTP_PROXY` and `HTTPS_PROXY` reach the build as build args, with a loopback host (`127.0.0.1`, `localhost`, `::1`) rewritten to `host.lima.internal`. `image.dockerfile` may start with `~/`. `ensureSandboxImage` runs under `<state>/locks/build.lock`, so two launches never build at once; the second says it waits. Build contexts and their archives live under `<state>/build/` and are removed after the build; the sweep clears what a killed build left while no build holds the lock. `ensureSandboxImage` records the base image in `<state>/image.json`; layer images are tagged `pi-sandbox-layer:<hash of the layer Dockerfile>` (packages sorted and deduped, so their order does not change the tag) and reused while the inputs stay the same, and each repository records the tag it wants. After a build the unreferenced layer tags and the previous base are removed; the daily collection removes unreferenced layers and untagged managed images older than an hour, never an image a container uses or a layer a repository records, and skips while a build holds `build.lock`.

## Locks and liveness

`shared/file-lock.ts` is the one lock primitive: the repository launch lock (launch registry, proxy start and idle exit, sweep), the container lock, the grants, the CA, the settings sync, the per-git-common-dir pin lock and the per-server MCP sign-in lock. A lock file holds `<pid> <boot time> <process start> <nonce>`. The liveness rule (`shared/liveness.ts`) applies to locks, launch entries and `proxy.json`, and it is process identity, never a timer: a holder is live when its pid exists, the boot time matches and the process start time (`ps -o lstart=` on macOS, field 22 of `/proc/<pid>/stat` on Linux, read by `shared/process-start.ts`) is the recorded one. A running pid counts as live when the start-time tool itself failed, and as dead when no start time is obtainable for that pid (another user's process, `/proc` hidden). A sleeping Mac or a stopped launcher therefore keeps its sandbox, and a pid reused by another process after a reboot or an exit does not count. A lock that is not live is taken over, one taker at a time, with a check that it did not change in between; a waiter that finds the takeover guard busy waits and keeps its timeout. A live holder is waited for: the repository launch lock, the container lock and the pin lock wait up to 120 s, then the waiter fails and asks to run the command again; there is no "delete the lock" advice, since a dead holder's lock is taken over anyway. The VM lock is an `mkdir` lock judged by age, so a share restart, a VM start (the engine check after a failed detection included) and `pi sandbox stop` never interleave.

## Lifecycle and sweep

- A launch registers an entry (`pid`, boot time, process start) under `repos/<hash>/launches/`; the sweep deletes the entries of dead launches. Every removal path runs under the repository launch lock and re-checks the live launches first; an entry is deleted only when its process is gone. `pi sandbox reset` refuses while a session of the repository runs and names how many.
- **Records first.** Each `commondir` pin goes into `pins.json` and each folder the launcher makes in the repository (hook dirs, mount points) into `created.json` (the ones that protect git, hook dirs included, also into `created-git.json`) right after it is written, before the next check can refuse, so a refused launch leaves nothing the sweep does not know; a pin already present (an empty one discovery filled in place, or one whose record was lost) is recorded too before a create. The session-share probe runs under the container lock right after the create and discards only the container it just made.
- **Last session.** `removeRepoSandbox` (`cli/sweep.ts`) removes the container (waiting for the engine's auto-removal) and the relay together, then the repository network, while it stops the proxy and deletes the token; then the recorded `commondir` pins (only while they read `.` and no other sandbox shares the git dir), the recorded created folders (deepest first, only empty real directories; one inside a git dir, or recorded as protecting git like a `core.hooksPath` dir in the working tree, only under the pin lock of its own common dir, recorded with it, and while no other sandbox shares that dir; one whose owner is unknown is kept while the repository has no pin or any of its pinned common dirs is in use), the git config copies, then sweeps the whole host session directory. Pins and the git-protection folders are kept while the engine does not answer (except under `pi sandbox stop`) or its removal fails. When the engine is unreachable the engine steps are skipped and the rest still runs. The git checks after the last session run after the lock is released, since they write nothing.
- **Proxy idle exit.** The proxy checks the live launches under the launch lock and exits after two empty checks, stopping any sign-in it started.
- **Sweep.** `sweepOrphans` runs at every launch start and end, at `pi sandbox gc` and, without the engine, at `pi sandbox stop` (and at `gc` or `reset` while the VM is stopped, which then say the engine step was skipped): it runs `removeRepoSandbox` for each repository with leftovers and no live launch, and forgets a repository whose folder is gone, and one known only from engine labels once its engine side is removed. A folder counts as gone only when `stat` reports it missing, its parent directory exists, and `repo.json` did not record it as a mount point; when the parent is missing too (a disk that is not mounted), the repository's state, pins, container and volumes are all kept. Once a day (`gc.json`, written only when the engine answered) it also removes volumes of deleted repositories and unused images.
- **kill -9.** A killed launcher's entry stops counting at once, since its pid is gone, and its proxy idles out within a minute; its container, relay, network, token, pins and created folders stay until the next launch of any repository, `pi sandbox gc`, `pi sandbox stop` or the uninstall. A VM restart removes containers and relays.
- **Uninstall.** `bin/uninstall-engine.mjs --host-side` refuses while a launch is live, else releases every repository's pins, created folders, live proxy and the sign-in groups whose recorded start still matches, before the engine objects (removed with the profile, and through the engine only with `--keep-vm`, without a profile, or when `colima delete` fails, which then exits 1 naming the command to run), the Colima profile and the state dir go.

## Invariants

- No real secret in the container's filesystem, environment or volumes; derivers and renderers take placeholders only, and `tests/support/expect-no-leak.ts` checks specs, exec argv, env, stdin and render files.
- The container's only network path is its repository's proxy; SNI check and private-range deny are always on.
- Nothing is mounted from a protected path; the git code host git runs is read-only inside.
- A project file cannot add hosts, mounts, credentials or images.
- Every removal re-checks liveness under the repository launch lock, so a live sandbox is never removed.
- Every file the launcher writes is listed below and removed when no longer needed, except the user's caches and sessions.

## Alternatives considered

- A published, pinned image instead of a local build: rejected, so the sandbox runs the same pi version as the host.
- An unauthenticated proxy shim inside the container: rejected; JVM flags and rendered tool settings cover most clients, and the rest is a documented gap.
- One shared proxy per policy: replaced by one proxy per repository, so rules, env secrets and tokens never cross repositories.
- A second engine, Docker Desktop, or a host process under Seatbelt or OpenShell: not taken; Colima is the one engine, and a container keeps credentials out of reach by construction.

## Tests

Tests check behaviour through public entry points with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server, a fake backend, temp dirs, real localhost sockets and openssl certificates. The CLI tests run whole commands against the fake backend. Tests that run real git go through `tests/support/git.ts`, which keeps the developer's git config out. Live tests against the real Colima engine run only with `PI_SANDBOX_LIVE=1` and fail when their cleanup had to remove anything.
