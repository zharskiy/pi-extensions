# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a per-repository container and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens is in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` is run as a separate Node process against the pi installed next to the launcher and loads its provider list; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else, which `test/architecture.test.ts` asserts.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `config`, `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `config`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` (its own folder) and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only, and imports nothing from the per-folder test suites. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal. The proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), reported as `pi-sandbox: <message>` and `  hint: <hint>` on stderr with exit code 1 and no stack trace. Any other error is `pi-sandbox: unexpected error: <message>` with exit code 70.
- External processes run through the `CommandRunner` interface, so tests replace them with a scripted fake: git (workspace discovery, `core.hooksPath`, the checkout `HEAD`), npm (`npm pack`), tar (the build context), openssl (the launcher CA), `security` (keychain credentials and the host CA store), `ps` (checking a proxy pid before killing it), the Apple `container` CLI, secret `command`s, the bundled pi (`auth print-api-key`, `mcp login`, `mcp list`) and `hostpi/provider-hosts.mjs`.

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs.

Node refuses to strip types under `node_modules`, so the published command runs compiled JavaScript. `tsconfig.build.json` emits `dist/` with relative `.ts` imports rewritten to `.js`; `npm run build:launcher` builds it and `prepack` runs that. `bin/pi-sandbox.js` imports `../dist/cli/main.js`. Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, profiles, examples, schema, install scripts) stay in the `launcher/` folder and are published from there (`tsc` does not copy them into `dist/`, and nothing looks for them there), so code finds them through `launcherRoot()` (the `launcher/` folder in either layout) and runnable entries through `launcherEntry()`, never relative to its own compiled file.

## The pipeline

`pi [args]` runs these steps, each a function the other commands reuse (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir):

1. Discover the workspace: `git rev-parse --show-toplevel --git-common-dir` from the cwd, real paths. Outside git the repository is the cwd.
2. Load the effective config from the layers (policy, org, user, project), print the org layer's notices, check `workspaceRoots`: the repository and its git common dir must be inside the roots (a linked worktree whose main repository is outside is refused); `outside: warn` prints a warning instead.
3. Intercepted commands (`cli/intercept.ts`, routed by `run.ts` before the pass-through and never with `--no-sandbox`): `install|remove <source>` without `-l`, `mcp add|remove`, `mcp login|logout <name>` with pi's own flags (`-l`, and `--timeout <seconds>` for login) and a bare `update`; see [Intercepted commands](#intercepted-commands).
4. `--no-sandbox`: refused under `fallback: refuse`, naming the layer; otherwise exec the first host `pi` on `PATH` that is not the launcher.
5. Refuse a workspace that would mount too much (`workspace/guard.ts`, regardless of `workspaceRoots`): a repository root or git common dir that equals or contains `$HOME`, `~/.pi`, the launcher state dir, the user config dir, or `/`, or that lies inside `~/.pi`, the state dir or the config dir. The config dir is protected only when it is the default `~/.config/pi-sandbox`; with `PI_SANDBOX_USER_CONFIG` elsewhere only that file is, so a repository equal to or containing it is refused and its siblings are not. A dotfiles repository rooted at `$HOME` is the case this catches. The hint is `run pi inside a project directory`.
6. Select the backend (`auto` tries Colima, then Apple `container`). The error lists every adapter and why it is unavailable, and suggests `--no-sandbox` when the fallback is `host`.
7. Host side (`cli/derive.ts`): read the host pi files (`readHostPiFiles` of `PI_CODING_AGENT_DIR` or `~/.pi/agent`), seed MCP OAuth tokens (`seedMcpAuth`), read the provider host table through the bundled pi (`readProviderHosts`), `ensureSalt`, and `deriveSandboxPi` with the manual `credentials.rules`, the legacy gateway and `credentials.derive`. Print its notices and `privateHostNotices`. The proxy is needed when a gateway, an allowlist, MCP hosts or any rule exists; the trust bundle (`ensureTrustBundle`: the launcher CA plus `tls.extraCa`) is built when the proxy is needed and a rule or an extra CA exists.
8. Register the session (`registerSession`, under the repository's lock) with a fresh launch id.
9. Proxy (`cli/sandbox-proxy.ts`): `ensureProxyRunning` with the config, the D3 `egressCap` and the bundled pi command; a proxy that cannot start stops the launch. `repoProxyToken` gives this repository's token, `writeProxyDynamic` records the derived rules, the derived hosts and `sha256(token) -> repo hash`, and `sendProxyControl` hands over the `env` secrets (rules whose secret is `{ env }`, and `egress.parentProxy.auth`), resolved from the launcher's environment.
10. Image: the hot path reads `<stateDir>/image.json` and, when `findCurrentContainer(backend, workspace, digest, configHash)` finds this repository's container with that digest and config hash, skips the base build; the cold path prints `preparing pi sandbox, one time`, resolves the extensions source and runs `ensureBuiltImage` (with the extra CAs and the parent proxy for the build). `ensureLayerImage` then adds the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer, or returns the base id when there is none. The container is created from the layer id; its digest label stays the base digest.
11. Container: `renderAgentDir` writes `<state>/render/<repo hash>/`, `backend.prepareProxyRoute(port, policyHash, imageId)` gives the guest's route, `guestProxyUrl(route, repoToken)` the proxy URL, and `buildContainerSpec` adds the render mount, the trust mount and `PI_SANDBOX_TRUST_HASH`. `ensureContainer` reuses or replaces the container; when it created one, `pruneGrants` drops session grants of ended launches. `syncWritableFiles` then merges the host `settings.json` and the derived `mcp.json` into the volume (a failure is a warning, not a stop).
12. Exec pi in the container with the host cwd as workdir, the `env.allow` host variables and `PI_SANDBOX_LAUNCH_ID` as the exec's environment, and return pi's exit code.
13. When pi exits: `readDenials` (`GET /denials?since=<launch start>` with the repository token) prints one stderr line per blocked host, and `endSession` removes the session and, under the same lock, stops the container (`stopIdleContainer`) when no live session of the repository remains (D2). A session whose launcher pid is dead does not count, so a crashed launcher never keeps a container alive.

`pi sandbox doctor` runs the same steps one by one, so it builds the image and creates the container, then runs its probes through execs into it (`container/probes.ts`, `cli/commands/doctor-container.ts`) and its host checks (`cli/commands/doctor-host.ts`). A container the doctor created is removed when it ends. Rendering stays in `cli/commands/doctor.ts`.

### Intercepted commands

- `pi install|remove <source>` without `-l` runs inside like any launch, around a read of the volume `settings.json` before and after. On exit 0, `packageChangeFor` finds the change for that source only and `writeBackPackageChange` applies it to the `packages` key of the host `settings.json` (atomic, other keys and the indent kept). A local path outside the repository, its git dir and `mounts.extraReadOnly` exists only inside and is not written back.
- `pi mcp add|remove ...` runs the bundled pi on the host with the host agent dir.
- `pi mcp login|logout <name>`: `mcpLoginServer` takes the server from the host user `mcp.json`, or from the repository's `.pi/mcp.json` after a y/N on the terminal; `prepareMcpLogin` records the sanitised `{ url, oauth }` in `<state>/mcp-auth/servers/<name>.json` and writes the one-server `mcp-auth/mcp.json`; the bundled pi then runs `mcp login <name>` there with `PI_CODING_AGENT_DIR=<state>/mcp-auth`, passing `--timeout` through and dropping `-l` (the helper dir has no project file). Logout uses the recorded server (`oneServerDir`).
- A bare `pi update` prints `pi follows the launcher; update it with npm install -g pi-extensions-mz`; `pi update <target>` and `pi update --extensions` pass through.

The bundled pi is `locateBundledPi()`: `@earendil-works/pi-coding-agent` found in a `node_modules` folder at or above the launcher, run as `[process.execPath, <bin>]`. Without it, `cli/host-pi.ts` falls back to the host pi on `PATH`.

### Signals

`runPi` (`container/run-pi.ts`) puts a tty stdin in raw mode, so Ctrl-C reaches pi as a keystroke. It listens for SIGTERM and SIGHUP, and for SIGINT only when stdin is not a tty. Pi runs as `sh -c 'echo $$ > /tmp/pi-sandbox-<launch id>.pid; exec "$@"' sh pi <args>`, with a random hex launch id per `runPi` call. On one of the signals it runs `kill -TERM "$(cat <pid file>)"` inside the container through `backend.exec`, waits up to five seconds for pi's exec to end, stops the container (two-second timeout) only if it has not, restores the terminal and returns `128 + signal number` (130, 143, 129). Afterwards it removes the pid file, best effort. Only pi gets the signal, so the container's idle process keeps running and the next `pi` reuses the container.

## Config

`SandboxConfig` is the merged result of the defaults, the profile, and the policy, org, user and project layers. Each layer is validated by a hand-written key spec (precise `<layer>: <key> <problem>` messages); `schema/sandbox-config.schema.json` documents the same keys, and a test keeps the two key sets equal.

The merge has two kinds of keys. Security keys (`egress.allow`, `egress.mcpHosts`, `credentials`, `mounts.extraReadOnly`, `fallback`, `workspaceRoots`, `ssh.agent`, `image.digest`, `image.reference` while a digest is pinned above, `gateway`, and `backend` when policy sets it) may only be tightened by a lower layer: lists may lose entries, `refuse` stays `refuse`, `ssh.agent: false` stays off, roots may only narrow, a value set above cannot change. The project layer is locked by everything above it, including the defaults and the profile, so it can never turn `ssh.agent` on; the user layer is locked by policy, and by the profile when policy chose it. A violation is a `LauncherError` naming the locking layer.

Three keys are host-only: a project layer that sets `env.allow`, `image.reference` or `image.digest` is refused when it loads, with a `LauncherError` naming the file. Above the project, `env.allow` is the union of the policy and user layers, and secret-looking names (the shared `isSecretName` predicate, also used by the doctor's credential sweep) are refused. Convenience keys take the lowest layer's value; `resources` (`cpus`, `memoryGiB`) merges per subkey.

Egress entries are `host`, `*.domain`, `host:port` or `*.domain:port`. `fallback` is `refuse` or `host`. `PI_SANDBOX_POLICY_FILE` is honoured only when the default policy file does not exist, so a user environment cannot hide a real policy; `PI_SANDBOX_STATE_DIR` and `PI_SANDBOX_USER_CONFIG` always apply.

The org layer (`config/org-source.ts`) is named by `org` in the policy layer, else the user layer: an HTTPS URL (fetched with `node:https`, the system CAs plus `NODE_EXTRA_CA_CERTS`, three-second timeout) or an absolute path, cached in `<state>/org/baseline.json` with `meta.json` (`source`, `fetchedAt`, `sha256`), refreshed when older than `refreshHours` (24 by default), and validated as layer `org`. A failed fetch keeps the cache and returns a notice, which `cli/` prints; a pinned `sha256` that does not match refuses the new copy and, without a valid cache, the launch. Lockers: the project is locked by everything above it; the user by policy, org, and the profile when policy or org chose it; org by policy, and the profile when policy chose it. The new keys follow tighten-only rules: `credentials.rules` may only drop rules, `credentials.derive.enabled`, `egress.grants.enabled` and `.permanent` may only turn off, `egress.grants.maxHours` may only shrink, `credentials.derive.hosts`, `egress.privateHosts` and `tls.extraCa` may only lose entries, `egress.parentProxy` and `org` cannot change, `egress.deny` is the union, and `image.packages`, `npmGlobal` and `dockerfile` take the lowest layer. `config/rule-cap.ts` applies the derived-host cap to `credentials.rules` too when the config loads: a rule from a layer other than policy whose host and port no cap entry matches is dropped with a notice. `EffectiveConfig.egressCap` (D3) is the intersection of the `egress.allow` lists of policy and org, for derived hosts unless that layer sets `credentials.derive.enabled: true` and for grants unless it sets `egress.grants.enabled: true`; it goes to the proxy and into the policy hash. `setConfigValue` resolves the same four layers, so `config set` honours org locks.

The merge also records the source layer of every dotted key, which `pi sandbox config` prints. `setConfigValue` applies a change to one layer, validates and lock-checks the result against the layers above, and writes nothing when refused. `configHash` is the sha256 of the key-sorted JSON of the effective config (`stableHash` in `shared/`), so every security key, `ssh.agent` included, changes it.

## Backend contract

A `Backend` is the only thing that talks to a container runtime. It detects itself, pulls images by digest (`pullImage(reference, digest?)`, which pulls `repo@digest` when a digest is given and verifies it), looks images up locally (`resolveImage`), builds them (`buildImage`), all returning `ImageInfo { id, digest }`; it finds, creates, starts, stops (`stopContainer(id, timeoutSeconds?)`) and removes containers, runs an exec (`exec(ExecSpec, ExecIo)`: stdin, separate stdout and stderr, tty, size and `onResize`), manages volumes, exports and imports them through a helper started from an image id the caller passes (`exportVolume(name, tarPath, imageId)`, `importVolume(name, tarPath, imageId)`), prepares the guest's proxy route and reports a status map. Specs are runtime-agnostic: `ContainerSpec` (image id, mounts, `NetworkRef`, env, user, read-only root, tmpfs, init, resources, labels, and `sshAgent: { guestSocket }` when the agent is forwarded) and `ExecSpec` (container, command, env, workdir). The image id is opaque: on Apple it may be a `repo@digest` string.

Each backend declares `BackendCapabilities`, which the container spec and `status` read instead of branching on the backend name:

| capability | docker-engine (`colima`) | apple |
| --- | --- | --- |
| `singleFileMount` | yes | no |
| `sshAgent` | when a Colima profile is detected (bind mount of the forwarded agent socket) | yes (`--ssh`) |
| `internalNetwork` | yes | yes |

- `backend/docker-engine/` is the adapter behind the backend name `colima`. It speaks the Docker Engine HTTP API over a Unix socket with `node:http`. The socket is `DOCKER_HOST` (unix), then `~/.colima/pi-sandbox/docker.sock`, `~/.colima/default/docker.sock`, `/var/run/docker.sock`; `status()` reports it. Exec is a hijacked `Upgrade: tcp` stream with raw stdin and demultiplexed stdout and stderr frames; the exit code comes from exec inspect. Volumes carry `pi-sandbox.managed` and are exported and imported as tar archives through a helper container, created from the given image id and never started. Builds use the legacy build endpoint, so the Dockerfile avoids BuildKit-only syntax.
- `backend/apple/` drives the `container` CLI through the `CommandRunner`; a tty exec uses the host terminal directly through an interactive spawn, a non-tty exec pipes `ExecIo`. Its ssh agent comes from `--ssh`. Every flag and JSON shape it relies on is kept in one table so it can be corrected against a real host.
- `backend/image-reference.ts` splits references into repository and tag and builds `repo@digest`.

A conformance suite runs the same behaviour tests against both adapters on fakes (an in-process engine HTTP server, a fake `container` CLI) and against a real engine in the live tests.

## Network: proxy instances and relays

There is one proxy instance per policy hash (`proxyPolicyHash(config, egressCap)`: allowlist, MCP hosts, deny list, manual rule hosts, gateway settings, credential source, private hosts, parent proxy, grant limits, extra CAs and the D3 cap), so two repositories with different policies never share a proxy. What changes with host files (derived rules and hosts) lives in `dynamic.json` instead, so a host-file change never recreates a container or restarts a proxy.

Each instance has a control token (32 bytes, hex) in `proxy-token` (mode 600), which only the launcher holds: it authenticates `POST /control` as `Basic base64("pi-sandbox-control:" + token)`. Each repository has its own token in `tokens/<repo hash>` (mode 600, created once by `repoProxyToken`), which the guest gets in its proxy URL, `http://pi-sandbox:<repo token>@<route address>`; the proxy maps it to the repository hash (the token files, and `dynamic.json` `tokens`, keyed by `sha256(token)`), and answers `407` to any request without a known one (a repository token on `/control` gets `407` too). Restarting the proxy keeps both tokens, so the container's proxy URL and spec hash stay. They rotate only when the instance directory goes: `pi sandbox reset` removes the instance of the repository's policy hash (`removeProxyInstance`) unless a running container of another repository carries that `proxy-policy-hash` (`policyHashesInUse`, the same check `collectGarbage` uses). A token only proves which repository's container a request comes from; it is not a credential for anything else, and it never appears in the proxy's logs.

Agent containers have no route out. With the docker engine they join only `pi-sandbox`, an internal bridge network carrying `pi-sandbox.managed`; the launcher inspects it and refuses a network of that name that is not internal or not managed, naming it. One relay container per proxy instance, `pi-sandbox-relay-<first 8 of the policy hash>`, from the sandbox image id passed to `prepareProxyRoute` (which has socat), sits on both the default `bridge` network and `pi-sandbox`. It runs `socat TCP-LISTEN:3128` and forwards each connection to its proxy's port through `host.lima.internal` (Colima) or `host.docker.internal` (mapped to the host gateway). Its address is read from network inspect after creation, not fixed. Relays carry `pi-sandbox.managed`, `pi-sandbox.relay`, `pi-sandbox.relay-port`, `pi-sandbox.relay-image` and `pi-sandbox.proxy-policy-hash`; a relay whose port and policy hash labels match is reused whatever its image (started again when stopped, so it usually keeps its address and the agent's spec hash), and only a relay whose port or policy hash differ is recreated; the image id is used only when a relay is created and kept in `pi-sandbox.relay-image` for information. An agent container carries the same `pi-sandbox.proxy-policy-hash`, so `gc` removes relays and stops proxy instances that no running container uses.

With `apple`, the agents join an internal network created with `--internal` and `--label pi-sandbox.managed=true`, and the route address is that network's gateway with the proxy's port. An existing `pi-sandbox` network is inspected first (`container network inspect` JSON, the fields assumed in `APPLE_NETWORK_FIELDS` in `apple/cli.ts`); one that is not internal, not managed, or whose output cannot show it is internal is refused with a `LauncherError`.

The internal network's embedded DNS answers container names only; external names do not resolve inside, so every tool must go through the proxy.

## Proxy

The proxy is a detached Node process (`proxy/daemon.ts`) on `127.0.0.1`, started on demand. Its state lives in `<stateDir>/proxy/<policyHash>/`: `proxy.json` (pid, port, policy hash, token), `proxy-token` (mode 600, kept when the proxy stops), `proxy-config.json` (mode 600), `proxy.log` (the daemon's stderr), `proxy-access.log` and `lock`. Start-up holds `lock` (exclusive create, a stale lock is detected by its pid and taken over by renaming it to a unique name, then creating a new one, so of two waiters only one creates the lock and the other sees `EEXIST` and waits; the renamed file is compared with the stale lock read before, by inode, mtime and content, and only a different lock whose owner is alive is linked back, so a lock whose holder has gone is not resurrected); the launcher reuses an instance whose pid is alive and whose `/healthz` answers with the same policy hash, and kills and replaces one that fails the health check twice. `readProxyInstances` lists only live instances; `stopProxy` stops one or all and removes dead records, keeping the token; `removeProxyInstance` stops one and deletes its directory. The launcher CA is shared at `<stateDir>/ca/`.

- `CONNECT host:port` is allowed for hosts in `egress.allow`, `egress.mcpHosts`, manual rule hosts and the gateway host, then for the repository's extra list: derived hosts and active grants (`extraAllowList`), each clipped by the D3 cap. `egress.deny` wins over all of them. Ports are 443 unless an entry names one. IP literals, localhost, loopback, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except names in `egress.privateHosts` and the legacy gateway host. The proxy resolves and dials itself (or through the parent proxy), reads the TLS ClientHello and refuses a missing SNI or one that differs from the CONNECT host. Tunnels to hosts without a rule are not decrypted.
- A denial is `403` with a JSON body `{ denied, rule, reason }` and `Proxy-Agent: pi-sandbox`; an allowlist denial's reason is `pi-sandbox: <host> is not allowed; run pi sandbox egress allow <host>`. The last 200 denials per repository are kept in memory and served at `GET /denials?since=<ms>` to that repository's token. Plain HTTP is refused except `/healthz` (`{ ok, policyHash, pid }`), `/policy`, `/denials` and `/control`.
- Credential rules (`proxy/rules.ts`, `proxy/terminate.ts`): TLS is terminated for every rule host with a per-host leaf signed by the launcher CA (made with openssl). For the matching rule (host, port, path prefix), the placeholder is replaced in auth-like request headers only (`authorization` and `isSecretName` names, never `proxy-authorization`, never query or body), then a `header` rule sets its header from `template` when it is absent or still carries the placeholder. Every response header value is scrubbed by substring (real secret to placeholder). A secret that cannot be resolved removes the header that carried the placeholder, so public endpoints still work, and logs `rule: credential, reason: unavailable`; an upstream `401` invalidates the cached secret once. The legacy gateway is one such rule plus its URL path rewrite. Server-sent events stream unbuffered and WebSocket upgrades are forwarded.
- Secret sources (`proxy/secrets/`, one file per kind, behind `createSecretResolver`): `env` (the map the launcher sent over `/control`, memory only, never the daemon's own environment), `file` (a JSON pointer into a host file), `command` (argv, stdout trimmed or `{ token, expiresAt }`, cached for `ttlSeconds`, 300 by default, single-flight), `piAuth` (the bundled pi's `auth print-api-key` or `print-bearer-token --min-expiry 5m`, cached 240 s), `mcpOAuth` (the token entry of `<state>/mcp-auth/mcp-auth.json` whose key ends with `|<url>`; within 30 s of expiry, the skew at which pi itself refreshes, or after a 401 it rewrites the one-server `mcp-auth/mcp.json` from the recorded server and runs `pi mcp list` there, single-flight; a token that is still unexpired afterwards is used and asked again after 10 s at most, an expired one is unavailable). Values never reach disk, logs or error messages.
- Parent proxy (`proxy/parent.ts`): `"env"` takes the address of `HTTPS_PROXY` and `NO_PROXY` from the daemon's environment, which the launcher passes without userinfo; the credentials from that URL come only from the control map under `egress.parentProxy`, sent on every launch. An object names the URL, `noProxy` and an `auth` secret for Basic auth. The private-range check still runs on local resolution; an NXDOMAIN while a parent is set is passed to the parent.
- Upstream trust is the system roots plus `<state>/ca/extra.pem` when `tls.extraCa` is set.
- Every decision is one JSON line in `proxy-access.log` (`time, user, repo, host, sni, decision, rule, reason, credential, bytesIn, bytesOut`), never a credential or a token.

## Credentials and derivation

`hostpi/` turns the host pi files into the sandbox's (`deriveSandboxPi`, pure, no secret value in its output):

- `auth.json`: an `api_key` entry becomes `{ type: "api_key", key: P }` with a rule `{ piAuth: id }`; an `oauth` entry keeps its non-secret fields, `access` becomes P (JWT-shaped when the token is a JWT, so the header and payload stay real), `refresh` an opaque placeholder and `expires` far in the future, with a rule `{ piAuth: id, bearer: true }`. A provider key found only in an environment variable the provider host table names gets an `api_key` placeholder and the same rule.
- `models.json`: `apiKey` becomes a placeholder; header values that are `$NAME`, `!cmd` or under an auth-like name become placeholders with `{ env }`, `{ command: ["sh","-c",cmd] }` or a `{ file, pointer }` into the host `models.json`. Rule hosts come from the provider and model `baseUrl`s, or the provider host table for built-in providers. A `localhost` or plain-`http` `baseUrl` gets a notice.
- `mcp.json`: HTTP server headers as in `models.json`, `oauth` blocks removed, and a server without `Authorization` gets `Authorization: Bearer P` with an `mcpOAuth` rule (and a notice to run `pi mcp login <name>` when no token exists). stdio servers are copied; secret `env` values become placeholders with a notice.

Placeholders are `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`, so they are stable across launches and unguessable. Derived rule ids are `derived:<identity>`; manual ids cannot contain `:`. Rules and hosts are filtered by `credentials.derive`, and a manual rule for the same host wins. The provider host table comes from `hostpi/provider-hosts.mjs`, run with `process.execPath` against the bundled pi's provider list and cached at `<state>/provider-hosts/<pi version>.json`; when the bundled pi's version differs from the image pin, built-in providers get no rule and a notice.

## Provisioning the agent dir

- `renderAgentDir` (`provision/render.ts`) builds `<state>/render/<repo hash>/` on every launch: the derived `auth.json` and `models.json`, an empty `mcp-auth.json`, and filtered copies of `agents/`, `prompts/`, `skills/`, `themes/`, `extensions/`, `AGENTS.md`, `SYSTEM.md` and `keybindings.json` (no symlink is followed, secret-looking files are left out, entries gone on the host are removed). It is mounted read-only as a directory at `/opt/pi-sandbox/render`, and the entrypoint links each present entry into the agent dir, replacing a dangling or older link, never a file or dir the user created inside. A read-only `auth.json` link makes `/login` fail instead of writing a real secret into the volume.
- `syncWritableFiles` (`provision/sync.ts`) keeps `settings.json` and `mcp.json` as writable files in the volume, since pi writes them: a top-level three-way merge against the last synced host copy in `<state>/sync/<repo hash>/` (host-changed keys win, volume-only keys stay, host-deleted keys go), through `backend.exec` (`cat`, and a write through stdin). Host-absolute local package paths outside the mounted paths are dropped with a notice, and the baked `pi-extensions-mz` entry is deduplicated against a host `npm:pi-extensions-mz`.
- Nothing is written back to the host except the `packages` entry of an intercepted `pi install|remove`.

## Sessions and grants

- `grants/sessions.ts`: one file per running launch in `<state>/sessions/<repo hash>/`, written and removed under a lock there; `liveSessions` ignores entries whose pid is dead. The launch id (16 hex) is in the exec environment as `PI_SANDBOX_LAUNCH_ID`, never in the spec.
- `grants/store.ts`: `<state>/grants.json` (mode 600, atomic, locked) holds `{ host, port, repoHash?, createdAt, expiresAt?, launchId? }`; no `repoHash` means every repository. `addGrant` applies `egress.grants` (`enabled`, `maxHours`, `permanent`); a session grant carries the launch id and a 12 h expiry. `activeGrants` keeps grants that have not expired, whose launch is live, for the repository or the user. The proxy reads them live on every CONNECT that the static policy refused; `pruneGrants` runs on container creation, `reset` and `gc`.

## Container identity

A container belongs to one repository: its name is `pi-sandbox-<first 12 of the repo hash>`. Its labels carry `pi-sandbox.managed`, the full `repo-hash`, `repo-root`, `image-digest`, `image-reference`, `config-hash`, `proxy-policy-hash` (when it has a proxy), `version` and `spec-hash`, the sha256 of the rendered spec as key-sorted JSON. The container is created from the image id, with the reference kept in its label. `ensureContainer` reuses a container whose image digest, config hash and spec hash all match (starting it when stopped) and otherwise stops and removes it and creates a new one. So a config change, a new image or any change in the rendered spec (a new proxy route, a token rotated by `reset`, a new mount) gives the next `pi` a fresh container, while the volumes survive.

The spec mounts the repository and git common dir read-write at their host paths and overlays these read-only: the git dir's `hooks` and `config`, the effective `core.hooksPath` when it resolves inside a mounted path, the `hooks` and `config` of every submodule git dir, `config.worktree` and every `.git/worktrees/*/config.worktree`. Hook dirs are overlaid whether they exist or not: `discoverGitOverlay` creates a missing `.git/hooks`, `core.hooksPath` or submodule `hooks` dir (empty) on the host first, so the agent cannot create hooks the host would run. A `core.hooksPath` outside every mounted path is left alone, since the container cannot see it. Submodule git dirs are found by walking `.git/modules/`: a dir with a `HEAD` file is a module git dir, and only its `modules/` subdir is walked further (a dir without `HEAD` is a path segment of a module name and is walked into), so objects are never listed. When the backend has no single-file mounts, the files come from copies under the spec's `copiesDir` (`<stateDir>/copies/<repo hash>/`). It adds `mounts.extraReadOnly`, the repository's agent volume `pi-sandbox-agent-<user hash>-<repo hash>` at `/home/pi/.pi/agent` and per-repository cache volumes; `repoVolumes` lists both kinds for `reset --volumes` and `migrate`. The root is read-only with tmpfs `/tmp` and `/home/pi`, under an init process, as `<uid>:<gid>` on Linux. It mounts the render dir read-only at `/opt/pi-sandbox/render` and, when there is one, the trust bundle at `/etc/pi-sandbox/ca.pem` (a read-only copy on backends without single-file mounts). The environment holds no host variables (the allowlisted ones and `PI_SANDBOX_LAUNCH_ID` go to each exec, so the spec hash does not change with the terminal): the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_USE_ENV_PROXY`) with the repository token when there is a proxy, `NODE_EXTRA_CA_CERTS` and `PI_SANDBOX_TRUST_HASH` when the trust bundle is mounted (so a CA change recreates the container), the CA bundle paths, `PI_SANDBOX=1`, `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`. `PI_OFFLINE` is not set, so pi installs configured packages and runs updates through the proxy. With `ssh.agent` on and a backend that can forward it, the spec asks for the agent at `/run/host-ssh-agent.sock` and the adapter sets `SSH_AUTH_SOCK`.

## Image

`image/Dockerfile` builds on a slim Node image with git, search tools, ssh, tini, socat and netcat, a `pi` user with uid 1000, pi pinned to the version in the package's dev dependencies, and this package's extensions from `EXTENSIONS_SOURCE`: a tarball packed from the checkout (`npm pack`, cached in `<stateDir>/pack/` by package version and git `HEAD`, `image/extensions.ts`), a registry version when the launcher itself runs from `node_modules`, or none when the digest is pinned. It bakes no pi config and no credential: `auth.json`, `models.json` and the rest come from the render dir at run time. `PI_SELF_UPDATE_COMMAND` points at a script that prints that pi follows the launcher. During the build the extra CAs are trusted (`trust.pem` in the context) and removed again at the end, and a parent proxy without credentials is passed as the predefined proxy build arguments (`image/build-proxy.ts`); one with credentials refuses the build.

The entrypoint removes dangling links into the render dir, links each render entry into the agent dir, seeds `settings.json` once (the agent dir is a volume), builds a CA bundle from the system roots plus `/etc/pi-sandbox/ca.pem` so tunneled hosts keep the system roots, and idles under tini; pi runs through exec. `ensureBuiltImage` pulls and verifies a pinned digest through `backend.pullImage`, or hashes the build inputs (reference, pi version, Dockerfile, entrypoint, tarball) against `<stateDir>/image.json` and rebuilds when they changed or the recorded image is gone. Either way it records the reference, digest and image id; `recordedImage` is the one reader of that record.

`ensureLayerImage` (`image/layer.ts`) renders `FROM <base id>`, `USER root`, the build trust, `apt-get install` of `image.packages`, `npm install --global` of `image.npmGlobal`, the `image.dockerfile` text (a `FROM` line is refused) and `USER pi`, tags it `pi-sandbox-layer:<first 12 of the inputs hash>` and records it as `image.json` `layer`, so it is built once per set of inputs.

## Files written

- `~/.local/state/pi-sandbox/` (or `PI_SANDBOX_STATE_DIR`): the launcher's own state.
- `~/.config/pi-sandbox/config.json`: the user config, written by the installer when absent (its `org` key with `--org`), on `pi sandbox config set` and by `migrate`.
- `~/.pi/agent/settings.json` on the host: only the `packages` key, only on `pi install|remove <source>` typed in the shell with exit 0 (`writeBackPackageChange`, atomic).
- Inside the repository's git dir and worktree: empty hook directories (`.git/hooks`, a `core.hooksPath` inside a mounted path, submodule `hooks`) created when missing, so they can be mounted read-only.
- `<repo>/.pi/sandbox.json`: written only on the user's command (`pi sandbox config set --project`). When the launcher creates `<repo>/.pi/`, it also writes `<repo>/.pi/.gitignore` with `*`. It may not import `platform/shared`, so it carries its own equivalent of that write; an existing `.pi/` is left as it is.

## Tests

Tests check behaviour with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server on a temp Unix socket, a fake `container` CLI, a fake backend, temp dirs, real localhost sockets and openssl certificates. A folder's tests may reach that folder's inner modules; everything else goes through `index.ts`. The CLI tests run whole commands against the fake backend with an injected proxy control (ensure, list, stop, remove, control, denials, trust), a fake bundled pi, a fake resolver and a fake terminal confirmation, and collect their output. Live tests against a real engine run only with `PI_SANDBOX_LIVE=1`.
