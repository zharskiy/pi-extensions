# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a container on a Colima VM, one container per launch, and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens and the known gaps are in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` runs as a separate Node process against the host pi of host jobs and loads its packages; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal, and `cli/prompt/` the only code that reads keys or sets raw mode; the proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), printed as `pi-sandbox: <message>` and `  hint: <hint>` with exit code 1. Any other error exits 70.
- External processes that run to completion (git, glab, openssl, `security`, colima, tar, secret commands, the host pi's jobs) run through the `CommandRunner` interface, so tests replace them with a scripted fake. `cli/main.ts` resolves `git` once, to the git on `PATH` outside the started folder and its repository. The two detached children, the proxy daemon (`proxy/start.ts`) and the proxy's host `pi mcp login` (`proxy/sign-in.ts`), start through an injected `spawn`, and the liveness rule reads a start time with `ps` directly (`shared/process-start.ts`).

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs. Node refuses to strip types under `node_modules`, so the published `bin/pi-sandbox.js` imports `../dist/cli/main.js`, which `tsconfig.build.json` emits (`npm run build:launcher`, run by `prepack`). Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, examples, schema, install scripts) stay in `launcher/`, and code finds them through `launcherRoot()`. A script run as its own node process is a typed `.ts` file too, such as `cli/commands/tls-probe.ts`, the `tls inspection` and `tls in sandbox` handshake: code finds it through `launcherEntry()`, the `.ts` in a checkout or its `dist/` `.js` when installed, resolved from the launcher's own location; the host runs that file, and a container, which has no launcher files, gets its text with `-e` and `--input-type=module-typescript` (`module` for the `.js`). Its request, proxy credentials and timeout included, goes on stdin, never in argv or the script text.

## The pipeline

`cli/run.ts` routes the command line. `pi sandbox …` runs a command, the hidden `pi-sandbox __uninstall` runs the uninstall cleanup, intercepted commands run on the host, and everything else is a launch (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir from `cli/context.ts`):

1. **Intercepted commands** (`cli/intercept.ts`, with `cli/host-routes.ts` for the commands that start no session): `install|uninstall|remove <source>` without `-l`, `mcp add|remove|login|logout`, every `update …`, `config` without `-l`, every `auth …`, pi's help (`--help`, `-h`, `<command> --help`, bare `mcp`), `--list-models [search]`, `--export <file> [out]` and `--version` run on the host and stop here, before the folder is read. Only `--version` reads the config, to see whether the image is pinned.
2. **Folder and config** (`cli/context.ts`). `workspaceFolder` takes the real cwd and walks up to the nearest `.git` without following links; that root, else the cwd, is the folder to mount. The config is loaded from the one config file. Before anything is searched, the guard (`assertSafeMounts`) runs on the folder and `workspaceRoots` refuses a folder outside every root. Then discovery runs (below), and after it `workspaceRoots` and the guard run again on the repository root and its git common dir (`assertSafeWorkspace`).
3. **`--no-sandbox`** uses a lenient context (no guard, no search), checks `workspaceRoots`, sweeps the host session directory and execs host pi, mounting nothing.
4. **Register the launch** (`cli/launches.ts`, `grants/launches.ts`) under the folder's prepare lock (`locks/prepare-<repo hash>.lock`), which writes `repo.json` and then the launch entry under the launch registry lock (`locks/launches.lock`), before the VM stage, so `pi sandbox stop`, a share restart and the uninstall count a launch that is still preparing. From here to the end of the session one guard holds SIGINT, SIGTERM and SIGHUP: during preparation the first signal prints `pi-sandbox: stopping after the current step` and ends the launch like a normal exit once the step in flight finishes, a second signal, while that step finishes or during the cleanup after it, makes the cleanup skip its waits for a lock (the next sweep does that work) and prints `pi-sandbox: the cleanup will not wait for other pi-sandbox commands; another Ctrl-C ends pi-sandbox at once, leaving the rest to the next start`, and a third ends the launcher at once. While pi runs, signals go to pi (`container/run-pi.ts`); in the cleanup after pi exits, the first signal skips the waits for a lock with the same line and the second ends the launcher at once.
5. **VM** (`cli/vm.ts`, `backend/colima/`). The host pi files are read first and the host side (step 7) starts deriving alongside. The host session directory is created, then a stopped `pi-sandbox` profile is started when its `colima.yaml` exists, at the `vm` size (below). Without that file the launch refuses with `the sandbox VM does not exist` and the hint `run pi sandbox init`, never a bare `colima start`, which would create the profile with colima's defaults (size, VM type, no mounts) that `pi sandbox init` then never revisits.
6. **Shares.** Without `workspaceRoots`, any path the running VM lacks (the folder, the git common dirs, `<state>/vm`, the host session dir) is shared by restarting the profile once with the full mount list, only when no other launch is live, and the share is kept. With `workspaceRoots`, the wanted list is exactly the roots (writable), `<agent dir>/sessions` (writable) and `<state>/vm` (read-only) (`workspace/roots.ts` refuses a root with `,`, `:` or a control character, the home or a folder above it, and a root that overlaps a path of the workspace guard's list (`protectedPaths` in `workspace/mounts.ts`, which names `~/.colima`, `~/.config` and the credential dirs), the roots-only `~/.local/bin` and `~/Library` (the launch-folder guard allows them), the user config's folder, `/etc`, `/usr`, `/opt`, `/System`, `/Library`, `/bin` or `/sbin`, or is or holds `/private` or `/var`; it drops a root written inside another before following links and again after, then checks the rest on their real paths, and skips a missing one with a notice; `cli/vm.ts` builds the list, refuses with a `config:` error when two of its entries nest (the session dir resolving into a root, say), and creates the two dirs). The list is built before the VM step, so a stopped VM starts with exactly it in one boot. "Another launch is live" counts this state dir's live launches and every running launcher container in the engine that is not one of them, so a session of another agent dir (which shares the one profile) holds the restart too. The VM paths a launch needs, the shares and the container's bind sources of the session dir and the render dir (`container/spec.ts`) all use real paths, so a linked `~/.pi` or `PI_CODING_AGENT_DIR` binds what the VM shares. `reconcileVm` (`cli/vm.ts`) hands that list (or, without `workspaceRoots`, the paths the launch needs) and the config's `vm` to `reconcile` (`backend/colima/vm.ts`), which reads the VM's shares and size under `vm.lock` and decides with `vmDecision` (`backend/vm-decision.ts`, which `pi sandbox init`'s plan uses too): equal does nothing; a `lima.yaml` that cannot be parsed leaves the shares as they are, with a notice when `workspaceRoots` is set or the VM is restarted or held for its size (and the doctor's `vm shares` check warns); different with no other launch live restarts the profile once with exactly that list (or the current shares plus the missing ones) and the size flags, with one notice (`restarting the sandbox VM to …`), so with `workspaceRoots` set a share outside the list, such as the home, is dropped; different while another launch is live goes on with the notice `the sandbox VM will … at the next launch with no other pi session running` when the current shares already cover this launch, and otherwise refuses, naming the paths that are not shared. The hidden `pi-sandbox __vm-shares` (`cli/commands/vm-shares.ts`) builds the same list (so it fails on the same `config:` errors and creates the two dirs) and prints the roots of it that exist, one per line, or `$HOME` without `workspaceRoots`, for `install.sh`, which runs it after `pi sandbox init` and takes the first line as the smoke check's folder: `~/.cache` when it is `$HOME`, no smoke check when there is none. `install.sh` prints paths with `printf '%s\n'`, and runs the smoke doctor as the hidden `pi-sandbox __smoke-doctor` (`cli/commands/smoke-doctor.ts`), the same doctor and report that exits 3 instead of 0 when the sandbox part was skipped because the VM does not share the folder yet; on 3 it says the sandbox part runs at the first launch instead of claiming it passed. On a terminal (stdout and stderr both TTYs) `install.sh` runs brew, npm, `pi sandbox init` and the smoke doctor directly on it, so their own colours and progress lines show, and puts a blank line and a rule (dim `─` with colour, `-` under `NO_COLOR` or `TERM=dumb`) before each new step header, which is bold with colour; otherwise it indents their merged output by six spaces under plain `[n/6]` lines. Either way the children other than an interactive `pi sandbox init`, which reads `/dev/tty`, keep the script's stdin. A failed setup or `__vm-shares` stops the install before the smoke check. Outside `pi sandbox init`, a profile that exists keeps its shares until the first launch reconciles them. The shares the VM has are read from its `lima.yaml`. A new share absorbs any share inside it, since colima refuses nested mounts, and a share that colima mounts at another path in the VM is refused before the VM is stopped and before the refusal that other pi sessions run. Every `colima` command runs against `~/.colima`, whatever `COLIMA_HOME` says.
   `mounts.binds` sources are checked on the host first (`workspace/binds.ts`): each must exist and pass the same guard as a root (not the home or above it, apart from the guarded paths), with a `config: mounts.binds[<i>].source` error otherwise, before the engine is called. A source whose real path overlaps a host path the launch mounts writable (the repository root, a workspace root, the git common dirs of the folder and of its linked worktrees and the host sessions dir, which `writableMounts` in `cli/vm.ts` lists for the share list and for this check alike; the same path, inside it or holding it) is refused (`… overlaps <root>, which the sandbox already mounts`, hint: bind a folder or file apart from the folders the sandbox already mounts). Right before the create, after the git plan's `ready()`, `confirmBinds` checks each source again (not a link, the same kind, the same real path) and refuses one that changed (`… changed while pi was starting, refusing`, hint: run pi again). The window between that check and the engine resolving the source at the create stays open, and so does a source inside another repository that another session works in (see THREAT-MODEL); binds are read-only. The VM must see a source, so a folder source, or the folder of a file source, is a read-only VM need without `workspaceRoots`, and with them `cli/vm.ts` adds it to the wanted list as a read-only share unless it lies inside a share already (no new share then); a source that holds a share is refused (`config: mounts.binds: the sandbox VM would share <path> for a bind source, which holds the share <share>, and colima refuses nested shares`). A new share costs a VM restart like any other: it happens at a launch with no other session running, and while sessions run the launch is refused, naming the path that is not shared.
   Before the VM is started, `assertVmFitsHost` (`cli/vm.ts`) refuses a `vm.cpus` above this Mac's CPU count or a `vm.memoryGiB` above its memory less 2 GiB with a `config:` error naming the key, the value and the host's figure, so a size the VM cannot boot at never stops it; `hostVmLimits` is the one bound, which the setup's VM editor (`vmBounds`), `pi sandbox init`'s apply step and the doctor's `vm size` check (failed, and the sandbox not started) use too. The static validator keeps fixed bounds only, since the same file may be valid on another Mac. For the size, `reconcile` (with `backend/vm-size.ts`) asks nothing when `vm` is empty and changes nothing when colima reports no size. It compares `cpus` and `memoryGiB` for equality and `diskGiB` only upwards with what `colima status --json` reports; a `diskGiB` below the current disk prints a notice and is never applied, since colima cannot shrink a disk. A size that differs goes into the same restart as the shares, `--cpu`, `--memory` and `--disk` for the values that differ, and no `--mount` when the shares are equal, so the shares in `colima.yaml` stay; the notice names both (`restarting the sandbox VM to change its size to …`, or `…, and change its size to …`), so a launch that finds both changed boots the VM once. A stopped VM is started at the `vm` size directly, by a launch and by `pi sandbox doctor` alike: the start passes `--cpu`, `--memory` and `--disk` for the values that differ from the `cpu`, `memory` and `disk` of its `colima.yaml` (the disk only when it grows; without a readable size there, only `--cpu` and `--memory`). `pi sandbox doctor` never restarts a running VM to resize it; its `vm size` check compares with `vm` when it is set, else with the automatic size for this Mac (`recommendedVmSize`), which `pi sandbox init` also creates a new profile with where `vm` is unset.
7. **Host side** (`cli/derive.ts`): read the provider host table, derive the sandbox files and the credential rules (`hostpi/`), collect the CAs the image layer trusts (the launcher CA and the `tls.extraCa` certificates, written to `ca/extra.pem`: a `sha256` entry is matched by fingerprint, computed in Node, against `security find-certificate -a -p` of the macOS System and login keychains (a keychain that cannot be read is skipped, and named when nothing matches), a `file` entry is read as PEM, and every certificate must be unexpired and a CA or a self-signed root (issuer equals subject and the signature verifies with its own key), or the launch stops), run the orphan sweep, and sign in to MCP servers that need it (`cli/mcp-sign-in.ts`, only when input and output are a terminal, never from `pi sandbox doctor`, which reports `pi mcp login <server>` instead). Then the VM's trust store follows the `tls.extraCa` certificates (`backend/colima/vm-trust.ts`), so the VM's engine pulls through an inspecting proxy: the marker `/etc/pi-sandbox/extra.sha256` in the VM, read through `colima ssh` right after the VM stage, is compared with the SHA-256 of the certificates in `<state>/ca/extra.pem`; when they match, or there are no certificates and no marker, nothing else runs; a marker that cannot be read (ssh fails) counts as a mismatch. Otherwise, under `vm.lock` and only when no other launch is live (else one notice says the VM picks the change up at the next launch with no other pi session running), the launcher clears the marker, writes each certificate to its own `/usr/local/share/ca-certificates/pi-sandbox/pi-sandbox-extra-<n>.crt` (all removed when there are none), runs `update-ca-certificates --fresh`, restarts `containerd` and `docker` (which ends any container in the VM, with a 60 s timeout), writes the marker once that restart has run, then polls the engine for up to 60 s. Each step is a fixed `sudo` command through `colima ssh`; certificates and marker reach the VM on stdin, never in a command line. A failed step before the restart stops the launch and leaves no marker, so the next launch tries again; an engine that is still down after the wait stops the launch with the marker in place, so the next launch does not reinstall. Nothing is written on the host.
8. **Proxy and image, in parallel**, alongside rendering the agent dir (the status file among it), planning the git overlay and preparing the host session directory. `openSandboxProxy` (`cli/sandbox-proxy.ts`) starts or reuses the install's proxy through `ensureProxy` under the ground lock (see Network and Locks and liveness); the proxy always runs. `ensureSandboxImage` ensures the current image (see Image).
9. **Container** (the `container` stage of `prepareSandbox` in `cli/launch.ts`, `container/`), all under the repository's preparation lock (`locks/prepare-<repo hash>.lock`, see Locks and liveness). First the proxy route (`prepareProxyRoute`: the install's network and the relay, under the ground lock, see Network), then the services (`prepareServices`, which calls `startServices` under the ground lock, see Services), then the notices and the spec (`prepareContainer`), which hands the services' ports to the container's port forwarder (see Container). For the launch's own container, right before the create the git plan's `ready()` re-checks each repository's layout, creates missing hooks dirs (left in place), checks the hooks dirs and bare dirs, and records the git baseline, and `confirmBinds` re-checks the bind sources. The create then prunes overlay volumes no container mounts, ensures the volumes, creates missing mount points, creates and starts the container, hands the volume roots to the sandbox user and probes the session share. Each `setup` command (`cli/prepare.ts`) then runs in order as an exec in the agent container, as `pi` with the `env.allow` variables and `PI_SANDBOX_LAUNCH_ID`, in the repository root, without stdin or a pty, printing `pi-sandbox: setup: <command>`, its output on the terminal and Ctrl-C aborting it; a non-zero exit stops the launch with `setup: <command> exited with code <n>, so pi did not start` (hint: fix or remove that command in `setup`), and the end of the launch removes the container. The doctor's probe container skips the services, `setup` and the binds. After the preparation lock is released the agent files are synced (see Provisioning): sandbox changes of the allowlisted keys are written back to the host, then the host `settings.json` and `pi-*.json` files are written into the agent volume; a failed sync is a warning (`the agent settings were not synced`) and pi still starts.
10. **Run pi** through exec: `sh` starts in the repository root and `cd`s into the host cwd; a cwd the sandbox does not have (hidden by an overlay volume) prints `pi-sandbox: <cwd> is not in the sandbox, pi starts in <root>`. A pty and raw mode are used only when stdin and stdout are both terminals. The `env.allow` variables are forwarded, except the names `env.set` sets (`forwardedNames`, `container/spec.ts`), so the `env.set` value wins, and one whose value is shaped like a credential (`env.allow: <NAME> holds a credential, so it stays on the host`). Pi flags that name a host file (`--system-prompt`, `--append-system-prompt`, `-e`/`--extension`, `--session`, `@file`) pass unchanged; when the file lies outside the mounts, a notice names it. A signal reaches pi as SIGTERM through a pid file in its container; when pi exits within 5 s its exit code is returned, else the launcher stops the container and returns 128+N. A closed stdout or stderr (EPIPE, EIO) stops pi like SIGTERM (exit 143). Pi's exit code is the launcher's. While pi runs, with `vm.releaseFileCache` on, `withSandbox` (`cli/launch.ts`) starts the VM's file cache watch (`Vm.watchFileCache`, `backend/colima/file-cache.ts`) and stops it first in the cleanup after pi exits, waiting for a release under way (with its `vm.lock`) to end; a tick still counting when pi exits takes no lock and releases nothing. It is an unref'd timer that every 10 s counts the open files of the Mac process behind the VM (`lsof -n -P -p <pid> -F f`). The pid is, of the processes `lsof -n -P -t` lists as holders of `~/.colima/_lima/colima-pi-sandbox/disk`, of `diffdisk` beside it (the name Lima before 2.1 gave the disk, kept by an instance it created) or of `~/.colima/_lima/_disks/colima-pi-sandbox/datadisk`, one `lsof` for each path since `lsof` exits non-zero for a name that does not exist, the one with the most open files; it is found again when it is gone and every 5 minutes, so another holder of the disk file (a backup tool, say) or a reused pid cannot switch the watch off for a session. A lookup that times out or cannot start (not the non-zero exit of a missing path) is not taken as no holder: when no path yields one, the pid found before is kept, and counted, while it exists. A count that times out (10 s) while the pid still exists counts as past the limit. virtiofs keeps one host file open for each inode the VM caches, so a very large tree can use up the Mac's file descriptors. When the count reaches the lower of half `kern.maxfilesperproc` and a quarter of `kern.maxfiles` (read with `sysctl -n`, again on each tick until a read succeeds, then kept), the watch takes `vm.lock` only if it is free (`withDirectoryLockIfFree`, else it skips the tick), counts again under it, and runs `sudo sysctl -q -w vm.drop_caches=2` through `colima ssh`, at most once every 30 s per pi session. It prints nothing, since stderr belongs to pi's terminal; with no VM process found or no limit read it does nothing. `pi sandbox doctor` does not start it; its `file cache` check reads the same discovery, count and limit through `Vm.readFileCache` and never releases.
11. **End the launch.** Print one line per blocked host from the proxy's denial list, `<host> was blocked in the sandbox; <hint>`, with a hint for its kind: not allowed (`run pi sandbox egress allow <host> on the host`), a private, loopback, link-local or reserved address (the proxy's reason, which names the address a name resolved to, then `add <host> to egress.privateHosts in <config file>`), `egress.deny` (`denied by egress.deny`), plain HTTP (`use https`), an upstream failure of a spliced or terminated host (`it could not be reached: <reason>`), a credential the proxy could not supply (`it could not authenticate: <reason>`), a provider login host pi could not resolve (`the <provider> login on the host is missing or expired; log in again with pi --no-sandbox and /login`), else the proxy's reason. Write the sandbox's changes of the allowlisted keys back to the host and sync again (see Provisioning), only when the sandbox got ready and never from `pi sandbox doctor`. Remove the launch's container, also after a failed preparation or a signal, then the launch entry; when it was the repository's last live launch, `removeRepoSandbox` runs and then the git end-of-session report. `sweepOrphans` runs after either way (see Lifecycle).

`pi sandbox doctor` first computes the VM share coverage; while a path is missing its `vm shares` check warns with the path (with `workspaceRoots` set, it also warns, naming them, while the VM's shares differ from the wanted list), a `skip sandbox` check says the sandbox was not started, and only the host checks run. Otherwise it runs the same preparation without the shares stage and the MCP sign-in, turning each stage and probe into a check. A rule probe sends the rule's placeholder; when the proxy recorded a credential denial for that rule since the doctor's launch began, the rule check is a `warn` with the end-of-launch reason and hint (an expired provider login, say) instead of `ok` or `fail` on the status. When the probe got no HTTP answer and the proxy recorded a denial without `credentialRule` for the rule's host and port (a CONNECT refusal: a private address, `egress.deny`), the `fail` check is `<url>: the sandbox proxy refused it` with the end-of-launch reason and hint under it (`denialAdvice` in `cli/sandbox-proxy.ts` splits that hint into the two) instead of fetch's bare error code (`0`); any other fetch error keeps its text, and `CERT_NOT_YET_VALID` on a `trust` or `rule` check adds that the VM's clock is more than an hour behind the host's (the proxy dates its certificates an hour back by the host's clock) and to restart the VM with `pi sandbox stop` and run the doctor again. The doctor writes no end-of-launch report: `withSandbox` hands the proxy's denials to its `denials` option before `finishLaunch` may stop the proxy (the default prints the end-of-launch lines), and the doctor turns those no rule check explains (credential denials and denials for a rule's host and port) into `warn blocked <host:port>` checks with reason and hint; when a stage failed before the probes, the sandbox never ran, there are no denials to read, and a `skip probes` check names the stage. Its stderr goes to a line sink during the run, so every launch notice (without the `pi-sandbox: ` prefix, deduplicated, without the missing-pi notice its `host pi` check repeats; without a host pi the `provider hosts` check is a `skip`, so the one cause fails once) lands in the report's `notices` section, also when an error ends the run, in which case the report so far comes before the error and has no result line. The checks are plain data (`cli/commands/doctor-checks.ts`: the result types and builders, the order and the verdict the exit code and the result line share), and `cli/commands/doctor-report.ts` renders them as text: sections in the order host, sandbox, network, credentials, leak sweep, notices, the checks of a section in the fixed order of their names (`LAYOUT`, so `vm size` follows `vm`, `file cache` follows `vm size`, and `parent proxy` comes before `no-route`, whatever order the probes finish in), one line per check (`  <status>  <name padded to 16>  <detail>`, the home shown as `~` where a path starts: at the start of the text or after a space, `(`, `:` or `=`), reasons and `hint:` lines indented under it, the passing credential rules collapsed into one `rules` line unless `--verbose`, the hint `run pi sandbox doctor` dropped as circular, and a `result:` line that counts every check. Colour (words only, the same layout) follows the rule of the setup prompts (`colourOf` in `cli/prompt/terminal.ts`): never with `TERM=dumb`, always with `FORCE_COLOR` set to anything but `0` or `false`, else only when stdout is a terminal and `NO_COLOR` and `NODE_DISABLE_COLORS` are unset or empty. The preparation's progress (the build steps, `starting the sandbox VM`) reaches the doctor through the `progress` option of `withSandbox` instead of stderr: on a terminal whose `TERM` is not `dumb` it shows as one stderr line overwritten in place and cleared before the report, otherwise it is dropped. The credential sweep (`sweepCredentials`) does not check a variable whose name `env.set` sets while its value inside is the configured one (a different value is checked as any other); when nothing else is found, its `ok` detail names the secret-named variables it skipped (`…; env.set values not checked: <NAME>, …`). A secret written into `env.set` is therefore not caught by the doctor. The `file cache` check (macOS only) runs after the sandbox part, outside its probes, so it shows when a stage fails, the VM lacks a share or `vm` does not fit the Mac; it is a `skip` when the `vm` stage failed, and, when no stage ran, a `skip` too if no process holds the VM's disk. It calls `Vm.readFileCache`, which runs the file cache watch's own VM process discovery, count and `sysctl` read: `ok` with the count and the limit (noting when `vm.releaseFileCache` is off), `warn` at or past the limit (a count that timed out reads as past it) with a hint that depends on `vm.releaseFileCache`, and `warn` when no VM process is found, naming the paths it looked for, when no path yields one and a lookup timed out or could not start (`lookup-failed`, told apart from none found), or when the limit cannot be read. The exit code is 1 when a check failed, else 0, or 128 plus the signal number after a signal.

The `tls inspection` check (`cli/commands/doctor-tls.ts`) shows whether the network intercepts the TLS of tunnelled hosts, which the container verifies itself. On the host it runs a node script through the command runner that handshakes with `pi.dev:443` (the one host every allow list holds), through the parent proxy unless `NO_PROXY` bypasses it, with its credentials on stdin, never failing on an untrusted issuer: once against Node's built-in roots and, when `<state>/ca/extra.pem` holds a certificate, once against those roots plus it. Verified by the built-in roots it passes as `not inspected`; verified only with the extras, as `inspected by <issuer>, trusted via tls.extraCa`. A verdict that is not an issuer error (`UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, `SELF_SIGNED_CERT_IN_CHAIN`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`), such as an expired certificate or a name mismatch, fails as `TLS to pi.dev does not verify: <verdict>`. Otherwise it fails as `TLS to pi.dev is signed by "<root>" (sha256 <fp>), which the sandbox does not trust` with the `{ "sha256": … }` entry for the user config and a second hint for a PEM file: the root is the self-signed certificate above the topmost presented one, found by issuer name and signature among the certificates `security find-certificate -a -p` lists from the System and login keychains (walking up through keychain intermediates); the sha256 is given only for a root that is itself in a keychain, as the launcher looks it up there. With no such root, the detail names the topmost certificate's issuer and the hint says to ask IT for that CA as PEM. Nothing is added to the config. A failure that is not about the certificate (the parent proxy refuses, no answer) is `pi.dev:443: <error>`, as for other unreachable hosts. Inside the container, with the probes, `tls in sandbox` runs the same script with the container's node, its `HTTPS_PROXY` (the launcher's proxy) and its own trust (`NODE_EXTRA_CA_CERTS`); when the host trusts the chain and the container does not, it fails naming the layer: the sandbox proxy, when it presents another leaf than the host sees, else the container's trust. The keychains are read only for an untrusted chain.

### Discovery

`workspace/discover.ts` and `workspace/git/layout.ts`. Discovery reads files and runs git; it writes nothing.

- **One repository.** Derive the git dir and common dir from the files alone (a real `.git` dir, a separate git dir, a submodule git dir or a linked worktree), refuse any link or pointer git would not have written, and refuse a `commondir` in a git dir where git never writes one (the common dir, a submodule git dir) unless it reads `.`. Then `git rev-parse --show-toplevel --git-common-dir` must agree. A cwd that is or lies inside a git dir (`.git`, `.git/hooks`, a bare repository in the working tree) refuses with `workspace: <cwd> is a git dir, refusing` or `… lies inside the git dir …`. A repository root whose only git entry is `.git` in another letter case refuses.
- **A workspace.** Without a `.git` above the cwd the folder is a workspace: one walk finds every nested repository, each checked like a single repository; the launch fails closed when one fails those checks. A nested checkout counts as a repository only when its git dir and common dir lie wholly inside the folder (the `gitdir:` text resolved as git resolves it, one component at a time with links followed, and the lexical and real paths all inside). Any other nested `.git` file, one whose git dir is missing included, makes a detached checkout: plain files, no git call, nothing outside mounted. A folder shaped like a git dir (`HEAD` plus `commondir`, or plus `objects` and `refs`, any file type, names ignoring letter case) outside every nested repository is a bare dir, bound read-only as a whole with no git call; a cwd of that shape refuses. An entry named `.git` in another letter case refuses (the message names a case-insensitive volume). A directory the walk cannot read refuses when it is the cwd or belongs to the user, since the sandbox could `chmod` it open; one owned by someone else is left alone. More than 50 000 directories, or more than 128 repositories and bare dirs, refuse.
- **Build output.** The same walk collects the build output folders beside their marker files (`workspace/overlay-markers.ts`). With `mounts.autoOverlays` on it does not descend into a marked folder that exists, since its overlay volume hides it; off, it neither collects nor skips, and a single repository then skips the walk. More than 512 overlays turn every overlay off (a workspace walks again without skipping); a single repository whose walk exceeds 50 000 directories gets no overlays. Both print a notice. `node_modules` and `.pi` are never searched.
- **Lenient.** `pi sandbox status`, `config`, `egress`, `reset` and `--no-sandbox` use a lenient discovery without git calls or refusals; it walks nothing, except where a command asks for overlays (status), and never in the home or `/`. Nested repositories are not listed there.

### Intercepted commands and host pi

`pi install|uninstall|remove`, `pi mcp add|remove|login|logout`, every `pi update` and `pi config` without `-l` run the host pi on the host. A bare `update` (or `update pi|self|--self`) runs the host pi's own update in the same empty folder, with `PI_CODING_AGENT_DIR` set to the host agent dir, so it reads only user-scope settings (`selfUpdateCommand`, `npmCommand`) for the self target. Every other `update` form (`--all`, `--extensions`, `--extension <source>`, `<source>`, `--models`, `--force`, combined flags), `config` without `-l`, `install|uninstall|remove` and `mcp login|logout` run in an empty `<state>/mcp-login-<random>/` folder so no project config loads (pi reads project settings only from `<cwd>/.pi/settings.json`, so a project `npmCommand` never runs on the host); `update`, `config` and `mcp` get `PI_CODING_AGENT_DIR` set to the host agent dir; `mcp add|remove` run in the cwd. After an `update` exits 0 whose target includes pi itself as pi parses it (bare, `--self`, `--all`, `pi`/`self`, `--self --extensions`, `pi --extensions`; not `--extensions`, `--extension <source>`, `<source>` or `--models`), the launcher names the pi version the sandbox follows. A source counts as remote only as a plain `npm:<name>[@version]`, an `http(s)://`, `ssh://` or `git://` git URL with owner and repository, or `git:git@host:owner/repo` and `git:host.tld/owner/repo`; every other source is a local path, handed over as an absolute path (an `update` source that looks like a path, starting with `.`, `~` or `file://` or holding a `/`, is made absolute the same way). `install` refuses a local source whose path or real path lies in a git working tree (ignoring a git root no sandbox could hold, such as a home folder) or in a folder a sandbox has run in (the repository records under the state dir), wherever it is started. An `npm:` spec that names a path or another protocol (`npm:file:…`, `npm:link:…`, `npm:/…`) is refused too.

Commands that start no session run on the host too; `cli/host-routes.ts` decides, and what it does not recognise launches. `--help`, `-h`, `--version`, `-v`, `--list-models [search]` and `--export <file> [out]` count only as the whole command line, so a flag value (`--system-prompt --version`), a word after `--` or any other flag launches. A subcommand wins, as in pi: `-h` or `--help` anywhere after `install`, `remove`, `uninstall`, `update`, `list` or `config` is that command's help, bare `mcp`, `mcp help` and `mcp … --help` are mcp's help, and `auth …` always runs on the host. Help, `--list-models` and `auth` run host pi in the empty folder with `PI_CODING_AGENT_DIR` set to the host agent dir. Pi builds a runtime for top-level `--help` and `--list-models`, so they get `--no-extensions --no-skills --no-prompt-templates --no-themes --offline`: no extension (built-in ones included) or package resource loads and no missing package is installed, at the cost of extension flags in the help and extension-only providers in the list. Subcommand help, mcp's help and `auth` return before pi reads any package or extension. `--export` runs in the cwd, since pi exports before it loads any settings resource or extension and reads only the session file. `--version` starts nothing: it prints `imagePiVersion` of the resolved host pi, the version the image is built with, unless `image.reference` and `image.digest` pin an image, when pi inside answers. `pi list` stays inside, since host pi in a trusted project runs the project's `npmCommand` to find a global package, as do `mcp list`, `config -l` and `install -l`. Without a host pi these fail as `mcp login` does.

`cli/host-pi.ts` resolves one host pi for everything (host jobs, `--no-sandbox`, `pi update`, the doctor line): pi's managed install in the host agent dir first (`locateManagedPi`: the `install/managed-install.json` marker, `install/current-version`, the release's pi package with a safe version and a `bin` entry inside the package, and an executable `bin/pi`), and only without it the pi of `npm install -g` (`locateNpmPi`): the `npm` found on `PATH` asks `npm root --global` from the home folder (so no project `.npmrc` sets the prefix, 10 s limit) with its own folder first on `PATH`, the root must be an absolute path named `node_modules`, and the package `<root>/@earendil-works/pi-coding-agent` passes the same manifest check. `hostpi/locate.ts` only locates: the package's real path must lie inside the real global root and the entry's real path inside the package's, so an `npm link`ed pi is never used, and it keeps `npm`, the package folder and the entry only when the caller's `accept` predicate takes each path and its real path. `cli/host-pi.ts` computes `workspace`'s `sandboxWriteRoots` once per lookup (the folders state records a sandbox in, and the launch folder and its git root when a sandbox could hold them) and accepts a path whose path and real path lie outside all of them. The check is made at lookup, not again when the proxy reruns `HostPi.command`. It is narrower than `isSandboxWritable`, the test `pi install` applies to local sources, which refuses any git working tree a sandbox could hold: Homebrew's `/opt/homebrew` and nvm's `~/.nvm` are git checkouts, and their npm and global packages must stay usable. Nothing else is used: not a pi in the launcher package's or a checkout's `node_modules`, not a `PATH` pi, so how the launcher itself was installed does not matter. Without either, the launch notice, the doctor's `host pi` line, `--no-sandbox`, a bare `pi update` and every intercepted command print the same line (`missingPiText`): no managed pi in the agent dir and none in npm's global packages, that a `PATH` or project pi is not used, what is lost (provider credentials, host commands, `--no-sandbox`) and the remedy (pi's own installer or `npm install -g`, then `install.sh` again). `install.sh` requires one of the two in both modes, after its preflight and before it starts Colima or runs npm (for npm only that `npm root -g` from the home folder holds the package's `package.json`; the launcher applies the full check at run time). A `HostPi` carries `command` (the entry under the launcher's Node), `hostJob` (the argv prefix host jobs, `--no-sandbox` and a bare `pi update` run, through `spawnHostJob`), `version`, `packageDir` and `location` (the path the doctor and the `--no-sandbox` warning print). For the managed install `hostJob` is its wrapper `<agent dir>/bin/pi` (the wrapper picks the current release, puts the Node pi's installer brought on `PATH` for pi and its child processes (npm for `pi install`) and sets `PI_MANAGED_INSTALL_ROOT`); for npm it is `command`, the launcher's Node and the package's entry, and `location` is the package folder. The proxy's `pi auth` and `pi mcp login` and the launch-start MCP sign-in always run `HostPi.command`, which is part of the proxy input. Nothing records which pi was picked, only what it was used for (the image's pi version, the proxy input's pi command), so a host pi update rebuilds the image at the next launch and restarts the proxy at the next launch that is alone in the repository. Without a host pi the image takes the pi version the launcher is tested with (`testedPiVersion`, the root `package.json` devDependency).

## Config

`SandboxConfig` is the defaults with the one config file, `<agent dir>/pi-sandbox/config.json` (`PI_SANDBOX_USER_CONFIG` overrides the path), laid over them (`config/`). The file belongs to the user who runs the launcher; there is no other layer. It is validated by a hand-written key spec, whose node types include a `map` (a check for each key and a spec for each value, messages naming `<key>["<name>"]`), used by `env.set`; `schema/sandbox-config.schema.json` documents the same keys, and tests keep the key sets and the string constraints equal. One host grammar (`config/egress-entry.ts` `parseHostEntry`) checks every host field and the egress commands, and the proxy uses its `isHostName`. A validation message names the key and, for paths, names and choices, the value (cut at 200 characters, JSON-escaped when not printable); host, credential and `npmGlobal` values are never shown. `validateConfig` passes every message through `printable`, so no key name or value brings a control, bidi or line separator character to the terminal.

- A key the file sets replaces the default, per leaf key (`workspaceRoots` and `env.set` count as one, so a file's `env.set` replaces the default empty map whole); a list the file sets adds to a non-empty default list, which only `env.allow` has (the terminal variables). `config/merge.ts` records each key's source, `default` or `config`, for `pi sandbox config`.
- `egress.allow` (empty by default) follows `pi.dev` (port 443, that name only, no credential), which pi fetches its model list from at start and which every allow list holds (`config/egress-allow.ts`); `egress.deny` still wins over it. Grants are always on and `--no-sandbox` always runs host pi. `config/parent-proxy.ts` is the one reader of `HTTPS_PROXY` (else `https_proxy`) and `NO_PROXY` for the launcher, the proxy, the image build and the doctor; a parent proxy is used whenever the shell that runs `pi` sets one.
- `image.reference` and `image.digest` are set together or not at all; without them the image is built locally.
- `terminal.clipboard` (on by default) turns the clipboard bridges on a Mac on or off (see Container). `pi sandbox init` does not own it, so it keeps it as written, and it is no write-back key.
- `vm` (`cpus`, `memoryGiB`, `diskGiB`, whole numbers within 1-64, 2-256 and 20-2048) sizes the VM; `resources` limits each container inside it (`pids` 256-4194304, default 4096; `openFiles` 1024-1048576 and `shmMiB` 1-262144, sent only when set; the bounds are `RESOURCE_BOUNDS` in `config/validate.ts`, which the schema test pins), and a `resources` value above the matching `vm` value is a config error, since such a container could never get it.
- `mounts.volumes` entries are a target string or `{ target, name? }`; a target is absolute or starts with `~/` (`/home/pi/...` must be written as `~/...`), and two entries may not name the same volume. The volume is `pi-sandbox-shared-<install id>-<hash of the identity>`, shared by every repository of this state dir and by the services that name it. The identity is `name` when set, else the target as written, so renaming a target without a `name` starts a new volume. `configVolumeName` (`container/names.ts`) is the one function that names such a volume; it carries only the managed and install labels. A service that mounts a volume the agent also mounts must run as the default service user (`1000:1000`, the agent's `pi`).
- `mounts.binds` entries are `{ source, target }`, always read-only; `source` is an absolute host path or starts with `~/`.
- Every mount target is checked twice: `config/validate.ts` refuses a configured target that overlaps a reserved tree (`GUEST_TREES` in `shared/state-layout.ts`: the system trees `/usr`, `/bin`, `/sbin`, `/lib*`, `/boot`, `/dev`, `/proc`, `/sys`, `/run`, `/var/run`, `/var/lock`, `/root`, `/opt/pi-sandbox`, `/etc/ssl` and the loader, account and name-service entries of `/etc`; the target may be neither inside nor above them, so `/`, `/etc` and `/var` are refused while `/etc/<app>` and `/var/lib/<app>` are not) or is or lies above a mount point the launcher owns (`/home/pi`, `/tmp`; a target inside them is allowed), that is, lies in or lies above a marker file (`GUEST_MARKERS`: `/tmp/pi-sandbox-handover`, `/tmp/pi-sandbox-ready`, `/tmp/pi-sandbox-forward`), that lies under `~/.pi`, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `~/.config` or `~/.local/bin`, that two entries share or that lies inside another entry; `container/spec.ts` applies the same reserved rule to every mount of the spec except the render binds the launcher puts in `/opt/pi-sandbox`, refuses a target mounted twice, and refuses a configured target that nests with any other mount (the repository, git dirs, overlays, the agent volume, the session dir).
- `setup` is a list of argv lists, run at every launch (see the pipeline, step 9).
- `writeBack` adjusts the write-back allowlist (see Provisioning) inside a ceiling the code owns. The built-in table and the ceiling live in `shared/write-back-table.ts` as plain data (file, key, value spec), so `config/validate.ts` checks the file against the ceiling and `provision/` compiles the specs into checks without importing `config`. `config/write-back.ts` resolves the effective table: no file at all when `enabled` is false, else the built-in table without the `exclude` keys, with each `add` key replacing a built-in key's spec in place or appended, and each new `add` file appended. `cli/launch.ts` resolves it once per launch from the config the launch loaded and hands the same table to the launch-start and the end-of-launch write-back. `pi sandbox config` lists the effective keys of each file with their source (`default` or `config`), one `# writeBack <file> <source>: <keys>` line each, and `--json` adds them as `writeBack`.

`pi sandbox init` is the one writer of the config file, and only on the user's command: after Apply at a terminal, or with `--yes`. It changes only the keys it owns (`workspaceRoots`, `vm.cpus`, `vm.memoryGiB`, `vm.diskGiB`, `writeBack.enabled`): it re-reads the file just before writing and refuses when it changed since setup read it, writes through `writeFileAtomic` keeping the file's mode (0600 for a new file, in a 0700 folder) and its target when it is a link, keeps every other key and the key order, and re-indents the file with the indentation it detected. Nothing else in the launcher writes the file.

## Backend

Colima is the only engine. A `Backend` (`backend/types.ts`) is the only thing that talks to it, and the seam tests replace with a fake. `backend/colima/` speaks the engine HTTP API over `~/.colima/pi-sandbox/docker.sock` with `node:http`, and owns the VM as `Backend.vm` (start, shares, trust store, size and the restart to the `vm` size, stop, and for the setup `inspect`, which reads the profile's state, size and shares within 3 s, and `apply`, which under `vm.lock` creates an absent profile with `--vm-type vz --mount-type virtiofs`, the size and the mounts, leaves a stopped one to the next launch, defers while other launches are live, and otherwise restarts a running one whose size or shares differ). It pulls by digest, builds through the classic build endpoint, creates the agent container with `AutoRemove`, typed mounts (a missing bind source fails the create), every capability dropped except `CHOWN`, `no-new-privileges` and the `resources.pids` process limit (4096 by default), with a `nofile` ulimit from `resources.openFiles` and a `ShmSize` from `resources.shmMiB` only when set (`backend/colima/container-body.ts`), runs execs over a hijacked stream with backpressure (the output demultiplexer works through each chunk in slices of 16 KB), manages labelled volumes, networks and relays, and imports only `shared`. Every container carries `pi-sandbox.role` (`agent`, `relay`, `pod` or `service`); `roleOf` (`backend/labels.ts`) reads it, and a container without it is ignored. Every object the backend creates carries `pi-sandbox.managed` and `pi-sandbox.install` (the install id, a short hash of the state dir), and the container, volume and network listings return only this install's objects; `listOtherInstallSessions` returns the running agent containers of other installs. Image listings are not scoped to the install. The role decides every listing, so a pod or service is never taken for a session: `isSession` (an agent) counts the running sessions that keep the host session sweep off (`cli/host-sessions.ts`), the sessions `pi sandbox status` shows, the dead launches the sweep removes (`cli/sweep.ts`), and the launch's own container at its end (`removeLaunchContainer`). The sweep's removal of a repository's engine side (`clearEngine`, `cli/sweep.ts`) removes only the repository's agent containers; the relay, the pod and the services carry no repository label and belong to the install (`removeEngineGround`, `cli/ground.ts`). `busyLaunches` (`cli/busy.ts`) counts this state dir's live launches; `vmSessions` adds the running agent containers of other installs and their names (`VmBusy`), and is what holds a VM restart or stop, `pi sandbox init`'s apply and the uninstall: they see another install only through its running agent containers, so a launch of another install that is still preparing is not counted. Every refusal or deferral that another install's session causes (stop, a share restart, a size change, the trust store, the uninstall) names those containers and says `remove a leftover with docker --context colima-pi-sandbox rm --force <name>` (`busyText`, `backend/colima/profile.ts`). The setup screens show only the count. The services code picks pods and services by `roleOf`. Every `ContainerSpec` names its `capabilities` and `autoRemove`; the optional fields (`user`, `entrypoint`, `command`, a `container:<id>` network that joins another container) are left out of the agent's body, which stays byte for byte the same (`tests/backend/container-body.test.ts`). `inspectContainer` reads a container's state, exit code (left out when the engine reports none, so a service's error says `unknown`) and labels; the check whether a container that failed during startup still runs and the doctor's sessions-share check inspect it by id instead of listing (an inspect error counts as running), `containerLogs` its last lines, and `stopContainer` waits the grace period plus the call timeout. `buildImage` takes `BuildOptions` (`args`, `progress`, `offline`); the layer passes `offline` when it fetches nothing. The agent container and the pod name `CHOWN` (`HANDOVER_CAPABILITIES` in `container/spec.ts`), only for the launcher's own root exec that hands volume roots to their user (the agent's volumes to `pi`, the service volumes to each service's user); pi itself runs as uid 1000 with no capabilities, and a service spec names an empty list and gets none. The relay container drops every capability, runs with `no-new-privileges`, a read-only root and at most 1024 processes; it runs one node process as `pi` on port 3128, which needs no capability. Before it creates the install's network, the adapter reads the engine's version and refuses one older than 28.0 (`the sandbox VM runs Docker Engine <version>, and the sandbox network needs 28.0 or later to keep the VM itself off it`, hint: update colima, then delete and recreate the sandbox VM), since older engines ignore the isolated gateway mode. `removeContainer` resolves only once the engine has removed the container, within 30 s, else it fails with the hint that the next pi start removes what is left, and removes the container's anonymous volumes with it. `removeNetwork` removes the install's network (found by its labels) and takes an engine answer that it is gone or still in use (`404`, `409`, `403`) as done, so the teardown leaves a network a container still holds.

Requests other than builds, pulls and execs give up after 30 s without an answer, volume and image removals after 10 minutes and the ping after 5 s, and the error names the request; a container removal returns only once the engine has finished it, and gives up after 30 s for the delete and 30 s for the wait, or 10 s each for the relay, whose replacement runs under the ground lock. An answer that stops halfway is reported as closed by the engine, with the advice to run the command again. When colima reports the VM running but its engine does not answer the ping, the launch says so and advises `colima stop --profile pi-sandbox && colima start --profile pi-sandbox --activate=false`. An exec whose host output is closed ends quietly with the exec's exit code. A container name that is already taken is reported as an unexpected clash. A launch prepares the install's network and the relay under the ground lock, so two launches never create them at once; an outdated relay is removed, and its replacement created once the engine has finished the removal. A conformance suite runs the same tests against the adapter on an in-process engine, against the fake backend, and against the real engine in the live tests.

## Network

- **One proxy per install.** One proxy process, `proxy/daemon.ts` (`dist/proxy/daemon.js` in a published install), on `127.0.0.1` of the host, shared by every launch of this state dir. It reads its `ProxyInput` (allow and deny lists, rules, derived hosts, `env` secret values, parent proxy, token) from stdin at start, and afterwards only the egress settings from `egress.json` (below); the parent proxy's credentials arrive separately from the `HTTPS_PROXY` it is handed and are put back into that URL only in memory. It records `{ pid, boot, start, port, inputHash }` in `proxy/proxy.json`. The launcher starts it with `<state>/proxy/` as its working directory, waits up to 10 s for its health check, and on failure quotes the daemon's own tagged line (`pi-sandbox-proxy failed: …`) from `proxy.log`. A live proxy with the same input hash is reused once its health check answers, within three tries; one that does not answer is replaced when no other launch of this state dir is live (`busyLaunches`, `cli/busy.ts`), else the launch stops with `the pi-sandbox egress proxy (pid <n>) does not answer, and other pi sessions use it, so it was kept`; one with another hash is replaced only when no other launch of this state dir is live, else kept with the notice `the credential, parent proxy or CA settings changed; the pi sessions running in the sandbox keep the earlier ones until they all exit (egress allow and deny changes apply now)`. The input hash covers the rules, `env` secret values, the parent proxy's address, `NO_PROXY` (`parentEnv`) and credentials, the extra CA file, the host pi command, the host agent dir and the access-log limit, not the egress settings: every launch writes `egress.allow`, `egress.deny`, `egress.privateHosts` and the derived hosts to `proxy/egress.json` (mode 600), which the running proxy re-reads when the file changes, as it does `grants.json`, so a tightened or loosened egress policy reaches every session of this install from the first CONNECT after a new launch rewrote the file (editing the config alone changes nothing for running sessions), and that launch prints `the network allow and deny settings changed and now apply to every pi running in the sandbox` when other sessions are live. The last launch to write the file sets the policy for all of them. Each CONNECT is decided against one snapshot of those settings; tunnels and terminated connections already open stay until they close, and a missing, unreadable or garbled file keeps the last good settings and is read again at the next CONNECT; concurrent CONNECTs share one read. The proxy checks the launch registry every 30 s under its lock and exits after two checks in a row find no live launch.
- **Token and preamble.** The guest proxy URL is `http://pi-sandbox-proxy:3128`, with no credentials. The token (`proxy/token`, 32 random bytes, mode 600) admits a caller to the proxy, and only the relay and host-side callers hold it: every connection to the proxy port must open with the line `PI-SANDBOX <token>\n` (`proxy/preamble.ts`). The proxy reads that line on the raw socket before its HTTP server sees a byte: at most 128 bytes, within 5 s, compared as a sha256 with `timingSafeEqual`; anything else is closed without a reply and without a log line, and the bytes after the line go on to the HTTP server. The relay writes the line on each upstream connection it opens; the launcher's own calls (the health check, the denial reader, the doctor) write it through `connectWithPreamble`. No HTTP header carries the token: a `Proxy-Authorization` a client still sends is ignored, a terminated request never forwards it, and the proxy never answers `407`. The proxy answers `/healthz` and `/denials` as plain requests and refuses every other plain request as `plain-http`, so a client inside reaches the same two routes through the relay and nothing more. The token survives proxy restarts and is deleted when the ground is torn down (see Lifecycle).
- **Relay and alias.** Containers join only their install's internal network `pi-sandbox-network-<install id>` (`networkName`, `backend/install.ts`) and have no route out. `prepareNetwork` (`backend/colima/networks.ts`) creates it internal, with `EnableIPv6: false`, `com.docker.network.bridge.gateway_mode_ipv4=isolated`, the managed and install labels and no `IPAM` settings (the engine picks the subnet), so the engine gives it no gateway: the VM has no address on it, and a container on it has only the on-link route and no default route, so the VM's own services (its ssh, the engine), `host.lima.internal` and public addresses answer `ENETUNREACH`; nothing reads its `IPAM` gateway. The network's embedded DNS answers no outside name (`EAI_AGAIN`), so a tool leaves resolution to the proxy (a CONNECT by name). A network of that name without the managed label stops the launch (`network <name> exists but is not managed by pi-sandbox`, hint: remove that network from the sandbox VM so the launcher can create its own). A network of that name that carries the managed label is used as it is: only this launcher creates a network of the install's name, and it always creates it the same way, so the launcher does not inspect or replace it. One relay container per install, `pi-sandbox-relay-<install id>` (`relayName`), runs `node -e <relay script>` (`backend/colima/relay-script.ts`) from the sandbox image. It is created on the default bridge, then attached to the install's network, where it resolves as the alias `pi-sandbox-proxy` and as its container name and listens only on port 3128. The launcher reads the network's IPv4 subnet from its `IPAM` config and passes it to the script, and a network without one stops the launch with `network <name> has no IPv4 subnet, so the relay cannot tell the sandbox containers from other clients` (hint: exit every pi session, remove that network from the sandbox VM and start pi again). The relay listens on `0.0.0.0` and serves only clients whose address is inside that subnet: any other connection, such as one from the default bridge, is closed before an upstream connection opens. For each served connection it connects to the proxy port on `host.lima.internal`, writes the preamble and pipes both ways. The preamble reaches it in `PI_SANDBOX_RELAY_PREAMBLE`, which the script deletes from its own environment at start; the variable is visible to the engine API and nowhere in the agent container. The relay carries no repository label; its `pi-sandbox.relay-inputs` label is a sha256 of the preamble, the proxy port, the network's subnet and the script text, and the relay is recreated under the same name and alias when it is not running, is not on the network or any label differs (a new token, port, subnet or launcher); a name the engine has not released yet stops the launch with `relay <name> is still being removed by the engine, so its replacement cannot be created` (hint: run pi again in a minute). A replacement drops the connections other sessions have open through it; new connections use the new relay. `prepareProxyRoute` returns the network (`internal`, `pi-sandbox-network-<install id>`) and the address `pi-sandbox-proxy:3128` the agent container's spec takes.
- **Decisions.** A CONNECT is allowed for allowlisted, rule, derived and granted hosts on their ports; a host listed only for another port is denied as `egress.allow`, with a reason that names `host:port`. A rule host is terminated even when `egress.allow` also lists it. `egress.deny` wins, where an entry `d` denies `d` and every name under it and `*.d` every name under `d`. A CONNECT to port 80 and a plain HTTP request are refused as `plain-http`. IP literals, loopback, private and reserved ranges and the metadata address are refused. A name that resolves only to such addresses is refused with a 403 before the tunnel opens, for terminated and spliced hosts alike, unless `egress.privateHosts` names it; it is recorded as `private-address`, so it gets the `egress.privateHosts` hint; an IP literal or loopback name refused for its range gets the proxy's reason and the note that such hosts are never reachable instead, since `egress.privateHosts` rejects them. A tunnel that is not terminated must present a ClientHello whose SNI equals the CONNECT host before the proxy dials. A denied host gets a 403 page over TLS with a launcher-CA certificate for its name, carrying the grant hint. A terminated request whose upstream fails before the response headers answers `502` with the reason and is recorded as a denial (`upstream`, or the restricted-address rule when a rebinding answer is refused at dial time); a certificate failure adds a pointer to `tls.extraCa`, and the doctor counts a `502` as failed. Grants are read live from `grants.json`. Every decision is a JSON line in `access.log`; an allow names the rule that allowed it (`egress.allow`, `credential`, `grant-or-derived`, and `terminate` for a terminated tunnel). An unavailable credential is a `deny` line with rule `credential` whose reason names the credential and the resolver's reason, or with rule `login` and the reason `the <provider> login on the host is missing or expired` when host pi's `auth` command exits non-zero; the request is forwarded without it. Its denial record carries the rule id as `credentialRule`. No line holds a credential or a token.
- **Termination.** TLS is terminated only for rule hosts, with per-host leaves signed by the launcher CA; a leaf's key is written briefly under the state dir for openssl to sign and kept in memory after. Leaves are signed with `openssl ca` from a throwaway config in a temp work dir and are valid from an hour before the host clock to 397 days after it; a new CA is self-signed the same way (`openssl ca -selfsign`, valid from an hour back for 3650 days), and a CA already on disk is kept. So a VM clock up to an hour behind still accepts the CA and a new leaf. A client that closes the connection during the handshake without an alert, or sends a certificate alert (unknown CA, bad, expired or unknown certificate), is recorded at once as a `tls` denial whose reason names the launcher CA and the VM clock; one that closes or resets the connection before sending any byte is recorded as having left before its hello, while one that stays silent until the hello timer fires keeps the missing server name as its reason. A client that completes a TLS 1.2 handshake and then drops the connection is not told apart from a normal close. Upstream connections are pooled per host, port and access inside the proxy process. The check of a public name before the tunnel opens, the same check before a parent-proxy dial, each direct connect and the terminator's upstream TLS handshake give up after 10 s. A check before the tunnel opens that times out refuses the CONNECT without dialling, for terminated and spliced hosts alike: `502` with `upstream request failed: <host> did not resolve in time`, the body a terminated host's failed dial gets, and an `upstream` denial; any other lookup error lets the CONNECT go on to the dial, which resolves the name again and refuses restricted addresses. The other timeouts take the path of any other dial failure (`502 upstream request failed: …` and an `upstream` denial on a terminated host, an `upstream` denial and a closed tunnel on a spliced one); a handshake that times out or closes destroys both the TLS socket and the dialled socket under it. Nothing bounds a response once the handshake is done, since LLM streams run long. A parent proxy from `HTTPS_PROXY` is chained for upstream dials; an `HTTPS_PROXY` that is not an `http://` URL gives no parent route, and the launch warns and the proxy connects directly.

## Placeholders and secret sources

A placeholder is `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`; so placeholders are stable across launches and unguessable. A JWT access token gets a JWT-shaped placeholder: the launcher's own header (`{"alg":"none","typ":"JWT"}`), the token's payload without `exp`, `iat`, `nbf`, `jti` and `auth_time`, and the opaque placeholder as the signature, so it stays the same when the host refreshes the token and a consumer inside that reads an account claim still finds it.

On a terminated host, the proxy first drops every header that carries a placeholder of one of the host's other rules (another port or another path prefix). It then replaces the placeholder of the matching rule (host, port, decoded path prefix compared with the decoded path, which carries no query, so an encoded `?` cannot widen it) only in the rule's header, or in auth-like request headers for a rule without one, and strips stray placeholders from every other header. A rule with a `header` sets that header on every matching request. A placeholder is never substituted in a query or body. A `Basic` value is decoded, substituted and re-encoded, which is how git, npm, pip and Maven send passwords. Response headers are scrubbed of the secret and of the exact base64 the proxy sent. A dot-segment path or a cross-origin absolute target gets `400`. A request body sent chunked is forwarded chunked.

The secret comes from a source resolved on the host and kept in the proxy's memory only (`proxy/secrets/`): `env` (from the stdin input), `file` (a JSON pointer, or a key of an npmrc, ini or Maven settings file), `command` (stdout, or `{ token, expiresAt }` with `expiresAt` an ISO 8601 time; cached 300 s, or until `expiresAt` less 30 s; 30 s per run, a failed one retried at most every 5 s), `piAuth` (the host pi's `auth print-api-key` or `print-bearer-token`; a non-zero exit is reported as a missing or expired login, never with the command's output) and `mcpOAuth` (below). An upstream `401` invalidates a cached secret once. A failed lookup is retried at most every 5 s, except a host sign-in state (signed out, or a sign-in running), which is never cached, so a sign-in finished on the host is used by the next request.

Derivation (`hostpi/`) is pure: it turns the host `auth.json`, `models.json` and `mcp.json` into sandbox copies with placeholders and rules, and `hostpi/derive-tools.ts` adds the glab, npm, pip, Maven and git derivers (`hostpi/tools/`), which read host files and run host commands and render placeholder-only tool files.

- glab and git run only from absolute `PATH` entries outside the repository and its git common dir, each probe with a 10 s limit (the glab token probe and the provider host script 30 s; a probe that does not answer leaves that tool without credentials for the launch, with a notice). A `GLAB_CONFIG_DIR` or `XDG_CONFIG_HOME` path inside those roots is ignored with a notice. A glab host without a token gets the `no token on the host` notice, except an entry with neither a `token` nor a `user` field (never logged in to, like the `gitlab.com` entry glab writes by default) while another glab host has a token; a token probe that timed out always keeps its notice. The launcher has no gh integration: a user who wants gh installs it with `image.packages` and gives its token with `env.set` and `credentials.rules` (`REMOVED-DEFAULTS.md`).
- `auth.json`: a credential's `env` is copied, with placeholders for secret-named or credential-shaped values. A built-in provider whose key is only in the launcher's environment gets an `api_key` entry whose rule reads that variable (`{ env }`).
- `mcp.json`: a disabled HTTP server gets no rule and no sign-in; a server with `auth.provider` gets a rule on its host with that provider's placeholder and secret. Every other reachable HTTP server without a credential header gets the OAuth bearer. A header is a credential when its name is auth-like (authorization, a secret word, `auth`, `cookie`, `session id`) or its value has a credential shape or reads a host value; header names that differ only in case are merged, the last one winning. An absolute stdio `command` or `cwd` gets a notice. A `models.json` provider or model whose `baseUrl` has a secret-looking query parameter is dropped, as an MCP server is.
- npm and pip: a URL with userinfo in `.npmrc` (`registry`, `@scope:registry`) or `pip.conf` (`index-url`, `extra-index-url`) is rendered with a placeholder in place of the password, or of the user name when the token is the user name, and gets a rule on that host (for npm also the URL path) whose secret reads that part of the URL back from the host file. Other values with URL userinfo, npm and pip proxy settings, and values that reach userinfo through `${VAR}` stay on the host. `.npmrc` keys that name host paths (`prefix`, `cache`, `userconfig`, `globalconfig`, `init-module`, `script-shell`, `*file`) stay on the host with a notice. The pip config is the first of `~/.config/pip/pip.conf`, `~/Library/Application Support/pip/pip.conf` and `~/.pip/pip.conf`.
- Maven: the settings keep each profile's `id`, `activation`, `repositories` and `pluginRepositories` (never its properties), `activeProfiles`, `pluginGroups` and the mirrors, with URL userinfo removed and `localRepository` dropped with a notice; a server's password and its `httpHeaders` values become placeholders bound to the server's repository hosts (a header rule injects only in that header), a server with no credential field is copied unchanged, and one with only a private key stays on the host.
- A registry, mirror or index host with neither a credential rule nor an `egress.allow` entry gets a notice naming the entry to add; egress is not widened.
- Manual `credentials.rules` win over derived rules for the same host; `credentials.derive` filters or disables derived ones.

## MCP sign-in

MCP OAuth tokens stay in host pi's `<agent dir>/mcp-auth.json`, which the launcher only reads (`shared/mcp-auth-key.ts` is the one parser). The sandbox `mcp.json` has no `oauth` block; a server that gets the OAuth bearer has an `mcpOAuth` rule. Two triggers start `pi mcp login <name> --timeout 300` with the host pi, in an empty folder against the host agent dir:

- at launch start, when both input and output are a terminal, for each derived server whose token is missing or expired and has no refresh token (`cli/mcp-sign-in.ts`), interactively;
- in the proxy (`proxy/sign-in.ts`), when the token it injects has expired or was answered `401` upstream; a `401` to a request with the container's own `Authorization` starts nothing. The login runs in its own process group, which the proxy kills when it stops. While that login runs the request gets a local `503` (`pi-sandbox: sign-in to MCP server <name> opened in the browser on the host; finish it there, then retry.`); otherwise the request goes out without the credential. When the login the proxy started exits 0, the proxy uses the token host pi then holds even if its stored expiry has passed, until the server answers `401`.

A server for which the host holds no token gets its requests without a credential, so servers that need no sign-in work; a `401` to such a request starts no login and is answered with `pi-sandbox: MCP server <name> is not signed in on the host; run pi mcp login <name> on the host, then retry.` A `401` to an injected token answers "opened in the browser" when a sign-in starts, else "not signed in on the host", and the start spacing below applies.

Both triggers take one lock per server and record starts and failures in `<state>/mcp-login.json` (`lastStart`, `failedAt` and `rejectedStart` per server), written under its own file lock. The proxy starts at most one sign-in per server per minute host-wide and none for 10 minutes after a failure; a start caused by a `401` to an injected token that has not expired runs at most once per server per 10 minutes whatever its exit code. The launch-start sign-in runs once per launch and is skipped for 24 hours after a failed sign-in by either path, unless a later sign-in succeeded, printing `not signed in; run pi mcp login <name>` once (`seen.json`). Host pi's login refreshes a stored token silently when it can.

## Provisioning

`renderAgentDir` (`provision/render.ts`) writes `vm/render/<hash>/` on every launch under `render.lock`: the derived `auth.json`, `models.json` and `mcp.json`, filtered copies of the host agents, prompts, skills, themes, extensions and instruction files, of the host `~/.agents/skills` (pi's second user skills dir) into `agents-skills/`, and `tools/` (the Maven settings with the sandbox proxy and derived servers, and when derived the glab, npm, pip and git configs). The copy leaves out directories named `secrets`, `.secrets`, `credentials` or `.credentials` outside `node_modules`, secret-looking files, files over 8 MiB and private keys, follows no link, and one render notice lists what was left out and why; another names every skipped link (a render source that is itself a link included), except one: a direct child of the agent dir's `skills/` whose real path is a directory directly inside `~/.agents/skills`, when `~/.agents/skills` is itself a real directory and no link, since that skill arrives through `agents-skills/`; a link at any other depth, to a file, or anywhere under `~/.agents/skills`, is named. Both go through the once-per-repository notice file, so an unchanged notice is printed once. It is mounted read-only; the entrypoint links each entry into the agent dir, `agents-skills/` to `/home/pi/.agents/skills` (where pi looks for it with `HOME=/home/pi`), and the tool files into the home, copying the ones the tools must write. The Maven settings are linked too: their proxy is the literal `pi-sandbox-proxy` and `3128`, with `nonProxyHosts` `localhost|127.*|[::1]|pi-sandbox-proxy` and no credentials. `auth.json` is the exception in the agent dir: it becomes a regular 0444 copy, because pi locks it through its resolved path and a lock dir next to a link would land in the read-only render dir. The copy holds placeholders only. Every copy goes to a temp name carrying the entrypoint's pid, so concurrent containers of the repository never share one, and is then moved into place.

`syncVolumeFiles` (`provision/sync.ts`) runs under `sync.lock` and always writes back first, then syncs. The sync writes the filtered host `settings.json` into the volume: package URL credentials and the host `httpProxy` dropped, the host-owned keys (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`) and `sessionDir` left out, local package sources inside the repository handed over as absolute host paths (`file://` included), others skipped with a notice, and the entries of `extensions`, `skills`, `prompts` and `themes` placed for the container (`placedResource`): a plain path resolves against the host agent dir and `~` against the host home, a `!`, `+` or `-` entry or glob is placed only when it is rooted (`/`, `~`, `file://`, placing the part before the first glob segment), and relative patterns and `builtin:`-style names stay as written, since pi matches them against its own base dirs, whose layout the copy keeps. A plain entry is trimmed first, as pi trims plain entries and not patterns. A path inside the repository becomes its absolute host path; one anywhere inside the host agent dir (the copied entries and pi's own `git/` and `npm/` package installs on the agent volume alike) or inside `~/.agents/skills` becomes the same relative path under the guest agent dir or the guest `~/.agents/skills` (`/home/pi/.pi/agent/…`, `/home/pi/.agents/skills/…`), absolute because pi matches `+`/`-` entries against either a path relative to the base dir of the resource (the agent dir, or `~/.agents` for its skills) or the absolute path; any other entry is dropped with a notice, prefix kept. It copies the host `pi-subagents.json`, `pi-style.json`, `pi-notifications.json`, `pi-session-limits.json` and `pi-prune.json`, and every other `pi-*.json` the write-back table names, into the volume as they are (not through the read-only render dir, so they stay writable inside), and removes the volume copy of one the host lacks or holds as no JSON object. It also removes the volume copy of each `pi-*.json` the last sync recorded as copied that the table no longer names (a file that left `writeBack.add`, or every added file once `writeBack.enabled` is false); a `pi-*.json` the launcher never copied, such as one an extension created inside, stays, and a baseline without a `copied` list removes nothing. With `writeBack.enabled` false the table is empty: nothing is written back, while the filtered `settings.json` and the five built-in `pi-*.json` files are still copied in, since pi in the sandbox reads them. It then records, in `<state>/repos/<h>/sync/baseline.json`, the allowlisted keys of what it wrote, a hash of the effective table (`allowlist`) and the names of the `pi-*.json` files it copied (`copied`).

Npm and git packages follow the host (`provision/host-packages.ts`, `provision/package-refresh.ts`). Pi in the container installs a configured package only when it is missing or, for npm, when the installed version does not satisfy the version in its source; it never refreshes an existing git checkout at start. So the sync pins the npm and git sources of the volume `settings.json` to what the host has installed, read from host files only. An npm source without a version, or with a range or dist-tag (only `[0-9A-Za-z.^~<>=|* -]`, no `:` or `/`), becomes `npm:<name>@<version>` from `<agent dir>/npm/node_modules/<name>/package.json` when that manifest's `name` is `<name>`; an exact pin (`npm:x@1.0.0`), an alias (`npm:x@npm:other@2`), a hosted, URL or file spec keeps the source as written and gets no record, since the host settings decide it. A git source gets `@<commit>` in place of its ref, the commit read from `<agent dir>/git/<host>/<path>/.git/HEAD` (a loose ref or `packed-refs`), only when that commit is the value of a `refs/remotes/origin/*` ref or a tag of the checkout (loose, packed, or the peeled `^` line of an annotated tag), so the sandbox's fresh clone can check it out; a host commit not on the remote (local commits, an upstream force-push) leaves the source as written and is recorded as `unpinned:<commit>`. `git:` is the shorthand prefix only when not followed by `//`, so `git://host/u/r` is a protocol URL. The host of a source is the one pi installs under: lowercased, without `www.`, for the hosts pi resolves itself (github.com, gitlab.com, bitbucket.org, gist.github.com, git.sr.ht), as written otherwise; a `#ref` fragment source does not place and is left unpinned. A package the host has not installed there (a legacy global npm install, a checkout the parser cannot place) keeps its source. Pi inside then reinstalls an npm package whose version changed by itself. For git, the launch-start sync (not the end-of-launch sync) compares the commits with `<state>/repos/<h>/sync/packages.json`, the identities and versions it saw last time, removes the volume's `git/<host>/<path>` checkout of each git package whose recorded value differs or is not recorded (all of them when the record is missing or garbled, so such a launch re-clones every git package once), then writes the record. Host and every path segment must match `[A-Za-z0-9._-]+` and not be `.` or `..`, with at least two path segments, since the host `settings.json` is also written by extensions; a source that fails this keeps its source, gets no pin and is never removed, and the removal checks each `git/…` path again before it runs. The removal script refuses a target any of whose parent folders below the agent dir is a symbolic link (planted by an agent in an earlier session) and names it; it runs under a 60 s host-side timeout. While another launch of the repository is live, nothing is removed, the stale git entries keep their old value in the record while the npm packages and unchanged git packages are recorded, the settings are still pinned, and one line says `sandbox packages follow the host: git packages refresh at the next launch (another session is running)`; one line, `sandbox packages follow the host: reinstalling <n> packages`, counts the recorded packages whose version changed, printed before the deferral line when both apply. A failed, refused or timed-out removal prints a warning and leaves the record, so the next launch tries again. Nothing is read from the container for this; the record lives on the host and only steers what is removed in the volume. An unchanged launch costs no exec and no network call. When the registry or git host is not reachable from the sandbox, pi inside reports the package as failed to install, as for any missing package, and does not load an old copy.

The write-back (`provision/write-back.ts` is the pure part: allowlist, three-way merge, lines) runs in the launcher's host process, never in the container, at every launch after the container exists and before the sync (this recovers changes left by a killed session or by another live session sharing the volume) and at the launch's end after pi exits and before the container is removed; `pi sandbox doctor` writes back before its sync too, so it never drops a live session's change. Without a baseline (the first launch) nothing is written back, and a baseline whose `allowlist` hash differs from the launch's table (or that lacks it) counts as none, so any change of the effective table costs one write-back on purpose: the sync then records a fresh baseline under the new table, and a live session of the old table writes nothing back at its end. A sync that finds a baseline of another `allowlist` hash prints `pi-sandbox: the write-back list changed; nothing is written back from sessions started under the old list`. The built-in table (`shared/write-back-table.ts`): in `settings.json` `defaultProvider`, `defaultModel`, `defaultThinkingLevel`, `enabledModels`, `theme`, `hideThinkingBlock`, `quietStartup`, `collapseChangelog`, `doubleEscapeAction`, `treeFilterMode`, `steeringMode` and `followUpMode`; in the first four `pi-*.json` files the top-level keys their extensions read, as type `json`, except `disabledPlugins` of `pi-subagents.json`, which the extension reads from the user file only, so it stays host-owned; in `pi-prune.json` only `days`, as an `enum` of `0`, `7`, `30`, `60`, `90`, `180` and `365` (the choices of `/prune`, written literally since the launcher imports nothing from the extensions), because that value decides what the host deletes. The value spec vocabulary is fixed: `string` (`maxLength`, at most 512), `boolean`, `integer` and `number` (`min`, `max`), `enum` (`values`), `stringList` (`maxItems`, strings of at most 512 characters), `fileName` (the theme-name rule below), `anyOf` (`of`, nested at most 4 levels deep) and `json` (any value; the byte cap of the file bounds it); there is no user regular expression. The ceiling, checked by the config validator and applied again by `provision` before it compiles a table: a file is `settings.json` or `pi-<lowercase letters, digits, dashes>.json` directly in the agent dir, never `auth.json`, `models.json`, `mcp.json`, `mcp-auth.json` or `trust.json`; `settings.json` never takes the host-only keys of `provision/merge-settings.ts` (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`, `httpProxy`, `sessionDir`), `packages`, `extensions`, `skills`, `prompts`, `themes`, `defaultProjectTrust`, `modelOverrides`, `sessionShareDestination`, `defaultTools`, `enableAnalytics`, `enableInstallTelemetry`, `trackingId` or `deviceId`, nor a `json` spec, and its `theme` keeps the `fileName` spec; `pi-subagents.json` never takes `disabledPlugins`. `writeBack.exclude` may name only built-in keys of built-in files, and a key both excluded and added is a config error. `schema/sandbox-config.schema.json` holds the file names, the never-written key names, no `json` in `settings.json` and its `theme` only as `fileName`; `min` above `max`, an exclude key off the built-in list, a key both excluded and added and the `anyOf` depth only the validator checks, and the schema's descriptions name them. The byte caps, the read timeout, regular-file-only reads, the merge, the notice filtering and the atomic write below are not configurable. Each volume file is read through `sh -c` exec (`readVolumeText`, regular files only, at most 64 KiB for a `pi-*.json` and 1 MiB for `settings.json`, given up after 5 s on the host side through the exec's abort signal; the doctor's `readVolumeFile` of `mcp-auth.json` and `settings.json` reads through it with a 1 MiB cap, counts an empty or whitespace-only file as missing and reports one over the cap or not a JSON object as not a JSON object; the `mcp-auth sweep` fails a file it cannot read with the reason); one missing is skipped silently and one not a regular file, unreadable, over its limit or not a JSON object is skipped with a notice, so a lost volume never deletes host keys. Each value is checked against its spec before it is written; with the built-in table: `defaultProvider` and `defaultModel` strings of at most 512 characters, `enabledModels` a list of them, `hideThinkingBlock` and `collapseChangelog` booleans, `quietStartup` a boolean or `header`, `theme` a file name of `[A-Za-z0-9._-]` other than `.` and `..` (host pi joins it into a path), and `defaultThinkingLevel`, `doubleEscapeAction`, `treeFilterMode`, `steeringMode` and `followUpMode` one of pi's own values; a failing change is dropped with `<file>: <key> in the sandbox is not a valid value; not written back`. The built-in `pi-*.json` keys are `json`, left to their extensions' schemas, except `pi-prune.json` `days`, an enum. Per key, with B the baseline, V the volume and H the host, compared by deep JSON equality (an absent key is a value): V = B or H = V leaves it; H = B writes V to the host (a deletion included); otherwise the host wins with `<file>: <key> changed on the host and in the sandbox; kept the host value`. The host file is re-read right before the write, a host file that is no JSON object is skipped, every other key is kept, a link is written through to its target, and the write is atomic in the target's dir with its mode kept; a missing host `pi-*.json` is created only from a volume copy. Each applied change prints `pi-sandbox: <file> <key>: <old> → <new> written to the host` (values cut at 60 characters, control, bidi and line separator characters shown as `\uXXXX` escapes, the same rule as the prompt's); nothing prints when nothing changed. A write-back failure prints one warning line and never fails the launch or changes pi's exit code. When the sync into the volume fails it replaces the baseline with a record of only `copied` (the earlier names and the ones this sync meant to copy), so the next sync writes nothing back but still removes copies the table dropped, and warns that later changes will not be written back. Nothing else from the volume (`auth.json`, `models.json`, `mcp.json`, `trust.json`, agent files, keys outside the table) reaches the host.

## Host sessions

With `sessions.host` on, the container binds host pi's session directory of the repository at its host path and `PI_CODING_AGENT_SESSION_DIR` points pi at it. The slug is pi's formula, copied since the launcher may not import pi. `assertHostSessionsDir` (`workspace/guard.ts`) is the one exception to never mounting under `~/.pi`: the directory must be exactly one level under `<agent dir>/sessions`, a real directory, and overlap no other agent dir entry. `provision/host-sessions.ts` creates missing directories 0700, probes the share from inside, and sweeps the directory before each launch, after pi exits and before `--no-sandbox`: it deletes links and special files and renames session files whose header `cwd` lies outside the repository (or cannot be read) to `.rejected-<random>`, reading headers as pi does. A file the sweep cannot rename is reported and kept, never deleted, and the next launch refuses until it is fixed. The whole tree is swept only while no other launch of the repository is live and no container of it runs, under the repository's preparation lock, and only when that lock is free.

## Container

Every launch creates its own container and removes it when its pi exits. Its name is `pi-sandbox-<h12>-<launch id>`; its labels are the managed flag, the install id (both set by the backend), the role `agent`, the repository hash and root, the launch id, the image digest and the session dir. A launch never joins another's container, so container settings apply at the next launch. The agent and overlay volumes are per repository (in workspace mode, the workspace root) and shared by its containers; the proxy, the relay, the network and the services are per install (one state dir) and shared by every container of it. Containers run with `AutoRemove`.

The container drops every capability except `CHOWN`, runs with `no-new-privileges` and at most `resources.pids` processes (4096 by default), and pi runs as the image's `pi` user (uid 1000) without capabilities. The spec mounts the repository and git common dirs read-write at their host paths, binds onto themselves the common dir and the folders between the repository root and each hooks dir (so none can be renamed away from its mounts), then each hooks dir read-only straight from the host. In a workspace it also binds each bare dir read-only and the folders between the workspace root and each nested repository and bare dir onto themselves. It adds the render dir read-only, the host session dir, the agent volume, the build output overlay volumes, then the `mounts.binds` entries, each read-only, and the `mounts.volumes` entries. The container joins its install's network `pi-sandbox-network-<install id>` (see Network), also when services run. No CA is mounted: trust is baked into the image layer (see Image). A build output overlay that lies inside a git dir or a read-only mount is left out with a notice (`<path> is not overlaid: it lies inside <guard>, which the sandbox protects`). The spec refuses a target mounted twice, a `mounts.volumes` or `mounts.binds` target that equals, holds or lies inside another mount (`mounts: the sandbox would mount <a> and <b> inside one another, refusing`), and, except for its own render binds, a mount that breaks the reserved rule of Config (`GUEST_TREES`, the mount points `/home/pi` and `/tmp`, `GUEST_MARKERS`): `workspace: the sandbox would mount <path> over <reserved>, which the sandbox image needs, refusing`. As a backstop it refuses (`workspace: the sandbox could write in <dir>, which the launcher did not search for repositories, refusing`) when, for an overlay folder, the mount with the longest target over it is not a volume or a read-only bind, or a writable bind has its target or source inside it. Mount points are created as the host user, one level at a time, after a real-path check, so no spelling (case, links) creates one inside a protected path. Volume names, with the install id the short hash of the state dir: `pi-sandbox-agent-<install id>-<h12>`, `pi-sandbox-cache-<install id>-<h12>-<8 hex of the repository-relative path>` (overlays) and `pi-sandbox-shared-<install id>-<8 hex of the name or target>` (`mounts.volumes` entries and service volumes, both through `configVolumeName`, `container/names.ts`). Every volume carries the managed and install labels. The agent and overlay volumes also carry the repository hash and root (overlays also the cache path); shared volumes carry nothing else, so nothing per repository removes them, and a `mounts.volumes` entry and a service volume of the same `name` are one volume.

The root is read-only with tmpfs `/tmp` and `/home/pi` (exec allowed), under an init process, as the image's `pi` user. The environment holds the proxy variables, which carry no token (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY` in both cases, all `http://pi-sandbox-proxy:3128`, and `NODE_USE_ENV_PROXY`; JDKs get the proxy from the layer's `net.properties`, Maven from the rendered `settings.xml`, and `JAVA_TOOL_OPTIONS` is the user's), the CA paths (`SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `GIT_SSL_CAINFO` and `NODE_EXTRA_CA_CERTS`, all `/etc/ssl/certs/ca-certificates.crt`, the system store the image layer wrote), the derived tool variables (the `GITLAB_TOKEN` placeholder and `GITLAB_HOST`), `GIT_TERMINAL_PROMPT=0`, `PI_SANDBOX=1`, `PI_SANDBOX_STATUS=/opt/pi-sandbox/render/tools/status.json` and pi's own switches (no version check, no telemetry, OSC 52 clipboard), with `NO_PROXY` and `no_proxy` set to `localhost,127.0.0.1,::1,pi-sandbox-proxy` so a client reaches the container's own servers directly and asks the proxy's `/healthz` and `/denials` without proxying to itself. `env.set` is laid under these in the spec, so it reaches every exec, and a launcher-set name, refused by the validator through the same `isLauncherSetVariable` list (`shared/pi-env.ts`) that `env.allow` uses, would still lose to the launcher's value. No host variable is in the spec; the `env.allow` variables reach the exec only.

The engine creates each volume, and the home folders above a configured volume or bind, owned by root. Once the container runs, `startLaunchContainer` hands them to `pi` in one root exec (`/bin/sh` running `/bin/chown -h 1000:1000`, both by absolute path under a reserved tree, the one use of `CHOWN`), which then creates `/tmp/pi-sandbox-handover`. Since the engine merges the container's environment into every exec, that exec and the pod's (`chownRoots`) send `ROOT_EXEC_ENV` (`container/lifecycle.ts`): a fixed `PATH` and an empty value for each loader and libc variable glibc drops for setuid programs, plus `GLIBC_TUNABLES`, so an `LD_PRELOAD` from `env.set` or the image never loads into the root commands. Whenever there is such a path, wherever it lies, the spec sets `PI_SANDBOX_AWAIT_HANDOVER=1` and the entrypoint waits for that file before it writes into the home, since it may link a tool file into a folder that holds a volume (`~/.m2/settings.xml` beside `~/.m2/repository`); it stops after 60 s with `the launcher did not hand the volumes to the sandbox user within 60 s, stopping`. A `mounts.volumes` entry that names a service volume is left to the services hand-over, not chowned to `pi`. A container with no such path starts without waiting. A failed hand-over, or an exec the engine rejects, stops the launch (`the sandbox could not hand its volumes to the sandbox user: <stderr>`). The entrypoint creates `/tmp/pi-sandbox-ready` as its last step, after the links and copies and just before it runs its command or idles. After the hand-over, and before the session dir probe, the agent files sync and pi, the launcher waits for that file in one exec as `pi` (no root); it stops after 60 s with `the sandbox entrypoint did not finish preparing the home within 60 s (no /tmp/pi-sandbox-ready)`. An image whose entrypoint writes no marker, such as one pinned by `image.digest`, is told apart by its entrypoint file: when `/usr/local/bin/pi-sandbox-entrypoint` does not name `/tmp/pi-sandbox-ready`, the exec returns at once and the launch goes on without the wait. With services that list `ports`, the spec sets `PI_SANDBOX_SERVICE_PORTS` (the ports, space-separated) and `PI_SANDBOX_SERVICES_HOST=pi-sandbox-services`, and the entrypoint, before it creates the ready marker, starts `/usr/local/lib/pi-sandbox/forwarder.mjs` in the background: it listens on `127.0.0.1` and `::1` at each port and pipes each connection to the same port of the pod, so pi and its tools reach a service at `localhost`. The forwarder writes `/tmp/pi-sandbox-forward`, empty once every port listens, or the error (a port in use) before it exits; the entrypoint waits for that file and writes `the port forwarder exited before it listened` when the forwarder dies first. The launcher's wait for the ready marker then reads the file, and a non-empty one stops the launch with `the sandbox could not forward the services' ports: <error>`. When the hand-over, the wait or the session dir probe fails and the container is no longer running, the launch reports `the sandbox container exited during startup, before pi could run (<error>)` instead of the engine's bare `not running`, with the hint of the failed step (or `run pi sandbox doctor`), and, when `image.digest` is set, that the image is pinned by image.digest and may predate this launcher; the container is removed when it exits, so its output is gone.

On a Mac with `terminal.clipboard` on, `container/run-pi.ts` puts the bridges of `container/clipboard.ts` on an interactive terminal; without a terminal, off a Mac or with the key off, both streams pass untouched.

- Copy: pi's output reaches the terminal unchanged. A complete OSC 52 write in it (`ESC ] 52 ; <selection> ; <base64>` ended by BEL or `ESC \`) is also decoded and piped to `/usr/bin/pbcopy`, one copy after the other. A write split across chunks is found through a carry that starts at an unterminated opener and is dropped past 1 MiB. Queries and malformed writes are ignored.
- Pasted path: an input chunk that is one whole bracketed paste of a single absolute path (backslash escapes or quotes, trailing whitespace kept) to a regular `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp` file of at most 20 MiB that the sandbox does not see at the same path (`visibleInside`) is copied by a side exec to `/tmp/pi-paste/<uuid>.<ext>`, and the paste carries that path instead. Anything else, a paste split across chunks, or a failure passes unchanged. When such an image path fails (a read error, a file over 20 MiB or not regular, or the copy), the paste still passes unchanged and the bridge hands one OSC 9 notification (`ESC ] 9 ; pi-sandbox: image not copied into the sandbox: <reason> BEL`) to the copy tee, which writes it to the host terminal between pi's output chunks, held while the last chunk ended inside an escape sequence or a UTF-8 character, which the terminal shows as a desktop notification without touching pi's screen: for EPERM or EACCES that macOS blocked the terminal and access is granted under Privacy & Security → Files and Folders, for ENOENT that there is no such file on the host, else the error code. A visible path, a non-image path, several paths (an unquoted paste with an unescaped space before a `/`, or a quoted one holding its quote again) and other text stay silent.
- Ctrl+V: an input chunk that is exactly the key (`16`, kitty `CSI <key>;<mod>[:<event>]u` with key `118` or a layout code whose base is 118, mod 5, 69, 133 or 197, event 1 or 2, or xterm `CSI 27;5;118~`) makes `cli/launch.ts` run `/usr/bin/osascript` with a 5 s timeout. The script reads the file URLs on the pasteboard first (AppKit `readObjectsForClasses`, since AppleScript's `clipboard info` sees only the first item and Finder also offers the file icon as an image): with exactly one it prints its POSIX path, with several it fails; otherwise it prints the clipboard as `«class PNGf»` hex, and fails on text. A printed path goes the way of a pasted one, notification included; an image path the sandbox already sees is pasted as it is unless it holds a C0 or C1 control character or DEL (which could end the bracketed paste and type keys into pi), and a non-image path or such a path passes the key. The PNG is copied in the same way and pi gets `ESC[200~<path>ESC[201~` instead of the key; with no PNG or on a failure the key passes.

Input chunks go through one promise chain, so what is typed after a paste or a Ctrl+V reaches pi after it.

## Services

`container/services.ts` runs the config's `services`, one set per install. `ensureServices` is called through `startServices` (`cli/ground.ts`), which `prepareServices` (`cli/launch.ts`) calls inside the preparation lock, after the image and the proxy route and before the agent's spec is built; it takes the ground lock, and the doctor probe skips it. With no services it returns at once and touches no running service. Otherwise one holder container, the pod (`pi-sandbox-pod-<install id>`, role `pod`), sits on the install's network under the alias `pi-sandbox-services`, and every service (`pi-sandbox-service-<install id>-<name>`, role `service`) joins its network namespace with `NetworkMode: container:<pod id>`, so the services share `localhost` and the alias. The agent is not a joiner: it stays on the install's network and reaches the listed `ports` through its port forwarder (see Container). The engine refuses a hostname, extra hosts, DNS, ports, links and a static address on a joiner, so the spec sets none. Removing or restarting the pod ends the namespace of every service, so the pod is never restarted while a service may be in use.

- **Pod.** The sandbox image running `sleep infinity` under init, as 65534:65534, read-only root, `/tmp` tmpfs, 64 processes, the agent container's capability set (`CHOWN`), `no-new-privileges`, `AutoRemove` off. It mounts every service volume at `/pi-sandbox/service-volumes/<volume>` and, once it runs, hands each root to its service's user with the agent's hand-over script generalised to an owner (`chownRoots`, one root exec per user; a failure stops the launch with `the service volumes could not be handed to <user>`). A fresh volume root is root:root 0755, so a service with another user could not write without it. No helper container is used. Its labels are the managed and install labels, the role and `pi-sandbox.services-hash`, the stable hash of the sandbox image id and the resolved services list (the `ports` are not part of it).
- **Service.** Its image (the sandbox image by default; another is pulled with `backend.pullImage`), the command as the entrypoint, the numeric user (`1000:1000` by default), only its own `env`, its volumes (shared volumes through `configVolumeName`, so the same volume as a `mounts.volumes` entry of that `name`), `/tmp` and its `tmpfs` paths at mode 1777, read-only root, init, no capabilities, `no-new-privileges`, 4096 processes, its `memoryGiB` and `shmMiB`, `AutoRemove` off. Labels: managed, install, role and `pi-sandbox.service-name`; no repository label. It gets no workspace, home, render folder, credential or forwarded variable. Services are never started by exec in another container, and never restarted in place.
- **Bring-up.** One find of the install's pod and service containers (`installServices`) feeds `decide` (`fresh`, `refresh` or `keep`) and the steps after it. With no running pod: stop and remove what is left, create the volumes, prepare the install's network, create the pod, hand over, then start the services in order, each printing `pi-sandbox: starting service <name>` and waiting for its `ready.command` (an exec as the service user, no TTY, output discarded, every 500 ms until the timeout; the container is inspected only after a check fails, and once for a service without `ready`). With a running pod of the same hash: check again that each running service is ready, and remove and start again the services that are missing or exited. With a running pod of another hash: when another launch of this state dir is live (`busyLaunches`, `cli/busy.ts`, without the launch itself), keep everything, print `pi-sandbox: the services in the config changed; they restart once every pi session has ended` and start again only the stopped ones (one that cannot start stops the launch with `service <name> is stopped and could not be started`, hint: end every pi session, so the services start afresh from the config); otherwise start fresh. A service that exits or is not ready in time fails the launch with its last 40 log lines and a hint naming `services[<i>]`; Ctrl-C aborts the wait. On a failure the services are stopped unless another launch of this state dir is live, or the count itself fails.
- **Stop.** `stopServices` stops the install's services together, 30 s each, so the grace periods do not add up, removes them and then the pod; volumes stay. It runs only in the ground teardown (`removeEngineGround`, `cli/ground.ts`) when no launch of this state dir is live: in the sweep, in `pi sandbox stop` and in the uninstall (see Lifecycle and sweep). `pi sandbox reset --services` (`wipeServices`) stops them the same way under the ground lock, then removes the volumes the config's services name; it refuses with `a pi session is running, so the services were kept` while a launch of this state dir is live, and leaves the network alone.
- **Race.** Bring-up and teardown both run under the ground lock and count the busy sessions inside it, and a launch registers before it prepares. So a teardown either runs first and the launch brings the services up afresh, or it counts the registered launch and stops nothing. A sweep that finds the ground lock held skips the teardown; the end of a session and `pi sandbox stop` wait for it while no other launch is registered (see Lifecycle and sweep).

## Status file

`provision/status.ts` renders `tools/status.json` into the render folder, under the render lock with the rest of it, from the config (`RenderInput.status`). The container sees it at `/opt/pi-sandbox/render/tools/status.json`, named by `PI_SANDBOX_STATUS`; the entrypoint links nothing from it. It holds `version` 1, the proxy URL with its `/denials` and `/healthz` URLs, the `resources`, the `mounts.volumes` targets, the `mounts.binds` targets (from the config, also when the doctor's probe mounts none), the `setup` commands and each service's name, command, `ready` and `ports`. It holds no token, no host path and nothing that differs per launch.

## Image

`image/Dockerfile` builds on `node:24-bookworm-slim` with git, search tools, socat, curl, jq, python3 and a pinned, checksum-checked glab, a `pi` user and pi installed at the host pi's version, passed as the `PI_VERSION` build argument. It bakes no pi config, package or credential. The base carries no launcher CA; extra CAs are trusted during its build steps and removed from the trust store and the final filesystem afterwards. It sets `LANG=C.UTF-8`, the one UTF-8 locale bookworm's glibc ships, so the sandbox has a valid locale whatever the host's is; `LANG` is not in the default `env.allow`, and a `LANG` the user lists there reaches the exec, whose environment wins over the image's. The base carries no sandbox script and no `ENTRYPOINT`: the layer adds them (below), so a pinned base, whatever launcher built it, gets this launcher's entrypoint and hint. `BASH_ENV` and the first line of `/etc/bash.bashrc` source `bash-env.sh`, which prints the missing-command hint; for `sudo`, `doas` and `systemctl` the hint says instead that the sandbox has no root, that packages come from `image.packages` and that servers run as `pi`. The entrypoint re-creates the render links (`~/.agents/skills` among them, removed when the render dir has none) and the read-only `auth.json` copy, then idles under the engine's init.

`ensureSandboxImage` runs under `<state>/locks/build.lock`, so two launches never build at once; the second says it waits. It pulls `image.reference` at `image.digest` when both are set, else builds the base locally, tagged `pi-sandbox-base:local`; with `tls.extraCa` set the base build copies those certificates in as `trust.pem` (an empty file otherwise), trusts them for its own downloads and removes them again with `update-ca-certificates --fresh`, so the base keeps no extra CA. Then it adds the layer, which is always built, over a pinned image too, tagged `pi-sandbox-layer:<hash of the layer Dockerfile and every context file>` (packages sorted and deduped) and reused while that hash stays the same; a launch whose layer tag is missing builds it. Its first step copies the launcher CA and the `tls.extraCa` certificates, one per file (`ca/proxy-<hash>.crt`, `ca/extra-<hash>.crt`), to `/usr/local/share/ca-certificates/pi-sandbox/` and runs `update-ca-certificates`, which a base without it (not Debian's `ca-certificates`) fails with `the sandbox layer needs update-ca-certificates`. Its second step copies `entrypoint.sh` to `/usr/local/bin/pi-sandbox-entrypoint` and `bash-env.sh` and `forwarder.mjs` to `/usr/local/lib/pi-sandbox/`, puts the line that sources it first in `/etc/bash.bashrc` unless it is there already, and sets `BASH_ENV`; these scripts are context files, so a launcher that changes them builds a new layer tag. Then come `image.packages`, `image.npmGlobal` and `image.dockerfile`, and its last step, as root, runs `/usr/local/lib/pi-sandbox/trust-jdk.sh`. The script finds every JDK by a `*/bin/keytool` file on the root filesystem (`/proc`, `/sys`, `/dev` skipped), takes `lib/security/cacerts` or `jre/lib/security/cacerts` and `conf/net.properties`, `jre/lib/net.properties` or `lib/net.properties`, follows each with `readlink -f` (Debian links them into `/etc`), imports each CA as `pi-sandbox-<file name>` and deletes `pi-sandbox-*` aliases no longer in the folder, and replaces the proxy keys of `net.properties` with `jdk-net.properties` (`http(s).proxyHost=pi-sandbox-proxy`, `http(s).proxyPort=3128`, `http.nonProxyHosts=localhost|127.*|[::1]|pi-sandbox-proxy`). It unsets `JAVA_TOOL_OPTIONS`, `JDK_JAVA_OPTIONS` and `_JAVA_OPTIONS` for its own `keytool` runs and fails when `jdk-net.properties` is missing. A discovered JDK without `keytool`, `cacerts` or `net.properties` is skipped with `pi-sandbox trust: skipping <home> has no <file>`; a JDK given as an argument fails the step instead. It writes nothing when nothing changed, so a second run is a no-op; given JDK paths it handles only those, so an `image.dockerfile` that installs a JDK after the layer, or an agent with its own JDK, can run it again. A layer with no packages, npm globals or Dockerfile gets no build proxy and builds with network mode `none`, so a parent proxy with credentials does not refuse it. The progress line `preparing pi sandbox, one time` shows once, before the base or the layer builds. `<state>/image.json` records the base image (id, digest, inputs hash) and the current layer tag; the inputs hash covers the Dockerfile and the pi version. Build contexts and their archives live under `<state>/build/` and are removed after the build; the sweep clears what a killed build left while no build holds the lock.

- The build gets the parent proxy (`HTTPS_PROXY`, else `https_proxy`, http only) as `HTTP_PROXY` and `HTTPS_PROXY` build arguments, with a loopback host (`127.0.0.1`, `localhost`, `::1`) pointed at `host.lima.internal`, and `NO_PROXY` from the same parser. A proxy the launcher does not use gives the build no proxy; one with credentials refuses the build.
- A failed build's error keeps the last 30 lines of the build output. A certificate error in a build step adds the `tls.extraCa` hint; a certificate error while the engine pulls the base or the pinned image adds the hint that the network's CA is not declared in `tls.extraCa` and that `pi sandbox doctor` prints the line to add; npm's `No matching version found` for the pi package says the host pi version is not published.
- Prune, one rule: after every build and in the daily collection (which skips while a build holds `build.lock`), layer tags other than the current layer, and untagged launcher images (the replaced base included) other than the recorded base, are removed once they are older than an hour and no container uses them.

## Setup

`pi sandbox init` (`cli/commands/init.ts`) sets up the project folders, the VM size and the settings write-back, and creates or restarts the VM. It takes one option, `--yes`, and decides by this table:

| situation | behaviour | exit |
| --- | --- | --- |
| `--yes` | asks nothing, whatever the terminal: keeps the file's settings, writes `workspaceRoots` from `PI_SANDBOX_ROOTS` into a config without them (a config with other roots is refused, and so is a config that `validateConfig` refuses anywhere, owned keys included, with nothing written), applies the plan to the VM through the wizard's `applyPlan` (a VM colima does not answer for in time gets the warning that it could not be checked and the closing `Done. Settings saved.`, exit 0) and prints the plain review and then its events in the plain setup's ASCII lines, the VM's progress with a `still working` line every 15 s and the success lines on stdout, the unchecked VM, a failed save or VM step and the notices on stderr; a failed VM step exits 1 without Try again, and an error that is not a `LauncherError` reaches the unexpected-error handler (exit 70) as any other command's would | 0 / 1 |
| `CI` set and non-empty | refuses: `pi sandbox init asks questions, and CI is set`, never opening `/dev/tty` | 1 |
| no terminal | refuses: `pi sandbox init asks questions and needs a terminal` | 1 |
| a terminal | the interactive setup, rich or plain | 0, 1, 130 |
| SIGTERM, SIGHUP during the setup | restores the terminal, prints nothing | 143, 129 |

The terminal (`cli/prompt/terminal.ts`) is stdin with stderr when both are TTYs, so stdout stays empty; otherwise `/dev/tty`, opened through `CliDeps.openTty`, which covers `curl … | sh` and a piped install log. The mode is rich (raw mode, a live frame) unless `PI_SANDBOX_PLAIN` is set, `TERM` is `dumb` or unset, or the terminal has fewer than 40 columns; plain prints each question and answer as ASCII lines, read through readline's line editing (Tab completes paths), and with a dumb or unset `TERM` reads lines without raw mode or cursor sequences. `withTerminal` restores raw mode, the cursor and bracketed paste in `finally`, on SIGTERM and SIGHUP and in a synchronous `exit` listener, and closes `/dev/tty`; a restored session refuses to start another prompt, so nothing turns raw mode on again. Keys typed ahead are kept: one key listener per terminal (`keys.ts`) queues the keys that arrive between two prompts, the next prompt replays them after its first draw, and plain mode keeps the lines that arrive with an answer for the following questions. Keys typed while a spinner runs (the detection, the VM step) are dropped on purpose, so a stray Enter never answers a question not yet shown. Esc counts as Esc after 50 ms without a following byte. Exit 130 means cancelled in every form (ctrl-c, ctrl-d, the end of input, Cancel, leaving the review), so `install.sh` can tell set up from not set up.

`cli/setup/` holds the core. `runSetup` (`flow.ts`) reads only through its inputs and touches the terminal only through the `Prompts` of `cli/prompt/` (rich over raw mode, or plain line by line): it prints the intro, runs the detection (`detect.ts`: the VM's `inspect`, the live sessions as `cli/vm.ts` counts them, the free disk and the candidate folders, in parallel within 3 s, through asynchronous file-system calls so a hanging mount cannot hold the timer; a folder search that runs out of time says so and still lists the configured roots), and on a first run (no `workspaceRoots`) asks three steps, the project folders, the VM size and the settings write-back, each with its position in the title line and Esc going back one step, before the review hub; a re-run opens the hub. A typed folder is checked as it is added, against the folders checked at that moment (the multiselect hands them to its add action): a protected folder is refused with the reason, one that holds a checked folder is refused, one inside checked folders replaces them (the add action returns the new choice with the folders to uncheck, and a note names them), so an add never leaves two checked folders nested (a toggle, or configured roots that already nest, still can), "did you mean" offers only a near sibling that may be shared, and Tab completes case-insensitively when no name matches exactly. The folders step pre-checks the detected project folders whenever the file has no `workspaceRoots`, says what an existing VM shares now, and an empty selection always asks the home-sharing confirm (starting on Yes when the VM already shares the home), so no run shares the whole home unasked. The hub prints each owned key with its value and tag, the file diff, the one VM action and the problems as ordinary output, again after every edit so the latest summary sits right above the menu (on the first arrival after the three steps it leaves out the key table, whose answers stand right above it), and only the menu (Apply or a section editor) is the live frame. No live frame is taller than the terminal's rows minus one (`frame.ts` keeps the title and the rows around the cursor or the pointer), so a redraw never leaves stale copies in the scrollback. Text is wrapped to the room the prompts give it (the width less the rail, and at most 79 columns in plain mode; notes and detail functions get the same room), never cut: titles, answers, folder tags, hub values, problems and diff lines wrap with their rail and indentation, long paths break after a `/`, and below 60 columns a hub value goes under its label; the frame cuts only a line still wider than the screen, such as an over-long choice label. Nothing is written before Apply: `apply.ts` then writes the file (`document.ts`: re-read and compared first, through `writeFileAtomic`, keeping the mode, the key order and CRLF line endings, and writing through a link, also a dangling one whose target folder exists, never over it; a byte-order mark is refused by name, and a save failure names the reason, such as a folder that is not writable) and runs the VM step through `Backend.vm.apply` with its progress, a failure screen with Try again, and the success screen, which says the sandbox is ready only when the VM was not held for live sessions and could be checked. `applyPlan` performs these steps and reports each as a typed `ApplyEvent` (saved, save failed, VM done, deferred, stopped, not checked, failed, not ready, cancelled, done) to a front end: `wizardFrontEnd` draws them through the prompts, `lineFrontEnd` prints them as lines for `--yes`, after the plain review the hub shows before Apply (`createReview` in `review.ts`, the one source of the hub's summary: the three settings with their tags, the file changes and the VM action), so a run without a terminal still records what it writes and which folders the VM shares, with the heartbeat of the plain task (`heartbeat`, `cli/prompt/task.ts`); `eventLines` in `screens.ts` gives each event its one text. The share plan is a launch's (`vmSharesFor`): the roots, pi's sessions folder, `<state>/vm` and the folders of `mounts.binds` sources outside them, so a VM it restarts keeps its bind shares. A restart passes `--mount` only when the shares change, through the same merge as a launch's share restart (a broader share absorbs every share inside it, since colima refuses nested mounts), and when it adds shares to the ones the VM keeps (the whole home) it refuses a share that colima mounts at another path in the VM before stopping anything. During the VM step the first ctrl-c warns in the words of the current phase (`vmInterruptWarning`), and a second stops waiting with exit 130 and a closing line true to the phase it ended in (`stoppedWaiting`: being created, stopped with the next pi starting it, or still starting); the `colima` command in flight is neither waited for nor killed, and neither is it on SIGTERM, so the next `pi sandbox init` or pi start finishes the step. `screens.ts` holds every sentence. Every file-system text is passed through `printable` before it reaches the terminal. An owned key that fails validation is tagged invalid and only that key is replaced: an invalid VM value goes back to automatic while the valid ones stay. The plan is pure (`plan.ts`): the answers, the edited config and its diff, and one VM action (create, restart, defer while sessions run, leave a stopped VM to the next launch, or none), so `--yes` runs the same plan (`answersForYes`, `planOf`) and the same `applyPlan` without the prompts. Only `init.ts` decides that `CI` means no prompts; `findTerminal` only finds a terminal.

## Locks and liveness

`shared/file-lock.ts` is the one lock primitive: the launch registry lock (`locks/launches.lock`, one per state dir: the launch records only, written at a launch's registration and end and read by the proxy's idle exit and every busy count, and held by the uninstall across its removal so that no launch registers meanwhile), the ground lock (`locks/ground.lock`: the proxy start, the install's network and relay, the services, their teardown, `reset --services`, the sweep's ground teardown at a session's end and in `pi sandbox stop`, and the uninstall's removal of the ground, volumes and images), the preparation lock, the render and settings sync locks, the grants, the CA and the per-server MCP sign-in lock. A lock file holds `<pid> <boot time> <process start> <nonce>`. The liveness rule (`shared/liveness.ts`) applies to locks, launch entries and `proxy.json`, and it is process identity, never a timer: a holder is live when its pid exists, the boot time matches and the process start time (`ps -o lstart=` on macOS, field 22 of `/proc/<pid>/stat` on Linux, read by `shared/process-start.ts`) is the recorded one. A running pid counts as live when the start-time tool itself failed, and as dead when no start time is obtainable for that pid. A sleeping Mac or a stopped launcher therefore keeps its sandbox, and a pid reused by another process does not count. A lock that is not live is taken over, one taker at a time. A live holder is waited for: the launch registry lock waits up to 120 s, the render, sync and CA locks 30 s, the build lock up to an hour, then the waiter fails and asks to run the command again. The VM lock is a directory lock judged by its age and refreshed while held (180 s wait; the file cache watch takes it only when it is free, `withDirectoryLockIfFree`, and never waits), so a share restart, a VM start and `pi sandbox stop` never interleave. `ensureRunning` checks the engine only under it, so a launch that registers while another launch or `pi sandbox init` restarts the VM (after its busy count) waits for that restart instead of building its container on a VM that is going down.

The preparation lock (`locks/prepare-<repo hash>.lock`, `cli/prepare.ts`) makes the launches of one repository prepare one at a time: the registration, then the proxy route, the services, the container create, the hand-over and `setup`, so two sessions never run `setup` against one repository's volumes at once. Every removal of a repository's sandbox runs under it too: the sweep, the uninstall's per-folder release and the host session directory's full sweep take it only when it is free (`whenNotPreparing`) and skip the work otherwise, `pi sandbox reset` waits for it, and the launch end waits for it unless another launch of the repository is registered (see Lifecycle and sweep). It has no short timeout, since `setup` may take as long as it needs: a launch waits for it (`withFileLock` without a timeout) and, when it is held, prints `pi-sandbox: waiting for another pi session of this folder to finish preparing` once and retries every 250 ms until it is free, a holder that is not live (the liveness rule above) is taken over, or Ctrl-C aborts the wait. The ground lock (`withGroundLock`, `cli/ground.ts`) waits the same way, with no timeout, a 250 ms retry and `pi-sandbox: waiting for another pi session to finish with the sandbox network, proxy or services` once; a launch takes it for the proxy before the preparation lock and for the route and the services inside it. The locks nest in one order: preparation, then ground, then registry, or preparation, then registry; the registry lock is a leaf, and nothing is taken inside it. The uninstall takes ground, then registry. The end of a launch and the sweep's ground teardown (also in `pi sandbox stop`) wait for the preparation or ground lock only while no other launch is registered (`withFileLockUnless`: they retry the free lock every 250 ms, so a launch that registers meanwhile and may hold the lock for minutes ends the wait and takes over the cleanup); the sweep and the other opportunistic removals take the locks only when they are free (`whenNotPreparing`, `withFileLockIfFree`), so they never wait on a launch that prepares.

## Lifecycle and sweep

- A launch registers an entry (`pid`, boot time, process start, launch id, repository hash) under `<state>/launches/`; registering and ending prune the entries of dead launches. Every removal of a repository's sandbox runs under the repository's preparation lock and re-checks that repository's live launches first. `pi sandbox reset` refuses while a session of the repository runs and names how many.
- **Records first.** Each mount point the launcher makes in the repository goes into `created.json` right after it is written, so a refused launch leaves nothing the sweep does not know. Hooks dirs are not recorded; they stay.
- **Launch end.** The launch's own container is removed, and the call waits until the engine has removed it. When it was the repository's last live launch, `removeRepoSandbox` (`cli/sweep.ts`) runs under the preparation lock, with the live launches counted again inside it, and removes the repository's agent containers, removes the mount points in `created.json` (deepest first, only empty real directories), and sweeps the whole host session directory. When the engine is unreachable the engine step is skipped and the rest still runs. A held preparation lock does not skip this cleanup: the end waits for it (`whenLastOfRepo`, `cli/prepare.ts`), retrying every 250 ms and printing `pi-sandbox: waiting for another pi-sandbox command to finish before cleaning up; Ctrl-C skips the cleanup` once, and skips it only when another launch of the repository is registered, which then owns the cleanup. Ctrl-C during the wait skips the cleanup; the next sweep does it. A failure anywhere after the launch registered (signal setup, host side, the write-back table, preparation) ends the launch the same way: it is unregistered and cleaned up like a normal end. The install's network, relay, proxy, token and services stay for the sweep below.
- **Git report.** The first launch of a repository records the git baseline; a launch that starts while another is live keeps the earliest one. At the last launch's end, after `removeRepoSandbox`, `gitLaunchEndNotices` prints the layout re-check failures, new alternates, changed own git files, new or changed nested `.git` entries and gitlinks, and deletes the baseline; an earlier launch's end makes no git call. A baseline left by an unfinished session is reported at the next launch that is alone in the repository, under `git: the check after the last sandbox session did not run; it reports now:`.
- **Proxy idle exit.** The proxy checks the live launches under the launch registry lock every 30 s and exits after two empty checks, stopping any sign-in it started.
- **Sweep.** `sweepOrphans` runs at every launch start and end and at `pi sandbox stop`. For a repository with live launches it removes the agent containers whose launch-id label is not a live launch (`removed container <name> (<id>) of an ended launch`); for one without, it runs `removeRepoSandbox` when the repository has leftovers (`created.json`, or engine objects with its label). A repository whose folder is gone is forgotten (`forgot <root>, which no longer exists`): its folder under `repos/` and its render folder are deleted. `repo.json` records `mountRoot`, the nearest mount point above the root: a missing root counts as unreachable (everything kept) while that mount point is not mounted or the parent folder is missing, and as gone only when the parent exists and the mount point is mounted. Then the ground teardown runs when no launch of this state dir is live (`busyLaunches`), and waits for the ground lock otherwise held (`withFileLockUnless`: the same wait and line as the preparation lock above, where the line adds `; Ctrl-C skips the cleanup` only at the end of a session, the one place Ctrl-C ends the wait; a registered launch ends the wait and the teardown is skipped, and the count is taken again inside the lock): `stopIdleGround` stops the install's services, removes its relay and network, stops the proxy and deletes the token, and stops the proxy even when the engine part fails; a failure warns `the sandbox network, proxy and services were not all stopped`. The teardown runs even when the sweep of the repositories failed (`the sweep of the folders' leftover sandboxes failed`), so it is the only proxy stop `pi sandbox stop` needs. Once a day (`gc.json`, written only when the engine answered) the sweep also removes unused volumes labelled with a repository root that is gone, the engine objects of older builds, and unused images. Older builds' objects are those named `pi-sandbox-*` with `pi-sandbox.managed=true` and no `pi-sandbox.install` label (`isOlderBuild`, `backend/labels.ts`), which `listOlderBuildObjects` lists once: `pruneOlderBuilds` (`cli/sweep.ts`) removes the stopped or created containers first, then tries every listed volume except the shared ones (`isSharedVolumeName`, `container/names.ts`) and every listed network (`removeNamedNetwork`), printing `removed container|volume|network <name>`. It checks no use itself: the engine refuses a volume a container mounts and a network a container is on, and a refused or failed removal prints nothing and is skipped. A label of another install keeps an object, and so does a missing managed label. The same pass removes every entry under the state dir that the current layout does not name (`pruneUnnamedState`, `cli/sweep.ts`, over `stateEntries`, `shared/state-layout.ts`) once its own modification time is a day old, printing `removed state entry <path>` through `printable`, but only when the state dir is the default one (`isDefaultStateDir`), never one `PI_SANDBOX_STATE_DIR` moves: it walks `repos/`, `vm/render/` and the folders above named paths, keeps a named path whole and never looks inside `locks/`, `launches/`, `build/` and `provider-hosts/`, which have their own removers or computed names; the repository hashes are those with a folder under `repos/`, and a symbolic link is removed itself, never followed. A failed entry is skipped. Running an older build after a newer one removes the newer build's entries the older layout does not name.
- **kill -9.** A killed launcher's entry stops counting at once, since its pid is gone, and the proxy idles out within about a minute when no other launch is live; the container, created folders and the install's relay, network, services and token stay until the next launch's sweep, `pi sandbox stop` or the uninstall. A VM restart removes containers and relays.
- **Install smoke.** `pi sandbox doctor` exits 0 on a pass with the sandbox part skipped; only the hidden `__smoke-doctor` that `install.sh` runs turns that into exit 3, so the doctor's own exit codes stay as they are.
- **Stop.** `pi sandbox stop` runs the sweep, then stops the VM when no session runs in it (`vmSessions`, `cli/busy.ts`: this state dir's live launches plus the running agent containers of other installs, which it names), then stops the proxy when no launch of this state dir is live, waiting for the ground lock the same way (Ctrl-C ends the command).
- **Uninstall.** `uninstall.sh` runs the hidden `pi-sandbox __uninstall`, which refuses with exit 75 while a session runs in the VM (`vmSessions`), printing `pi-sandbox: <n> pi sessions are running in the sandbox VM; exit them first`; when running agent containers of other installs count, their names and the hint follow the count inside parentheses, before `in the sandbox VM`: `<n> pi sessions are running (<names> of another pi-sandbox install; remove a leftover with docker --context colima-pi-sandbox rm --force <name>)` (`busyText`; the context is the sandbox VM's own). Otherwise it runs `removeRepoSandbox` for every known repository and every repository the engine labels, each under its preparation lock when free and only when no launch of it started meanwhile (agent containers when the engine answers, created folders, host sessions), then holds the ground lock and, inside it, the launch registry lock, and counts the sessions again: while the registry lock is held no launch can register, so nothing starts during the removal that follows (a launch that tries waits for the lock, up to its 120 s timeout). When a session started before the count it prints the repository lines and `pi-sandbox: a pi session started in the sandbox VM meanwhile (<the busyText above>), so the sandbox network, proxy, services, volumes and images were kept; exit it, then uninstall again` and exits 75; otherwise it tears the install's ground down with the sweep's `removeGround`, which stops the proxy even when the engine part fails (lines prefixed `install:`), removes the install's volumes and every managed image no container uses, and ends with `host: released the created folders of <n> folders`. The script then deletes the profile and the host files, even when the launcher could not run.

## Invariants

- No real secret in the container's filesystem, environment or volumes; derivers and renderers take placeholders only, and `tests/support/expect-no-leak.ts` checks specs, exec argv, env, stdin and render files.
- The container's only network path is the install's proxy, through the relay, and the services' ports on the install's internal network; SNI check and private-range deny are always on.
- Nothing is mounted from a protected path; the hooks dirs are read-only inside.
- Only the user's one config file is read; nothing in the repository configures the sandbox.
- Every removal of this install's objects re-checks liveness under the repository's preparation lock, and the ground teardown counts the live launches under the ground lock, so a live launch's container, and the ground it uses, are never removed. The daily removal of older builds' objects takes no lock: it touches no object with an install label, removes only stopped containers, and leaves what the engine refuses as in use. The daily removal of unnamed state entries takes no lock either: every writer's path is named in the layout, and the temporary files, lock drafts and work folders writers leave beside them for a moment are younger than a day. The one exception is the empty `mcp-login-<random>` folder a host pi command such as `pi auth` or `pi config` runs in: its time never changes, so a host command left open for more than a day can lose its working folder when another launch runs the daily pass.
- Every file the launcher writes is listed below.

## Alternatives considered

- A published, pinned image instead of a local build: rejected as the default, so the sandbox runs the same pi version as the host; `image.reference` and `image.digest` pull one when an organisation builds it.
- The proxy token in the container, sent as `Proxy-Authorization` by each client: rejected, since many clients (JVMs among them) send no proxy credentials on a CONNECT; the relay writes the token preamble instead.
- One proxy, relay and network per repository: not taken; the user's one config holds the rules and env secrets for every repository, so one proxy per install applies them all, and one network per install lets one set of services serve every session of it.
- Read-only file binds for `.git/config` and the other git files: rejected, since on a case-insensitive volume another letter case of the name writes the host file through the bind; only directory binds are used.
- A second engine, Docker Desktop, or a host process under Seatbelt or OpenShell: not taken; Colima is the one engine, and a container keeps credentials out of reach by construction.

## Tests

Tests check behaviour through public entry points with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server, a fake backend, temp dirs, real localhost sockets and openssl certificates. The CLI tests run whole commands against the fake backend. Tests that run real git go through `tests/support/git.ts`, which keeps the developer's git config out. The prompt tests run on fake TTY streams through a pure screen reducer (`tests/cli/prompt/screen.ts`, `fake-tty.ts`), so no test needs a real terminal; the `install.sh` tests run it without a controlling terminal, and on macOS once inside `script` for the terminal path. Live tests against the real Colima engine run only with `PI_SANDBOX_LIVE=1` and fail when their cleanup had to remove anything.
