# launcher architecture

The launcher is a standalone host-side layer. It provides the `pi-sandbox` command (installed as `pi`), which runs pi inside a per-repository container and keeps credentials and network access on the host. What it does for the user is in [README.md](README.md), where things are in [STRUCTURE.md](STRUCTURE.md), what each feature weakens is in [THREAT-MODEL.md](THREAT-MODEL.md).

## Layer rules

- No pi imports (`@earendil-works/*`, `typebox`) and no imports from `platform/`, `extensions/` or `test/`. Only `node:*` built-ins and files inside `launcher/`; `launcher/tests/` may also import `vitest`. No npm dependencies: validation, HTTP, TLS and process control are hand-rolled over Node. The one exception is `hostpi/*.mjs` (only files directly in `hostpi/`): `hostpi/provider-hosts.mjs` is run as a separate Node process against the host pi of host jobs (pi's managed install, else the pi installed next to the launcher) and loads its packages; nothing imports it.
- Each folder exposes what other folders use through its `index.ts`, and nothing more. Another folder imports only `../<folder>/index.ts`, never an inner file. `bin/` is the exception: it imports `cli/main.ts` (or `dist/cli/main.js`) and nothing else, which `test/architecture.test.ts` asserts.
- The folder graph is exact, and `test/architecture.test.ts` asserts it edge for edge:

  | folder | imports |
  | --- | --- |
  | `shared` | nothing |
  | `config` | `shared` |
  | `workspace` | `config`, `shared` |
  | `backend` | `shared` |
  | `grants` | `shared` |
  | `hostpi` | `config`, `shared` |
  | `proxy` | `config`, `grants`, `shared` |
  | `container` | `backend`, `config`, `workspace`, `shared` |
  | `image` | `backend`, `config`, `shared` |
  | `provision` | `backend`, `config`, `hostpi`, `shared` |
  | `cli` | `backend`, `config`, `container`, `grants`, `hostpi`, `image`, `provision`, `proxy`, `shared`, `workspace` |
  | `bin` | `cli` |

  Nothing imports `cli` except `bin/`, there are no cycles, and shipped code never imports `launcher/tests/`.
- Tests: a file under `launcher/tests/<folder>/` may import inner modules of `launcher/<folder>/` (its own folder) and reaches every other folder through its `index.ts`. `launcher/tests/support/` reaches every folder through its `index.ts` only, and imports nothing from the per-folder test suites. Any test may import `tests/support/`.
- `cli/` is the only folder that writes to the terminal. The proxy daemon writes only its own log files. Every expected failure is a `LauncherError` (`message` and optional `hint`), reported as `pi-sandbox: <message>` and `  hint: <hint>` on stderr with exit code 1 and no stack trace. Any other error is `pi-sandbox: unexpected error: <message>` with exit code 70.
- External processes run through the `CommandRunner` interface, so tests replace them with a scripted fake: git (workspace discovery, `core.hooksPath`, `ls-files --stage` for gitlinks, the checkout `HEAD`), npm (`npm pack`), tar (the build context), openssl (the launcher CA), `security` (keychain credentials and the host CA store), `ps` (checking a proxy pid before killing it), secret `command`s, the host pi of host jobs (`auth print-api-key`, `mcp login`), the managed pi's `update`, `hostpi/provider-hosts.mjs` and `colima` (`status` for the doctor, `stop` and `start` to share a folder with the VM).

## Dev and dist entry

The sources run directly under Node 22.19 or newer through type stripping, so they follow its rules: no enums, no parameter properties, no namespaces, `import type` for types, `.ts` extensions in relative imports. `bin/pi-sandbox-dev.js` imports `../cli/main.ts` and is what a checkout install runs.

Node refuses to strip types under `node_modules`, so the published command runs compiled JavaScript. `tsconfig.build.json` emits `dist/` with relative `.ts` imports rewritten to `.js`; `npm run build:launcher` builds it and `prepack` runs that. `bin/pi-sandbox.js` imports `../dist/cli/main.js`. Assets that are not TypeScript (Dockerfile, entrypoint, `hostpi/provider-hosts.mjs`, examples, schema, install scripts) stay in the `launcher/` folder and are published from there (`tsc` does not copy them into `dist/`, and nothing looks for them there), so code finds them through `launcherRoot()` (the `launcher/` folder in either layout) and runnable entries through `launcherEntry()`, never relative to its own compiled file.

## The pipeline

`pi [args]` runs these steps, each a function the other commands reuse (`cli/launch.ts`, around a `LaunchContext` of workspace, effective config and state dir):

1. Discover the workspace (`workspace/discover.ts`, `workspace/git-layout.ts`): walk up from the real cwd to the nearest `.git` (`lstat`, no link followed); without one the cwd is a workspace (workspace mode, below), where git runs for its repositories and, when git is installed, for the folder's config check. Before any git call, `gitLayoutAt` derives the git dir and common dir from the files alone: a real `.git` directory is both (its `commondir`, if any, must be the launcher's pin `.`; an empty one, the bind mountpoint the engine creates when a stopped container is started without the launcher, is filled with the pin in place, so its inode and the mount on it stay); a `gitdir:` file names the git dir, which is its own common dir when it has no `commondir` (or the pin), and otherwise must be `<C>/worktrees/<name>` with `commondir` resolving to `C` and `gitdir` resolving to this checkout's `.git`. A link at any of these paths, a target that is not a directory, or a pointer that does not match refuses with `git: <path> ...`. Then `git -c core.fsmonitor=false -c core.hooksPath=<state>/git/no-hooks rev-parse --show-toplevel --git-common-dir` must agree on both real paths (a mismatch or a failing git refuses, so a `gitdir:` file pointing at a directory that is not a repository never gets mounted). A `gitdir:` file pointing at a directory named `.git` (the git dir of another checkout) refuses before git runs. The workspace carries `repoRoot`, `gitDir` and `gitCommonDir`, and `nodeProjects` from `scanWorkspace(root, "git")` (`workspace/workspace-scan.ts`, below).
   Workspace mode: without a `.git` above the cwd, `scanWorkspace(cwd, "workspace")` walks the folder level by level (no recursion into links: `readdir` entries that are directories only; hidden dirs included; `node_modules`, `.pi` (agent worktrees) and `.git` dirs not entered; a budget of 50 000 directories; a directory it cannot read for any reason but `ENOENT` or `ENOTDIR` is recorded as unreadable). Every directory with a `.git` entry is a repository and the walk goes on inside it; a `.git` file whose `gitdir:` resolves into an ancestor repository's `.git/modules/` is a submodule checkout and is not registered (its git dir is protected through the superproject). The same walk collects `nodeProjects`: every directory holding a lockfile (`package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `bun.lockb`) and every directory holding a `package.json` below a lockfile directory within the same repository (a `.git` entry ends that, at most 256 per repository), each only when its `node_modules` is missing or a real directory. The node projects are collected whatever `mounts.autoNodeModules` says (the option only decides whether overlays are mounted); more than 512 in one discovery sets `nodeProjectsCapped`, leaves the list empty, and the launch prints `pi-sandbox: more than 512 node_modules directories; overlay disabled, host node_modules is used` instead of the overlay notice. The strict discovery (`discoverWorkspace` in `workspace/discover.ts`) then refuses a walk that ran out of budget (`<root> has more than 50000 directories to search for repositories, refusing`) or found more than 128 repositories (both hinted `start pi in a narrower folder`), refuses an unreadable directory (`workspace: <dir> cannot be protected: cannot read it (<code>)`, hint `fix or move that repository, or start pi inside it`), runs the single-repository checks above on each repository with that repository as cwd (`confirmedRepo`; any error becomes `workspace: <repo> cannot be protected: <message>`), refuses a repository whose git dir or common dir lies outside the root (`workspace: <repo> uses a git dir outside <root>`), and `assertWorkspaceGitConfig` (`workspace/git-workspace.ts`) runs `git config --list --show-origin --show-scope -z` at the root and inside every nested repository, takes every file origin of every scope but `command` (a repository's own `config` and `config.worktree` aside; files named by `include.path` and `includeIf` show up as origins too) and refuses one whose path or real path lies inside the root but outside every repository and its git dirs (`workspace: git configuration <path> lies inside the workspace, refusing`). The root listing always runs and is skipped only when git is not installed (`git: command not found`); a git that runs and fails refuses with `git: could not list the git configuration of <dir>: <stderr>`, as does a failing listing in a nested repository. The result is `{ repoRoot: cwd, isGitRepo: false, nested, nodeProjects }`, and `gitRepos(w)` gives `[w]` for a repository and `nested` for a workspace; every git step below runs over `gitRepos`. `reset`, `gc`, `status` and `--no-sandbox` (which mounts nothing) pass `{ lenient: true }` (the doctor uses the strict path and prints the launch notices below): the walk only, no git call and no refusal, unreadable directories skipped, so they still work in a folder that would not launch.
2. Load the effective config from the layers (policy, org, user, project), print the org layer's notices, check `workspaceRoots`: the repository and its git common dir must be inside the roots (a linked worktree whose main repository is outside is refused); `outside: warn` prints a warning instead.
3. Intercepted commands (`cli/intercept.ts`, routed by `run.ts` before the pass-through and never with `--no-sandbox`): `install|remove <source>` without `-l`, `mcp add|remove|login|logout` with every flag passed through and a bare `update`; see [Intercepted commands](#intercepted-commands).
4. `--no-sandbox`: the config loads offline (`loadEffectiveConfig({ offline: true })`): an HTTPS org source uses its cached copy of any age, and without one the org layer is skipped with a notice, so `--no-sandbox` never touches the network. Refused under `fallback: refuse`, naming the layer; otherwise sweep the host session directory of the repository when host sessions are on (`sweepForHostPi`, see [Host sessions](#host-sessions); the `agents/` trees too when the backend answers and the repository's container is not running) and exec `hostPiCommand` (`cli/host-pi.ts`, see [Host pi](#host-pi)): the managed install's `bin/pi` wrapper, else the first `PATH` pi that passes the filters, else the bundled pi.
5. Refuse a workspace that would mount too much (`workspace/guard.ts`, regardless of `workspaceRoots`): a repository root or git common dir that equals or contains `$HOME`, `~/.pi`, the host agent dir (`hostAgentDir`, so a custom `PI_CODING_AGENT_DIR` with a managed pi install in it), the launcher state dir, the user config dir, or `/`, or that lies inside `~/.pi`, the host agent dir, the state dir or the config dir. The config dir is protected only when it is the default `~/.config/pi-sandbox`; with `PI_SANDBOX_USER_CONFIG` elsewhere only that file is, so a repository equal to or containing it is refused and its siblings are not. A dotfiles repository rooted at `$HOME` is the case this catches. The hint is `run pi inside a project directory`.
6. Open the engine: the one backend talks to `~/.colima/pi-sandbox/docker.sock` (resolved from the home, so a test `HOME` moves it); Colima is the only engine. When its `detect()` fails the error is `the sandbox VM engine is unreachable at ~/.colima/pi-sandbox/docker.sock` (hint `run launcher/install.sh or colima start --profile pi-sandbox --activate=false`), with `or run pi --no-sandbox to use host pi` appended when the fallback is `host`. On the launch path only (`openLaunchBackend` in `cli/vm-lifecycle.ts`, called by `openSandboxContext`; the admin commands keep `openBackend`), when `detect()` fails and `~/.colima/pi-sandbox/colima.yaml` exists and `colima status --profile pi-sandbox` exits non-zero, it takes `<state>/locks/vm.lock`, asks `detect()` again (another launch may have started it), prints `pi-sandbox: starting the sandbox VM`, runs `colima start --profile pi-sandbox --activate=false` (no other flag, so the saved size and mounts apply) and asks `detect()` up to five times over about 5 s. `colima status` exiting 0 while the engine is unreachable starts nothing, and the unreachable error stands. Its errors are `could not start the sandbox VM: colima: command not found` (hint `run launcher/install.sh`), `could not start the sandbox VM: colima start failed: <last stderr line>` and `the sandbox VM started but its engine is unreachable: <reason>` (hint `run colima start --profile pi-sandbox --activate=false and see ~/.colima/_lima/colima-pi-sandbox/ha.stderr.log`), with the same fallback suffix. Then, as the first step of `withSandbox`, share the folders the Colima VM lacks (`cli/vm-shares.ts`). It reads the running instance's `~/.colima/_lima/<instance>/lima.yaml` `mounts`; when the repository, its git dirs, the state dir, `mounts.extraReadOnly` or the host session dir (the one `hostSessionsChoice` binds) lies outside every share, or needs writing and its share is read-only, it builds the full list from `~/.colima/<profile>/colima.yaml` (`[]` or no key stands for the home, writable) plus, for each missing path, the home when the path lies in it, else the volume root under `/Volumes` or the parent folder (a read-only entry it needs writable is upgraded to `:w` in place). It takes `<state>/locks/vm.lock` and reads `lima.yaml` again. It refuses before touching the VM, naming the command or `edit ~/.colima/pi-sandbox/colima.yaml mounts, then colima stop --profile pi-sandbox && colima start --profile pi-sandbox --activate=false`, when colima.yaml is missing, holds a flow-style list or a mount with keys other than `location`, `writable` and an empty `mountPoint`; when the new list would drop a share the VM has now; and when any pi session of any repository is live, checked right before `colima stop`. Otherwise it prints `pi-sandbox: sharing <folders> with the sandbox VM, one time`, runs `colima stop --profile pi-sandbox` and `colima start --profile pi-sandbox --activate=false --mount <loc>[:w] …`, requires every path in the new `lima.yaml` and asks `detect()` up to five times over about 5 s. A launch that registers its session between that check and the stop sees an engine error and should be run again. Under `fallback: host` every hint of this step ends with `or run pi --no-sandbox to use host pi`.
7. Host side (`cli/derive.ts`): read the host pi files (`readHostPiFiles` of `PI_CODING_AGENT_DIR` or `~/.pi/agent`), read the provider host table through the host pi of host jobs (`resolveJobPi`, resolved once per launch in `withSandbox` and kept as `HostSide.pi`; `readProviderHosts`, cached per pi version), `ensureSalt`, and `deriveSandboxPi` with the manual `credentials.rules` and `credentials.derive`. Print its notices and `privateHostNotices` (`proxy/private-hosts.ts`: a rule host outside `egress.privateHosts` that resolves to an address the proxy's own restricted-address check refuses; the launch waits at most 2 s for those lookups and goes on without the notices after that). The proxy is needed when an allowlist or any rule exists; the trust bundle (`ensureTrustBundle`: the launcher CA plus `tls.extraCa`) is built when the proxy is needed and a rule or an extra CA exists. Then the MCP sign-in (`cli/mcp-sign-in.ts`, after the host side and before the session starts): `mcpSignInsNeeded` (`hostpi/mcp-auth.ts`) lists the derived `mcpOAuth` servers whose entry in host pi's `mcp-auth.json` has no `refresh_token` and an access token that is missing or expired. With a terminal, for each one whose lock `<state>/locks/mcp-login-<sha8(key)>.lock` is free and whose record in `<state>/mcp-login.json` has no `failedAt` in the last 24 h, it records `lastStart`, prints `mcp <name>: signing in on the host; your browser opens` and runs `pi mcp login <name> --timeout 120` (the host pi of host jobs, interactive, in a fresh empty `<state>/mcp-login-<random>/` folder with `PI_CODING_AGENT_DIR` set to the host agent dir) holding the lock, with a no-op SIGINT listener so Ctrl-C ends only the login; a non-zero exit records `failedAt`. A held lock prints `a sign-in is already open on the host`; no terminal, a failure or a recent `failedAt` prints `not signed in; run pi mcp login <name>`. The launch always goes on.
8. Register the session (`registerSession`, under the repository's lock) with a fresh session id. From here until pi starts, SIGINT, SIGTERM and SIGHUP end the launch the way a normal exit does (step 13: end the session, stop the container when no other session is live) and exit `128 + signal number`. The signal does not abandon the preparation: `withSandbox` aborts an `AbortSignal` that `prepareSandbox` and `prepareContainer` check between steps (after the proxy and the image, which run in parallel, before `ensureContainer`, before the settings sync), waits for the step in flight to finish, and only then ends the session, so no container is created or started after the session has ended and the session sweep never runs beside a container start. A second signal while that step finishes is not caught and ends the launcher at once.
9. Proxy (`cli/sandbox-proxy.ts`): `ensureProxyRunning` with the config, the host pi command of host jobs, the host pi version (`piVersion`; with `piCommand` and the host agent dir stored in the daemon config, and a running daemon whose stored version, command or agent dir differ counts as unhealthy and is replaced at that launch) and a minimal environment (`daemonEnv` in `proxy/control.ts`: `PATH`, `HOME`, `TMPDIR`, user and locale, `NO_PROXY`, CA file variables, `PI_CODING_AGENT_DIR`, the `PI_SANDBOX_*` path overrides, and `HTTPS_PROXY` without userinfo; no secret and no other proxy variable); a proxy that cannot start stops the launch. An `env` secret whose value holds CR or LF stops the launch with `<VAR> contains a line break and cannot be used as a credential`. `repoProxyToken` gives this repository's token (a file in the instance's `tokens/`, the only place a token is kept), `writeProxyDynamic` (under `<dynamic.json>.lock`, so concurrent launches do not lose each other's sections) records the derived rules and the derived hosts as this repository's section under `sha256(token)`, and `sendProxyControl` hands over the `env` secrets (`envSecretsFor` in `proxy/secrets/`: rules whose secret is `{ env }`, and the Basic credentials of the launcher's `HTTPS_PROXY` under `egress.parentProxy: "env"`), resolved from the launcher's environment, with `repoTokenHash: sha256(repo token)`; the daemon refuses a message that names no live repository token and keeps the secrets per repository, a launch replacing only its own map. `dynamic.json` is `{ repos }`, keyed by token hash (every write names one), and every write keeps only the sections whose token file still exists; the proxy maps a token hash to its repository from the token files alone, applies a repository's rules only to that repository, and derived hosts as a union.
10. Image (`ensureSandboxImage`, `image/sandbox-image.ts`, run in parallel with step 9 through `settleAll` in `cli/deps.ts`, which waits for both and then throws the first error): the hot path reads `<stateDir>/image.json` and, when `findCurrentContainer(backend, workspace, digest)` finds this repository's container with that digest, skips the base build without resolving the pi and extensions versions, unless that container is stopped and the image record's `pi` differs from the host pi's version or is missing (`hostPiMoved` in `cli/launch.ts`; never under `image.digest`), so a stopped container never pins an image after a host pi update; the image's pi version is `imagePiVersion` (`cli/versions.ts`): the host pi of host jobs, else the `@earendil-works/pi-coding-agent` devDependency pin (`testedPiVersion`), and a local build records it as `pi` in `image.json` (a reused build whose record lacks it gets it written, so the next stopped-container launch takes the warm path again). After the image, `imagePiNotices` prints `pi-sandbox: the sandbox image has pi <x>, the host pi <y>; the image is rebuilt after every session in this repository exits` when the image in use recorded another version or none (`of an unrecorded version`), except under `image.digest`, whose pulled record carries no pi version; the cold path prints `preparing pi sandbox, one time`, then pulls a pinned digest (`pullPinnedImage`) or resolves the extensions source and runs `ensureBuiltImage` (with the extra CAs and the parent proxy for the build). `ensureLayerImage` then adds the `image.packages`, `image.npmGlobal` and `image.dockerfile` layer, or returns the base id when there is none. The container is created from the layer id; its digest label stays the base digest.
11. Container: five steps run in parallel through `settleAll` and all finish before the proxy route is prepared or any container or relay is created: `renderAgentDir`, `gitLaunchNotices`, the launcher version, `planGitOverlay` and `readyHostSessions`, each described below. `renderAgentDir` writes `<state>/render/<repo hash>/` (the copied agents, prompts, skills, themes and extensions skip `.git`, `.env*`, `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials`, `id_*`, key and certificate stores and secret-named files other than source and markdown), `backend.prepareProxyRoute({ hostPort, repoHash, relay: { policyHash, imageId } })` gives the guest's route on the repository's own network, `guestProxyUrl(route, repoToken)` the proxy URL, and `buildContainerSpec` adds the render mount, the trust mount and `PI_SANDBOX_TRUST_HASH`. Before the spec, `readyHostSessions` (`cli/host-sessions.ts`) prepares the host session directory when host sessions are on: it creates the missing directories 0700 (`prepareHostSessions`), checks the result with `assertHostSessionsDir`, and sweeps it (the whole tree when no container of the repository runs, the top level otherwise); the spec then binds it at its host path and sets `PI_CODING_AGENT_SESSION_DIR`. Before the spec, `gitLaunchNotices` re-runs the git layout checks (`assertGitIntegrity`: the layout as in step 1, every `worktrees/*/commondir` resolving to the common dir, the pin in the common dir and in each submodule git dir) and names `objects/info/alternates` and `http-alternates` when present; `planGitOverlay` (`container/git-overlay.ts`, over `workspace/git-protect.ts`) finds the protected git paths once per launch without writing anything, and the spec is built from its overlay. `findProtectedGitPaths` lists the repository's config origins the same way (every scope but `command`, includes too) and binds read-only every one inside the repository's working tree or git dir; in single-repository mode a failing listing is ignored, as the `core.hooksPath` lookup is, so the included files are then not bound. In workspace mode it plans each nested repository with the workspace in its context (so a `core.hooksPath` or config origin that lies in the workspace outside the repositories refuses, and one inside any nested repository, a sibling included, becomes a read-only file in the overlay of the repository that reads it; a failing listing refuses) and merges the overlays with `workspaceSelfBinds` (every nested repository root and every directory between the workspace root and it, sorted by depth); `gitLaunchNotices` runs per repository. The launch then prints `workspaceNotices` (`pi-sandbox: workspace with <n> repositories, git metadata protected`, `1 repository` for one), and, when `nodeModulesOverlays` is not empty, `pi-sandbox: node_modules overlaid in <n> directories; host node_modules is hidden; set mounts.autoNodeModules=false to keep it` (`1 directory` for one); `pi sandbox doctor` prints the same notices during its smoke run. `ensureContainer` runs under a per-repository lock (`<state>/wanted/<short repo hash>.json.lock`), records the wanted identity (image digest, spec hash) in `<state>/wanted/<short repo hash>.json` (read by `status` to tell a current container from a stale one), and reuses the running container whose labels match. When it is about to create or start one (a fresh create, the replacement of an outdated container after discarding it, or the restart of a stopped matching one), it first calls `beforeStart` inside `aroundStart` (in the launcher `withGitPinLock`, held through the create or start so another checkout's last session cannot remove a pin before the engine binds it; in workspace mode it takes the pin lock of every repository, sorted by git common dir and nested), which in the launcher is the plan's `ready()`: the `commondir` pins written and the layout checked again (`assertGitIntegrity`; the protected paths are found again only when the submodule list changed since the plan), missing hook dirs created, every protected path checked again (a link, or a path that goes through one, refuses), the snapshots rewritten (in workspace mode every repository's into the one snapshot dir of the workspace root) and the nested-repository baseline recorded (`recordGitBaseline` in `workspace/git-session.ts`); the spec is rebuilt from that result and a stopped container is restarted only when its identity still matches the rebuilt spec, otherwise replaced. A container whose identity differs is replaced only when no other live session of the repository exists; otherwise it is reused and the launcher prints `pi-sandbox: the sandbox config changed; it applies after every session in this repository exits`. A create that fails on a name conflict (another launcher won the race outside the lock) re-reads and reuses that container. Before a create or start, every volume mount point that lies inside a read-write same-path bind (a `node_modules` overlay, a `mounts.cacheVolumes` target) and is missing is created on the host as the host user, one level at a time after an `lstat` (a link or a non-directory refuses with `the mount point <path> is a symbolic link` or `is not a directory`), after the real path of the nearest existing ancestor is checked to lie within the writable root (otherwise `the mount point <path> leads outside <root>`, and nothing is created), so the engine never creates it as root. After every start (a create, or the restart of a stopped container that is current for the spec; not when joining a running one, and not for a stopped container adopted after a lost create race that is not current, which is only started) one exec as root runs `chown -h <spec user, or 1000:1000>` over the spec's `ownedPaths` (every cache, overlay and shared-cache mount point and each directory between `/home/pi` and a shared-cache mount point), so new volumes are writable by the sandbox user; a failure is the notice `warning: the sandbox user may not be able to write its cache volumes: <stderr>`. When it created one, the share probe (`probeHostSessions`) checks that the container sees the host session directory (a stop with `pi-sandbox: sessions: <dir> is not writable from the sandbox; set sessions.host: false or share it with the VM`, after removing the new container, when not). Then `syncSettingsFile` writes, under `<state>/sync/<repo hash>/sync.lock`, the host `settings.json` keys (package URLs stripped of userinfo, with a notice) over the volume copy (a failure is a warning, not a stop).
12. Exec pi in the container with the host cwd as workdir, the `env.allow` host variables and `PI_SANDBOX_LAUNCH_ID` (the session id) as the exec's environment, and return pi's exit code.
13. When pi exits: `readDenials` (`GET /denials?since=<launch start>` with the repository token) prints one stderr line per blocked host (`run pi sandbox egress allow <host>`, or `egress grants are off, add it to egress.allow` under `egress.grants: false`), and `endSession` removes the session and, under the same lock, stops the container (`backend.stopContainer`) when no live session of the repository remains (D2), then runs `gitSessionEndNotices` (`workspace/git-session.ts`, under `withGitPinLock` (`<state>/git/pins/<sha256 of the git common dir>.lock`), unless `gitDirInUseElsewhere` finds a created or running container of another checkout whose `pi-sandbox.git-common-dir` label, or an entry of its `pi-sandbox.git-common-dirs` label, is, holds or lies inside this git common dir (in workspace mode each repository is unpinned under its own lock, asked per git common dir, so a running single-repository sandbox of one of them keeps its pin and a running workspace sandbox keeps the pins of the repositories it holds), removes each `commondir` pin, with a notice when its content changed or it could not be removed, re-runs the layout checks as notices, names alternates that appeared, and compares a new walk of the checkout and `git ls-files --stage` with the baseline, printing a notice for each new or changed `.git` entry and each new gitlink; in workspace mode the walk covers the whole folder skipping every known git dir, within the same 50 000-directory budget as the launch scan, the gitlinks are listed per repository, and the record is keyed by the workspace root), then sweeps the whole host session directory, `agents/` trees included; when other sessions remain, only the top level is swept, after `endSession`. A session whose launcher pid is dead does not count, so a crashed launcher never keeps a container alive.

`pi sandbox doctor` runs the same steps one by one, so it builds the image and creates the container, then runs its probes through execs into it (`container/probes.ts`, `cli/commands/doctor-container.ts`) and its host checks (`cli/commands/doctor-host.ts`). Inside, `mcp-auth sweep` fails on any `mcp-auth.json` token that is not a placeholder, `settings sweep` fails on a `settings.json` package whose URL carries userinfo (`settings.json package <host> carries a credential in its URL`); on the host, each OAuth server of the host user `mcp.json` gets one line from host pi's `mcp-auth.json` (`mcpSignIns`): `ok mcp <name>: signed in on the host (expires in <duration>)` (a refresh token counts as signed in) or `warn mcp <name>: needs sign-in: run pi mcp login <name>`. `vm size` reads `colima status --profile <profile> --json` (`cpu`, and `memory` in bytes) for the profile `backend.status()` reports and returns the `warn` status (`warned` in `container/probes.ts`, printed as `warn <check>: <detail>` and not counted as a failure) below 8 CPUs or 10 GiB, with the `colima stop … && colima start … --activate=false --cpu 8 --memory 10` command; it is skipped for any other backend, without a profile, when `colima` is not on `PATH` and when the JSON lacks the numbers. `vm shares` runs the same coverage check as the launch from `lima.yaml`, for any profile, and only reports: `ok` naming the shares, `fail` naming the missing path and the full restart command (with `run pi here once` only for `pi-sandbox`), `skip` for any other backend, without a profile and without `lima.yaml`. A container the doctor created is removed when it ends, unless another session of the repository is live by then. Rendering stays in `cli/commands/doctor.ts`.

### Intercepted commands

- `pi install|remove <source>` without `-l` runs the host pi of host jobs on the host in the cwd, like `pi mcp add`, and the host `settings.json` reaches the sandbox at the next launch. A local `pi install` source inside the repository, its git dirs or the workspace root (`mountedGitDirs`, lexical or real path) is refused with `pi-sandbox: <source> lies in the repository, which the sandbox can rewrite; not installed on the host`, since host pi would load code the container can rewrite; nothing is written.
- `pi mcp add|remove ...` runs the host pi of host jobs on the host with `PI_CODING_AGENT_DIR` set to the host agent dir, in the current folder; `pi mcp login|logout ...` does the same in a fresh empty `<state>/mcp-login-<random>/` folder (removed after), so no project `.pi/mcp.json` loads and only servers of the host user `mcp.json` sign in. Every flag passes through. `pi mcp list` runs inside the sandbox.
- A bare `pi update` (or `pi update pi|self|--self`) resolves the host pi with `resolveShellPi` (roots: the cwd and its git root, `nearbyRoots`). A managed or `PATH` pi gets its own `update` run on the host (the managed one through its `bin/pi` wrapper, which sets `PI_MANAGED_INSTALL_ROOT` so pi updates the managed release); after exit 0 the host pi of host jobs is resolved again and the launcher prints `pi-sandbox: the sandbox follows pi <version> at the next launch`, or for a `PATH` pi `pi-sandbox: the sandbox follows pi <version> next to the launcher, not <path>; update it with npm install -g pi-extensions-mz`. With only the bundled pi (or none) it prints `pi follows the launcher; update it with npm install -g pi-extensions-mz`. `pi update <target>` and `pi update --extensions` pass through.

### Host pi

`hostpi/locate.ts` finds pi packages without importing them. `locateManagedPi(agentDir)` reads pi's managed install in the host agent dir: `install/managed-install.json` with `kind: "pi-managed-install"`, `schemaVersion: 1`, `layout: "releases-v1"`; `install/current-version` matching the safe version pattern (so it cannot leave `install/releases/`); the release's `node_modules/@earendil-works/pi-coding-agent/package.json` version and `bin`; and an executable `bin/pi`. It returns `command: [process.execPath, <release package>/<bin>]` and `wrapper: <agentDir>/bin/pi`. `locateBundledPi()` is `@earendil-works/pi-coding-agent` found in a `node_modules` folder at or above the launcher, run as `[process.execPath, <bin>]`. `locatePiPackage(bin)` walks up from a `PATH` pi's real path to a `package.json` named `@earendil-works/pi-coding-agent`. Which pi was picked is not recorded, so `pi update` (which rewrites only `current-version`) and re-runs of `install.sh` need no step; only its uses are (the image record's `pi`, the daemon config's `piVersion`, `piCommand` and `discoverCommand`).

`cli/host-pi.ts` resolves them in two orders. `resolveJobPi` (host jobs: the proxy's `piCommand`, the provider host table, `pi mcp`, the MCP sign-in, the image version): managed, then bundled; a `PATH` pi never, since one proxy daemon serves every repository of a policy and no per-repository filter protects it. `resolveShellPi(deps, roots)` (`--no-sandbox` through `hostPiCommand`, the doctor line and a bare `pi update`): managed (run through its wrapper), then the first `PATH` pi (with its version when `locatePiPackage` finds its package), then bundled; one selection, so the doctor names the pi `--no-sandbox` runs. `PATH` candidates skip relative entries, the launcher itself (its `bin/` or a wrapper naming `launcher/bin/pi-sandbox`) and any candidate whose path or real path lies inside `roots` (`sandboxRoots`: the repository, its git common dir and `mounts.extraReadOnly`), which the sandbox can write. The managed wrapper runs only for `--no-sandbox` and `pi update`, which need `PI_MANAGED_INSTALL_ROOT`; host jobs never run it, since it prepends a node directory to `PATH` and starts `env node`.

### Signals

`runPi` (`container/run-pi.ts`) puts a tty stdin in raw mode, so Ctrl-C reaches pi as a keystroke. It listens for SIGTERM and SIGHUP, and for SIGINT only when stdin is not a tty. Pi runs as `sh -c 'echo $$ > /tmp/pi-sandbox-<session id>.pid; exec "$@"' sh pi <args>`, with the launch's random hex session id. On one of the signals it runs `kill -TERM "$(cat <pid file>)"` inside the container through `backend.exec`, waits up to five seconds for pi's exec to end, sends `kill -KILL "$(cat <pid file>)"` the same way only if it has not (never stopping the shared container, which other sessions may use), restores the terminal and returns `128 + signal number` (130, 143, 129). Afterwards it removes the pid file, best effort. Only pi gets the signal, so the container's idle process keeps running and the next `pi` reuses the container.

## Config

`SandboxConfig` is the merged result of the defaults and the policy, org, user and project layers. Each layer is validated by a hand-written key spec (precise `<layer>: <key> <problem>` messages); `schema/sandbox-config.schema.json` documents the same keys, and a test keeps the two key sets equal.

`config/merge.ts` overlays a fixed list of dotted leaf keys, layer by layer. A key set by the policy or the org layer is final: a lower layer that sets it too is a `LauncherError` naming both layers (`<layer>: <key> is set by the <policy|org> config and is final there`). `egress.deny` and `env.allow` are unions across every layer instead. Any other key takes the lowest layer's value.

A project layer may set only `mounts.cacheVolumes`, `mounts.autoNodeModules`, `resources.cpus` and `resources.memoryGiB` (`PROJECT_KEYS` in `validate.ts`, an allowlist); `projectKeyRefusal` names the first other leaf key it sets, with the file, and both the loader and `validateLayer` use it, so a repository cannot switch the runtime, add hosts or credentials, or open a channel to other repositories. Secret-looking names in `env.allow` (the shared `isSecretName` predicate, also used by the doctor's credential sweep) are refused. `mounts.sharedCaches` entries must start with `~/`, have no empty, `.` or `..` segment, and not be or lie under `.pi`, `.ssh`, `.gnupg`, `.aws`, `.docker`, `.colima`, `.kube`, `.config` or `.local/bin` (`PRIVATE_HOME_PATHS`); the list may not name an entry twice or one inside another (a trailing `/` ignored).

Egress entries are `host`, `*.domain`, `host:port` or `*.domain:port`. `fallback` is `refuse` or `host`. `PI_SANDBOX_POLICY_FILE` is honoured only when the default policy file does not exist, so a user environment cannot hide a real policy; `PI_SANDBOX_STATE_DIR` and `PI_SANDBOX_USER_CONFIG` always apply.

The org layer is named by `org` in the policy layer, else the user layer: the absolute path of a file that `loadEffectiveConfig` reads at every launch and validates as layer `org` (a missing file is `org: <file> does not exist`). `org` itself is accepted only in the policy and user layers, and a user `org` below a policy `org` is refused like any other final key. The doctor's org line names the file the config loaded.

The merge also records the source layer of every dotted key, which `pi sandbox config` prints; the launcher never writes a config layer.

## Backend contract

Colima is the only engine. A `Backend` is the only thing that talks to it, and the interface is the seam the tests replace with a fake backend. It detects the engine, pulls images by digest (`pullImage(reference, digest?)`, which pulls `repo@digest` when a digest is given and verifies it), looks images up locally (`resolveImage`), builds them (`buildImage`), all returning `ImageInfo { id, digest }`; it finds, creates, starts, stops (`stopContainer(id, timeoutSeconds?)`) and removes containers, runs an exec (`exec(ExecSpec, ExecIo)`: stdin, separate stdout and stderr, tty, size and `onResize`), manages volumes (`ensureVolume(name, labels?)` adds the labels only when it creates the volume; `listVolumes()` returns the managed ones as `VolumeSummary { name, labels, inUse }`, `inUse` when any container mounts it), prepares the guest's proxy route (`prepareProxyRoute({ hostPort, repoHash, relay: { policyHash, imageId } })` returns `ProxyRoute { network, address, notices? }`) and reports a status map. `ContainerSpec` carries the image id, mounts, `NetworkRef`, env, read-only root, tmpfs, init, resources, labels; containers run as the image's `pi` user. `ExecSpec` carries container, command, env, workdir, and `user` for the root `chown` exec.

- `backend/docker-engine/` speaks the Docker Engine HTTP API over the Colima socket `~/.colima/pi-sandbox/docker.sock` with `node:http`; `status()` reports the socket and the `pi-sandbox` profile. Every spec mount goes into `HostConfig.Mounts` (`Type` `bind` or `volume`), so a missing bind source fails the create instead of being created as a root-owned directory. Exec is a hijacked `Upgrade: tcp` stream with raw stdin and demultiplexed stdout and stderr frames, with backpressure: the socket pauses while a stdout or stderr writer is full and resumes on its `drain`; the exit code comes from exec inspect. Volumes carry `pi-sandbox.managed`, plus the labels `ensureContainer` passes from the spec's `volumeLabels`: `pi-sandbox.repo-hash` and `pi-sandbox.repo-root` for a repository's agent, cache and `node_modules` volumes, and only `pi-sandbox.user-hash` and `pi-sandbox.shared-path` for a shared cache; `listVolumes` reads `GET /volumes` filtered on the managed label and takes `inUse` from the volume mounts of `GET /containers/json?all=true`. Builds use the legacy build endpoint, so the Dockerfile avoids BuildKit-only syntax. A `400` on container create whose message is `bind source path does not exist: <path>` for a path that exists on the host becomes `the sandbox VM does not share <path>` (hint: `run pi sandbox doctor; its vm shares line names the command`); any other `400` keeps the `engine: POST /containers/create failed (400): …` text.
- `backend/image-reference.ts` splits references into repository and tag and builds `repo@digest`. `backend/labels.ts` holds every `pi-sandbox.*` label key, `backend/managed-network.ts` the per-repository network name and labels, the prune candidates and the removal that deletes a repository's network after its last container, and `backend/exec-capture.ts` a non-tty exec with its output collected.

A conformance suite runs the same behaviour tests against the adapter on an in-process engine HTTP server, against the fake backend, and against the real Colima engine in the live tests.

## Network: proxy instances and relays

There is one proxy instance per policy hash (`proxyPolicyHash(config)`: allowlist, deny list, manual rule hosts, whether grants are on, the rules, private hosts, parent proxy and extra CAs), so two repositories with different policies never share a proxy. What changes with host files (derived rules and hosts) lives in `dynamic.json` instead, so a host-file change never restarts a proxy, and it does not recreate a container while the container's proxy route stays. It does when it decides whether the proxy is needed at all: the first derived rule of a repository that had no proxy adds the proxy route, the trust mount and their environment to the spec, so the spec hash changes and the container is recreated (deferred while other sessions are live).

Each instance has a control token (32 bytes, hex) in `proxy-token` (mode 600), which only the launcher holds: it authenticates `POST /control` as `Basic base64("pi-sandbox-control:" + token)`. Each repository has its own token in `tokens/<repo hash>` (mode 600, created once by `repoProxyToken`), which the guest gets in its proxy URL, `http://pi-sandbox:<repo token>@<route address>`; the proxy maps it to the repository hash from the token files alone (`sha256` of each file in `tokens/`, read again when the directory changes), and answers `407` to any request without a known one (a repository token on `/control` gets `407` too). `pi sandbox gc` deletes the token of each repository whose container it removes (`removeRepoToken`), so that token stops authenticating, and the next launch of the repository makes a new one. Restarting the proxy keeps both tokens, so the container's proxy URL and spec hash stay. They rotate only when the instance directory goes: `pi sandbox reset` removes the instance of the repository's policy hash (`removeProxyInstance`) unless a running container of another repository carries that `proxy-policy-hash` (`policyHashesInUse`, the same check `collectGarbage` uses). A token only proves which repository's container a request comes from; it is not a credential for anything else, and it never appears in the proxy's logs.

Agent containers have no route out. They join only their repository's internal bridge network `pi-sandbox-<first 12 of the repo hash>` (`prepareProxyRoute({ hostPort, repoHash, relay })`), carrying `pi-sandbox.managed` and `pi-sandbox.repo-hash`; the launcher inspects it and refuses a network of that name that is not internal (hint `run pi sandbox gc`) or not managed (hint: remove that network from the sandbox VM), naming it. The relay is connected to each such network, and `removeContainer` deletes the repository's network (disconnecting relays first) when its last container is gone (`removeWithNetworkCleanup`), unless called with `{ keepNetwork: true }`: `ensureContainer` passes that when it discards an outdated container to replace it, since the route (and so the network) was prepared before and the new container starts on it; reset, the doctor's cleanup, the probe failure and `gc` remove without it, so an ended repository's network still goes; `uninstall.sh` removes every managed `pi-sandbox*` network (through `bin/uninstall-engine.mjs`, which calls the engine API on the socket with Node's `http`, so no `docker` CLI is installed or needed), and `pi sandbox gc` prunes the managed networks (`pi-sandbox-<12 hex>`) of repositories outside the keep set (a container or a live session), force-disconnecting relays first and never deleting a network that holds a non-relay container (`backend.pruneNetworks(keepRepoHashes)`). One relay container per proxy instance, `pi-sandbox-relay-<first 8 of the policy hash>`, from the sandbox image id passed in `relay.imageId` (which has socat), sits on the default `bridge` network and on each repository network it serves. It runs `socat TCP-LISTEN:3128` and forwards each connection to its proxy's port on `host.lima.internal`, Colima's name for the Mac, where the proxy listens on `127.0.0.1` only. Its address is read from network inspect after creation, not fixed. Relays carry `pi-sandbox.managed`, `pi-sandbox.relay`, `pi-sandbox.relay-port`, `pi-sandbox.relay-image` and `pi-sandbox.proxy-policy-hash`; a relay whose port and policy hash labels match is reused whatever its image (started again when stopped, so it usually keeps its address and the agent's spec hash), and a relay whose port or policy hash differ is recreated only when no running container of another repository is attached to one of its networks; otherwise it is kept and `prepareProxyRoute` returns a notice (`route.notices`, printed by the launcher) that it still forwards to the old port, since recreating it would cut those sandboxes, whose proxy URL names the relay's address. The proxy keeps its port across restarts (`proxy-port` in the instance directory, reused when it is free), so a relay rarely sees a new port. The image id is used only when a relay is created and kept in `pi-sandbox.relay-image` for information. An agent container carries the same `pi-sandbox.proxy-policy-hash`, so `gc` removes relays and stops proxy instances that no running container uses and no repository with a live session (whose launch may still be preparing) has a token under; it also keeps a stopped or created container of a repository with a live session.

The internal network's embedded DNS answers container names only; external names do not resolve inside, so every tool must go through the proxy.

## Proxy

The proxy is a detached Node process (`proxy/daemon.ts`) on `127.0.0.1`, started on demand. Its state lives in `<stateDir>/proxy/<policyHash>/`: `proxy.json` (pid, port, policy hash, token), `proxy-token` (mode 600, kept when the proxy stops), `proxy-config.json` (mode 600), `proxy-port` (the last port, reused on the next start when free), `proxy.log` (the daemon's stderr), `proxy-access.log` and `lock`. Start-up holds `lock` (`withFileLock`, see Locks); the launcher reuses an instance whose pid is alive and whose `/healthz` answers with the same policy hash, and kills and replaces one that fails the health check twice. `readProxyInstances` lists only live instances; `stopProxy` stops one or all and removes dead records, keeping the token; `removeProxyInstance` stops one and deletes its directory. The launcher CA is shared at `<stateDir>/ca/`.

`proxy/server.ts` (`startProxyServer`) only checks the token, decides a CONNECT (`decideConnect`) and hands it to the denial page, the TLS interceptor (`proxy/intercept.ts`, per-host TLS contexts) or the tunnel (`proxy/tunnel.ts`, address check, ClientHello and splice), then listens and closes; the plain-HTTP routes are in `proxy/control-routes.ts`, denial recording in `proxy/denials.ts`, the shared reply helpers in `proxy/replies.ts`, and the launcher's HTTP client to a daemon (`readHealth`, `sendProxyControl`, `fetchDenials`) in `proxy/client.ts`.

- `CONNECT host:port` is allowed for hosts in `egress.allow` and manual rule hosts, then for the repository's extra list: derived hosts and the grants of the repository and the user (`extras` in `proxy/runtime.ts`). `egress.deny` wins over all of them. Ports are 443 unless an entry names one. IP literals, localhost, loopback, link-local, private and reserved ranges, the metadata address and names that resolve only to such addresses are refused, except names in `egress.privateHosts`. For a tunnel that is not terminated the proxy resolves the name and refuses one that resolves only to restricted addresses with a `403`, then answers `200`, reads the TLS ClientHello and refuses a missing SNI or one that differs from the CONNECT host, and only then dials (itself or through the parent proxy), so a refused server name opens no upstream socket. A direct dial gives up after 10 s (`proxy/dial.ts`) and is recorded as an `upstream` denial. Tunnels to hosts without a rule are not decrypted.
- A denial is `403` with a JSON body `{ denied, rule, reason }` and `Proxy-Agent: pi-sandbox`; an allowlist denial's reason is `pi-sandbox: <host> is not allowed; run pi sandbox egress allow <host>`, or `pi-sandbox: <host> is not allowed; egress grants are off, add it to egress.allow` under `egress.grants: false`. For a CONNECT the allowlist or port check denies, the denial page (`proxy/denial-page.ts`) accepts the tunnel instead, never resolves or contacts the host, serves a `403` text page carrying that reason over TLS with a launcher-CA leaf for the denied name (kept in memory only, LRU of 256), and closes; it mints at most 30 new names a minute and keeps 256, beyond which the CONNECT itself gets the JSON `403`. The fetch tool inside thus shows the hint to the model. The last 200 denials per repository are kept in memory (`proxy/denials.ts`) and served at `GET /denials?since=<ms>` to that repository's token. Plain HTTP is refused except `/healthz` (`{ ok, policyHash, pid }`), `/policy`, `/denials` and `/control`.
- Credential rules (`proxy/rules.ts`, `proxy/terminate.ts`): TLS is terminated for every rule host with a per-host leaf signed by the launcher CA through openssl, kept in the daemon's memory only (an LRU of 256 hosts, one mint per host at a time, minted again once it nears expiry); the daemon builds one TLS context per leaf. The CA itself is created once under `<stateDir>/ca/ca.lock`: a fresh key and certificate pair that match is never replaced; otherwise a new pair is made in a temporary directory and renamed into place under the lock, and a reader that finds a pair that does not match takes the lock and reads again; the TLS handshake of a terminated CONNECT gets the ClientHello timeout, and the parent proxy dial and CONNECT head a 10 s timeout. For the matching rule (host, port, path prefix), the placeholder is replaced only in the rule's header, or for a header-less rule in auth-like request headers (`authorization` and `isSecretName` names, never `proxy-authorization` or `sec-*`), and stripped from every other header, never in query or body; an absolute-form target for another origin and a dot-segment path (raw, `%2e`, encoded slash, backslash) get `400`, and `pathPrefix` matches the decoded path; then a `header` rule sets its header from `template` when it is absent or still carries the placeholder. Every response header value is scrubbed by substring (real secret to placeholder). A secret that cannot be resolved removes the header that carried the placeholder, so public endpoints still work, and logs `rule: credential, reason: unavailable`; an upstream `401` invalidates the cached secret once. A gateway is one such rule; a private gateway host is listed in `egress.privateHosts`. Upstream connections are kept alive (4 s idle) in one pool per repository, host, port and access, so two repositories never share an upstream connection or parent tunnel; an upgrade request gets a fresh connection outside the pool. Server-sent events stream unbuffered and WebSocket upgrades are forwarded.
- Secret sources (`proxy/secrets/`, one file per kind, behind `createSecretResolver`): `env` (the map the launcher sent over `/control`, memory only, never the daemon's own environment), `file` (a JSON pointer into a host file), `command` (argv, stdout trimmed or `{ token, expiresAt }`, cached for `ttlSeconds`, 300 by default, single-flight), `piAuth` (the host pi's `auth print-api-key` or `print-bearer-token --min-expiry 5m`, cached 240 s), `mcpOAuth` (see MCP sign-in below). Values never reach disk, logs or error messages.
- Parent proxy (`proxy/parent.ts`): `"env"` takes the address of `HTTPS_PROXY` and `NO_PROXY` from the daemon's environment, which the launcher passes without userinfo; the credentials from that URL come only from the control map under `egress.parentProxy`, sent on every launch. An object names the URL, `noProxy` and an `auth` secret for Basic auth. An IPv6 literal (`http://[::1]:3128`) is dialled without its brackets. The private-range check still runs on local resolution; an NXDOMAIN while a parent is set is passed to the parent.
- Daemon children (host pi refresh, discovery, command secrets) run with a minimal environment; `proxy/control.ts` also strips the daemon's own environment to `PATH`, `HOME`, `TMPDIR`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, the CA file variables and `NODE_OPTIONS`, and writes the parent proxy address without userinfo as `parentEnv` in `proxy-config.json`. File secrets lose trailing newlines; an env secret with CR or LF is unavailable (the launcher refuses it before).
- MCP sign-in (`proxy/secrets/mcp-oauth.ts` over `proxy/sign-in.ts`): the token is the entry of host pi's `<hostAgentDir>/mcp-auth.json` (`readMcpAuthEntry` in `shared/mcp-auth-key.ts`, the one parser; the launcher never writes that file). An access token with more than 30 s left is used. Otherwise, when the server's lock is free, `lastStart` in `<state>/mcp-login.json` is older than 60 s and `failedAt` older than 10 min, it records `lastStart` and `running: { pgid, boot }` and starts `pi mcp login <name> --timeout 300` (stdin ignored, output to `proxy.log`, a fresh empty `<state>/mcp-login-<random>/` cwd, `PI_CODING_AGENT_DIR` the host agent dir, its own process group) holding the lock until it exits, which clears `running` and on failure records `failedAt`. pi's login connects first, which refreshes a stored token and exits 0 (`Already signed in`), else it opens the browser on the host. The request waits up to 10 s; a login that exits 0 with a fresh entry gives its token, anything else answers the request locally, without dialling upstream, with `503`, `retry-after: 30`, `text/plain` and `pi-sandbox: sign-in to MCP server <name> opened in the browser on the host; finish it there, then retry. If no browser opened, run pi mcp login <name> on the host.` An upstream `401` to a request whose placeholder the proxy substituted marks that token rejected, starts the same login under the same checks and is replaced with that `503`; a `401` to a request carrying the container's own `Authorization` passes through and starts nothing. Proxy stop sends SIGTERM to every login group it started (SIGKILL after 2 s); after a kill -9 of the proxy a login ends at its own timeout.
- Upstream trust is the system roots plus `<state>/ca/extra.pem` when `tls.extraCa` is set.
- Every decision is one JSON line in `proxy-access.log` (`time, user, repo, host, sni, decision, rule, reason, credential, bytesIn, bytesOut`), never a credential or a token.

## Credentials and derivation

`hostpi/` turns the host pi files into the sandbox's (`deriveSandboxPi`, pure, no secret value in its output):

- `auth.json`: an `api_key` entry becomes `{ type: "api_key", key: P }` with a rule `{ piAuth: id }`; an `oauth` entry keeps its non-secret fields, `access` becomes P (JWT-shaped when the token is a JWT, so the header and payload stay real), `refresh` an opaque placeholder and `expires` far in the future, with a rule `{ piAuth: id, bearer: true }`. A provider key found only in an environment variable the provider host table names gets an `api_key` placeholder and the same rule.
- `models.json`: `apiKey` becomes a placeholder; header values that are `$NAME`, `!cmd` or under an auth-like name become placeholders with `{ env }`, `{ command: ["sh","-c",cmd] }` or a `{ file, pointer }` into the host `models.json`; for a model with an `id`, its header and `baseUrl`-userinfo rules use a `command` secret instead, `hostpi/model-secret.mjs` run with node, which finds the model by provider, id and base URL when the secret is resolved and fails if it moved, so reordering `models.json` cannot send one model's secret to another's host (cached for the command TTL, 300 s by default). Rule hosts come from the provider and model `baseUrl`s, or the provider host table for built-in providers. A `localhost` or plain-`http` `baseUrl` gets a notice.
- `mcp.json`: HTTP server headers as in `models.json` (literal `Cookie`, `Set-Cookie`, `Proxy-Authorization`, `X-Auth*`, `X-Api*`, `X-Access*` and `X-Session*` headers included), `oauth` blocks removed (the container never sees a client secret or a token); a server whose URL has a secret-like query parameter (`isSecretName`, or `auth`, `sig`, `signature`, `pass`, `passwd`, `pwd`) is dropped with `mcp <name>: the url carries a credential in its query string; add a header rule instead`; for a stdio server, env values with URL userinfo, URL arguments with userinfo and `--name=value` arguments with a secret-like name become placeholders, with the stdio notice; and a server without `Authorization` or a URL password gets `Authorization: Bearer P` with an `mcpOAuth` rule `derived:mcp:<name>:oauth`. stdio servers are copied; secret `env` values become placeholders with a notice.

Placeholders are `pi-sandbox-` plus the first 24 hex of `sha256(salt + identity)`, where the identity names the source (`auth:<id>:key`, `models:<id>:header:<name>`, `mcp:<server>:oauth`, ...) and the salt is `<state>/salt`, so they are stable across launches and unguessable. Derived rule ids are `derived:<identity>`; manual ids cannot contain `:`. Rules and hosts are filtered by `credentials.derive`, and a manual rule for the same host wins. The provider host table comes from `hostpi/provider-hosts.mjs`, run with `process.execPath` against the provider list of the host pi of host jobs and cached at `<state>/provider-hosts/<pi version>.json`; it is used whatever the image's pi version, and a launch whose image recorded another version prints the image notice of step 10.

## Provisioning the agent dir

- `renderAgentDir` (`provision/render.ts`) builds `<state>/render/<repo hash>/` on every launch: the derived `auth.json`, `models.json` and `mcp.json` and filtered copies of `agents/`, `prompts/`, `skills/`, `themes/`, `extensions/`, `AGENTS.md`, `SYSTEM.md` and `keybindings.json` (no symlink is followed, secret-looking files are left out, at most 16 files read at a time through `inPool` in `provision/pool.ts`, entries gone on the host are removed) and returns `{ renderDir }`. It is mounted read-only as a directory at `/opt/pi-sandbox/render`, and the entrypoint links each present entry into the agent dir, replacing a dangling or older link, never a file or dir the user created inside. A read-only `auth.json` link makes `/login` fail instead of writing a real secret into the volume.
- `syncSettingsFile` (`provision/sync.ts`) keeps `settings.json` a writable file in the volume, since pi writes it: at each launch the host keys overwrite the volume copy and volume-only keys stay, through `backend.exec` (`cat`, and a write through stdin only when the result differs), under `<state>/sync/<repo hash>/sync.lock`. Host-absolute local package paths outside the mounted paths are dropped with a notice, and a credential in a package URL is removed with a notice.
- Nothing from the volume is written back to the host; an intercepted `pi install|remove` runs on the host pi instead, and the sync drops the volume's host-owned settings (`npmCommand`, `selfUpdateCommand`, `shellPath`, `shellCommandPrefix`, `externalEditor`, `httpProxy`) in favour of the host's.

## Host sessions

`sessions.host` (default on, `cannotEnable` under policy and org, refused in the project layer) puts this repository's pi sessions in host pi's own session directory, so host pi lists them.

- `workspace/pi-session-dir.ts`: `hostAgentDir` (the one resolver of `PI_CODING_AGENT_DIR` or `~/.pi/agent`, also used by `mounts.ts` and `cli/deps.ts`), `sessionSlug` and `hostSessionsDir`, and `hostSessionsChoice`, which gives `{ dir }` or `{ off, notice }` (a custom dir counts when the env value or `sessionDir` is a non-empty string, as in pi; a `file://` `PI_CODING_AGENT_DIR` is converted as pi's `normalizePath` does; `sessionsSwitchNotice` names an unknown `PI_SANDBOX_SESSIONS_HOST` value, which is ignored): off when the key is off, when `PI_SANDBOX_SESSIONS_HOST=off`, when host pi uses a custom session dir (host `PI_CODING_AGENT_SESSION_DIR` or `sessionDir` in the host `settings.json`; that dir is flat and shared by every repository), and when the directory lies under the guest agent dir `/home/pi/.pi/agent` (a Linux host user named `pi`). The last two print a notice.
- The slug is a pi interface the launcher copies, since launcher code may not import pi: `--` + the resolved path with its leading `/` or `\` removed and `/`, `\` and `:` replaced by `-` + `--` (`getDefaultSessionDirPath` in pi's `core/session-manager.js`). The repository path is the real path, as the cwd pi runs in, so the slug matches what host pi writes for the repository root. The live test `tests/live/host-sessions.live.test.ts` checks that host pi and sandbox pi land in the same directory.
- `workspace/guard.ts` `assertHostSessionsDir` is the one exception to never mounting under `~/.pi`: it recomputes the directory, requires it exactly one level under `<agent dir>/sessions` with a slug matching `^--[^/]*--$`, a real directory (`lstat`, not a symlink), and a real path equal to the slug under the real path of `<agent dir>/sessions`; that real path may not be or contain `~/.pi` or the agent dir, and may not be, contain or lie inside any other entry of the agent dir (real paths compared, so a symlinked `sessions` that resolves into `extensions/` is refused).
- `provision/host-sessions.ts`: `prepareHostSessions` (`mkdir -p` with mode 0700, so only missing directories are created and an existing mode stays), `sweepHostSessions` and `probeHostSessions`. The sweep handles at most 8 top-level entries at a time; it `lstat`s each, re-`lstat`s and compares device and inode right before acting, and `unlink`s only that entry: symlinks, fifos, sockets and devices. A top-level `*.jsonl` is opened with `O_NOFOLLOW | O_NONBLOCK`, checked against the `lstat`, and read in 64 KiB chunks only until pi's header rule decides: the first non-blank line (split on `\n`, as pi's opening does) that parses to a truthy JSON value; a bare `\r` in any line up to that one rejects the file, because pi's listing (readline) also breaks at it, so with none the two splittings agree. A first entry that is not `type: "session"` makes pi skip the file, so it stays; a session whose `cwd` is not an absolute path inside the repository (lexically), no deciding line within 1 MiB (pi's listing has no such cap), or an open or read error fails closed: the file is renamed to `<name>.rejected-<random>` (so an existing name cannot block it), and deleted after the identity check when the rename fails. Empty files and a final line that does not parse yet (a header being written) stay, since pi does not list them either. A top-level file over 256 MiB gives a warning. Before reading the root or descending into a subdirectory, the sweep restores `u+rwx` on a directory the host user owns. It returns `failures` for an entry it could neither rename nor delete, or a directory it could not list; `readyHostSessions` and `sweepForHostPi` then refuse with a `LauncherError` naming the file and the dir (before any container is created, or before host pi runs), and the exit sweep warns. With `full`, the walk recurses into directories (the `<session>/agents/` trees) and removes special files at any depth. The probe writes an empty `.pi-sandbox-probe-<random>` on the host and runs `test "$PI_CODING_AGENT_SESSION_DIR" = "$1" && test -f "$1/$2" && : > "$1/$2.guest" && rm "$1/$2.guest"` inside, so the guest's own create and delete is what counts, then deletes both files; `probeSessionsShare` removes the new container when the probe fails or its exec throws.
- Sweep timing: before the spec and before host pi on `--no-sandbox`, `sweepWhenIdle` takes the repository's session registry lock (`withRepoSessionLock`, the lock `registerSession` and `endSession` use) and sweeps the whole tree only when no other live session is registered and the container is not running (on `--no-sandbox`, also only when the backend answers); every container start follows a `registerSession`, so no agent can start during that walk. After pi exits, the whole tree is swept inside `endSession`'s `onLast` after the stop, otherwise the top level after `endSession`. The swept directory is the repository's default slug directory whatever the toggle, so a directory left from an earlier launch is still cleaned when the feature is off; it is created only when the feature is on.
- The spec label `pi-sandbox.session-dir` holds the directory or the reason it is off; it is part of the spec hash with the bind and the env variable, so switching the key or a host change that switches it recreates the container. `pi sandbox status` prints `session dir:` from that label of the existing container, and the doctor's `sessions share` probe reads the same label of the container it probes (`target.containerId`), so both describe the container as created, not the config.
- `env.allow` refuses `PI_CODING_AGENT_DIR`, `PI_CODING_AGENT_SESSION_DIR` and `BASH_ENV` (`LAUNCHER_SET_VARIABLES` in `shared/pi-env.ts`, with the variable names the spec and the probe use), and `forwardedEnv` drops them, so no exec environment overrides the spec's or the image's value.
- In workspace mode the session directory is the workspace root's slug, and the sweep's inside check is against the workspace root, so a session started in any folder under it is kept.
- No migration: sessions from the volume stay there (`/home/pi/.pi/agent/sessions/<slug>`), reachable inside with `--session-dir`, removed by `reset --volumes`.

## Sessions and grants

- `grants/sessions.ts`: one file per running launch in `<state>/sessions/<repo hash>/`, written and removed under a lock there; `liveSessions` ignores entries whose pid is dead, and `registerSession` and `endSession` delete those entries. `pi sandbox stop` (`cli/commands/stop.ts`, no backend, no repository) reads them for every repository: it prints `no sandbox VM: the colima profile pi-sandbox does not exist` without `~/.colima/pi-sandbox/colima.yaml` and `the sandbox VM is already stopped` when `colima status --profile pi-sandbox` exits non-zero (both exit 0), refuses with `<n> pi sessions are running; stopping the sandbox VM would end them` (hint `exit them and run pi sandbox stop again`) while any is live, and otherwise, under `<state>/locks/vm.lock` and after checking the sessions again, runs `colima stop --profile pi-sandbox`, then `proxy.stop(stateDir)` for every instance, printing `stopped proxy pid <pid> port <port>` for each and `stopped the sandbox VM (profile pi-sandbox); the next pi starts it again`. Containers stop with the VM; relays come back at the next launch's `prepareProxyRoute`. The session id (16 hex) is in the exec environment as `PI_SANDBOX_LAUNCH_ID`, never in the spec.
- `grants/store.ts`: `<state>/grants.json` (mode 600, atomic, locked with `withFileLock`, see Locks) holds `{ host, port, repoHash?, createdAt }`; no `repoHash` means every repository (`egress allow --user`). Grants last until revoked. `addGrant` refuses while `egress.grants` is `false`. `activeGrants` keeps the grants of the repository and the user-wide ones. The proxy reads them live on every CONNECT that the static policy refused.

## Container identity

A container belongs to one repository: its name is `pi-sandbox-<first 12 of the repo hash>`. Its labels carry `pi-sandbox.managed`, the full `repo-hash`, `repo-root`, `image-digest`, `image-reference`, `proxy-policy-hash` (when it has a proxy), `version`, `git-common-dir` (a repository) or `git-common-dirs` (a workspace: the JSON array of its repositories' git common dirs) and `spec-hash`, the sha256 of the rendered spec as key-sorted JSON. The container is created from the image id, with the reference kept in its label. `ensureContainer` reuses a container whose image digest and spec hash both match (starting it when stopped) and otherwise stops and removes it and creates a new one. So a new image or any change in the rendered spec (the proxy policy hash and the launcher version are labels in it) (a new proxy route, a token rotated by `reset`, a new mount, such as a repository added to a workspace or a new lockfile folder) gives the next `pi` a fresh container, while the volumes survive. In workspace mode the container belongs to the workspace root: its name, repo hash, volumes and session directory are the root's.

The spec mounts the repository and git common dir read-write at their host paths, then, from the git plan (`planGitOverlay` in `container/git-overlay.ts`, the paths from `workspace/git-protect.ts`), binds onto themselves read-write the git dir and every directory between the repository root (or a git dir outside it) and a read-only path (`.git`, `.git/modules`, `.git/modules/<name>`, `.git/worktrees/<name>`, the parents of a `core.hooksPath` inside the repository), so none of them can be renamed away from its mounts, and then the read-only paths, each bound from its snapshot `<state>/git/<repo hash>/snapshots/<first 16 of the sha256 of the path>`: the dirs `hooks` of the common dir and of every submodule git dir and the effective `core.hooksPath` when it resolves inside the repository or git dir (refused when it goes through a link inside them, or is the repository or contains the git dir; left out outside them, since the container cannot see it), and the files `config`, `config.worktree`, `commondir` of the common dir and of every submodule git dir (the `commondir` pin whether or not it exists yet), `commondir`, `gitdir` and `config.worktree` of every `worktrees/<name>`, and the checkout's `.git` when it is a file. `git config --show-scope --get-all core.hooksPath` (with the inert options of step 1) gives the hooks path, ignoring the command-line value. Submodule git dirs are found by walking `.git/modules/`: a dir with a `HEAD` file is a module git dir, and only its `modules/` subdir is walked further (a dir without `HEAD` is a path segment of a module name and is walked into), so objects are never listed; a link anywhere in that walk or under `worktrees/` refuses. Every listed path is `lstat`ed: a link refuses, a path whose real path differs from it refuses, and every path must pass the `mounts.extraReadOnly` protected-path check (`gitPathGuard` over `protectedRealPathGuard`, with the engine socket handed in by `container/`, so `workspace/` does not import `backend/`). `writeGitSnapshots` (`container/git-snapshot.ts`) deletes the snapshot dir and copies each file through `readRegularFile` (`O_NOFOLLOW`, device and inode of the open file equal to a fresh `lstat`, at most 8 MiB) and each hooks dir as regular files and directories only; it runs only in the plan's `ready()`, when no container of the repository runs, and the snapshot paths depend on the target path alone, so the spec hash stays stable from launch to launch. It adds `mounts.extraReadOnly`, checked by `workspace/mounts.ts` `resolveExtraMounts` (each entry exists as a file or directory, is bound from its real path at its `~`-expanded path, and is refused when it is or contains the home, or is, contains or lies under `~/.pi`, the agent dir, the state dir, the user config, `~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.docker`, `~/.colima`, `~/.kube`, `/var/run`, `/run`, `/etc`, `/proc`, `/sys`, `/dev`, a `.git` dir or the engine socket), the repository's agent volume `pi-sandbox-agent-<user hash>-<repo hash>` at `/home/pi/.pi/agent`, per-repository cache volumes, the `node_modules` overlays and the shared caches. `nodeModulesOverlays(workspace, config)` maps each of the workspace's `nodeProjects` to `<dir>/node_modules`, drops those equal to or inside a `mounts.cacheVolumes` target and names each like a cache volume, `cacheVolumeName(root, relative(root, path))`; it is empty with `mounts.autoNodeModules: false`. `sharedCacheVolumes(config, stateDir)` gives `pi-sandbox-shared-<user hash>-<first 8 of the sha256 of the ~/ path>` mounted at `/home/pi/<path>`, where the user hash (`userHashOf`) is the first 12 hex of the sha256 of the state dir path, so two repositories of one user share the volume. `repoVolumes` lists the agent, cache and overlay volumes for `reset --volumes`, never the shared ones. Repository volumes are labelled with the repository's `repo-hash` and `repo-root` when created (an existing volume keeps its labels), so `pi sandbox gc` removes those whose root is gone from disk and no container mounts (a removal the engine refuses is skipped), and counts the unlabelled ones in a notice; shared caches carry `user-hash` and `shared-path` and no repository label, so that sweep never takes them, the unlabelled count leaves them out, and `gc --shared-caches` removes those of this user's hash that no container mounts (`removed shared cache <volume> (<~/path>)`, `kept shared cache <volume> (<~/path>), in use`). `reset --volumes` removes `repoVolumes` and every volume labelled with the repository whose name starts with `pi-sandbox-cache-` (the overlays of packages deleted since). The spec's `volumeLabels` carries each volume's labels and `ownedPaths` the mount points the root `chown` covers; neither is part of the runtime spec. The root is read-only with tmpfs `/tmp` and `/home/pi`, under an init process, as the image's `pi` user (uid 1000). It mounts the render dir read-only at `/opt/pi-sandbox/render` and, when there is one, the trust bundle at `/etc/pi-sandbox/ca.pem`. The environment holds no host variables (the allowlisted ones and `PI_SANDBOX_LAUNCH_ID` go to each exec, so the spec hash does not change with the terminal): the proxy variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, `NODE_USE_ENV_PROXY`) with the repository token when there is a proxy, `NODE_EXTRA_CA_CERTS` and `PI_SANDBOX_TRUST_HASH` when the trust bundle is mounted (so a CA change recreates the container), the CA bundle paths, `PI_SANDBOX=1`, `PI_SKIP_VERSION_CHECK=1` and `PI_TELEMETRY=0`. `PI_OFFLINE` is not set, so pi installs configured packages and runs updates through the proxy.

## Image

`image/Dockerfile` builds on a slim Node image with git, search tools, ssh, tini, socat and netcat, a `pi` user with uid 1000, and pi pinned to the version in the package's dev dependencies. It bakes no pi config, no pi package and no credential; this package's extensions, like every pi package, come from the `packages` key of the host `settings.json`, which the sandbox's pi installs. Likewise `auth.json`, `models.json` and the rest come from the render dir at run time. `PI_SELF_UPDATE_COMMAND` points at a script that prints that pi follows the launcher. `BASH_ENV=/usr/local/lib/pi-sandbox/bash-env.sh` makes every non-interactive bash define `command_not_found_handle`, which prints `bash: <cmd>: command not found` and the `image.packages` / `image.npmGlobal` hint to stderr and returns 127. The Dockerfile also puts `. /usr/local/lib/pi-sandbox/bash-env.sh` on the first line of `/etc/bash.bashrc`, before Debian's early return for non-interactive shells: a `bash -c` whose stdin is a socket and whose environment has no `SHLVL` counts as run by rshd, reads the system bashrc and `~/.bashrc` and skips `BASH_ENV`, and that is how pi's shell tool runs commands (Node's piped stdio is a socketpair and the `sh` entrypoint exports no `SHLVL`). The script only defines the function, so a shell that reads it through both is unchanged. `BASH_ENV` is set in the Dockerfile, not in the spec, so a pinned older image without the file does not break every shell; `env.allow` refuses the variable. The build context (`buildInContext` in `image/context.ts`, a temporary dir under the state dir, removed after) holds the Dockerfile, `trust.pem`, `entrypoint.sh` and `bash-env.sh`; the Dockerfile copies `trust.pem` into `/build/` before the pi install and the entrypoint and `bash-env.sh` only after it (no `COPY . /build/`), so a change to either script does not rerun the install. During the build the extra CAs are trusted (`trust.pem` in the context) and removed again at the end, and a parent proxy without credentials is passed as the predefined proxy build arguments (`image/build-proxy.ts`); one with credentials refuses the build.

The entrypoint removes dangling links into the render dir, re-creates every render link in the agent dir (`rm -rf` then `ln -s`, so whatever the agent put in place of `auth.json`, `models.json`, `skills` and the rest is replaced), builds a CA bundle from the system roots plus `/etc/pi-sandbox/ca.pem` so tunneled hosts keep the system roots, and idles under tini; pi runs through exec. `ensureSandboxImage` is the entry point: it reuses the recorded image when a current container of the repository runs it, else `pullPinnedImage` pulls and verifies a pinned digest through `backend.pullImage`, or `ensureBuiltImage` hashes the build inputs (`stableHash` of reference, pi version, Dockerfile, entrypoint, `bash-env.sh`) against `<stateDir>/image.json` and rebuilds when they changed or the recorded image is gone. Either way it records the reference, digest and image id; `recordedImage` is the one reader of that record.

`ensureLayerImage` (`image/layer.ts`) renders `FROM <base id>`, `USER root`, the build trust, `apt-get install` of `image.packages`, `npm install --global` of `image.npmGlobal`, the `image.dockerfile` text verbatim (it is user, org or policy config, never the project's, and a `RUN` as root could change anything a directive check would guard), then the build trust removal and a fixed tail (`USER pi`, `WORKDIR /home/pi`, the entrypoint and an empty `CMD`), tags it `pi-sandbox-layer:<first 12 of the inputs hash>` and records it as `image.json` `layer`, so it is built once per set of inputs.

## Locks

`shared/file-lock.ts` has the launcher's one lock primitive, used for the proxy start-up, the grants and session registries, `ensureContainer`, the CA, `provision/sync.ts`, `dynamic.json` and the MCP sign-in (`<state>/locks/mcp-login-<sha8(key)>.lock`, held for the whole login; `withFileLockIfFree` tries it once and reports a held lock instead of waiting). `withFileLock` writes the holder's pid to a temporary file and links it into place, so the lock always holds a complete pid. A lock whose pid is alive is never taken over, however long its holder has stalled; one whose pid is dead, or that holds no readable pid, is taken over at once. Takeovers go one at a time through `<lock>.takeover` (a lock of the same kind, held for the few system calls of the takeover); the taker checks the lock again under it, renames it to a unique name, compares the renamed file with the stale lock it measured (inode and mtime) and links it back when it is a different, live one. A holder removes the lock on release only when it is still its own file (same inode). `withDirectoryLock` is an `mkdir` lock: an empty directory whose mtime the holder refreshes every second, taken over when older than 10 s, through the same guard, rename and check. The VM share step, the launch's VM start and `pi sandbox stop` take it as `<state>/locks/vm.lock` (180 s timeout), so two launches that both need a share restart the VM once, two launches on a stopped VM start it once, and a stop never interleaves with a start or a share restart.

## Files written

- `~/.local/state/pi-sandbox/` (or `PI_SANDBOX_STATE_DIR`): the launcher's own state, including `git/<repo hash>/snapshots/`, `git/<repo hash>/baseline.json`, the `git/pins/<hash>.lock` locks, `mcp-login.json` (mode 600), the `locks/mcp-login-<hash>.lock` locks and an empty `mcp-login-<random>/` folder as the cwd of each host `pi mcp login` or `logout` the launcher runs, removed when it exits.
- Host pi, not the launcher, writes `<hostAgentDir>/mcp-auth.json` during the `pi mcp login` the launcher starts.
- `~/.colima/pi-sandbox/colima.yaml`: never written by the launcher; its `colima start --mount …` (with colima's default `--save-config`) has colima save the new mount list there, and `install.sh` passes `--mount $HOME:w` only when that file is missing.
- `~/.config/pi-sandbox/config.json`: the user config, written only by the installer, its `org` key with `--org`.
- `~/.pi/agent/sessions/<slug>/` on the host while host sessions are on: the launcher creates the missing `~/.pi/agent/`, `sessions/` and `<slug>/` (0700), writes and deletes the probe marker at container creation and on each doctor run, the installer `rmdir`s its smoke repository's empty slug dir, and the sweep deletes special files and renames (or, failing that, deletes) rejected sessions there, also with the feature off; pi inside writes the session files.
- Inside the repository's git dir and worktree: empty hook directories (`.git/hooks`, a `core.hooksPath` inside a mounted path, submodule `hooks`) created when missing, so they can be mounted read-only, and the `commondir` pin (`.`, written by a hard link of a temporary file, or an exclusive create where the file system has no hard links, so it never replaces an entry) in the common dir and in each submodule git dir before every container create or start, removed after the last session only when it still reads `.`; in workspace mode in every nested repository's git dir.
- Inside the repository or workspace folder: an empty directory at each missing volume mount point under a read-write same-path bind (`node_modules` of a node project, a `mounts.cacheVolumes` target), created as the host user before a container create or start.

## Tests

Tests check behaviour with fakes only at the process boundary: a scripted `CommandRunner`, an in-memory engine HTTP server on a temp Unix socket, a fake backend, temp dirs, real localhost sockets and openssl certificates. A folder's tests may reach that folder's inner modules; everything else goes through `index.ts`. The CLI tests run whole commands against the fake backend with an injected proxy control (ensure, list, stop, remove, control, denials, trust), a fake bundled pi, a fake resolver and a fake terminal confirmation, and collect their output. Live tests against the real Colima engine (`~/.colima/pi-sandbox/docker.sock`) run only with `PI_SANDBOX_LIVE=1`. Live conformance runs pass `{ sharedRuntime: true }`, which skips the cases that plant networks, so a live run never touches networks the user has. `tests/support/expect-no-leak.ts` checks that no secret reaches a container spec, an exec argv, env or stdin, or a render file.
