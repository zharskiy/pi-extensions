# Future plans

One folder per research topic. Each folder holds its research and, where one exists, its spec. This README is the only overview.

## Folders

| Folder | Status | What it holds |
|---|---|---|
| [claude-code-compat/](claude-code-compat/README.md) | researched | Running skills and plugins written for Claude Code in pi. Finding: tool names cannot be redirected at runtime and aliases are not worth it; a prompt-level mapping table covers the rare references. Recommended: an import extension that discovers `~/.claude/skills`, `.claude/skills` and installed plugins, offers `/name` commands with Claude Code's argument substitutions, hands plugin agents to subagents through the publish channel, and (last) bridges `hooks.json` through new `tool_call`/`tool_result` host methods. research.md holds the two formats side by side, pi's surface with citations and a survey of 1,029 skill files. |
| [enterprise-workflow/](enterprise-workflow/README.md) | planned | Feature and epic workflows. company/ is primary: company-side.md, the example company package and the process research. harness/ lists the primitives the harness adds: `cwd`, the precedence sentence, the MCP filter. |
| [goap-subagents/](goap-subagents/research.md) | researched | Feasibility of GOAP-based subagent orchestration: preconditions, effects and cost on agents are not enough; reliable goal execution needs an observed-state model, effect validation and replanning. Recommends a bounded, opt-in action planner above the current runner, one narrow domain first. |
| [idle-handoff/](idle-handoff/spec-dropped.md) | dropped | Handing off while the cache is warm after a long idle. Spec and research kept in case the topic comes back. |
| [implementer-agent/](implementer-agent/README.md) | planned | A named `implementer` subagent for developing this repository with Claude Code: user-level agent file with `skills: [personal-code-style]` preloaded, body holding only the worktree, git, check and report contract, briefs reduced to the task. A reviewer counterpart follows the same mechanism. |
| [no-host-pi/](no-host-pi/README.md) | open | Removing the need for a pi installed on the host. Records what the host pi does for the launcher today (credentials for the proxy, MCP and provider sign-in, config commands, the provider host table, the image version, `--no-sandbox`, the commands that start no session), how the two instances are kept in step, and what extension settings survive in the sandbox: user-scope `pi-*.json` files stay in one folder's volume and model picks are erased at the next launch. Lays out a replacement for each job with its cost and its effect on the threat model, the store of record once no pi runs on the host, and migration. Recommends getting there in eight independently shippable steps, starting with keeping model picks across the settings sync and a helper container; lists the questions that are the owner's to decide. |
| [plan-mode-and-guards/](plan-mode-and-guards/q4-q8-plan-mode-guards.md) | dropped | Harness-enforced plan mode, guards and project rules. Kept because the owner may reconsider. |
| [sandbox/](sandbox/README.md) | superseded | Running the main session and every agent in a sandbox. Whole-session isolation became the launcher (`launcher/`); per-agent tool policy and one sandbox per agent are not planned. README.md lists what the launcher deferred: project `image.packages` with an approval prompt, mise toolchains, sidecar services, dev-server ports, idle VM stop, uv and environment-variable token derivation, corporate CA trust in the VM's engine and smaller items. research/ holds the pi surface, the OpenShell fact sheet and the landscape survey. |
| [sandbox-services/](sandbox-services/README.md) | planned | Sidecar services for the pi sandbox launcher, so test suites get Postgres, Redis and the like. A `services` config section names images the host launcher pulls and runs on a second internal network per repository, reachable from the sandbox by name and from nowhere else: no published port, no relay, no proxy, no host mapping. Services start with the sandbox, wait for a healthcheck or TCP probe before pi starts, go away with the last session and are cleaned up by `gc` and `reset`. User and policy layers define them; a project file only with `services.allowProject` from above and a digest-pinned image on an allowlist set above. Passwords are test values visible inside. spec.md holds config, layers, lifecycle, networking, CLI, alternatives and the implementation outline; the launcher README carries the interim recipe. |
| [skill-autosetup/](skill-autosetup/README.md) | researched | `/agents setup` proposes each lead's skills for the current project from the skill inventory as pi finds it on the machine, with no extra frontmatter and no catalogue conventions. When no agent has a skills override yet the proposal runs unasked; otherwise a Yes/No step with Yes preselected comes first. The main session classifies the project, picks at most five skills per lead (most useful first, project-level preferred) and answers through a model-only tool; the user confirms in the existing setup form; the result goes to `.pi/pi-subagents.json` through the existing write path. Chores never reach the model; skills that name interactive tools are filtered out. Release 1 is this flow alone; automatic re-runs are release 2, if ever. Claude Code files, company catalogues and the main session are out of scope. research.md holds this package's mechanics and pi's surface; implementation.md says what it takes to build. |
| [skills-in-main-session/](skills-in-main-session/README.md) | researched | Letting the main session use skills on demand without listing them all in its prompt. Deferred: a `skill` tool (modelled on OpenCode) that lists the inventory in its description and returns the body in pi's `<skill>` block, deferrable through `tool_search`. research.md holds the pi surface and the industry survey. |
| [workflow-mechanics/](workflow-mechanics/README.md) | planned (cwd), open (worktrees) | Where an agent runs and how its work gets back. cwd/spec.md: `cwd` on `run_agent`, an agent runs in a chosen directory under the session cwd, with trust checked per target; it replaces the dropped workspace and epic design, whose research is kept in cwd/research/. worktrees.md: a thinking document on agent worktrees, today's behaviour and its gaps, the use cases to choose between and the design questions, no decision made. The README lists the questions that span both. |

Dropped without a folder: the workflow engine (workflows are company skills), the code map (company business; its research sits in enterprise-workflow/company/code-exploration.md) and loading agent files from pi packages (excessive; agents are installed into the user agent dir or `.pi/agents` by script).

Done or in progress elsewhere, not tracked here: the `verifier` and `editor` chores with complexity-based delegation, and absolute token thresholds in session-limits.

## Delivery order

1. `cwd` on `run_agent` ([workflow-mechanics/cwd/spec.md](workflow-mechanics/cwd/spec.md)). Its worktree rule is subject to [workflow-mechanics/worktrees.md](workflow-mechanics/worktrees.md).
2. The precedence sentence in the main-session prompt: "When a skill or the user says who does a step, follow that over this guide." (harness-side.md 2.4)
3. Optional per-agent MCP filter, `mcp: [server, "server:pattern"]` (harness-side.md 2.3).
4. An examples folder in the repo with the company example as documentation, including its `install-agents.sh`.

Each step ships alone with docs and `npm run check` green.
