So pinata itself raises the limit to about one million. Install or session start was left to this plan; the choice made for the owner is in [Track C](#track-c-the-macs-open-file-limit), and the owner may overrule it. ### What the decision costs

Plain facts for the docs; the decision stands.

- Inside the container the launch repository's `node_modules` (beside a node lockfile, or a `package.json` below one), `.venv` (beside `uv.lock`, `poetry.lock` or `Pipfile.lock`), `target` (beside `Cargo.lock`) and `.gradle` (beside `settings.gradle` or `settings.gradle.kts`) become the Mac's own folders, as sibling repositories' already are (`workspace/overlay-markers.ts:1-18`, `workspace/overlay-scan.ts:55-60`). No config route remains to keep a repository folder off the share, since `mounts.volumes` targets may not lie inside the workspace root (O5).
- An install inside writes Linux files into the Mac's folder, and the Mac's install is visible inside. Native binaries are chosen per OS and CPU at install time, so a tree installed on one side breaks on the other, and a shared lockfile can lose the other platform's optional packages ([node-modules.md](research/node-modules.md#short-answer), item 4; esbuild, sharp and npm/cli#4828 under [What the industry does](research/node-modules.md#what-the-industry-does)). Inferred: a `.venv` points at the interpreter of the side that made it; both sides' Cargo and Gradle builds write the same `target` and `.gradle`.
- Every file such an install writes crosses Apple's share, which holds one Mac descriptor per file the VM has cached ([synced-workspace/README.md](../synced-workspace/README.md#the-problem)). In the lab, 20,000 files cost the Mac +20,201 descriptors in a shared folder and none in a VM mount (L1, [README.md](README.md#what-was-measured)); one `node_modules` held 1,910 folders (E11 in [node-modules.md](research/node-modules.md#experiments)). What stays against exhaustion is the file cache release, `vm.releaseFileCache` ([CONFIGURATION.md](../../launcher/CONFIGURATION.md#file-cache)).
- Gone with the overlays: the empty mount-point folders on the Mac, the `EBUSY` of `rm -rf` on a mounted `node_modules` (L1, E9), a tracked `node_modules` hidden and shown as deleted ([README.md](README.md#decision)), and the notice for a folder outside git.

## Not in this plan

- Steps 2 and 3 of the `node_modules` design (on-demand mounts, the `mkdir` trap): not to be built. Step 1, the whole-root overlay, is no longer planned either.
- A replacement for the overlays: a user-listed overlay form, package-manager redirection (`CARGO_TARGET_DIR`, `UV_PROJECT_ENVIRONMENT`, [node-modules.md](research/node-modules.md#d-package-manager-redirection)), a warning about a shared `node_modules`.
- A shim or a migration for `mounts.autoOverlays`: excluded by the decision.
- The index guard and the sandbox-private git dir ([git.md](research/git.md#conclusion)).
- The `place_link` race in `launcher/image/entrypoint.sh` (`:52`): it exists on `main` and needs its own branch.
- Lowering `kern.maxfilesperproc`, a guest-side governor, or removing the file cache release (`vm.releaseFileCache`): proposed by the earlier research ([proposal.md](../synced-workspace/attempt-2-live-share/proposal.md#the-solution)), not part of track C.
- The vnode exposure of Macs whose default per-process limit is already large (C9).
