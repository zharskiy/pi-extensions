# How frontier labs and agentic coding tools structure development work

Date: 2026-10-17. Scope: process types and spec-driven development, plan mode, multi-agent orchestration, model tiering, per-project customisation and quality gates, as implemented by Anthropic (Claude Code, Agent SDK), OpenAI (Codex, Agents SDK), Google (Gemini CLI, ADK, Jules), GitHub (Copilot, spec-kit), AWS (Kiro), Cursor, Amp, Factory Droid, Devin, and the community methods BMAD, OpenSpec and Superpowers. Sources are official docs or changelogs unless marked "third-party"; "unverified" marks claims I could not reach an official page for. Each section ends with what converges across tools and what pi's subagents extension can reuse.

## 1. Process types and spec-driven development

- **Kiro specs** ([docs, updated 2026-10-15](https://kiro.dev/docs/specs/)): three files per feature, `requirements.md` (EARS: `WHEN [condition] THE SYSTEM SHALL [behaviour]`), `design.md`, `tasks.md`. Feature Specs offer Requirements-First or Design-First; **Bugfix Specs** replace requirements with root cause, fix design and regression tests and generate property-based tests for "the preservation of existing behavior"; **Quick Spec** generates all three without approval gates ("the difference is whether you review each one before the next is generated"). "Run all Tasks" builds a dependency graph and runs independent tasks in concurrent waves; "Sync Files" re-derives tasks after edits.
- **GitHub spec-kit** ([repo](https://github.com/github/spec-kit)): `/speckit-constitution → specify → plan → tasks → implement → converge`, optional `clarify`, `checklist`, `analyze`; bug investigations under `.specify/bugs/<slug>/` end with a verdict `verified | partial | failed`; `.specify/assessments/` return `go | needs-clarification | kill`. Third-party: tasks get stable IDs (T001) and parallel markers.
- **OpenSpec** ([repo](https://github.com/Fission-AI/OpenSpec)): `openspec/specs/` is the truth; a change lives in `openspec/changes/<name>/` with `proposal.md`, delta specs (`ADDED/MODIFIED/REMOVED` with `WHEN/THEN` scenarios), `design.md`, `tasks.md`, archived on merge. Pitched as "fluid not rigid" and brownfield-first; recommends high-reasoning models for the proposal and a clean context before implementation.
- **BMAD** ([repo](https://github.com/bmad-code-org/BMAD-METHOD), [docs](https://docs.bmad-method.org/)): v6.12 stable, v7 alpha. Entry by work size: vague idea → planning path; big clear idea → `bmad-spec`; "Small changes go straight to build" (`bmad-build`, which "writes the code and reviews it"). "Every path runs the same loop. Bigger work enters it earlier." Third-party ([release notes](https://github.com/bmad-code-org/BMAD-METHOD/releases)): v6.11 collapsed the create-story/dev-story pair into `bmad-sprint-planning → bmad-build → bmad-code-review`.
- **Superpowers** ([repo](https://github.com/obra/superpowers)): brainstorming → git worktree → writing-plans (tasks of 2–5 minutes with file paths, code and a verification step) → subagent-driven development (fresh subagent per task, two-stage review: spec compliance, then code quality) or executing-plans (inline, one review at the end) → TDD → requesting-code-review (critical issues block) → finishing-a-development-branch. Ships for 16 harnesses including pi.
- **Anthropic best practices** ([docs](https://code.claude.com/docs/en/best-practices)): Explore → Plan → Implement → Commit; "If you could describe the diff in one sentence, skip the plan"; "Let Claude interview you" to produce `SPEC.md`, then start a fresh session; Writer/Reviewer across sessions; `/batch` splits one change across 5–30 worktree-isolated subagents and ends with an adversarial `/code-review` pass.
- **Codex** ([CLI docs](https://learn.chatgpt.com/docs/codex/cli)): `/plan`, `/review` ("reports prioritized findings without modifying your working tree", targets uncommitted, commit or base branch), `/init` for AGENTS.md, delegation to subagents. The dedicated plan-mode page 404s; third-party guides describe `/plan` as prompt-level rather than runtime-enforced (unverified).
- **Cursor** ([planning](https://cursor.com/docs/agent/planning)): Plan Mode (Shift+Tab) is auto-suggested for complex tasks, asks clarifying questions, writes a markdown plan (saveable to the workspace) and builds on approval.
- **Factory Droid** ([Spec Mode](https://docs.factory.com/cli/user-guides/specification-mode)): "research and planning before implementation"; Droid may not edit, commit or start services; it "calls `ExitSpecMode` to ask for approval"; approved plans save to `.factory/docs/YYYY-MM-DD-slug.md`; approval chooses the autonomy level for execution.
- **Devin** ([playbooks](https://docs.devin.ai/product-guides/creating-playbooks), [guidelines](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)): playbooks are "like a custom system prompt for a repeated task" with Procedure, Specifications ("what should be true after Devin is done?"), Advice, Forbidden Actions, What's Needed From User; guidance: "Split tasks into verifiable sub-tasks, and start one Devin session for each sub-task." Interactive Planning (plan after scanning the codebase, default 30 s wait, "Wait for my approval" option) is only confirmed on translated doc pages (partly unverified).
- **Jules** ([docs](https://jules.google/docs)): generates a plan the user approves before any code changes, runs in a cloned VM, reads AGENTS.md.

**Convergence.** Everyone separates intent from execution with a written artefact (spec, plan or story), scales ceremony to risk (Kiro Quick Spec, BMAD "straight to build", Anthropic "skip the plan" rule), and makes the artefact a file on disk that a fresh context can execute. Bug fixes get their own lighter shape (Kiro Bugfix, spec-kit bugs) ending in a verdict. Tasks are small, ordered by dependency, and carry their own verification step.

**Reusable here.** Make the planner's output a persisted plan file with dependency-ordered batches (already the batch model) and add two more shapes: a bugfix plan (root cause, fix, regression test, verdict) and a "skip the plan" rule in the main-session prompt for one-sentence diffs. Keep spec files in the project's own directory (`.pi/` or the company's config), never in the tool.

## 2. Plan mode

- **Claude Code** ([permission modes](https://code.claude.com/docs/en/permission-modes)): plan mode reads and runs exploratory commands "but does not edit your source"; enter with Shift+Tab, `/plan`, or `claude --permission-mode plan`; `defaultMode: plan` per project. Approval offers "Yes, and use auto mode", "Yes, manually approve edits", "No, keep planning"; Ctrl+G edits the plan in an editor; `showClearContextOnPlanAccept` approves and clears the planning context. The plan file is re-injected after compaction ([large codebases](https://code.claude.com/docs/en/large-codebases)). A built-in read-only `Plan` subagent researches in plan mode ([sub-agents](https://code.claude.com/docs/en/sub-agents)). `opusplan` "uses `opus` during plan mode, then switches to `sonnet` for execution" ([model config](https://code.claude.com/docs/en/model-config)).
- **Gemini CLI** ([plan mode, updated 2026-06-18](https://geminicli.com/docs/cli/plan-mode/); Gemini CLI was replaced by Antigravity CLI that day): read-only, on by default, entered via Shift+Tab, `/plan [goal]`, an `enter_plan_mode` tool or `--approval-mode=plan`; writes only `.md` files to `~/.gemini/tmp/<project>/<session>/plans/`; discuss first, then formal approval; `general.plan.modelRouting` uses Pro for planning and Flash for implementation; non-interactive runs fall through to YOLO.
- **Copilot in VS Code** ([planning](https://code.visualstudio.com/docs/agents/run/planning.md)): `/plan` switches a session to Plan mode; "The agent researches your project, asks clarifying questions, and creates a plan for you to review"; review card actions Implement Plan, Approve Plan Only, Implement with Autopilot, Reject; local Plan agent stores the plan in `/memories/session/plan.md`; `chat.planAgent.defaultModel` and an experimental `implementAgent.model` let you plan on a reasoning model and implement on a cheaper one, with the caveat that "retries and rework can offset the savings". Asking for a plan in a normal chat "guides the agent's behavior but does not change the session's permissions".
- **Cursor**: see §1; **Kiro**: the spec is the plan; **Factory**: Spec Mode has its own `specModeModel`/`specModeReasoningEffort` and makes subagents read-only while active ([custom droids](https://docs.factory.com/cli/configuration/custom-droids)); **Codex**: `/plan` (official page unavailable).

**Convergence.** Plan mode is a permission state, not just a prompt: edits are blocked by the harness, exploration commands are allowed, the plan is a markdown file outside the repo (or saved on request), approval is a discrete event that chooses the execution autonomy level, and the planning model may differ from the execution model. Several tools re-inject or keep the plan across compaction or fresh sessions.

**Reusable here.** Treat the planner lead as pi's plan mode: read-only tool loadout enforced by `prepareLoadout`, plan written to a file under the session dir, and a single approval step in the main session that chooses how the implementer batches run. Record the plan path in the handoff document so it survives context limits.

## 3. Multi-agent orchestration

- **Anthropic essays**: "Building effective agents" (2024-12-19, [link](https://www.anthropic.com/engineering/building-effective-agents)) names prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimizer, and advises starting simple. "How we built our multi-agent research system" (2025-06-13, [link](https://www.anthropic.com/engineering/multi-agent-research-system)): orchestrator-worker; lead saves its plan to memory; each brief needs objective, output format, tool guidance and boundaries; 3–5 subagents in parallel; ~15× the tokens of chat; Opus 4 lead + Sonnet 4 workers beat a single Opus 4 by 90.2%; "most coding tasks have fewer parallelizable subtasks"; store outputs externally and pass references; resume from the error point.
- **Claude Code** ([run agents in parallel](https://code.claude.com/docs/en/agents)) has five surfaces and chooses by "who holds the plan": subagents (Claude, turn by turn; results in context), agent teams (lead; shared task list), workflows (a script; results in script variables), agent view (you), projects (cloud threads). Subagents ([docs](https://code.claude.com/docs/en/sub-agents)): fresh context, return a summary only, background by default, 20 concurrent (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`), 3 layers deep, per-agent `isolation: worktree`, resumable by id, final messages scanned for instruction-shaped text. Agent teams ([docs](https://code.claude.com/docs/en/agent-teams), experimental, shipped with Opus 4.6 on 2026-02-05 per [TechCrunch](https://techcrunch.com/2026/02/05/anthropic-releases-opus-4-6-with-new-agent-teams), third-party): peers with own contexts, direct messaging through JSON mailboxes under `~/.claude/teams/`, a shared task list with dependencies and file-claiming, hooks `TeammateIdle`/`TaskCompleted` that block with exit 2; "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; best practice 3–5 teammates, 5–6 tasks each; no nested teams. Dynamic workflows ([docs](https://code.claude.com/docs/en/workflows)): Claude writes a JavaScript script with `agent()`, `pipeline()`, `parallel()`, `phase()`, optional JSON `schema` per agent; 16 concurrent agents, 1,000 per run; resumable with cached results; "adversarially review each other's findings"; size guideline small/medium/large; `ultracode` lets Claude decide per task. Agent SDK ([subagents](https://code.claude.com/docs/en/agent-sdk/subagents)): `maxBudgetUsd` ends a query and stops background subagents; "Claude Opus 5 delegates to subagents more readily than earlier models", so the system prompt tells it not to call the Agent tool unless asked.
- **OpenAI Agents SDK** ([handoffs](https://openai.github.io/openai-agents-python/handoffs/), [multi-agent](https://openai.github.io/openai-agents-python/multi_agent/)): "Handoffs are represented as tools to the LLM" (`transfer_to_refund_agent`) and make the specialist the active agent; `Agent.as_tool()` keeps a manager in control; code-driven orchestration is "more deterministic and predictable". **Codex subagents** ([docs](https://learn.chatgpt.com/docs/agent-configuration/subagents.md)): built-ins `default`, `worker`, `explorer`; custom agents as TOML in `.codex/agents/` with `developer_instructions`, `model`, `model_reasoning_effort`; "Return summaries from subagents instead of raw intermediate output"; "use parallel agents for read-heavy tasks such as exploration, tests, triage, and summarization" and be "more careful with parallel write-heavy workflows"; `agents.max_concurrent_threads_per_session`.
- **Google ADK** ([patterns](https://adk.dev/workflows/patterns/)): `sub_agents` hierarchy with LLM-driven `transfer_to_agent`, `AgentTool` for explicit calls, `SequentialAgent`/`ParallelAgent`/`LoopAgent` (ends on `max_iterations` or `escalate=True`), results passed through session state via `output_key`; named patterns coordinator/dispatcher, pipeline, fan-out/gather, hierarchical decomposition, generate-and-review, iterative refinement, human-in-the-loop (no built-in human agent).
- **Cursor** ([subagents](https://cursor.com/docs/agent/subagents), [worktrees](https://cursor.com/docs/configuration/worktrees)): built-in Explore (faster model) and Browser; `.cursor/agents/` plus `.claude/agents/` and `.codex/agents/` are read; parallel Task calls; worktree or cloud isolation with parent-side merge; nesting one level since 2.5; `/best-of-n sonnet,gpt,composer <task>` "compares runs only", you then `/apply-worktree`. **Amp** ([models and subagents](https://ampcode.com/docs/models-and-subagents)): Search, Oracle, Librarian, Task, Read Thread subagents; "They work in isolation, so they can't communicate with each other, you can't guide them mid-task"; the main agent "only receives their final summary". **Factory** ([custom droids](https://docs.factory.com/cli/configuration/custom-droids)): `worker`/`explorer` built-ins, `run_in_background` with `TaskOutput`, `resume` by task id.

**Convergence.** Orchestrator-worker with summary-only returns is the default everywhere; peer teams (Claude agent teams, ADK collaboration) are reserved for independent, file-partitioned work and are flagged as costlier. Results flow back as a short message, with large outputs stored in files or script variables and referenced by path. Parallelism is for read-heavy work; write-heavy work gets worktrees or strict file ownership. Chunk sizes converge on small, verifiable units (Superpowers 2–5 minutes, 5–6 tasks per teammate, one Devin session per sub-task, Kiro waves). Depth, concurrency and spend caps are first-class settings.

**Reusable here.** pi already matches the core (result.md files, hidden wake message, maxDepth 3, maxChildrenPerAgent 6, worktree agents). Gaps worth closing: a spend cap per run, "never two editing agents on the same files" enforced by the manager rather than the prompt, structured results (a schema or at least a required `Files touched` section) so the main session can route without reading, and a scripted batch runner for repeatable pipelines (the workflows idea) that the planner can emit instead of prose batches.

## 4. Model tiering and routing

- **Claude Code** ([model config](https://code.claude.com/docs/en/model-config)): aliases `haiku` ("fast and efficient... for simple tasks"), `sonnet` ("daily coding"), `opus` ("complex reasoning"), `fable` ("hardest and longest-running tasks"), `opusplan`; effort `low`…`max` per session, per skill or per subagent; subagent model order per-invocation → frontmatter → `CLAUDE_CODE_SUBAGENT_MODEL` → main; `/goal` and background summarisation run on the "small fast model" ([goal](https://code.claude.com/docs/en/goal)); auto mode routes every tool call through "a second model, the classifier", default starting mode since v2.1.283 ([permission modes](https://code.claude.com/docs/en/permission-modes)). Blog (2026-07-07, [link](https://claude.com/blog/claude-model-and-effort-level-in-claude-code)): "Choose smaller models for more routine tasks and larger models for more complex or ambiguous tasks"; precisely described edits suit the smaller model; the high-effort path "generates roughly 7x more tokens"; larger models can cost less per task on long multi-step work.
- **Gemini CLI**: Pro plans, Flash implements (§2). **Copilot**: separate plan and implement models with the rework caveat (§2). **Factory**: `specModeModel` plus per-droid `model` and `reasoningEffort`. **Codex**: per-agent `model` and `model_reasoning_effort` in TOML. **Amp**: modes `low/medium/high/ultra` each bundle "a model, reasoning effort, system prompt, tools, and oracle"; every subagent role has its own model and routing stays automatic unless you pin a role. **Cursor**: Explore on a faster model; `/best-of-n` across models. **Anthropic research**: Opus lead, Sonnet workers (§3). **OpenSpec**: high-reasoning model for proposals.

**Convergence.** Strong model for planning, review and ambiguity; cheaper model for well-specified execution, search and summarisation; a third, small tier for classifiers and evaluators (permission classifier, goal evaluator). Effort is a per-task dial, not only a per-model one. Automatic routing exists only in narrow forms (plan vs implement, classifier). Everyone warns that cheap execution of an under-specified task costs more in rework.

**Reusable here.** pi's roster (planner and reviewer on a high-thinking strong model, implementer medium, chores low) is the mainstream shape. Add an explicit evaluator tier: a `verify`-style chore on the cheapest model that judges a result against its `Done when` line, and let the brief set thinking effort per task rather than per agent.

## 5. Per-project customisation

- **AGENTS.md** ([agents.md](https://agents.md/)): 60k+ projects, 20+ tools, stewarded by the Agentic AI Foundation under the Linux Foundation; nearest file wins in monorepos; prompts override files. **Codex** ([docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md.md)): global `~/.codex/AGENTS.md`, then root → cwd with `AGENTS.override.md` taking precedence per directory, one file per directory, concatenated with the closest last, `project_doc_max_bytes` 32 KiB; a `## Code Review Rules` section is read by `/review`.
- **Claude Code** ([memory](https://code.claude.com/docs/en/memory)): managed policy file (MDM/Ansible, "cannot be excluded by individual settings"), `~/.claude/CLAUDE.md`, project `CLAUDE.md`, gitignored `CLAUDE.local.md`; `@path` imports (4 hops); subdirectory files load when a file there is touched; `.claude/rules/*.md` with `paths:` globs; `claudeMdExcludes` for other teams' files; `managed-only` mode; AGENTS.md read natively since v2.1.277. Best practices: "Bloated CLAUDE.md files cause Claude to ignore your actual instructions"; convert hard rules to hooks because hooks are "deterministic" and CLAUDE.md is "advisory". The auto-mode classifier reads `autoMode` only from user or managed scope because "a checked-in repo or a build step could otherwise inject its own allow rules" ([auto mode config](https://code.claude.com/docs/en/auto-mode-config)).
- **Agent Skills** ([spec](https://agentskills.io/specification)): `SKILL.md` with name/description/allowed-tools, progressive disclosure (~100 tokens of metadata, body under 5,000 tokens, resources on demand), under 500 lines. **Cursor** ([rules](https://cursor.com/docs/context/rules), [skills](https://cursor.com/docs/context/skills)): `.cursor/rules/*.mdc` as Always, Auto-attached (glob), Agent-requested or Manual; nested AGENTS.md; Team rules from the dashboard outrank project rules; keep under 500 lines; skills read from `.agents/skills`, `.cursor/skills`, `.claude/skills`, `.codex/skills`; `/migrate-to-skills`.
- **Copilot** ([repository instructions](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)): `.github/copilot-instructions.md`, `.github/instructions/*.instructions.md` with `applyTo` globs and `excludeAgent`, nested AGENTS.md ("the nearest `AGENTS.md` file in the directory tree will take precedence"), organisation instructions ranked last but always included; custom agents in `.github/agents/*.agent.md` with `tools`, `model`, `handoffs`, `agents` ([VS Code](https://code.visualstudio.com/docs/copilot/customization/custom-agents)).
- **Kiro steering** ([docs](https://kiro.dev/docs/steering/)): `.kiro/steering/` with `product.md`, `tech.md`, `structure.md`; inclusion `always`, `fileMatch`, `manual`, `auto`; global `~/.kiro/steering/` pushed "via MDM solutions or Group Policies". **Devin**: org-level playbooks; Knowledge (triggered, repo-pinned notes) is deprecated in favour of Skills ([knowledge](https://docs.devin.ai/onboard-devin/knowledge-onboarding.md)).
- **"Do not run the full build" style rules** are handled as hooks or permission rules, not prose: Claude `permissions.deny`/`ask` and `PreToolUse` (exit 2 blocks, `updatedInput` rewrites) ([hooks](https://code.claude.com/docs/en/hooks)); Cursor `beforeShellExecution` with deny/ask and `failClosed` ([hooks](https://cursor.com/docs/agent/hooks)); Codex `PreToolUse` with `permissionDecision: "deny"` and repo hooks that load only once trusted ([hooks](https://learn.chatgpt.com/docs/hooks.md)).

**Convergence.** Four layers everywhere: organisation (managed file, dashboard, MDM), user, project (AGENTS.md, nearest wins), and path-scoped rules or skills loaded on demand. Instructions are short and advisory; prohibitions are hooks. Private or company-wide conventions live outside the repo (managed settings, user dir, internal plugin marketplace, gitignored local files), and tools refuse to read security-relevant config from the checked-in project.

**Reusable here.** pi already reads `.agents/skills` and AGENTS.md. Add path-scoped loading (skills or rules with `paths:` globs) so a polyrepo with several stacks loads only the matching conventions, a user-level and an organisation-level layer for `pi-subagents.json` and agent files, and a hook-based deny list (via the `tool_call` hook) that company config can populate with commands such as full builds or deploy scripts. Keep every company-specific name in that config, never in shipped prompts.

## 6. Quality gates

- **Claude Code**: "Give Claude a way to verify its work" (tests, build exit code, linter, screenshot); gate options are a condition in the prompt, `/goal` (a session-scoped prompt Stop hook on the small fast model that returns not-yet/met/impossible after every turn and only judges what the transcript shows), a deterministic Stop hook, or "a verification subagent or dynamic workflow ... so the agent doing the work isn't the one grading it" ([best practices](https://code.claude.com/docs/en/best-practices), [goal](https://code.claude.com/docs/en/goal)). Hook events include `PostToolUse` on `Edit|Write` for lint, `Stop`, `SubagentStop`, `TaskCompleted` and `TeammateIdle` (exit 2 feeds the failure back) ([hooks](https://code.claude.com/docs/en/hooks), [agent teams](https://code.claude.com/docs/en/agent-teams)). Reviewer caveat: ask for correctness gaps only, or it invents findings. Workflows and `/batch` end with adversarial review.
- **Codex**: `/review` finds prioritised issues without editing; `Stop` hook "A block doesn't reject the turn. Instead, Codex continues and uses the hook's `reason` as a new prompt"; `PostToolUse` replaces the tool result with hook feedback ([hooks](https://learn.chatgpt.com/docs/hooks.md)). **Cursor**: `afterFileEdit` formatter, `stop`/`subagentStop` can return a `followup_message` with `loop_limit` 5, `failClosed` ([hooks](https://cursor.com/docs/agent/hooks)). **Kiro**: `PostFileSave` lint-on-save, `Stop` hooks with command or agent actions ([hooks](https://kiro.dev/docs/hooks/)); bugfix specs generate property-based regression tests.
- **Superpowers**: verification-before-completion, TDD, two-stage review after every task where critical issues block the merge. **spec-kit**: bug fixes end in `verified | partial | failed`. **BMAD**: `bmad-build` "writes the code and reviews it", then `bmad-code-review`. **Amp**: the Task subagent "carries out delegated coding and verification work end to end". **Devin**: "Run npm test after each iteration" in the prompt; Devin Review runs on every PR, posts a commit status check, and can auto-fix its own findings ([review](https://docs.devin.ai/work-with-devin/devin-review.md)). **Copilot**: "Approving a plan and approving tool actions are separate decisions."

**Convergence.** Tests are run by the agent that made the change, but completion is judged by something else: a hook, a cheap evaluator model, a separate review agent, or CI. Gates are layered: deterministic (lint on edit, deny rules), model-judged (goal evaluator, reviewer), and human (plan approval, PR). The Stop/complete hook that blocks and feeds a reason back is the universal loop primitive. Review output is kept narrow (correctness, blocking issues) to avoid noise.

**Reusable here.** Make the `Verification` section of the result contract mandatory evidence (command and exit code), add a manager-side completion gate that re-runs a project-configured check or a cheap evaluator before a result is marked `done`, run the reviewer automatically after each implementer batch (already in the guide; make it a setting), and let company config register a `tool_result`/stop hook that runs its own checks for the QA-automation repo.

## Top 10 practices to adopt

1. Persist the plan as a file with dependency-ordered, individually verifiable tasks; re-inject or reference it after compaction and in handoffs.
2. Scale ceremony to risk: one-sentence diffs skip planning; bug fixes use a lighter root-cause/fix/regression shape with a verdict.
3. Enforce read-only planning in the harness (loadout), not the prompt; approval is one explicit event that sets execution autonomy.
4. Orchestrator-worker with summary-only returns; large outputs in files referenced by path; structured result sections the manager can route on.
5. Parallelise read-heavy work freely; give write-heavy work worktrees or exclusive file ownership enforced by the manager.
6. Cap depth, concurrency and spend per run; warn on large fan-outs.
7. Three model tiers: strong for planning/review/ambiguity, mid for specified execution, small for classifiers and evaluators; effort set per task.
8. Four instruction layers (org, user, project nearest-wins, path-scoped on demand); short advisory text, prohibitions as hooks; never read security config from the checked-in repo.
9. The worker runs the tests; a different party (hook, evaluator, reviewer) decides done, with evidence in the result.
10. Package repeatable pipelines (review every branch, migrate N files) as scripts or saved workflows the planner can emit instead of prose.

## Dead ends to avoid

- Peer agent teams for dependent or same-file work; every vendor says subagents or a single session win there, and teams cost more tokens.
- Cheap models on vague tasks; the rework erases the savings (Copilot, Anthropic blog).
- Long instruction files; they get ignored (Claude Code `/doctor`, Cursor and Skills 500-line limits, Codex 32 KiB cap).
- Prose prohibitions ("never run the full build") instead of hooks or deny rules.
- Letting the implementing agent grade its own completion, or asking a reviewer for "feedback" instead of blocking issues.
- Unbounded delegation: newer strong models over-delegate (Opus 5 note), so limits must be enforced by the manager.
- Reading agent output verbatim into the orchestrator; return summaries and paths.
- Heavy spec frameworks applied to every change (the BMAD and Kiro quick paths exist because full ceremony on small work stalls teams).
