## Q2. Confinement (decisive)

### What a handle is and how it becomes a vnode
- Handle layout, `struct nfs_exphandle` in `nfs.h`: `nxh_version`, `nxh_fsid` (export file system id), `nxh_expid` (export id), `nxh_flags`, `nxh_reserved`, `nxh_fidlen`, then the file system's own file id (`VFS_VPTOFH` output). No MAC, no random secret, no path, nothing bound to the client. [S `nfsrv_vptofh`, nfs_subs.c]
- `nfsrv_fhtovp` (nfs_subs.c) per request: checks the version and length, finds the export by `(fsid, expid)` (`nfsrv_fhtoexport`), looks up the client's address in that export's address table (`nfsrv_export_lookup`, radix match on `nd_nam`; no match and no default export -> `EACCES`), checks the security flavour, finds the mount by the export's path and calls `VFS_FHTOVP(mp, fidlen, fid)` on **the whole mounted file system**. Nothing afterwards checks that the vnode lies under the exported directory: no subtree check exists in the server (`grep issubdir` hits only `nfsrv_rename`). [S]
- The only containment is in handle *issuing*: `nfsrv_vptofh` gets the directory handle when the name is `..` and returns an invalid handle (`NXHF_INVALIDFH`) if that directory is the export root. Called so from `nfsrv_lookup` (nfs_serv.c, `isdotdot`) and `nfsrv_readdirplus`. A client that walks honestly cannot leave; a client that writes its own handle bytes is not stopped. [S]
- So: the client address list **is** enforced per request (`nfsrv_fhtovp` -> `nfsrv_export_lookup`), and the handle must name a real export, but the export path is only the starting point, not a boundary. The boundary is the APFS volume that holds the export. [S]
- Forging needs the APFS fid bytes of a target. APFS's fid format is closed source [G]. If it is the object id (inode number) alone, or the object id plus a guessable field, one forged handle for the volume root (inode 2: `stat -f %i /Volumes/<volume>` -> 2 [V]) opens the whole volume, and ordinary LOOKUPs from there do the rest (the `..` check only compares against the export root). A guest learns its own files' fileids from GETATTR and their handles (Linux `name_to_handle_at` on an NFS mount returns the server handle), so the layout is easy to learn [G]; the lab's `forge-probe.py` settles it. Linux NFS maintainers say the same of subtree-less servers in general: "once a single filehandle outside the export directory is found, it's easy to access the rest of the filesystem"; export a separate filesystem instead (lore.kernel.org/all/20210118225557.GB23934@fieldses.org/T/). [S URL]
- Other volumes are out of reach: the handle must match an export's `(fsid, expid)` and `VFS_FHTOVP` runs on that export's mount only. [S]

### As whom a forged handle acts
- `nfsrv_credcheck` (nfs_subs.c): with `NX_MAPALL` every request's credential is replaced by the export's; with `NX_MAPROOT` only uid 0's. Otherwise the AUTH_SYS uid/gids the client sends are used as is. [S]
- So without `-mapall` a guest with root can send any uid and act as **any Mac user except root** (root maps to -2 by default, `exports(5)`). `-mapall=<mac user>` is mandatory: every request, forged or not, then acts as that one user. [S]
- On top of the uid, the server runs in the `nfsd` process, whose Sandbox/TCC rights decide what it may read: `mountd.c` runs `sandbox_check(nfsd_pid, "file-read-data", path)` at export load; `nfsd(8)` says to grant Full Disk Access when it fails. With FDA granted, `nfsd` passes TCC everywhere, so a forged handle reaches anything the mapall user can on that volume. [S] Per-request TCC checks inside the kernel were not traced [G].
- This Mac: `/Volumes/<volume>` is its own APFS volume (disk7s2, external, case-insensitive "APFS", mounted `noowners`) [V `mount`, `diskutil info`]. `noowners` means ownership is ignored on that volume, so permissions are evaluated as if every caller owned every file [G from the flag's meaning]: even `-mapall=nobody` would not narrow access there.

### Conclusion
- **Yes, a guest with root can read and write files outside the exported directory on the same volume**, by forging handles; nothing in `nfsrv_fhtovp` stops it. Exporting a subfolder of the Data volume (the home) would expose the whole home, `~/.ssh` included. That weakens criterion 7. [S]
- What closes it: export only the **root of a volume that holds nothing but the share**. Here `/Volumes/<volume>` is a dedicated volume, so if `workspaceRoot` is that volume's root the forged-handle reach equals the share. If `workspaceRoot` is a subfolder, the rest of that volume is exposed; a dedicated APFS volume per workspace (same container, no size cost) or a user-mounted disk image fixes it. pinata's other VM shares (`<agent dir>/sessions` and the render dir, on the Data volume) must stay on virtiofs; they are small. [S + G]
- Mapall to the Mac user, never `-maproot` alone. Read-write as that user is exactly what the virtiofs share gives today.

### Network path and who else can mount
- Lima 2.3.0 vz default network: user-mode (gvisor-tap-vsock in the host agent); the Mac is `host.lima.internal` = 192.168.5.2, which reaches the Mac's loopback services; `networkOpts.hostLoopback` (vz only, default true since 2.3) turns that off and the template advises false for untrusted guests. [S `/opt/homebrew/share/lima/templates/default.yaml` L536-541, L696-708, `limactl --version` 2.3.0 V]
- On that path the connection reaching `nfsd` is made by the host agent: source 127.0.0.1, an unprivileged source port [G from the proxy design; lab checks with `nfsd verbose` / `netstat`]. The export must then list 127.0.0.1, and `nfs.server.mount.require_resv_port = 0` (or `nfsd -N`) is needed because MOUNT requires a reserved port by default (`nfs.conf(5)`; `nfsd/main.c` default `mount_require_resv_port = 1`). NFS requests themselves do not (`nfs.server.require_resv_port` default 0; sysctl shows 0 [V]). [S]
- Consequence: an export to 127.0.0.1 is open to **every local process of every local user**, and to **every VM of this Mac on lima/colima user-mode networking** (all arrive as 127.0.0.1), each able to send any AUTH_SYS uid (irrelevant under mapall: they act as the Mac user) and to forge handles. The reserved-port rule would not help: a non-root process here can bind source port 1001 on 0.0.0.0 [V: python bind succeeded as uid 502; 127.0.0.1:1001 was refused]. For a local process of the same Mac user this is no new right; for other local users, sandboxed apps that may only talk to the network, and other VMs (colima's `default` profile) it is.
- vzNAT (`networks: [{vzNAT: true}]`): the guest gets a 192.168.64.x address from vmnet and talks to the Mac's bridge address directly, guest source port kept [G]. Export to that single address (host form, not `-network`). Another vz guest on the same vmnet bridge could take that address [G]; lima's template says the vzNAT address "is accessible from the host, but not from other guests" [S template L538].
- Other machines: `nfsd` listens on all interfaces (no bind option in `nfs.conf(5)` [S]); a LAN client is refused per request by the address table [S], but it can probe and the service advertises itself by Bonjour unless `nfs.server.bonjour = 0` [S nfs.conf(5)]. The application firewall may also be set to block incoming for `nfsd` [G].
- The only real authentication the server offers is `-sec=krb5*` (needs a Kerberos realm on the Mac and the guest): exotic, rejects criterion 8. [S exports(5)]
- pf could limit 2049 and the mount port by address, and on the user-mode path perhaps by the socket's owner (`user` match) to keep other local users out [G]; it cannot tell one VM's host agent from another's.

## Q1. Resources
- Per request: `nfsrv_fhtovp` -> `VFS_FHTOVP` returns a vnode with an iocount; each handler drops it with `vnode_put` before replying (118 `vnode_put` sites in nfs_serv.c). No `falloc`, no file table entry, no `vnode_ref` (use count) between requests. `kern.num_files` does not move for served files. [S] Only `fhopen(2)` (nfs_syscalls.c, a root-only syscall used by `rpc.lockd`) allocates a descriptor. [S]
- Held between requests: `nfsrv_modified` (nfs_serv.c) keeps a `vnode_get` iocount on each file written in the last `nfsrv_fmod_pendtime` = 1000 ms, to coalesce the FSE_CONTENT_MODIFIED fsevent, then drops it in `nfsrv_fmod_timer`. Bounded by files written per second; a 100k-file build writing 10k files/s pins about 10k iocounts for about a second, no descriptors. [S + G for the rate]
- Vnodes the server looked up stay in the vnode cache unreferenced, as after a local `ls -R`, and are recycled under `kern.maxvnodes`. [S/G: standard VFS behaviour]
- Duplicate request cache: `nfs_srvcache.c`, `nfsrv_reqcache_size` = 64 entries (sysctl `vfs.generic.nfs.server.reqcache_size` 64 [V]). Bounded, global. [S]
- Per-user statistics: up to `NFSRV_USER_STAT_DEF_MAX_NODES` = 1024 nodes, idled out. [S nfs.h, nfs_subs.c]
- Sockets: one per client TCP connection (`nfsd_tcp_connections`), idle timeout 3600 s [V sysctl]. Not per file. [S]
- NLM locks: `rpc.lockd` (`lockd_lock.c`) `fhopen`s the file for each held lock and keeps the descriptor while the lock is held: per held lock, not per cached file. With `nolock` / `local_lock=all` on the client, none. [S]
- Verdict on criterion 1: met by construction; the lab confirms with `sysctl kern.num_files` and `lsof -p $(pgrep nfsd)` during walks.

## Q3. Setup on macOS 27.2
- Root, once: write `/etc/exports` (the launchd job `com.apple.nfsd` has `KeepAlive.PathState./etc/exports = true`, so the file's presence starts `nfsd`, also at every boot) [V `plutil -p /System/Library/LaunchDaemons/com.apple.nfsd.plist`]; `nfsd status` here: "enabled", "not running", no `/etc/exports` [V]. Edit `/etc/nfs.conf` (here only a 3-line comment header [V]) for `nfs.server.mount.require_resv_port = 0`, `nfs.server.bonjour = 0`, a fixed `nfs.server.mount.port`, optionally `nfs.server.async`. `nfsd update`/`restart` after changes. Nothing to do at boot. [S nfsd(8), nfs.conf(5)]
- `nfs.conf(5)`: a removed line's value stays until reboot (kernel sysctls such as `vfs.generic.nfs.server.async`), so undo must reset sysctls by hand. [S]
- Full Disk Access for `/sbin/nfsd`: needed when `sandbox_check` fails (`nfsd(8)` NOTES, `mountd.c`); a GUI step, not scriptable. Whether a non-home, non-removable external volume needs it: [G], the lab's `checkexports` tells.
- Versions: the server speaks NFSv2 and v3 only (`nfs_socket.c`: `nfsvers < NFS_VER2 || nfsvers > NFS_VER3` rejected). No v4, so no v4.2 xattrs, no delegations. Max transfer 1 MiB (`NFS_MAXDATA`, nfsproto.h). [S]
- Case-insensitive APFS: `/Volumes/<volume>` is case-insensitive [V]. The server passes names through; the Linux client assumes a case-sensitive server, so `Foo` and `foo` can be two dentries for one file and negative-cache answers can be wrong [G]. Same class of problem as today's virtiofs share.
- System updates: `/etc` lives on the Data volume and survives updates [G, commonly reported]. Apple changed behaviour before: after macOS 11.3, nfsd stopped exporting subdirectories of external volumes for some users (discussions.apple.com/thread/252726325) [S URL, user reports]. Exporting a volume root avoids that case.
- Exports must not contain symlinks; all paths on one line in one file system; `-fspath`/`-fsuuid` pin the volume (recommended for `/Volumes/...`). [S exports(5)]

## Q4. The Linux client (Ubuntu 24.04, 6.8)
Facts below are from Linux `nfs(5)` and the kernel client as I know them [G unless marked]; the lab measures the delays.
- Close-to-open (default `cto`): `open()` revalidates with a GETATTR and the parent directory; data written and closed on the Mac is seen by a later `open()` in the guest regardless of `actimeo`. A Mac rename-over is seen at the next `open()` because the parent directory's mtime changed (new LOOKUP); a stale handle gets ESTALE and the VFS retries the lookup once.
- `stat()` without open, directory listings and negative lookups use the attribute cache: defaults `acregmin=3, acregmax=60, acdirmin=30, acdirmax=60` -> a Mac change can stay invisible to `stat` for 3-60 s, to `ls` of a directory for 30-60 s, and a name the guest looked up as missing for as long as the directory's attributes are cached (30-60 s) with `lookupcache=all`.
- Tightest that keeps caching: `actimeo=1` (all four to 1 s) and `lookupcache=positive` (no negative cache): about 1 s worst case for `stat`, listings and new names; open() still immediate. `noac` makes every access a GETATTR and writes synchronous: correct, slow. Today's vz virtiofs: rename-over missing 0.72 s, name created after a guest miss empty for 0.92 s (track.md, Lab C). So NFS with `actimeo=1,lookupcache=positive` is about equal for listings, better for open() [G until measured].
- inotify in the guest sees only changes made through the guest's own mount; Mac edits never fire it. Same as virtiofs [G; Lab B note]. Mac side: `nfsd` posts fsevents for guest creates, deletes and content changes (`nfs.server.fsevents` default 1; `add_fsevent` in `nfsrv_create`, `nfsrv_remove`, `nfsrv_fmod_timer`) [S], so IDEA's file watcher sees guest edits; content-change events are delayed up to 1 s by the fmod coalescing [S].
- A build creating 100k small files: per file LOOKUP (miss) + CREATE + WRITE (unstable) + COMMIT at close (cto flush), + SETATTR when the tool sets mode or mtime (copy-with-timestamps, `chmod +x`), + GETATTR on reopen: 3-5 round trips per file, about 400k round trips. At an assumed 0.1-0.3 ms per round trip on the user-mode path that is 40-120 s serial, divided by client concurrency (`nconnect`, parallel writers) and the server's 8 threads (`nfs.server.nfsd_threads`). [G; lab measures]
- `nfs.server.async = 1`: the server answers unstable WRITEs as FILE_SYNC, so the client skips COMMIT (one round trip fewer per file); risk: data the guest was told is on disk is lost if the Mac crashes or loses power before APFS flushes; global for all exports. Acceptable for build output, a risk for the agent's source edits. [S nfs.conf(5); G on effect]
- Options: `vers=3,proto=tcp,port=2049,mountport=<fixed>,mountproto=tcp,hard,timeo=600` (hard: a stalled server blocks, never corrupts); `nolock` or `local_lock=all` (locks local to the guest, no `rpc.lockd`/`statd`; Mac processes do not see guest locks); `nconnect=4` (5.3+); `rsize=wsize=1048576` (server max 1 MiB [S]); `async` is the client default (write-back until close). `actimeo=1,lookupcache=positive` for coherence.
- uid/gid: `-mapall=<mac user>` makes everything the guest creates owned by the Mac user on the Mac. The guest sees the Mac uid/gid (501:20) in `stat`; permission checks are made by the server via ACCESS, so the container's uid 1000 can write. `chown` in the guest to another uid fails with EPERM (the server acts as a non-root user) [G]; on a `noowners` volume ownership is ignored anyway.
- Hard links (LINK) and symlinks (SYMLINK/READLINK, resolved by the client) work [S RPC handlers exist]. xattrs: none over NFSv3 (EOPNOTSUPP) [G]. `flock`: emulated with POSIX locks over NLM, or local only with `local_lock=all` [G]. `mmap`: works; shared writable mappings flush on msync/close; coherence with Mac writers only at open [G]. `O_EXCL` create (git `index.lock`): NFSv3 EXCLUSIVE create, honoured by the server [G].

## Q5. Published measurements
- No published comparison of macOS `nfsd` against Apple virtiofs since 2022 found (searches 2026-11-25).
- Jeff Geerling 2020-07 (jeffgeerling.com/blog/2020/revisiting-docker-macs-performance-nfs-volumes/): NFS volumes about 2x faster than osxfs in Docker for Mac, a Drupal install a few seconds slower. Pre-virtiofs, Intel, osxfs era: a different era. [S URL]
- Geerling 2022-03-19 (jeffgeerling.com/blog/2022/new-docker-mac-virtiofs-file-sync-4x-faster/): virtiofs 25.5 s vs gRPC FUSE 93.8 s; no NFS run. [S URL]
- dev.to/dkechag 2023-03 and ddev discussion #5599 (2023-12): virtiofs vs gRPC-FUSE and vs Mutagen (Mutagen 1.6-2.2x faster than Colima virtiofs on Drupal); no NFS. ddev's Dec 2022 benchmark post (updated 2026): no NFS numbers. [S URLs]
- So the speed criterion has no outside evidence either way; only the lab can answer.

## Q6. Verdict (desk)
1. Host descriptors: met by construction (no file table entries; vnode iocounts only during a request and 1 s after a write). [S]
2. No errors/stalls under 8 walkers: needs measurement; no descriptor ceiling to hit, 8 server threads may queue. [G]
3. Speed vs virtiofs: needs measurement; no post-2022 data.
4. Coherence: open() immediate (cto), stat/listings/new names about 1 s with `actimeo=1,lookupcache=positive`; IDEA sees guest edits through nfsd's fsevents. Needs measurement for "at least as prompt"; guest inotify blind to Mac edits as today.
5. Same files in place: met.
6. No macOS limit changed: met (no sysctl limit raised; `nfs.conf` and `/etc/exports` are service config, not limits).
7. Boundary: **not met as exported by default** (forged handles reach the whole volume; 127.0.0.1 exports are open to every local user and every user-mode VM). Met for the guest-outside-share part only when the export is the root of a dedicated volume; the "no one else can mount it" part is not met on the user-mode path and only partly on vzNAT.
8. Operable: partly; stock kernel and `nfs-common` suffice, but root setup on the Mac, FDA by hand, `nfs.conf` edits, and a fixed network address for vzNAT.
