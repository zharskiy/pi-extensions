# Ecosystem notes: bounding macOS host fds for a big shared workspace (researched 2026-11-25)

Host used for spot checks: macOS 27.2, kern.maxfiles 122880. Labels: [V] verified from a primary source I read, [I] my inference, [U] could not verify.

## Core facts on the problem (primary sources)

- Apple Developer Forums 741572 (Nov 2023 - 2026): Lima/vz user, `com.apple.Virtualization.VirtualMachine` holds host fds for files the guest looked up. 70,000 files listed by `ls` -> 58,625 host handles; 30 min later 58,143. Apple engineer: handles are kept for performance unless the guest sends FUSE_FORGET; recycled when count nears the process limit. FB13640480 "significant changes in macOS 15", closed May 2026; new FB25600630 on macOS 26.7.3: after hundreds of thousands of lookups the share hangs 1-10 min. Workaround reported: in the guest `echo 2 > /proc/sys/vm/drop_caches` when host has >~150k open files (makes guest send FORGET). https://developer.apple.com/forums/thread/741572 [V]
- Docker desktop-feedback #168 (Mar 2023 - 2026): same leak with Docker Desktop VirtioFS; gRPC FUSE avoids it. Docker's ctalledo (2026-05-08): Apple's framework is the host-side virtiofsd, holds fds, does not reliably honor RELEASE; Docker cannot fix. https://github.com/docker/desktop-feedback/issues/168 [V]
- apple/container #1097 (opened 2026-01-26, open as of 2026-07-24): same with Apple's `container`; maintainer dcantah 2026-01-29: "Virtualization.framework's virtiofs device behavior (an fd is held open after doing vfs lookups; this is intentional)"; 2026-04-01: "device holds open FDs right around until kern.maxfilesperproc, then tries to purge a portion"; raising rlimit in the guest did not fix; a user got a host kernel panic (2026-07-24). Workaround users: sysctl kern.maxfiles=1048576 kern.maxfilesperproc=524288 kern.maxvnodes=1048576. https://github.com/apple/container/issues/1097 [V]
- So the fd-per-looked-up-inode behaviour is in Apple's closed host server. The only guest-side lever is to make the guest kernel forget inodes (drop_caches, vfs_cache_pressure, fewer cached dentries/inodes) or to touch fewer files over that share. Host-side lever: raise limits (sudo sysctl, not persistent without a LaunchDaemon). [V]
- Lima/colima: I found no lima or colima issue with "too many open files in system" / EMFILE on virtiofs and no maintainer recommendation (GitHub issue search over lima-vm/lima and abiosoft/colima returned nothing relevant). Colima discussion #836 and cross-rs #1292 mention EMFILE with colima vz+virtiofs but only from a search snippet. [U] Lima open issue #5784 (2026-11-11): mountInotify on macOS+virtiofs loops forever once ~20k paths active (v2.3.0). https://github.com/lima-vm/lima/issues/5784 [V]

## 1. Lima/colima mount types

- Lima docs https://lima-vm.io/docs/config/mount/ : reverse-sshfs (host runs sftp-server, guest sshfs; independent of VM type), 9p (QEMU only), virtiofs (vz on macOS; default for vz since 1.0). reverse-sshfs "writable: true is discouraged"; sshfs cache default true => host changes may appear late; default.yaml notes PHP breaks with cache off. [V]
- mountInotify: experimental since Lima 0.21; forwards host FSEvents to the guest as inotify (touches files in guest), writable mounts only; bug #5784 above. Colima has own inotify sync (PR #1649 open, 2026-10-08). Irrelevant to the host fd problem. [V]
- reverse-sshfs fd behaviour: SFTP is handle based; sftp-server opens a host fd on SSH_FXP_OPEN and closes it on CLOSE, and has no per-inode state. [I] -> host fds ~ files actually open at the moment, bounded. Not found documented in primary text. Known problems: slow metadata (one SFTP round trip per op, single ssh channel), symlinks (follow_symlinks option), permissions/uid mapping, no inotify without mountInotify, stale cache. Published numbers: none rigorous; one Colima blog single run (sshfs ~2:19 vs virtiofs vz ~0:29 for an npm build) [U, anecdotal]. Expect 5-20x slower than virtiofs on metadata-heavy work [I, opinion].
- Lima releases: v2.3.0 2026-11-06, Apache-2.0, very active. Colima v0.10.3 2026-06-04, MIT. https://github.com/lima-vm/lima https://github.com/abiosoft/colima [V]
- Lima/colima also support `krunkit` vmType (libkrun; experimental, Apple Silicon, macOS 14+): https://lima-vm.io/docs/config/vmtype/krunkit/ ; colima `--vm-type krunkit` (README). With krunkit, virtiofs mounts cannot be made read-only. [V]

## 2. Docker Desktop

- VirtioFS (default; Apple server) has the fd leak above. gRPC FUSE (Docker's own Go server) does not leak but is slower and some report it eventually crashes the VM (desktop-feedback #168). osxfs legacy/removed. Docker VMM: still same virtiofs family per user reports [U].
- Synchronized file shares (Docker Desktop 4.27+, Feb 2024; paid Pro/Team/Business per Docker blog): ext4 cache of the host dir inside the VM, bidirectional Mutagen sync; bind mounts matching the share use the cache; `.syncignore` (dockerignore syntax) at share root; ~2 million files per share limit; targeted at repos with 100k+ files; case-conflicts show as "File exists"; conflict handling not documented; no numbers for latency; ignored paths stop syncing and are not deleted. Docker's claim 2-10x faster file ops (vendor figure). https://docs.docker.com/desktop/features/synchronized-file-sharing/ https://www.docker.com/blog/announcing-synchronized-file-shares/ [V]
- Host fds: bounded; Mutagen/the sync daemon on the host only stats and reads files in a scan, then watches via FSEvents. Guest side is plain ext4. [I]
- Not usable by us directly (we run colima), but the design is the template: guest-local ext4 + two-way sync.

## Mutagen state
- Repo mutagen-io/mutagen: licence shown as NOASSERTION (mixed MIT + SSPL parts); latest release v0.18.1 on 2025-02-24 (v0.18.0 2024-10-24); last push 2026-04-22; 4.6k stars. https://github.com/mutagen-io/mutagen [V via gh api]
- v0.17 (2023-02-21) licensing post: core MIT; new paid-feature code SSPL, same binaries, paid features (xxHash, zstd, etc.) disabled without Pro; "Mutagen Pro subscriptions are no longer being offered". https://mutagen.io/blog/building-a-robust-future-for-mutagen/ [V]
- Docker acquired Mutagen 2023, said no licence changes planned. https://www.docker.com/blog/mutagen-acquisition/ [V]. Release cadence has slowed (no release in 21 months). [V]
- Mutagen features relevant: two-way-safe mode with conflict surfacing, ignore patterns (gitignore-ish), FSEvents watching on macOS, agent installed over ssh/docker/lima transports, one-way modes. Size-limits doc: https://mutagen.io/documentation/synchronization/size-limits/ . DDEV docs state large node_modules makes Mutagen slow and recommend excluding them (https://docs.ddev.com/en/stable/users/install/performance/). No published scan/memory numbers for ~500k files found. [U]

## Other sync tools (not deeply verified)
- Syncthing: MPL-2.0, v2.1.7 2026-10-21, very active (gh api). Two-way, block-level, FSEvents/inotify watching, .stignore; designed for peer-to-peer; ~seconds-to-tens-of-seconds latency, rescan interval and DB size grow with files; memory use proportional to file count (forum). Needs a daemon on both ends; no ssh transport. [I for latency/perf]
- Unison: two-way, `unison -repeat watch` with unison-fsmonitor; very slow first scan for huge trees, versions on both sides must match; maintained but low cadence. [U/I]
- watchman (Meta, MIT, releases weekly, 2026-11-23): a file-watching service, not a sync tool. [V repo state]
- rsync+fswatch: one-way hacks; two-way requires conflict policy of your own. docker-sync (unison/rsync wrapper) is largely abandoned [U]. devspace/okteto/skaffold/tilt sync: one-way-ish dev loops into k8s pods (devspace sync is two-way, uses its own ignore rules), designed for source dirs, not 500k-file trees [I/U].

## 3. OrbStack
- Built on VirtioFS "with custom optimizations/dynamic caching" (https://docs.orbstack.dev/architecture); "reducing per-call overhead by up to 10x"; benchmarks vs native macOS (1,614 pkgs, 807 MiB): pnpm install 88% of native, yarn 77%, rm -rf node_modules 87% (https://orbstack.dev/blog/fast-filesystem) [V]. Nothing on fds/inodes published. Release notes: "Fixed 'too many open files' after long uptime" and "...on external FAT disks" (https://docs.orbstack.dev/release-notes) [V] -> evidence of fd pressure being handled, mechanism [U]. Closed source; free personal, $8/user/mo commercial (https://docs.orbstack.dev/faq) [V]. Not usable with our colima architecture anyway.

## 4. Podman machine / libkrun (krunkit)
- libkrun (now github.com/libkrun/libkrun, Apache-2.0, v1.19.8 2026-11-06) has its own virtio-fs server on macOS (src/devices/src/virtio/fs/macos/passthrough.rs). Read the source: inodes are addressed by volfs path `/.vol/{dev}/{ino}` (no fd per inode); an fd is kept per open guest handle, plus one only for unlinked-but-still-referenced inodes (`unlinked_fd`). PR #988 (merged 2026-11-18) states: "VMM holds a host file descriptor for every handle the guest keeps open ... descriptor stays open until RELEASE"; fixed to share one fd across read-only handles of one inode. So host fds ~ open files in the guest, not cached inodes: bounded in principle. [V from source + PR]
- Costs: each op that needs a fd does open(path) via /.vol (extra path resolution per op); hard links/renames/unlinked files are the awkward cases. Performance numbers vs Apple's virtiofs: none found [U]. Open correctness issue: libkrun #939 (open() drops page cache under CachePolicy::Auto) and #329 (guest can escape shared dir via crafted names on the Linux backend; macOS backend status not checked). Maintained actively. [V]
- krunkit v1.3.2 2026-07-03 (Apache-2.0). Podman applehv uses Apple's virtiofs (same problem as vz) [I]; libmachine provider libkrun uses krunkit. Lima and colima both can drive krunkit (experimental). No fd-exhaustion issue found for libkrun on macOS (searched issues; zero hits) [U].

## 5. Apple container / containerization
- apple/container 1.7.1 (2026-11-06), apple/containerization 0.33.3 (2026-06-01), Apache-2.0. Uses Virtualization.framework virtiofs: same fd exhaustion, confirmed by maintainers in container #1097 (above), unresolved, causes host panic reports. [V]

## 6. NFS from macOS
- macOS nfsd: requires `sudo` to edit /etc/exports and run `nfsd`, plus Full Disk Access for nfsd for paths outside the home dir (Jeff Geerling 2020: https://www.jeffgeerling.com/blog/2020/revisiting-docker-macs-performance-nfs-volumes/) [V via search, old]. Needs `nfs.server.mount.require_resv_port = 0` or reserved ports from the guest. NFSv3 handles are stateless filehandles; XNU nfsd resolves them per request (no per-client open fd for cached files) [I; XNU source not read]. Vnode cache is still bounded only by kern.maxvnodes. Exposure: export restricted by -network/-mapall; traffic on the vmnet/user network; Apple docs list nfsd as legacy-ish but still shipped [U on macOS 27 status]. Performance: Geerling/Qiita figures (~7x faster than osxfs) are from 2020 and not comparable; NFS attribute caching gives stale reads (actimeo) and no inotify on guest for host-side edits. Locking (lockd/NLM) flaky; case insensitivity on APFS default; uid mapping via -mapall. [I mostly]
- User-space unprivileged servers on macOS: Samba (smbd from Homebrew can run as user on high ports), diod/9p, go-nfs, unfs3 — I did not verify maturity of any for 500k-file trees [U].

## 7. Inverting storage (sources on guest ext4, Mac reaches them remotely)
- IDEA on a network mount: JetBrains support repeatedly says not recommended: native watcher does not work on network mounts ("External file changes sync may be slow"), indexing latency per file, SMB change notification issues; remote files over a network protocol "not a supported scenario" (support community threads, e.g. https://intellij-support.jetbrains.com/hc/en-us/community/posts/206602515-Disable-warning-External-file-changes-sync-may-be-slow ). [V via search, forum]
- JetBrains Remote Development: IDEA 2026.1 help: Gateway needs a Linux backend; Toolbox adds macOS/Windows backends; Rider 2026 docs say the Gateway SSH workflow "will soon be deprecated" in favour of dev containers (https://www.jetbrains.com/help/idea/2026.1/faq-about-remote-development.html, https://www.jetbrains.com/help/rider/2026.2/FAQ_about_remote_development.html). Included with the paid IDE subscription. Constraint violated: IDE would no longer be the Mac-local one with a local index. [V]

## 8. Splitting by data class
- VS Code dev containers docs: named volume mounted over node_modules (and for whole tree "clone in container volume") to avoid bind-mount cost (https://code.visualstudio.com/remote/advancedcontainers/improve-performance). [V]
- Effect on host fds: only files accessed through the share count; regenerable trees (node_modules, target, .gradle) on a guest volume never reach Apple's server. For a Maven monorepo + frontends that is the bulk of the 100k+ inodes; sources+.git remain (a few hundred thousand files in a 1000-module repo plus dozens of frontend repos could still be 100k+, [I] must be measured with find|wc).
- IDE on Mac: node_modules absent -> JS/TS resolution and types missing, run configurations on the Mac fail; target/ absent -> Maven import still works (IDEA builds its own output under out/ or uses mvn on the Mac), but the IDE cannot see classes produced by the agent unless it rebuilds locally. Fix is to run `npm install`/mvn on the Mac too (separate copy), which costs disk but gives the IDE its own consistent tree. [I, opinion]

## 9. Other bounds
- virtiofsd (Linux, Rust): `--inode-file-handles=prefer|mandatory` uses name_to_handle_at file handles instead of O_PATH fds ("reduces the number of file descriptors virtiofsd keeps open"); needs CAP_DAC_READ_SEARCH, shared dir on its own filesystem; default RLIMIT_NOFILE up to 1M. Linux only. https://gitlab.com/virtio-fs/virtiofsd (README) [V]
- macOS equivalents: `/.vol/<fsid>/<ino>` path (used by libkrun, still works on this macOS 27.2 host: `ls -l /.vol/16777244/6718998` resolved a real file) [V local]; `fsgetpath(2)` (inode -> path, DTS: prefer over volfs); `openbyid_np(2)` is private SPI in sys/fsgetpath.h; no public open-by-handle. [V headers via search]
- Virtualization.framework custom virtio devices: NEW in macOS 27 (`VZCustomVirtioDeviceConfiguration`, `VZCustomVirtioDevice`, `VZVirtioQueue`, `VZVirtioSharedMemoryRegion` with mapMemory/unmapMemory of host memory; WWDC26 session 224 "Expand the capabilities of your Virtualization app"). So my caller's belief ("Virtualization.framework cannot plug your own virtiofs device") is outdated for macOS 27+: a host app can implement virtio device id 26 (virtio-fs) itself, including a DAX shared-memory window, in-process. I found NO existing virtio-fs implementation on top of it; this would mean writing/porting a FUSE-over-virtqueue server (libkrun's macOS passthrough is the obvious code to port). Does the guest need a special driver? virtio-fs driver is in mainline Linux, so no. Unknown: entitlement requirements, whether lima/colima expose it (they don't) [V docs, U rest]. https://developer.apple.com/documentation/virtualization/custom-drivers https://developer.apple.com/videos/play/wwdc2026/224/
- Before macOS 27 the only options are Apple's VZVirtioFileSystemDevice (closed) or other VMMs (krunkit/libkrun, QEMU+virtiofsd is unavailable on macOS).

## Shortlist (ranked, opinion)

1. Split data classes AND shrink what virtiofs sees: keep sources+.git on the share, mount regenerable trees (node_modules, target, .gradle, dist, build) on guest-local volumes/overlay; add periodic guest `drop_caches=2` (or tune vfs_cache_pressure) as a bound enforcer, plus monitor kern.num_files. Risk: not a true bound, only a reduction; IDE needs its own node_modules/target on the Mac.
2. Two-way sync (Mutagen or Syncthing) between Mac tree and guest ext4 with ignore rules for regenerable trees: truly bounded on host, ext4 speed in guest, IDEA keeps real local files. Risk: initial sync and steady scan cost at several hundred thousand files unmeasured, conflicts and lag, Mutagen is slow-moving (last release 2025-02).
3. krunkit (libkrun) as VM backend in colima/lima: fd per open handle, inodes by volfs path, so the bound follows open files not cached inodes. Risk: experimental in lima/colima, no published performance numbers, hold on correctness bugs (#939), needs a try-it benchmark; read libkrun macOS passthrough code before trusting.
4. reverse-sshfs: bounded, simple, no host deps, but slow on npm/mvn; probably only for a small subset.
5. Custom virtio-fs device on macOS 27 (VZCustomVirtioDevice): cleanest long-term bound but a project of its own.
6. NFS: bounded probably, needs sudo/FDA; operationally fragile; IDE side fine (files stay on Mac).
Not viable under the hard constraints: sources on guest + IDE over network mount, JetBrains remote dev, Docker Desktop paid features, OrbStack.
