# Notes: inside Apple's virtiofs server (track t2, reverse engineering)

Binary: `/System/Library/Frameworks/Virtualization.framework/Versions/A/XPCServices/com.apple.Virtualization.VirtualMachine.xpc/Contents/MacOS/com.apple.Virtualization.VirtualMachine`, CFBundleVersion 308.2.7, macOS 27.2 (26B123). arm64e slice thinned with `lipo`, disassembled with `otool -tV` (stripped: no local symbols; addresses below are in the arm64e slice, unslid, base 0x100000000). Framework binary (client side) extracted from the dyld shared cache with `dsc_extractor.bundle`.

Evidence classes: [V] confirmed by experiment here, [S] read in the binary, [G] guess.

The server is C++ in the XPC service, not in the framework: `VzCore::Hardware::FuseSession`, `VzCore::Hardware::FuseDirectorySharingBackend`, `VzCore::Hardware::SharedResourceLimit` (+ `SharedResourceLimit::Observer`), `Fuse::InHeader` etc. (RTTI strings) [S].

## Q1 where the ceiling comes from (first findings)

- [S] Purge threshold = `kern.maxfilesperproc * 9 / 10`, read once with `sysctlbyname("kern.maxfilesperproc")` in the constructor of a process-wide singleton `SharedResourceLimit` (function 0x100137e00, run via `std::call_once` on 0x1004cdc90; object stored in global 0x1004cdc80/0x1004cdc88):
  ```
  0x100137e28 add x0, ..."kern.maxfilesperproc"; bl _sysctlbyname
  0x100137e60 add x8, x8, x8, lsl #3          ; x8 = maxfilesperproc*9
  0x100137e64 mov x9,#-0x6666666666666667; eor x9,x9,#0x8000000000000003  ; x9 = 0x199999999999999A (~2^64/10)
  0x100137e6c umulh x21, x8, x9               ; x21 = *9/10
  0x100137ea4 stp x21, x8(=1), [x0,#0x18]     ; limit stored at +0x18
  ```
  So 0.9 is a constant in the code (x9/10, integer). 61,440 * 9 / 10 = 55,296, matches the measured purge point. If sysctl fails or returns <= 0 it aborts (0x1001380c4).
- [S] The same singleton creates two dispatch queues: serial `com.apple.virtualization.shared-resource-limit` (0x100137ee4) and `com.apple.virtualization.shared-resource-limit.resource-freeing-queue` with `dispatch_queue_attr_make_with_qos_class(NULL, 0x11 = QOS_CLASS_UTILITY, 0)` (0x100137f40), plus an `unordered_map` (max_load_factor 1.0 at +0x70), presumably of observers (sessions).
- [S] Hard limit: the FUSE backend start (function 0x100118be0) calls `getrlimit(RLIMIT_NOFILE)` and, if `rlim_cur < rlim_max`, sets `rlim_cur = rlim_max` and calls `setrlimit` (0x100118fb8..0x100118fdc; errors "Unable to get/set file descriptor limit"). The kernel clamps the soft limit to `kern.maxfilesperproc`, so the hard ceiling is 61,440 here. Both numbers come from `kern.maxfilesperproc` (one via sysctl x 0.9, the other through the rlimit clamp), but through two separate reads.
- [S] The singleton is per process; each VM has its own XPC process (`_MultipleInstances` true in Info.plist), so the 55,296 budget is per VM and shared by all virtiofs devices of that VM [S for the code path, G that several devices in one VM share it: one singleton, all sessions get it].

## Q2 per-VM knobs (first findings)

- [S] The backend's configuration decoder (function 0x1001170d0) reads three keys from an in-process `Base::PropertyBag`: `share`, optional `file_descriptor_limit_override`, optional `file_handle_range_override`. The override value is a `shared_ptr` (holder +0x8 pointer, +0x10 control block, refcount incremented at 0x100117268) stored at backend +0x78/+0x88, and 0x100118cc0 uses it instead of the global `SharedResourceLimit` singleton when present. A shared_ptr cannot come over XPC: this is an in-process injection hook (tests) [S for type, G for "tests"].
- [S] The literal `file_descriptor_limit_override` is referenced once in the whole service binary (the reader) and does not occur in the Virtualization framework binary at all; nothing in shipped code writes it.
- [S] Client-side config struct `VzCore::VirtualMachineConfiguration::DirectorySharingDevices::VirtioFileSystem` = { tag string, optional<variant<Single, Multiple, Rosetta>> }, `SharedDirectory` = { FileDescriptor, bool read_only, uint64 unique_id } (ObjC type encodings of `-[VZVirtioFileSystemDeviceConfiguration _directorySharingDevice]`). No cache, limit or timeout field.
- Public/private ObjC: `VZVirtioFileSystemDeviceConfiguration` (tag, share), `VZSharedDirectory` (URL, readOnly), `VZSingleDirectoryShare`, `VZMultipleDirectoryShare`, `VZLinuxRosettaDirectoryShare` (+ caching options for Rosetta only). No limit/cache/descriptor selector in any of them [S, runtime dump of all 326 classes/protocols].
- [S] No environment, no defaults, no boot-args: the service imports no `getenv`, no `CFPreferences*`, no `NSUserDefaults`; `__objc_methname` has no `environment`/`arguments` selector (NSProcessInfo is used twice, not for those). The only `sysctlbyname` names are hw.physicalcpu_max, hw.logicalcpu_max, kern.maxfilesperproc, kern.osversion, kern.ipc.maxsockbuf/maxsendmsgx/maxrecvmsgx, kern.hv_vmm_present (no kern.bootargs). `os_variant_has_internal_content("com.apple.virtualization")` gates 7 sites (Apple-internal builds only).
- [S] Entitlements of the VM service include `com.apple.private.vfs.open-by-id` (needed for `openbyid_np`), `com.apple.private.virtualization.plugin-loader`, `com.apple.security.hardened-process`. Client-visible entitlement strings: `com.apple.security.virtualization`, `com.apple.private.virtualization(.plugin|.plugin-loader|.private-vsock|.security-research|.unit-test)`. None is about file sharing.
- Conclusion Q2: no per-VM or per-client knob that a non-Apple client can set; the only override is an in-process test hook. Raising/lowering `kern.maxfilesperproc` (root, Mac-wide) is the only lever on the threshold [S].

## Q7 custom devices and plugins (first findings)

- [S] Two provider kinds for both `VZCustomVirtioDevice` and `_VZCustomMMIODevice`: a *delegate provider* (`VZCustomVirtioDeviceDelegateProvider`: ivars `_endpoint` (xpc endpoint), `_deviceQueue`, `_delegate`) and a *plugin provider* (`_VZCustomVirtioDevicePluginProvider`: `_pluginName`, `_pluginPersonality`). The service-side connection identifier is `variant<CustomDeviceConfiguration::CommonConfiguration::PluginIdentifier, Base::Xpc::Endpoint>`.
- [S] Public `VZCustomVirtioDevice` runs in the client (app) process: ivars `_device_queue`, `_messenger_queue`, `_connection` (xpc), `_device_manager` (`Vz::CustomVirtioDeviceManager`), `_queues` of `VZVirtioQueue`, each holding a `VzCore::Hardware::VirtioQueue` and a `shared_ptr<Vz::SharedMemoryMap>`. The client manager handles XPC messages `did_accept_driver_ok(vector<VirtioQueueConfiguration>, BitSet features)`, `handle_notification(uint16 queue)`, `handle_reset/stop/pause/resume/save/restore`, `update_shared_ram_manager(vector<HvCore::SharedRamEntry>)`, `address_space_did_reset` (framework RTTI strings `ZN2Vz25CustomVirtioDeviceManager19handle_notificationEtE3$_0` etc.). So: guest RAM is shared into the app process, the app walks the rings itself, and every guest kick arrives as one XPC message (Base::Messenger handler with a `uint16` argument) dispatched to the device queue; the delegate `customVirtioDevice:didReceiveNotificationForQueue:` runs there. The service-side `VzCore::Hardware::CustomVirtioDevice` has handlers for `uint16` (interrupt request for a queue, [G] on meaning), `()` (reset request), device-specific config update, shared-memory map/unmap. Latency per request is therefore at least one XPC hop each way (kick and interrupt) [S for the channel, G for cost; not measured].
- [S] Plugins: loaded by `com.apple.Virtualization.PluginLoader.xpc` (entitlements `com.apple.private.virtualization.plugin-loader`, `...plugin-loader-service`, `com.apple.private.xpc.domain-extension`, hardened process; `_MultipleInstances`, `JoinExistingSession`). The framework (`_VZPluginService +xpcMain`) only accepts plugin bundles from `/System/Library/VirtualizationPlugins` or `/AppleInternal/Library/VirtualizationPlugins` ("Invalid plugin path.", "Plugin path does not exist.", "Bundle identifier is incorrect.", "Service is not multi-instance."), reads `VZPluginPersonalities` from the plugin's Info.plist (`PersonalityName`, `PersonalityType`, `PersonalityClass`), loads the bridge class (`_VZCustomVirtioDevicePluginBridge` / `_VZCustomMMIODevicePluginBridge`, `initWithXPCConnection:personalityDictionary:personalityClass:connectionDelegate:options:`) and sandboxes it (`PLUGIN_TMP_DIR`, `PLUGIN_ROOT_DIR`, "FATAL: Sandbox initialization failed"). The plugin runs in its own XPC process, not inside the VM process. `/System/Library/VirtualizationPlugins` does not exist on this Mac [V: ls]. Both folders are on the sealed system volume or Apple-internal, so a third party cannot install a plugin; and the `_pluginName` setters are private (`_setPluginName:`). Answer: no third-party plugin inside the VM process.

## Address note

The service binary is fat with three slices: x86_64, arm64e (UUID C4BA04A1, what I disassembled first) and a third arm64 slice with cpusubtype 12 (UUID 31E13F5A), which is the one that actually runs here [V: `sample` load-address UUID]. Same code, addresses shifted (e.g. the only `openbyid_np` call is 0x10013313c in the arm64e slice, 0x1001312c4 in the running slice). Addresses below are arm64e unless marked "(s12)".

## Q5 timeouts and FUSE_INIT

- [S] Dispatcher 0x100119c4c: `opcode-1` vs 0x33, jump table 0x10040357c. Handled: LOOKUP 0x124e50, FORGET 0x1254e8, GETATTR 0x1257e0, SETATTR 0x125cac, OPEN 0x127e78, READ 0x128700, WRITE 0x128cc0, RELEASE 0x1292dc, INIT 0x124b04, OPENDIR 0x126a2c, READDIR/READDIRPLUS 0x1332b8 (flag 0/1), RELEASEDIR 0x127a28, BATCH_FORGET 0x12561c, DESTROY 0x1244cc, STATX 0x131884, LSEEK 0x130ea0, RENAME 0x119a5c, RENAME2 0x12d048, CREATE 0x12bf04 (plus the usual MKDIR/UNLINK/... not itemised). ACCESS, INTERRUPT, BMAP, POLL, NOTIFY_REPLY, SETUPMAPPING/REMOVEMAPPING (no DAX), SYNCFS, TMPFILE share one error-reply stub 0x119c80 (ENOSYS, [G] on the errno).
- [S] INIT 0x124b04: needs major 7; reply major 7, minor = min(guest, 34). flags_out = guest_flags & 0x46029 = ASYNC_READ | ATOMIC_O_TRUNC | BIG_WRITES | DO_READDIRPLUS | READDIRPLUS_AUTO | PARALLEL_DIROPS (each only if offered); + SETXATTR_EXT if offered; + FLOCK_LOCKS if offered and a session flag is set. Never: POSIX_LOCKS, AUTO_INVAL_DATA, WRITEBACK_CACHE, EXPORT_SUPPORT, CACHE_SYMLINKS, EXPLICIT_INVAL_DATA, DAX. max_readahead = max_write = clamp(guest max_readahead, 16 KiB, 128 KiB); max_background 0, congestion_threshold 0, time_gran 0, max_pages 0 (guest defaults apply).
- [S] Entry and attribute timeouts are constants: every fuse_entry_out the server builds (LOOKUP builder 0x100134460, the root/"."/".." paths, multi-share root) has entry_valid = 1 s, attr_valid = 1 s, nsec 0, generation 1, attr.ino = nodeid. GETATTR replies use attr_valid 1 s as well [S].
- [S] No invalidation is ever sent to the guest: no FUSE_NOTIFY_* writer (NOTIFY_REPLY is unsupported, there is no notify unique=0 path), no kqueue/kevent, no FSEvents, no dispatch vnode source imports. So a Mac-side change becomes visible only when the guest's 1 s entry/attr timeout expires (and page cache follows open/attr rules; no AUTO_INVAL_DATA). Not measured here (see "Experiments").

## Q3 purge (SharedResourceLimit) and reopen

Object layout of `SharedResourceLimit` (singleton): +0x18 limit (maxfilesperproc*9/10), +0x20 enabled, +0x28 serial queue `shared-resource-limit`, +0x30 serial `resource-freeing-queue` (UTILITY), +0x38 unfair lock, +0x40 count of descriptors in use, +0x48 lock and +0x50.. unordered_map of observers (one per FuseSession), +0x78 lock, +0x7c "notification pending" flag.

- [S] acquire, 0x10013abf8 (s12 0x100138ca4): lock; `count++`; unlock. If enabled and `count >= limit`: `dispatch_sync_f(freeing_queue, noop 0x10013af20)` - i.e. the calling request thread waits until every close job already queued on the freeing queue has run; then re-check, and if still over, call 0x10013ad04. Acquire never refuses: the count can run past the limit; the only hard stop is the rlimit (EMFILE).
- [S] 0x10013ad04: if no notification is pending, set the flag and `dispatch_async_f(shared-resource-limit queue, 0x10013afc4)`. 0x10013afc4 copies the observer list under the lock, clears the pending flag, and calls each observer's virtual "free resources" method. The observer method 0x100136598 does `dispatch_async_f(observer+0x20, 0x10013a594)`: the purge itself runs later on the session's queue [S]; that this is the `virtio.filesystem-device:N` request queue is [G] (strong: the purge walks the session's maps without taking a lock).
- [S] Purge 0x10013a594, per session:
  1. Closes all descriptors held in the vector at session+0x1f0 (deferred closes) and subtracts them from the count.
  2. Builds a hash set of inodes that must keep their fd: the ones with an open file handle (tree at session+0x38) and with an open directory handle (list at session+0x1d0).
  3. Batch = max(fd-holding inodes of this session (session+0x1b8) / 10, 64) (`umull 0xcccccccd; lsr #35`, `cmp #0x40; csel`).
  4. Walks the inode LRU list (session+0xa8, list length at +0xd0) from the front (oldest). For each node with an fd that is not in the pinned set: captures the path (0x1003de6d8: `fcntl(F_GETPATH)` + `fstat` check, fallback `fstatfs` + `fsgetpath`), stores it in the node (+0x30), `close(fd)`, fd = -1, moves the node to the back. Nodes without an fd or pinned are moved to the back without counting. Stops after `batch` closes or after one pass.
  5. session+0x1b8 -= closed; limit.count -= closed.
  So: LRU, about 10% of that session's descriptors per round (5,500 at 55k), done synchronously on one queue with two syscalls per descriptor (F_GETPATH and close). Only one round per notification; the next round needs another acquire over the limit after the pending flag was cleared [S].
- [S] Reopen of a purged inode, helper (s12 0x100133ef0, 27 callers = every handler that needs the inode fd): if node fd == -1, call 0x1001312a0..(s12 0x100131274): if the inode number fits in 32 bits, `openbyid_np(fsid = {dev,0}, objid = {ino,0}, O_RDONLY|O_NONBLOCK|O_SYMLINK)`; on failure or a 64-bit inode, `open(saved path)` then `fstat` and require st_dev/st_ino to match (else ENOENT). On success: fd stored, session+0x1b8++, acquire() again. On failure the node is dropped from the maps. So reopen = by file id first, path second; never `/.vol`.
- [S] FUSE OPEN (s12 0x100126144) uses the same wrapper with the guest's open flags: every guest open() is an `openbyid_np` on the Mac, not a dup of the cached fd.
- Why it loses [S + G]: (a) acquire only schedules a purge, it never blocks the open, so parallel LOOKUPs keep adding fds while the purge waits in the queue behind them; (b) the purge is one batch of 10% (min 64) per notification and it re-arms only when a later acquire still sees count >= limit; (c) every reopen of a purged entry calls acquire again; (d) FORGET closes go through the UTILITY-QoS freeing queue, so under load they lag, and every acquire above the limit does a `dispatch_sync` on that queue: the single request queue stalls behind the backlog of closes (and behind the 2-syscalls-per-fd purge batch). This matches "stalls for seconds after the purge" [G for the cause attribution, not traced].

## Q4 one descriptor per inode

- [S] Each inode node holds an fd from `openat(dirfd, name, O_RDONLY|O_NONBLOCK|O_SYMLINK)` (0x10011ef7c: flags 0x200004), taken at LOOKUP (new-inode path 0x100134608: nodeid = session counter +0xa0, inserted into maps +0xe0 and +0xa8, refcount 1, session+0x1b8++, acquire). The fd is the inode's identity and the dirfd for `openat`/`fstatat`/`getdirentries64`/`fgetattrlist` of children; GETATTR is `fstat` on it. No watching (no kqueue/FSEvents/vnode sources imported) [S]; no FUSE notify sent to the guest [S].

## Q6 FORGET, queues, threads

- [S] `num_request_queues` = 1, a constant (s12 0x10013d7f4 `mov w8,#1; str w8,[x19,#0x1d14]`). [V] the guest shows `virtio4-hiprio` and `virtio4-requests.0` only.
- [V] `sample` of my lab VM's process under 8 parallel `cat *` readers: all FUSE work runs on one serial dispatch queue `com.apple.virtualization.virtio.filesystem-device:0` (1,773 of 2,287 samples busy). Inside it 1,256 samples are in `openbyid_np` (from FUSE OPEN), then fcntl 73, fstatat 59, close 39, getdirentries64 18. No worker pool, no pthreads for FUSE (one `std::thread` create+join exists in a handler, s12 near 0x12aad4 arm64e, purpose not read).
- [S] FORGET 0x1254e8 and BATCH_FORGET 0x12561c parse the entries and call 0x100134d80 per node (decrement nlookup; "Over-forgot node" check). When the count reaches 0 the node is erased and 0x10012487c collects its fd into a vector and `dispatch_async_f(limit.freeing_queue, 0x100139344)`, which does `count -= n` and `close()` each one. So FORGET itself is cheap but each zero-ref forget is one heap block + one async job on a UTILITY serial queue shared by all virtiofs sessions of this VM (one process per VM) [S]. Both vqs (hiprio, where the guest sends FORGET, and requests) are served by the same serial device queue [G strong: one queue seen in the sample; hiprio not separately observed], so forgets wait behind every queued request.

## Experiments (lab VM `lab-t2-vz`: lima 2.3.0, vz, virtiofs, 2 vCPU, 2 GiB, Ubuntu 26.04 guest kernel 7.0.0-34, scratch folder shared rw; its VM process was identified by start time and by `lsof` showing its disk; no other process was sampled)

- [V] Q6: the guest sees one request queue (`/proc/interrupts`: `virtio4-hiprio`, `virtio4-requests.0`).
- [V] Q6: `sample` under 8 parallel `cat` readers over 2,000 files: all FUSE handling is on the serial queue `com.apple.virtualization.virtio.filesystem-device:0`, one thread at a time; 71% of its samples are inside `openbyid_np` called from FUSE OPEN.
- [V] Q5: visibility of a Mac-side change in the guest (5 runs each; the guest had looked at the name just before the change; the Mac side made the change within about 1 ms of a trigger file):
  - stat size after a Mac append: 999-1002 ms (= attr_valid 1 s)
  - old name after a Mac rename still resolves: 1000-1002 ms; the new name resolves at once after that
  - a new file in a directory listing: 0-1 ms (readdir is not cached)
  - a name the guest found missing, then created on the Mac: 0-3 ms (no negative dentries: the server answers LOOKUP of a missing name with an error, not with nodeid 0 and a timeout)
- [V] Q3: purge run (exclusive lock held about 3 minutes, watchdog on `kern.num_files` > 100,000 did not trip). 90,000 empty files in 90 folders, guest `stat` over all of them with 8 parallel workers, process fd count polled with `lsof` every 0.3 s. The count rose to 51-55k and then fell to 24 (baseline) or about 9-12k within under 0.3 s, three times in about 5 s: far more than one 10% batch. My explanation [G, strong]: while the purge job waits in the serial queue, each further acquire above the limit (after the notify job has cleared its pending flag) schedules another notify, so several purge jobs queue and run back to back, each closing 10% of what is left (0.9^n).
- [V] Q3: `sample` during that run: the purge function (s12 0x1001387xx, the LRU walk, with the path capture s12 0x1003d8094 under it) runs as its own block on the same `filesystem-device:0` queue (198 of 1,693 queue samples). The reopen of purged inodes dominates afterwards: 1,096 of 1,693 samples are `openbyid_np` under the reopen helper (s12 0x100133ef0) called from LOOKUP, i.e. after a purge every stat of a purged entry costs one `openbyid_np` on the single request queue. The two `stat` passes over 90k files took 3.1 s and 2.7 s; I did not reproduce a multi-second stall at this scale (2 vCPUs, empty files).
