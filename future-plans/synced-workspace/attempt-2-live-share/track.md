# Track: bounding the VM's host descriptors

Worktree `.claude/worktrees/virtiofs-fd-bound`, branch `research/virtiofs-fd-bound`. `docs/` is gitignored, so this folder is local to the worktree.

## Question

While the pinata VM runs, Apple's virtiofs server keeps about one host descriptor per inode the Linux guest has cached. The count grows with files ever touched and fills the Mac's system-wide table (`kern.maxfiles` 122,880). Find the most elegant way to bound it while the whole `workspaceRoot` stays shared and editable on the Mac.

## Host at the start (2026-11-25 01:02)

- macOS 27.2, Apple silicon, 16 GB RAM, 12 CPUs.
- `kern.maxfiles` 122,880, `kern.maxfilesperproc` 61,440, `kern.num_files` 6,596.
- colima profiles: `default` Running (2 CPU, 4 GiB), `pinata` Stopped (8 CPU, 8 GiB). Neither is touched by the labs.

## Hypotheses going in (to be tested, not assumed)

1. A FUSE inode is evicted as soon as its last dentry goes, so pruning the dentry cache of the virtiofs superblock alone releases the host descriptors.
2. `mount -o remount` on the virtiofs mountpoint prunes exactly that superblock's unused dentries (`reconfigure_super` calls `shrink_dcache_sb`), leaving every other guest cache alone. That would make a targeted prune possible without `drop_caches`.
3. A recent kernel may expire FUSE dentries on a timer (`inval_wq`), which would bound the count by time since last use with no governor at all.
4. Two VMs at the default per-process limit (2 × 61,440 = 122,880) fill the table exactly; the README's advice to raise limits lets one VM do it alone.
5. Reverse-sshfs holds descriptors only for open files but is much slower for metadata-heavy work.
6. Moving build output off the share lowers the load but does not bound it: a recursive grep over the sources alone can exceed the table.

- 02:50 Reading after Lab E; it changes the recommendation.
  - What the problem statement calls the cause is half of it. Apple's server does release without the guest forgetting: at about 0.9 of its own per-process allowance it purges down to 11 to 13 thousand while the guest keeps its cache. So one VM is bounded by its allowance (61,440 here), softly at 55.3k and hard at 61,440. Not once in five labs did one VM exceed it.
  - The Mac-wide failure is arithmetic. macOS sets `kern.maxfiles` to exactly two allowances on every Mac. One VM plus the rest of the Mac fits (61,440 + about 7k); two VMs do not (2 × 61,440 + 7k = 129,680 > 122,880). The README's advice raises both numbers and keeps the ratio, so it postpones; raising only `kern.maxfiles` changes the ratio and makes the sum a bound that the kernel enforces.
  - Apple's purge is the better governor: it frees host descriptors and leaves the guest's cache alone (26 µs per revisit). The remount prune frees them by emptying the guest's cache (55 µs per revisit, and 11 to 13 times slower `git status` once the working set is larger than the budget). This workload's sets are larger than any budget below Apple's ceiling.
  - A guest governor cannot bound another VM, and without backpressure it does not bound its own bursts.
  - So: layer 1 is the invariant `kern.maxfiles ≥ (VMs + 1) × kern.maxfilesperproc`, checked by pinata at launch and in doctor, fixed by one privileged command; the host watcher and `vm.releaseFileCache` go. Layer 2, the governor, is for a Mac whose limits cannot be changed. Not verified: that `kern.maxfiles` can be raised alone on macOS 27 (from XNU source of an older tag; no sudo was used here).
