# Deviations from PLAN.md in release 0.1

Each entry: what the plan says, what was built, and why.

1. **Spike location.** Plan: three concurrent children from an extension inside the TUI. Built: the three-child test runs through the adapter from an SDK script; the TUI runs (driven through a pseudo-terminal) spawned two concurrent children. Reason: no interactive terminal is available to the agent doing the work. See `docs/spike.md`.
2. **Agent view scrolling.** Plan: `ScrollView` in fullscreen mode, manual windowing otherwise. Built: pi's `ScrollView` drives scrolling in both modes (follow-the-tail, clamping, PgUp/PgDn/Home/End). Pi composites overlays outside its layout engine, so the view calls `ScrollView.updateLayout` itself and slices the visible rows; pi draws no scrollbar there, so the hint bar shows the position instead. The mouse wheel works in fullscreen mode (pi's default), where pi routes wheel events to the overlay. In regular mode pi sends no mouse events, so scrolling there is keyboard only.
3. **Transcript rendering.** Plan: pi's message and tool components. Built as planned: `UserMessageComponent`, `AssistantMessageComponent`, `ToolExecutionComponent` (results matched by tool call id, as pi does when it loads a session) and `CustomMessageComponent`; the tools-expand key (Ctrl+O by default) toggles tool detail inside the view. Built-in tools use pi's own renderers. Tools registered by other extensions are drawn with pi's generic tool renderer, because a view that reads a session file has no access to those extensions' tool definitions. Thinking blocks are collapsed to pi's hidden-thinking label.
4. **Nesting delivered in 0.1 (F10 pulled forward).** Plan: depth 2 in 0.1, nesting in F10. Built: default `maxDepth` 3 (2 to 4). Children never load this extension; instead, at spawn an agent whose `subagents` list is not empty and whose depth is below `maxDepth` gets `run_agent`, `message_agent` and `agent_status` as custom tools of its SDK session, with the `run_agent` description built by `describeRunAgent` from its own list and frozen at spawn. The caller of a grandchild is the child's agent id. A child caller is woken through the same outbox code as the main session: held while its run is in flight, delivered once per batch through its own session's `followUp` (a prompt when idle). Concurrency: a semaphore slot is held only while a run is in flight; an agent that ends its turn with an open batch stays `running` but releases its slot and takes a new one when woken, and a child blocking in `run_agent` with `wait` releases its slot until the batch settles, so no tree can deadlock. Instead of the plan's reserved capacity, no slot is ever held while waiting. Agent tools of children never attach usage to their tool results, so every agent's usage reaches the ledger once under its own id and the main session's tools deliver it once. Closing an agent stops its open children at once.
5. **Grace state.** Built as F11 describes, ahead of the view's input box. `stop` aborts the current run and puts the agent in `grace` for `stopGraceSeconds` (default 60, 0 closes at once); the caller is not woken yet. A message in grace goes by `followUp` and starts a run; the countdown pauses while the run is in flight and restarts from the full period when it settles. When the countdown ends the agent closes as `stopped` and the batch wakes once, carrying the agent's last output. A grace agent counts as open for the batch. Limits still apply (a handoff closes it as `handoff`, a limit abort as `failed`), a second stop closes at once, and reload or shutdown closes it as `stopped` without a wake. Queued agents and `stop(id, { immediate: true })` skip grace.
6. **Opening the agent view from the widget.** The widget is not focusable in pi, so `/agents <id>` (or `/agents` with pi's select dialog) is the entry point by design. An unknown id only shows a warning; nothing opens. The full list view is F12.
7. **Own-extension filter in children.** The first spike run showed that filtering child extensions by "path under the package root" also dropped the inline child extension (its pseudo path resolved under the project directory when the project is this repository). The filter now drops only absolute paths under `src/` of this package; an `AsyncLocalStorage` guard also keeps the extension factory from running inside a child.
8. **Model runtime in children.** One `ModelRuntime` per extension instance, created from `auth.json` and `models.json`, is shared by all children. Providers or virtual models registered at runtime by other extensions are not replayed into it, so an agent on such a model fails to spawn with a clear error.
9. **MCP.** Children do not get MCP tools: SDK sessions do not load pi's built-in MCP extension and 0.1 does not add it.
10. **Package name.** `pi-subagents` is taken on npm, so the package is `pi-subagents-mz`. Now: the package ships three extensions and is `pi-extensions-mz` (entry 49).
11. **Handoff enforcement.** The handoff instruction is steered as a message; tools are not restricted for the last turn, so the cache is never broken. If the agent keeps working, it is aborted at 115 % of the budget or three turns after the request, and closes as `failed` unless a valid handoff file exists. Now: the limits plugin acts only on turns that end in a tool call, so a finished agent is never asked for a handoff (entry 48).
12. **Wake message rendering.** The batch result arrives as a user message (`sendUserMessage`), not a custom message with its own renderer, because `sendMessage({triggerTurn})` skips `before_agent_start` and busts the cache (pi issues #5581, #10267). Per-agent finish rows are drawn live in the `run_agent` tool row instead.
13. **"Main" spend figure.** Our footer's `main` is pi's session total minus the agent usage we delivered through tool results, so `main + agents` never counts an agent twice while pi's own footer includes delivered agent usage. Now: the delivered channel is gone and the footer belongs to the spending extension (entry 47).
14. **Commits.** The brief asked for a commit per feature; the user later asked for no commits. All work is uncommitted on `feat/mvp`.
15. **Main session prompt replaces pi's prompt at runtime, not on install.** Requested: installing the extension replaces pi's default system prompt with `prompts/main-session.md`. Built: every `before_agent_start` in the main session sets the file as pi's preamble (`customPrompt`) and rebuilds the `tools`, `rules` and `docs` sections that a custom preamble drops, from the same structured options pi uses (`src/adapter/main-prompt.ts`, checked against pi's own builder in a test). Reason: pi has no install hook, and writing `~/.pi/agent/SYSTEM.md` would change every pi session, including ones without this extension, and would also drop those three sections. Consequences: a user `SYSTEM.md` is overridden in sessions where the extension is loaded; the rebuilt `rules` see the tool set and guidelines as they are when our handler runs, so guidelines added by an extension whose `before_agent_start` runs after ours are not included.
16. **Prompt files are not settings.** The `orchestratorPrompt` and `basePrompt` settings are gone. Both prompts are read from the package's `prompts/` directory when the extension loads; to customise them, edit the files in a local checkout and `/reload`.
17. **Mandatory `limit` and `subagents`.** The optional `budget` field became the mandatory `limit`, and every agent file must declare `subagents` (`[]` for none). Files without them fail to load, so agent files copied from Claude Code or other pi packages need both fields added.
18. **Tests live in `test/`.** Plan: tests next to the code (`src/adapter/conformance.test.ts`). Built: every test sits under `test/`, mirroring `src/`; shared fakes and the harness are in `test/helpers/`. Only `test/adapter/**` may import pi packages (Biome rule and architecture test).
19. **Allowed subagents.** The runner rejects any agent outside the caller's `subagents` list before starting anything; the main session may spawn every loaded agent.
20. **Model resolution.** The design note (`docs/design/agent-and-model-selection.md`) recommended exact `provider/id` only, with candidates on anything else. The user chose harness-side resolution instead: `run_agent` items take an optional `model` as `name[:thinking]` (the same form is the frontmatter `model`), and a pure resolver (`src/adapter/model-resolver.ts`) matches it against pi's catalog limited to providers with credentials: exact `provider/id` or id, then containment and word-order-free token matches, then Damerau-Levenshtein typo matches. Matches are grouped by model family (id without version numbers, regions and vendor prefixes); within one family the newest numeric version wins, then the main session's provider, then the user's `defaultProvider`, then the undated alias. Several families with similar scores return `ambiguous` with ranked candidates; nothing above the threshold returns `unknown` with "did you mean" suggestions, or the matching models whose providers have no credentials. Any such result rejects the whole batch before anything starts. pi's catalog has no release dates, so only version numbers are compared. The main session passes `model` only when the user explicitly named a model or thinking level; it never chooses one. The resolved `provider/id:thinking` is shown in the start message, the progress row, `agent_status` and the manifest.
21. **Adapter model bugs fixed.** A `provider/id` whose provider has no credentials is now rejected before the spawn (it used to fail on the first request), and a bare id shared by several providers follows the resolver's preference order instead of the first registry match.
22. **Thinking suffix parsing.** The last `:` starts a thinking suffix when the rest is a known level; an alphabetic suffix that is not a level is an error, a numeric one (Bedrock's `-v1:0`) stays part of the id. In a request an exact catalog id always wins, but the loader cannot see the catalog, so an agent file cannot name an id that ends in an alphabetic suffix such as OpenRouter's `:free` or `:batch`.
23. **General agent.** `agents/general.md` is a fallback (`fallback: true`, listed by `run_agent` in its own block "only when no agent above fits the work"), with every built-in tool, `openai/gpt-6.1-sol` and `subagents: [explorer, reviewer]`; the three role agents keep `subagents: []`.
24. **No `thinking` frontmatter field.** Plan: accept the community `thinking` field. Built: an agent file sets its thinking level only as the `model` suffix (`model: openai/gpt-6-luna:high`, or `inherit:high`); without a suffix the agent inherits the main session's level. A file that still has a `thinking` key is not loaded and the warning tells the author to move the level onto `model`, so files copied from other pi packages need that one edit. Other unknown keys are still ignored. The per-call `run_agent` `model` keeps the same `name[:thinking]` form.

## Release 0.2

25. **Successor chain (F9).** When a link closes with a valid handoff whose Status is `partial`, the runner starts a successor in the same batch slot without waking the caller, provided the link's `chainIndex` is below `maxChainLength` (new setting, default 3, 1 to 20), the agent was never stopped by the user (no `stop`, not in grace), the runner is not shutting down and the batch has not been woken. The successor gets the same agent, task, description, caller, depth, batch, budget, model and file-output mode, with `chainIndex + 1` and `predecessorId`. It is created and added to the batch before the predecessor closes, so the batch cannot wake on that close; the predecessor then closes as `handoff` with `successorId`, and both manifests carry the link. The successor's caller is the original caller, so closing the predecessor never stops it. Its task names the predecessor and its link number, tells it to read the predecessor's handoff file first and continue from its Next section, repeats the original task, and lists the handoff file first under Input files. It writes its own handoff to its own directory and the limits plugin tracks it as a new agent. "Same batch slot" means the same place in the batch, not the same concurrency slot: the successor acquires a semaphore slot like any new agent, so with the semaphore full it queues behind other waiters (it cannot deadlock, since waiting callers hold no slot). A message routed by the predecessor's id while that link is still in its handoff turn is steered into that link, not the successor; it reaches the successor only if the model carries it into the handoff's Next section.
26. **What each handoff status does (product call, not in the plan).** `done`: no successor; the link closes as `done` with the handoff text as its result, so the caller gets a normal result. `blocked`: no successor; the link closes as `handoff`, because another session cannot remove the blocker. `partial` at the chain cap closes as `handoff`, as before. A user stop, a grace period (even if a `partial` handoff is written during it), a reload or a shutdown never starts a successor. Now: `done` is no longer a handoff status (entry 48).
27. **One logical agent per chain.** The batch wake message and the batch's resolved records list only the last link of each chain, headed with its id, with a `Chain: <id1> → <id2> → <id3> (3 sessions)` line and totals over all links (tool calls and tokens summed, elapsed from the first start to the last end). `route`, `stop` and `abort` called with an earlier link's id act on the chain's last link, so `message_agent`, the view and the `run_agent` live row keep working with the id the caller knows. `agent_status` asked for an earlier link reports the last link's state and names both ids; called without ids it lists last links only. The `run_agent` description and the main session prompt describe the automatic continuation; the caller only handles `handoff` results that are blocked or hit the cap.
28. **Permission prompts from children (F14).** Pi's SDK runs a child's extensions with a no-op UI whose `confirm` answers `false`, so every confirmation inside a child used to be denied silently. The adapter now binds each child with its own `uiContext` (`bindExtensions({ uiContext })`): `confirm`, `select`, `input` and `notify` are forwarded to the main session's dialogs with the title `<id> (<agent>) asks: <title>`, everything else stays a no-op. While a dialog is pending the record carries `attention: { kind, title, since }`, shown as `needs input: <title>` in the progress widget, the list and the view header; `Esc` in the dialog answers `false` or `undefined` for that one call and the agent keeps running. A closed agent gets the denial without a dialog. If an agent closes while its dialog is open the dialog stays until the user answers and the answer is discarded. Pi has no permission system of its own; what is forwarded is whatever extensions loaded in the child ask through `ctx.ui`. Because the child now has a real `uiContext`, pi reports `hasUI` as true inside children, so extensions that branch on it use dialogs instead of their non-interactive path; `custom()` and `editor()` resolve to `undefined` at once. Pi's interactive mode has a single dialog slot and a second dialog replaces the first without resolving it, so child dialogs go through one FIFO queue shared by all agents and are shown one at a time.
29. **Message box in the agent view (F11).** The view opens with the first prompt section focused; `Tab` goes through the sections, then the message box (open agents only), then back. In the box every key edits the text, including `x`; `Enter` sends through the runner's route with sender `user` (steer while running, followUp in grace, held while queued) and clears the box; `Esc` clears the text, and on an empty box leaves it (the next `Esc` closes the view). A dim line under the box says how the message was delivered; a failed send shows the error in warning colour and puts the text back. Whitespace-only text is not sent. When the agent closes while the box is focused, the box disappears and the hint bar says messages are disabled. The header line carries `#N` for chain links, `continues <id>`, `continued by <id>` and `needs input: <title>`. `/agents <id>` follows the successor chain: when the opened agent handed off to a successor, the view shows the chain's live last link (header, state, transcript and session file), the message box and `x` stay available while that link is open, the hint bar says "opened <id>, following the chain", and the view refreshes on changes to any link. The message box shows pi-tui's cursor only while it has focus.
30. **Agent list view (F12).** `/agents` without an id opens the list overlay instead of pi's select dialog (the select dialog remains as a fallback when the list plugin is disabled). The list and the view reach each other through two services (`agentList.open()`, `agentView.open(id)`) rather than a second slash command, so a disabled plugin can never turn a dispatched command into a prompt. Summary line `Agents · N open · M total`, then groups Working (queued, running), Needs attention (grace, or open with `attention`), Done, Failed, Closed (stopped, handoff), newest first, empty groups left out, rows indented by depth with the grace countdown like the widget. The cursor stays on the same agent across refreshes and does not wrap; moving it scrolls to keep it visible, PgUp/PgDn/Home/End scroll without moving it. `X` stops every open agent after `y` confirms in the hint bar (running agents enter grace like a single `x`; a second `X` `y` closes them); with no open agents it only says so. The filter (`/`) matches name, id, state and group title, case-insensitive; `Enter` keeps it, `Esc` clears it, and `Esc` with an active filter clears before closing. The list redraws on `agent:changed` (throttled) and once a second while any agent is open. The widget header now says `/agents to browse`.
31. **Main session handoff location (F13).** The main session writes its handoff to `<session file without .jsonl>/main-handoff.md`, next to the `agents` directory; without a session file it goes under `<tmpdir>/pi-subagents/<session id>/`. The plugin creates the directory before sending the instruction. Now: the session-limits extension writes the file and creates the directory; the fallback is `<tmpdir>/pi-session-limits/<session id>/` (entries 38, 40).
32. **Main handoff template.** `prompts/main-handoff.md` keeps the six sections and validation of `prompts/handoff.md`, so the same validator applies, but the wording is for the orchestrator: Status is the state of the user's goal, Outcome holds the goal, the user's last request and the decisions taken, Evidence has one line per delegated agent with id, name, state and result file, Next starts with the answer the user is waiting for. The instruction tells the model to use its write tool, not to start or message agents, and to reply with one line. As with entry 11 it is sent as a user message (`sendUserMessage`, a followUp while busy) and tools are not restricted, so the cache is not broken; "written before any other tool call" is asked for in the prompt, not enforced. The main session prompt has a short section telling the model to comply and to read a seeded handoff at the start of the next session. Now: the template is `extensions/session-limits/prompts/handoff.md` and names no agents; the agent wording (no new agents or messages in that turn, one Evidence line per delegated agent) moved into the subagents main session prompt (entry 41).
33. **Switch waits for open agents.** Switching sessions closes every open agent as failed (run-agent handles `session_shutdown` with reason `new`), so the automatic switch waits until the registry has no open agents; the footer segment says "handoff waits for agents" meanwhile and the next idle or turn end performs the switch. Once the session has settled after an instruction, any further turn end counts as user activity (a batch wake counts too, since the old file does not hold those results); if there was any since the current file was written, the switch is not performed and one fresh request is sent instead (the existing file then counts as stale, the instruction count restarts at one so the single resend stays available, and the activity flag is cleared), and the switch happens on the next settle with the newer file, so at most one fresh request is sent per settle in which the user spoke. Results of agents that finished after the file was written are appended to the seed under "Agents that finished after the handoff was written" (id, agent, state, result path); predecessor links of a chain are left out. Running `/subagents-handoff` by hand while agents are open asks for confirmation instead. Now: the switch waits for every source reported busy on the `session-limits:busy` channel, to which subagents reports its open agents (entry 38); the "Agents that finished after the handoff was written" seed section is gone (entry 39), and the command is `/session-handoff`.
34. **Retry policy and the switch.** The file is judged when the main session settles; turn ends can trigger the switch but never count as a failure. A missing or invalid file gets exactly one resend with the validation errors appended; the second failure gives one warning naming the path, the segment stays red and no third instruction is sent. A file that existed before the request (same modification time) counts as missing, so a stale file from an earlier cancelled attempt cannot trigger a switch. The switch runs through the registered `/subagents-handoff` command, dispatched with `pi.sendUserMessage("/subagents-handoff", { expandPromptTemplates: true })`, which pi executes as a command without persisting a message; it is dispatched only when the session is idle, so in pi it always happens on `agent_settled`. The new session is linked with `parentSession` and seeded with a displayed custom message (`pi-subagents-main-handoff`, no turn triggered) that names the previous session file and carries the handoff text. If `newSession` is cancelled or throws, the user gets one warning, the segment stays red and no further automatic attempt is made; `/subagents-handoff` retries by hand. Whether pi fires `session_start` for the new session and keeps the extension working there has only been exercised through the fake host, not in a real pi session. Now: the command is `/session-handoff` and the custom type `pi-session-limits-handoff` (entry 40); the retry policy is unchanged.
35. **Footer colour.** `setStatus` takes text only, so the segment is coloured with pi's theme through a new `HostUi.style(token, text)`: warning (orange in the default theme) from the soft limit (`ctx 62% · handoff at 75%`), error (red) while a handoff is pending or stuck. Defaults are `mainSoftRatio` 0.6 and `mainHardRatio` 0.75 of the model's context window, both settings; they are validated individually, so a soft ratio above the hard ratio is accepted and simply skips the orange stage. Now: the segment key is `pi-session-limits` and the ratios are `softRatio`/`hardRatio` in the extension's own settings file (entries 40, 42); the session-limits extension has its own `style` in its own contract. Now: `style` is part of the shared `HostUi` in `core/adapter/contract.ts` (entry 46).
36. **Contract additions for 0.2.** `KeyPress.raw` carries the raw terminal data and `OverlayApi.createInput` wraps pi-tui's `Input` so views can edit text; `Host.onTurnEnd`, `contextUsage`, `dispatchCommand` and the `SessionControl` passed to command handlers (`newSession` with a seed) serve F13; `SpawnSpec.prompts` and `HostUi.confirm`/`input` serve F14. Adapter tests for the input pane and the child UI context live in `extensions/subagents/test/adapter/ui.test.ts`. Now: with F13 extracted into its own extension, the F13-only members of the subagents contract (`Host.onTurnEnd`, `contextUsage`, `dispatchCommand`, `SessionControl`/`NewSessionOptions`, the `control` parameter of `CommandSpec.run`) and `HostUi.style` were removed with the adapter refactor. Now: these members are back in the shared contract for session-limits, and the adapter tests live in `core/test/adapter/` (entries 45, 46).

## Review of 0.2

37. **One folder per extension.** The repository is now a single pi package with one folder per extension: `extensions/subagents/` and `extensions/session-limits/`, each with its own `src/`, `test/` (mirroring `src/`), `prompts/` and README. Inside an extension, `src/index.ts` is the one file outside `src/adapter` allowed to import `adapter/pi-adapter.ts` (to build the host and hand it to the boot code); everything else depends on the contract. Root keeps the shared tooling (`package.json` with every entry file under `pi.extensions`, `tsconfig.json`, `vitest.config.ts`, `biome.json`), `test/architecture.test.ts` with the repo-wide import rules (pi imports only in an extension's `src/adapter` and `test/adapter`, extensions never import each other), and the plan, docs and research. The package name stays `pi-subagents-mz`. Now: the package is `pi-extensions-mz` (entry 49). Now: the adapter and the manager are shared in `core/`; pi imports are allowed only in `core/adapter` and `core/test/adapter`, and each entry may import `core/adapter/pi-adapter.ts` (entry 45).
38. **Main session limits are their own extension (F13).** The product owner's rule: the extension that limits the main session knows nothing about agents except that something is running. F13 moved out of the subagents plugin set into `extensions/session-limits/`, with its own small contract and adapter. The two extensions talk only over pi's event bus, channel `session-limits:busy`, payload `{ source: string; busy: boolean }`. Session-limits keeps the set of sources whose last signal was busy, clears it at every session start, holds the automatic switch while the set is not empty, and has `/session-handoff` ask for confirmation naming the sources when run by hand meanwhile. Subagents' registry plugin publishes `{ source: "pi-subagents", busy }` whenever the number of open agents crosses between zero and non-zero, and its current state at session start. Because the old flow re-checked on the settle that followed an agent closing and a generic source may not wake the session, a release while idle runs the check after one second if no turn happened in between; a turn in between (such as a batch wake) counts as user activity as before. Now: session-limits uses the shared adapter and contract instead of its own (entry 46).
39. **No late agents in the seed.** The seed no longer lists agents that finished after the handoff was written, since session-limits cannot know about agents. A batch wake after the file was written still counts as activity and triggers a fresh handoff, so the results normally reach the new file; results that arrive after the switch are only in the old session and in the agents' result files.
40. **Renamed identifiers.** Command `/subagents-handoff` became `/session-handoff`; footer key `pi-subagents-context` became `pi-session-limits`; custom message type `pi-subagents-main-handoff` became `pi-session-limits-handoff`; the stuck label says `handoff failed, run /session-handoff`; the waiting label `handoff waits for agents` became `handoff waits for running work`; the tmpdir fallback moved from `pi-subagents/` to `pi-session-limits/`. The handoff file name `main-handoff.md` next to the session file is unchanged.
41. **Agent-neutral handoff template.** `extensions/session-limits/prompts/handoff.md` (formerly `prompts/main-handoff.md` of subagents) keeps the six sections and the Status values, validated by a copy of the six-section validator in `src/handoff.ts`, but says "do not start new work in this turn; work already running in the background keeps running and the switch waits for it" and asks Evidence for delegated or background work with where its results land. The agent-specific guidance moved into "Your own context" of the subagents `prompts/main-session.md`: no new agents or messages in that turn, one Evidence bullet per delegated agent with id, agent name, state and result file path, running agents keep running.
42. **Own settings file.** `mainSoftRatio`/`mainHardRatio` left the subagents settings. Session-limits reads `softRatio` (0.6) and `hardRatio` (0.75) from `~/.pi/agent/pi-session-limits.json` and, in trusted projects, `.pi/pi-session-limits.json` (project wins), again at every session start. Values must be numbers above 0 and at most 1 (the old lower bound of 0.1 is gone); each invalid value is reported once per pi process as a warning and ignored. Old keys in `pi-subagents.json` are ignored silently.
43. **Session-limits only in conversational modes.** Subagents filters only its own sources out of child sessions, so child sessions load session-limits like any other installed extension. Children are bound in pi's `print` mode, so session-limits acts only when `ctx.mode` is `tui` or `rpc`; in print and JSON runs, and in agents, it registers its command but ignores every event. Now: the guard lives in `extensions/session-limits/src/conversation.ts` and reads `SessionInfo.mode` (entry 46).
44. **Session-limits fix round.** The release timer is kept and cleared at session start, on pi's `session_shutdown` (new `Host.onShutdown` in the session-limits contract) and when a source turns busy again, and the adapter's `isIdle` is false without a live context, so a timer left over from a previous runtime cannot act. When the automatic switch is not carried out because the user declines the confirmation (a source turned busy between dispatch and the command running), the phase goes back from `switching` to `waiting` and the footer is refreshed; the release then switches as usual. The busy sources are no longer cleared at session start (superseding that part of entry 38): pi creates a new extension instance per runtime, so the set is already empty, and clearing it dropped a `busy: true` announced in the `session_start` of an extension listed earlier. The test fake host now defers a command dispatched during `settle()` until every settle handler has run, as pi does after `agent_settled`, so the dispatch window is reproducible. Subagents' `publish` returns early without a live context, since `pi.events.emit` throws after pi invalidates the runtime; its busy signal is now covered through the run-agent harness (shutdown, stop, chain successor) in `test/plugins/agent-registry/agent-registry.test.ts`. Now: `onShutdown` is the shared `Host.onSessionShutdown`, the shared adapter keeps the `isIdle`, `publish` and shutdown-order fixes for both extensions, and the deferring fake host is `core/test/helpers/fakes.ts` (entries 45, 46).

## Shared core

45. **Shared core.** The product owner's rule: the pi adapter and the extension manager are shared infrastructure that knows nothing about any extension. Both moved to `core/` at the repository root: `core/adapter/` (contract, pi adapter, scope, UI, tools, models, child sessions, main prompt, model resolver, route, session file, usage; still the only code importing `@earendil-works/*` and `typebox`) and `core/manager/` (`createExtensionManager<Events, Services, Settings>`, `Plugin<Events, Services, Settings>`, a bus generic over an event map, generic settings helpers that read a JSON file, validate it against a schema of `{ type: "number", min, max, minExclusive? } | { type: "list", of }` rules and apply a patch, and `sessionDataDir(info, namespace)`). Everything extension-specific is passed in by the extension's entry point: `createPiExtension(boot, { root, namespace, childExclude })` takes the extension's folder (handed to boot as `paths.root`, replacing the adapter's `PACKAGE_ROOT`), a namespace for what the adapter writes (the child prompt record entry `<namespace>:prompt-record` and the hidden child extension `<namespace>-child`; subagents passes `pi-subagents`, so existing session files still read) and the source directories child sessions must not load (subagents passes its own `src`). The manager takes the plugin list, the settings object, the root and the disabled plugin ids. Subagents keeps one entry, `src/index.ts`, with its plugin list in `src/plugins.ts` next to it; its types, bus events, service map, settings schema and defaults and paths moved from `src/manager/` to `src/model/`. Tests: `core/test/` mirrors `core/` (adapter and manager tests plus `helpers/fakes.ts`, the fake host, runtime and child used by both extensions); subagents keeps its plugin and component tests and `test/helpers/harness.ts`. The shared `isIdle` is now false without a live context for subagents too, so a result posted to the main session while no context is live is held until the next idle instead of being sent into a stale session. `test/architecture.test.ts` enforces: (a) only `core/adapter/**` imports pi packages (runtime code in `core/` and every extension's `src/`; `scripts/spike.ts` is a dev tool and may); (b) among tests only `core/test/adapter/**` imports pi packages; (c) outside `core/adapter` the only adapter module imported is `contract.ts`, except each extension's `src/index.ts`, which may import `pi-adapter.ts`, and tests, which may import any adapter module; (d) plugins never import another plugin's code; (e) extensions never import each other; (f) `core/` never imports from `extensions/`; (g) no `.test.ts` under any `src/` or under `core/adapter` and `core/manager`. Side-effect imports (`import "x"`) are now checked too. `package.json` ships `core/adapter` and `core/manager` with the extensions. pi loads every extension entry through its own jiti instance without a module cache, so each extension gets its own copy of `core/adapter`; the child-session scope in `pi-scope.ts` therefore lives on `globalThis` under `Symbol.for("pi-extensions.child-scope")`, so the guard that keeps spending and session limits out of child sessions sees the scope subagents runs its children in.
46. **Session-limits on the shared adapter.** Session-limits dropped its private `src/adapter/` and builds on `core/adapter`. The shared contract got back the members it needs: `Host.onTurnEnd(handler(context))` (pi's `turn_end`, with the context snapshot), `contextUsage()`, `dispatchCommand(name, args?)` (sent as `/name args` with `expandPromptTemplates`), command handlers receiving a `SessionControl` whose `newSession({ parentSession, seed: { customType, text } })` seeds the new session with a displayed custom message that triggers no turn, `HostUi.style(token, text)`, `subscribe(channel, handler)` on pi's event bus next to `publish`, and `SessionInfo.mode` (`tui`, `rpc`, `print`, `json`). Its `onShutdown` became the shared `onSessionShutdown`, whose handlers run before the context goes stale. Its logic stays standalone: `src/limits.ts`, `thresholds.ts`, `handoff.ts` and `settings.ts` are unchanged apart from the contract shape (`host.ui.notify`/`setStatus`/`style`/`confirm`), the settings reader uses the core helpers with its own schema (same messages), and the handoff path uses `sessionDataDir` (same paths). The "only in conversational modes" guard moved from its adapter into its own `src/conversation.ts`, a host wrapper that drops session start, turn end, idle and command calls outside `tui`/`rpc` and reports such sessions as not idle and without session info. As before, child sessions load session-limits like any other installed extension (only the source directories an entry passes as `childExclude` are filtered out), and this guard keeps it inactive there because children run in `print` mode.

## Second review round

47. **Spending as its own extension.** Session spending totals moved out of subagents into a standalone `extensions/spending/` extension that knows nothing about agents. Subagents' `spending` plugin, its `ledger` service, the `spend:changed` event and the `pi-subagents:spend` / `pi-subagents:delivered` entries are gone. A new `usage-report` plugin (requires `run-agent`) turns each `agent:usage` bus event into a publish on pi's event channel `spending:usage` with `{ source: "agents", id, usage }`. It fires for every agent at every depth, under the id `<runtime token>/<agent id>`, and only when the usage is ahead of what it last published for that agent. The runtime token is the session start time in base36, taken on every session start, so an agent whose short id repeats one from an earlier runtime of the same session (agent ids carry only 2 random bytes, and a resumed session restores the earlier figures) is not mistaken for it; the agent ids users see stay short. Channel protocol: `source` is a short non-empty display label of the reporting extension; `id` is unique within the source across every runtime of the session; `usage` is the absolute high-water `UsageTotals` for that id. Reports are idempotent (the highest per source/id is kept) and malformed payloads are ignored. The spending extension shows `main $x · <source> $y … · total $z` (`(sub)` suffix, hidden while every source total is zero), where main is pi's own session usage. It persists changed figures as `pi-spending:usage` custom entries on idle and on shutdown and restores them on session start. The delivered-usage channel is removed: `run_agent`, `message_agent` and `agent_status` results no longer carry `usage`, and `ToolResult.usage` and `subtractUsage` are gone from the core contract. As a result pi's own session cost shows the main session only; the total including agents is in the spending footer.
48. **Limits act only on continuing turns, and handoffs have no `done` status** (amends entries 11 and 26). `agent:turn` now carries `continuing: boolean`. It is true when the turn's last assistant message had tool calls and its stop reason is neither `error` nor `aborted`, taken from the child's `assistant_message` event (which carries `toolCalls`, the number of tool calls in the message, and arrives before `turn_end`). This follows pi's loop, which continues after a `length` stop that contains tool calls; the stop reason alone (`toolUse`) would miss that case. The limits plugin warns, requests the handoff, aborts past the hard line after a handoff, and applies the turn-limit warning and abort only on continuing turns. A turn that ends with the final answer is left alone even when it crosses a line, so the agent closes as `done` and is never asked to write a handoff after finishing. The abort rules still apply to an agent that got the handoff instruction and keeps working with tool calls. Because a handoff is written only by an agent that is still working, its Status is `partial` or `blocked`; `done` is rejected as invalid. A handoff file that exists but fails validation (a `done` status included) still closes the agent as `handoff`, never `failed`, with the validation errors on the record and in its result section (`Handoff file: <path> (invalid: <reasons>)`), so the caller can read what the agent wrote; such a link never starts a successor. Only a missing file closes the agent as `failed`. `partial` continues the chain, or closes as `handoff` at `maxChainLength` or when the chain cannot continue. `blocked` closes as `handoff`. The old rule that closed a `done` handoff as a `done` result is removed. The main session handoff in session-limits keeps `done`, because there it describes the user's goal.
49. **Package rename.** The package is `pi-extensions-mz`, since it ships three extensions (subagents, session-limits, spending) and `pi-extensions` without a suffix would collide with the repository's generic name on npm. Install commands in the READMEs use the new name; the git install URL is unchanged.
50. **MCP tools per agent (planned).** The product owner wants each agent to see only the MCP tools it may use. Pi names MCP tools `mcp__<server>__<tool>` and a child session's `tools` list filters them by `mcp__` entries. Planned as F20 in PLAN.md for a later release: an `mcp` frontmatter field, empty by default, validated by the loader and frozen into the child's tool list at spawn.
