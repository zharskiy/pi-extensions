# Agent roles, utility agents and skills: research notes

## Scope and method

These notes test five proposals for the subagents extension against current practice: renaming the shipped agents, adding small utility agents (fetch, shell, image), letting expensive agents spawn cheap scouts, and letting the orchestrator pass skills at call time. Research was done on 2026-10-16. It combined web sources (vendor docs, changelogs, engineering posts, arXiv papers from 2025 and 2026) with a reading of the installed host package `node_modules/@earendil-works/pi-coding-agent` v1.3.0 and of this repo's own code.

Most vendor documentation pages carry no publication date. Those are marked "undated, fetched 2026-10-16", which means they describe behaviour current on that date. A claim is marked "unverified" when it came from a search snippet or a secondary write-up and could not be checked at its source.

## Q1. Skill propagation

Findings, Claude Code:

- Create custom subagents, https://code.claude.com/docs/en/sub-agents, undated, fetched 2026-10-16 (references v2.1.296). The subagent `skills` field preloads skills: "The full skill content is injected, not only the description." It does not restrict them: "This field controls which skills are preloaded, not which skills the subagent can access". The subagent can still discover and invoke any project, user or plugin skill through the Skill tool. To block skills you remove `Skill` from `tools`. Built-in agents preload nothing, and a subagent does not see "the skills you've already invoked" in the parent. Implication for this repo: Claude Code separates "preload" from "may use", while our `skills` field is an access filter with no preload. These are two separate features, and a redesign should name them separately.
- Claude Code CHANGELOG, https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md, v2.1.295 (2026, exact date not shown): "Changed subagents to preload at most 32 skills from the `skills` field, each once". Implication for this repo: even static preloading needed a cap, because each preloaded skill costs its full body in tokens on every run.
- Skills, https://code.claude.com/docs/en/skills, undated, fetched 2026-10-16. Setting `context: fork` plus `agent: <type>` in a skill's own frontmatter runs that skill inside a fresh subagent of the named type, with SKILL.md as the task. A v2.1.218 change (about 2026-07, unverified date) runs these in the background by default. Implication for this repo: Claude Code inverts the direction, so the skill picks its agent and not the reverse. That is a third design option.
- No Agent or Task tool parameter for passing skills at invocation exists in Claude Code as of 2026-10. The Agent tool gained `effort` (v2.1.292) and per-call `model`, but not `skills`. Agent teams ignore a definition's `skills` entirely (https://code.claude.com/docs/en/agent-teams, undated). Implication for this repo: a call-time `skills` parameter would go further than the reference tool. That is not a reason to refuse it, but there is no field experience to borrow.

Findings, pi (local package, verified):

- pi docs/skills.md, in node_modules/@earendil-works/pi-coding-agent, v1.3.0. pi discovers SKILL.md directories under `~/.pi/agent/skills`, `.pi/skills`, `~/.agents/skills` and `.agents/skills` (ancestors up to the repo root), plus the `skills` settings key and packages. Only name, description and path enter the system prompt, and the model reads the body on demand with `read`. `/skill:name` forces a skill, and `disable-model-invocation: true` hides a skill from the model. Implication for this repo: in pi, making a skill "available" costs only one line of prompt, so allowing more skills is cheap. Preloading the body would be a new behaviour the extension has to add, through `promptAppend`.
- pi dist/core/resource-loader.d.ts lines 76-90, v1.3.0. `DefaultResourceLoaderOptions` has `additionalSkillPaths?: string[]`, `noSkills?: boolean` and `skillsOverride?: (base) => {skills, diagnostics}`. Implication for this repo: the SDK already lets a child session be built with an exact skill list, so a call-time list needs no host change.
- This repo, core/adapter/pi-child.ts lines 138-139 and 190-204. Today the child is built with `noSkills: true`. `additionalSkillPaths` is set to the parent's discovered skill files, filtered by `spec.skills`, and a `skillsOverride` applies the same filter. `spec.skills` comes from `allowlist(definition.skills)` in extensions/subagents/src/plugins/run-agent/runner.ts:595. Implication for this repo: a call-time list only has to be intersected with the definition's grant before it reaches `spec.skills`. The child can never get a skill the parent did not discover. That is a useful safety property and should be kept.

Findings, other systems:

- Codex subagents, https://developers.openai.com/codex/subagents.md, undated, fetched 2026-10-16. Custom agents are TOML files with `name`, `description`, `developer_instructions` and an optional `model`. Skills are inherited from the parent, and an agent can only switch them off (`skills.config`, `skills.bundled.enabled=false`). There is no per-call skill parameter. Implication for this repo: "inherit everything, opt out per agent" is the simplest model in the field.
- OpenCode skills, https://opencode.ai/docs/skills/, undated, fetched 2026-10-16. Skills are listed in the `skill` tool's description and loaded on demand. Each agent controls them with `permission: skill:` glob rules (allow, ask, deny). Implication for this repo: a glob allowlist in agent config is the established form for a static grant.
- Cursor subagents, https://cursor.com/docs/agent/subagents, undated, and Gemini CLI subagents and skills, https://geminicli.com/docs/core/subagents/ and https://geminicli.com/docs/cli/skills/, undated. Neither documents how skills reach subagents. Gemini loads skills through an `activate_skill` tool after the user consents. Implication for this repo: no vendor offers an orchestrator-chosen skill set to copy.
- Agent Skills specification, https://agentskills.io/specification, undated, fetched 2026-10-16. It defines `name`, `description`, `license`, `compatibility`, `metadata` and an experimental `allowed-tools`. It recommends three-tier progressive disclosure (about 100 tokens of metadata, body under 5000 tokens, resources on demand). It says nothing about agents, subagents or inheritance. Implication for this repo: the choice is ours. The spec's `compatibility` and `metadata` fields could carry a hint such as which agent a skill suits, without breaking portability.

Recommendation for Q1. Do both, in a bounded way. The definition's `skills` stays the static grant, the ceiling of what the agent may ever see, as a list of names or globs. `run_agent` takes an optional `skills` parameter that can only narrow the grant or preload a subset of it, never widen it. That keeps an agent author's guarantees while letting the orchestrator point the child at the right method ("use the tdd skill") for this call. Keep "listed" (pi's default, cheap) separate from "preloaded" (body injected, costly). Offer preload as an explicit frontmatter field, capped like Claude Code's 32.

Risks:

- Prompt-injection surface. Every skill body is instructions that the child follows with its own tools. A call-time parameter lets a compromised or confused parent turn on a skill the agent's author never reviewed with that agent's toolset. The grant ceiling is the mitigation.
- Cost. A preloaded body is paid on every run, and with prompt caching only on later turns of that run. Listing costs about one line per skill. Prefer listing and use preload rarely.
- Weak orchestrator. A small parent model may pick skills by surface keywords, as ToolTweak (Q3) shows for tools. Make the parameter optional, have the extension validate names against the grant, return an error that lists the valid names, and fall back to the definition's own list when the parameter is omitted.
- Silent mismatch. A name that resolves to nothing must fail loudly, not run without the skill.

## Q2. Utility agents versus tools

Findings:

- Claude Code tools reference, "WebFetch tool behavior", https://code.claude.com/docs/en/tools-reference, undated, fetched 2026-10-16. "It fetches the page and converts the response to Markdown... runs the prompt against the content in a separate model call, and Claude receives the result of that call rather than the raw page". The doc calls this "lossy by design". Implication for this repo: the market leader made fetch a tool with a hidden second model call, not an agent. A pi `fetch` agent would copy this pattern, with turns, which allows following links.
- Gemini CLI web_fetch, https://geminicli.com/docs/tools/web-fetch/, undated, fetched 2026-10-16. It takes a prompt with up to 20 URLs and returns a synthesised answer with attribution. It falls back to a raw fetch on failure. Implication for this repo: a prompt-plus-URLs input and a synthesised, cited answer is the common contract.
- Claude Code sub-agents docs, as above. Built-ins are Explore (read-only search, with quick, medium and very thorough levels), Plan, general-purpose, claude-code-guide (Haiku) and statusline-setup (Sonnet). "The parent doesn't see the subagent's intermediate tool calls or outputs, only that final result". The docs also warn: "Latency matters. A subagent that isn't a fork starts fresh and may need time to gather context." The Explore model is now documented as inheriting the main model, though older material said Haiku (unverified which applies today). Implication for this repo: built-in utility agents in the leading CLI are organised by job (search, plan), not by medium. No vendor ships a dedicated shell or image agent.
- Codex built-ins `default`, `worker` and `explorer`; Cursor built-ins `Explore` (faster model) and `Browser`; Gemini built-ins `codebase_investigator`, `cli_help`, `generalist` and `browser_agent`; OpenCode built-ins `General`, `Explore` and `Scout` ("external docs and dependency research"). Sources: https://developers.openai.com/codex/subagents.md, https://cursor.com/docs/agent/subagents, https://geminicli.com/docs/core/subagents/, https://opencode.ai/docs/agents/, all undated, fetched 2026-10-16. Implication for this repo: a web or browser agent has precedent (Cursor Browser, Gemini browser_agent, OpenCode Scout). A shell digest agent and an image agent do not.
- pi example extension examples/extensions/subagent in the host package, v1.3.0. pi ships no built-in task tool, only this example, which runs each agent as a separate `pi` process with single, parallel and chain modes. Implication for this repo: this extension is pi's de facto delegation layer, so its utility agents set the convention.
- Anthropic, "How we built our multi-agent research system", https://www.anthropic.com/engineering/multi-agent-research-system, 2025-06-13. Multi-agent runs used about 15x the tokens of chat. Subagents return condensed findings, and large artefacts go to the filesystem with only "lightweight references" passed back. Implication for this repo: a utility agent pays off when its input is much larger than its answer. It loses when the answer is the input (a short command's exit code, a small file).
- Cognition, "Don't Build Multi-Agents", https://cognition.com/blog/dont-build-multi-agents, 2025-06-12. "Actions carry implicit decisions, and conflicting decisions carry bad results". It accepts subagents that answer a well-defined question. Implication for this repo: read-only, question-answering utility agents are the safe kind. A `shell` agent that mutates state is the risky kind.

When an agent beats a tool: the raw output is large and mostly noise (web pages, build or test logs, big images), the job needs several steps (follow links, rerun with flags), and the parent can state the question up front. A tool wins when the output is small, when the parent needs it verbatim, or when the round-trip latency of a fresh session (seconds plus a cold context) matters more than the parent's context.

What each should return, and on which tier:

- fetch: an answer to the question asked, with quoted extracts, source URLs and a fetch date, and a note when a page failed or was truncated. Cheap tier. This is summarisation.
- shell: the exit status, the command actually run, a short digest (the failing tests, the first error with file and line), and a path to the full log saved under the session dir so the parent can read it verbatim if needed. Cheap tier, read-only by intent. Anything that changes the tree belongs to the implementer.
- image: a description scoped to the parent's question (text transcription, UI state, chart values), with stated uncertainty. It needs a vision-capable model at the cheapest tier that has one. Mid tier if fine detail matters.

## Q3. Naming and routing

Findings:

- Built-in names across systems (sources as in Q2). They are role nouns or adjectives: Explore, Plan, general-purpose (Claude Code); explorer, worker, default (Codex); Explore, Browser (Cursor); codebase_investigator, generalist, browser_agent (Gemini); Build, Plan, General, Explore, Scout (OpenCode). Implication for this repo: "scout" has direct precedent in OpenCode, though there it means external research, not the codebase. "check" and "edit" as agent names have none. In most hosts "edit" is the name of a file-editing tool, which invites confusion.
- Anthropic, "Writing effective tools for agents — with agents", https://www.anthropic.com/engineering/writing-tools-for-agents, 2025-09-11. It advises namespacing by shared prefix, reports that prefix versus suffix choice had "non-trivial effects on our tool-use evaluations", and calls for writing descriptions as if onboarding a teammate. Small description refinements gave large gains. Implication for this repo: the description carries most of the routing weight. Names matter at the margin and should be tested, not argued.
- Claude Code sub-agents docs, as above. "Claude uses each subagent's description to decide when to delegate tasks". "include phrases like 'use proactively'" to encourage delegation. Combined descriptions have a 15,000-token budget, with a "Keep descriptions brief" warning. Implication for this repo: put "use when..." trigger wording in the descriptions. Do not rely on the name.
- "Don't Adapt Small Language Models for Tools; Adapt Tool Schemas to the Models", https://arxiv.org/abs/2510.07248, 2025-10-08 (v3 2026-04-19, ACL 2026). Small models invent tool names absent from the schema. Renaming tools to names the model finds familiar gave up to +17% on MetaTool and RoTBench and cut misalignment errors by 80%. Implication for this repo: for weak orchestrators, familiar and conventional names (explorer, reviewer) beat novel short verbs, because those are the names models have seen.
- "Which Metadata Matters for LLM Tool Selection in MCP?", https://arxiv.org/abs/2610.14334, 2026-10-09. A controlled single-factor study across 5 LLMs found that parameter schemas and parameter-explaining descriptions shift selection most. Name effects were weaker and inconsistent. Implication for this repo: the effect of renaming is probably small either way. Spend the effort on descriptions.
- "ToolTweak: An Attack on Tool Selection in LLM-based Agents", https://arxiv.org/abs/2510.02554, 2025-10. Rewriting only a tool's name and description raised its selection rate from about 20% to as high as 81%. Implication for this repo: wording does steer routing. It also means one over-eager description (for example "use proactively for everything") can starve the other agents.
- OSWorld-MCP, https://arxiv.org/abs/2510.24563, 2025-10, and Chain-of-Tools, https://arxiv.org/abs/2503.16779, 2025. Accuracy falls as the tool count rises, and similar tools get confused. Implication for this repo: adding fetch, shell and image raises the agent count from 4 to 7. The descriptions must not overlap. For example, scout is the codebase and fetch is the web, and each says so.

Verdict on renaming. explorer→scout is harmless and has precedent. reviewer→check is weaker: "check" overlaps with `npm run check`, with shell's purpose, and with every "check X" in user prose. Prefer "review" if a verb is wanted. implementer→edit is not worthwhile: it collides with the ubiquitous `edit` tool name, so a weak orchestrator may call or describe the wrong thing, and no evidence suggests a rename improves routing. A rename also breaks users' muscle memory and any saved agent overrides for no measured gain. If short names are wanted, keep the old names as aliases, and measure routing with the live tests before and after.

## Q4. Nested cheap scouts under expensive leads

Findings:

- Claude Code sub-agents docs, as above. "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation". `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` tunes this, and `1` disables nesting. At the limit the `Agent` tool is withheld. Concurrency is capped at 20 (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`). The `Agent(worker, researcher)` allowlist in `tools` "applies only to an agent running as the main thread"; inside a subagent definition "any type list inside the parentheses is ignored". Implication for this repo: depth limits and tool withholding are the proven bound. The per-agent child allowlist is a gap even in Claude Code, which is room to do better.
- Claude Code agent teams, https://code.claude.com/docs/en/agent-teams, undated. These are experimental, and "teammates cannot spawn their own teammates". Implication for this repo: peer teams are a different feature and out of scope here.
- Codex subagents (search-derived, unverified on the fetched page). `agents.max_depth` defaults to 1 with the root at depth 0, so a direct child may spawn but deeper nesting is blocked. `agents.max_threads` defaults to 6. The docs warn that raising depth causes repeated fan-out. Implication for this repo: depth 1 below the lead (orchestrator → reviewer → scout) is the conservative industry default.
- Cursor subagents, https://cursor.com/docs/agent/subagents, undated. Since Cursor 2.5, direct subagents may launch subagents but grandchildren may not, which gives an effective depth of 2. Gemini CLI forbids nesting entirely. Implication for this repo: everyone caps depth, and most at 2 levels below the user.
- OpenCode agents, https://opencode.ai/docs/agents/, undated. `permission.task` is a glob allowlist of the subagents an agent may call, the last match wins, and `deny` hides the subagent from the Task tool description. Implication for this repo: this is the cleanest precedent for the allowed child set, as a frontmatter-level grant mirroring how `skills` and `tools` are granted here.
- OpenAI Agents SDK, agents as tools, https://openai.github.io/openai-agents-python/tools/, undated. `agent.as_tool()` with `max_turns`, `is_enabled` and `custom_output_extractor`, where the parent receives only the child's final output (or whatever the extractor returns). The parent's conversation is "not inherited automatically". Implication for this repo: a typed extractor or result shape is a good model for what a scout hands back.
- Google ADK. `sub_agents` trees with description-driven `transfer_to_agent`, and `AgentTool` for call-and-return. This comes from prior knowledge, since the docs at adk.dev could not be fetched (unverified). Implication for this repo: this repo's run_agent is the AgentTool pattern, and nesting fits it naturally.
- Anthropic research system, as above, 2025-06-13. An Opus lead with Sonnet workers beat single-agent Opus by 90.2% on their eval at about 15x tokens. Effort rules in the prompt: 1 agent for simple facts, 2-4 for comparisons, more than 10 for complex research. Implication for this repo: expensive-lead and cheap-worker is the validated shape, but the lead needs explicit effort-scaling guidance or it over-spawns.

Pattern for this repo. Add an `agents` grant to frontmatter (names or globs, default none), in the same shape as `skills` and `tools`. Only agents that hold a grant get run_agent in their child session, listing only the granted children. Enforce a global depth cap, default 2 levels below the user, so the main session's agent may spawn one more level. Withhold the tool at the cap. Count child cost and turns into the parent's run so the existing usage figures and any budget see the full tree. Children return final text only, the same as today.

## Q5. Image handling

Findings:

- pi dist/core/tools/read.js lines 36-53 and docs/models.md lines 71-90, v1.3.0 (verified). `read` returns jpg, png, gif, webp and bmp as an image content block plus a text note. If the model's `input` lacks `image`, the note says "[Current model does not support images. The image will be omitted from this request.]". Images are auto-resized by default (2000x2000, 4.5 MiB base64, JPEG quality 80, with per-model profiles), once, when stored. `images.blockImages` stops images being sent. Implication for this repo: a non-vision parent already reads images silently as nothing. An image agent pinned to a vision model is the only way such a parent can learn what an image shows.
- pi agent-session.d.ts:181 and CHANGELOG, v1.3.0. `PromptOptions.images?: ImageContent[]`, `steer(text, images?)`, `followUp(text, images?)` and `sendUserMessage` with image parts. Resized images are not rewritten when the model switches. Implication for this repo: run_agent could pass image paths and the child could attach them to its first prompt, so the child needs no extra `read` turn.
- Claude Code tools reference, "Read tool behavior", undated, fetched 2026-10-16. Images are returned "as visual content", large ones are resized and re-encoded, and the docs suggest cropping with ImageMagick when detail is lost. There is no documented image subagent. Implication for this repo: a dedicated image agent is new ground but follows naturally from "subagent reads, parent gets text".
- Codex CLI reference, https://developers.openai.com/codex/cli/reference, undated. Images attach with `-i/--image`, and a `view_image` tool is mentioned (third-party, 2026-03-28). Cursor, Gemini and OpenCode docs fetched do not describe image delegation. Implication for this repo: no vendor delegates image analysis to a separate model. The justification rests on local needs: a non-vision or text-only cheap parent, many or large screenshots polluting an expensive context, and pi's catalog-only per-request image limits.

Verdict: an image agent is sensible as a narrow, read-only agent whose definition pins a vision-capable model. It earns its place when the parent lacks vision, or when there are several images or large ones. When the parent has vision and needs one small image, the plain `read` tool is better.

## Recommendations

Ranked by value for effort.

1. Keep the definition's `skills` as the static ceiling and add an optional `skills` parameter to run_agent that can only narrow it. The SDK and pi-child.ts already filter by name, so this costs one intersection and a validation error, and it keeps the agent author's safety guarantee.
2. Add an `agents` grant in frontmatter, with a global depth cap of 2 and child cost rolled up into the parent. This is the OpenCode `permission.task` shape, closes the gap Claude Code leaves inside subagent definitions, and makes cheap scouts under opus-class leads safe.
3. Rewrite every shipped agent description with "use when..." triggers and explicit non-overlap lines before renaming anything. Studies and Anthropic's own guidance put most routing weight on descriptions, and the agent count is about to grow.
4. Add `fetch` as a cheap read-only agent returning an answer with cited extracts. It has the strongest precedent (WebFetch, Gemini web_fetch, OpenCode Scout, Cursor Browser) and the best ratio of input size to answer size.
5. Add `image` as a read-only agent pinned to a cheap vision model. pi drops images for non-vision models, so this is the only route for such parents.
6. Add `shell` only as a read-only "run and digest" agent that saves the full log under the session dir and returns status plus digest. It has no vendor precedent, and Cognition's warning applies if it mutates state.
7. Rename explorer→scout if desired, keep reviewer (or use "review", not "check"), and do not rename implementer→edit. Any rename should ship with aliases and a before-and-after live routing check.
8. Consider an explicit `preload` frontmatter list, capped, separate from the grant. This copies Claude Code's useful split, but costs tokens on every run, so it should be opt-in.

## Open questions

- Should a call-time `skills` list be allowed to name a skill outside the grant when the user, not the model, asked for it (for example via `/skill:name` in the parent)?
- Does Claude Code's Explore run on Haiku or on the inherited model in late 2026? The docs and older material disagree, and it decides whether "scout" should default to the cheap tier.
- Codex `max_depth` and `max_threads` defaults came from search snippets. They need confirming on the official page before being cited as the norm.
- Is the shell agent's digest trustworthy enough that the parent will not re-run the command anyway? If not, it only adds latency. A live test with a failing build would settle this.
- Should the image agent accept image paths in run_agent and attach them via `PromptOptions.images`, or read them itself? The first saves a turn but needs a new parameter.
- How should a nested child's usage show in the parent's progress UI and in session-limit handoffs?
