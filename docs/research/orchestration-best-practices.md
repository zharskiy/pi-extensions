# Orchestration best practices for the subagents extension

## Scope and method

This note checks the owner's redesign idea against published practice as of 2026-10-16. The idea: a cheap, weak main session that only delegates; expensive role agents (implementer, reviewer) that spawn cheap scouts for exploration; code writing treated as cheap compared with exploration. Four questions are covered: weak-model orchestration, nested delegation, data flow and token reduction, and prompt design. Sources are vendor engineering posts and docs (Anthropic, OpenAI, Google, Cursor, Gemini CLI, OpenCode, Roo Code), practitioner posts (Cognition, Manus, LangChain) and papers (MAST, ToolOrchestra, RouteLLM, Mixture-of-Agents). Research agents fetched most pages in October 2026; a few figures come only from search excerpts or secondary coverage and are marked "(secondary)". Many docs pages carry no date; for those the fetch month is given. The current repo state used for the implications: `run_agent` with batches, `maxDepth` default 3, results inlined up to `inlineResultChars` 4000 and otherwise kept in `result.md`, a main-session prompt of about 1,330 words, and only `general` allowed to spawn (explorer and reviewer).

## Q1. Weak-model orchestrator

- Anthropic, "How we built our multi-agent research system", https://www.anthropic.com/engineering/multi-agent-research-system, 2025-06-13. The lead was Opus 4 with Sonnet 4 workers, the reverse of the proposal, and it beat single-agent Opus 4 by 90.2%. Multi-agent runs used about 15x the tokens of chat, and token use explained about 80% of the performance variance. Early failures were orchestration failures: 50 subagents for a simple query, duplicated subtopics, vague briefs. Implication for this repo: the published success case puts the strongest model where the decisions are, so a weak orchestrator needs its decisions removed, not merely reduced.
- Cognition, "Multi-Agents: What's Actually Working", https://cognition.com/blog/multi-agents-working, 2026-04-22. In their "Smart Friend" setup a fast, weak primary model calling a stronger model did not work well, because the weak model cannot tell when it is out of its depth. A strong primary gained on the hardest cases. Manager-child delegation failed through over-prescriptive instructions, assumed shared state, and children that did not report back. Writes should stay single-threaded; extra agents should add intelligence (review, planning, advice), not parallel actions. Implication: the riskiest judgement for a weak main session is "is this hard, and who should take it"; make that a fixed rule, not a model judgement.
- Cognition, "Don't Build Multi-Agents", https://cognition.com/blog/dont-build-multi-agents, 2025-06-12 (read via excerpts). Share full context or traces, not just messages; parallel agents make implicit, conflicting decisions. Implication: the brief is the only context an agent gets, so the weak orchestrator's brief quality caps the whole system.
- Anthropic, advisor tool docs, https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool, 2026 (beta `advisor-tool-2026-03-01`). The supported cheap/strong split is the inverse of the proposal: a cheap executor does the work and consults a stronger, tool-less advisor a few times (`max_uses`, `max_tokens`; advice is typically 400-700 tokens). Reported (secondary, https://claude.com/resources/articles/the-advisor-strategy): Haiku with an Opus advisor went from 19.7% to 41.2% on BrowseComp. Nudges to consult helped Haiku about 7 points. Independent tests found no gain on task decomposition (secondary, https://mediumroast.dev/blog/model-testing/). Implication: a cheap main session that asks a strong agent "how should this be split?" is closer to proven practice than one that splits on its own.
- NVIDIA, ToolOrchestra / Orchestrator-8B, arXiv 2511.21689, https://research.nvidia.com/labs/lpr/ToolOrchestra, 2025-11 (figures from excerpts). An 8B orchestrator beat GPT-5 on HLE (37.1% vs 35.1%) at about 30% of the cost, but only after RL training on correctness, cost and latency. Prompted GPT-5 as orchestrator chose itself or its mini variant 98% of the time. Implication: small orchestrators work when trained for routing; a prompted cheap model will not be calibrated, so routing must be simple enough not to need calibration.
- Anthropic, "Building effective agents", https://www.anthropic.com/engineering/building-effective-agents, 2024-12-19. Routing easy inputs to small models and hard ones to large models is a named pattern, but the router is a classification step, and the advice is to start with the simplest workflow. "Poka-yoke" tool arguments prevent misuse. Implication: treat the main session as a classifier over a short fixed roster, with a tool schema that makes wrong calls impossible or loud.
- RouteLLM, https://lmsys.org/blog/2024-07-01-routellm/, 2024-07-01, and NVIDIA "Small Language Models are the Future of Agentic AI", arXiv 2506.02153, 2025-06 (secondary). Cost wins from small models come from trained routers and narrow, repetitive subtasks. Implication: cheap models fit narrow repeated roles (exploration, status relay) better than open-ended coordination.
- Cemri et al., "Why Do Multi-Agent LLM Systems Fail?" (MAST), https://arxiv.org/abs/2503.13657, 2025-03 (v3 2025-10, NeurIPS 2025). 14 failure modes from 1,600+ traces. The top modes were step repetition (15.7%), reasoning-action mismatch (13.2%), unawareness of termination (12.4%), disobeying the task spec (11.8%) and incorrect verification (9.1%). By the research agent's own sums, about 44% were system design, 32% inter-agent misalignment and 24% verification. Clearer role specs gave +9.4%, and an objective-verification step gave +15.6%. Implication: termination rules, role specs and a verification step are structural; they belong in the extension and agent files, not in the weak model's judgement.
- Anthropic, "Effective context engineering for AI agents", https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents, 2025-09-29, and "Writing effective tools for agents", https://www.anthropic.com/engineering/writing-tools-for-agents, 2025-09-11. Use few non-overlapping tools ("if a human cannot say which tool to use, the agent cannot"), unambiguous parameters and prompts at the "right altitude". Small description edits produced large gains. Implication: a weak orchestrator needs a roster where every request maps to exactly one agent.
- Roo Code, Orchestrator (Boomerang) mode, https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks, docs fetched 2026-10. Since v3.15.2 the orchestrator mode cannot read, write, run commands or use MCP; it only delegates, and each subtask returns a summary through `attempt_completion`. Implication: a "delegate only" main session is a shipped, working product shape, as long as tool removal enforces it rather than prompt wording.

Synthesis. Practitioners do not recommend a prompted weak model making open-ended orchestration decisions. The cheap/strong split that works is either a strong lead with cheap workers, a cheap executor with a capped strong advisor, or a trained router. A weak main session can work if almost every decision is taken away from it. That means a tiny roster, deterministic defaults (one default agent per request type), a strict schema, a fixed brief template, fixed result shapes, and termination and verification enforced by code.

## Q2. Nested delegation

- Claude Code subagents docs, https://code.claude.com/docs/en/sub-agents, fetched 2026-10. Subagents can call the Agent tool; nesting arrived at a fixed 5 layers in v2.1.172 (about 2026-06-10, secondary), dropped to a default of 1, then settled at default 3 (v2.1.219) via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. At the cap the Agent tool is removed from the deepest agents, so they must do the work themselves. Concurrency is a separate cap (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`, default 20). Built-in Explore and Plan now inherit the main model; a cheap Explore needs an explicit `model`. Implication: the repo's `maxDepth` 3 with tool removal at the cap matches the market leader, and cheap scouts should be pinned to a cheap model in their own file, not inherited.
- Claude Agent SDK subagents, https://code.claude.com/docs/en/agent-sdk/subagents, fetched 2026-10. It warns that "one prompt can grow into a tree of agents" and that recent strong models delegate more readily. Controls: `maxBudgetUsd` refuses new spawns and ends the run, `maxTurns` returns partial and resumable output, and final messages are scanned for injected instructions. Implication: add a tree-wide spend or turn budget next to depth and concurrency, because depth alone does not bound cost.
- Cursor subagents, https://cursor.com/docs/agent/subagents, fetched 2026-10 (since Cursor 2.5). Exactly one extra level: the main agent and its direct subagents may spawn; grandchildren may not. A built-in Explore runs on a faster model. Five parallel subagents cost about 5x, and for simple tasks the main agent is often faster. Implication: two levels (main, role agent, scout) cover the owner's design; depth 3 below main is more than needed.
- Gemini CLI subagents, https://geminicli.com/docs/core/subagents/, fetched 2026-10. Subagents cannot call subagents, explicitly to prevent loops and token blow-up; `max_turns` defaults to 30 and `timeout_mins` to 10. Implication: per-agent turn and time caps are a standard safety net worth adding.
- OpenAI Codex subagents, https://learn.chatgpt.com/docs/agent-configuration/subagents, fetched 2026-10. Built-in `default`, `worker`, `explorer`; `agents.max_concurrent_threads_per_session` caps concurrency. Secondary guides (https://www.morphllm.com/codex-multi-agent, 2026) report `agents.max_depth` default 1 and warn of exponential token use when raised. Approval-needing actions fail in child runs, and parallel writers conflict. Implication: nested agents should not need interactive approvals, and writers should not run in parallel on one tree.
- OpenAI Agents SDK handoffs, https://openai.github.io/openai-agents-python/handoffs/, fetched 2026-10, and Google ADK, https://cloud.google.com/blog/products/ai-machine-learning/build-multi-agentic-systems-using-google-adk, 2025 (secondary). Both separate a handoff/transfer (control moves, the parent leaves the loop) from agent-as-tool (call and return, the parent stays in charge). Implication: `run_agent` is agent-as-tool, which is right for a main session that must keep talking to the user.
- OpenCode agents, https://opencode.ai/docs/agents/, fetched 2026-10. Ships read-only Explore and Scout agents; `steps` caps iterations, and at the cap the agent must summarise and list the remaining work. Implication: a "budget reached, here is the partial result" exit is better than a hard kill.
- LangChain Deep Agents, https://docs.langchain.com/oss/python/deepagents/overview, fetched 2026-10, and LangChain, "How and when to build multi-agent systems", https://blog.langchain.com/how-and-when-to-build-multi-agent-systems, 2025-06-16 (excerpts). Subagents may use smaller models; the main agent sees only the final answer. Users asked for a way to block nested spawning (issue #1265). Nested async runs were hard to attribute in traces. Implication: per-agent cost attribution across the tree is needed before nesting is turned on widely.
- Anthropic multi-agent research system (above), 2025-06-13. Effort scaling in the lead prompt: 1 agent with 3-10 calls for simple facts, 2-4 for comparisons, 10+ only for complex research. A synchronous lead waits for its slowest worker. Implication: numeric spawn rules work, and they belong in the prompt of whichever agent spawns scouts.

Synthesis. Nesting is now common but shallow by default (Cursor one extra level, Codex depth 1 by report, Gemini none, Claude Code 3). Failure modes are multiplicative cost, runaway trees, duplicated work, context lost at every hop, conflicting writers and hard cost attribution. Flat fan-out from the top is preferred when tasks are independent and read-only, because one owner deduplicates and budgets. The "expensive lead with cheap scouts" pattern is well supported, provided scouts are read-only, pinned to a cheap model, capped in turns, and return a fixed short shape. That supports the owner's idea for implementer and reviewer.

## Q3. Data flow and token reduction

- Anthropic, "Effective context engineering for AI agents", 2025-09-29 (above). Subagents may spend tens of thousands of tokens but should return "a condensed, distilled summary (often 1,000-2,000 tokens)". Keep lightweight identifiers (paths, queries, links) and load just in time. Clearing old tool results is the safest compaction. Implication: 4,000 characters (about 1,000 tokens) inline is in the recommended range; keep it and make the shape fixed.
- Anthropic multi-agent research system, 2025-06-13 (above). Subagents "store their work in external systems, then pass lightweight references back". Implication: the existing `result.md` plus inline preview is the right mechanism; scouts' results can go to the parent agent as paths too, not only to the main session.
- Anthropic, "Writing effective tools for agents", 2025-09-11 (above). A `response_format` enum (concise vs detailed; 72 vs 206 tokens in their example); Claude Code caps tool responses at 25,000 tokens. Truncation notices should steer the agent toward narrower queries, and errors should be actionable. Implication: the over-cap message should say how to read the full `result.md` selectively, and failures should carry a one-line next step.
- Claude Code MCP docs, https://code.claude.com/docs/en/mcp, fetched 2026-10. Warns at 10,000 tokens of tool output, caps at 25,000 (`MAX_MCP_OUTPUT_TOKENS`); oversized results are spilled to a file and only the path enters the conversation. Long errors keep the first and last 5,000 characters. Tool search is on by default, with schemas loaded on demand. Implication: "spill to file, return path plus head" is the industry pattern; keep both ends when truncating error text.
- Claude Code subagents docs (above). A subagent returns only its final message; at `maxTurns` the output is marked partial and resumable. Agent descriptions cost context every session, so descriptions should be short and the detail should sit in the agent body; Claude Code warns when combined descriptions pass 15,000 tokens. Implication: the roster in the `run_agent` description should be one line per agent, with the rest in the agent files.
- Manus, "Context Engineering for AI Agents: Lessons from Building Manus", https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus, 2025-07-18. KV-cache hit rate is "the single most important metric"; cached input was 10x cheaper; the input:output ratio is about 100:1. Keep the prefix byte-stable (no timestamps, deterministic JSON), keep context append-only, mask tools instead of adding or removing them, and use the file system as restorable memory. Implication: the main-session prompt and tool list must not change between turns (for example no live agent lists or counts in the system prompt); put status in messages.
- Anthropic prompt caching docs, https://platform.claude.com/docs/en/build-with-claude/prompt-caching, fetched 2026-10. Prefix order is tools, then system, then messages, so any tool-definition change invalidates the whole cache. Reads cost 0.1x base (0.05x on the newest models), writes 1.25x, TTL 5 minutes. Implication: a long but stable main prompt is cheap per turn; an unstable short one is expensive. Prompt length matters more for a weak model's attention than for cost.
- Anthropic, "Managing context on the Claude Developer Platform", https://claude.com/blog/context-management, 2025-09-29. Context editing cut tokens 84% in a 100-turn eval; with a memory tool, task performance rose 39%. Implication: since agents run with compaction disabled, clearing old tool results inside long-running role agents is the cheapest relief to consider before handoff chains.
- Anthropic, "Equipping agents for the real world with Agent Skills", https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills, 2025-10-16 (updated 2025-12-18). Only name and description preload; the body and linked files load on demand. Implication: routing details, brief templates and rare-case instructions for the main session can live in an on-demand skill-like file, keeping the always-on prompt short.
- Anthropic, "Introducing advanced tool use", https://www.anthropic.com/engineering/advanced-tool-use, 2025-11-24. Tool Search cut definitions from about 77K to 8.7K tokens (85%) and raised Opus 4.5 tool accuracy from 79.5% to 88.1%; programmatic tool calling cut usage 37%; tool-use examples raised parameter accuracy from 72% to 90%. Implication: one or two worked `run_agent` examples in the tool description may help a weak model more than extra rule text.
- Anthropic, "Code execution with MCP", https://www.anthropic.com/engineering/code-execution-with-mcp, 2025-11-04. Filtering data in code before the model sees it cut usage from 150,000 to 2,000 tokens (98.7%). Implication: scouts should filter (grep, counts, line ranges) and return extracts, never whole files.

Synthesis. The return contract should be fixed and short: outcome first (done, partial, blocked), then findings as `path:line` with one-line reasons, then open questions, at most about 1-2k tokens, with anything larger in a file referenced by path. Keep the tool list and system prompt byte-stable for caching. Keep routing text to one line per agent in the always-on prompt and move the rest into agent files or an on-demand document.

## Q4. Prompt design for role agents and a weak orchestrator

- Anthropic multi-agent research system, 2025-06-13 (above). Every brief needs an objective, an output format, tool and source guidance, and clear boundaries; vague briefs caused duplication and gaps. A rewritten tool description cut task time 40%. Implication: the current Goal/Scope/Context/Expected output template is right; add "where to look" and "done when".
- Claude prompting best practices, subagent orchestration, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, and "Prompting Claude Opus 5", https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5, both fetched 2026-10. Strong models over-spawn. Recommended damping: delegate only large, independent, parallel work; do not delegate what takes a handful of tool calls; do not use subagents to double-check yourself; "if one subagent can complete the task, use one". Prefer harness caps over prompt rules. "Be conservative" in review prompts makes the model report less, so ask for everything and filter afterwards. Implication: expensive role agents that may spawn scouts need explicit "when not to spawn" rules and a numeric cap, and the reviewer prompt should ask for all findings, ranked.
- OpenAI GPT-5 prompting guide, https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide, 2025-08 (archived). Control eagerness with explicit early-stop criteria ("you can name the exact content to change"; "top hits converge on one area"), a hard tool-call budget with an escape hatch ("proceed and list open questions"), and tool preambles. Cursor softened "be thorough / maximize" wording because it caused over-search. Implication: explorer prompts should carry stop criteria and a budget, not "be thorough".
- OpenAI Codex prompting guide, https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide, 2026 (search summary only). Autonomy and persistence instructions matter most; upfront-plan and preamble instructions can make the model stop early. Implication: implementer prompts should push to completion and verification, with no "present a plan first" step.
- OpenAI Agents SDK handoffs (above) and Google ADK LLM agents, https://adk.dev/agents/llm-agents/, fetched 2026-10. Routing reads each agent's description, so make it specific ("handles X", not "X agent"), with a functional name; give examples for complex cases; routing is non-deterministic, so test it. Implication: write each agent's `description` as "use when / not for / returns", and add routing cases to the live tests.
- Claude Code subagents docs (above). The description drives delegation ("use proactively after code changes"); the body is the whole system prompt; restrict tools per role. Delegate high-volume, parallel or chained work; keep small tightly coupled edits in one place. Implication: tool lists enforce roles better than prose; give scouts read-only tools and no `run_agent`.
- Roo Code Orchestrator mode (above). The subtask brief must carry all context, state that the subtask does only the outlined work, and override the mode's general instructions; completion must come with a concise summary. Implication: the brief should say explicitly that it overrides the agent's defaults where they conflict.
- Cognition, 2026-04-22 (above). Over-prescriptive manager instructions hurt; children must report back. Implication: a weak orchestrator should pass the user's goal and constraints through nearly verbatim instead of inventing a plan.

Suggested role-agent skeleton, based on the sources above. One: a role statement in one sentence, plus what the role never does. Two: the inputs it gets (the brief) and the tools it may use. Three: the method (broad then narrow; for expensive roles, when to send a scout and when not to). Four: stop conditions (you can name the answer or change, or a call budget is reached; then report what is open). Five: the output contract (outcome first, `path:line` findings, verification result, open questions, under about 300 words, larger material in a file). Six: boundaries (only the outlined work, no self-double-checking beyond the contract, reviewers report everything ranked).

Suggested weak-orchestrator skeleton. One: "You talk to the user and delegate; you do not read, edit or run anything." Two: the roster as one line per agent ("use when / not for / returns") plus one or two worked examples. Three: a default agent per request type, so most turns need no choice. Four: a brief template where every field is filled, with the user's words passed through. Five: numeric effort rules (one agent by default, parallel only for independent read-only parts, never an agent to verify another unless it is the reviewer). Six: relay the result outcome-first, and ask the user when the request fits no row.

## Recommendations

1. Do not let the cheap main session make open-ended routing or decomposition decisions; give it a default route per request type (for example: questions go to explorer, changes go to implementer, then reviewer) and send anything ambiguous to one strong planner-style agent that decides the split. Rationale: Cognition, NVIDIA and Anthropic all report that prompted weak or even strong orchestrators misjudge escalation and over-spawn, while fixed routing has no judgement to get wrong.
2. Enforce the "delegate only" role with tools, not prose: the main session gets `run_agent`, `message_agent` and `agent_status` and nothing that reads or edits files. Rationale: Roo Code ships exactly this, and MAST shows spec-disobedience is a top failure that prompt text alone does not prevent.
3. Let implementer and reviewer spawn a cheap, read-only explorer, with spawn rules in their prompts ("not for anything you can do in a few calls", "at most N scouts") and a per-agent cap in code. Rationale: the cheap-scout pattern is well supported (Anthropic, Cursor, OpenCode), and strong models over-spawn without explicit damping.
4. Lower the default `maxDepth` to 2 below the main session (main, role agent, scout), add a tree-wide spend or turn budget that refuses new spawns, and add per-agent turn or time caps with a partial-result exit. Rationale: the market trend is shallow nesting, and depth alone does not bound cost (Agent SDK `maxBudgetUsd`, Gemini `max_turns`, OpenCode `steps`).
5. Fix a result contract for every shipped agent: outcome first (done, partial, blocked), then `path:line` findings, verification run, open questions, about 1-2k tokens at most, with larger output in `result.md`. Rationale: Anthropic recommends 1-2k-token distilled returns and file references, and a fixed shape is what lets a weak relay summarise reliably.
6. Keep the main-session system prompt and tool definitions byte-stable, put the roster in the tool description as one line per agent, and move rare-case guidance into an on-demand file. Rationale: cache invalidation comes from any prefix change, and weak models follow short prompts better, while caching makes stable length cheap.
7. Make the brief template mandatory and slightly richer: goal, user's words verbatim, known and ruled out, where to look, scope in and out, done-when, return shape. Rationale: vague briefs caused most duplication and gaps in Anthropic's system, and over-prescriptive briefs hurt in Cognition's.
8. Keep writes single-threaded: never run two writing agents on one checkout in parallel; parallelism goes to read-only scouts and reviewers, and parallel writers need `worktree: true`. Rationale: Cognition and Codex both report parallel writers as a persistent failure.
9. Rewrite role prompts using the skeleton above, removing "be thorough", "be conservative" and generic "double-check" lines, and add stop criteria with an escape hatch. Rationale: OpenAI and Anthropic guides show these phrases cause over-search, under-reporting and over-verification.
10. Consider an "advisor" agent the cheap main session or cheap implementer can consult briefly (no tools, capped output) instead of handing it a whole task. Rationale: the cheap-executor/strong-advisor split has vendor benchmarks behind it, though independent results are mixed.
11. Add routing cases to `test:live`: a set of user requests with the expected agent and brief fields, run against the cheap main-session model. Rationale: ADK and the advisor docs both say routing is non-deterministic and must be measured, and the weak-orchestrator design stands or falls on it.

## Open questions

- Which cheap model will run the main session, and does it reliably follow a one-row-per-request routing table and fill a brief template? Only the proposed live routing tests can answer this; no source measures it for prompted small models.
- Is "writing code is cheap relative to exploration" true for this workload? Anthropic's data says tokens are dominated by reading and searching, which supports it, but implementer output tokens on expensive models cost several times input tokens, and no source quantifies the split for coding agents.
- Should the strong planner (recommendation 1) be a separate agent or a mode of the implementer? Cognition favours one strong primary that holds context; a separate planner adds a hop and loses context.
- How should cost be attributed and shown for nested trees (per agent, per batch, per user turn)? LangChain users report attribution as a real problem once nesting is on.
- Should scouts' results go only to the spawning agent, or also be visible to the main session or user? Visibility helps trust but costs main-session context.
- The advisor results, the Codex depth default and the ToolOrchestra figures come partly from secondary sources and should be rechecked before they drive decisions.
