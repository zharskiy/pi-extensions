# Review: subagents runtime

Scope: `extensions/subagents/src/{index.ts,plugins.ts,model/**}`, `src/plugins/{run-agent,agent-registry,agent-definitions,limits,handoff}/**`, their unit tests, `test/helpers/{harness,handoff,live}.ts`, `test/live/**` (read only), `agents/*.md`, `prompts/*.md`, `README.md`, `scripts/spike.ts`.

### High

- **Shipped agents only work with OpenAI credentials, README says otherwise** `README.md:13`, `agents/explorer.md:4`, `agents/general.md:4`, `agents/implementer.md:4`, `agents/reviewer.md:4`. "What you need" says "Agents use the main session's model unless their file names another one", but all four shipped files name `openai/gpt-6-*` models. A user without OpenAI auth gets every `run_agent` call rejected ("matches only models whose providers have no credentials", `run-agent/model-text.ts:26-28`, covered by `test/plugins/run-agent/models.test.ts:108`). Fix: ship the agents with `model: inherit[:level]`, or state the OpenAI requirement in "What you need".
- **A held or early message can start a second concurrent prompt and fail the agent (Unverified at runtime)** `run-agent/runner.ts:669-674`, `runner.ts:906-908`, `core/adapter/pi-child.ts:393-397`. `launch` calls `child.start(task)` and then sends the held messages with `"steer"` straight away. `deliver` only steers when `session.isStreaming`, and pi sets that flag (`_isAgentRunActive`) after several awaits inside `prompt()`. So the held message goes through a second `session.prompt()` with no `streamingBehavior`. pi throws "Agent is already processing" (`pi-coding-agent/dist/core/agent-session.js:1551-1553`). `failStart` catches it and, because the child has not settled yet, emits an error `assistant_message` plus `settled`. The runner then closes the agent as `failed` while its real first turn is still running. `message_agent` sent right after `run_agent` (state `running`, `inFlight` true, session not yet streaming) takes the same path. The unit tests use fakes (`message-agent.test.ts:60-77`) and cannot catch this. To confirm: a live test that messages a queued agent with `maxConcurrent: 1`. Fix: hold routed messages until the child's first `turn_start`/streaming, or pass `streamingBehavior` in the adapter's `prompt` fallback. The adapter part belongs to the core reviewer.

### Medium

- **Semaphore slot leaks when a `wait: true` caller closes while slots are full** `runner.ts:807-819`. The waiting caller releases its slot (`:810`), then re-acquires one in `settled.then` without checking whether it is still open. If the caller is stopped or closed, `stopChildrenOf` settles the batch and the re-acquire queues behind other agents. `releaseLive` for the caller has already run with `live.release === undefined`, so the slot granted later is never released, and `maxConcurrent` drops by one for the rest of the session. Fix: after `await semaphore.acquire()`, release at once if the caller record is closed or `shuttingDown`. That is the same check `resume` makes at `runner.ts:250`.
- **`checkBatch` never resolves batches during shutdown; the second `shuttingDown` check is unreachable** `runner.ts:195` and `runner.ts:213-215`. The early return at `:195` skips `batch.resolve`, so the `settled` promise of a nested `wait: true` `run_agent` call (`tools.ts:198`, `runner.ts:813`) never resolves at shutdown. That child's tool call hangs, and `abortChild` probably runs into its 5 s `settleWithin` timeout (Unverified: depends on whether pi's abort waits for the running tool). The dead check at `:213` suggests the intended order: resolve and emit always, skip only the outbox post. Fix: drop `shuttingDown` from `:195` and keep `:213`.
- **Turns that run without a concurrency slot** `runner.ts:863`, `runner.ts:911-915`, `runner.ts:244-246`. (a) `stop` releases the slot when grace starts, but a message answered during grace starts a follow-up turn without acquiring one. (b) `resume` sets `inFlight = true` before `await semaphore.acquire()`. While it waits for a slot, `route` treats the agent as mid-turn and calls `send(..., "steer")`. The session is idle, so the adapter falls back to `session.prompt` and runs a turn without a slot. (c) A batch wake during grace acquires a slot in `resume`, and `settleGrace` -> `armGrace` (`:467-475`) keeps it until the grace period ends. Fix: route grace answers through `resume`, set `inFlight` only after the acquire, and release the slot in `settleGrace`.
- **`disabledPlugins` in the project settings file is silently ignored** `src/index.ts:18-19`, `src/index.ts:41`. The manager is built at boot from the user file only. The project file is applied later, in `onSessionStart`, after the plugins are enabled. README (`README.md:109`, `:120`) documents both files for every key. Fix: say "user file only" for `disabledPlugins` in the README, or warn when the project file sets it.
- **Lead refuted in practice: settings merging onto one object** `src/index.ts:21-25`. pi rebuilds the extension runtime (and reruns the factory) for `/new`, `/resume`, `/fork` and `/reload` (`pi-coding-agent/dist/core/agent-session-runtime.js:137-166`, `agent-session.js:2937-2966`), so each `settings` object sees one `session_start`, and a key removed from the file cannot keep a stale value. What remains is redundancy: the user file is read twice per boot (`:18` and `:23`), boot-time parse errors (`user.errors`) are dropped, and ARCHITECTURE's "so plugins see new values live" describes a case that does not happen. Fix: read user and project settings once, at session start, and keep the boot read only for `disabledPlugins`.
- **The `run_agent` description contradicts the result format for stopped agents** `run-agent/tools.ts:91` says "failed or stopped: the reason is given; there is no result". `result.ts:71` includes the result inline or as a file for `stopped` agents with text, and `stop-grace.test.ts:79,102` asserts it is there. Fix: change the description to "stopped: the reason, plus the last output when there was any".
- **File write failures leave the registry inconsistent** `agent-registry/registry.ts:89-91`, `:101-105`, `:119-122`, `run-agent/result.ts:15-16`. `writeManifest` and `storeResult` are synchronous and unguarded. In `create`, the record is stored before the write, so a throw midway through `startBatch` (`runner.ts:770-788`) leaves `queued` records with no batch and no launch. They count as open forever, so the `session-limits:busy` signal stays true and the automatic session switch is blocked. In `update` and `close`, the mutation happens but `agent:changed`/`agent:closed` are not emitted, so the batch never settles and the slot is never released. In `expireGrace` (`runner.ts:447-456`, called as `void` from a timer) the throw becomes an unhandled rejection. Fix: catch manifest and result write errors, record them in `error`, and always emit.
- **Worktrees and `pi-agents/*` branches are never cleaned up** `runner.ts:585-592`. `discardWorktree` is only called at `runner.ts:629`, when the agent is closed during placement. A spawn failure after a worktree was created (`runner.ts:675-678`) also leaves it behind, though no agent ever ran in it. Every `worktree: true` run leaves a full checkout under the pi sessions directory and a branch in the user's repo. README (`README.md:87`) states this, so it is documented, but the spawn-failure case is not. Fix: discard on spawn failure, and consider a `/agents` action or a `done` + clean-diff auto-removal. `removeWorktree`, `runGit` and `BRANCH_PREFIX` stay module-internal (see table).
- **The main session prompt is replaced even when the tools it relies on are disabled** `agent-definitions/index.ts:48`. `setMainPrompt` runs unconditionally in `agent-definitions`. With `disabledPlugins: ["run-agent"]` (or `"agent-status"`), `prompts/main-session.md:1,73` still tells the model to delegate with `run_agent` and to use `agent_status`. Fix: set the main prompt from `run-agent` (or only when `services.has("runner")`), and drop the `agent_status` paragraph when that plugin is off.
- **Handoff validation is duplicated with session-limits** `handoff/schema.ts:3-75` vs `extensions/session-limits/src/handoff.ts:7-90`. The section list and heading parser are identical. The status sets differ (`partial, blocked` vs `done, partial, blocked`), and so does the instruction substitution (`handoff/index.ts:12` vs `session-limits/src/handoff.ts:25-26`). A pi-free `core/manager/handoff-schema.ts` exporting `HANDOFF_SECTIONS` and `validateHandoffSections(text, statuses)` would not break the rules (extensions may import `core/manager`). The same applies to the channel names `session-limits:busy` (`agent-registry/index.ts:5`, `session-limits/src/limits.ts:24`) and `spending:usage`, which would make the cross-extension contract a single shared constant.

### Low

- **During shutdown, nested children are recorded as "stopped by the user"** `runner.ts:938-947`. Parents are listed first. Closing a parent fires `agent:closed` -> `stopChildrenOf` -> `stop(child, { immediate: true })`, which synchronously closes the child as `stopped` / "stopped by the user". The loop's own `close(..., "interrupted")` is then a no-op. Manifests read later by `/agents` show a user stop that never happened. Fix: skip `stopChildrenOf` while `shuttingDown`.
- **`agentsDirFor(undefined)` drops the `agents` level** `model/paths.ts:7-8`: `tmp/pi-subagents/no-session` vs `<data dir>/agents` elsewhere. Confirmed. It is harmless today because the runner (`runner.ts:762`) and agent-view (`agent-view/index.ts:28,45-46`) both use the same function. Fix: `join(sessionDataDir(info, NAMESPACE), "agents")` in both cases.
- **Agent ids can repeat across reloads of the same session** `registry.ts:16`, `:53-57`. Ids are `<agent>-<4 hex>`, and `uniqueId` only checks records in memory. After `/reload` or `/resume`, the session data dir is the same, so a repeated id reuses `<dir>/<id>/`: the manifest and `result.md` are overwritten, and `git worktree add` into the existing `worktree/` fails. Fix: also check `existsSync(join(dir, id))`.
- **Unbounded runner state and O(n) scans** `runner.ts:145-148`. `batches`, `lives`, `launches` and `userStopped` are never pruned (each `launches` entry keeps the full task). `hasOpenBatches` (`:234-235`) scans every batch ever created on each `settled`. `stopChildrenOf` (`:220-227`) and `hasOpenAgents` (`agent-registry/index.ts:9`, run on every `agent:changed`, which includes every `tool_start`) scan every record. This only matters in very long sessions. Fix: delete entries on close and batch settle.
- **Redundant or unreachable conditions** `runner.ts:361`: `!batch.woken` is always true, since the record being finished is still open. `runner.ts:336`: the `?? { ok: true, status: "unknown" }` fallback cannot run, because `handoffRequested` is only set by `limits` (`limits/index.ts:52`), which `requires` `handoff` (`limits/index.ts:12`).
- **The caller loses pending child results when it closes on a handoff** `runner.ts:540-552`. When `handoffRequested` is set, `waiting` is false even with `outbox.pending() > 0`, so held wakes are dropped (`releaseLive` clears the outbox, `:313`). The results exist only as files the successor is not told about. Fix: list the undelivered batch ids in the successor's task, or deliver before finishing.
- **The base prompt says routed messages come from the caller** `prompts/base-system-prompt.md:10`. Limit warnings arrive as `[message from pi-subagents]` (`limits/index.ts:6,20`), and agent-view messages come from the user. Fix: "from your caller, the user or the harness".
- **Unknown frontmatter keys are ignored without a warning** `loader.ts:175` (asserted by `agent-definitions.test.ts:88-104`). A typo such as `worktre: true` silently gives `worktree: false`. Fix: warn on keys outside `FRONTMATTER_FIELDS`.
- **The agent name and `subagents` entries use different patterns** `loader.ts:29` (`/^[a-z0-9][a-z0-9_-]*$/i`, no leading `_`) vs `model/frontmatter.ts:39` (leading `_` allowed). README `README.md:58` and the error at `loader.ts:47` do not mention the leading-character rule. Fix: use one pattern.
- **`startBatch` trusts a caller-supplied depth** `runner.ts:746`. The depth could come from `registry.get(callerId).depth`. The tests exploit this and pass a wrong `callerDepth: 1` for a depth-2 caller (`run-agent.test.ts:355`, `:380`, `:406`).
- **`run_agent` description says it "returns at once"** `tools.ts:75`, though `wait: true` blocks (`tools.ts:129-132`).
- **The main prompt hard-codes assumptions** `prompts/main-session.md:1` ("You run on a cheap model on purpose") and `:66-68` (session-limits switch behaviour) apply even when the user runs an expensive model or has no session-limits extension.
- **A test uses an abort reason that does not exist** `stop-grace.test.ts:223`: "turn limit of 5 exceeded". There is no turn limit; the only production abort reason is the context hard limit (`limits/index.ts:58`).
- **Unit tests leak temp dirs and git repos** `test/helpers/harness.ts:12`. `mkdtempSync` dirs are never removed, and `worktree.test.ts:44-54` leaves repos with registered worktrees in tmp. The live helper does clean up (`test/helpers/live.ts:128`).
- **`scripts/spike.ts` is shipped and outside the lint guard** `package.json` `files: ["extensions"]` includes it, although `STRUCTURE.md:38` calls it "not shipped code". It imports `@earendil-works/pi-coding-agent` directly (`scripts/spike.ts:3-11`), which biome's restriction does not cover (`biome.json` overrides list only `extensions/*/src/**` and tests). `architecture.test.ts` only scans `src`. Its default model `gpt-5.4-mini` (`:17`) is stale, and `projectRoot` (`:19`) is actually the extension root. Only `docs/spike.md` and `PLAN.md` reference it. Fix: move it to a dev-only `scripts/` at the repo root, or add it to `files` exclusions. The same `files` entry also ships each extension's `test/` tree, including live fixtures.

### Simplification opportunities

- **Rename the two `frontmatter.ts` files.** The split itself is justified: `model/frontmatter.ts` is the schema plus `AgentFrontmatter` types, which `run-agent/tools.ts` and `model/types.ts` need without importing the definitions plugin, and `agent-definitions/frontmatter.ts` is a generic YAML-subset parser. Two files with the same name and different roles still confuse readers. Suggested names: `model/agent-schema.ts` and `agent-definitions/yaml-lite.ts`. The parser-only rule fields (`hint`, `entry`, `min`, `byDefault`, `namesMeaning`, `allMeaning`, `meaning`) could also move next to the loader, leaving only types and `ALL` in `model/`.
- **Settings reading.** One function `loadSettings(agentDir, cwd, trusted)` returning defaults + user + project, called at session start (as session-limits does), plus a boot read for `disabledPlugins` only, would remove the double read and the ambiguity about live updates.
- **`RunnerDeps.handoff`** could be a plain optional service read once, since `limits` requires `handoff` anyway. Alternatively, `run-agent` could `require` `handoff` and drop the fallback.
- **`checkBatch` and `stopChildrenOf`** are the only `agent:closed` listeners in the runner. Folding them into a single `onClosed` that also prunes `lives`/`launches`/`batches` fixes the growth and the shutdown labelling in one place.
- **`message_agent` access check** (`tools.ts:239`) and `route` could share the chain-terminal lookup: `route` already resolves `terminalOf`, so the check could move into `route`, with a `callerId` argument.
- **Shared contracts in `core/manager`.** Handoff section validation, and the `session-limits:busy` / `spending:usage` channel names with their payload types, belong there. See Medium.

### Open questions

- Held-message double prompt (High): confirm with a live run that messages a queued agent, or by checking whether `_isAgentRunActive` is set before `prompt()`'s first await in pi 1.1.0.
- Shutdown with a nested `wait: true` batch: does pi's `session.abort()` wait for the pending tool promise? If so, shutdown stalls for `ABORT_WAIT_MS` (5 s, `runner.ts:109`) per such agent tree.
- Can `ChildSession.send` reject? `session.steer`/`followUp` errors would surface as unhandled rejections from `void send(...)` in `limits/index.ts:45,53` and `void resume(...)` callers. Confirm by checking pi's `_queueSteer`/`_queueFollowUp` for throws on a disposed session.
- Extension reload per session: the refutation of the settings lead relies on `createRuntime` building a new resource loader, and so rerunning extension factories. A one-line log in `boot` on `/new` would confirm it.
