# Review: session-limits and spending

Scope: `extensions/session-limits/**` (src, test, prompts/handoff.md, README.md) and `extensions/spending/**` (src, test, README.md), compared with `extensions/subagents/src/plugins/{handoff/schema.ts,handoff/index.ts,usage-report/index.ts,limits/context-step.ts,agent-registry/index.ts}` and `core/manager/settings.ts`. Live tests were not run.

### High

None found. Both extensions match their READMEs on settings keys, defaults, command name, channel names and payload shapes. The handoff retry flow is bounded (see Verified behaviour).

### Medium

- **Handoff validator duplicated with subagents** `extensions/session-limits/src/handoff.ts:7-98` vs `extensions/subagents/src/plugins/handoff/schema.ts:3-75`. About 45 lines of logic are the same: `HANDOFF_SECTIONS` (identical six names), `headingsOf`, `bodyOf`, missing/order/empty checks, the first-line-of-Status parse and the `[^a-z]` strip. The only real differences: (1) statuses are `["done","partial","blocked"]` in session-limits (handoff.ts:16) and `["partial","blocked"]` in subagents (schema.ts:12); (2) session-limits has a `positionOf` helper and an `isStatus` type guard (handoff.ts:49,56) where subagents inlines `titles.indexOf` and casts (schema.ts:66); (3) the `HandoffValidation` type is declared in `handoff.ts:18` in one and in `subagents/src/model/types.ts:135` in the other (same shape). Fix: add a pi-free `validateSections(text, sections, statuses)` plus `HandoffValidation` to `core/manager` (for example `core/manager/handoff-validation.ts`); both extensions pass their own status list and keep their own prompt template. This is legitimate under ARCHITECTURE.md:8-9 (core/manager is pi-free shared infrastructure that extensions may import, and session-limits already imports `core/manager/settings.ts` and `paths.ts`). Keep the section list and statuses as parameters so the two extensions can still diverge.
- **`isAhead` duplicated** `extensions/spending/src/ledger.ts:49-55` and `extensions/subagents/src/plugins/usage-report/index.ts:8-14`. Identical bodies. The extensions may not import each other (ARCHITECTURE.md:10), so the legitimate home is `core/adapter/contract.ts` next to `addUsage`/`emptyUsage`/`UsageTotals`, or `core/manager`. Also note the publisher-side dedup (usage-report/index.ts:29) is redundant with the ledger's own idempotence (ledger.ts:66); it only saves bus traffic. Either drop it (then no duplicate is needed) or share the helper.
- **Channel names are duplicated literals, never shared** `session-limits:busy` at `session-limits/src/limits.ts:24` and `subagents/src/plugins/agent-registry/index.ts:5`; `spending:usage` at `spending/src/spending.ts:7` and `subagents/src/plugins/usage-report/index.ts:4`. Checked: strings match exactly on both sides, and the payloads match (busy: `{source:string,busy:boolean}` against `parseBusySignal` limits.ts:52-64; usage: `{source,id,usage:UsageTotals}` against `parseUsageReport` ledger.ts:35-47, where `usage` is the same `UsageTotals` type from `contract.ts`). Nothing but convention keeps them in sync, and no test spans both sides (each side's tests use its own constant). Fix: export `BUSY_CHANNEL` / `USAGE_CHANNEL` and the payload types from `core/adapter/contract.ts` (types and string constants only, no pi import), or add one architecture-level test asserting both sides agree.
- **Stale context after compaction or unknown usage** `session-limits/src/limits.ts:326-328`. `state.context` is only replaced when `level !== "unknown"`. When pi reports `tokens: null` (adapter `contextOf`, `core/adapter/pi-adapter.ts:44-48`, returns `null` when usage is unknown) the footer in `refresh()` (limits.ts:77-83) keeps showing the old percentage and warning colour. Test at `limits.test.ts:358` only checks that nothing is requested. Unverified whether pi returns `null` right after compaction; confirm by running a compaction in a session above `softRatio` and watching the footer. Fix: on `unknown`, clear `state.context` (or store it with a flag) so the segment disappears while `phase === "watching"`.
- **`phase: "switching"` has no exit if the dispatched command never runs** `limits.ts:143-148`. `switchSession` sets `switching` and calls `host.dispatchCommand`, which silently returns when there is no live context (`pi-adapter.ts:198-202`) or if the extension-command wrapper skips because `active()` is false (`conversation.ts:37`). Nothing then moves the phase on; `handoffStep` returns `"none"` for non-pending phases (`thresholds.ts:46-49`, `isPending` excludes `switching`), and the footer says `switching session` forever. Only `failSwitch`/`holdSwitch` leave that state and both run inside `runSwitch`. Low probability, so Medium only because the failure is silent. Fix: treat `switching` as pending-with-timeout, or reset to `stuck` on the next `onIdle` if still `switching`.

### Low

- **Unsynchronised filesystem checks can throw inside event handlers** `limits.ts:66,115,103`. `mtimeOf` is `existsSync` then `statSync` (TOCTOU), `inspect` calls `readFileSync` unguarded, and `request()` calls `mkdirSync` unguarded. They run from `onTurnEnd`/`onIdle`/timer callbacks (limits.ts:317-345, 280-289), where a throw (permissions, file removed between calls) is an unhandled exception in a handler, and for `mkdirSync` it recurs on every turn end since the phase never leaves `watching`. Fix: wrap in try and treat as `missing`/notify once.
- **`runSwitch` is re-entrant** `limits.ts:226-268`. It awaits `confirmBusy()` and `newSession` with no in-flight flag, so a second `/session-handoff` typed during the confirmation dialog runs a second switch. Fix: a `switching` guard at the top of `runSwitch`.
- **Equal soft/hard ratio is undocumented** `thresholds.ts:27-31` returns `"hard"` first, so `softRatio === hardRatio` skips the warning stage exactly like soft above hard. README `README.md:52 ("A soft ratio above the hard ratio skips the warning stage")` should say "at or above". A user who sets only `hardRatio: 0.5` gets the same silent skip because the default soft is 0.6 (`settings.ts:14`, merged at 36).
- **A context window of 0 or tokens of `null` silently disables the whole extension** `thresholds.ts:20,23`. By design, but there is no notice; README does not mention it. Fix: one line in README.
- **`percentOf` rounds, `contextLevel` does not** `thresholds.ts:20` vs `27-31`. The footer can show `ctx 75%` while level is still `soft` (74.6%), and `handoff at ${Math.round(hardRatio*100)}%` (line 89) rounds a ratio like 0.755 to 76%. Cosmetic.
- **`ctx` segment text for the pending phase is red even for `waiting`** `thresholds.ts:77-81` uses token `error` for every non-watching phase including `waiting` (a normal, healthy state). README says "the segment turns to the error colour" only for writing; consider `warning` for `waiting`.
- **Footer total rounds after summing** `spending/src/footer.ts:11-17`. Each part is `toFixed(3)` of the raw value and the total is rounded separately, so displayed parts may not add to the displayed total by $0.001. Cosmetic.
- **`isVisible` hides the footer when the only reporting source has zero cost but nonzero tokens** `footer.ts:7`. Intended per README ("hidden while every source total is zero"); noting that free or subscription models with `cost.total = 0` never show token activity.
- **`formatCost` fixed at 3 decimals, `main` not subject to `isVisible`** `spending.ts:28`: main spend is never shown on its own; also by design.
- **`settings.ts` is a layer of five one-line aliasing wrappers** `session-limits/src/settings.ts:2-27`. `parseWith`, `readWith`, `userPath`, `projectPath` renames re-export `core/manager/settings.ts` with the schema bound. `parseSettings` (line 20) is referenced only from tests (see table). Fix: bind the schema once in `loadSettings`, drop the unused wrappers.
- **`createLimits` returns `busySources`, used only by tests** `limits.ts:358` (tests: `limits.test.ts:149,400,409,552`); `createSpending` returns `{ figures, refresh }` that nothing uses, tests included (`spending.ts:56`, `index.ts:9`). Production API surface kept for tests. Fix: drop `figures`/`refresh` from the return, assert via `host.statuses` which the tests already do.
- **`subscribe` unsubscribe handles are discarded** `limits.ts:297`, `spending.ts:31`. `Host.subscribe` returns an unsubscribe (`contract.ts:196`, adapter `pi-adapter.ts:215`) but neither extension calls it on shutdown. README says pi creates a new extension instance per session, so if `pi.events` outlives instances, old instances keep receiving signals. Unverified; see Open questions.

### Simplification opportunities

- Shared handoff validator and shared usage helper in core, as described in Medium (about 60 duplicated lines removed).
- Collapse `settings.ts` wrappers (Low above); `loadSettings` plus `watchSettings` are all `index.ts` needs.
- `check()` in `limits.ts:150-188` chains six `if (step === ...)` branches with early returns; a `switch (step)` would make the one-action-per-call rule explicit and removes the fall-through reading burden. The `"wait"` branch intentionally falls through to later ifs that cannot match.
- `parseBusySignal` (limits.ts:52) and `parseUsageReport`/`isUsage` (ledger.ts:18-47) both hand-roll record narrowing (`typeof x === "object" && x !== null`); `isRecord` in ledger.ts:20 could live in core/manager and be used by both.

### Open questions

- Does `pi.events` outlive extension instances across a session switch? If yes, every handoff leaves an old instance subscribed to `session-limits:busy` and `spending:usage`; old `spending` instances would call `host.ui.setStatus`, relying on `liveCtx` to no-op. Confirm by logging in the subscribe handlers across a `/session-handoff` switch, or by reading pi's `events` implementation.
- `core/adapter/usage.ts:51` includes `toolResult` message usage in `sumSessionUsage` (main) but excludes it in `sumOwnUsage` (child). If subagent tool results carry a `usage` field in the main session, those costs would be counted both in `main` and again via `spending:usage`. Nothing in `extensions/` writes such a field, so likely a pi convention; confirm by inspecting a real session file containing a subagent tool result. Belongs to the core/adapter reviewer.
- Resume of an old session with subagents: usage ids are `${runtimeToken}/${agentId}` with a fresh token per session start (`usage-report/index.ts:21,24`). Old entries restore under the old token, so if a resumed run re-reports an agent whose child session file already contained earlier usage, both the old and new entry would be summed. I could not find code that resumes child sessions across a pi resume (`runner.ts:364-388` only creates a successor with a new id and a fresh child). Confirm by checking whether the registry restores agents on session start.
- Whether `/session-handoff` dispatched through `sendUserMessage` (`pi-adapter.ts:198-202`) leaves a visible user message in the conversation; README says "nothing is said in the conversation". Confirm in a live TUI run.
- Spending shutdown persist depends on `liveCtx` still being live in `onSessionShutdown` (`pi-adapter.ts` `appendEntry` guard); the README ordering note (spending.README line on `pi.extensions` order) is not testable here.

### Verified behaviour (no finding)

- **Thresholds**: `contextLevel` checks hard first (`thresholds.ts:27`), inclusive `>=` for both, so soft equal to or above hard never yields `soft`; matches README. Zero window or null tokens return `unknown` (line 23), no divide-by-zero. Settings schema rejects 0, negative, above 1 and non-finite (`core/manager/settings.ts:16-20`, `minExclusive`).
- **Retry bound**: at most `MAX_INSTRUCTIONS = 2` messages per request (`thresholds.ts:5,59`), then `give-up` and phase `stuck`, which no handler leaves except session start. The one reset is `sendRequest` setting `instructions: 1` (limits.ts:90), reachable only when a valid file exists and the user spoke after the first settle (limits.ts:171-174); it needs user activity each time, so it is not a loop. Model never writes the file: `inspect` returns `missing` when mtime is absent or equals the pre-request mtime (limits.ts:111), so one resend then a single warning (limits.ts:126). Malformed file: one resend with the error list (thresholds.ts:92-99), then warning.
- **Timers**: a single `releaseTimer`; it is cleared by `cancelRelease` on busy:true, new `release()`, session start and shutdown (limits.ts:306,278,348,355). The callback does not reschedule itself. No unbounded timers.
- **Busy channel**: sources are a `Set`, repeated signals are idempotent, an unknown `busy:false` does nothing (limits.ts:310-314). A source that crashes without sending `false` blocks the automatic switch indefinitely, as README says; the manual command asks for confirmation.
- **Settings pattern**: `loadSettings` rebuilds `{...defaultRatios(), ...user, ...project}` on each session start (`settings.ts:35-38,46-48`), so a key removed from a file reverts to its default. Subagents instead mutates one object with `applySettings` (`core/manager/settings.ts:92-96`, `subagents/src/index.ts:19,25`), so a removed key keeps its old value until restart. session-limits is the correct pattern; `applySettings` is the odd one.
- **Spending cost source**: `main` is `sumSessionUsage` of the session's own entries (`pi-adapter.ts:224`), costs are pi's own `usage.cost.total` numbers, not recomputed. Other sources come from channel reports. No rounding is applied to stored figures, only `toFixed(3)` at display (`footer.ts:5`).
- **Persistence growth**: memory is bounded by the number of (source,id) pairs. On disk, `persist` appends one full-usage custom entry per changed id per idle and once on shutdown (`ledger.ts:75-86`, `spending.ts:47-54`); roughly one small entry per changed agent per main-session idle, never rewritten or compacted, so the session file grows linearly with activity but modestly. `restore` reads all entries and keeps the highest per key (ledger.ts:93-103), so duplicates are harmless.
- **Double counting via successors**: a successor agent is a new registry record with its own id and fresh child session (`runner.ts:364-388`), and each child reports `ownUsage()` of only its own session (`pi-child.ts:440`); the predecessor and successor are separate keys, so no double count from handoff. Grandchildren are not counted in the parent's `ownUsage` because tool results are excluded (`usage.ts:51`).
- **Cost across a handoff switch**: the new session is a fresh session file, so `spending` restarts at zero for it (`ledger.clear()` at spending.ts:42, nothing carried from the parent). This is consistent with the README ("what the whole session has cost") but a user who relies on session-limits will see the total reset at every switch. Not a bug, worth a README sentence.
- **README vs code**: settings keys `softRatio`/`hardRatio`, defaults 0.6/0.75, paths `~/.pi/agent/pi-session-limits.json` and `.pi/pi-session-limits.json` (trusted only), command `/session-handoff`, message type `pi-session-limits-handoff`, tmpdir fallback `pi-session-limits/<id>` (`core/manager/paths.ts:5-15`), seed text, confirmation text, entry type `pi-spending:usage`, `(sub)` suffix and alphabetical source listing all match the code. Only the equal-ratio wording and the missing notes above are gaps.
