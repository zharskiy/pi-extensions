# Review: subagents UI and observability

Scope: `extensions/subagents/src/components/{agent-list,agent-row,collapsible,context-breakdown,system-prompt-block}.ts`, `src/plugins/{agent-view,agent-list-view,agent-status,progress-widget,notifications,usage-report}/**`, their tests under `test/components/` and `test/plugins/{agent-view,agent-list-view,agent-status,progress-widget,notifications,usage-report}` (incl. snapshot and `fixtures/recorded-session.jsonl`); `core/adapter/pi-ui.ts` and `core/adapter/session-file.ts` read as consumers only.

### High
- None found. Every keyboard claim in the README (`extensions/subagents/README.md:36-40`) matches the key handlers (`agent-view/view.ts:476-547`, `agent-list-view/view.ts:213-292`). The `notifications` setting is read live (`notifications/index.ts:42`). The `spending:usage` payload `{ source, id, usage }` (`usage-report/index.ts:34`) passes `parseUsageReport` (`extensions/spending/src/ledger.ts:35-47`).

### Medium
- **Spinners turn backwards in the widget and list.** `progress-widget/model.ts:84` and `agent-list-view/view.ts:117` compute `frame = floor(now / 120)`, but the widget redraws on a 1 s tick (`progress-widget/index.ts:7,66`) or a 250 ms throttle, and the list on a 1 s tick (`agent-list-view/index.ts:7,30`) or after a 300 ms debounce. Between two 1 s redraws the frame moves by 8 or 9. With 10 frames (`agent-row.ts:4`) that is the same as moving back 2 or 1, so the spinner turns backwards and jumps. `SPINNER_INTERVAL_MS`/`FRAME_MS` give the false impression of a 120 ms animation. Fix: advance a frame counter once per redraw (or per tick), or tick at the spinner interval while agents are running.
- **The agent view re-reads and re-parses the whole session file on every refresh.** Each `agent:changed` of an agent in the chain (one per turn end, tool start, grace change: `run-agent/runner.ts:495,524,463`) schedules `reload` (`agent-view/index.ts:110-118`). That calls `load()`, which does `existsSync` and then `runtime.readSession` (`agent-view/index.ts:64-69`): a sync `readFileSync` plus a `JSON.parse` of every line (`core/adapter/session-file.ts:142-190`), at most every 300 ms on the TUI thread. Every reload also rebuilds `promptSections` and builds a new `sections` array (`view.ts:220-222`). That always misses `promptCache` (`view.ts:292`), so the whole prompt block (including the provider payload JSON) is wrapped again, and the context breakdown is estimated again because `contextCache` is keyed on `data` identity (`view.ts:256`). Fix: skip the parse when the file size or mtime has not changed (or read only the tail), and keep `sections` when the prompt record is unchanged.
- **Three hand-rolled throttles.** `agent-view/index.ts:108-127` and `agent-list-view/index.ts:16-43` each build a "first event arms a 300 ms timer" debounce. `progress-widget/model.ts:96-130` already exports `createThrottle` with cancel. Fix: move `createThrottle` to `components/` (or core) and use it in all three.
- **Linger and throttle settings are listed but not explained.** `README.md:122` names `lingerMs`, `failedLingerMs` and `renderThrottleMs` but gives no meaning and no defaults (30000, 60000, 250 at `model/settings.ts:36-38`). It also does not say that `failedLingerMs` covers `stopped` and `handoff` too (`progress-widget/model.ts:8-9`). Fix: one sentence per key.
- **`isAhead` and the channel name are duplicated across extensions.** `usage-report/index.ts:8-14` is a verbatim copy of `extensions/spending/src/ledger.ts:49-55`. `SPENDING_CHANNEL = "spending:usage"` (`usage-report/index.ts:4`) duplicates `USAGE_CHANNEL` (`extensions/spending/src/spending.ts:7`). The two can drift without any test failing, since each side tests only its own constant. Fix: move the channel name, `isAhead` and the report type to a shared module under `core/` and import it on both sides. `SPENDING_SOURCE = "agents"` can stay local.

### Low
- **Agent view header goes stale.** The view has no tick, unlike the list (`agent-list-view/index.ts:30`). Elapsed time in the header (`view.ts:237`) only moves on `agent:changed` or a keypress. A running agent in a long tool call shows a frozen clock. Fix: reuse the list's 1 s tick while the record is open.
- **Stop and send promises can reject unhandled, and can reload after close.** `view.ts:425` and `agent-list-view/view.ts:180,197` do `void Promise.resolve(deps.stop()).then(reload)` with no `catch`. `send` is caught (`view.ts:461`) but `stop` is not. Both `then(reload)` calls can run after the overlay closed: `deps.load()` re-reads the file and calls `api.requestRender()` on a disposed view. Fix: add `.catch` and a `closed` flag checked in `reload`.
- **`fromManifest` throws on a corrupt manifest.** `agent-view/index.ts:34` parses without `try`, so `/agents <id>` for a past-session agent with a broken `manifest.json` throws out of the command. `followChain` casts a possibly `undefined` result to `AgentRecord` (`index.ts:57`), so `load` would crash on `record.id` if the manifest vanishes after open. The manifest is also read twice per open (`findRecord` at `index.ts:87`, then `load` at `view.ts:167`). Fix: catch and report "cannot read manifest", and pass the found record into the view.
- **Past-session chains are not followed.** `followChain` only follows successors through the live registry (`index.ts:54-58`). Opening link #1 of a chain from an earlier session shows #1, not the terminal, although the README says any id of the chain works with `/agents` (`README.md:41`). Fix: follow `successorId` through manifests too, or narrow the README to the current session.
- **`agent_status` output quirks.** `snapshotLine` writes `${toolCalls} tool calls` (`agent-status/snapshot.ts:97`), so one call reads "1 tool calls". `agent-row.ts:70` already has `plural`. Explicit `ids` that name two links of one chain produce the same terminal snapshot twice (`agent-status/index.ts:45-49`). The `continued by` extra (`snapshot.ts:103`) is effectively unreachable, because `snapshotOf` always gets `chainTerminal(...)`, which has a successor only when that successor is missing from the registry.
- **The batch notification names agent types, not ids.** `notifications/index.ts:15` gives "explorer failed, explorer failed" (the test pins this exact title: `notifications.test.ts:71-74`). In a batch of two, the first failure is announced twice: once alone (`index.ts:82-83`, batch not settled yet) and again in the batch title. The test shows this is intended, but the README says "one per batch" (`README.md:42`). Fix: use ids in the batch title, or say so in the README.
- **The README says the widget lists running agents** (`README.md:36`). It also lists queued and grace agents, plus finished ones for the linger window (`progress-widget/model.ts:11-23`).
- **The `ModeStore.write` boolean is never read.** `mode-store.ts:6,26-34` returns success, but `view.ts:193` ignores it. A failed write is silent, so the mode just does not persist. Fix: return `void`, or show a status line on failure. The persistence itself is needed (README promises it), reads back correctly (`mode-store.ts:12-25`) and is tested (`agent-view.test.ts:898-938`). It is a single global preference file in `agentDir`, so no cleanup is needed.
- **`onSessionStart` resets in plugins are likely redundant.** `usage-report/index.ts:23-26`, `notifications/index.ts:49-51` and `progress-widget/index.ts:81-84` reset state at session start. According to `docs/deviations.md` entry 44, pi creates a new extension instance per runtime and `disableAll` runs on every shutdown (`src/index.ts:45-47`), so the state is already fresh. `usage-report.test.ts:109` ("forgets what it published when a new session starts") tests a sequence pi does not produce. See Open questions.
- **Snapshot tests mostly freeze output.** `agent-view.test.ts:67-74` snapshots the prompt block, and `agent-view.test.ts:99-112` asserts the same headers explicitly. The transcript snapshot (`agent-view.test.ts:279-287`, `.snap:3-25`) freezes pi-tui component output from `core/adapter/pi-ui.ts` `createTranscriptPane` more than any view behaviour. It will churn on pi upgrades. Acceptable as a regression guard; consider asserting key lines instead. The fixture matches the current reader: system `sections`/`toolsAdded` and a custom `pi-subagents:prompt-record` with `skills`/`guidelines`/`providerPayload`/`model`, as written by `core/adapter/pi-child.ts:115-120`. `agentId` in the fixture data is written but never read by `session-file.ts`.

### Simplification opportunities
- One throttle helper for the agent view, list view and widget (see Medium).
- One shared `stopHint` and scroll-hint text: `agent-view/view.ts:61-70` and `agent-list-view/view.ts:23-31` are near copies.
- Build `graceSecondsLeft` on the same helper as `graceCountdown`.
- Drop `widgetRow`/`WidgetRow` and the unused default parameter, and call `treeRow` directly.
- One spinner frame constant and one frame source for the widget and list (see Medium).
- In the list view, `entries()` (sort plus 5 group filters) runs twice per render (`agent-list-view/view.ts:73,111`) and again per key. Computing it once per render is enough. This is O(n log n), not O(n²), so it is only a nit at realistic agent counts.

### Leak audit (no leak found)
- Agent view: the bus listener and pending timer are cleared by `unsubscribe` (`agent-view/index.ts:121-127`). `unsubscribe` runs on Esc (`view.ts:419`) and from pi's `dispose` (`view.ts:555`, wired at `core/adapter/pi-ui.ts:413`). Calling it twice is harmless because `bus.on`'s off is a `Set.delete`.
- List view: the listener, the 1 s interval and the pending timer are all cleared (`agent-list-view/index.ts:36-43`) on close and on dispose.
- Widget: the interval stops when no visible rows remain (`progress-widget/index.ts:45-55`). It keeps running while only lingering closed rows remain, which is needed to expire them, but it skips redraws via the signature check (`index.ts:68-72`). The plugin's disable function cancels the throttle, stops the interval and clears the widget (`index.ts:86-96`).
- Notifications: all four listeners are removed (`notifications/index.ts:87-92`). The `asked` map entries go on `agent:closed`.
- Usage report: its disable function is the bus off (`usage-report/index.ts:28`).
- `host.onSessionStart` has no unsubscribe in the contract (`core/adapter/contract.ts:187`), so these handlers outlive `disableAll`. This is harmless only if pi never fires `session_start` again on the same instance.

### Open questions
- Does pi 1.1.0 ever fire `session_start` again on an extension instance after `session_shutdown`? If it does, `progress-widget/index.ts:81-84` would call `throttled()` after dispose and restart the `setInterval` (`index.ts:66`) with no bus listener, and the other plugins' resets would matter. If it does not, those resets and the usage-report test at `usage-report.test.ts:109` are dead. To confirm: check pi's runtime rebuild path, or add a probe in a live test.
- Does pi clear widgets from the previous runtime on a session switch? `progress-widget/index.ts:82` sets `shown = false` without calling `setWidget(KEY, undefined)`. This only matters if the answer to the previous question is "same instance".
