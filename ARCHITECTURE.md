# Architecture

Fifteen pi extensions in one package, on a small set of shared layers. This file holds the rules that span folders; how each folder works is in its own `ARCHITECTURE.md`, linked below. Where things are is in [STRUCTURE.md](STRUCTURE.md).

## Layers

```
pi-adapter ← shared ← ui-kit ← extension-manager ← extensions (core ← ui ← api ← index.ts) ← test/framework ← test/evals
```

An arrow points at what a layer may import. `extension-manager` sits after `ui-kit` in the chain but imports only `pi-adapter` and `shared`. Each folder reaches the folders to its left only through their `index.ts`, never through an inner file.

- `platform/pi-adapter/` imports nothing from the repo. Its `types/` imports only other `types/` files.
- `platform/shared/` imports only `platform/pi-adapter/index.ts`. What may enter it is narrow: no host, no theme painting (the admission rule in [platform/shared/STRUCTURE.md](platform/shared/STRUCTURE.md)).
- `platform/ui-kit/` imports `platform/pi-adapter/index.ts` and `platform/shared/index.ts`.
- `platform/extension-manager/` imports `platform/pi-adapter/index.ts` and `platform/shared/index.ts`, never `platform/ui-kit/`.
- Inside an extension, `core/` is logic: it imports its own `core/`, `platform/shared/` and `platform/pi-adapter/` and never its own `ui/`, `api/` or `index.ts`, `platform/ui-kit/`, `platform/extension-manager/` or another extension. `ui/` is rendering: it may add its own `core/` and `platform/ui-kit/`, and still never imports `api/`, `index.ts`, `platform/extension-manager/` or another extension. `api/` is the composition root: it may import its own `core/` and `ui/`, all four platform layers and another extension's `index.ts`. `index.ts` holds nothing but `export … from "./api/…"`.
- Extensions import each other only through `index.ts`, and only from `api/`. None does today: they talk over pi's shared event bus (`Host.publish`/`subscribe`; the channel names and payloads are in `platform/shared/channels/host-channels.ts`; among them `pi:handoff-pending` and `pi:held-results`), through formats in `platform/shared/` (the handoff document and its seed format (an agent's successor seed also ends with its task), the handoff limit, the seam rule label (`LIMIT_SEAM`, `seamLabel`), which session-limits puts on the main session's seam and the subagents view on the boundaries of an agent's chain, the handoff prompt template in `platform/shared/handoff/handoff-prompt.md`, which has the model call the `handoff` tool and end its turn without a reply, filled from the audience each consumer owns, and the `handoff` tool), through a bus channel session-limits publishes its settings on (`session-limits:limits`) for the footer, which then labels its context figure `working context` since the base is the handoff point, through two shared status-key prefixes (`HINT_STATUS_PREFIX` for statuses the footer moves into its hint row, such as subagents' `hint:subagents`, and `MIRROR_STATUS_PREFIX` for statuses it hides because it draws their figures itself, such as spending's `mirror:spending`; each extension owns its key), and, for tool rows and message renderers, through the records the adapter keeps on `globalThis`, through which rows and renderers one extension registers reach the transcript panes another draws. The context limit's look (the footer's figure colours and session-limits' `» handoff at …` notice) lives in `platform/ui-kit/context-limit.ts`, which the subagents agent view also uses, so an agent near its limit looks like the main session near its own.
- An extension's `tests/` may import anything inside the extension, `test/framework/`, the four platform layers and another extension's `index.ts`.
- `test/framework/` imports the four platform layers' `index.ts` and never an extension or `test/evals/`. Its pi-free modules never import `test/framework/pi/`.
- `test/evals/` imports `test/framework/`, the four platform layers, `extensions/<name>/index.ts` and `extensions/<name>/tests/support/`. Nothing imports `test/evals/`.
- `launcher/` stands apart from the chain: it imports only `node:*` built-ins and its own files (its `tests/` also `vitest`), never pi, `platform/`, `extensions/` or `test/`, and nothing imports it. The one pi reference is `launcher/hostpi/*.mjs`, run as a separate Node process against the host pi of host jobs (pi's managed install, else the pi of `npm install -g`, not `npm link`ed, outside every folder a sandbox has run in and the launch folder and its git root when a sandbox could hold them; never a project's `node_modules` pi or a `pi` on `PATH`) to read its provider list. Inside it, a folder reaches another only through that folder's `index.ts`; `bin/` imports only `cli/main.ts` (or its built `dist/cli/main.js`). Its folder graph is fixed (`shared` on nothing; `config` on `shared`; `workspace` on `shared`; `backend` on `shared`; `grants` on `shared`; `hostpi` on `config` and `shared`; `proxy` on `config`, `grants` and `shared`; `container` on `backend`, `config`, `workspace` and `shared`; `image` on `backend`, `config` and `shared`; `provision` on `backend`, `hostpi` and `shared`; `cli` on all of them; nothing imports `cli` but `bin/`). Its rules are in [launcher/ARCHITECTURE.md](launcher/ARCHITECTURE.md).
- There are no import cycles anywhere.

## Repo rules

- Only `platform/pi-adapter/` (with its `tests/`) and `test/framework/pi/` import pi packages (`@earendil-works/*`, `typebox`). Everything else sees pi through `platform/pi-adapter/index.ts`.
- Shipped code never imports `test/` (`test/framework/`, `test/evals/`, `test/architecture.test.ts`, `test/docs-sync.test.ts`) or any `tests/` folder.
- No provider knowledge: no code or prompt names a model provider or a model id. Pi resolves providers, credentials and models; the harness passes `provider/id[:thinking]` strings through, and cost is pi's own usage figure. The only exception is configuration: the shipped agent files name their `model` (`reviewer`, `planner` and `general` one model, `implementer` another, the chores a third). Unit-test fixtures use invented names.
- Folder shape: an extension folder holds only `index.ts`, `api/`, `core/`, `ui/`, `tests/`, `README.md`, `ARCHITECTURE.md`, `STRUCTURE.md`, `prompts/` and `agents/`; source sits at most three folders below it, in `api/`, `core/` and `ui/` only. `*.test.ts` live only in `tests/` (or directly in `test/`), `*.eval.ts` only in `test/evals/`. Non-index, non-test files have unique basenames.
- No dead code: no unused exports, types, enum members, files or dependencies, and no unused locals, imports, parameters or private members. Class members outside the API are `private` or `#` by convention, since no tool checks them.
- User-facing failures become data, not exceptions: a failed agent is a closed record with its error (also when its launch or its settle handling throws), an error in a child session's event subscriber becomes an error notice instead of stopping the other subscribers, tool misuse returns an error result, bad settings or agent files become warnings and are skipped.

## Who enforces what

- Biome (`biome.json`, part of `npm run check`) enforces the import rules: one `noRestrictedImports` override per folder and per folder depth bans inner files of another layer, the layers an extension's `core/` and `ui/` may not see, other extensions except their `index.ts`, and test code from shipped code. The `test/framework/**` override also keeps its pi-free modules from importing `test/framework/pi/`. It also rejects import cycles, `export *`, self-imports and unused locals, imports, parameters and private members.
- `test/architecture.test.ts` checks what an import pattern cannot express: the shape of each extension's `index.ts`, the folder shape and depth, that every `platform/<x>` folder is a known layer, where `*.test.ts` and `*.eval.ts` may live, unique basenames, that `package.json` `pi.extensions` lists exactly the 15 `extensions/<name>/index.ts` files, that in `subagents` no plugin (`api/plugins/<p>.ts`, `core/<p>/**`, `ui/<p>/**`) imports a sibling plugin, that relative imports are written in normalised form with no `./../`, so the Biome path rules cannot be bypassed, that `launcher/` imports only `node:*` and its own files (`vitest` in its tests) and that only `platform/pi-adapter/`, `test/framework/pi/` and `launcher/hostpi/*.mjs` reference a pi package anywhere in the repo (one check, `PI_PACKAGE_REFERENCE`, which also catches `require`, `import()` and `.resolve` forms; Biome does not repeat it), that the launcher folder graph is exactly the documented one and shipped launcher code never imports `launcher/tests/`, that a launcher folder reaches another only through its `index.ts` and `bin/` reaches only `cli/main.ts`, and that a test under `launcher/tests/<folder>/` reaches inner modules of `launcher/<folder>/` only, every other folder through its `index.ts`, while `launcher/tests/support/` uses `index.ts` files only. Every check reads the same source files: `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs` and `.cjs`, outside `node_modules/` and `launcher/dist/`.
- `test/docs-sync.test.ts` checks that every extension whose code changed since the base commit also changed its `README.md`, `ARCHITECTURE.md` and `STRUCTURE.md` and the root `ARCHITECTURE.md` and `STRUCTURE.md`. `launcher/` counts as one unit with its own three docs, and neither changes under a `tests/` folder nor a change to `launcher/THREAT-MODEL.md` or `launcher/CONFIGURATION.md` count as code. It checks only that they changed, not how. The base is the merge base of `HEAD` with `origin/main`, or `main` when there is no `origin/main`; `DOCS_SYNC_BASE` overrides it, and CI sets it to the pull request's base commit.
- knip (`knip.json`, part of `npm run check`) finds unused exports, types, enum members, files and dependencies, the entry exports of the 15 `index.ts` files included.
- `tsc` checks types only. CI runs `npm run check` and checks that `npm pack` ships the 15 entry files and no tests, fixtures, `test/framework/` or `test/evals/`.
- Provider names and the write locations below are kept by review.

## Files the extensions write

Everything lives under pi's agent dir or session dir (`~/.pi/agent` by default; the `sessionDir` setting or `--session-dir` moves session data), except:

- handoff documents, in the OS temp dir: `pi-handoff/<session id>/main-handoff.md` for the main session and `pi-handoff/<session id>/<agent id>-handoff.md` for agents;
- `worktree: true` agents: a checkout under `<cwd>/.pi/worktrees/`, git's `pi-agents/…` branch and `.git/worktrees/` metadata;
- two project files written on the user's command in a trusted project: `.pi/pi-subagents.json` (`/agents setup`, which offers only the user file in an untrusted project and whose write may follow a model tool call once the user confirms the form) and `.pi/mcp.json` (`/mcp-import … project apply`, or the interactive `/mcp-import` picker);
- `<cwd>/.pi/.gitignore` (`*`), written once by whichever of the writers above creates `<cwd>/.pi/`; every write under `<cwd>/.pi/` goes through `platform/shared` (`writeSettingsFile` for a project settings file, at the path `settingsPath` picks for its scope, `ensureProjectSubdir` for a folder, with the folder's own `.gitignore` when asked), which owns the `.pi` name and the `.gitignore`, so no extension can create `.pi/` without it, so a new `.pi/` stays out of git; an existing `.pi/` is never touched, and deleting the file tracks `.pi/`.

The launcher (`launcher/`, host side) is the one exception outside the extensions: it writes nothing under `<repo>/.pi/` and no file into a git dir; every file it writes, its state under `<agent dir>/pi-sandbox/state/`, the user config `<agent dir>/pi-sandbox/config.json` through `pi sandbox init`, the sandbox status file it renders into the repository's render folder, the mount points and missing hooks dirs it creates in a repository and the allowlisted preference keys it writes back from the sandbox into the host `settings.json` and `pi-*.json` files included, is listed in [Files written](launcher/ARCHITECTURE.md#files-written) in `launcher/ARCHITECTURE.md`. Its engine objects, among them the pod and service containers of the config's `services`, are listed there too; service volumes are shared by every folder of the install (one launcher state folder, one per agent dir by default) and stay until `pi sandbox reset --services` or the uninstall.

`/agents create` writes nothing itself: it briefs the main session, whose own write tool creates the agent file. Inside the agent and session dirs: settings files `<agentDir>/pi-<extension>.json` (and `<cwd>/.pi/pi-<extension>.json` in trusted projects), pi's own global `<agentDir>/settings.json` (model-default writes `defaultProvider` and `defaultModel` through pi's `SettingsManager` whenever the user picks a model in the main session, and adds the model to `enabledModels` when a scope exists and leaves it out, as pi's Ctrl+S does, and writes `defaultThinkingLevel` whenever the user picks a thinking level in the main session, never for the reset or clamp of a model switch, nor for the model and thinking level a handoff restores), custom session entries named `<namespace>:<kind>` (such as `pi-spending:usage`, `pi-adapter:kept-selection`, the model and thinking level a handoff carries into the new session and restores without moving pi's defaults, `pi-adapter:previous-session`, the session file, leaf and seam label a handoff shows above the new session (with what pi's resume draws of it, kept entries left out, closed by a labelled rule), `pi-context:snapshot`, `pi-transcript:answer`, the rule drawn above the final answer of a settled turn (the adapter's `labelledRule`) and stored before it, `pi-session-limits:kept-rule` and `pi-session-limits:kept-message`, the rule and the user-message look, drawn flush with the chat like pi's own bubble, a message typed during a handoff is shown with in the old session), and the agents dir of each session, described in the [subagents architecture](extensions/subagents/ARCHITECTURE.md). Prune writes a liveness marker `<agentDir>/pi-prune/live/<session id>.<pid>.json` while a session is open, and `/prune` writes `<agentDir>/pi-prune.json` when the user picks an `Auto-prune` interval. Registries, ledgers and limit phases live in memory and are lost on reload.

Prune is the only extension that removes sessions: once per pi process, and when the user confirms an interval in `/prune`, it removes the session files under `<agentDir>/sessions/` last written before the cutoff, then their agent runs and handoff folders, plus orphan runs, old orphan handoff folders, the liveness markers of ended pi processes and, at session start, empty handoff folders. It keeps every chain of sessions linked by `parentSession` that holds a live or fresh session, runs that keep a worktree or are recent, session files without a readable header, and anything behind a symbolic link ([prune README](extensions/prune/README.md)).

## Folders

- [pi-adapter](platform/pi-adapter/ARCHITECTURE.md): the only shipped code that imports pi; the host, the agent runtime and the UI bridge. Its `KeyPress.shortcut` is what every letter hotkey matches, so the hotkeys fire on the same physical key in a Cyrillic layout. A child session takes every message through one `ChildSession.send`, routed or custom, shown or hidden, so the subagents runner routes without telling them apart.
- [shared](platform/shared/ARCHITECTURE.md): pi-free, theme-free, host-free helpers and the cross-extension formats. Its `formatDuration` and `formatPercent` give `""` and `formatCost` nothing for a value that is not finite; every caller then leaves out the figure with its label, brackets or separator. A whole percentage rounds as `Math.round` does.
- [ui-kit](platform/ui-kit/ARCHITECTURE.md): theme-aware components: the row language, hints, lists, fixed-height scroll windows, forms and tabs, flat or grouped in labelled rows.
- [extension-manager](platform/extension-manager/ARCHITECTURE.md): `createManagedExtension`, plugins, the bus and settings. An extension that uses its `pi-<name>` namespace outside `api/extension.ts` (settings file, notices, entry types, signal sources, message prefixes) exports it once as `NAMESPACE` and passes that constant to `createManagedExtension`.
- Extensions, each with its own architecture: [command-aliases](extensions/command-aliases/ARCHITECTURE.md), [composer](extensions/composer/ARCHITECTURE.md), [context](extensions/context/ARCHITECTURE.md), [footer](extensions/footer/ARCHITECTURE.md), [mcp-import](extensions/mcp-import/ARCHITECTURE.md), [model-default](extensions/model-default/ARCHITECTURE.md), [notifications](extensions/notifications/ARCHITECTURE.md), [questionnaire](extensions/questionnaire/ARCHITECTURE.md), [prune](extensions/prune/ARCHITECTURE.md) (plans the sweep from the disk, then applies it; liveness markers keep the sessions of running pi processes), [session-limits](extensions/session-limits/ARCHITECTURE.md), [spending](extensions/spending/ARCHITECTURE.md), [style](extensions/style/ARCHITECTURE.md), [subagents](extensions/subagents/ARCHITECTURE.md) (every `run_agent` batch runs in the background and wakes its caller once, also when the caller stops one of its agents with `stop_agent`; an agent's handoff waits for its open batches and passes their results to its successor; a launch or settle step that throws closes the agent `failed`, so its batch still settles; the walks along a chain stop at a link they already visited, so a loop in restored manifests yields a shorter chain, and `registry.restore` repairs restored links (pairs one-sided ones, cuts link and caller cycles) so the agent list never meets a cycle, and the shared duration, cost and percentage formatters print a value that is not a finite number as empty, which `agent_status` leaves out; a skill listed twice in an agent file, a settings override or `/agents setup` is kept once with a warning, and a settings `skills` override with bad or unknown names keeps only the good ones, never widening to the agent file's grant; a skill may be named by any name pi loads that has no comma, whitespace or control character, and a model value outside `run_agent` is `[provider/]id[:thinking]` or `inherit[:thinking]`), [transcript](extensions/transcript/ARCHITECTURE.md) (a shell row reads both forms of pi's timeout status line as `timed out after Ns`), [working-indicator](extensions/working-indicator/ARCHITECTURE.md). `style` applies its `concise` prompt when no settings file names a style. `session-limits` lets the new session carry on by itself after every automatic handoff, whatever its Status, and keeps the messages the user sends while a handoff is in flight (through the adapter's `Host.onInput`, pi's `input` event) for the new session, as its user messages after the seed or in its editor, instead of answering them in the old one, composed only when the new session is ready.
- [launcher](launcher/ARCHITECTURE.md): the standalone `pi-sandbox` command (the package `bin`, run from `launcher/dist/`, which `prepack` builds with `npm run build:launcher`) that runs pi on a Colima VM in a container of its own for each launch, removed when pi exits (a daily pass also removes the stopped containers, unused volumes other than shared ones and free networks named `pi-sandbox-*` that older builds left with the managed label and without an install label, and, in the default state dir, the state entries the current layout does not name once they are a day old), with no credentials inside; commands that start no session (pi's help, `--version`, `auth`, `config` without `-l`, `--list-models`, `--export`) and every `pi update` form run on the host instead, with host pi and without a sandbox. Pi inside gets the host's providers, MCP servers, settings and packages with every secret replaced by a placeholder, a filtered copy of its agent dir resources and of `~/.agents/skills` that follows no symlink (each skipped link named in a notice shown once per install), `settings.json` resource paths pointed at the repository or that copy or dropped with a notice, its unversioned, range and tag npm sources and its git sources whose host commit is on the remote pinned to the versions the host installed and reinstalled at the next launch after they change on the host; an allowlist of data-only preferences changed inside (by default the default model, theme, the extensions' `pi-*.json` settings; `writeBack` in the config can drop, add or recheck keys inside a ceiling the code owns, or turn it off) is written back to the host when pi exits, the host winning a conflict; its only network exit is an allowlisting proxy on the host, one for each install, that injects the real credentials (derived from the host pi files, glab, which gives no notice for a host never logged in to while another has a token, and the npm, pip and Maven configs, or configured rules), signs in to MCP servers with host pi, and always allows `pi.dev` for pi's model list unless `egress.deny` names it; a provider login host pi cannot resolve is reported as missing or expired, with the host pi command to log in again, at the end of the launch and as a `warn` rule check in `pi sandbox doctor`, and a rule host the proxy refused (a private address, say) gets the same hint under its `fail` rule check. The doctor reports its checks by area (host, sandbox, network, credentials, leak sweep), with the reasons and a `hint:` under each problem, the launch notices in one section and a result line; its leak sweep does not check `env.set` values that match the config and names the secret-named ones it skipped, so a secret written into `env.set` is not caught. One config file decides the limits, `<agent dir>/pi-sandbox/config.json`, owned by the user who runs it; there is no administrator layer. Its `env.set` gives every sandbox process fixed variables (a name the launcher sets is refused, and an `env.set` name is not forwarded from `env.allow`), and `resources` caps each container's processes (4096 by default), open files and `/dev/shm` besides its CPUs and memory. Behind a TLS-inspecting proxy its `tls.extraCa` names the network's CA by keychain fingerprint or PEM file, trusted by the proxy, the container and image builds; the proxy's CA and certificates are dated an hour back, so a VM clock a little behind the host's still accepts them, and the always-built image layer bakes these CAs into the system store and every JDK's `cacerts`, its `net.properties` pointed at the proxy. The proxy's token never enters the container: a node relay on the install's network holds it and sends it as a preamble line ahead of each connection, the proxy checks that line on the raw socket before any HTTP (bounded, timed, constant-time) and ignores and never forwards a `Proxy-Authorization`, the proxy is `http://pi-sandbox-proxy:3128` inside with no credentials (no `JAVA_TOOL_OPTIONS`, no token variables, Maven settings without a password), and the install's network is created with an isolated gateway (Docker Engine 28 or later): it has no gateway, the VM has no address on it, the relay holds `.1` with only port 3128 open, a joining container has no default route, and the engine's DNS answers no outside name, so tools reach the network only through a CONNECT by name. The layer copies this launcher's entrypoint, bash hint and services forwarder, so a pinned base still gets them. Its `mounts.volumes` are named volumes shared by every folder of the install, kept until the uninstall; its `mounts.binds` are read-only binds of host paths, whose sources the VM shares read-only (a source inside a share needs none, one that holds a share is refused, and one inside or around a host path the launch mounts writable, such as the repository, a workspace root, a git common dir or the host sessions dir, is refused, with a short window left between the check and the engine's create that THREAT-MODEL states); every mount target is checked against the trees the launcher owns and against the others; its `setup` argv lists run in the container, as pi with pi's env in the repository, after the hand-over and before pi, under a per-repository preparation lock that a second session of the folder waits on. The container's entrypoint waits for the launcher's hand-over of the owned volumes before it writes into them, the launcher waits for the entrypoint's ready marker before the steps that use the home (an image whose entrypoint has no marker is not waited for), and a container that exits during startup is named as such. The image sets `LANG=C.UTF-8` and the host's `LANG` is not forwarded by default, so perl and other programs find a valid locale; `sudo`, `doas` and `systemctl` get a hint that the sandbox has no root. The proxy gives up on an upstream lookup, connect or TLS handshake after 10 s, never on a response. While pi runs, with `vm.releaseFileCache` on (the default), the launcher drops the VM's file cache with one fixed root command through `colima ssh` when the Mac process behind the VM holds as many open files as the lower of half `kern.maxfilesperproc` and a quarter of `kern.maxfiles`, so a very large build over virtiofs does not exhaust the Mac's file descriptors; it finds that process through the instance's `disk` file or the `diffdisk` an older Lima named it, and the doctor's `file cache` check shows the same count and limit without releasing. It refuses folders that would mount protected paths (checked before any folder is searched) and repositories whose git layout it cannot trust (the cases are listed in [launcher/THREAT-MODEL.md](launcher/THREAT-MODEL.md#3-baseline-guarantees), summarised in [launcher/README.md](launcher/README.md#where-pi-can-start)); it binds the hooks dirs read-only, reports changes to the rest of `.git` after the session, binds bare repositories in a workspace read-only, mounts nothing outside the folder for a checkout whose git dir lies there, shares host pi's session directory of the folder, on a Mac with `terminal.clipboard` on also puts what pi copies (OSC 52) on the host clipboard with `pbcopy`, and copies a pasted image path, or the clipboard PNG or single copied image file on Ctrl+V, to `/tmp/pi-paste/` inside and pastes that path (a failed import shows an OSC 9 notification and pastes the original), with `vm` set restarts the VM to that size when no other launch is live (the disk only grows), with `workspaceRoots` set restarts the VM so it shares only those roots, the session dir and a read-only `<state>/vm` dir (never the home; a root that is, holds or lies inside a protected path or system dir is refused, and a running launcher container of another agent dir holds the restart), removes the folder's containers and created folders when its last session exits, and the install's services, relay, network, proxy and token once no session of the install runs; these end-of-session steps skip only when another launch is registered, otherwise they wait for the lock (one line is printed, Ctrl-C ends the wait), and the uninstall holds the ground and registry locks, so no launch registers meanwhile. A failure right after a launch registers is cleaned up by that launch. The config's `services` run in containers of their own that join the network namespace of one pod per install, confined (no capabilities, read-only root, a numeric non-root user, their own `env` only); the pod sits on the install's network under the alias `pi-sandbox-services`, and a forwarder in each agent container listens on every service port on `127.0.0.1` and `::1` and passes the connection to that alias, so pi reaches a service at `localhost`. The services start under the install's ground lock, and changed services wait until every session of the install has ended. Every launcher container carries a `pi-sandbox.role` label (agent, relay, pod, service), and only agents count as sessions. Images are shared by every install on the VM, and a stop, a VM change or an uninstall sees another install only through its running agent containers, which its refusal names with a `docker --context colima-pi-sandbox rm --force <name>` hint. An interactive `pi sandbox init` (`cli/setup/`, over the hand-rolled prompts of `cli/prompt/`), which plans the same VM shares as a launch, bind sources included, sets the project folders (an added folder inside a checked one replaces it, so an add never leaves two checked folders nested), the VM size and the settings write-back and creates or restarts the VM: it shows the file diff and the VM action and writes nothing before Apply, and `--yes` prints the same review and applies the same plan through the same steps, printed as lines; without a terminal it refuses, and `--yes` applies the current settings without asking, which `install.sh` uses when it finds no terminal. `install.sh` runs its commands directly on a terminal under ruled step headers, and learns that the smoke doctor skipped the sandbox part from the exit code of the hidden `__smoke-doctor`. Its threat model and known gaps are in [launcher/THREAT-MODEL.md](launcher/THREAT-MODEL.md).
- [test/framework](test/framework/ARCHITECTURE.md): fakes, harnesses, real-pi helpers, live and eval mechanics.
- [test/evals](test/evals/README.md): prompt-quality runs with real agents, local only.
- `test/architecture.test.ts`: the repo-wide structure test above.
- `test/docs-sync.test.ts`: the docs sync test above.
