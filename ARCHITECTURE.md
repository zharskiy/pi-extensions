# Architecture

How the thirteen extensions work at runtime. Folder layout is in `STRUCTURE.md`.

## Layers and dependency rules

- `core/adapter` is the only code that imports pi (`@earendil-works/*`, `typebox`). It exposes `contract.ts`: `Host` (the main session as seen by an extension) and `AgentRuntime` (spawning and reading agent sessions).
- `core/manager` is pi-free shared infrastructure: plugin manager, typed bus, settings parsing, `settleWithin`, and the cross-extension contract: `handoff.ts` (handoff sections, `HandoffValidation`, `validateHandoff`) and `channels.ts` (the `pi:busy`, `pi:awaiting-input`, `spending:usage` and `spending:totals` channel names, payload types and parsers), plus `format.ts` (`formatTokens`, `formatDuration`, shared by the footer, the working indicator, context and subagents, `formatWindow`, the context window in whole thousands or tenths of a million, shared by the footer and context, `errorText`, shared by the settings loader, session-limits and subagents, `homeRelative`, a path under the home directory as `~/…`, shared by context and mcp-import, `shortPath`, a path relative to the working directory or else home-relative, shared by the transcript rows and the working indicator, `noun` and `counted` (`1 agent`, `3 agents`), and the receipt format: `formatCost` (`$0.04`, `<$0.01`, zero omitted or `$0.00`), `formatCalls` (`1 call`, `4 calls`), `receipt`, the ordered segments of a state word or failure reason, the time (`Elapsed …` only while running), calls, tokens, cost and activity, with empty ones omitted except `0 calls` on `Stopped`, and `receiptText`, which joins them with a muted ` · ` (`plainReceipt` joins the bare text) and drop the activity, then the cost, the calls and the tokens to fit, never the word or the time), `cache.ts` (the cache hit rate, its colour thresholds and `cachePercentText`, the rounded percentage in its colour, shared by context and the footer), `layout.ts` (`PAD`, `DOT`, the one ` · ` separator, `ELLIPSIS`, pi's ASCII `...` and the only cut mark, `cutStart`, a cut at the start by columns, the accent `rule` and `prefixed`/`padded` wrapped lines), `hints.ts` (the hint grammar: `EXPAND_BINDING`, `expandHint`, `appendHint` and `countLine`, described with the rows below, plus dim `hintLines` and `keyHints`, the bottom-strip grammar `enter to view · x to stop` with keys dim, words muted and a dim ` · `), `marks.ts` (the state marks below), `list.ts` (the selectable list over `ThemeLike` and `KeyPress`: `listLines` with descriptions `below` or `beside` the label, `listKey`, and the shared `SELECT_HINTS`/`CANCEL_HINT`, used by the questionnaire form, the `/style` picker and the subagents forms), `select.ts` (`selectForm`, a single-choice `FormFactory` for `HostUi.showForm` over the list), `tabs.ts` (the tab bar `← □ A  ■ B  ✓ Submit →` and `tabStep` for Tab/→ and Shift+Tab/←, used by the questionnaire and `/agents setup`) and `multi-select.ts` (checkbox rows over a scroll window: Space toggles, `a` all, `n` none; `initialMulti`, `multiKey`, `multiLines`, which cuts each description to one row, `descriptionRoom`/`descriptionFits`, the room it leaves (used by `/agents setup` to decide when to show a skill's full description), and `scrollWindow`, used by `/agents setup` for skills; and `multiSelectForm`, a `FormFactory` that returns the checked values on Enter and `undefined` on Esc, used by `/mcp-import`), and `row.ts`, the pi-native row layout every row of the package is built with (pi's tool rows, the run_agent block, the subagents and questionnaire tool rows, the `/context` row, the handoff seed row). `MARKS` are one single-column glyph per state, read by shape first and colour second: `◌` pending (`dim`), `✓` success (`success`), `✗` error (`error`), `⊘` stopped, cancelled or handed off (`muted`, since a call you stopped needs no attention), `»` informational, a row with no state (`accent`), plus `↳`, the dim mark of a row's first outcome line, and `›`, the accent selection pointer (pi's message cursor). `Mark` names the five states, `markGlyph` paints one in its token, and `markOf` derives it from a call (pending until started (the adapter counts a call with a result as started) and while partial, stopped when aborted, then error or success). The grid is two columns: the glyph at column 0, the title at `TITLE_COLUMN` 2, `↳` at 2 on the first child line with the child text at `CHILD_COLUMN` 4 and every later child or body line at 4, and a nested row (an agent in a run_agent block, a codemode sub-call, a `/context` section) shifted by `NEST` 4, its glyph at 4, its text at 6 and its own `↳` at 6. `row`/`rowChildren` build a row from a `MarkedRow`: a title (plain, multi-line with continuation at column 2, or `TitleParts` laid out by `titleLine`), children (styled lines or nested rows), an optional hint and an optional body drawn at `width - 4` and indented 4; blank lines stay empty. `titleLine` gives the title its width priority: the glyph, the failure reason or state word, the verb, the target (paths cut at the start by `cutStart` so the file name stays, everything else at the end), the arguments, which are cut before the target, then the duration, which drops first (hints go on the last line through `MarkedRow.hint`); the parts after the target join with a muted ` · `. `failureSuffix` decides whether a reason goes on the title as ` · reason` (one line, at most 32 columns, beside at least 8 columns of target) or onto the `↳` line. The hint grammar is pi's: `expandHint(key)` is the dim `(ctrl+o to expand)` for the key of `EXPAND_BINDING` (pi's `app.tools.expand`), and none when the key is unset; `appendHint` drops a hint that does not fit, except that a one-line summary that must be cut anyway keeps 20 columns; `countLine` is pi's tool-renderer count line, `... (37 more lines, ctrl+o to expand)` with `more`/`earlier` and `line`/`item`, whose `, key to expand` part drops first when narrow while the count stays; bottom strips use `keyHints`, so every hint reads `key to verb` with pi's lower-case key names. `wrapChild` wraps a child at column 4, `preview` keeps the head or the tail of an output with the hidden count in logical lines, and `rowText` is the small helper the tool renderers share. Every row's status line is a receipt from `format.ts` (time first, then calls, tokens and cost; a state word such as `Stopped` or a failure reason leads). All of them use only `contract.ts` types, so they stay pi-free. Channel names and the handoff format live only there; extensions and subagents plugins import them from there, never from each other.
- Extensions import only `contract.ts` and `core/manager`. Each extension's `src/index.ts` is the single file allowed to import `pi-adapter.ts`.
- Extensions never import each other; they talk over pi's shared event bus (`Host.publish/subscribe`) and, for tool rows, over the tool-rows record on `globalThis` (`Symbol.for("pi-extensions.tool-rows")`, `pi-row-component.ts`), through which the rows one extension registers reach the transcript panes another draws. Plugins inside an extension never import another plugin's folder; they share code through `src/model` and `src/components` and talk through the manager.
- No provider knowledge: no code or prompt names a model provider or a model id. Pi resolves providers, credentials and models; the harness passes `provider/id[:thinking]` strings through. The only exceptions are configuration: the shipped agent files name their `model`, and the subagents README lists those models. Cost is pi's own usage and cost figures.
- `test/architecture.test.ts` enforces the import rules above by scanning imports, plus: `core` never imports `extensions`, no tests inside `src`/`core/adapter`/`core/manager`, `core/test` holds only `adapter` and `manager` tests, and extension tests reach the adapter only through `contract.ts` and `core/test/adapter` (no pi package, no other adapter module). Which files may import pi packages (`core/adapter`, and among tests only `core/test/adapter`) is otherwise enforced by biome's `noRestrictedImports` overrides in `biome.json`.

## Startup and the adapter

1. pi loads each entry listed in `package.json` (`pi.extensions`). Each default export is `createPiExtension(boot, { root, namespace, childExclude })`.
2. The factory returns immediately when it runs inside an agent session (an `AsyncLocalStorage` scope set while children load), so no extension boots inside an agent.
3. Otherwise it builds a `Host` over pi's `ExtensionAPI` and an `AgentRuntime` over pi's SDK, then calls `boot(host, runtime, paths)`.

Host behaviour worth knowing:
- The adapter keeps the latest pi `ExtensionContext`, captured on every event, tool call and command. On `session_shutdown` every registered handler runs even if an earlier one throws, the context is then always dropped, and the first error is rethrown afterwards so pi reports it.
- `Host.session()` always returns a `SessionInfo`; outside a live session (before `session_start`, after `session_shutdown`) it throws, and so do `readEntries`/`sessionUsage` without a file argument. Every other Host call that needs the context (UI, `publish`, `appendEntry`, `sendUserMessage`, `dispatchCommand`, `isIdle`) is then a no-op. Code that can run after its own shutdown (spending, for reports arriving while other extensions shut down) must not call `session()`.
- `onSessionStart(info, parent)`: `parent` is the session file a freshly created session came from (its header's `parentSession`): `/fork`, `/clone`, or a handoff switch. It is unset for a plain `/new` and for resume, startup and reload. `readEntries(customType, file?)` and `sessionUsage(file?)` read the live session, or another session file when one is given. `onCompact` fires after pi compacts the main session.
- pi builds a fresh extension instance and event bus for every session (`/new`, `/resume`, `/fork`, `/reload`) and fires `session_start` once per instance, except in RPC mode where it fires twice. State therefore starts empty in each instance: handlers that only reset state at session start and unsubscribe handles at shutdown are not needed. Settings are the exception below.
- `onIdle` is pi's `agent_settled` and passes `{ aborted }`, true when the run that just settled was aborted; `onTurnEnd` passes a `ContextSnapshot` (tokens, window, percent).
- `onPhase` is computed by `pi-phase.ts` from `turn_start`, `message_update`, `message_end`, `tool_execution_*` (top-level only), `agent_end`, `agent_settled`; `idle` fires after `onIdle`. `PhaseDetail.tools` lists each running top-level tool with its `name`, the `args` of `tool_execution_start` and, for an MCP tool, its `server/tool` `label`; `toolName` is the last of them. A phase is emitted whenever the phase or the set of running tools changes.
- `pi-editor.ts` installs one `HostEditor` subclass when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `onEmptyEditorDown`, `onEmptyEditorEscape`, `captureEditorKeys`) is used; the frame is optional; keys reach the hooks only while the editor has focus. `onEmptyEditorEscape` fires on pi's interrupt key (matched by keybinding, so a rebound key works) when the editor is empty, pi is idle and no autocomplete shows; a handler returns true to consume the key, otherwise pi gets it. The frame's `decorate(lines, layout, paint, theme)` gets the border paint and a `ThemeLike` over `ctx.ui.theme` of the adapter copy that set the frame (no theme, no frame). Every extension of the package shares that editor: pi loads each extension with its own module cache, so the frame, hooks and installed factory live in one record on `globalThis` (`Symbol.for("pi-extensions.editor-hooks")`, like `pi-scope.ts`). Hooks registered while the extension loads are kept and the adapter installs the editor at `session_start`; at `session_shutdown` each adapter copy drops what it registered. It removes the editor again when no frame and no hook remain. The record also holds the ↑ input history, kept by `pi-editor-history.ts`, which each `HostEditor` takes as one collaborator: it points pi's private `history` array at the shared one, so prompts survive pi rebuilding the editor on `/reload` and `/new`, and on `/resume` and `/fork` the copy that installs the editor seeds it with the session's user messages, as pi does for its own editor.
- `onDialog` is pi's `ui_prompt_start/end` (outermost dialog only; overlays are `custom`). `HostUi.onKeyPress` observes terminal input without consuming it.
- `sendUserMessage` and `dispatchCommand` deliver immediately when idle, otherwise as a follow-up (pi counts a run as busy from its submission, and still runs an extension command at once). `sendHiddenMessage` sends a `display: false` custom message: a follow-up of the active run, or, when idle, a message that starts a run itself (`triggerTurn`); pi emits `before_agent_start` for such runs, so `setMainPrompt` applies, and nothing is rendered. While pi is busy without a run (a compaction) the message is held until idle; a run starting meanwhile takes the held messages as follow-ups; several messages sent in one pass go out as next-turn messages behind the first, which starts one run for all of them.
- `AgentRuntime.skillCatalog()` lists the available skills as `{ name, description }`; `skillNames()` is the same list by name: where skill names come from (agent files, overrides, `/agents setup`, `/agents create`). `sessionSkillNames()` is the main session's loaded skill commands, read live from `getCommands()` (settings exclusions applied): the main session's effective skill set, and what `skills: all` resolves to when the main session is the caller. The inventory (`pi-skills.ts`) is the main session's loaded skill commands first (`--skill` paths, `resources_discover` additions), then, under names not already taken, every skill pi's default discovery finds for the main cwd and agent dir: pi's `DefaultPackageManager.resolve` with missing packages skipped (never installed), over a settings manager whose storage reads the user and project settings files without a lock, drops writes and strips the `!` and `-` entries of their `skills` arrays (so those exclusions apply to the main session only; plain entries, globs and `+` includes stay, as do other resource types and package filters), its enabled skill paths (auto-discovered skill folders mapped to their `SKILL.md` as pi's resource loader does; packages already give `SKILL.md` files) and loaded by `loadSkills` (`includeDefaults: false`). Nothing is written; the project's `.pi/skills` and `.agents/skills` count only when it is trusted. Skills with `disableModelInvocation` are included; the loader's diagnostics (collisions) are dropped. An extension built with `createPiExtension(…, { skillInventory: true })` (subagents only) scans in a `session_start` handler registered before the host's, so the scan ends before any start handler (and the definitions load) runs; every session start (pi's `/reload` included) scans again. A failed scan is not caught: pi's runner reports a throwing `session_start` handler as an extension error and runs the remaining handlers. Before the first scan, during and after a failed one and in other extensions, the inventory is the loaded skill commands alone. The main session keeps whatever skills pi gives it; the discovered part of the inventory does not depend on them (only the loaded part does). The adapter's `sessionSkillFiles(pi)` reads the loaded skill commands; the runtime gets them as `ParentSource.sessionSkillFiles` and the inventory as `ParentSource.inventorySkillFiles`. `AgentRuntime.availableModels()` (`pi-models.ts`) is the model catalogue for `/agents setup`: every model of pi's registry whose provider has configured credentials, as `provider/id` with its context window, input and output price and the thinking levels it accepts (pi-ai's `getSupportedThinkingLevels`: `off` alone for a model without reasoning; `xhigh` and `max` only when the model maps them), sorted by ref; credentials are checked once per provider. `AgentRuntime.reserveCodemodeWorkers(agentSessions)` (`pi-codemode.ts`) sizes pi's process-wide codemode worker cap, which every in-process agent shares: it sets `PI_CODEMODE_MAX_WORKERS` to `agentSessions` plus two spare workers (the main session, and a cancelled worker that is still exiting) unless the value was set by someone else, recognises the value it wrote last through a `globalThis` marker shared by every adapter copy (so `/reload` re-applies it rather than taking it for a user value), never changes a value it did not write (an invalid one counts as unset), and returns a `CodemodeShortfall` (`setting`, `workers`, `wanted`) when such a value is below the wanted count, otherwise `undefined`.
- `setMainPrompt` replaces pi's default prompt in `before_agent_start` and re-adds the `tools`, `rules` and `docs` sections pi would otherwise drop (`main-prompt.ts`). Only the subagents `run-agent` plugin calls it, so the main prompt is replaced only when that plugin is enabled.
- `ToolSpec` and overlay/widget factories are plain-text contracts; the adapter converts them to pi tools and TUI components. UI calls degrade to no-ops outside TUI mode. The `ThemeLike` every renderer receives carries `width(text)`, `truncate(text, cols)` and `wrap(text, cols)`, pi-tui's `visibleWidth`, `truncateToWidth(text, cols, "...")` (pi's own ASCII ellipsis, the one every pi tool renderer cuts with) and `wrapTextWithAnsi` (`textMetrics` in `pi-tools.ts`; plain text comes back plain, the resets pi wraps around the ellipsis are stripped; `wrap` keeps at least one column), so the extensions measure, cut and wrap text by the rule the adapter cuts their lines with (`fitLines` in `pi-tools.ts`, used for widgets, overlays, forms and entry renderers). `ThemeToken` names roles, not pi's colours: the status colours (`accent`, `muted`, `dim`, `success`, `warning`, `error`, `text`), pi's chrome colours `border` and `borderAccent`, and `thinkingOff` through `thinkingMax`, pi's thinking-level colours of the same names (an extension maps `Host.thinkingLevel()` to its token itself; `/context` leaves `thinkingMax` unused so red there only means failure). Two syntax-highlighting tokens are exposed as an exception, used only for the footer's git branch: pi's chrome palette has only blue, violet, greys and state colours, and the folder, model name, values and gauges already take those. The branch is `syntaxString` (pi's orange), or `syntaxVariable` (pi's cyan) when the theme paints `syntaxString` with exactly the same escape as `success`: pi's system theme takes `syntaxString` from the terminal's green slot, and the branch must not look like the gauge. `italic(text)` and `inverse(text)` are pi's `Theme.italic`/`Theme.inverse`; `panels` is false when `getBgAnsi("toolSuccessBg")` is the bare default background `\x1b[49m` (pi's system theme without a terminal colour report), so renderers can fall back from background panels to foreground colour and inverse. `bg(token, text)` paints a background by `BgToken`: `added` and `removed` are pi's `toolSuccessBg` and `toolErrorBg`, `addedWord` and `removedWord` those colours mixed 40% toward `toolDiffAdded` and `toolDiffRemoved` (pi-tui's `mixColors` over `Theme.colors`, applied with `Theme.style(text, { bg })`).
- `ToolSpec` also carries pi's `promptGuidelines` (bullets pi adds to the prompt's guidelines while the tool is active; `main-prompt.ts` keeps them when the main prompt is replaced), `executionMode` (`sequential` or `parallel`) and `modelOnly` (the model calls the tool directly and codemode scripts cannot; `toPiTool` maps it to pi's `model-only` exposure and passes the others through unchanged).
- `KeyPress.name` names pi's editor bindings (`up`, `down`, `left`, `right`, `toggleTools`) and the fixed keys `pageUp`, `pageDown`, `home`, `end`, `enter`, `escape`, `backspace`, `space`, `tab` and `backTab` (Shift+Tab, pi-tui `Key.shift("tab")`); anything else is `other` with `char` for a single character, and every key carries `raw`, the terminal data.
- `HostUi.showForm(factory, { signal })` (`pi-form.ts`, with `pi-overlay.ts` and `pi-text-input.ts`) shows a form inline, in the editor's place, through pi's non-overlay `ctx.ui.custom` (pi saves and restores the editor text). Before it opens it waits until no overlay is visible (`overlaysCleared`: `TUI.hasOverlay()`, polled every 100 ms on an unref'd timer; the TUI is the last one a widget or overlay saw, or is captured through a widget factory that is removed at once), because pi would move focus to the inline form while an overlay such as `/agents` still covers it. The factory gets `theme`, `requestRender`, `done(value)` and `createTextInput()`, a pi-tui `Editor` behind `TextInput` (`render`, `handleKey`, which forwards `key.raw`, `text`, `setText`, `onSubmit`) whose `focused` follows the form's, so the hardware cursor and IME land in it. The promise resolves with the value given to `done`, or `undefined` outside tui, when the signal aborts (while waiting or before the form opens, nothing is shown; while open, the form closes), or when the session changed while it waited. Keys are named by `keyPress` and every line is cut to the width, as for overlays.
- `setPromptSection(name, text)` adds a named section (`<name>…</name>`, placed by pi after `cwd`) to the main session and to every agent at any depth; `undefined` removes it. Each extension loads its own adapter copy, so the sections live in one record on `globalThis` (`Symbol.for("pi-extensions.owned-prompt-sections")`, `pi-sections.ts`), each stored with an owner token of the adapter copy that set it. The adapter applies them in `before_agent_start` of the main session, after `setMainPrompt`'s replacement and independently of it, and the hidden child extension applies them in each child's `before_agent_start`, so a change reaches the next run of the main session and of every agent. At `session_shutdown` each adapter copy drops the entries it still owns, so a copy that set the same name, even with the same text, keeps its section.
- `ToolSpec` renderers receive `ToolRenderState` (pi's render context: `toolCallId`, `expanded`, `isPartial`, `isError`, `args`, `invalidate`, plus `durationMs`, pi's recorded duration of a finished call, `result`, the latest result of the call, and `aborted`, set by the same text match as tool rows) and may set `renderShell: "row"` (pi's self shell through `RowComponent` in `pi-row-component.ts`: every line after pi's `outputPad`, rendered at the width left after it and cut with `...`, no background, empty lines without the pad, an empty render draws nothing; the call is rendered when pi draws the row, after `updateDisplay` has run both renderers, so a row's `renderCall` sees the result its `renderResult` was last given; pi puts one blank line before the call; the repo's tools build their lines with `core/manager/row.ts`); the `ToolResult` a `renderResult` receives carries `isError`; `update(text, details)` forwards details to partial renders. `execute` also receives pi's `toolCallId`, and an optional `pendingResult(toolCallId, owner)` supplies the partial result of a call still executing to transcripts read from a session file, which never see pi's partial updates; `owner` is the transcript's `createTranscript({ owner })`, the session that made the calls, since tool call ids are unique only within one session. The adapter keeps every spec an extension passes to `registerTool`, by name, and an overlay's transcript renders calls with them.
- `contextFacts()`, `lastRequestUsage()` and `mainRequestUsage()` (`core/adapter/pi-context.ts`, composed from `pi-context-prompt.ts`, `pi-context-messages.ts` and `pi-usage.ts`) measure the main session for `/context` and the footer. They return what pi exposes and no `/context` policy: `ContextFacts` is the model name, window, pi's total (or null), the compaction reserve, the system prompt as named sections with their text, every declared tool and every tool pi loads on demand with its source (`builtin`, `mcp` or `extension`), an `onDemand` flag and the size of its declaration in characters, and each conversation message with pi's `estimateTokens` figure (assistant messages also per content block); prompt usage figures are `PromptTokens`, the type `core/manager/cache.ts` reads too. `ToolInfo`, exposures, source paths and usage records stay inside the adapter. `mainRequestUsage()` is memoised on the session id, session file and leaf id, so a fork or resume never serves a stale figure; outside a live session the facts are undefined and the usage zero.
- `registerEntryRenderer(customType, render)` (`pi-entries.ts`) wraps pi's `registerEntryRenderer`: `render(data, width, expanded, theme)` returns plain lines, the adapter puts each after the shared output pad (pi gives entries no `outputPad`; the adapter reads pi's `outputPad` setting from `getSettings()` at every tui session start and then takes the `outputPad` of each tool render, kept on `globalThis` under `Symbol.for("pi-extensions.tool-rows")`; so a change of the setting during a session reaches entries only after the next tool render), renders at the width left after it, cuts each line with `...` and passes pi's tool-expansion state (`Ctrl+O`) as `expanded`. Custom entries are stored in the session file and never enter the model's context. `registerMessageRenderer(customType, render)` does the same for displayed custom messages (pi's `registerMessageRenderer`), with `{ text, details }` of the message (text parts joined) and pi's own `outputPad` as the pad.
- `registerToolRows(rows)` (`pi-tool-rows.ts`) restyles tool calls the repo does not draw itself. It registers one `pi.registerToolRenderer` resolver: for each tool name it takes `next()` (the renderers pi would use, built-ins merged in) and keeps them for any tool other than pi's built-ins (`read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`) that renders itself in any way (a self shell, its own `renderCall` or `renderResult`; pi's built-in `edit` draws its own frame, so the built-ins are always restyled), or when `rows` returns nothing for a probe view of the name; otherwise it hands pi a self shell whose call and result are `RowComponent`s over `ToolRow.call` and `ToolRow.result` (`(width, theme) => string[]`, from a `ToolCallView`: name, args, `argsComplete`, `started` (pi's `executionStarted`, or a result exists), `isPartial`, `isError`, `expanded`, `cwd`, `durationMs` (pi's recorded `ToolResultMessage.durationMs`, live, on resume and in the agent pane), `aborted`, `label`, and the result's text, details, `isError` and image count). The call's view is built when pi draws the row, not when it calls `renderCall`: `renderResult` keeps pi's result on the row's slot (a `WeakMap` on pi's renderer state, `slotFor` in `pi-row-component.ts`), and the call reads it, so a title can carry the failure reason, duration or abort of its result. `aborted` is pi's wording matched by `abortedText` (`pi-row-component.ts`): an error result that is exactly `Operation aborted` or `Aborted after N retry attempt(s)`, or a `bash`/`powershell` result whose last line is `Command aborted`; a result that is only the abort text reaches the rows as empty text. `label` is `server/tool` for an MCP tool: from `getAllTools()` (source path `builtin:mcp`, `namespace.aliases[0]` and the name after `<namespace>__`), else pi's own `mcp__<server>__<tool>` pattern (`mcpLabel`, the only source in the agent pane); the host looks each name up once. A component pi hands back is reused, and keeps its drawn lines per width until pi updates it (`renderCall`/`renderResult`) or invalidates it, so a frame does not recompute every row. When the row is expanded and sets `piBody`, the result also draws the base renderers' own `renderResult` (pi's diff for `edit`, the whole output for `read`, `bash`, `grep`, `find`, `ls`) under it, rendered at the width left after the pad and four columns (`CHILD_COLUMN`), leading blank lines dropped, hung under `  ↳ ` when the row draws no result line of its own and indented four columns otherwise, blank lines left empty, and without pi's `Took …`/`Elapsed …` timing line when the row sets `dropTiming`, with its own state and component kept per tool row (a `WeakMap` on pi's renderer state), so pi's renderer never sees the row's component; a throwing base renderer draws no body. The rows are also kept on the `globalThis` record with an owner token per registering copy, so a transcript pane of any adapter copy (the agent view) applies them through `applyToolRows`; at `session_shutdown` a copy drops its own rows, and the record falls back to the rows of the latest copy still registered, empty once none is. A row whose `call` or `result` throws draws pi's own call or result component instead. There are two paths to one source: pi's resolver closes over the `rows` it was registered with, the agent-view overlay reads them from the record. pi still wraps call and result in its click `MouseRegion` (a click toggles the row in fullscreen mode) and appends images.
- `HostUi.setHiddenThinkingLabel(label, hint?)` (`pi-ui.ts`, tui only) and `pi-thinking-label.ts`. There are no overrides of pi's message components: user and assistant messages are pi's own. The label is composed as `label`, or `label`, a space, a full SGR reset `\x1b[0m` and the hint in `dim` (`composeLabel`), because pi wraps the whole label in `theme.italic(theme.fg("thinkingText", …))` and chalk reopens italic after an inner `\x1b[23m` but leaves a full reset alone; so the hint draws dim and upright. The composed label goes to pi's `ctx.ui.setHiddenThinkingLabel` and onto a `globalThis` record (`Symbol.for("pi-extensions.thinking-label")`) kept per owner, from which transcript panes pass it to the assistant messages they build; `session_shutdown` releases the copy's own label. `pi-thinking-label.ts` also holds `OSC133_ZONE_PREFIX`, the prompt marks transcript panes take off pi's message lines. `HostUi.workingColumns()` is the room for the working message: `terminal.columns` of the TUI the adapter last saw (captured through a widget factory when none was seen yet) less the columns of the installed `EditorFrame` while it draws the editor (`frameColumns` in `pi-editor.ts`), pi's status border and its spinner; `undefined` outside tui. `HostUi.metrics` gives the extensions pi's `width` and `truncate` for text they fit outside a render.
- `terminalNotify(message, channel)` writes BEL for `bell`, and for `auto` only an OSC 9 notification (OSC 777 titled `pi` on rxvt), no BEL; tui only.

Unit tests use `core/test/helpers/fakes.ts` (fake host, runtime and child session) instead of pi, except that the fake theme's `width`/`truncate`/`wrap` are the adapter's `textMetrics`, so fixtures are measured as pi would; the fake `showForm` (`core/test/helpers/fake-form.ts`) keeps each form (`host.forms`, `host.form()`) so tests render it, press keys and type into a fake text input (`backspace` deletes), and it honours the signal; a few tests (UI and message-agent) import `core/test/adapter/offline.ts`, which loads pi offline, and only `core/test/adapter` tests import pi packages directly. `core/test/adapter` holds conformance tests against pi, offline.

### Child sessions

`runtime.spawn` returns a `ChildSession`. The adapter tracks a `running` flag, set when `start`, `send` or `wake` issue `session.prompt` and cleared on the `settled` event. While `running` is set (including the window before pi marks the session as streaming), `send(msg, "steer" | "followUp")` and `wake(text)` never call `prompt` again: they queue on pi's own steer or follow-up queue, so a message sent right after `start` joins the first turn and pi's "already processing" error cannot come from the adapter. When nothing is in flight they start a new prompt; if pi rejects it, the child emits an error `assistant_message` and `settled` so the runner closes the agent instead of hanging. If extension binding fails during spawn, the child's extensions get `session_shutdown` and the session is disposed before the error propagates. `lastText()` is the last assistant text; `runTexts()` (`finalRunTexts` in `messages.ts`) returns every non-empty assistant text of the child's final run, read from its session entries: from the last user message that follows an assistant message without tool calls (or the start), so a message steered into a running turn does not cut the run short.

## Extension manager and plugins

Only subagents uses the manager; session-limits, spending, working-indicator, notifications, command-aliases, composer, questionnaire, style, context, footer and mcp-import wire a few functions directly in `boot`.

- A `Plugin` is `{ id, requires?, enable(ctx) => disable? }`. `ctx` holds `host` (the real one), `runtime`, `bus`, `settings`, `services`, `root`.
- Boot order: plugins are topologically sorted by `requires` (cycles throw). A plugin is skipped silently when listed in `disabledPlugins`, and with one warning at session start when a plugin it requires is off or missing.
- Plugins communicate two ways: `services` (a typed map; `provide`/`require`/`has`, where `require` throws if the provider is not enabled) and the typed in-process `bus` (`agent:changed`, `agent:turn`, `agent:closed`, `agent:usage`, `batch:settled`). Bus listener errors are caught and passed to `onError`, which shows a UI error notification.
- On every `session_shutdown` the entry calls `disableAll()`, which runs the disable callbacks in reverse order, sequentially; a failing callback goes to `onError` and the rest still run. The adapter's own shutdown handlers are fault tolerant in the same way (see above).
- `settleWithin(promise, ms)` waits for a promise or a timeout, whichever comes first, and never rejects. It bounds child aborts (5 s) and child extension shutdown (2 s).

Settings: each extension has a JSON file `<agentDir>/<file>` (user) and `<cwd>/.pi/<file>` (project, read only when the project is trusted). `parseSettings` validates each known key against a schema (number range, string list, boolean, choice of strings, or an object with its own `parse`, which returns the value it keeps and its errors); invalid keys are dropped and reported as a warning notification, the rest is applied. Settings are read once per session start as defaults, then user, then project, because pi builds a new extension per session. Subagents additionally reads `disabledPlugins` from the user file at boot, since it decides which plugins enable; a project file cannot set it (warning, key ignored). `loadSettingsFiles`/`watchSettings` in `core/manager/settings.ts` do the user-then-project merge and the once-per-value warning for notifications and session-limits (`watchSettings` returns a getter over the values read at the latest session start). Nothing is reloaded live.

## Subagents

Plugins (`src/plugins.ts`; requirements in brackets): `fetch-tool` (the `fetch` tool as a `fetchTool` service, no requirements), `agent-registry` (in-memory records, `manifest.json`), `agent-definitions` (agent `.md` files, agent prompts), `run-agent` [registry, definitions] (runner, tools, outbox, main prompt, the `handoff` service: template and schema), `usage-report` [run-agent], `agent-status` [registry], `limits` [registry, run-agent], `agent-panel` [registry] (panel below the footer block, keyboard selection), `interrupt` [registry, run-agent] (Esc after an interrupted turn offers to stop running agents), `agent-setup` [definitions] (`/agents setup` and `/agents create`, the `agentSetup` service with their usage lines), `agent-view` [registry] (`/agents`: the menu, the list and the agent view in one overlay, the `agentView` service; `setup` and `create` are routed to `agentSetup`, and give an error naming that plugin when it is off).

### Agent definitions and prompts

- Markdown files with frontmatter are loaded from the built-in `agents/` when the plugin enables, and from the built-in `agents/`, then `<agentDir>/agents/`, then `<cwd>/.pi/agents/` (trusted projects) at session start. Later files override earlier ones by `name`. Invalid files, unknown `subagents` references and `subagents` cycles remove the offending definitions and produce warnings.
- Shipped agents name `model: provider/id:thinking`. A file without a `model` line (or with `inherit[:thinking]`) runs on the main session's model and, without a suffix, its thinking level.
- An agent's configured model and thinking are computed in one place, `parseDefinition` (`agent-definitions/loader.ts`), and stored on the `AgentDefinition`; the runner (`planModel`) and the `run_agent` description read them only through the `definitions` service. `startBatch` reads each definition once and keeps it in the agent's launch slot, so a queued agent and every handoff successor start with that definition even if a reload changed it meanwhile. The `model` parameter of `run_agent` and the main-session fallback are applied on top in `planModel`.
- Overrides: `pi-subagents.json` may hold `agents: { <name>: { model?, thinking?, skills? } }`. The settings schema parses it as an object rule (`model/settings.ts`: `model` is `provider/id[:thinking]` or `inherit`, a suffix becomes `thinking`; `thinking` a known level; `skills` a list or `all`; any other field is an error that says to create an own agent), and `loadSettings` merges user then project per agent and per field. After the files are loaded (the file that wins the name decides the definition), `loadDefinitions` applies each override field by field: each field replaces the definition's (`inherit` clears the model), so `skills: []` gives an agent no skills. It checks each override at load: a `model` that `runtime.resolveModel` does not resolve, or `skills` that name a skill that is not available (`runtime.skillNames()`), warn and drop that field; an agent file's own `skills` list (when no override replaced it) that names a skill that is not available gives a file warning and is kept, since unknown names are skipped at spawn; an override for an unknown agent warns, and one for an agent defined only in an untrusted project's `.pi/agents` gives an info message instead (each notice once per extension instance). The `model`, `thinking` and `skills` value checks (and the unknown-skill text) live in `model/agent-override.ts`, shared by the settings schema, the one-line `/agents setup` and `/agents create`; `model/model-resolution.ts` `resolutionProblem` is the one text for a model that does not resolve (the load notice, the setup line and, wrapped with advice, `run_agent`). One load reads `runtime.skillNames()` at most once, resolves each override model once, and reads the untrusted project's agent files only when an override names an agent that is not loaded. `definitions.reload()` is the one place that re-reads the settings files at runtime (`reloadSettings` in `model/settings.ts`, the same function the session start uses) and then re-runs the load; `/agents setup` calls it after a save. Every `reloadSettings` (session start and `definitions.reload()`) also calls `runtime.reserveCodemodeWorkers(maxConcurrent * maxDepth)`, the agent sessions the tree may keep alive (an agent that waits on its own batch gives up its semaphore slot but keeps a codemode worker when it waits inside a script); a shortfall joins the settings errors and is shown once like them. Settings errors, invalid-file errors, file warnings and override notices are each shown once per extension instance.
- `mcp` (frontmatter, `true` or `false`, default `true`) is stored on the definition and passed to `SpawnSpec.mcp`; the shipped leads set `true`, the chores `false`.
- Agent prompt = pi's own prompt for the child, with appended text: `prompts/base-system-prompt.md` (shared rules and the one result contract: `Status: done|partial|blocked`, the agent's sections, `Verification`, `Open`), then `# Agent: <name>` and the file body. Agent bodies hold only the role, its rules and its sections; no output line.
- The shipped roster is ten agents: `scout` (codebase questions), `editor` (exactly described edits), `planner` (ordered batches of briefed tasks), `implementer`, `reviewer`, `fetch`, `shell`, `image`, `verifier` (pass, fail or incomplete against given checks) and `general` (fallback). `planner` may start `scout`, `shell` and `fetch`, `reviewer` `scout` and `shell`, `implementer` `scout`, `shell` and `verifier` (it runs no checks itself; one `verifier` is its last step); `general` may start every other agent. `scout` replaces the former search agent, with no alias.
- The main session keeps its full tool set; nothing restricts it. Its prompt is `prompts/main-session.md` (its role: understand the request, read one short file or run one orienting command when a brief needs it, delegate the rest, judge every result, and for multi-step or ambiguous work agree a plan with the `planner` lead and the user first; a guide to which agent fits; the brief template; the result handling, where `unverified partial output` is not a result and a `Result file:` line on a planner result means reading the file before any batch). The lead prompts add that a lead never hands its whole task to another agent and returns `Status: partial` instead. The main prompt is set by `run-agent` at session start (plus `prompts/main-session-agent-status.md` when the agent-status plugin is on). `prompts/handoff.md` is the agents' handoff instruction template (`{{path}}` substituted), read by run-agent's `handoff.ts`. Prompt files are read once when their plugin enables.

### A run_agent call, end to end

1. Main model calls `run_agent { agents: [...], wait? }` (each item: `agent`, `task`, `description`, optional `files`, `model`, `skills`) -> `runner.startBatch` validates agent names, the caller's allowed `subagents`, depth (`callerDepth + 1 <= maxDepth`, main is depth 1), the spawn cap (`capError`: an agent caller may start at most `maxChildrenPerAgent` agents per run, counted per handoff-chain root over all its batches in the runner's `spawned` map, and a refused call starts nothing; the main session is not capped), the `skills` names (`skillError`: each must be in the caller's effective skill set, `runtime.sessionSkillNames()` for the main session and the caller record's `skills` for an agent, and the agent's tools must include `read`; a union with the agent's own skills, `all` resolved to the caller's effective set, is stored on the new record as its `skills` and passed to the spawn as names, never as `all`) and resolves every model. Any error throws and nothing starts.
2. Registry creates one record per agent (`queued`), writes `manifest.json`, emits `agent:changed`. The tool reports the batch through `update(text, details)` at once (`details.agents`: id, agent, description, model), returns ids and tells the model to end its turn (`wait: true` blocks until the batch settles instead). The block renders with `renderShell: "row"`: `renderCall` draws nothing, so only the result row is drawn (it stays defined so pi draws no generic call line; the working-status line shows the run); `renderResult` draws the block from the first update as one row (`render.ts` over `core/manager/row.ts`) whose title is the header and whose children are one nested row per agent, from the registry (chain terminals, chain totals). The header is `N [background] [kind] agent(s)`, with the kind when every agent of the batch shares it. Its mark (`blockMark`) comes from the chain terminals: `◌` while any is open, then `✗` when the call or an agent failed, `⊘` when every agent was stopped or handed off, otherwise `✓` with `· N stopped` when some were; an interrupted `wait: true` call, whose result is pi's abort text, is `⊘ … · stopped`. Once every terminal closed, the header adds the batch receipt: the wall time from the earliest start to the latest close, then the summed calls, tokens and cost. While any record of a main-session batch is open, the header carries the hint `(↓ to manage, ← to list)`, each key only while its plugin (`agent-panel`, `agent-view`) is not in `disabledPlugins`, `← to list` dropped first when the header is narrow; a batch an agent started, drawn only in the agent view, gets no hint. Each agent row is `name  description · id:thinking` (the model without its provider, dim, left out when fewer than 20 columns would stay for the description) with a receipt status line under it: a background batch never ticks in scrollback, so open agents read `Queued`, `Starting`, `Running` or `Stopping` (the panel carries the live figures), a `wait: true` batch is the live bottom row and shows the running receipt (`Elapsed 42s · 9 calls · …`), a closed agent its finished receipt with the worktree outcome after it, a short failure reason leads the receipt and a long one wraps under it, two rows and a count line while collapsed. An errored call without a batch is `✗ No agents started · <reason>`, a long reason on the `↳` line, the whole error when expanded. The adapter indents each line by pi's `outputPad` and cuts it, never wraps. Each rendered block is computed once per width and changes only when `renderResult` runs again: the stored `invalidate` (the latest per batch) re-renders through `watchAgents` at once on an `agent:changed` of an open batch, then at most every `renderThrottleMs`, and once more at `batch:settled`; without a record (resume, `/reload`) a row carries `»` and reads `Status unavailable · /agents <id>` (`Status unavailable` when the agent-view plugin is off).
3. `launch` per agent: acquire a semaphore slot (`maxConcurrent`, shared by the whole tree) -> optionally create a git worktree -> `runtime.spawn(SpawnSpec)` -> record becomes `running` -> `child.start(task)` -> messages queued while `queued` are steered in.
4. `spawn` builds an in-process pi `AgentSession` (not a subprocess) inside the child scope: in-memory copy of the main session settings with compaction disabled, `reserveTokens` set and cache warming off; tools = the definition's allowlist or the main session's active tools (minus excluded extension paths), plus `codemode` and `tool_search` unless `tools: []`, and MCP (pi's MCP built-in and the MCP tool names) only when the spec's `mcp` is not false (the definition's `mcp`, default true), plus custom tools from the runner (the `handoff` tool for every agent, the agent tools when it may start agents, and the `fetch` tool, built by the `fetch-tool` plugin from the `fetchTimeoutSeconds`, `fetchMaxBytes` and `fetchMaxChars` settings, only when the definition's `tools` lists `fetch`; `tools: all` does not include it); skills = the inventory's skill files named by the spec's `skills` (always a resolved list; `noSkills` and `additionalSkillPaths`, so the child's own cwd is never scanned and a worktree agent keeps uncommitted project skills; names outside the inventory are dropped); model resolved again by exact ref; session file in the agent's dir with `parentSession` = main session file; binds no UI, like pi's print mode: dialogs resolve to their denials (`confirm` false, `select` and `input` undefined), `notify` does nothing, `ctx.hasUI` is false; only the main session is interactive, and an agent that needs a decision reports it in its result.
5. The child's first message is `Task from <caller> (agent id <id>):`, `Agent folder: <dir>` (`task.ts`; the agent's own folder, where a shell agent keeps its command logs), the task and `Input files:`.
6. A hidden child extension cancels every compaction and, on the first provider request, appends a `pi-subagents:prompt-record` entry (skills, guidelines, raw provider payload, model) to the child session file. The entry stays in the session file and `runtime.readSession` still parses it; the agent view shows its provider payload, the first request as sent, as one collapsed Request block (key `r`).
7. Child events (`turn_end`, `assistant_message`, `tool_start`, `settled`) update the record (turns, tool calls, tokens, context, last text, and `activity`: the last tool name or `writing` after assistant text, set only when it changes and cleared while the agent waits idle for its own batches) and emit `agent:turn` and `agent:usage`.
8. On `settled`: if the agent has its own open batches or undelivered wakes, it goes idle and releases its slot. Otherwise it closes: `done` with its result written to `result.md`, or `failed` (abort, error stop reason, empty result). The result is picked without an extra turn (`pickResult` in `result.ts`): the last text of `child.runTexts()` that carries a `Status:` line within its first five non-empty lines (case-insensitive, markdown emphasis and heading marks ignored), else the run's last text; a run without texts gives an empty result (the cumulative last text of earlier runs is never used). The Status-line check is stored on the record as `statusLine` when it closes, so the batch text does not scan the result again. A failed or stopped agent's text, picked the same way, is stored as well when there is any, as partial output. Closing releases the slot, emits final usage, disposes the session and immediately stops any open children of that agent.
9. When every record of the batch is closed and every worktree cleanup is done, `batch:settled` fires and the batch text (one `## <id> (<agent>) - <state>` section per chain terminal, its summary line the plain receipt the UI draws, `Done · 1m 5s · 4 calls · 12.3k tokens · $0.04` or `Failed · <error> · …`, summed over a chain; results inline up to `inlineResultChars` (8000), otherwise the head up to it, cut at the last newline before the limit, and a last line `Result file: <path> (<N> more chars)`; a done result without a Status line gets a `(shape: no Status line)` note; failed and stopped agents' text, under the same rule, with an `(unverified partial output: <error>)` note) is posted to the caller's outbox.
10. Outbox: for the main session the batch texts posted in one synchronous pass are joined (`---` between them) into one `pi-subagents:wake` hidden message sent through `Host.sendHiddenMessage` on the next microtask. The adapter picks the path: while a run is active the hidden message joins it as a follow-up; when idle the hidden message starts a run itself. Either way nothing new appears in the transcript besides the working indicator and the model's reply. For an agent caller it holds texts while that agent's turn runs and, on its idle, re-acquires a slot and wakes the child with the joined texts as one follow-up prompt.

Nesting: a child gets `run_agent`, `message_agent` and `agent_status` as custom tools only when its definition allows subagents and it is below `maxDepth`; these tools are bound to the child as caller and drive the same runner, which applies `maxChildrenPerAgent` to them (the cap and the prompt rules of each role keep helper fan-out small; a helper's result wakes the agent that started it, never the main session).

Skills narrow down the tree in three layers: the definition's `skills`, replaced field-wise by an `agents.<name>` override, plus the call-time `skills` of `run_agent`. A caller may pass only skills of its own effective set: the main session's is its loaded skills (`runtime.sessionSkillNames()`), an agent's is the `skills` stored on its record at spawn (its own, with `all` resolved to its caller's set, plus what its caller passed; a successor inherits it).

The main prompt and tool list stay the same for the whole session. A child waiting on its batch holds no slot, so the tree cannot deadlock.

### Messages, stop and shutdown

- `message_agent` (only the agent's caller) routes `[message from <sender>]` text: held while queued, steered while a turn is in flight, a follow-up (after re-acquiring a slot) when idle. Its render is silent: `renderCall` and a successful `renderResult` draw nothing (shell `row`, so nothing at all), and an error result draws `✗ Message <id> · <error>`, or the error on the `↳` line in the error colour when it does not fit on the title. The model still gets the result text unchanged.
- Stop: a running agent enters `grace`, its turn is aborted and its slot released; a message during grace is answered, otherwise after `stopGraceSeconds` it closes as `stopped` (last text kept as result). A queued agent, a second stop during grace, or `stopGraceSeconds: 0` closes at once.
- Interrupt (`interrupt` plugin): every `Host.onIdle` settle sets it: armed when the run that settled was aborted, disarmed otherwise (a new run does not disarm it by starting; the editor hook only fires while pi is idle, and that run's own settle decides again). While armed, Esc on an empty idle editor (`HostUi.onEmptyEditorEscape`) with at least one queued or running agent (`stoppableAgents` in `components/tree.ts`, also used by the list's stop-all) is consumed and opens a confirm `Stop running agents?` naming up to three ids. Yes stops each with `runner.stop` (the graceful stop above) and notifies `stopping N agents`; consuming the key disarms it before the confirm opens, so whatever the answer the next Esc goes to pi (its double-Esc). Without an abort, or without running agents, the key is not consumed. `disabledPlugins: ["interrupt"]` turns it off.
- Session shutdown: unsent wakes are dropped, every open agent closes as `failed (interrupted)` (or `stopped` if in grace), children are aborted and disposed.

### Context limits and handoff chains

- Effective limit = `min(definition limit, model window - reserveTokens)`. After each turn that continues with tool calls, `limits` compares context tokens: at `softContextRatio` it routes one warning; at the limit it sets `handoffRequested` and routes `prompts/handoff.md` with the agent's handoff path (OS temp dir), which tells it to call its `handoff` tool and then reply `handoff saved`. Every agent gets that tool whatever its `tools` (so read-only agents need no general write tool); it is bound to the agent's own record, refuses before `handoffRequested` is set, writes its `content` to the agent's handoff path, validates it and returns `Handoff saved at <path>` or the validation errors so the agent can fix the sections and call again (an invalid handoff stays saved). `limits` aborts the agent 3 turns after the request, or past `limit * hardContextRatio` from the second turn after it (the first turn is a grace turn, so a single huge tool result that crossed the hard line at once still leaves the agent one turn to hand off; the tool call turn and the one-line reply fit in that).
- When an agent with a handoff request settles, the runner reads the handoff file; when there is none (the agent did not call the tool) and the agent's whole final reply validates as a handoff, a fallback the prompt does not mention, it writes that reply to the handoff path and goes on as if the agent had written it. It validates the handoff (sections Status, Outcome, Evidence, Blocker, Next, Files touched in order; Status `partial` or `blocked`). `partial` within `maxChainLength`, not stopped and not in a settled batch -> a successor record in the same batch (same task, same worktree, task text points at the handoff) and the predecessor closes as `handoff`. Otherwise the agent closes as `handoff`, flagged invalid if the schema failed. No file and a final reply that is not a handoff is `failed`.
- Chains are invisible to the caller: one wake, one result section with a `Chain:` line, and any id of a chain resolves to its last link for status, messages and stop.

### Status and views

- `agent_status` reads in-memory records only; it never touches the agent. Its text gives one line per agent in the receipt's words (`<id> (<agent>, <model>) running · 42s · 9 calls · 31.0k tokens · 31% context`) with `last:`, `error:`, `result:`, `handoff:` and `worktree:` lines under it. Its row is `✓ Agent status <ids or all>` with `↳ N agents (ctrl+o to expand)` under it and, expanded, one agent row per agent in the panel's columns (static marks, the figures as of the call). The `handoff` tool every agent gets draws `✓ Handoff` with `↳ Saved <path>` (`~/…` under home) or its error lines.
- Every surface reads the same clock, state marks and spinner (`components/state-text.ts`: `◌` queued, starting or stopping, `✓` done, `✗` failed, `⊘` stopped or handed off; on the live surfaces, the panel, the list and the agent view header, a running agent draws pi's braille spinner with the frame from `Date.now()` instead, and scrollback rows draw the static `◌`), the receipt (`agentReceipt` in `components/format.ts`, over `receipt` in `core/manager/format.ts`, which it re-exports with `formatTokens`, `formatDuration` and `errorText`: `Elapsed 1m 5s · 4 calls · 12.3k tokens · $0.04 · grep` while running, `1m 5s · …` once done, `Queued`, `Starting`, `Stopping · Elapsed …`, `Stopped · …` and `Handed off · …` otherwise), the state words and the `x` hint words per state (`stopWords`), the chain and tree helpers (`components/tree.ts`: `isTerminal`, `withLinks`, `carrySelection`, `treeOrder`, over `chainTerminal`/`chainLinks` from `model/types.ts`, which take any `{ get }` lookup: the registry, a `Map`, or the view loader's manifest reader) and the tick cadence (`components/refresh.ts` `tickFor`: 100 ms while a record runs or is in grace, 1 s while one is queued or closed rows linger, none otherwise); widths and truncation come from `ThemeLike.width`/`truncate`, backed by pi-tui, so the extension and the adapter cut lines by one rule; the record's `activity` (last top-level tool name or `writing`, set by the runner, cleared while the agent waits for its batches, not persisted) feeds the panel. The agent view renders nested calls with the specs the extension registered on the host, which the adapter keeps. Re-render throttling is `renderThrottleMs` everywhere.
- The agent panel (`agent-panel`) renders the registry in tree order (`components/tree.ts`) with the shared agent row (`components/agent-row.ts`; every row reserves the two pointer columns, blank unless selected, where the selected row draws the accent `›`, so names do not shift when a selection appears; an agent started by another sits under its caller, the first child with `↳` in its parent's glyph column and later siblings indented to the same column; `rowLayout` aligns the columns over all rows: the name (capped at 24 columns, `#N` for a chain link and `(+N)` for open descendants dim, finished names muted), the muted description (capped at 48 columns), the dim model as `id:thinking` without the provider (capped at 20 columns, cut in the middle so the `:thinking` suffix stays, `modelLabel`; dropped for the whole surface when it would not fit), and the receipt, which on a narrow row first cuts the description down to 12 columns and then drops the activity, the cost, the calls and the tokens, never the state word or the time) in a `belowEditor` widget (set when the first row appears, never during session start, so it lands under the footer block; see Footer; rows are recomputed on each refresh (throttled events and ticks), not per frame): at most five rows plus `↑/↓ N more` markers, a selection driven by `HostUi.onEmptyEditorDown` (`↓` on an empty editor that is not browsing input history, where pi's `↓` would be a no-op) and `captureEditorKeys` (consumed: `↑`, `↓`, `Enter`, `x`, `Esc`; any other key, `←` included, releases the capture and clears the selection, and the released `←` then reaches the empty-editor hook that opens the list), `done` rows kept `doneLingerMs`, other closed rows `failedLingerMs` or until cleared. It refreshes through `components/refresh.ts` (`watchAgents`: `agent:changed` throttled by `renderThrottleMs`, plus an unref'd ticker at 100 ms while any row runs, 1 s while only queued or closed rows show, none otherwise; the cadence is re-read after every refresh, from the rows that refresh computed). The same refresh owns the status `pi-subagents` (dim `← to list agents`, shown in the footer block with the footer extension): set exactly when the rows it just computed are empty, so it hides while any row shows, lingering closed rows included, and returns when the last row leaves by timer or `x`; only in `tui` mode and only while `agent-view` is not in `disabledPlugins` (the check `run_agent` uses for `← to list`); written only when the value changes, forced at each session start (pi clears statuses), cleared on disable and never set again.
- The `/agents` list shows the agent tree in two sections (`Running`: open roots with their listed descendants; `Finished (n)`: closed roots, newest first, with their descendants; `list-model.ts`, `treeOrder` per section), re-renders on `agent:changed` (throttled by `renderThrottleMs`) plus the shared ticker; closed records stay for the session or until `x` clears them (the registry lives in the extension instance, which pi rebuilds on `/new`, `/resume`, `/fork` and `/reload`, so the list starts empty then); only the 200 newest closed roots are listed (`MAX_CLOSED_ROOTS`), an older one dropping out with its subtree and chains. The panel keeps its own `doneLingerMs` and `failedLingerMs`. Besides `/agents`, `←` on an empty editor opens the list (`agent-view` registers `HostUi.onEmptyEditorLeft`), also with no rows (the list shows its empty state); `→` closes the list back to the editor like `esc`, and the bottom strip reads `↑↓ to select · enter to view · x to stop · shift+x to stop all · esc to close`.
- The agent view shares the list's overlay (one `openOverlay`; the host component swaps list and view, `Esc` returns to the list only when the view was opened from it; `agentView.open(id)`, used by `/agents <id>` and the panel, resolves the agent once and hands the record to the view). It reads the agent's session file through `runtime.readSession`, re-parsing only when the file's size or mtime changed; it reloads on throttled chain events and at most once per second on the ticker (`watchAgents`' `onTick`, since tool results are written without a registry event), and other ticks only redraw the spinner and the stats. It falls back to `manifest.json` (which stores the final `turns`, `toolCalls` and `tokens`) for agents not in memory. Its transcript renders built-in tools with pi's definitions, `codemode`/`tool_search` with renderers captured from pi's exported extension factories (generic fallback if capture fails), and the subagents tools with the specs the extension registered on the host (`createTranscript({ owner })`). A call with no result yet is filled once, at render, with its spec's `pendingResult`: `run_agent` keeps a plugin-level map from caller agent id and call id to the batch details of each executing call in an agent's session (`createPendingCalls` in `tools.ts`, shared by the child's tool and the spec the view renders with, which the view creates with the viewed agent's id as `owner`; an entry lives until its call returns, when pi writes the result to the session), so a nested batch shows its live block before the result is written. The pane strips the OSC 133 prompt marks pi puts on message lines, as pi's own fullscreen render does, because overlay lines skip that step and the terminal would keep drawing marks. Clicks are routing only: in pi's fullscreen mode the overlay forwards a left click to the view's `handleClick`, which maps the row through the header and the scroll position and hands it to `TranscriptPane.click`, so pi's own components toggle one tool call (their `MouseRegion`), and stops following so the clicked row stays put; `Ctrl+O` stays the global toggle and the only keyboard path. Above the transcript, a collapsed Request line (`plugins/agent-view/request-block.ts`) expands with `r` (or a click on it) to the prompt record's `providerPayload` as pretty-printed plain text. Nothing of the view is persisted.

### Agent setup and agent files

- `/agents` with no argument, in tui mode, opens a menu (`selectForm` titled `Agents`): `view` (the agents list, with `N running, M finished` from `listCounts` in `list-model.ts`), `setup` and `create`. Esc closes it silently. Without the `agent-setup` plugin the menu is skipped and the list opens. Outside tui, `/agents` and `/agents view` notify that the list needs the interactive terminal. `←` on an empty editor still opens the list directly.
- `/agents` takes `view`, `setup` and `create` as first words (completed in the slash menu with the agent names after `setup `); any other argument is an agent id. `view` works without the `agent-setup` plugin.
- `/agents setup` (`agent-setup` plugin) in tui mode opens a form through `HostUi.showForm`: one tab per loaded agent (shipped agents by name, then own agents by name) and a Submit tab, with the tab bar and keys from `core/manager/tabs.ts`. Each agent tab has three fields, pre-filled from the effective definition: Model (a picker over `inherit` and `runtime.availableModels()`), Thinking (the levels the chosen model accepts) and Skills (the `multi-select.ts` checkbox list over `runtime.skillCatalog()`, one row per skill, `name  description` with the description cut to the row; below the list the full description of the skill under the cursor, wrapped to three lines, when it did not fit; an agent with `all` opens with no box ticked and keeps `all` on Enter unless a box was changed), plus read-only Tools and MCP lines. The Submit tab lists the changed fields and picks the file: this project's `.pi/pi-subagents.json` (preselected in a trusted project; refused in an untrusted one) or the user's `<agentDir>/pi-subagents.json`. Outside tui mode it fails with a message naming both files and the one-line form.
- One-line form: `/agents setup <agent> model=<provider/id[:thinking]|inherit> thinking=<level> skills=<a,b|all|none> scope=<project|user>` (any subset; scope `project` by default in a trusted project, `user` in an untrusted one); the model is resolved and the skills checked before anything is written.
- Saving (`write.ts`) reads the JSON file (refusing a file that is not an object or whose `agents` is not one), merges the changed fields into `agents.<name>` and keeps every other key, then calls `definitions.reload()`, which reloads the settings and the agent files, so agents started afterwards use the new values; running agents keep theirs. A user save that a project override shadows gets a warning naming the fields.
- `/agents create [<name> [project] | <what the agent is for>]` (`agent-setup/create.ts`) writes no file. It checks what it can (a shipped agent's name, a name that is not letters, digits, `_` and `-`, an existing file, `project` outside a trusted project), then sends a brief to the main session as a hidden message (`Host.sendHiddenMessage`, custom type `pi-subagents-create`, which starts a turn when the session is idle) and notifies that it did. The brief is `prompts/create-agent.md` filled by `createBrief`: the command as typed, the name or purpose when given, the target path (the user agents dir; the project dir too in a trusted project, when the name is not fixed), the names taken, the available skills with descriptions and both `agent-template.ts` skeletons, lead and chore, so the brief cannot drift from the kind defaults. The main session asks the user for what is missing, writes `<agentDir>/agents/<name>.md` (or `<cwd>/.pi/agents/<name>.md`) with its own write tool and tells the user to run `/reload`. The `/agents` menu's `create` runs the same flow with no name.

### Worktrees

`worktree: true` writes `<cwd>/.pi/worktrees/.gitignore` (`*`) when missing, then runs `git worktree add -b pi-agents/<id>-<stamp> <cwd>/.pi/worktrees/<id>-<stamp> <base>` from the session cwd, where `base` is the HEAD sha; the agent's cwd is the same subdirectory inside it. A failed git or fs step fails the agent with `worktree failed: <error>`. `Worktree = { path, branch, base, cwd, cleanup? }`. A successor is created holding its predecessor's worktree. `releaseLive` is one teardown per agent: it disposes the child, then, for a closed record without a successor, runs `git worktree remove <path>` (no `--force`), deletes the branch only if it still points at `base`, and stores the outcome as `worktree.cleanup` (`removed`, `branch kept`, `kept`) on every link of the chain. A batch settles only after every member's cleanup, so results show the final outcome; shutdown awaits every pending removal except one whose `git worktree add` is still running. Stopping an agent queued for a slot tears it down at once.

## Session-limits

- Active only in `tui` and `rpc` modes (a `Host` wrapper suppresses events otherwise). Thresholds compare main session context tokens to `min(window × ratio, token cap)`: the soft threshold (`softRatio` 0.45, `softTokens` 125,000) shows the warning notice `» Handoff at <hard threshold> tokens · <used> used` (`» Handoff at 175k tokens · 142.3k used`) through `HostUi.setNotice` (key `pi-session-limits`, below the editor and above the footer block), the hard threshold (`hardRatio` 0.60, `hardTokens` 175,000) triggers the handoff. Ratios decide on small windows, the caps on large ones (`thresholdsFor` in `thresholds.ts`).
- Sequence: turn end at hard level -> send the `prompts/handoff.md` instruction as a hidden message (`Host.sendHiddenMessage`, custom type `pi-session-limits-request`) with the path `<OS temp dir>/pi-session-limits/<session id>-handoff.md`, plus one info notice naming the path -> on each turn end/idle check whether the file is new (mtime changed) and valid (same six sections, Status `done`, `partial` or `blocked`) -> if valid and no busy source -> dispatch `/session-handoff` -> `newSession({ parentSession, seed })`, seeding the new session with a `pi-session-limits-handoff` custom message holding the handoff.
- `/session-handoff [what the next session is for]` starts the same flow on demand, with the reason "the user ran /session-handoff" and the optional focus folded into the instruction and the new session's seed. By phase: while watching it sends the instruction (notice `» Handoff writing the document`), or holds it while pi is busy (see `queued` below); while requested it only notifies that one is being written; while waiting it switches at once without arguments; while stuck it switches at once when the file at the path is valid and no focus was given, otherwise it sends (or, while pi is busy, queues) a fresh request; the switching call is the internal dispatch. A manual handoff does not wait for busy sources: when the file is valid it dispatches the switch and the busy confirm (`Switch to a new session?`) asks. On No the phase becomes `waiting` and the switch happens when the work ends, as in the automatic flow.
- `queued`: when `/session-handoff` would send a request while a run is active (tracked from `onAgentStart` to `onIdle`) or pi is not idle (a compaction before or without a run), the request is held in phase `queued` (warning notice `» Handoff after this turn`) instead of going into pi's follow-up queue, which RPC `abort` and a mid-turn `/compact` do not clear. A clean settle sends it; an aborted settle drops it with `Session handoff cancelled.` and returns to `watching`. After a compaction with no run active, `onCompact` polls `isIdle()` every 250 ms and sends it once pi is idle, unless a run starts first, which then holds it until its settle. While queued a new focus replaces the stored one and the automatic request does not fire, so a turn end at the hard level sends the queued manual request at settle.
- Esc during the writing turn of a manual request (the settle reports `aborted` while the phase is `requested`) cancels it: the phase returns to `watching`, path, focus and counters are cleared, and an info notice says `Session handoff cancelled.`; an automatic request still gets its resend.
- An invalid or missing file after the session settles gets one resend with the errors; after 2 instructions the phase becomes `stuck` and the user runs `/session-handoff` again (it switches at once when a valid fresh file exists). User activity after the request causes the instruction to be re-sent before switching.
- Busy sources: any extension can publish `pi:busy { source, busy }`. Subagents publishes it while any agent is open; the switch waits until all sources are idle (then 1 s), and a switch with busy sources asks for confirmation (always for a manual handoff). The notifications extension reads the same channel to hold its idle notification.
- All state is in memory, per extension instance; the only file is the handoff. A pending switch whose `/session-handoff` command never runs ends in the failed phase at the next idle or turn end; a second `/session-handoff` while the switch runs is ignored. A context window of 0 or unknown token usage turns the extension off for that moment (no request, notice cleared).
- The seed message is drawn by a message renderer (`Host.registerMessageRenderer`, `src/seed-row.ts`) as an informational row like the `/context` row: `» Handoff from the previous session` with the seed's first sentence, muted, on the `↳` line and the `(ctrl+o to expand)` hint after it (cut with the sentence on a narrow terminal); expanded, the whole seed wrapped at column 4.
- `Host.onCompact` fires after pi compacts the main session; session-limits uses it to forget its cached context size (pi reports unknown tokens after compaction), which clears the notice until the next turn. Every notice follows one pattern, `Handoff <phase>` plus an optional ` · <detail>`, after pi's info marker `»` and in the warning colour (`» Handoff after this turn`, `» Handoff writing the document`, `» Handoff waiting for running work`, `» Handoff switching to a new session`), except the failure, `✗ Handoff failed · run /session-handoff` in the error colour (`segmentFor` in `thresholds.ts`); the normal level shows nothing.

## Spending

- Main cost = `sumUsage` over the session entries (assistant, tool result, `usage`, compaction and branch-summary usage; `Host.sessionUsage()`), as priced by pi. Child agents use the same `sumUsage` (`ChildSession.ownUsage`).
- Other costs arrive on `spending:usage { source, id, usage }`. Subagents' `usage-report` forwards every `agent:usage` (child session's own usage, at any depth, since all agents share one runner) with `source: "agents"` and the agent id as `id` (ids are unique within the session's agents folder, earlier runs included), with no dedup of its own, since the ledger is idempotent.
- The ledger keeps the latest report per `(source, id)` and replaces it only when neither cost nor tokens go down and one goes up (monotonic: totals never go down), sums per source, and shows `main $x · agents $y · total $z` (plus `(sub)` when the adapter's `subscription` is set: pi reports OAuth for the main model and the provider's OAuth sign-in is marked as a subscription, pi's own footer check) in the footer once any source is above zero, each figure in the shared money format (`formatCost`: two decimals, `<$0.01` under a cent, `$0.00` for nothing); total is the raw sum rounded once.
- Persistence: changed reports are appended as `pi-spending:usage` custom entries in the main session file at once when a report arrives while the main session is idle (agents mostly run then, so a crash loses little), otherwise on the next idle, and on shutdown; they are replayed on session start (resume). Reports that arrive after spending's own shutdown are ignored. Offset entries that are not finite numbers read as zero.
- Lineage: totals cover the whole session lineage. Compaction and `/tree` only append to the same file, and `sumUsage` reads every entry of every branch. When a session is created from another one (`/fork`, `/clone` or a handoff switch; `parent` set) spending appends a `pi-spending:main-offset` entry (the parent's main cost, its own last offset plus all its entries, minus the usage of the entries copied into the new session), so main = last offset + `sumUsage` of the new session's entries; it also appends a continuation marker report, absorbs every parent `pi-spending:usage` report under an id prefixed with the parent file name (so new agents cannot collide with parent agent ids) and persists them into the new session at once; restore ignores reports before the last marker, so resumed sessions and chains of forks and handoffs keep the totals. Only a plain `/new` starts at zero; a handoff switch keeps the totals, since it continues the same work in a new session. Without a session file (`--no-session`) there is no parent file: a fork starts from the copied entries only, and a handoff switch starts from zero (session-limits passes no parent). A parent that cannot be read falls back to the resume path over the session's own entries, with a warning. Only the first `session_start` of an instance inherits: pi's rpc mode rebinds extensions twice for fork, clone and new-with-parent, and a second inheritance would append a second continuation marker after the absorbed parent reports, which a later resume would then drop.
- Totals: on every refresh (session start, accepted report, turn end, compaction, idle) spending publishes `spending:totals { main: { cost, tokens }, sources: [{ source, cost, tokens }], subscription }`. pi constructs every extension and runs its subscriptions before `session_start`, so listeners hear the first publish regardless of load order; there is no request channel. Tokens are chargeable tokens (`input + output + cacheRead + cacheWrite`); main tokens carry over a fork or handoff through a `pi-spending:main-tokens-offset` entry, like main cost (a parent forked before that entry existed has none, so main tokens undercount its ancestors while cost stays right; new chains are complete). Both offsets are read once at session start (or set by the fork inheritance) and each refresh reads `sessionUsage()` once.

## Working-indicator

- Active only in `tui` mode. The spinner is pi's own braille spinner; the extension never replaces it (the contract has no call to), so pi keeps colouring its frames with the editor's border colour (thinking level, bash mode).
- The clock counts the current prompt (one agent run), not a turn. The first `Host.onAgentStart` of a run (skipped outside `tui`, so no interval runs in other modes) records the start and reads pi's `app.interrupt` key once through `HostUi.keyText`; repeated `agent_start`s inside the run (retry, compaction, continuation) are ignored. An unref'd interval rewrites `HostUi.setWorkingMessage` every `TICK_MS` (1 s), even while the row is hidden and only when the text changed, as `<activity> · <elapsed> (<key> to interrupt)`: the time from 1 s on in `formatDuration`'s format (`12s`, `1m 5s`), the hint dim.
- The activity names what the run is doing, from `Host.onPhase` and `PhaseDetail.tools`: `Waiting for the model` (request sent, a tool call streaming, between steps), `Thinking`, one verb per running tool with the target the transcript row titles show (`Reading src/stats.py`, `Editing …`, `Writing …`, `Running <first command line>` for `bash`/`powershell`, `Searching`, `Finding`, `Listing`, `Running codemode`, `Calling server/tool` for an MCP tool by the `label` the adapter gives it, `Waiting for N agents` for a `run_agent` with `wait: true`, `Running <name>` for any other), and `Running N tools` while several run at once.
- Width: the text is composed to `HostUi.workingColumns()`, measured with `HostUi.metrics`, so wide characters count by their columns. The activity is cut first with `...` (paths at the start, commands at the end) down to 12 columns, then the hint is dropped; the elapsed time is never dropped. Without a terminal width the full text is sent and pi cuts it.
- The row is drawn by pi inside the input's top rule (the composer's editor embeds it), not in a separate line above the editor.
- Visibility follows `Host.onPhase`: entering `writing` calls `HostUi.setWorkingVisible(false)`, and leaving it writes the message and then calls `setWorkingVisible(true)`. pi re-shows the row at once while a run is active (`isStreaming`), so the row returns as soon as assistant text stops, in the same turn. Only transitions call pi, so a run without text never toggles it. `onPhase("idle")` (after the `onIdle` handlers of `agent_settled`) stops the interval, restores pi's visibility flag if it was hidden, and restores pi's default message. Shutdown stops the interval and clears the message; pi resets the flag itself on session switch and reload.
- Only the main session drives it: phases come from the main session's pi events, child sessions run in their own `AgentSession` with no-op working UI, and the extension subscribes to no bus or channel. Nothing is persisted.

## Notifications

- Active only in `tui` mode and when `channel` is not `off`; otherwise it registers no key listener and arms no timer. `pi-notifications.json` is read at session start; nothing is persisted, timers are unref'd and cleared on shutdown.
- Idle notification: `Host.onIdle` (pi's `agent_settled`, once per run) marks the settle pending and, when no source is on the busy channel (`pi:busy`, kept as a set of source names like session-limits), arms an `idleDelayMs` timer. `Host.onAgentStart`, any key (`HostUi.onKeyPress`, observed without consuming) and a busy source appearing cancel it; the last busy source clearing or a dialog ending re-arms it with the full delay while the settle is still pending. At fire time it checks only that no dialog or waiting source is open (a dialog starting does not clear the timer), sends `pi is waiting for your input` and clears the pending settle, so a settle notifies at most once.
- Agents and the wake: subagents holds the busy channel while any agent is open. Agents finishing while main is idle arm the timer, but the outbox's hidden wake starts a run at once, which cancels it; that run's settle arms it again. One notification follows the finished work.
- Waiting extensions: a source on the awaiting-input channel (`pi:awaiting-input`, `{ source, waiting, title? }`, parsed by `parseAwaitingInput` in `core/manager/channels.ts`) counts as an open dialog with that title, under the same rules below: it arms the dialog notification, holds the idle one, and `waiting: false` from the same source closes it like a dialog ending. Open waits are kept in a map keyed by owner (pi's dialog is one owner, each source its own), so a dialog opening over a waiting source, or the reverse, closes only its own entry. The questionnaire publishes it while it waits to show its form and while the form is open, since pi reports that form only as a `custom` dialog, which is ignored.
- Dialog notification: `Host.onDialog` (pi's `ui_prompt_start`/`ui_prompt_end`, outermost dialog only, main-session dialogs only since agents never open one; `custom` overlays ignored). `dialogDelayMs` after the later of the latest wait opening and the last key it sends `pi needs your input: <title>` with the most recently opened wait's title and marks every open wait as notified, so each notifies at most once; a wait closing re-arms the full delay while a wait not yet notified remains open, and cancels it otherwise.
- Output: `HostUi.terminalNotify(message, channel)` with `auto` (OSC 9/777 only, no BEL: the idle notification follows ordinary replies too, and a bell each time is noise) or `bell`.

## Command-aliases

- `ALIASES` maps an alias to a built-in command (`/continue` -> `/resume`, `/clear` -> `/new`, `/exit` -> `/quit`). pi runs built-ins in the editor's submit path before extension commands, so the alias is rewritten before pi sees it, through three `HostUi` calls implemented in `core/adapter/pi-editor-input.ts`, all no-ops outside tui mode.
- `onEditorSubmit`: a terminal input listener that, on the `tui.input.submit` key, swaps an editor text that is exactly an alias for its target before the key is processed. `mapCommandCompletion`: wraps the autocomplete provider so picking an alias in the slash menu inserts the target.
- Each alias is also a registered command. If it still runs, `submitEditor` waits one macrotask, sets the target as editor text and feeds Enter to the TUI's focused component (the TUI is captured through a widget factory that is removed at once); when no component takes input the extension notifies `Could not run <target>`. No state, no files.

## Composer

- On session start composer hands `host.ui.setEditorFrame(frame)` a pure `EditorFrame` (`chrome`, `left`, `minWidth`, `decorate(lines, layout, paint)`). The adapter (`core/adapter/pi-editor.ts`) installs one `HostEditor` subclass of `CustomEditor` through `ctx.ui.setEditorComponent` when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `onEmptyEditorDown`, `captureEditorKeys`) is used, only in `tui` mode and only when no editor other than the one the package installed is set (`getEditorComponent()`). Composer and subagents share that one editor through a `globalThis` record, whichever loads first; hooks registered before `session_start` take effect at session start. The record also keeps the ↑ input history shared by every `HostEditor` instance, so it survives `/reload` and `/new`; `/resume` and `/fork` add the session's user messages to it like pi's own editor. The subclass is constructed with pi's `embedWorkingStatus`, as pi's own editor is, so pi draws the working, compaction and retry status inside the top rule (`── ⠹ Running npm test · 12s ──`) with no blank line or spacer; the top rule is still one line that `decorate` extends. The frame is optional (without one the editor renders as pi's own), the instance reads the current frame on every render, and keys reach the hooks only while the editor has focus.
- The subclass renders pi's editor `chrome` columns narrower and passes the lines, the layout and the editor's live `borderColor` to `decorate`; below `minWidth` it renders the plain editor. The layout comes from the subclass's `renderTopBorder` and `renderBottomBorder` overrides, not from parsing lines: `bottom` is the index of the line `renderBottomBorder` returned and `scrolled` is whether the top border is an `↑ N more` hint. The rules are extended by `chrome` painted rule characters to the full width: the top rule gets them in front, so pi's embedded working status starts right of the prompt gutter (3 columns right of the input), the bottom rule gets them after; the lines between get a one-column left margin (`MARGIN`) and the prompt gutter (pi's `›` message cursor, bold accent, `CHEVRON` in `frame.ts`, only on the first line and not while scrolled), and lines below the bottom rule (autocomplete) are indented by `MARGIN`, so pi's `→` sits under the prompt. No pipes or corners: `chrome` and `left` are the margin plus the gutter width. Mouse events are shifted left by `left` and narrowed by `chrome` before pi's editor handles them, so clicks land on the clicked character.

## Questionnaire

- Registers one tool, `questionnaire` (`modelOnly: true`, so codemode scripts cannot call it; `executionMode: "sequential"`, so two calls in one message never compete for the editor slot), with the description, `promptSnippet` and three `promptGuidelines` (decisions as concrete options, batch independent questions and defer dependent ones, fall back to a default or stop on cancel). Parameters are plain JSON schema: `questions: [{ id, label?, prompt, options: [{ value, label, description? }], allowOther? }]`. Only the main session has it: no extension boots inside an agent, and an agent that inherits the name finds no tool behind it.
- `execute`: outside tui mode, an empty batch, duplicate ids or a question with no options and `allowOther: false` return an `isError` result and show nothing. Labels default to `Q1`, `Q2`… and `allowOther` to true. Otherwise it calls `host.ui.showForm` with the tool's signal, and publishes `pi:awaiting-input` `{ source: "pi-questionnaire", waiting: true, title: "questionnaire" }` as soon as it starts waiting (before `showForm` waits for an open overlay such as `/agents` to close) and `waiting: false` exactly once when the form closes, `showForm` resolves without a form or the signal aborts.
- `form.ts` is a pure reducer over `{ questions, tab, option, answers, typing }`. One question: no tab bar, Enter or a digit answers and submits. Several: Tab/→ and Shift+Tab/← move between the question tabs and a Submit tab (wrapping), ↑/↓/Home/End move the selection, digits `1`-`9` pick that option, Enter confirms (the tab keys are `tabStep` from `core/manager/tabs.ts`, the list keys `listKey` from `core/manager/list.ts`); an answer moves to the next unanswered question, then to the Submit tab, where Enter submits only when every question is answered. Coming back to a question selects its saved answer. `Type something.` (the last option while `allowOther`) opens the text input; Enter saves a non-empty, trimmed answer, Esc returns to the options (while typing, `pressKey` handles only Esc; `view.ts` forwards every other key to the text input, and reopening the input pre-fills an earlier typed answer). Esc anywhere else cancels the form. Digits and Enter are ignored for the first 250 ms after the form opens (`pressKey`'s `armed` option, set by `view.ts` from an injectable clock), so text typed ahead into the editor does not answer it.
- `render.ts` draws it over `ThemeLike` only: accent rules above and below, the tab bar `← □ Scope  ■ Priority  ✓ Submit →` (`tabBar` from `core/manager/tabs.ts`; ■ success when answered, the active tab accent and bold, Submit success once complete), the wrapped prompt, the options with a `›` pointer and wrapped muted descriptions (`listLines` from `core/manager/list.ts`; rules and hints from `core/manager/layout.ts`), the text input under `Your answer:`, the Submit tab's answers (`(wrote)` for typed ones) with `Press enter to submit` or `Unanswered: …` in warning colour, and the key strip in pi's `key to verb` grammar (`↑↓ to select · 1-9 to pick · enter to submit · esc to cancel`, keys dim, words muted, wrapping between hints).
- Result text, one line per answered question in question order: `<label> (<id>): selected <n>. <option label> [value: <value>]` or `<label> (<id>): wrote: <text>`. A cancel (Esc, or the signal aborting) gives `User cancelled the questionnaire`, the answers given so far under `Answered before cancelling:`, and `Pick a sensible default for anything unanswered, or stop.` Details are `{ questions, answers, cancelled }`, so the row (`summary.ts`, shell `row`) works from session files too: the title `Questionnaire · N questions` after the call's mark, the answers under `↳`, one per line (`<label>: <n>. <option label>`, a typed answer followed by a dim `(wrote)`; labels in accent), a cancelled form `⊘ Questionnaire · cancelled` with any answers given before, the error on the `↳` line in the error colour. Nothing is persisted.

## Style

- Styles are the markdown files in `prompts/` (`concise.md` ships), read once when the extension loads by `loadStyles` (`src/styles.ts`); `normal` means no style. A file may start with YAML-style front matter (`---` lines) whose `description:` line is the short text shown in the picker; the front matter is stripped, the rest is the prompt section. `/style <name>` applies one through `Host.setPromptSection("output_style", text)`, `/style normal` passes `undefined`, so the main session and every agent at any depth get it from their next run (a run in flight finishes under the old one); pi sends only the changed section as a system patch. `/style` alone opens `selectForm` (`core/manager/select.ts`) through `HostUi.showForm` (`src/pick.ts`): every style plus `normal`, each with its description beside the name, the current one marked `✓` and preselected; Enter or a digit applies the pick exactly like `/style <name>`, Esc changes nothing. Outside tui mode `/style` alone notifies the current and the available styles instead. An unknown name notifies an error. Commands run in the main session only.
- `pi-style.json` (`{ "style": "concise" }`, a `choice` over the styles plus `normal`) is read at each session start by `src/settings.ts` through `readSettingsFiles` (`core/manager/settings.ts`), user file then trusted project file, each error warned once through `reportSettingsErrors`, and the stored style is re-applied. The command rewrites the user file (a failed write warns, the style still applies); `src/style.ts` only wires these together; when the project file sets a style the new one still applies live, with a warning that the project file wins at the next session start.

## Footer

- Replaces pi's footer (`HostUi.setFooter(render)`, tui only) with a block aligned to the composer prompt (`PAD`, one space, the composer margin) that starts and ends with one blank line (so pi's command list never touches it): context tokens (warning above 70 %, error above 90 %), the session cache hit rate (`cache 91%`, `cachePercentText`, hidden until the session reported cache activity and dropped first when the line is too narrow), main cost, model name and window (`formatWindow`); the session total (main plus every spending source); folder with `git:(branch)` when there is a branch, then the session name; thinking level with the `app.thinking.cycle` key; then the other extensions' status texts, one line per key sorted by key, without spending's own `pi-spending` status (`SPENDING_STATUS_KEY`), whose figures the block already shows.
- Cost and tokens come only from `spending:totals`: the footer keeps the last payload, so a render reads only cheap live values (`Host.context()`, `mainRequestUsage()`, `model()`, `thinkingLevel()`, `sessionName()`; the adapter memoises `context()` on the session leaf id and the model, as pi's own footer does, and `mainRequestUsage()` on the session id, file and leaf id). Until spending publishes the cost segment and the session-total line are hidden; the session total gets a dim ` (sub)` when `subscription` is set.
- Placement: the adapter draws the block as the below-editor widget `pi-footer` and installs an empty component in pi's footer slot (pi draws its built-in footer whenever the slot is unset; the empty component also hands the adapter pi's `footerData` for branch and statuses). Order is editor, notices (below), footer block (a blank line, usage, session total, folder and branch, thinking, a blank line and the statuses when any, a blank line), then the agent panel. pi has no ordering API for widgets: it keeps below-editor widgets in a `Map` in first-set order (re-setting a key moves it last) and clears them all, footer included, before every `session_start` (reload, `/new`, resume, fork). The order therefore rests on timing, not on load order: the footer sets its widget in its `session_start` handler and the adapter only re-renders it while it is mounted, and the panel sets its widget only when the first agent row appears, which happens after every extension's `session_start` has run (the registry is empty in a fresh runtime). pi runs `session_start` handlers in extension load order (`package.json` loads subagents first), so a below-editor widget set during another extension's `session_start` would land above the block if that extension loads first. `core/test/adapter/pi-footer.test.ts` checks this against pi's own `setExtensionWidget`/`setExtensionFooter`, and the panel tests check that the panel sets no widget at session start.
- Notices (`HostUi.setNotice`, `core/adapter/pi-notice.ts`): one-line texts that sit between the editor and the footer block, independent of load order. Each adapter copy keeps its own notices and registers them on a board shared through `globalThis` (`Symbol.for("pi-extensions.notices")`), so a notice set by one extension reaches the footer drawn by another. While a footer widget is mounted it draws every notice (sorted by key, indented by `PAD`) as its first lines, so they always sit right under the editor; without a footer they render in the adapter's own below-editor widget `pi-notices`, which the first adapter copy to see a tui `session_start` mounts (empty) before any extension's start handler runs, so its slot precedes every widget set later, the agent panel included; mounting the footer removes that widget and removing the footer mounts it again, so the notices change hands in both directions. When two copies set the same key the last one wins, and a call that does not change a copy's text does nothing. An adapter copy drops its notices at `session_shutdown`. Outside tui a notice falls back to `setStatus` under the same key, so RPC clients still see it; `session_shutdown` clears those statuses too. Notices are not statuses, so the footer's status lines never repeat them; `core/test/adapter/pi-footer.test.ts` checks the order against pi's own widget code.
- The adapter (`core/adapter/pi-footer.ts`) truncates every line to the width, re-renders on git branch changes and on `refresh()`, and drops the branch subscription when pi disposes the footer; the dim ellipsis is painted on each render, so it follows theme switches.

## Context

- `/context [all]` (main session only, like everything in the package) builds a snapshot: the breakdown the extension makes from `Host.contextFacts()` (`src/buckets.ts`), `lastRequestUsage()`, `mainRequestUsage()`, the time and `expandedByDefault` for `all`. Memory file paths are shortened to `./` (under the working directory) and `~` (under home) when the snapshot is taken. In tui mode it appends the snapshot as a `pi-context:snapshot` custom entry and the extension's entry renderer draws it in the transcript; pi draws it at once and again on resume, from the frozen figures, and the entry never enters the model's context. The renderer validates a stored entry field by field (`src/snapshot.ts`: numbers where numbers belong, `total` a number or null, `model` a string or absent, every message bucket a number) and draws nothing for one it cannot read. Other modes get a one-line `notify` summary instead (`src/summary.ts`, plain text, no theme), since no entry renderer runs there.
- Facts (`core/adapter/pi-context-prompt.ts`, `pi-context-messages.ts`): the system state is the replay of the `role: "system"` messages in `sessionManager.buildSessionProjection().messages` (`replaySystemMessages` in `session-file.ts`, the same replay agent session files use). pi writes the first system message when a run starts, so before the first request the adapter falls back to `ctx.getSystemPrompt()` (only the `<project_context>` and `<skills>` blocks cut out as their own sections, the rest as `prompt`) and to the active tools whose exposure is declared (not `hidden`, `deferred` or `codemode`). A tool's source comes from `getAllTools()` `sourceInfo.path`: `builtin:mcp` (pi's bundled MCP extension) is `mcp`, other `builtin:` paths `builtin`, anything else `extension`; registered tools that are `deferred` or `codemode` and not declared come with `onDemand: true`. Messages are pi's `estimateTokens` per non-system message of the projection. The reserve is compaction's `reserveTokens` (model override, setting, then pi's default) while compaction is on, else 0.
- Breakdown (`extensions/context/src/buckets.ts`): section `project_context` becomes the memory files, one row per `<project_instructions path>` block (one row when it cannot be split), `skills` one row per `<skill>` block, every other section and the leftovers of those two the system prompt; each is chars/4. Tools are chars/4 of their declaration, grouped by source; tools loaded on demand count 0 and only the MCP ones are listed, as loaded on demand. Messages are bucketed into user, assistant text, thinking, tool calls, tool results and other. The usage model (`src/breakdown.ts`) gives Messages the rest of pi's total after the fixed categories, or scales the fixed categories down to the total by largest remainder (`apportion`) and leaves Messages at 0 when their estimates exceed it (so the legend always adds up to the header), and falls back to the sum of the estimates, marked `~` and `estimated`, when pi does not know the total (after a compaction); free space is what is left after the reserve.
- Cache figures: hit rate = `cacheRead / (input + cacheRead + cacheWrite)` (pi normalises the four prompt buckets so they do not overlap, and its `/session` uses the same formula). Last turn = `getLastAssistantUsage` over the current branch (skips aborted, error and empty usage); session = `sumAssistantUsage` (`core/adapter/usage.ts`) over every assistant message of the main session file, leaving out cache-warming `usage` entries, compaction and branch-summary usage and tool-result usage, so it can differ slightly from pi's `/session`, which includes them. Agents' usage lives in their own session files and is never counted. Nothing is shown until the session reported a cache read or write; a last request without cache activity in a session that had it shows `0%` in the warning colour. The session figure is `sessionCacheHit` and every percentage is painted by `cachePercentText` (`core/manager/cache.ts`, success from 70 %, warning from 30 %, error below), the same functions the footer uses, so both show the same session figure.
- Rendering (pure over `ThemeLike`): `src/grid.ts` draws a 10 × 10 grid (20 × 10 for windows of 1M, 5 × 5 below 50 columns), each cell an equal share of the window; the filled cells are the rounded share in use, split between the categories by largest remainder, filled row-major in legend order as `■`, then free space `·`, then the reserve `░`, three shapes common fonts carry, so the grid reads the same in monochrome (there is no partial cell). The layout is measured: the widest of the header, cache and legend lines (`theme.width`) decides; 20 × 10 only when the grid, the gap and that line fit in the width, else 10 × 10 beside it when that fits, else the grid on top with the header, cache line and legend under it, and a header still too wide drops its `tokens` word; overflowing legend lines continue in the legend column. `src/details.ts` adds one section title per category with its summary on a `↳` line (a nested row: text at column 6), or every item by tokens when expanded, and `src/render.ts` composes the row: the accent info mark `»` (a snapshot, not a call that succeeded) before the bold `Context usage` and the dim ` · <time>`, then the grid, legend, overflow warning and details at column 4, and while collapsed pi's count line `... (N more items, ctrl+o to expand)` counting what expanding would list (none when expanded); the adapter's entry renderer puts the lines after the shared output pad and cuts them to the width with `...`. The window is `formatWindow` (`core/manager/format.ts`), as in the footer. Category colours are pi's thinking-level tokens from `thinkingOff` to `thinkingXhigh` (system prompt, system tools, MCP tools, extension tools, memory files, skills), messages `text`, free space `muted` and the reserve `warning`, so they follow the theme and red only ever means a failure.
- Footer segment: the footer reads `host.mainRequestUsage()` on each render and shows `cache 91%` (`sessionCacheHit` and `cachePercentText`) after the context tokens once the session reported cache activity; it is the first segment dropped when the line does not fit.

## MCP-import

- One command, `/mcp-import [<claude|cursor> [project] [apply]]` (`args.ts` parses and completes it). With arguments it does a dry run, or writes with `apply`. Without arguments, in tui mode, it picks interactively (`pick.ts`): it plans every source and scope pair (Claude Code and Cursor, user and project), keeps the pairs that would add a server (project pairs only in a trusted project) and, with two or more left, asks which with a `selectForm` (`Claude Code · user`, `3 new: … → <target>`). Then a `multiSelectForm` lists the servers to add, all checked (`a` all, `n` none, Enter adds), each row with its transport and a sign-in or notes marker. Unchecked servers are reported as skipped (`not selected`); nothing checked writes nothing. Esc on either form cancels silently. If nothing can be imported it says so, naming the checked files or that the servers are already present, or that the only servers are in an untrusted project. Outside tui, with no arguments, it fails with the usage line. `sources.ts` reads the tool's files for the scope: Claude Code user scope is the top-level `mcpServers` of `~/.claude.json`; its project scope is `projects["<cwd>"].mcpServers` of the same file (the cwd or its real path; Claude's local scope, which wins on a name clash) then `<cwd>/.mcp.json`; Cursor is `~/.cursor/mcp.json` or `<cwd>/.cursor/mcp.json`. A file that cannot be parsed is a warning, a missing file is skipped.
- `convert.ts` turns one entry into pi's shape, keeping only fields pi knows (`type`, `command`, `args`, `env`, `cwd`; `type`, `url`, `headers`) and recording a note for every rewrite or drop (Claude's `${VAR:-default}`, millisecond `timeout`, `headersHelper`, `oauth`; Cursor's `${env:X}`, `${userHome}`, `envFile`, `auth`), or a reason to skip it (`sse`, `ws` and other types, no `command` or `url`, a bad name, Cursor's `${workspaceFolder}`).
- `plan.ts` merges the converted entries into the target text (`<agentDir>/mcp.json`, or `<cwd>/.pi/mcp.json` with `project`): a name already present, also one that differs only in `-` and `_`, is skipped, and every other key of the file and its indentation are kept; a target that is not valid JSON stops the import. `report.ts` builds one notification, prefixed `pi-mcp-import:` like every notice of the extension (problems as warnings, usage and write errors as errors): the dry run lists the entries, notes and skips and writes nothing; `apply` and the interactive pick write the file (the interactive report starts `added N servers to <target>`, without a command echo) (a project write needs a trusted project) and says to `/reload` and check with `/mcp`, listing HTTP servers without an `Authorization` header for sign-in. No settings, no state.

## Transcript

- `extensions/transcript` switches the row look on. At load it registers `Host.registerToolRows` with `src/tools.ts`; at a tui session start it calls `setHiddenThinkingLabel("Thinking", "(K to expand)")`, `K` read from `HostUi.keyText("app.thinking.toggle")` (pi's thinking visibility toggle; no hint when unbound), which the adapter records for the agent pane too (see the thinking label above). User and assistant messages are pi's default: the repo patches no pi component. Disabling the extension leaves pi's look (the repo's own tools keep their rows, which they draw themselves).
- Which tools get rows (`core/adapter/pi-tool-rows.ts`): pi's built-in tools (`BUILTIN_TOOLS`), tools without a renderer of their own, and tools of pi's built-in extensions (e.g. `codemode`), which `ExtensionAPI.getAllTools()` lists with `sourceInfo.source` `builtin`; the check runs only for a tool that has a renderer of its own. Any other tool with a `renderCall`, `renderResult` or self shell keeps its look, so a third-party extension that replaces `codemode` draws itself. An extension that restyles a pi-shipped tool through `registerToolRenderer` keeps its look only when it loads before transcript (its resolver then wraps ours); loaded after, its renderers arrive through `next()` and the rows replace them. The agent view has no `getAllTools`; there the pi-shipped renderers it captures (`capturePiRenderers`) count as pi's.
- `src/tools.ts` is pure: it picks a `Look` (`src/look.ts`) per tool and builds every row the same way over `core/manager/row.ts`: the call is the title line, the result the children. The title is the mark (`markOf`: `◌` until the call finished, `⊘` when the adapter reports `aborted`, then `✗` or `✓`), the bold verb (`Read`, `Edit`, `Write`, `$`/`PS>` muted for `bash`/`powershell`, `Grep`, `Find`, `List`), the target in accent (paths cwd-relative or `~/…` by `homeRelative`, cut at the start; patterns and commands cut at the end), muted arguments (`read`'s `:5-14` range, `grep`'s ` in path`, a multi-line command's ` ...`), and then, after a muted ` · `: `stopped` (muted) for an aborted call, otherwise a failure reason in `error` when `failureSuffix` lets it sit on the title, then the recorded duration (`formatDuration` of `durationMs`, only from 5 s on and never on a running or timed-out call: a running row never ticks, since a changing row above the viewport forces pi's regular-mode renderer to clear and replay the scrollback). A title whose key argument has not streamed yet is the verb alone. Reasons come from the result: for shell rows pi's last status line (`src/output.ts` `shellResult`: `Command exited with code N` gives `exit N`, `Command timed out after N seconds` gives `timed out after Ns`, `Command aborted` is the stop), `file not found` for a missing file, otherwise the error's text; a reason that does not fit is the `↳` line, wrapped at column 4.
- Outcomes are the `↳` children: `read` counts lines (`Image` for images), `write` the lines of its `content` argument (`Empty file`), `edit` the added and removed lines of `details.diff` (`Added N lines, removed M lines`), `grep`, `find` and `ls` matching lines, files and entries from pi's text (`No matches`, `No files`, `Empty directory`; pi's bracketed notices not counted). Shell rows (`src/shell.ts`) show the last three output lines under pi's count line `... (N earlier lines, ctrl+o to expand)`, muted in every state, `No output` when there is none. MCP and unknown tools (`src/generic.ts`) are titled `server/tool` in accent bold (the adapter's `label`) or the bold tool name, with up to three `key=value` arguments, and show the first three output lines, each cut, then `... (N more lines, ctrl+o to expand)`, every line wrapped when expanded. `codemode` (`src/codemode.ts`) is titled `codemode` with the script's first line muted (after a leading `// @options:` line); its outcome comes from `details.calls`, pi's per-call records `{ name, args, status, durationMs, cost, error }`: `3 calls, 1 failed · 1611 lines of output` (output counted without pi's `Script completed/failed … Output:` header), `2 calls` while running; expanded, the whole script, every call as a nested row (`running`, `ok`, `error` and `cancelled` mapped to `◌`, `✓`, `✗`, `⊘`; pi's own `12ms` and `$0.0012` figures kept dim; a failed call's error under it) and the output. A failed non-shell call shows its error in the error colour, three rows until expanded.
- The hint is `expandHint` with the key of `HostUi.keyText("app.tools.expand")` at render time, only while collapsed and only where expanding shows more: after an edit, write or codemode summary, and pi's count line where output is cut. `read`, `grep`, `find` and `ls` have none (the count is the result). When the row is narrow the hint gives way to the content, and a count line drops only its `, key to expand` part.
- Bodies: an expanded `edit` draws `details.diff` itself (`src/diff.ts`, parsed once per render from pi's display lines `+NN text`, `-NN text`, ` NN text` and the blank-numbered `...` between hunks; the counts come from the same parse, so a diff it cannot read shows none and pi's own body instead): the gutter `+`/`-`, the right-aligned number and a space, tabs expanded to three spaces and control characters dropped, each run of removed lines paired with the added run after it, the changed tokens of a pair marked (`src/words.ts`: a longest common subsequence over grapheme-safe word, space and single-symbol tokens, skipped above 400 tokens or when more than half of the pair's characters changed); removed and added rows sit on the `removed`/`added` backgrounds padded to the width with the changed tokens on the word backgrounds, wrapped lines keep the background under a blank gutter, and context and gap rows are muted. When `ThemeLike.panels` is false (pi's system theme without a terminal colour report, where every panel background is the bare default) the diff falls back to pi's own look: changed lines in `success`/`error` and the changed tokens `inverse`. An expanded `write` draws every line of `content` the same way, as added lines. `piBody` is set for every built-in but `write` when the result is not a failure (for `edit` only when its diff does not parse, for shell rows only when there is output), so expanded rows show pi's own output at column 4 under the outcome; shell rows set `dropTiming`, since the title already carries the duration. An aborted call draws no outcome or body, except shell rows, which keep their streamed output.
- Not done: tool-call grouping (folding consecutive reads and searches into one row), a per-run thinking duration (pi has one hidden-thinking label for every message), a separate denied state (a call another extension blocked is `✗` with the reason: the adapter never sees another extension's block decision), syntax highlighting in diffs, an ASCII glyph fallback.

## Persistence summary

Every file the extensions write lives under pi's agent dir or session dir (`~/.pi/agent` by default; the `sessionDir` setting or `--session-dir` moves session data), except handoff files (OS temp dir), `worktree: true` agents (checkout under `<cwd>/.pi/worktrees/`, git's `pi-agents/...` branch and `.git/worktrees/` metadata) and the project files written on the user's command in a trusted project (`.pi/pi-subagents.json`, `.pi/mcp.json`). `.pi/agents/<name>.md` is written by the main session's own write tool on `/agents create … project`, not by an extension.

- Agents dir (`agentsDirFor` in `extensions/subagents/src/model/paths.ts`) = `<main session file without .jsonl>/agents`, or `<agentDir>/pi-subagents/<session id>/agents` for a session without a file.
- `<agents dir>/<id>/`: `manifest.json` (rewritten on state or worktree change; final counters on close), the child pi session `.jsonl` (with `parentSession` and the prompt record), `result.md`, and any files the agent writes there (a shell agent's `<n>.log` command logs; the task's `Agent folder:` line names it).
- `<OS temp dir>/pi-session-limits/<session id>-handoff.md` (main) and `<OS temp dir>/pi-subagents/<session id>/<agent id>-handoff.md` (agents): handoff files.
- `<cwd>/.pi/worktrees/<id>-<stamp>/`: a worktree agent's checkout, removed when its chain ends unless git refuses (uncommitted changes); its branch stays only if it moved past `base`. `.pi/worktrees/.gitignore` keeps them out of `git status`.
- Main session file: `pi-spending:usage`, `pi-spending:main-offset` and `pi-spending:main-tokens-offset` entries; `pi-context:snapshot` entries (one per `/context` in tui mode); the new session's seed message after a handoff.
- `<agentDir>`: `pi-subagents.json` (its `agents` key written by `/agents setup` with the user scope), `pi-session-limits.json`, `pi-notifications.json`, `pi-style.json` (written by `/style`), `agents/**/*.md` (the main session writes `agents/<name>.md` on `/agents create`; no extension writes it), `mcp.json` (written by `/mcp-import … apply`). `<cwd>/.pi/` (trusted projects only): the same settings files and `agents/**/*.md`, of which `/agents setup` writes `pi-subagents.json`, `/mcp-import … project apply` writes `mcp.json`; `/agents create <name> project` has the main session write `agents/<name>.md`.
- Registry, batches, ledger totals and limit phases live in memory and are lost on reload.

## Cross-cutting

- Errors: user-facing failures become data, not exceptions: a failed agent is a closed record with `error`, tool misuse returns an error result, bad settings or agent files become warnings and are skipped. `startBatch` throws for invalid requests so nothing is half-started.
- Model resolution (`core/adapter/model-resolver.ts`): no request means the main session's model; otherwise exact `provider/id` or id among models with credentials (preferring the session provider, then the default provider), then fuzzy matching by tokens and edit distance within a provider scope, newest version per family. Several families -> `ambiguous`, nothing -> `unknown` with suggestions; both make `run_agent` fail with the candidates. Thinking level: request suffix, then definition, then the main session's level.
- Prompt cache: agents never compact and never get cache warming; their prompt prefix is fixed at spawn.
- Tests: unit tests run against the fakes with no network (`npm run check`, also what CI runs). `*.live.test.ts` spawn real agents under `npm run test:live`, locally only: `PI_LIVE_MODEL=provider/id[:thinking]` is required (the suites fail at once when it or the credentials are missing), the optional `PI_LIVE_CHORE_MODEL` runs the chore agents on a second model, and a temporary agent dir holds only copies of the credentials.
