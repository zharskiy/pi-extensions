# Architecture

How the eight extensions work at runtime. Folder layout is in `STRUCTURE.md`.

## Layers and dependency rules

- `core/adapter` is the only code that imports pi (`@earendil-works/*`, `typebox`). It exposes `contract.ts`: `Host` (the main session as seen by an extension) and `AgentRuntime` (spawning and reading agent sessions).
- `core/manager` is pi-free shared infrastructure: plugin manager, typed bus, settings parsing, `settleWithin`, and the cross-extension contract: `handoff.ts` (handoff sections, `HandoffValidation`, `validateHandoff`) and `channels.ts` (the `pi:busy`, `spending:usage` and `spending:totals` channel names, payload types and parsers), plus `format.ts` (`formatTokens`, `formatDuration`, shared by the footer, the working indicator and subagents). Channel names and the handoff format live only there; extensions and subagents plugins import them from there, never from each other.
- Extensions import only `contract.ts` and `core/manager`. Each extension's `src/index.ts` is the single file allowed to import `pi-adapter.ts`.
- Extensions never import each other; they talk over pi's shared event bus (`Host.publish/subscribe`). Plugins inside an extension never import another plugin's folder; they share code through `src/model` and `src/components` and talk through the manager.
- No provider knowledge: no code or prompt names a model provider or a model id. Pi resolves providers, credentials and models; the harness passes `provider/id[:thinking]` strings through. The only exceptions are configuration: the shipped agent files name their `model`, and the subagents README lists those models. Cost is pi's own usage and cost figures.
- `test/architecture.test.ts` enforces the import rules above by scanning imports, plus: `core` never imports `extensions`, no tests inside `src`/`core/adapter`/`core/manager`, and `core/test` holds only `adapter` and `manager` tests. Which files may import pi packages (`core/adapter`, and among tests only `core/test/adapter`) is enforced by biome's `noRestrictedImports` overrides in `biome.json` alone.

## Startup and the adapter

1. pi loads each entry listed in `package.json` (`pi.extensions`). Each default export is `createPiExtension(boot, { root, namespace, childExclude })`.
2. The factory returns immediately when it runs inside an agent session (an `AsyncLocalStorage` scope set while children load), so no extension boots inside an agent.
3. Otherwise it builds a `Host` over pi's `ExtensionAPI` and an `AgentRuntime` over pi's SDK, then calls `boot(host, runtime, paths)`.

Host behaviour worth knowing:
- The adapter keeps the latest pi `ExtensionContext`, captured on every event, tool call and command. On `session_shutdown` every registered handler runs even if an earlier one throws, the context is then always dropped, and the first error is rethrown afterwards so pi reports it.
- `Host.session()` always returns a `SessionInfo`; outside a live session (before `session_start`, after `session_shutdown`) it throws, and so do `readEntries`/`sessionUsage` without a file argument. Every other Host call that needs the context (UI, `publish`, `appendEntry`, `sendUserMessage`, `dispatchCommand`, `isIdle`) is then a no-op. Code that can run after its own shutdown (spending, for reports arriving while other extensions shut down) must not call `session()`.
- `onSessionStart(info, parent)`: `parent` is the session file a freshly created session came from (its header's `parentSession`): `/fork`, `/clone`, or a handoff switch. It is unset for a plain `/new` and for resume, startup and reload. `readEntries(customType, file?)` and `sessionUsage(file?)` read the live session, or another session file when one is given. `onCompact` fires after pi compacts the main session.
- pi builds a fresh extension instance and event bus for every session (`/new`, `/resume`, `/fork`, `/reload`) and fires `session_start` once per instance, except in RPC mode where it fires twice. State therefore starts empty in each instance: handlers that only reset state at session start and unsubscribe handles at shutdown are not needed. Settings are the exception below.
- `onIdle` is pi's `agent_settled`; `onTurnEnd` passes a `ContextSnapshot` (tokens, window, percent).
- `onPhase` is computed by `pi-phase.ts` from `turn_start`, `message_update`, `message_end`, `tool_execution_*` (top-level only), `agent_end`, `agent_settled`; `idle` fires after `onIdle`.
- `pi-editor-frame.ts` installs one `HostEditor` subclass when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `captureEditorKeys`) is used; the frame is optional; keys reach the hooks only while the editor has focus. It removes the editor again when no frame and no hook remain.
- `onDialog` is pi's `ui_prompt_start/end` (outermost dialog only; overlays are `custom`). `HostUi.onKeyPress` observes terminal input without consuming it.
- `sendUserMessage` delivers immediately when idle, otherwise as a follow-up. `sendHiddenMessage` sends a `display: false` custom message: a follow-up of the active run, or, when idle, a next-turn message plus a short visible user line that starts the turn through `prompt()`, because only `prompt()` emits `before_agent_start` (pi skips it for custom messages that start a run). `registerEntryRenderer` renders `appendEntry` entries, each line indented by pi's `outputPad` and cut at `width - 2 * outputPad`.
- `setMainPrompt` replaces pi's default prompt in `before_agent_start` and re-adds the `tools`, `rules` and `docs` sections pi would otherwise drop (`main-prompt.ts`). Only the subagents `run-agent` plugin calls it, so the main prompt is replaced only when that plugin is enabled.
- `ToolSpec` and overlay/widget factories are plain-text contracts; the adapter converts them to pi tools and TUI components. UI calls degrade to no-ops outside TUI mode.
- `ToolSpec` renderers receive `ToolRenderState` (pi's render context: `toolCallId`, `expanded`, `isPartial`, `executionStarted`, `isError`, `args`, `durationMs`, `outputPad`, `invalidate`) and may set `renderShell: "self"` (the adapter then indents each line by pi's `outputPad` and cuts it at `width - 2 * outputPad` with `…`, never wrapping, since pi pads only its own box); the `ToolResult` a `renderResult` receives carries `isError`; `update(text, details)` forwards details to partial renders.
- `terminalNotify(message, channel)` writes BEL for `bell`, and for `auto` only an OSC 9 notification (OSC 777 titled `pi` on rxvt), no BEL; tui only.

Unit tests use `core/test/helpers/fakes.ts` (fake host, runtime and child session) instead of pi; a few tests (UI and message-agent) import adapter modules that load pi offline (`pi-ui.ts`, `session-file.ts`, `route.ts`), and only `core/test/adapter` tests import pi packages directly. `core/test/adapter` holds conformance tests against pi, offline.

### Child sessions

`runtime.spawn` returns a `ChildSession`. The adapter tracks a `running` flag, set when `start`, `send` or `wake` issue `session.prompt` and cleared on the `settled` event. While `running` is set (including the window before pi marks the session as streaming), `send(msg, "steer" | "followUp")` and `wake(text)` never call `prompt` again: they queue on pi's own steer or follow-up queue, so a message sent right after `start` joins the first turn and pi's "already processing" error cannot come from the adapter. When nothing is in flight they start a new prompt; if pi rejects it, the child emits an error `assistant_message` and `settled` so the runner closes the agent instead of hanging. If extension binding fails during spawn, the child's extensions get `session_shutdown` and the session is disposed before the error propagates.

## Extension manager and plugins

Only subagents uses the manager; session-limits, spending, working-indicator, notifications, command-aliases, composer and footer wire a few functions directly in `boot`.

- A `Plugin` is `{ id, requires?, enable(ctx) => disable? }`. `ctx` holds `host` (the real one), `runtime`, `bus`, `settings`, `services`, `root`.
- Boot order: plugins are topologically sorted by `requires` (cycles throw). A plugin is skipped silently when listed in `disabledPlugins`, and with one warning at session start when a plugin it requires is off or missing.
- Plugins communicate two ways: `services` (a typed map; `provide`/`require`/`has`, where `require` throws if the provider is not enabled) and the typed in-process `bus` (`agent:changed`, `agent:turn`, `agent:closed`, `agent:usage`, `batch:settled`). Bus listener errors are caught and passed to `onError`, which shows a UI error notification.
- On every `session_shutdown` the entry calls `disableAll()`, which runs the disable callbacks in reverse order, sequentially; a failing callback goes to `onError` and the rest still run. The adapter's own shutdown handlers are fault tolerant in the same way (see above).
- `settleWithin(promise, ms)` waits for a promise or a timeout, whichever comes first, and never rejects. It bounds child aborts (5 s) and child extension shutdown (2 s).

Settings: each extension has a JSON file `<agentDir>/<file>` (user) and `<cwd>/.pi/<file>` (project, read only when the project is trusted). `parseSettings` validates each known key against a schema (number range, string list, boolean); invalid keys are dropped and reported as a warning notification, the rest is applied. Settings are read once per session start as defaults, then user, then project, because pi builds a new extension per session. Subagents additionally reads `disabledPlugins` from the user file at boot, since it decides which plugins enable; a project file cannot set it (warning, key ignored). Session-limits computes its ratios the same way at session start. Nothing is reloaded live.

## Subagents

Plugins (`src/plugins.ts`; requirements in brackets): `agent-registry` (in-memory records, `manifest.json`), `agent-definitions` (agent `.md` files, agent prompts), `run-agent` [registry, definitions] (runner, tools, outbox, main prompt, completion lines, the `handoff` service: template and schema, and the `tools` service), `usage-report` [run-agent], `agent-status` [registry, run-agent], `limits` [registry, run-agent], `agent-panel` [registry] (panel below the editor, keyboard selection, footer status), `agent-view` [registry] (`/agents`: the list and the agent view in one overlay, the `agentView` service).

### Agent definitions and prompts

- Markdown files with frontmatter are loaded from the built-in `agents/` when the plugin enables, and from the built-in `agents/`, then `<agentDir>/agents/`, then `<cwd>/.pi/agents/` (trusted projects) at session start. Later files override earlier ones by `name`. Invalid files, unknown `subagents` references and `subagents` cycles remove the offending definitions and produce warnings.
- Shipped agents name `model: provider/id:thinking`. A file without a `model` line (or with `inherit[:thinking]`) runs on the main session's model and, without a suffix, its thinking level.
- An agent's configured model and thinking are computed in one place, `parseDefinition` (`agent-definitions/loader.ts`), and stored on the `AgentDefinition`; the runner (`planModel`) and the `run_agent` description read them only through the `definitions` service. A future per-agent override (for example a command that sets an agent's model and thinking) plugs in at the `onSessionStart` reload in `agent-definitions/index.ts`, by overlaying stored values onto the loaded definitions. The `model` parameter of `run_agent` and the main-session fallback are applied on top in `planModel`.
- Agent prompt = pi's own prompt for the child, with appended text: `prompts/base-system-prompt.md`, then `# Agent: <name>`, the file body and a fixed output contract.
- The main session prompt is `prompts/main-session.md`, set by `run-agent` at session start (plus `prompts/main-session-agent-status.md` when the agent-status plugin is on). `prompts/handoff.md` is the agents' handoff instruction template (`{{path}}` substituted), read by run-agent's `handoff.ts`. Prompt files are read once when their plugin enables.

### A run_agent call, end to end

1. Main model calls `run_agent { agents: [...], wait? }` -> `runner.startBatch` validates agent names, the caller's allowed `subagents`, depth (`callerDepth + 1 <= maxDepth`, main is depth 1) and resolves every model. Any error throws and nothing starts.
2. Registry creates one record per agent (`queued`), writes `manifest.json`, emits `agent:changed`. The tool reports the batch through `update(text, details)` at once (`details.agents`: id, agent, description, model), returns ids and tells the model to end its turn (`wait: true` blocks until the batch settles instead). The block renders with `renderShell: "self"`: `renderCall` draws `⠹ Running N agents…` while pi's `isPartial` is set and nothing afterwards; `renderResult` draws the rows from the registry (chain terminals, chain totals) and, once final, the header (`N background agents launched (← to manage)` while any record is open, `N agents finished` for `wait`; with the agent name, `N background explorer agents …`, when every agent of the batch shares it). The adapter indents each line by pi's `outputPad` and cuts it, never wraps. The stored `invalidate` re-renders at most every `renderThrottleMs` after an `agent:changed` of the batch and once more at `batch:settled`; without a record (resume, `/reload`) a row reads `Status unavailable · /agents <id>`.
3. `launch` per agent: acquire a semaphore slot (`maxConcurrent`, shared by the whole tree) -> optionally create a git worktree -> `runtime.spawn(SpawnSpec)` -> record becomes `running` -> `child.start(task)` -> messages queued while `queued` are steered in.
4. `spawn` builds an in-process pi `AgentSession` (not a subprocess) inside the child scope: in-memory copy of the main session settings with compaction disabled, `reserveTokens` set and cache warming off; tools = the definition's allowlist or the main session's active tools (minus excluded extension paths), plus MCP, `codemode` and `tool_search` unless `tools: []`, plus custom tools from the runner; skills = the main session's skill files, filtered; model resolved again by exact ref; session file in the agent's dir with `parentSession` = main session file; binds no UI, like pi's print mode: dialogs resolve to their denials (`confirm` false, `select` and `input` undefined), `notify` does nothing, `ctx.hasUI` is false; only the main session is interactive, and an agent that needs a decision reports it in its result.
5. A hidden child extension cancels every compaction and, on the first provider request, appends a `pi-subagents:prompt-record` entry (skills, guidelines, raw provider payload, model) to the child session file. The entry stays in the session file and `runtime.readSession` still parses it; the agent view shows its provider payload, the first request as sent, as one collapsed Request block (key `r`).
6. Child events (`turn_end`, `assistant_message`, `tool_start`, `settled`) update the record (turns, tool calls, tokens, context, last text, and `activity`: the last tool name or the first line of the last assistant text) and emit `agent:turn` and `agent:usage`.
7. On `settled`: if the agent has its own open batches or undelivered wakes, it goes idle and releases its slot. Otherwise it closes: `done` with the last assistant text written to `result.md`, or `failed` (abort, error stop reason, empty result). Closing releases the slot, emits final usage, disposes the session and immediately stops any open children of that agent.
8. When every record of the batch is closed and every worktree cleanup is done, `batch:settled` fires and the batch text (one `## <id> (<agent>) - <state>` section per chain terminal; results inline up to `inlineResultChars`, otherwise path and preview) is posted to the caller's outbox with the batch id and its terminal count. Separately, every closed record whose caller is `main` and which has no successor appends a `pi-subagents:agent-closed` entry (`{ v: 1, id, agent, description, state, durationMs, error?, sessions?, worktree?, branch? }`; for a worktree agent once `worktree.cleanup` is known), before the wake goes out; the entry renderer registered at boot draws one line (`✓ Agent "…" finished · 1m 5s`) and resume redraws it from the entry alone. Nothing is appended once run-agent's session-shutdown handler has started, so agents interrupted by a session switch print no line.
9. Outbox: for the main session it delivers each settled batch at once through `Host.sendHiddenMessage`: the text as a `pi-subagents:wake` hidden message (`details.batches`) with the visible line `↳ N agents finished` (N = the batch's chain terminals). The adapter picks the path: while a run is active the hidden message joins it as a follow-up and nothing visible appears; when idle the visible user line starts the turn through `prompt()` and the hidden message follows it (pi records the user line first). For an agent caller it holds texts while that agent's turn runs and, on its idle, re-acquires a slot and wakes the child with the joined texts as one follow-up prompt.

Nesting: a child gets `run_agent`, `message_agent` and `agent_status` as custom tools only when its definition allows subagents and it is below `maxDepth`; these tools are bound to the child as caller and drive the same runner. A child waiting on its batch holds no slot, so the tree cannot deadlock.

### Messages, stop and shutdown

- `message_agent` (only the agent's caller) routes `[message from <sender>]` text: held while queued, steered while a turn is in flight, a follow-up (after re-acquiring a slot) when idle.
- Stop: a running agent enters `grace`, its turn is aborted and its slot released; a message during grace is answered, otherwise after `stopGraceSeconds` it closes as `stopped` (last text kept as result). A queued agent, a second stop during grace, or `stopGraceSeconds: 0` closes at once.
- Session shutdown: the outbox is cleared, every open agent closes as `failed (interrupted)` (or `stopped` if in grace), children are aborted and disposed.

### Context limits and handoff chains

- Effective limit = `min(definition limit, model window - reserveTokens)`. After each turn that continues with tool calls, `limits` compares context tokens: at `softContextRatio` it routes one warning; at the limit it sets `handoffRequested` and routes `prompts/handoff.md` with the agent's handoff path (OS temp dir); past `limit * hardContextRatio`, or 3 turns after the request, it aborts the agent.
- When an agent with a handoff request settles, the runner validates the handoff file (sections Status, Outcome, Evidence, Blocker, Next, Files touched in order; Status `partial` or `blocked`). `partial` within `maxChainLength`, not stopped and not in a settled batch -> a successor record in the same batch (same task, same worktree, task text points at the handoff) and the predecessor closes as `handoff`. Otherwise the agent closes as `handoff`, flagged invalid if the schema failed. A missing file is `failed`.
- Chains are invisible to the caller: one wake, one result section with a `Chain:` line, and any id of a chain resolves to its last link for status, messages and stop.

### Status and views

- `agent_status` reads in-memory records only; it never touches the agent.
- Every surface reads the same clock, spinner (`components/spinner.ts`, frame from `Date.now()`), formatters (`components/format.ts`, which re-exports `formatTokens` and `formatDuration` from `core/manager/format.ts`) and state words (`components/state-text.ts`); the record's `activity` (last top-level tool name or first line of the last assistant text, set by the runner, not persisted) feeds the panel. The `tools` service (`{ list(), add(spec) }`, provided by `run-agent`; `agent-status` adds its spec) carries the three tool specs so the agent view renders nested calls with the main session's renderers. Re-render throttling is `renderThrottleMs` everywhere.
- The agent panel (`agent-panel`) renders the registry in tree order (`components/tree.ts`) with the shared row grammar (`components/agent-row.ts`) in a `belowEditor` widget: at most five rows plus `↑/↓ N more` markers, a selection driven by `HostUi.onEmptyEditorLeft` and `captureEditorKeys` (consumed: `↑`, `↓`, `Enter`, `x`, `Esc`; any other key releases the capture and clears the selection), `done` rows kept `doneLingerMs`, other closed rows `failedLingerMs` or until cleared. It refreshes through `components/refresh.ts` (`watchAgents`: `agent:changed` throttled by `renderThrottleMs`, plus an unref'd ticker at 100 ms while any row runs, 1 s while only queued or closed rows show, none otherwise). The same plugin sets the footer status `pi-subagents` (`N agents` while any record is open, `/agents to see agents` for `agentsHintMs` after the last closes).
- The `/agents` list shows the agent tree in two sections (`Running`: open roots with their listed descendants; `Completed (n)`: closed roots, newest first, with their descendants; `list-model.ts`, `treeOrder` per section), re-renders on `agent:changed` (throttled by `renderThrottleMs`) plus the shared ticker; closed records stay for `lingerMs` (a closed subtree from its root's `endedAt`), or under an open caller, or until `x` clears them.
- The agent view shares the list's overlay (one `openOverlay`; the host component swaps list and view, `Esc` returns to the list only when the view was opened from it). It reads the agent's session file through `runtime.readSession`, re-parsing only when the file's size or mtime changed, and falls back to `manifest.json` (which stores the final `turns`, `toolCalls` and `tokens`) for agents not in memory. Its transcript renders built-in tools with pi's definitions, `codemode`/`tool_search` with renderers captured from pi's exported extension factories (generic fallback if capture fails), and the subagents tools with the specs passed to `createTranscript({ tools })`. Above the transcript, a collapsed Request line expands with `r` to the prompt record's `providerPayload` as pretty-printed plain text. Nothing of the view is persisted.

### Worktrees

`worktree: true` writes `<cwd>/.pi/worktrees/.gitignore` (`*`) when missing, then runs `git worktree add -b pi-agents/<id>-<stamp> <cwd>/.pi/worktrees/<id>-<stamp> <base>` from the session cwd, where `base` is the HEAD sha; the agent's cwd is the same subdirectory inside it. A failed git or fs step fails the agent with `worktree failed: <error>`. `Worktree = { path, branch, base, cwd, cleanup? }`. A successor is created holding its predecessor's worktree. `releaseLive` is one teardown per agent: it disposes the child, then, for a closed record without a successor, runs `git worktree remove <path>` (no `--force`), deletes the branch only if it still points at `base`, and stores the outcome as `worktree.cleanup` (`removed`, `branch kept`, `kept`) on every link of the chain. A batch settles only after every member's cleanup, so results show the final outcome; shutdown awaits every pending removal except one whose `git worktree add` is still running. Stopping an agent queued for a slot tears it down at once.

## Session-limits

- Active only in `tui` and `rpc` modes (a `Host` wrapper suppresses events otherwise). Thresholds compare main session context tokens to the model window: `softRatio` (0.6) shows a warning footer segment, `hardRatio` (0.75) triggers the handoff.
- Sequence: turn end at hard level -> send the `prompts/handoff.md` instruction as a user message with the path `<OS temp dir>/pi-session-limits/<session id>-handoff.md` -> on each turn end/idle check whether the file is new (mtime changed) and valid (same six sections, Status `done`, `partial` or `blocked`) -> if valid and no busy source -> dispatch `/session-handoff` -> `newSession({ parentSession, seed })`, seeding the new session with a `pi-session-limits-handoff` custom message holding the handoff.
- An invalid or missing file after the session settles gets one resend with the errors; after 2 instructions the phase becomes `stuck` and the user runs `/session-handoff` by hand. User activity after the request causes the instruction to be re-sent before switching.
- Busy sources: any extension can publish `pi:busy { source, busy }`. Subagents publishes it while any agent is open; the switch waits until all sources are idle (then 1 s), and a manual switch asks for confirmation. The notifications extension reads the same channel to hold its idle notification.
- All state is in memory, per extension instance; the only file is the handoff. A pending switch whose `/session-handoff` command never runs ends in the failed phase at the next idle or turn end; a second `/session-handoff` while one runs is ignored. A context window of 0 or unknown token usage turns the extension off for that moment (no request, footer cleared).
- `Host.onCompact` fires after pi compacts the main session; session-limits uses it to forget its cached context size (pi reports unknown tokens after compaction), which clears the footer segment until the next turn.

## Spending

- Main cost = `sumUsage` over the session entries (assistant, tool result, `usage`, compaction and branch-summary usage; `Host.sessionUsage()`), as priced by pi. Child agents use the same `sumUsage` (`ChildSession.ownUsage`).
- Other costs arrive on `spending:usage { source, id, usage }`. Subagents' `usage-report` forwards every `agent:usage` (child session's own usage, at any depth, since all agents share one runner) with `source: "agents"` and the agent id as `id` (ids are unique within the session's agents folder, earlier runs included), with no dedup of its own, since the ledger is idempotent.
- The ledger keeps the latest report per `(source, id)` and replaces it only when neither cost nor tokens go down and one goes up (monotonic: totals never go down), sums per source, and shows `main $x · agents $y · total $z` (plus `(sub)` when the adapter's `subscription` is set: pi reports OAuth for the main model and the provider's OAuth sign-in is marked as a subscription, pi's own footer check) in the footer once any source is above zero; total is the raw sum rounded to three decimals.
- Persistence: changed reports are appended as `pi-spending:usage` custom entries in the main session file at once when a report arrives while the main session is idle (agents mostly run then, so a crash loses little), otherwise on the next idle, and on shutdown; they are replayed on session start (resume). Reports that arrive after spending's own shutdown are ignored. Offset entries that are not finite numbers read as zero.
- Lineage: totals cover the whole session lineage. Compaction and `/tree` only append to the same file, and `sumUsage` reads every entry of every branch. When a session is created from another one (`/fork`, `/clone` or a handoff switch; `parent` set) spending appends a `pi-spending:main-offset` entry (the parent's main cost, its own last offset plus all its entries, minus the usage of the entries copied into the new session), so main = last offset + `sumUsage` of the new session's entries; it also appends a continuation marker report, absorbs every parent `pi-spending:usage` report under an id prefixed with the parent file name (so new agents cannot collide with parent agent ids) and persists them into the new session at once; restore ignores reports before the last marker, so resumed sessions and chains of forks and handoffs keep the totals. Only a plain `/new` starts at zero; a handoff switch keeps the totals, since it continues the same work in a new session. Without a session file (`--no-session`) there is no parent file: a fork starts from the copied entries only, and a handoff switch starts from zero (session-limits passes no parent). A parent that cannot be read falls back to the resume path over the session's own entries, with a warning. Only the first `session_start` of an instance inherits: pi's rpc mode rebinds extensions twice for fork, clone and new-with-parent, and a second inheritance would append a second continuation marker after the absorbed parent reports, which a later resume would then drop.
- Totals: on every refresh (session start, accepted report, turn end, compaction, idle) spending publishes `spending:totals { main: { cost, tokens }, sources: [{ source, cost, tokens }], subscription }`. pi constructs every extension and runs its subscriptions before `session_start`, so listeners hear the first publish regardless of load order; there is no request channel. Tokens are chargeable tokens (`input + output + cacheRead + cacheWrite`); main tokens carry over a fork or handoff through a `pi-spending:main-tokens-offset` entry, like main cost (a parent forked before that entry existed has none, so main tokens undercount its ancestors while cost stays right; new chains are complete). Both offsets are read once at session start (or set by the fork inheritance) and each refresh reads `sessionUsage()` once.

## Working-indicator

- Active only in `tui` mode. On session start it sets `HostUi.setWorkingIndicator` to the `SPINNER` frames once; pi keeps them for the whole session, so they are not re-set per run (that would restart the animation). The adapter (`pi-working.ts`) paints them with the theme's accent colour, and the working calls are no-ops outside `tui`.
- The clock counts the current prompt (one agent run), not a turn. The first `Host.onAgentStart` of a run (skipped outside `tui`, so no interval runs in other modes) records the start, reads pi's `app.interrupt` key once through `HostUi.keyText`, and picks a random verb. Repeated `agent_start`s inside the run (retry, compaction, continuation) are ignored. An unref'd interval rewrites `HostUi.setWorkingMessage` every `TICK_MS`, even while the row is hidden, as `<verb>… (<tool> · <elapsed> · <key> to interrupt)`, picking a new verb every `VERB_MS`. `<tool> · ` appears only in phase `tool` (the most recent top-level tool still running), and `<elapsed>` uses `formatDuration` from `core/manager/format.ts`, the duration format shared with subagents (`12s`, `1m 5s`).
- Visibility follows `Host.onPhase`: entering `writing` calls `HostUi.setWorkingVisible(false)`, and leaving it writes the message and then calls `setWorkingVisible(true)`. pi re-shows the row at once while a run is active (`isStreaming`), so the row returns as soon as assistant text stops, in the same turn. Only transitions call pi, so a run without text never toggles it. `onPhase("idle")` (after the `onIdle` handlers of `agent_settled`) stops the interval, restores pi's visibility flag if it was hidden, and restores pi's default message. Shutdown stops the interval and clears the message; pi resets the flag itself on session switch and reload.
- Only the main session drives it: phases come from the main session's pi events, child sessions run in their own `AgentSession` with no-op working UI, and the extension subscribes to no bus or channel. Nothing is persisted.

## Notifications

- Active only in `tui` mode and when `channel` is not `off`; otherwise it registers no key listener and arms no timer. `pi-notifications.json` is read at session start; nothing is persisted, timers are unref'd and cleared on shutdown.
- Idle notification: `Host.onIdle` (pi's `agent_settled`, once per run) marks the settle pending and, when no source is on the busy channel (`pi:busy`, kept as a set of source names like session-limits), arms an `idleDelayMs` timer. `Host.onAgentStart`, any key (`HostUi.onKeyPress`, observed without consuming) and a busy source appearing cancel it; the last busy source clearing or a dialog ending re-arms it with the full delay while the settle is still pending. At fire time it checks again (pending, no busy source, no dialog, `isIdle()`), sends `pi is waiting for your input` and clears the pending settle, so a settle notifies at most once.
- Agents and the wake: subagents holds the busy channel while any agent is open. Agents finishing while main is idle arm the timer, but the outbox's wake starts a run through a visible user line at once, which cancels it; that run's settle arms it again. One notification follows the finished work.
- Dialog notification: `Host.onDialog` (pi's `ui_prompt_start`/`ui_prompt_end`, outermost dialog only, main-session dialogs only since agents never open one; `custom` overlays ignored). `dialogDelayMs` after the later of the dialog start and the last key it sends `pi needs your input: <title>`, at most once per dialog; the dialog ending cancels it.
- Output: `HostUi.terminalNotify(message, channel)` with `auto` (OSC 9/777 only, no BEL: the idle notification follows ordinary replies too, and a bell each time is noise) or `bell`.

## Command-aliases

- `ALIASES` maps an alias to a built-in command (`/continue` -> `/resume`, `/clear` -> `/new`, `/exit` -> `/quit`). pi runs built-ins in the editor's submit path before extension commands, so the alias is rewritten before pi sees it, through three `HostUi` calls implemented in `core/adapter/pi-editor-input.ts`, all no-ops outside tui mode.
- `onEditorSubmit`: a terminal input listener that, on the `tui.input.submit` key, swaps an editor text that is exactly an alias for its target before the key is processed. `mapCommandCompletion`: wraps the autocomplete provider so picking an alias in the slash menu inserts the target.
- Each alias is also a registered command. If it still runs, `submitEditor` waits one macrotask, sets the target as editor text and feeds Enter to the TUI's focused component (the TUI is captured through a widget factory that is removed at once); when no component takes input the extension notifies `Could not run <target>`. No state, no files.

## Composer

- On session start composer hands `host.ui.setEditorFrame(frame)` a pure `EditorFrame` (`chrome`, `left`, `minWidth`, `decorate(lines, layout, paint)`). The adapter (`core/adapter/pi-editor-frame.ts`) installs one `HostEditor` subclass of `CustomEditor` through `ctx.ui.setEditorComponent` when the composer frame or a subagents key hook (`onEmptyEditorLeft`, `captureEditorKeys`) is used, only in `tui` mode and only when no editor other than the one it installed is set (`getEditorComponent()`). The frame is optional (without one the editor renders as pi's own), the instance reads the current frame on every render, and keys reach the hooks only while the editor has focus.
- The subclass renders pi's editor `chrome` columns narrower and passes the lines, the layout and the editor's live `borderColor` to `decorate`; below `minWidth` it renders the plain editor. The layout comes from the subclass's `renderTopBorder` and `renderBottomBorder` overrides, not from parsing lines: `bottom` is the index of the line `renderBottomBorder` returned and `scrolled` is whether the top border is an `↑ N more` hint. Lines 0 and `bottom` (the rules) are extended by `chrome` painted rule characters to the full width, the lines between get a one-column left margin (`MARGIN`) and the chevron gutter (the chevron only on the first, and not while scrolled), and lines below the bottom rule (autocomplete) are indented by `left` under the text. No pipes or corners: `chrome` and `left` are the margin plus the gutter width. Mouse events are shifted left by `left` and narrowed by `chrome` before pi's editor handles them, so clicks land on the clicked character.

## Footer

- Replaces pi's footer (`HostUi.setFooter`, tui only) with a block aligned to the composer chevron (`PAD`, one space, the composer margin): context tokens (warning above 70 %, error above 90 %), main cost, model name and window; the session total (main plus every spending source); folder and session name; git branch; thinking level with the `app.thinking.cycle` key; then the other extensions' status texts, without spending's own `pi-spending` status (`SPENDING_STATUS_KEY`), whose figures the block already shows.
- Cost and tokens come only from `spending:totals`: the footer keeps the last payload, so a render reads only cheap live values (`Host.context()`, `model()`, `thinkingLevel()`, `sessionName()`; the adapter memoises `context()` on the session leaf id and the model, as pi's own footer does). Until spending publishes the cost segment and the session-total line are hidden; the session total gets a dim ` (sub)` when `subscription` is set.
- The adapter (`core/adapter/pi-footer.ts`) truncates every line to the width, re-renders on git branch changes and on `refresh()`, and drops the branch subscription when pi disposes the footer; the dim ellipsis is painted on each render, so it follows theme switches.

## Persistence summary

Every file the extensions write lives under pi's agent dir or session dir (`~/.pi/agent` by default; the `sessionDir` setting or `--session-dir` moves session data), except handoff files (OS temp dir) and `worktree: true` agents (checkout under `<cwd>/.pi/worktrees/`, git's `pi-agents/...` branch and `.git/worktrees/` metadata).

- Agents dir (`agentsDirFor` in `extensions/subagents/src/model/paths.ts`) = `<main session file without .jsonl>/agents`, or `<agentDir>/pi-subagents/<session id>/agents` for a session without a file.
- `<agents dir>/<id>/`: `manifest.json` (rewritten on state or worktree change; final counters on close), the child pi session `.jsonl` (with `parentSession` and the prompt record), `result.md`.
- `<OS temp dir>/pi-session-limits/<session id>-handoff.md` (main) and `<OS temp dir>/pi-subagents/<session id>/<agent id>-handoff.md` (agents): handoff files.
- `<cwd>/.pi/worktrees/<id>-<stamp>/`: a worktree agent's checkout, removed when its chain ends unless git refuses (uncommitted changes); its branch stays only if it moved past `base`. `.pi/worktrees/.gitignore` keeps them out of `git status`.
- Main session file: `pi-spending:usage`, `pi-spending:main-offset` and `pi-spending:main-tokens-offset` entries; the new session's seed message after a handoff.
- `<agentDir>`: `pi-subagents.json`, `pi-session-limits.json`, `pi-notifications.json`, `agents/*.md`. `<cwd>/.pi/`: the same settings files and `agents/*.md` (trusted projects only).
- Registry, batches, ledger totals and limit phases live in memory and are lost on reload.

## Cross-cutting

- Errors: user-facing failures become data, not exceptions: a failed agent is a closed record with `error`, tool misuse returns an error result, bad settings or agent files become warnings and are skipped. `startBatch` throws for invalid requests so nothing is half-started.
- Model resolution (`core/adapter/model-resolver.ts`): no request means the main session's model; otherwise exact `provider/id` or id among models with credentials (preferring the session provider, then the default provider), then fuzzy matching by tokens and edit distance within a provider scope, newest version per family. Several families -> `ambiguous`, nothing -> `unknown` with suggestions; both make `run_agent` fail with the candidates. Thinking level: request suffix, then definition, then the main session's level.
- Prompt cache: agents never compact and never get cache warming; their prompt prefix is fixed at spawn.
- Tests: unit tests run against the fakes with no network (`npm run check`, also what CI runs). `*.live.test.ts` spawn real agents under `npm run test:live`, locally only: `PI_LIVE_MODEL=provider/id[:thinking]` is required (the suites fail at once when it or the credentials are missing), and a temporary agent dir holds only copies of the credentials.
